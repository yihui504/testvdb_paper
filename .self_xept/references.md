### 判读：导师期望类型 + 预期 vs 现状映射（2026-07-15）

**导师想要什么类型**（从开题措辞判读）：
- **方法 + 技术**为主（方法 ×4、技术 ×2）
- **工具**为载体（非目的）
- **理论 ×0**（全文无"理论/定理/形式化"——导师没要求纯理论贡献）
- → "工程方法研究"类型：提出方法/技术 + 工具实证 + 论文
- **对心虚点 2/4 的启示**：不必拿"硬核理论创新"的尺子量自己；交付的 source-grounded falsification + 系统实证完全落在预期类型内

**预期 vs 现状映射**：

| 开题预期 | 现状 TestVDB | 满足度 |
|---|---|---|
| 调研分析报告 | bug study / roadmap / VDBMS 缺陷分析 | ✅ |
| 测试用例生成方法 | attack agents（boundary/semantic/state）+ knowledge-extractor | ✅（非核心卖点）|
| 正确性判断技术 | contract oracle + dev-reviewer（source-grounded falsification + multi-anchor）| ✅ **核心满足** |
| 质量保障工具 | TestVDB 20-agent pipeline | ✅ |
| 填补"测试生成" | 111 submissions | ✅ |
| 填补"语义校验" | contract（语义边界的一种）| 🟡 部分 |
| 填补"向量精度验证" | open（soft result-correctness 没做）| ❌ **放弃** |

| 论文 1 篇 | 在写（Round 23）| 🟡 进行中 |

**核心结论**：满足大半预期（判断技术 = 核心）；放弃"向量精度验证"（开题核心痛点之一，但太难、open）；把"正确性判断"从开题宽口径（精度+语义+合规）收窄到 API 合规子集。讲清这个边界 = 不乱、不显"没做完"。
