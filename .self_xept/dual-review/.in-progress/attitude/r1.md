## Reviewer 1 — Objective
> Confidence: 4/5 · Overall: Accept (7.2/10)

**Summary**
TestVDB targets documentation-implementation defects in vector databases—where a system silently accepts inputs that violate its API documentation—by using LLMs to extract behavioral claims from natural-language documentation and generate tests. The authors identify two false-positive failure modes (hallucination in claim extraction, self-preference bias in judgment), show that multi-perspective judging collapses recall, and introduce a source-grounded "dev-reviewer" agent that falsifies LLM verdicts against implementation source. Across three VDBMSs, TestVDB surfaced 107 candidate issues with 49 maintainer-acknowledged true-positive defects (15 fixed via merged PR). On a controlled retrospective of 48 candidates, the dev-reviewer reaches 67% precision and 74% recall against 37% recall without source grounding.

**Strengths**
1. **Clear problem framing.** The distinction between documentation-implementation consistency and result correctness (Section 2) is well-drawn, and the oracle-exclusion argument (Table 1) systematically walks through why deterministic oracles miss this defect class. This is a genuine contribution to the VDBMS testing roadmap's identified challenge of oracle definition.

2. **Solid empirical grounding.** The 49 maintainer-acknowledged true positives across three production VDBMSs (22 Milvus, 13 Weaviate, 14 Qdrant) provide strong evidence that the defect class is real and prevalent. The 15 merged-PR fixes demonstrate practical impact beyond toy systems.

3. **Rigorous false-positive diagnosis.** The two-mode failure analysis (Section 4)—hallucination in extraction, self-preference in judgment—is well-motivated by LLM literature, and the multi-perspective judging baseline (Table 3) provides concrete evidence that voting alone cannot resolve the ambiguity problem. The collapse from ~80% precision to ~15% recall is a compelling empirical result.

4. **Source grounding is a validated contribution.** The three-condition ablation (Table 5) and the controlled retrospective with source grounding disabled (Section 6.2) triangulate the claim: suppressing source access collapses recall from 74% to 19%, while source-grounded falsification alone accounts for 75% of false-positive suppression in the ablation control. This is the paper's strongest technical result.

5. **Bidirectional probe against VDBFuzz is methodologically sound.** The complementarity demonstration—TestVDB reaching a crash-class defect by contract reasoning, VDBFuzz missing a silent-accept defect under its templates—makes the boundary concrete rather than rhetorical (Section 6.3). The root-cause analysis of #9045 (debug_assert skipped in release) is a convincing illustration of why crash-only oracles are structurally incomplete.

**Weaknesses**
1. **[major, fixable]** **Cross-family generalization is unaddressed.** The cross-model re-run with DeepSeek, Qwen-3.8-Max, and LongCat-2.0 shows κ = 0.14–0.51 vs. GLM single-run, with all three families recalling fewer defects (18–56% vs. 85%). Section 6.2 acknowledges "cross-family generalization is an open question," but the abstract and conclusion frame TestVDB as a general solution. This is a validity gap. The authors should either: (a) limit claims to the GLM-5.2 backbone and explicitly state that cross-family transfer is future work, or (b) provide at least one hypothesis (e.g., backbone calibration via consensus cross-checking) for how the approach might generalize. Current framing overreaches the evidence.

2. **[major, fixable]** **Post-hoc operating-point selection without pre-registration.** The 3-run union ensemble is selected post-hoc from four operating points (Table 4), and the Wilson CIs do not account for this selection. The authors acknowledge this ("post-hoc operating point justified by falsifier semantics") and provide a Bonferroni-corrected CI range, but the fundamental problem is that the headline number could be inflated by selection. A cleaner approach would be to pre-register the operating point or to use cross-validation on the 48-candidate set to demonstrate that the 3-run union is not an artifact of the specific sample. The bootstrap validation helps, but it does not fully address selection bias.

3. **[minor, fixable]** **Construct validity: "implementation-as-correct" assumption is under-examined.** Section 7 mentions the limitation but provides no empirical quantification. How many of the 23 by-design or rejected cases were actually documentation errors rather than implementation bugs? The authors state "we did not observe maintainer-rejected confirmed TPs where the documentation itself was wrong," but with only 72 adjudicated submissions (49 TP + 23 by-design/rejected), the sample is small enough that this could be sampling bias rather than evidence. A simple audit—re-reading the 23 rejected issues and counting how many were closed as "wont-fix, docs will be updated" vs. "wont-fix, behavior is correct"—would strengthen the construct validity argument.

4. **[minor, fixable]** **External validity claim is overstated.** Section 7 claims transferability to non-VDBMS REST APIs on structural grounds, with CouchDB and Elasticsearch probes as evidence. However, both mature systems rejected every invalid probe with 400 errors, and the only silent-accept was limit=0/size=0 returning empty result sets—a graceful behavior, not a defect. The authors correctly note this is "probing method portability rather than defect detection," but the abstract and introduction still claim the setting is "not specific to VDBMSs in principle." This is equivocal. Either drop the generalizability claim or provide at least one non-VDBMS defect case. Current evidence shows portability, not generalizability.

5. **[minor, unfixable]** **Recall estimation is absent.** The authors acknowledge "no public ground-truth defect catalog exists" for VDBMSs, so absolute recall cannot be estimated. This is a real limitation, but it means the 74% recall figure is relative (against the 37% baseline), not absolute. The paper would benefit from a sensitivity analysis showing how the results change under different plausible assumptions about the false-negative rate of the dev-reviewer.

**Questions for Authors**
1. The cross-model κ scores (0.14–0.51) suggest substantial model-family dependence. Given this, how should a practitioner choose which backbone to use for a new VDBMS target? Is there any systematic way to predict which backbones will perform well, or is it trial-and-error?

2. On the 3-run union operating point: under what conditions would you recommend the 5-run union instead? The 5-run union reaches 85% recall at 62% precision—trade-off justified if false positives are cheap to triage. What is the cost model that should guide this choice?

3. The 48-candidate retrospective is maintainer-adjudicated but non-random. What biases might this introduce? For example, are candidates where the documentation is ambiguous more likely to be submitted and adjudicated (because maintainers can't easily dismiss them as "won't-fix")?

4. In the CouchDB/Elasticsearch probes, both mature systems rejected every invalid input with 400 errors. Do you think this reflects a maturity difference (older REST APIs have stricter validation) or a architectural difference (general-purpose databases vs. domain-specific VDBMSs)? If the latter, what structural features predict whether silent-accept defects are likely?

5. The cost breakdown (Table 2) shows ~50% of LLM calls are dev-reviewer source-grounding. Have you experimented with caching source-code traces (e.g., memoizing grep results for common parameter names) to reduce this cost? What's the replayability of a full run?
