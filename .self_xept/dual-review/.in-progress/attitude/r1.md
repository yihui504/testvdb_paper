## Reviewer 1 — Objective
> Confidence: 4/5 · Overall: Accept (7/10)

**Summary**
The paper addresses documentation-implementation defects in Vector Database Management Systems (VDBMSs), where systems silently accept inputs violating their API documentation. TestVDB uses LLMs to extract behavioral claims from documentation, generate tests, and confirm defects via a novel dev-reviewer agent that falsifies LLM verdicts against implementation source. The approach yielded 49 maintainer-acknowledged defects across three VDBMSs, with the dev-reviewer improving recall from 37% to 74% on a 48-candidate retrospective.

**Strengths**
1. **Concrete problem definition with clear boundary conditions** (Section 2). The Table 1 exclusion matrix systematically argues why deterministic oracles cannot handle natural-language documentation boundaries, leaving LLMs as the practical oracle. This framing is crisp and defensible.

2. **Well-motivated technical contribution.** The dev-reviewer's three-check falsification (reproducibility, evidence sufficiency, falsifiability) directly addresses the identified failure modes (extraction hallucination, judgment self-preference). The #9255 reversal example (Section 5) concretely demonstrates value.

3. **Strong empirical grounding.** The 48-candidate retrospective with maintainer-adjudicated ground truth, combined with ablation studies (Table 4, source vs. threat-model anchors), provides solid evidence for the source-grounded anchor's contribution. The bidirectional VDBFuzz probe (Section 7.3) is methodologically sound for exploring complementarity.

4. **Honest threat modeling.** The paper acknowledges construct validity limitations (single LLM family, no cross-family robustness), external validity gaps (no Weaviate controlled retrospective, single non-VDBMS case), and post-hoc operating-point selection with appropriate caveats.

**Weaknesses**
1. **[major, fixable]** **Post-hoc operating-point selection weakens RQ2 claims.** The 3-run union ensemble (Table 3, headline numbers) is selected post-hoc across four operating points, yet the Wilson CIs are presented as if this selection were pre-registered. The Bonferroni-corrected CIs mentioned in prose ("roughly [44%, 84%]" and "[51%, 89%]") are not reflected in the table, creating a disconnect between displayed uncertainty and actual uncertainty. The bootstrap CIs ([53%, 83%]/[71%, 96%]) are wider but still do not fully account for the selection effect. Fix: Add a column to Table 3 with Bonferroni-adjusted CIs, or move the bootstrap CIs to the table and explicitly note they are the post-selection uncertainty estimates.

2. **[major, fixable]** **Construct validity threat from single-backbone evaluation needs external validation.** All dev-reviewer results use GLM-5.2; the cross-model re-run (DeepSeek, Qwen, LongCat) shows family-specific verdicts (κ = 0.14–0.51) and lower recall (18–56% vs. 85%), yet the headline performance numbers (67% precision, 74% recall) are presented as general claims about the approach rather than GLM-5.2-specific results. The abstract states "these results use a single LLM backbone (GLM-5.2); cross-family generalization is an open question," but the evaluation section does not consistently flag this limitation when reporting numbers. Fix: Add "(GLM-5.2 backbone)" qualifiers to all RQ2 performance claims in the abstract, introduction, and RQ2 header.

3. **[major, fixable]** **External validity of VDBFuzz comparison is limited.** The systematic VDBFuzz probe on Qdrant v1.18.2 (26,000 requests, 0 of 14 TPs reached) is strong evidence for crash-oracle limitations on silent-accept defects. However, the reverse direction (TestVDB reaching VDBFuzz crashes) relies on two single-controlled cases (size overflow on v1.4.0, #9045/#7967 on v1.18.0) with n=1 each, which the paper acknowledges ("isolate the mechanism on crash-class defects") but then uses to support broader complementarity claims. Fix: Soften the RQ3 framing to separate the robust systematic direction (VDBFuzz → TestVDB TPs) from the exploratory reverse direction (TestVDB → VDBFuzz crashes), or add more crash-class cases.

4. **[minor, fixable]** **Table 1 exclusion matrix could be sharper on "why each misses the residual."** Row 4 (Property-based testing) states "needs a machine-checkable property and an OpenAPI schema; VDBMS endpoints serve no schema that encodes these constraints," but this blurs two separate limitations: (a) PBT needs a formal property (not just schema), and (b) VDBMSs lack OpenAPI. A PBT tool could theoretically synthesize properties from code (e.g., Daikon) even without OpenAPI. The current phrasing suggests the OpenAPI gap is the blocker, when the core gap is the absence of machine-checkable properties from prose documentation. Fix: Rephrase to emphasize "PBT needs a machine-checkable property; VDBMS documentation provides only prose, and no OpenAPI schema encodes these constraints either—two gaps, not one."

5. **[minor, fixable]** **Section 8 (Discussion) portability probe is yield-only.** The CouchDB/Elasticsearch probes confirm pipeline portability (steps run end-to-end) but do not demonstrate defect detection (0 silent-accept defects found). The paper frames this as "probing method portability rather than defect detection," but the placement in Discussion suggests a generalization claim that the data does not support. Fix: Move to a "Future Work" bullet, or explicitly flag as "portability validation only, defect detection untested."

6. **[minor, unfixable]** **Implementation-as-correct assumption bounds falsification but is not empirically validated.** Section 8 states the 15 merged-PR fixes "suggest the implementation-as-correct assumption holds often enough to be useful," but no data is presented on maintainer-rejected confirmed TPs where documentation was wrong (the false-negative rate). This is a fundamental limitation of the source-grounded approach and cannot be fixed without a ground-truth catalog of documentation errors, but it deserves explicit acknowledgment beyond the current brief mention. The abstract could surface this more clearly: "treats implementation as correct; documentation-bug cases would surface as dev-reviewer false negatives, which we did not quantify."

**Questions for Authors**
1. The 3-run union ensemble is justified as the operating point under falsifier semantics ("under-confirmation is costlier than forwarding a false positive for human triage"). However, the 5-run union reaches higher recall (85%) at modest precision cost (62%), and the paper notes "under-confirmation is costlier." Why is 3-run the knee rather than 5-run? Is the 5-point recall gain (74%→85%) not worth the 5-point precision loss (67%→62%) in your triage model? Please clarify the cost model.

2. The cross-model re-run (DeepSeek, Qwen, LongCat) shows severe recall degradation (18–56%) and low agreement (κ = 0.14–0.51). Given that source-grounded falsification is backbone-dependent, what is the path to cross-family robustness? Ensemble across families? Backbone-specific SOP tuning? Or is this accepted as a limitation?

3. The VDBFuzz comparison on Qdrant v1.18.2 is methodologically strong (26,000 requests, systematic probe). However, the paper reports "0 of 14 true positives reached" without detailing what the 14 TPs are. Please confirm: are all 14 silent-accept defects (HTTP 200 responses), or do some crash in v1.18.2? If all are silent-accept, the crash-oracle limitation is structurally guaranteed; if some crash, the 0/14 result is more surprising and worth explaining.

4. The threat model (Section 4) anchors on maintainer-acknowledged by-design and wont-fix patterns, but the paper does not quantify how many false positives the threat-model anchor suppresses beyond the 12-FP/4-TP ablation (6/12 = 50%). What is the threat-model anchor's contribution on the full 48-candidate set? Is it primarily useful for state/concurrency FPs, as suggested?
