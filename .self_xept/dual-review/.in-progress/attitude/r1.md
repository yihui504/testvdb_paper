## Reviewer 1 — Objective
> Confidence: 4/5 · Overall: Accept (7.5/10)

**Summary**
The paper addresses documentation-implementation defects in Vector Database Management Systems (VDBMSs) through TestVDB, an LLM-based oracle that extracts behavioral claims from API documentation and validates them against runtime responses. The authors identify a real gap—existing VDBMS fuzzers detect only crashes, while logical bugs that silently accept invalid inputs escape detection. Their core technical contribution is a source-grounded dev-reviewer agent that mitigates two LLM failure modes: hallucination in claim extraction and self-preference bias in judgment. Evaluation on 107 submitted issues across three VDBMSs (Milvus, Qdrant, Weaviate) yields 49 maintainer-acknowledged true positives (15 fixed), and a controlled retrospective shows the dev-reviewer lifts recall from 37% to 74% against a single-LLM baseline.

**Strengths**
1. **Concrete problem definition** — The paper clearly isolates a defect class (documentation-implementation inconsistency) that existing tools miss, supported by an oracle-exclusion argument (Table 1) that systematically walks through why deterministic oracles (crash, differential, metamorphic, property-based, REST doc/spec-derived) cannot handle natural-language documentation boundaries.
2. **Strong real-world validation** — 107 submitted issues with 49 maintainer-acknowledged true positives (15 merged-PR fixes) across three production VDBMSs. The 68.1% adjudicated yield precision is credible and the merged fixes demonstrate practical impact.
3. **Solid threat diagnosis** — The two failure-mode analysis (extraction hallucination, judgment self-preference) is well-grounded in LLM literature, and the demonstration that multi-perspective judging collapses recall to ~15% (Table 2) is convincing evidence that voting cannot break documentation-ambiguity agreement.
4. **Thorough evaluation design** — The bidirectional reachability probe against VDBFuzz (Section 6.3) concretely shows complementarity: VDBFuzz reaches 0 of 14 silent-accept true positives on v1.18.2, while TestVDB reaches a crash-class defect by contract reasoning on v1.4.0. The 48-candidate retrospective with ablation (Table 5) isolates the source anchor's contribution (75% FP suppression alone).
5. **Reproducibility commitment** — Full artifact (prompts, ground truth, reproduction driver) at https://github.com/yihui504/testvdb-anon under an anonymized repo addresses a key transparency concern for LLM-based tools.

**Weaknesses**

1. **[major, fixable]** **Post-hoc operating point selection inflates recall claim.** The headline 74% recall is the 3-run union ensemble selected post-hoc from four operating points (Table 3). Wilson CIs do not account for this selection. The authors acknowledge this ("flag it as a post-hoc operating point") and provide a Bonferroni-corrected CI (roughly [51%, 89%]) and bootstrap validation ([71%, 96%]), but the core issue remains: without pre-registration, the 74% figure is an upper bound. The paper should either (a) run a fresh validation set at the selected operating point, or (b) prominently frame 74% as "any-confirmed ensemble recall (post-hoc selection)" and present a pre-registered bound (e.g., single-run median 48% with wider CI) as the primary claim. As written, the abstract and introduction foreground 74% without sufficient qualification.

2. **[major, fixable]** **Single-backbone evaluation limits cross-family claims.** All results use GLM-5.2. A cross-model re-run (DeepSeek, Qwen, LongCat) shows verdicts are family-specific (κ = 0.14–0.51), yet the abstract still claims "results use a single LLM backbone (GLM-5.2); cross-family generalization is an open question." This is honest but insufficient for a venue that expects broader validation. The paper should either (a) expand evaluation to include at least one other backbone in the main results, or (b) foreground single-backbone as a primary limitation and remove any implied transferability claims. Currently, the cross-family data is relegated to RQ2's threat-to-validity rather than treated as a core finding.

3. **[major, fixable]** **Source-grounding requirement is under-discussed as a limitation.** Section 7 acknowledges that "source-grounded falsification requires source, so it does not transfer to closed-source VDBMSs" but treats this as a secondary limitation. For a paper positioning itself as a general VDBMS testing approach, the dependence on open-source access is critical. The paper should explicitly scope the contribution: "TestVDB targets open-source VDBMSs where source is available for falsification." Without this scope statement, the work risks being misread as a general solution for all VDBMSs.

4. **[minor, fixable]** **Per-run variance (15–78% recall) is not well-explained.** Figure 3 shows extreme single-run variance, attributed to "some runs are conservative." This is plausible but the mechanism is unclear—what causes a conservative run? Is it sampling variance, LLM temperature, or prompt ambiguity? The paper should either (a) provide a hypothesis for the variance driver, or (b) show that variance is consistent across backbones (not just GLM-5.2). Without this, the high variance undermines confidence in the single-run baseline.

5. **[minor, fixable]** **Implementation-as-correct assumption needs more empirical support.** Section 7 states "the 15 merged-PR fixes suggest the implementation-as-correct assumption holds often enough to be useful, without guarantee." This is reasonable evidence but the paper should also report whether any maintainer-rejected candidates were confirmed TPs by the dev-reviewer—such cases would directly falsify the assumption. The authors state "we did not observe maintainer-rejected confirmed TPs where the documentation itself was wrong" but this is buried in limitations. Move this to the main evaluation as a validation point.

**Questions for Authors**
1. What is the primary mechanism behind per-run variance (15–78% recall)? Is this sampling noise, temperature sensitivity, or prompt ambiguity? Have you characterized which parameter settings trigger conservative vs. liberal runs?
2. For the 49 maintainer-acknowledged TPs, how many were adjudicated by the dev-reviewer vs. the initial judge? The paper states the dev-reviewer reaches 67%/74% precision/recall on the 48-candidate retrospective, but it's unclear whether the real-world yield (49/107) used the dev-reviewer or the baseline pipeline.
3. The CouchDB/Elasticsearch probe (Section 7) found no silent-accept defects because both APIs "validate more strictly." Did you characterize why VDBMSs specifically under-validate? Is this domain-specific (vector search parameter complexity) or a maturity difference (older APIs vs. newer VDBMSs)? This would clarify the scope of where TestVDB is applicable.

**Scores** — Soundness: 4/5 | Significance: 4/5 | Novelty: 4/5 | Presentation: 4/5 | Overall: Accept

**Verdict Rationale**
Accept. The paper addresses a real problem with a well-motivated approach and strong empirical validation. The 49 maintainer-acknowledged defects (15 fixed) are credible evidence of practical impact, and the source-grounded falsification contribution is technically sound. The post-hoc operating point selection and single-backbone evaluation are serious but fixable—neither is fatal given the paper's transparency about both limitations. With minor revisions to foreground the post-hoc nature of the headline 74% recall and to better scope the single-backbone and source-access requirements, this work meets the bar for an SE venue of ISSTA/ICSE/FSE tier.
