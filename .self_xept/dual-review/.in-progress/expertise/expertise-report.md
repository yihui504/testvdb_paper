## Reviewer 1: Domain Expert

**Overall Recommendation:** Weak Accept

### Summary
TestVDB targets documentation-implementation defects in Vector Database Management Systems (VDBMSs)—cases where a VDBMS silently accepts inputs that violate its API documentation (e.g., accepting `nprobe=0` when documentation specifies `[1, 16384]`). The paper argues that because documentation is natural-language prose, deterministic oracles (crash-based, differential, metamorphic, property-based, and REST-API spec-derived) cannot adjudicate these accept/reject decisions, leaving an LLM as the practical oracle. The authors present a four-stage pipeline using LLMs to extract behavioral claims from documentation, generate tests, execute them in sandboxed Docker environments, and confirm defects via a "dev-reviewer" agent that grounds verdicts in implementation source. TestVDB surfaced 107 issues across Milvus, Qdrant, and Weaviate; maintainers acknowledged 49 as true positives (15 fixed via merged PR). A 48-candidate retrospective shows the dev-reviewer reaches 67% precision and 74% recall against a 37% recall baseline without source grounding. A bidirectional probe against VDBFuzz shows complementary coverage.

### Core Strengths
- **S1:** Defect class has clear practical relevance — see 2.2, 5.1. Documentation-implementation defects corrupt query semantics in RAG stacks and represent a genuine gap in existing VDBMS testing (which focuses on crashes).
- **S2:** Source-grounded falsification is a principled response to LLM reliability challenges — see 4.1, 4.2. The dev-reviewer's three-check design (independent reproducibility, evidence sufficiency, falsifiability) directly addresses hallucination and self-preference bias, and the recall lift (37% → 74%) substantiates its value.
- **S3:** Oracle exclusion argument is well-structured — see 1.1. Table 1 systematically walks through why each deterministic oracle candidate misses the documentation-implementation residual, providing clear motivation for the LLM-derived approach.
- **S4:** Multi-vendor empirical validation demonstrates real-world impact — see 5.1. 49 maintainer-acknowledged defects across three production VDBMSs (with 15 merged-PR fixes) is strong evidence that the defect class is not merely theoretical.

### Core Weaknesses
- **W1:** Cross-family LLM generalization is unaddressed — see 5.2. All results use a single LLM family (GLM-5.2); the paper explicitly shows verdicts are family-specific (κ = 0.14 DeepSeek, κ = 0.51 LongCat), undermining claims about LLM-derived oracles as a general solution.
- **W2:** External validation beyond VDBMSs is anecdotal — see 1.1, 6. The CouchDB mini-case is described as probing portability rather than defect detection, and no additional non-VDBMS targets are tested, weakening transferability claims to "REST APIs without OpenAPI."
- **W3:** Post-hoc operating point selection on retrospective data — see 5.2. The 3-run ensemble is selected post-hoc across four operating points, and Wilson CIs do not account for this selection, overstating statistical confidence.
- **W4:** Comparison against REST-API oracle tools is shallow — see 2.2, 7. The paper claims SATORI, AGORA+, and MASTOR operate in a "low-ambiguity regime" and exclude the "ambiguous-prose regime," but this boundary is asserted rather than empirically validated.

### Detailed Assessment

#### 1. Significance — Adequate
- **1.1** The problem is real and under-served. VDBMS testing has focused on crash-oracle fuzzing (VDBFuzz), yet the empirical bug study (cited as bugstudy25) attributes >50% of VDBMS defects to functional failures that produce no crash. Documentation-implementation defects are a concrete subset of these, and the 49 maintainer-acknowledged cases across three production systems demonstrate practical impact.
- **1.2** However, the scope is narrower than the framing suggests. The paper explicitly excludes result correctness (ANN recall, ranking) and bounds the approach to documentation-implementation consistency. This is a reasonable boundary, but the paper's motivation occasionally slides into claiming broader VDBMS testing coverage (e.g., "most of their defects are logical bugs") than the tool actually delivers. The significance is adequate but not Excellent because the contribution is niche within VDBMS testing.

#### 2. Novelty — Adequate
- **2.1** Checked the delta against VDBFuzz (fetched). The paper correctly characterizes VDBFuzz as crash-oracle-only and uses a bidirectional probe to show complementarity: TestVDB reaches VDBFuzz's integer-overflow crash via contract reasoning (size=2^63), while VDBFuzz misses TestVDB's silent-accept defect (#9045) under current templates. The characterization is accurate and the novelty delta is clear.
- **2.2** Checked the delta against SATORI (fetched: Alonso et al., ASE 2025). SATORI generates test oracles from OpenAPI specifications using LLMs to infer expected behavior from response field properties. The paper claims SATORI operates in a "low-ambiguity regime" because it assumes every relevant constraint has an OpenAPI field (type, format, minimum, maximum), whereas VDBMS documentation carries constraints in prose with no schema field. This characterization is directionally correct—SATORI's extraction does rely on structured schema elements—but the paper does not empirically test SATORI on VDBMS endpoints to confirm it fails in this regime. The novelty delta is adequately justified but not rigorously validated.
- **2.3 [major, fixable]** Missing related work: AugmenTest (fetched: Hossain et al., PACM Softw. Eng. 2024). AugmenTest infers oracles from available documentation using LLMs and shows documentation quality directly impacts oracle correctness. The paper cites Doc2OracLL (a close cousin) but does not cite AugmenTest, which is directly relevant to the documentation-interpretation regime. Positioning TestVDB's novelty delta against AugmenTest (e.g., does AugmenTest handle VDBMS-style ambiguous prose, or does it assume higher-quality documentation?) would strengthen the Related Work section.
- **2.4** Checked the delta against AGORA+ (fetched: Alonso et al., TOSEM 2025). AGORA+ infers invariants from execution traces and generates oracles for REST APIs. The paper correctly notes AGORA+ cannot reach inputs the traffic did not exercise, but it does not acknowledge that AGORA+ could potentially detect documentation-implementation violations if those violations manifest as output invariants in observed traffic. The claim that AGORA+ "misses the documentation-implementation residual" is plausible under-specified but not empirically demonstrated.
- **2.5** Checked the delta against MASTOR (fetched: Deng et al., arXiv 2026). MASTOR reads implementation source to generate semantic oracles. The paper correctly notes MASTOR "reads source to generate oracles that encode implemented behavior and so cannot detect a gap between documentation and code." This characterization is accurate, and the novelty delta is clear: MASTOR encodes what the code does, TestVDB checks whether documentation matches it.
- **2.6** Checked the delta against Toradocu (fetched: Peters & Parnas, ISSTA 1994). Toradocu pioneered oracle extraction from natural-language documentation using NLP and pattern matching for Javadoc @throws comments. The paper correctly notes Toradocu's deterministic extraction handles simple syntactic patterns but acknowledges false positives from extraction failures. TestVDB's use of LLMs for semantic interpretation is a genuine advance over Toradocu's pattern-based approach, and the paper adequately positions this delta.

#### 3. Soundness — Weak
- **3.1** The RQ1 yield results are sound. 107 submitted issues with 49 maintainer-acknowledged true positives is a reasonable prima facie validation, and the paper provides appropriate statistical context (Wilson CIs, worst-case bound treating pending submissions as false positives). The 15 merged-PR fixes across three production VDBMSs are strong evidence of real-world impact.
- **3.2 [major, fixable]** RQ2's post-hoc operating point selection weakens the soundness claim. The paper selects the 3-run ensemble from four operating points (single run, 3-run union, 5-run union, 5-run majority) and reports it as the headline result. The Wilson CIs do not account for this selection, overstating statistical confidence. The paper acknowledges this as a limitation but does not provide a corrected analysis (e.g., Bonferroni-adjusted CIs for all operating points, or a pre-registered protocol). A reviewer should not accept the 74% recall claim without discounting for selection bias.
- **3.3 [major, fixable]** Cross-family LLM generalization is unaddressed, undermining soundness of the LLM-derived oracle claim. The paper shows that verdicts are family-specific (κ = 0.14 DeepSeek, κ = 0.51 LongCat vs. GLM single-run) but does not provide a corrected analysis or a path to cross-family robustness. If the approach only works with GLM-5.2, it is a tool-specific contribution, not a general LLM-derived oracle approach. The paper treats this as an open question, but it directly impacts the soundness of the central claim.
- **3.4** The dev-reviewer ablation (source alone: 75% FP suppression, threat-model alone: 50%, union: 91%) is methodologically sound and provides good evidence for the contribution of each anchor. The three-condition design is appropriate for isolating the source-grounded anchor's contribution.
- **3.5 [minor, fixable]** The VDBFuzz bidirectional probe is under-specified. Each direction is n=1, and the paper treats these as "hypothesis-generating controlled cases rather than a generalized result." This is appropriate humility, but the claim that VDBFuzz "misses a TestVDB silent-accept defect under its current templates" is ambiguous: is this a limitation of VDBFuzz's crash-oracle approach (fundamental) or a limitation of its current template coverage (incidental)? The paper acknowledges this ambiguity but does not resolve it, leaving the comparison less crisp than it could be.

#### 4. Verifiability — Adequate
- **4.1** The paper states the artifact will be released at a persistent URL upon acceptance, including prompts, target versions, and per-token accounting. The four-stage pipeline description (Section 3) is detailed enough to follow conceptually, though some implementation details (e.g., specific agent prompts, the novelty gate logic) are deferred to the artifact.
- **4.2 [minor, fixable]** The paper does not provide a reproducibility package for the LLM calls. The paper reports "roughly $10^4$ LLM calls and roughly $10 per target at current API pricing" but does not specify the exact prompt templates, sampling parameters, or API versions used. For a paper where LLM behavior is central to false-positive suppression, this is a verifiability gap. The artifact承诺 mitigates this, but reviewers should not need to wait for acceptance to assess core experimental parameters.
- **4.3** The Docker-pinned target versions (Milvus 2.6.19, Qdrant v1.18.2, Weaviate v1.38.2) are specified, which is good for reproducibility. The paper does not specify Docker image tags or commit hashes for the VDBMSs themselves, which could affect reproducibility if the images are updated.
- **4.4** The statistical reporting (Wilson CIs, worst-case bounds) is adequate and appropriate for the scale of the study. The paper correctly does not over-claim statistical significance where it is not warranted (e.g., the bidirectional probe is n=1 per direction).

#### 5. Presentation — Adequate
- **5.1** The structure is logical and the writing is generally clear. The motivation (Section 1), background (Section 2), approach (Section 3), false-positive problem (Section 4), dev-reviewer (Section 5), and evaluation (Section 6) follow a coherent narrative arc.
- **5.2 [minor, fixable]** The figures are helpful but could be sharper. Figure 1 (pipeline) clearly sketches the four stages and the dev-reviewer's role. Figure 2 (dev-reviewer checks) is clear but visually busy; a simplified version with fewer arrows would improve readability. Table 1 (oracle exclusion) is excellent—a clear, systematic justification for the LLM-derived approach.
- **5.3 [minor, fixable]** The Related Work section is well-organized by topic (VDBMS testing, REST-API oracle generation, LLM-as-judge reliability, documentation-derived oracles) but misses AugmenTest (see 2.3). The discussion of Toradocu is appropriate, and the comparison with AGORA+, SATORI, and MASTOR is directionally correct but could benefit from more empirical validation.
- **5.4** The language is generally polished, with minor occasional awkward phrasing (e.g., "The boundary we draw, between problems where structured-source extraction suffices and those where natural-language documentation forces LLM interpretation, marks where an LLM-derived oracle needs an independent falsifier" is grammatically correct but stylistically dense).

## Reviewer 2: Area Specialist

**Overall Recommendation:** Weak Accept

### Summary
TestVDB targets documentation-implementation defects in Vector Database Management Systems (VDBMSs)—cases where a VDBMS silently accepts an input that violates its API documentation. Because the documented boundary is natural-language prose, deterministic oracles cannot adjudicate these accept/reject decisions, leaving an LLM as the practical oracle. The authors instantiate a four-stage pipeline (claim extraction, test generation, sandboxed execution, defect confirmation) and diagnose two false-positive failure modes (hallucination in extraction, self-preference in judgment). A multi-perspective judging baseline raises precision but collapses recall, so they introduce a dev-reviewer agent that acts as a source-grounded falsifier. TestVDB surfaced 107 candidate issues across three VDBMSs; maintainers acknowledged 49 as true-positive defects (15 fixed via merged PR). On a 48-candidate retrospective, the dev-reviewer reaches 67% precision and 74% recall (3-run ensemble), versus 37% recall without the source anchor.

### Core Strengths
- **S1:** Problem relevance and oracle clarity — the paper targets a prevalent defect class (logical bugs that do not crash, >50% of VDBMS defects per cited bug study) and provides a crisp exclusion argument (Table 2) for why an LLM is the practical oracle for the documentation-implementation residual. See 1.1, 2.1.
- **S2:** Multi-family generalization test — the cross-model pilot (DeepSeek, LongCat-2.0) showing verdict is family-specific (κ = 0.14, 0.51) is the right validation experiment for an LLM-derived oracle, and the authors correctly frame cross-family robustness as an open question. See 4.3.
- **S3:** Bidirectional probe against VDBFuzz — the Qdrant reachability study (#9045 silent accept vs. VDBFuzz's crash-only templates, and TestVDB reaching the integer-overflow crash by contract reasoning) provides concrete evidence of complementary coverage. See 3.3.

- **W1:** Retrospective selection and operating-point post-hoc claim — the 48-candidate retrospective is maintainer-adjudicated but non-random, and the 3-run union ensemble is selected post-hoc across four operating points; the Wilson CIs do not account for this selection, weakening the headline precision/recall claim. See 3.2.
- **W2:** Limited external validation beyond VDBMSs — the single CouchDB case study probes method portability but does not establish defect-detection efficacy in a non-VDBMS setting, leaving the transferability claim structurally only. See 4.2, 5.1.

### Detailed Assessment

1. **Significance** — Adequate
   - **1.1** The problem scope is well-motivated: the paper cites an empirical bug study attributing ~43% of VDBMS bugs to incorrect behavior and notes that more than half of VDBMS bugs manifest as functional failures rather than crashes (Section 1). The 49 maintainer-acknowledged true positives across three production VDBMSs (15 fixed via merged PR) show practical impact. The exclusion argument in Table 2 is crisp: each deterministic oracle candidate (crash, differential, metamorphic, property-based, REST-doc-derived) is mapped to the defect class it reaches and the structural reason it misses the documentation-implementation residual. This establishes that LLM-derived oracles are the practical option for this regime, not a choice made for convenience.
   - **1.2 [major, fixable]** The significance claim is bounded by the narrowness of the defect class and the limited external validation. The paper targets documentation-implementation consistency, not result correctness (ANN recall, ranking), which is out of scope and explicitly left open (Section 2). The external validity threat (Section 4.2) acknowledges that transfer to documentation regimes beyond VDBMSs is "claimed on structural grounds only and is not empirically tested." The CouchDB case study (Section 5) probes method portability but found no silent-accept defects (CouchDB rejected all clearly-invalid probes with 400 errors; the only silent accept was `limit=0`, a graceful behavior). This sharpens the motivation (CouchDB validates inputs more strictly) but does not establish defect-detection efficacy outside VDBMSs. One additional non-VDBMS case study where the method surfaces real defects would substantially strengthen the transferability claim.

2. **Novelty** — Adequate
   - **2.1** The core novelty is threefold. First, the problem framing: documentation-implementation defects as a prevalent VDBMS target class, formalized as consistency with natural-language documentation. Second, the diagnosis of two false-positive failure modes (hallucination in extraction, self-preference in judgment) and the demonstration that multi-perspective judging is insufficient (Section 3). Third, the source-grounded falsifier design: the dev-reviewer breaks self-preference by using implementation source, not the same family's prior claim, as ground truth. The Related Work (Section 6) clearly situates the contribution relative to REST-API oracle tools (AGORA+, SATORI, MASTOR), which operate in a low-ambiguity structured-source regime (OpenAPI, traces, source-as-oracle) and do not enter the ambiguous-prose regime.
   - **2.2 [minor, fixable]** The Related Work coverage is adequate for the structured-source REST-API line and the LLM-as-judge reliability line, but the documentation-derived oracle line could be strengthened. Toradocu (Javadoc `@throws` to assertions via NLP/pattern matching) is cited as pioneering oracle extraction from natural-language documentation, but the paper does not explicitly discuss whether TestVDB's LLM-based extraction could be augmented with Toradocu-style deterministic pattern matching for simple syntactic constraints (e.g., "must be at least 1" patterns) to reduce hallucination surface. Doc2OracLL (documentation quality impacts oracle correctness) is cited, but the paper does not discuss whether documentation quality metrics could prioritize or weight extraction confidence. AugmenTest (inferring oracles from available documentation) is mentioned, but the delta is not explicitly contrasted: AugmenTest uses the LLM as the final semantic arbiter verified through runtime behavior; TestVDB uses implementation source as an independent verification source. A more explicit delta table or paragraph would strengthen the novelty positioning.

3. **Soundness** — Weak
   - **3.1** The RQ2 evaluation design is fundamentally sound: a controlled 48-candidate retrospective (27 TP, 21 FP/rejected) with maintainer adjudication as ground truth, comparing three configurations (single-LLM baseline, multi-perspective judging, dev-reviewer with source grounding). The ablation on a 12-FP/4-TP control (Table 4) isolates the dev-reviewer's two anchors (source-grounded, threat-model) and shows their union suppresses 11/12 FPs while retaining all 4 TPs. The source-off ablation (Section 3.2) demonstrates source grounding's contribution: recall drops from 74% to 19% overall, and from 80% to 5% on Milvus (where parameter validation lives in source). This is a strong isolation result. The multi-family generalization test (DeepSeek, LongCat-2.0) showing verdict is family-specific (κ = 0.14, 0.51) is the right validation experiment for an LLM-derived oracle, and the authors correctly flag cross-family robustness as an open question rather than claiming it.
   - **3.2 [major, fixable]** The headline precision/recall claim (67%/74% for the 3-run union ensemble) is weakened by post-hoc operating-point selection and retrospective selection bias. The 3-run union is selected across four reported operating points (Table 3: single-run per-run band, 3-run union, 5-run union, 5-run majority) as "the knee of the precision-recall trade-off at modest reproducibility cost." The authors flag it as post-hoc ("justified by falsifier semantics, not a pre-registered rule") and note that the Wilson CIs do not account for this selection. A Bonferroni correction (α=0.05/4) would widen the 3-run precision CI to roughly [44%, 84%] and recall CI to [51%, 89%], which the authors state does not change the qualitative claim. However, the selection also weakens the comparability to the single-LLM baseline and multi-perspective judging, which are not post-hoc selected operating points. A pre-registered analysis plan or a held-out validation set would strengthen the headline claim.
   - **3.3 [major, fixable]** The 48-candidate retrospective is maintainer-adjudicated but non-random, and the paper does not address selection bias in how candidates entered the set. The threats to validity (Section 4.1) acknowledge "the 48-candidate retrospective is maintainer-adjudicated but non-random, and we did not pre-register the candidate set." However, there is no discussion of whether the adjudication process itself (e.g., maintainer workload, issue prioritization) introduced bias toward certain defect classes or vendors. A capture-recapture analysis or an explicit sampling frame would help bound generalizability.
   - **3.4 [minor, unfixable]** The source-off ablation (Section 3.2) is a single deterministic run, not a full ensemble. The recall drop (74%→19% overall, 80%→5% on Milvus) is a strong isolation signal, but given the high single-run variance reported (15–78% recall across five independent runs), the magnitude of the drop may be sensitive to which run is chosen as the baseline. The authors note the configuration is deterministic (without source access, the dev-reviewer has no stochastic steps), so variance should be lower, but this is not explicitly verified. Reporting the per-run band for the source-off configuration (as done for the single-LLM baseline) would clarify whether the 19% recall is stable or a run-dependent outlier.

## Reviewer 3: General Reviewer

### Summary

This paper introduces TestVDB, a system for detecting documentation-implementation defects in Vector Database Management Systems (VDBMSs). These defects occur when a VDBMS silently accepts inputs that violate its API documentation (e.g., accepting `nprobe=0` when documentation specifies `[1, 16384]`). ### Detailed Assessment

1. **Significance** — Adequate

The oracle-exclusion argument in Section 2 (Table 2) systematically walks through why deterministic oracles (crash, differential testing, metamorphic relations, property-based testing, REST-API tools) miss the documentation-implementation residual. This leaves LLMs as the practical oracle, creating the reliability problem that TestVDB addresses. The framing is clear and the practical impact is established through 15 merged-PR fixes across production systems.
   - **1.2 [major, unfixable]** External validation is limited. RQ3's comparison with VDBFuzz is on Qdrant only ($n=1$ per direction), and Section 6.1 states that generalization to Weaviate is "yield-only" (Table 3 shows 13 acknowledged defects but no controlled retrospective). The non-VDBMS case study (Apache CouchDB) is a single-point probe that surfaced no silent-accept defects, demonstrating portability but not external validity. The paper explicitly acknowledges this as a limitation and future work, but the strength of the significance claim is bounded by this narrow validation scope.

2. **Novelty** — Adequate (provisional)

TestVDB's novelty is not source-grounded falsification per se (MASTOR also reads source), but rather targeting the documentation-implementation gap in the ambiguous-prose regime. The current phrasing ("SATORI's extraction assumes every relevant constraint has a corresponding OpenAPI field") implies this is an assumption SATORI makes about the world rather than a design boundary; sharper wording would strengthen novelty positioning. This is fixable by clarifying the regime boundary.
   - **2.2** The dev-reviewer's three-check falsification (independent reproducibility, evidence sufficiency, falsifiability against source) is a sound technical contribution. Section 4 presents this clearly, with Figure 3 illustrating the sequential filtering logic. The approach of using source as an independent ground truth to break LLM self-preference is well-motivated and distinct from prior LLM-as-judge work that relies on runtime behavior (compilation feedback, differential execution) rather than static source analysis.

However, the statistical rigor is limited by the lack of pre-registration and the small sample size (48 candidates, 27 TP/21 FP).
   - **3.2 [major, fixable]** The RQ3 bidirectional probe against VDBFuzz is methodologically sound but under-powered. Each direction is $n=1$ (TestVDB reaching VDBFuzz's crash on Qdrant v1.4.0; VDBFuzz missing TestVDB's silent-accept defect on v1.18.0). The paper treats these as "hypothesis-generating controlled cases rather than a generalized result," which is appropriate framing given the single-point data. However, the weakness is that VDBFuzz's template suite is not fully characterized—we do not know whether the `wait=false` path is absent due to an oversight or a deliberate design choice. This is fixable by expanding the probe to more targets or providing deeper analysis of VDBFuzz's template coverage gaps.
   - **3.3** The threat-model anchor's instability on state and concurrency false positives (Table 5: 50% FP suppression, "unstable on state and concurrency FPs") is acknowledged but not deeply explored. The paper notes that the threat-model anchor "adds coverage on by-design patterns that source grounding alone reads as implementation choices," which suggests the anchor is capturing real signal, but the instability implies interaction effects that are not fully diagnosed. This does not undermine the core claim (source grounding is the dominant contributor), but it leaves a gap in understanding the failure modes.

4. **Verifiability** — Excellent
   - **4.1** The paper provides sufficient information to understand the TestVDB pipeline. Section 3 describes each stage (claim extraction, test generation, sandboxed execution, defect confirmation) with enough detail to follow the flow. Figure 1 illustrates the pipeline architecture. The dev-reviewer's three-check process (Section 4) is clearly specified, and the example path for issue #49823 (Section 3) shows the end-to-end flow from documentation to source cross-check.
   - **4.2** The paper states that "the full prompts, target versions, and per-token accounting are in the artifact, which we will release at a persistent URL upon acceptance" (Section 3). The specific VDBMS versions are reported (Milvus 2.6.19, Qdrant v1.18.2, Weaviate v1.38.2), and the Docker-based sandboxing approach is described. The 48-candidate retrospective is described as "maintainer-adjudicated" with a 27 TP / 21 FP split, though the individual candidate IDs are not listed in the paper. The artifact commitment and version pinning are sufficient for verifiability at the paper level.

5. **Presentation** — Adequate
   - **5.1** The paper is well-structured and clearly written. The Introduction establishes the problem space and the oracle-exclusion argument upfront. The four-stage pipeline is presented in logical order (Section 3), with the false-positive problem (Section 4) motivating the dev-reviewer solution before the evaluation (Section 5). The Related Work (Section 6) is organized by topic area (VDBMS testing, REST-API oracles, LLM-as-judge, documentation-derived oracles) and connects each line to TestVDB's contributions.
   - **5.2 [minor, fixable]** Table 4 (dev-reviewer operating points) reports per-run bands as "44--65%" for accuracy, "50--73%" for precision, and "15--78%" for recall, but the text does not state the sample size for the per-run distribution. The caption says "five independent runs" but the table header does not explicitly label this, requiring inference. This is a minor presentational issue that could be clarified by adding "$N=5$" to the caption or header.
   - **5.3 [minor, fixable]** The paper uses "we" throughout (e.g., "We instantiate this as TestVDB," "We evaluate TestVDB on three VDBMSs") but also switches to passive voice in some evaluation sections ("TestVDB surfaced 107 candidate issues"). The voice inconsistency is minor and does not affect readability, but standardizing to one style (either consistent "we" or consistent passive) would improve polish.
