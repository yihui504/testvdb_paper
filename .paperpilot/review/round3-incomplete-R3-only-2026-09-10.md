## Reviewer 3: General Reviewer

**Overall Recommendation:** Weak Accept

### Summary

The paper targets *documentation-implementation bugs* in VDBMSs: cases where the system silently accepts an input or behaves in a way its own API prose forbids (e.g., Milvus accepting `nprobe=0` although the documentation declares [1, 16384]). Because the expectation must be read from natural-language prose, the paper argues every deterministic oracle candidate (crash, differential, metamorphic, property-based, spec-derived) is structurally excluded, forcing an LLM-derived oracle — which imports a false-positive problem, since the same LLM writes and judges the oracle. TestVDB answers with a four-stage pipeline (spec extraction, pre-bound test generation, sandboxed execution, and a confirmation stage that splits an evidence builder from a chain auditor and grounds verdicts in the implementation source plus maintainer cognition). On Milvus, Qdrant, and Weaviate, maintainers confirmed 51 of 81 adjudicated submissions (23 fixed via merged PRs). A blinded three-run re-adjudication of the full 81-candidate pool shows the contract core suppresses 87–90% of false positives at 88.9% verdict agreement but recalls only 0.196–0.333; adding source forensics and cognition lifts majority-vote recall to 0.373 with all 30 false positives intercepted, and an independent source-only arm (recall 0.333) locates source grounding as the dominant contributor. A bidirectional probe against VDBFuzz shows the two oracles reach disjoint bug classes.

### Core Strengths

- **S1:** A substantial, externally validated yield: 51 maintainer-confirmed bugs with 23 merged fix PRs, and a fix-PR audit showing all 23 modify implementation code and none is documentation-only — see 1.1, 3.1.
- **S2:** Unusually careful measurement design for an LLM-oracle paper: blinded three-run re-adjudication of the whole pool, Wilson CIs, exact McNemar tests, a disclosed leakage audit of the cognition files, and internal figures that close to the digit — see 3.2.
- **S3:** Honest, mechanism-level attribution rather than score inflation: the paper reports its own low blinded recall (0.373), separates the source-only arm to locate the dominant contributor, and exposes the re-aggregation trap that inflates D-only recall — see 3.2, 3.3.
- **S4:** The oracle-exclusion analysis (Table 1, Section 2.4) is a clear conceptual contribution that delimits exactly where an LLM oracle is forced — see 1.2.

### Core Weaknesses

- **W1:** Both headline evaluations run on a submission-filtered, author-screened pool: submission decisions had no deterministic rule, so the automated stage's recall and suppression on the raw pipeline stream are unknown, and the paper quantifies the unsubmitted residue only loosely — see 3.3.
- **W2:** Key procedural detail is absent from the text and the replication artifact is not yet reachable: tested versions for Milvus and Weaviate are never stated, the frozen-pack assembly protocol is unspecified, and no snapshot identifier pins the GLM-5.2 backbone — see 4.2, 4.3, 4.4.
- **W3:** The confirmation mechanism is a bundle whose aggregation rule (by-design veto / contract confirm / source-absence rescue) is reported without any sensitivity analysis, and the operational stage's Neutral route sits outside all reported automated rates — see 3.5.

### Detailed Assessment

1. **Significance** — Adequate
   - **1.1** The submission ledger (Table 2, Section 5.2) reports 51 confirmed real bugs (63.0% of 81 adjudicated) across three production VDBMSs, with 23 fixed via merged PRs, 18 open with acknowledgment, and only 7 closed unfixed. Yield of this size, validated by upstream actions on widely used systems, is meaningful practical impact for a testing technique.
   - **1.2** The oracle analysis (Table 1; Sections 2.3–2.4) walks each deterministic-oracle candidate through the structural reason it cannot anchor an expectation in system-level prose. This is reusable analysis: it tells the field precisely which residual forces an LLM and where an independent falsifier is then required.
   - **1.3 [minor, fixable]** The impact is bounded by the paper's own numbers: blinded automated recall is 0.373 (Section 5.2), so autonomous reach is modest and the operational yield depends on the human–machine loop the ledger measures. The paper scopes its claims accordingly, but the abstract's "51 confirmed" headline should not be read as automated yield; a one-line reminder there of the author-in-loop nature would help.
2. **Novelty** — Adequate *(provisional: I surveyed no literature for this review; the rating rests on the paper's own positioning)*
   - **2.1** Within the paper's own account, the claimed delta is specific and well-argued: the *anchor inversion* — prose as ground, implementation as falsifier — against MASTOR (source-derived oracles), CASCADE (falsifier generated from the same documentation), and Metamon (an LLM judge whose falsifier is another LLM question) (Section 7). The quoted CASCADE failure mode (generated code and tests sharing a false assumption) is used precisely to motivate the source-grounding anchor.
   - **2.2 [minor, fixable]** The individual components are each established in the paper's own related work: doc-derived oracles (@tComment, JDoctor, DocTer, LLM generators), LLM-judged oracles (Metamon, RBCTest), and a builder/auditor split (MASTOR's ChallengerAgent). The contribution is therefore composition plus anchor change; Section 7 argues this honestly, but the delta is incremental on those premises, and I cannot verify from the text alone that no prior system anchors expectations in system-level untagged prose (see Q5).
   - **2.3 [minor, fixable]** The "pre-bound strategies" device (Section 4.3) — deterministically binding strategies instead of letting the LLM choose — is presented as a reliability contribution, but the registry and its trigger mappings are never described in the text, so neither its novelty nor its auditability claim can be assessed from the paper.
3. **Soundness** — Adequate
   - **3.1** The ground-truth protocol is stronger than typical: maintainer labels plus merged-fix PRs, a fix-nature classification showing 23/23 fix PRs modify implementation code with none documentation-only, and a validation of that classifier against the disproved #9149 (Section 5.2, "Fix nature"), whose PR it correctly identifies as test-only.
   - **3.2** The RQ2 measurement (Tables 4–6, Section 5.2) is rigorous and internally consistent: I recomputed the per-run suppression (26/30 = 0.867, 27/30 = 0.900), the majority recalls (11/51 = 0.216, 19/51 = 0.373, 17/51 = 0.333), all quoted Wilson intervals, the precision figures (17/21, 12/16, 11/15, 17/18), and the exact McNemar p-values (16 vs 7 → 0.093; 17 vs 5 → 0.017; 11 vs 8 → 0.648); all close exactly, and the discordant counts are consistent with the per-arm confirm counts over all 81 cases. The cognition-file leakage audit (six candidate-anchored entries removed, no verdict change) and the stratification showing packs without contract rows recall no worse (Table 5) are exactly the checks this design needs.
   - **3.3 [major, fixable]** The 81-candidate pool is submission-filtered: authors decided per candidate after novelty screening and manual review with no deterministic rule (Section 5.2, penultimate paragraph). All recall and suppression rates therefore characterize the confirmation stage on an author-curated, presumably easier-than-stream pool, and the size of the unsubmitted residue ("the remainder are either re-confirmations ... or unsubmitted findings") is not quantified. The paper argues the bias direction for suppression and calls recall a lower bound on misses, which is coherent, but the generalization of the RQ2 numbers to the automated stream remains unmeasured (see Q2).
   - **3.4 [minor, fixable]** Ground truth is maintainer adjudication, itself fallible and incomplete: 49 submissions are unadjudicated and excluded, and one fixed-TP flipped under the authors' own seven-version re-probe (#9149, Section 6). Both are disclosed; the residual risk is that undisputed labels in the pool share systematic biases with the pipeline (both derive from the same projects' maintainer cultures).
   - **3.5 [minor, fixable]** The full-stage configuration aggregates perspectives by a priority rule (in-source by-design veto; contract confirm; source-absence rescue; Section 5.2). No alternative aggregation is reported, so the 1.000-suppression / 0.373-recall operating point is one un-calibrated choice; and the operational stage's Neutral route (Section 4.5) is excluded from every automated rate, so the deployed configuration's automated-only yield is never directly measured.
   - **3.6 [minor, fixable]** RQ3 (Section 5.4) is structurally sound on the silent-accept class (a crash oracle cannot fire on HTTP 200 by construction), and the full-coverage run (205 templates, 50.8 min) strengthens the 0/7 and zero-defect results beyond a budget artifact; but the sampled probe's budget is author-set ("a bounded sampled probe whose budget we set"), and the VDBFuzz-side configurations (version, mutation settings for the coverage run) are described only briefly.
4. **Verifiability** — Weak
   - **4.1** The text is rich procedurally where the pipeline is concerned: the two-step extraction with its two self-checks, five generation gates (Section 4.3), the executor's log/marker protocol (Section 4.4), the five-section evidence-chain schema and the auditor's four checks (Section 4.5), and a cost profile with token counts (Section 5.1). The main flow can be followed in concept.
   - **4.2 [major, fixable]** The declared artifact is not yet reachable ("will be released ... once the archive is published", Data Availability), and the text alone does not contain what a re-adjudication needs: the frozen-pack assembly procedure (who selected each transcript and contract row, what else a pack contains — 4.2/3.3 hinge on this; see Q4), the strategy registry, and the prompts. Until the archive lands, RQ2 cannot be fully re-executed from the paper.
   - **4.3 [minor, fixable]** The tested versions for Milvus and Weaviate are never stated anywhere; only Qdrant versions appear (v1.4.0 / v1.18.0 / v1.18.2 / v1.19.0), and the Table 2 ledger accumulates "since early 2026" without per-bug version pinning. Version pinning is the paper's own first-class concern (version-alignment check, Section 4.2), so its absence for two of three targets is a real gap.
   - **4.4 [minor, fixable]** All agents run on GLM-5.2 "under default sampling" with no snapshot identifier, so runs are not weight-recoverable — disclosed in Section 6, but it caps replication of the reported rates.
5. **Presentation** — Adequate
   - **5.1** The running example (Qdrant #10369) is threaded through all four stages of Section 4, and Table 1 is a genuinely clear organizing device; figure and table references all resolve.
   - **5.2 [minor, fixable]** Table 1's caption says "Rows 1 to 5 anchor their expectations in signals, structured sources, or method-level/tagged prose ... only row 7 derives its expectation from system-level prose" — but row 6 (doc-derived oracles) also belongs to the anchored-elsewhere set the caption describes; it should read "rows 1 to 6".
   - **5.3 [minor, fixable]** Section 2.4 and Section 7 substantially duplicate each other: the MASTOR description (per-field status oracles plus behavioural-consistency oracles over operation sequences) and the doc-derived lineage (@tComment through Testora) appear nearly verbatim twice.
   - **5.4 [minor, fixable]** Several passages are overlong single paragraphs that impede parsing — notably the final RQ2 paragraph ("Which perspective carries the decision") and the Section 5.2 pool-bias paragraph; the abstract is also a very long single paragraph. Sub-paragraphing would help.
   - **5.5 [minor, fixable]** The Qdrant experiments span four versions (v1.4.0, v1.18.0, v1.18.2, v1.19.0) disclosed only across Sections 4.2, 5.2, and 5.4; a small experiment-to-version map in Section 5.1 would prevent misreading.

### Questions for Authors

- **Q1:** Which exact Milvus and Weaviate versions (and documentation versions) were tested, and was each candidate probed against a single pinned version? — If stated, item 4.3 would move up and the ledger's version coherence would be checkable.
- **Q2:** How many pipeline-confirmed candidates were never submitted (and how many were re-confirmations of known families) in the Qdrant run's 60 defect-confirming candidates? — A concrete count would let readers bound pool selectivity in 3.3 and either raise or lower confidence in the RQ2 rates' external validity.
- **Q3:** Was the full-stage priority aggregation rule varied (e.g., removing the by-design veto)? — Any sensitivity data would move 3.5 up by showing the reported operating point is not one arbitrary calibration.
- **Q4:** Who assembled the 81 frozen packs, under what written procedure, and were packs reviewed for neutrality before the runs? — Clarity here would move 4.2 up and firm up the blinding claim that Section 5.2's suppression figures depend on.
- **Q5:** Did you check for prior systems deriving behavioral oracles from system-level, untagged prose (e.g., guides/tutorials rather than reference pages) for stateful HTTP APIs? — A cited negative check would consolidate the provisional 2.1/2.2 rating.
