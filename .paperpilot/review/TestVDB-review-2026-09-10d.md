## Reviewer 1: Domain Expert

**Overall Recommendation:** Accept

### Summary

The paper targets a class of vector-database defects the authors call documentation-implementation bugs: inputs the system silently accepts, or behaviors it produces, that contradict the vendor's natural-language API documentation. The motivating example is Milvus accepting `nprobe=0` with HTTP 200 against documentation declaring the range as [1, 16384]. The paper first argues structurally that no deterministic oracle candidate reaches this class (Table 1 walks crash signals, differential testing, metamorphic relations, property-based testing, and spec/source-derived REST oracles, and locates each one's expectation outside system-level prose), then presents TestVDB, a four-stage pipeline: documentation crawling and behavioral-specification extraction; probe generation by three attack agents whose strategies are pre-bound by a registry rather than chosen by the LLM; sandboxed execution against Docker-pinned VDBMS versions with raw HTTP logging; and a bug-confirmation stage that splits an evidence builder from a chain auditor, the latter applying four mechanical checks and four perspectives (contract, physical behavior, maintainer cognition, implementation source) before issuing Confirmed / Refuted / Neutral. A running example (Qdrant #10369, a `lookup_from` dimension-validation bypass on `recommend`) is threaded through all four stages.

The evaluation has three parts: RQ1 reports a maintainer-adjudicated submission ledger (81 adjudicated submissions across Milvus, Qdrant, and Weaviate, 51 confirmed, 23 fixed, 30 adjudicated false positives, 49 pending and excluded), plus a process ledger of one complete Qdrant v1.18.0 run; RQ2 re-adjudicates the same 81-candidate pool three times under a frozen-package blinding, once with only the contract core and once with the full stage adding source forensics and maintainer cognition, and reports per-run true/false-positive splits, agreement, and an attributed recall boundary; RQ3 probes the two oracles' reach in both directions against VDBFuzz on Qdrant, including a full-template-space run with the time limit removed.

### Core Strengths

- **S1:** Demonstrated real-world impact: the maintainer-adjudicated ledger (Table 2) reports 51 confirmed bugs and 23 merged fixes across three production VDBMSs, with the ledger's categories, re-verification date, and the actionability of the 23 fixes (implementation-code changes, regression tests added, none documentation-only) all checked — see 1.1, 3.1.
- **S2:** The novelty delta over the closest prior work is real and I verified it against the sources: MASTOR's own stated limitation is that it cannot detect requirements not reflected in code, and CASCADE's cross-check is code generated from the same documentation, so TestVDB's inversion (documentation as ground, implementation source as the falsifier) is a genuine, non-obvious move — see 2.2, 2.3.
- **S3:** The RQ2 design is unusually candid: it freezes the packages, blinds the judge to labels and issue history, judges every case in every run, reports a recall of 0.196–0.431 rather than only the favorable FP-side numbers, and discloses both a leakage incident it re-mined and a prior unblinded run whose 0.841 recall it now disowns — see 3.2, 3.3.
- **S4:** Table 1 converts the paper's central structural claim into something checkable at a glance, and RQ3 then turns it into a measurement: the crash oracle cannot fire on an HTTP-200 silent accept by construction, and the full-template-space run on a pinned version makes the budget objection answerable — see 1.1, 2.1.
- **S5:** The pipeline is documented concretely enough to follow and reason about: the five generation gates, the five-section evidence chain, the four checks and four perspectives, the three-valued verdict, and the bounded rebuild loop — see 4.2.

### Core Weaknesses

- **W1:** The paper's headline yield and its measured method come from different configurations on the same candidate pool, and the ledger's own category definitions do not line up: the blinded re-adjudication confirms only 11–19 of the 51 true bugs, and three acknowledged duplicates are counted inside the 51 although the collection protocol defines duplicates as a category separate from confirmed — see 3.4, 3.7, 5.3.
- **W2:** Missing related work: Metamon (LLM4Code 2025) and RBCTest (ICSE 2026) both derive expectations from natural-language documentation with LLMs and both add their own verification schemes to suppress LLM error; neither is cited, and the paper's residual claim and design framing need to be positioned against them — see 2.4.
- **W3:** The attribution of the recall loss to three mechanisms, which the abstract calls the measured recall boundary, is asserted rather than measured: there are no per-mechanism counts and no coding rule — see 3.5.
- **W4:** RQ3 is not version- or budget-matched (v1.18.2 for the systematic direction, v1.18.0 for the head-to-head, v1.4.0 for the reverse direction; the 26,000-request and 205-template budgets are not tied to VDBFuzz's published configuration), and the statement about the Qdrant crashes VDBFuzz reports does not match the fetched VDBFuzz text — see 3.6.
- **W5:** The replication package is promised rather than declared reachable, carrying a live authoring TODO, and the agent role definitions that constitute the method are inside it — see 4.3.

### Detailed Assessment

1. **Significance** — Excellent
   - **1.1** The contribution's impact is demonstrated, not asserted. Table 2 reports 81 adjudicated submissions, 51 maintainer-confirmed bugs, and 23 merged fixes across Milvus (43 submitted), Qdrant (28), and Weaviate (10); the RQ1 "Fix nature" paragraph additionally classifies every merged fix PR by changed files and reports that all 23 modify implementation code, 15 add regression tests, and none is documentation-only. A bug-finding tool whose output has been merged into three shipped systems is the clearest form of practical impact this field recognizes, and the ledger is reported with the categories (confirmed / duplicate / false positive) and the re-verification date stated up front.
   - **1.2** The paper makes the target class concrete rather than rhetorical. Table 3 groups the 51 confirmed bugs into eight patterns and shows the acceptance family (Silent-Accept 25, Type-Coercion 8, Silent-Ignore 4) accounting for 37 of 51 (72.5%) — exactly the shape that returns success while violating a documented constraint — with per-system concentration noted (Type-Coercion only in Milvus, where the REST layer coerces types that gRPC rejects; the count-under-counting cluster in Qdrant). A taxonomy with defects behind it gives practitioners something to act on beyond "VDBMSs have bugs".
   - **1.3 [minor, fixable]** The significance of the *method* is bounded in ways the paper states only in its limitations: three systems, one LLM backbone, and a documentation regime restricted to prose-constraint APIs. Severity is also not established — the paper notes that the three projects share no severity-label scheme, so the reader cannot tell whether the confirmed bugs are service-threatening or cosmetic. Reporting whatever triage signal exists per project (Section 4.2's acceptance signals are a good start) and stating the bounded claim once in the introduction would keep the contribution's reach honest.

2. **Novelty** — Adequate
   - **2.1** The delta over VDBFuzz, the only dedicated VDBMS testing tool, is verified against the full text I fetched. VDBFuzz's own Discussion says it "currently only performs fuzzing for crash-related bugs in vector databases, as crashes present the most direct and observable oracle", and its Future Work names oracle development as the open direction. The paper's claim that the silent-accept class is structurally out of reach is therefore correct, and its complementarity framing is not a straw man. Note that VDBFuzz also reports six runtime exceptions alongside thirteen crashes, so "crash" is shorthand; the structural argument (HTTP-200 silent accepts generate no failure signal) is unaffected, but the shorthand should be stated once.
   - **2.2** The delta over MASTOR, which the paper calls the closest related work, is verified — and verified from MASTOR's side rather than the paper's. MASTOR's own limitations say it "infers semantics from implementation behavior. It cannot detect violations of intended requirements that are not reflected in code." TestVDB inverts that relationship: the specification is read from prose, and the source is used only as a falsifier. That inversion (source as falsifier rather than as oracle ground) is a clear, non-obvious idea, and the paper states it precisely in Section 6.
   - **2.3** The remaining deltas I checked hold. SATORI's oracle catalog is per-response-field and unary, read from OpenAPI metadata (verified from the cached paper), so Section 6's characterization of it as targeting response-field properties rather than behavioral conformance is accurate. The documentation-derived oracle line is correctly characterized for Toradocu (classical NLP over Javadoc `@throws`, oracle woven in as a runtime assertion and acting as the final arbiter), which supports the paper's claim that this line keeps the derived oracle as arbiter. AGORA+'s invariant learning is from observed request/response traffic alone (verified from its abstract), so "cannot reach inputs the traffic did not exercise" is fair.
   - **2.4 [major, fixable]** Two closely related works are uncited, and both bear on the paper's central positioning claim. Metamon (Lee, An, and Yoo, LLM4Code 2025) detects inconsistencies between program documentation and behavior by capturing behavior as regression tests and then scoring documentation-behavior agreement with metamorphic prompting and self-consistency over multiple LLM queries; RBCTest (Huynh et al., ICSE 2026) has an LLM mine logical constraints from API documentation, including natural-language descriptions, and generates validation tests for response bodies, with an Observation-Confirmation prompting scheme and a semantic verifier as its anti-hallucination devices. (Both descriptions come from the papers' abstracts and programme listings as surfaced in my searches; I could not fetch either full text from this environment, so the details are provisional and should be checked against the papers themselves.) Both derive expectations from prose documentation with an LLM and both reduce LLM error by adding a verification mechanism, so the Related Work claim that no tool derives its expectation from system-level prose survives only in its granularity ("system-level, stateful HTTP behavior" versus method-level or field-level prose), and the extraction/verification design is less unprecedented than Section 6 implies. Metamon in particular belongs in the LLM-arbiter-reliability discussion, where the paper currently cites TOGLL, Konstantinou et al., and Testora among LLM-oracle works. Note also that RBCTest's constraint mining covers request parameters (its "request-response" constraints), which is closer to the paper's accept/reject surface than the "response-field" framing in Section 6 suggests.
   - **2.5 [minor, fixable]** The characterization of CASCADE ("its falsifier is therefore another LLM artifact sharing the documentation's ambiguity") is verified at abstract level only: CASCADE reports an inconsistency only when the original code fails a generated test and code generated from the documentation passes it, so the shared-ambiguity argument follows by construction. I could not reach CASCADE's full text from this environment (arXiv unreachable, publisher page blocked), so the verbatim quotation attributed to it in Section 6 could not be checked; the authors should confirm that quote against the published version, since a misquote in a positioning sentence is cheap to fix and expensive to defend.
   - **2.6 [minor, fixable]** The confirmation stage's claimed novelty (builder/judge split, four-perspective audit) has nearer neighbours than Section 6 concedes. MASTOR already adds a ChallengerAgent review plus deterministic oracle normalization, and CASCADE's dual-check is a second-pass verification. Section 6 should say explicitly what the evidence-chain audit adds over a second-pass reviewer (the appeal to an information source outside the documentation, plus the cognition perspective) rather than leaving that inference to the reader.

3. **Soundness** — Adequate
   - **3.1** RQ1's protocol is defensible and its arithmetic is internally consistent. I recomputed the ledger: 43+28+10 = 81 submissions; 29+14+8 = 51 confirmed; 11+9+3 = 23 fixed; 14+14+2 = 30 false positives; and the bug-status breakdown (23 fixed, 18 open with acknowledgment, 7 closed without fix, 3 duplicates) sums to 51. The paper also reclassifies one of its own presumed true positives (#9149) after a seven-version re-probe showed the "fix" PR added a test rather than a fix, and it uses that same case as a validity check on its fix-PR classifier. Self-disproving a counted bug is a costly and rare act, and it earns the rest of the ledger credibility.
   - **3.2** The frozen-package RQ2 protocol is a direct answer to the paper's own disclosed threats (expectation-framing bias and observation leakage in Section 5), and the paper reports the unflattering numbers: run-level recall 0.196–0.333 for the contract core and 0.353–0.431 for the full stage, majority-vote recall 0.373, plus the admission that an earlier unblinded run had reported 0.841 and that this gap is "the measurement cost of blinding". This is the behaviour that makes the FP-side result (0.867 per-run for the core, 1.000 for the full stage) worth trusting.

Comparing Table 4's core rows to its full rows, the four FP cases the core misconfirms in two or three runs are exactly the ones the added perspectives veto, and the paper reports the symmetric cost rather than hiding it — "the veto power that perfects precision also suppresses boundary truths". The per-perspective readout (D carries the decision; the contract view confirms only a minority and is neutral on most) is the kind of detail that lets a reader see where the mechanism actually lives. Because the abstract's "measured recall boundary" and the paper's contribution claim both rest on this attribution, the misses should be enumerated with their mechanism labels, ideally in an appendix, so that the boundary's location is checkable and not just narratable.

The systematic direction runs on Qdrant v1.18.2 (26,000 mutated requests), the head-to-head heading says "on the same version" but its body is v1.18.0, and the reverse direction runs on v1.4.0 — a version old enough that the demonstration shows reach on stale code, not competitiveness on current code. The 26,000-request budget is not tied to anything VDBFuzz publishes: VDBFuzz's own evaluation protocol is 120 minutes per tool per VDBMS, and it reports more than ten million test cases across eight systems, so a reader cannot tell whether 26,000 is VDBFuzz's default throughput, a truncated run, or a chosen cap. Relatedly, the sentence "The two Qdrant crashes VDBFuzz reports in its own case study are also fixed in v1.18.2" does not match the VDBFuzz text I fetched: that paper presents one Qdrant case study (the dimension-overflow DoS) and its results table lists three Qdrant crashes, so "two ... in its own case study" matches neither reading. Fix the version statements in one place, justify both budgets, and re-check the crash count against VDBFuzz.

Section 4.2's collection protocol makes duplicate a category distinct from confirmed ("as duplicate when tracked to an existing issue"), but the bug-status paragraph then counts "3 were acknowledged as duplicates" inside the 51 confirmed. A reader cannot tell whether the headline precision (51 of 81) includes candidates that only re-report someone else's bug, or whether those three should be excluded. State where duplicates sit relative to the 51 and restate the protocol accordingly.
   - **3.8 [minor, fixable]** Statistical reporting is asymmetric between the two sides of RQ2. Suppression gets per-run Wilson intervals, but recall gets only a range across three runs, and the core-versus-full comparison — which is paired by construction, since the same 81 frozen packages are judged — is reported without a paired statistic even though four FP flips and a 0.216-versus-0.373 majority recall shift are the paper's central mechanism evidence. A paired test, or at least per-case overlap counts between runs rather than agreement rates alone, would make the mechanism claim measurable rather than suggestive.
   - **3.9 [minor, fixable]** The pipeline's own design claims are never ablated. Section 3.3 argues that pre-binding strategies "removes a degree of freedom in which the LLM could drift", Section 3.2 argues the two-step extraction buys auditability and context budget, and Section 3.3 lists five generation gates — but the only ablation in the evaluation compares the contract-only core with the full confirmation stage. Since the paper's design is the contribution, at least one of these claims (pre-binding versus free strategy selection, or gate-by-gate necessity) should be tested on the frozen packages rather than argued.

## Reviewer 2: Area Specialist

**Overall Recommendation:** Accept

### Summary

The paper targets *documentation-implementation bugs* in vector database management systems (VDBMSs) — cases where a system silently accepts an input or returns success while violating its API documentation (the paper's canonical illustration of the class is Milvus accepting `nprobe=0` against a documented range `[1, 16384]`). Its central argument is structural: crash oracles, differential testing, metamorphic relations, property-based testing, and structured-spec oracles all anchor their expectation somewhere other than system-level prose, so for this residual an LLM that reads the prose is the practical oracle — which imports the LLM's false-positive problem. The proposed system, TestVDB, is a four-stage pipeline: behavioral-specification extraction from vendor documentation (`knowledge.json` → `specifications.json`, with typed, evidence-leveled, source-verified constraints), test-script generation by three attack agents under deterministically pre-bound strategies with scenario construction for system-level constraints, execution in a Docker-pinned sandbox logging raw HTTP traffic, and a bug-confirmation stage in which an evidence builder assembles a five-section evidence chain and a chain auditor cross-examines it via four mechanical checks and four perspectives (contract, physical behavior, maintainer cognition mined from the project's issue history, and implementation source), with the source serving as the falsification anchor.

The evaluation covers Milvus, Qdrant, and Weaviate: 81 maintainer-adjudicated submissions with 51 confirmed real bugs and 23 merged fixes; a three-run blinded re-adjudication of the full 81-candidate pool that isolates a contract-only adjudication core (87–90% per-run false-positive suppression, 88.9% case-level verdict agreement, recall 0.196–0.333) and ablates the full stage on the same frozen packages (suppression 1.000 in all three runs, majority-vote recall 0.373); and a bidirectional probe against the crash-oracle baseline VDBFuzz, showing that a 26,000-request crash-baseline run reaches none of seven live silent-accept true positives on Qdrant v1.18.2 while TestVDB's boundary probe reaches VDBFuzz's crash-class integer-overflow bug on v1.4.0 by contract reasoning.

### Core Strengths

- **S1:** A large, maintained, and independently checkable real-world yield: 51 maintainer-confirmed bugs and 23 merged fixes across three production VDBMSs, with the nature of every fix PR classified (all touch implementation code; 15 add regression tests; none documentation-only) and the classifier validated on the one candidate it correctly reclassified — see 1.1, 3.3.
- **S2:** The complementarity claim against the crash-oracle baseline is measured rather than asserted, and the paper's statements about that baseline check out against VDBFuzz's own artifact (205 Qdrant templates, the 120-minute protocol, the `2**63` overflow PoC, the `?wait=true` upsert path) — see 2.1, 3.1.
- **S3:** The RQ2 protocol shows unusual measurement discipline for an LLM-oracle evaluation — frozen packages, full denominator, conservative verdict rule, Wilson intervals, a leakage audit of the cognition files, and an explicit, self-deflating disclosure that an earlier unblinded protocol had reported recall 0.841 where the blinded protocol reports 0.373 — see 3.2, 3.3.
- **S4:** The oracle-exclusion analysis cleanly delimits where an LLM-derived expectation is forced, and its central claim survives a check against the named competitors (SATORI's oracles are per-response-field from OpenAPI metadata; MASTOR's ground is the implementation source; VDBFuzz's oracle is crash-only) — see 2.1.

### Core Weaknesses

- **W1:** The novelty delta is asserted against the two closest works rather than demonstrated: MASTOR is described as targeting "response-field or runtime properties" although it also generates cross-operation behavioural-consistency oracles and runs a ChallengerAgent reviewer loop, and the closest-in-goal work, CASCADE, is positioned in one sentence resting on a quotation I could not verify at source — see 2.2, 2.3.
- **W2:** Missing related work: Metamon (LLM4Code 2025) is an uncited LLM judge of documentation-versus-observed-behaviour consistency whose reported precision/recall (0.722/0.480) is the nearest published comparator for this paper's reliability numbers and whose falsifier is exactly the LLM self-reference this paper claims to break — see 2.4.
- **W3:** RQ1 and RQ2 are earned under different operating configurations that the paper never states side by side: the 51 confirmed bugs come from cumulative unblinded operational rounds with manual screening and submission, while RQ2's blinded stage recalls at most 0.431 (majority 0.373) of the same pool — see 3.4.
- **W4:** Verifiability rests on a promised artifact: the Data Availability link is still a red TODO in the source, the frozen RQ2 packages and role prompts are not in the text, and the LLM snapshot is not pinned — see 4.2, 4.3, 4.4.
- **W5:** The abstract reports the precision half of the RQ2 tradeoff ("intercepts 87–90% of false positives with 88.9% verdict agreement") without its recall half, and "verdict agreement" can be misread as accuracy — see 5.2.

### Detailed Assessment

1. **Significance** — Excellent
   - **1.1** The submission ledger in §4.2 (the submission-ledger table) is a strong practical-impact record: 81 adjudicated submissions across Milvus (43), Qdrant (28), and Weaviate (10), with 51 maintainer-confirmed real bugs (63.0%), 23 merged fixes, 18 open with acknowledgment, 7 closed after acknowledgment, and 3 acknowledged duplicates; 49 further submissions are excluded from every rate. The paper additionally checks *what kind* of fix was merged — classifying all 23 fix PRs by changed files and finding that every one modifies implementation code, 15 also add regression tests, and none is documentation-only — which pre-empts the standard "these are documentation edits, not bugs" objection. I recomputed the table sums (29+14+8=51 confirmed; 11+9+3=23 fixed; 14+14+2=30 false positives) and they are consistent.
   - **1.2** The paper establishes that the blind spot it chose is real and quantified, not rhetorical: §2.2–§2.3 ground it in the VDBMS bug-distribution studies, §2.4's oracle-exclusion analysis shows why the standard oracle families cannot reach it, and §4.2's bug-pattern table shows the shape concentration (Silent-Accept, Type-Coercion, Silent-Ignore together 37 of 51 bugs; 72.5%), with only 2 of the 51 maintainer-confirmed bugs producing a crash or panic. Combined with the RQ3 probe (0 of 7 live silent accepts reached by the crash baseline on the pinned version), this is a well-posed problem with a demonstrated payoff.
   - **1.3 [minor, fixable]** The demonstrated impact is the yield of a human-machine pipeline, and the paper reports only part of its cost. §4.1 gives ≈67 active hours across five calendar days, ≈860 sandboxed script executions, and ≈70M input / 4.9M output tokens "for the orchestrating session alone" — explicitly a lower bound, since parallel attack-agent sessions are excluded — while §4.2 states that submission decisions were made by the authors with no deterministic rule. A cost-per-confirmed-bug estimate (tokens plus human hours) and an explicit list of the human decision points (novelty screening, submission, neutral-case review) would let readers judge how transferable the yield is to another team; it does not change the impact already demonstrated.

2. **Novelty** — Adequate
   - **2.1** The oracle-exclusion analysis (§2.4 and the oracle-candidates table) is the paper's cleanest conceptual contribution: instead of arguing by enumeration, it asks where each candidate oracle obtains its expectation and shows that crash signals, reference implementations, output relations, machine-checkable properties, and structured specs each fail structurally for system-level prose. I checked the characterizations that carry the argument against fetched sources and they hold: SATORI's oracle catalog is per-response-field, prompted from OpenAPI field names/types/descriptions (17 unary oracle types; F1 74.3% on OKAMI), MASTOR's ground truth is the Java source (OpenAPI items unsubstantiated in source are demoted to `pending`), and VDBFuzz's oracle is crash/exception-only, with its own discussion stating it "currently only performs fuzzing for crash-related bugs". The residual claim — no *deterministic* candidate derives its expectation from system-level prose — survives this check, and the paper is careful to keep the "system-level" qualifier when it discusses structured artifacts such as OpenAPI.
   - **2.2 [major, fixable]** MASTOR, the paper's self-declared closest work, is under-described in a way that flattens the delta. §6's structured-source paragraph and row 5 of the oracle-candidates table place it under "per-field structural anchoring ... target response-field or runtime properties", but MASTOR's own text (fetched) has two generation paths: single-operation status/field oracles, and a multi-operation path that generates *behavioural-consistency oracles for operation sequences* over five cross-operation associations (resource lifecycle, identifier flow, field-level data passing, nested-resource dependency, state propagation) — plus a **ChallengerAgent** reviewer that inspects generated oracles and drives targeted regeneration on both paths. That means the "generated oracle reviewed by a second LLM agent" architecture is not new here, and cross-request behavioural oracles are not unique to TestVDB. TestVDB's genuine delta is the *anchor inversion*: the prose documentation is the ground and the implementation source plus maintainer cognition is the falsifier, whereas MASTOR grounds in source. The paper should state that delta explicitly rather than relying on a response-field characterization of MASTOR; leaving it as written invites a reviewer to read the confirmation-stage novelty as narrower than the paper claims.
   - **2.3 [major, fixable]** CASCADE (FSE 2026) is the closest work in *goal* — detecting inconsistencies between code and documentation with LLM-generated tests — and the paper disposes of it in one Related-Work sentence whose comparative force rests on a quotation: that both of CASCADE's own residual false positives arose because "the generated code and tests made the same false assumption over something underspecified in the documentation". I could not verify that sentence: arXiv and the ACM PDF are unreachable from this network and CASCADE's artifact repository contains no paper copy, so my check is limited to the abstract and search-indexed material, which confirms the *mechanism* the paper describes (tests generated from natural-language documentation; a second phase that synthesizes an implementation from the same documentation and flags an inconsistency only when the original fails and the synthesized implementation passes) but not the quotation. Two things are needed: a section/page pointer for the quotation, and an outcome-level comparison (CASCADE's abstract-level record reports 13 newly found inconsistencies across 10 projects and three languages, at method level) so the reader can see the delta in granularity — method-level tagged prose versus system-level REST prose and stateful behaviour — and in the falsifier (same-documentation synthesized code versus the actual implementation plus maintainer cognition). Provisional: CASCADE details beyond the abstract are search-derived, not read at source.
   - **2.4 [major, fixable]** Missing related work: **Metamon** (Lee, An, Yoo; LLM4Code 2025; arXiv:2502.02794) is uncited and directly relevant to the paper's core claim. Metamon captures program behaviour with EvoSuite regression-test oracles and has an LLM judge whether each captured oracle is consistent with the method's documented specification, using metamorphic (negated-assertion) prompt pairs and self-consistency to stabilise that same LLM judge; it reports precision 0.722 / recall 0.480 at its permissive threshold on 9,482 pairs, with precision rising to 0.967–1.000 as recall collapses to 0.099–0.014, and attributes 16 of its 21 high-confidence false alarms to LLM underperformance and 2 to missing specification detail. This is the nearest published instance of "an LLM decides documentation-versus-behaviour inconsistency", and its falsifier is another LLM question — precisely the self-reference the paper claims to break, so the delta stands — but the paper's Related-Work paragraph on doc-derived oracles and judge reliability should name it, and its precision/recall profile is the most informative published comparator for the paper's own rates and for its Neutral/undecidable design choice.
   - **2.5 [minor, fixable]** Wording of the uniqueness claims. §1 calls VDBFuzz "the one dedicated VDBMS testing tool", while the paper itself cites MeTMaP (VDBMS-related metamorphic testing) and the roadmap and bug-study lines are dedicated VDBMS reliability work; VDBFuzz's own self-description is "the first fuzzing framework specifically designed for VDBMSs". "The one dedicated VDBMS *fuzzer*, crash-oracle by design" would state the same point without the overclaim.

3. **Soundness** — Adequate
   - **3.1** RQ3 is the paper's most verifiable experiment and its baseline statements hold up against VDBFuzz's artifact: I confirmed `"total_templates": 205` in `templates/qdrant/generation_summary.json` (with 205 template `.py` files), the 120-minute per-tool comparison protocol in VDBFuzz §5.3, the `recreate_collection(..., size=2**63)` integer-overflow PoC in its Listing 3, and the `PUT /collections/client_test/points?wait=true` upsert path in the very empty-vector template — which is exactly the evidence behind the paper's claim that the template suite uses the `wait=true` path and never probes `wait=false`. The bidirectional design (crash baseline against seven live silent accepts; contract reasoning reaching a crash-class bug on v1.4.0) supports the complementarity claim considerably better than a one-way comparison would.
   - **3.2** The RQ2 blinding protocol is well constructed: frozen candidate packages (observed transcript plus documented contract), no access to adjudication labels or issue history, every case judged in every run (denominator 81/81), a conservative binary rule that resolves uncertainty toward False-Positive, agreement plus per-run precision/recall, and Wilson intervals on suppression. The leakage audit is more than pro forma: one tracker's cognition file had absorbed six candidate-anchored entries, and the paper re-mined it, re-adjudicated the eleven affected candidates, and reports that no verdict changed in any run — a direct test of the most plausible leakage channel for the C perspective.
   - **3.3** The paper's honesty chain is a real asset: the earlier unblinded protocol's recall of 0.841 is disclosed and superseded (with the measurement cost of blinding stated as the reason), the pool's submission-filtered origin and the direction of the induced bias are spelled out, the #9149 false fix is reclassified by a seven-version re-probe and then used to validate the fix-PR classifier, and the neutral-route candidates (the replay-dependent batch updates; the same-second snapshot collision) are reported as escalated rather than forced. I also recomputed the arithmetic across the three result tables — ledgers sum correctly; both RQ2 panels satisfy TP+FN=51 and FP+TN=30; per-run suppression 26/30 and 27/30 give 0.867–0.900; per-run precision 0.750–0.810; agreement 72/81 = 88.9% — and found no inconsistencies.
   - **3.4 [major, fixable]** The paper never puts RQ1's and RQ2's operating points side by side, and they are not the same pipeline configuration. RQ1's ledger is cumulative across mining rounds since early 2026, produced by a pipeline that ran *unblinded*, with expectation-framed contract text and unsanitized probe descriptions entering the judge's observations (§5 lists these as disclosed threats), and with manual novelty screening and manual submission decisions (§4.2 states there is no deterministic submission rule). RQ2 then re-adjudicates the resulting pool under blinding and reports that the contract-only core recalls 0.196–0.333 (majority 0.216) and even the full stage recalls only 0.353–0.431 (majority 0.373). A reader can therefore take away either that the stage credited with 51 confirmed bugs misses roughly two-thirds of true bugs when measured, or that the measured protocol is a deliberately conservative variant that was never the operating configuration — and the text supports each reading in different places without ever saying which is intended. The fix is a short reconciliation paragraph naming the configuration that produced the ledger and stating explicitly that RQ2 is a lower-bound reliability measurement under blinding. This is the main reason Soundness is Adequate rather than Excellent: the two headline results currently rest on different measurement feet.
   - **3.5 [minor, fixable]** §4.4 claims that "the two Qdrant crashes VDBFuzz reports in its own case study are also fixed in v1.18.2". VDBFuzz's own bug listing gives Qdrant three crash bugs (Weaviate 2, Qdrant 3, Faiss 3, Hnswlib 1, Annoy 2, sqlite-vec 2; 13 crash plus 6 exception issues in total) and its text presents a single Qdrant case study, the `2**63` DoS. Please give the identities/issue links of the two crashes meant here and reconcile the count; as written, the sentence that establishes the "clean separation" of the two oracles on v1.18.2 cannot be checked.
   - **3.6 [minor, fixable]** The direction of the by-design veto should be stated as a scoping decision. The confirmation rule lets in-source by-design evidence and cognition evidence veto a contract violation (§3.5; §4.3 explains that this veto is what perfects precision while suppressing "boundary truths"), and the paper is candid about that cost. But the object of study is named *documentation-implementation bugs*: a mismatch in which the implementation's behaviour is intentional and the *documentation* is stale — a documentation-side defect — is structurally filtered out, even though "Doc-Spec-Gap" is counted as a confirmed bug pattern (Qdrant #9942). The paper should say plainly that it adjudicates code-side violations, and report how many of the 30 maintainer-adjudicated false positives are doc-side defects ("labeled by-design") rather than non-bugs; that number is currently invisible and it bounds the claim.
   - **3.7 [minor, fixable]** Scope of the stability claim. "False-positive interception is stable" is established within one backbone (GLM-5.2, default sampling) over three runs with *frozen packages*, and intervals are reported for suppression but not for recall or precision; no variance is measured for extraction or generation, and no cross-model replication exists. §5 discloses the single-backbone limitation, but the RQ2 subsection should carry the same qualifier where the stability claim is made — especially since the paper itself cites Molinelli et al. on per-subject oracle unreliability.

4. **Verifiability** — Adequate
   - **4.1** The method description is detailed enough to follow in concept: named intermediate artifacts (`knowledge.json`, `specifications.json`, `evidence_chain.json` with its five sections), the constraint typing/leveling/source-verification mechanics, the five generation gates, the strategy pre-binding rule, the verdict vocabulary (Confirmed / Refuted / Neutral), the C/D aggregation priority rule, and the run's aggregate cost profile (the single §4.1 figure set for the full Qdrant run). For a pipeline this complex, that is a reasonable text-level account.
   - **4.2 [minor, fixable]** The Data Availability section promises a replication package (agent role definitions, per-version knowledge bases and specifications, all generated scripts with raw HTTP logs, evidence chains, submission ledger) at an anonymous URL — but the LaTeX source still contains `\todo{Confirm anonymized artifact link before submission; keep author-anonymous.}`, so at review time the link is a placeholder and none of the reported numbers can be checked against data. If the anonymized artifact is live at camera-ready this resolves; if it is not, this criterion should be re-rated downward.
   - **4.3 [minor, fixable]** Because RQ2's numbers *are* the paper's reliability claims, at least the per-case adjudication table (target, bug pattern, verdict in each of the three runs, majority) belongs in an appendix; the paper reports only aggregate panels, and the frozen packages, prompts, and strategy registry live only in the promised artifact. A reader cannot inspect, for example, the distribution of the four systematically leaked Milvus packs.
   - **4.4 [minor, fixable]** An LLM study should pin the model: "GLM-5.2 under default sampling" (the Implementation paragraph of §3.5; §4.1) identifies a family, not a snapshot, and "default sampling" leaves temperature unspecified; the run dates (five calendar days, plus earlier cumulative rounds since early 2026) matter for attributing measured rates to a reproducible configuration.

5. **Presentation** — Adequate
   - **5.1** The structure is sound and the running example is effective: the Qdrant #10369 scenario is carried through all four approach subsections (extraction, generation, execution, confirmation), which makes an otherwise abstract multi-agent pipeline concrete at each stage, and the oracle-exclusion table is a strong organising device for the problem statement. The result tables are internally consistent (recomputed in 3.3).
   - **5.2 [minor, fixable]** The abstract presents one half of the RQ2 tradeoff: it reports "intercepts 87–90% of false positives with 88.9% case-level verdict agreement" but not the recall figures measured in the same experiment (core 0.196–0.333, majority 0.216; full stage 0.353–0.431, majority 0.373), and "verdict agreement" counts agreement on incorrect verdicts as well, so it can be read as an accuracy measure. State the recall number or explicitly frame these as two ends of a precision-recall tradeoff.
   - **5.3 [minor, fixable]** Terminology overload around "FP": the same abbreviation denotes a false-positive *candidate* (the 30 submissions) and the negative *verdict* (\textsc{False-Positive}) returned by the stage, including inside the RQ2 rule description and the caption of the RQ2 table ("FP leaked", "false positives the run confirms"). Define the two senses once and keep them distinct; otherwise a reader can mistake suppression of candidates for the stage's own verdict behaviour.
   - **5.4 [minor, fixable]** §4.2 is extremely dense: protocol caveats, the process ledger, the funnel, the pool bias, and the two-ledger distinction are packed into a handful of very long paragraphs, and the RQ2 subsection in §4.3 then packs the three-run core results, the full-stage ablation, the leak audit, the per-perspective attribution, the stratified recall analysis, and the historical 0.841-versus-0.373 comparison into a small number of single paragraphs. The experiment is well designed; splitting these into short subsections and moving the stratified analysis into a table would let readers see the design.
   - **5.5 [minor, fixable]** Remove the leftover submission artifact: the `\todo{...}` in Data Availability renders as red text in the compiled PDF, along with the `\todo` macro definition.
   - **5.6 [minor, fixable]** Citation hygiene: `togll24` is cited as a 2024 arXiv `@misc`, but TOGLL appeared at ICSE 2025 (IEEE Xplore 11029748); update the entry.

## Reviewer 3: General Reviewer

**Overall Recommendation:** Accept

### Summary

The paper targets a class of vector-database bugs that do not crash: cases where a VDBMS silently accepts an input or produces behavior that contradicts its own API documentation (the canonical illustration of the class being Milvus accepting `nprobe=0` against a documented range of [1, 16384]). It first argues that no deterministic oracle anchors its expectation in system-level prose documentation, and that an LLM-derived oracle is therefore the practical option, then presents TestVDB, a four-stage pipeline: documentation crawling and specification extraction into typed, evidence-leveled constraints; test-script generation by boundary, state, and semantic attack agents under deterministically pre-bound strategies; sandboxed execution against Docker-pinned versions with raw HTTP logging; and a bug-confirmation stage in which an evidence builder assembles a five-section evidence chain and a chain auditor applies four mechanical checks and four perspectives (contract, physical behavior, maintainer cognition, implementation source), with the implementation source serving as the falsification anchor.

The evaluation reports three studies. RQ1 presents a ledger of 81 candidate issues submitted to Milvus, Qdrant, and Weaviate, of which maintainers confirmed 51 as real bugs and fixed 23 via merged PRs, plus eight bug-pattern categories and a process funnel for one complete Qdrant run. RQ2 re-adjudicates the 81 frozen candidates in three independent blinded runs, measuring a contract-only confirmation core (false-positive suppression 0.867–0.900, case-level agreement 88.9%, recall 0.196–0.333) against a full stage that adds source forensics and maintainer cognition (suppression 1.000; majority-vote recall 0.373), and attributes missed true bugs to three mechanisms at the assertion-framework boundary. RQ3 probes the two oracles bidirectionally on Qdrant: 26,000 mutated requests and a full 205-template sweep by VDBFuzz reach none of the live silent-accept defects, while TestVDB's boundary reasoning reaches VDBFuzz's integer-overflow crash.

### Core Strengths

- **S1:** Externally validated detection impact: 51 maintainer-confirmed bugs and 23 merged fixes across three production systems, with dated re-verification and a fix-nature classification that confirms every fix touches implementation code — see 1.1, 3.1
- **S2:** A coherent structural account of why the documentation-implementation residual is unreachable by deterministic oracles, and of where the pipeline's own delta sits — see 2.1, 1.2
- **S3:** The confirmation stage's measurement is adversarial to the authors' own earlier numbers (frozen packages, three blinded runs, cognition-leakage audit, disclosed inflation of the prior unblinded protocol), and the production process is described in followable detail — see 3.2, 4.1
- **S4:** The VDBFuzz comparison is run under the baseline's own published protocol and then over its entire template space, which is a fair and unusually complete treatment of a crash-oracle baseline — see 3.3

### Core Weaknesses

- **W1:** The paper's central mechanism claim — source code as the falsification anchor that breaks the LLM self-reference loop — is not isolated: the only ablation bundles source forensics (D) with maintainer cognition (C) — see 3.4
- **W2:** The blinded pipeline's standalone capability is much lower and more volatile than the headline ledger suggests (full-stage majority recall 0.373; core recall 0.196–0.333), because the 81-bug yield also depends on author-side submission filtering — see 1.3, 3.7
- **W3:** Verifiability is capped by a replication package whose link is still a TODO, and by several procedures that are named but not described (the "reached 0 of 7" determination, the fingerprint table, the novelty matcher, the non-leakage verification) — see 4.2, 4.3
- **W4:** The one-run funnel ledger is not fully reconciled (19 first-pass-novel candidates to 5 registered defect numbers), and the "independently corroborated" claim overstates the third case — see 3.5, 5.6
- **W5:** Novelty is assessed provisionally and rests on the composition and target surface; the paper positions prior systems by description rather than by a head-to-head on the same constraint surface, and Table 1's exclusion argument slightly overstates the absence of structured artifacts — see 2.2, 2.3

### Detailed Assessment

1. **Significance** — Excellent
   - **1.1** The RQ1 ledger (§4.2, submission-ledger table) is ground-truthed outside the authors' own verdicts: of 81 adjudicated submissions to Milvus, Qdrant, and Weaviate, maintainers confirmed 51 as real bugs and fixed 23 via merged PRs; every submission state was re-verified as of September 2026; 50 of the 51 carry an official bug label; and the paper classifies all 23 fix PRs by changed files, finding that every one modifies implementation code, 15 add regression tests, and none is documentation-only. For a bug-finding paper this is the strongest available form of impact evidence, because the artifacts of the contribution are merged patches in production systems rather than a benchmark score.
   - **1.2** The problem selection is well motivated and tightly scoped: the paper uses the cited bug studies (§2.2) to establish that non-crashing functional failures are the majority class in this infrastructure, identifies the one dedicated tool as covering only the crash minority, and uses the oracle-exclusion analysis (Table 1, §2.4) to argue the residual is unreached. The paper is explicit about what it does *not* claim (result correctness, §2.3), which makes the significance case honest rather than inflated.
   - **1.3 [minor, fixable]** The headline "51 of 81" is the yield of a human-curated pipeline, not of the automated system. §4.2 states that submissions had "no deterministic submission rule" and were filtered by novelty screening and author manual review, and §4.3 measures the automated confirmation core's recall at 0.196–0.333. Both facts are disclosed in the evaluation, but the abstract and introduction lead with the ledger without the human-in-the-loop qualifier; a reader who stops at the abstract will over-attribute the yield to the system. Add the qualifier where the headline appears.

2. **Novelty** — Adequate *(provisional: I did not survey the field for this review; the assessment below is read from the paper's own positioning plus general knowledge, and the paper's characterizations of prior systems could not be independently checked)*
   - **2.1** The paper states a recognizable delta against the lines it itself names. Against documentation-derived oracle work it distinguishes (a) the target residual — expectations read from system-level, untagged prose governing stateful HTTP behavior — from method-level or tagged sources (it groups @tComment, JDoctor, DocTer, Toradocu, and LLM generators such as AugmenTest, ChatAssert, Doc2OracLL, TOGLL, Testora under the latter), and (b) an inversion of source code's role: prior source-derived oracles encode implemented behavior (it names MASTOR as "closest to this work"), whereas TestVDB reads source as a falsifier of a documentation-derived claim. Against CASCADE ("closest in spirit to our confirmation stage") it distinguishes a falsifier that is an independent artifact rather than another LLM artifact sharing the documentation's ambiguity. As the paper tells it, the arrangement — evidence chain grounded in source plus maintainer cognition — is new for this problem class.
   - **2.2 [minor, fixable]** The individual components — LLM extraction of constraints from documentation, strategy-bound test generation, evidence-chain adjudication, multi-run voting — are individually familiar, so originality rests on the composition and on the target surface. The paper positions the closest named works by description but never demonstrates a delta empirically (e.g., deriving constraints from the same documentation with a structured-spec- or pattern-based tool and comparing what each derives on the same endpoints). Because I cannot verify the state of the art myself, my "Adequate" rating is provisional; a sharpened side-by-side delta statement, or a small head-to-head on shared documentation, would move it toward Excellent.
   - **2.3 [minor, fixable]** The exclusion argument is slightly over-stated in one direction. §2.4 asserts that "VDBMS endpoints serve no schema that encodes these constraints, and several serve no OpenAPI at all", and Table 1 rows 4–5 make the same point; yet RQ3 (§4.4) itself uses Qdrant's OpenAPI as the documentation basis for the 2^63 size case ("the OpenAPI declares size ≥ 1"). The more precise — and still strong — claim is that the behavioral and state-coupling constraints at issue are not expressible in whatever structured artifacts exist, not that structured artifacts generally do not exist. Tightening this sentence protects the exclusion argument from an easy counterexample.

3. **Soundness** — Adequate
   - **3.1** Ground truth is constructed adversarially rather than conveniently: §4.1/§4.2 define confirmed/duplicate/false-positive with maintainer-side signals and a dated re-verification; adjudication is treated as revisable (the Qdrant #9149 candidate initially counted as fixed was disproved by the authors' own seven-version re-probe and reclassified); and the fix-PR classifier is validated against that same disproved case, where it correctly identifies a test-only PR. The submission ledger also breaks the 51 down into 23 fixed / 18 open-with-acknowledgment / 7 closed / 3 duplicates, so "confirmed" is not a single soft bucket.
   - **3.2** The RQ2 protocol (§4.3) is unusually careful for this genre: frozen packages, three independent runs, explicit blinding ("no access to adjudication labels or issue history"), majority aggregation with Wilson intervals, and a leakage audit of the mined cognition files that detects six candidate-anchored entries in one tracker's file, re-mines, and re-adjudicates the eleven affected cases. The paper also reports that an earlier unblinded run claimed recall 0.841 versus 0.373 under blinding and attributes the gap to framing and observation leakage. Disclosing a number that halves the apparent capability of one's own stage is the kind of self-correction that raises confidence in the rest.
   - **3.3** The RQ3 comparison is fair in the direction that matters: the systematic probe runs VDBFuzz in its default configuration (26,000 requests, 0 of 7 live silent-accept true positives reached), and the full-coverage run removes the time limit entirely and exhausts the tool's complete 205-template space in 50.8 minutes, well inside VDBFuzz's own published 120-minute comparison protocol, reporting zero crashes/failures/errors on the version where the defects are live. The paper also states the structural reason (a crash oracle cannot fire on HTTP 200) separately from the template limitation it acknowledges in the reverse direction, which is the right attribution discipline.
   - **3.4 [major, fixable]** The paper's distinctive mechanism claim is not isolated by its ablation. Table 4 compares the contract-only core against a "full" stage that adds source forensics (D) and maintainer cognition (C) as one bundle, and §4.3 reports that "D carries the decision … while the contract view confirms only a minority", but no D-only (or C-only) run is reported. The abstract's and conclusion's claim that "the implementation source is the falsification anchor" therefore rests on a C+D joint delta — the correction of the four majority misconfirmations and the recall rise from 0.216 to 0.373 cannot be attributed to source grounding specifically. Since the source-as-falsifier inversion is the paper's main design idea, a D-only ablation should be added before the mechanism claim is stated this strongly.
   - **3.5 [minor, fixable]** The one-run process ledger (§4.2) does not reconcile its own arithmetic: the novelty gate partitions the 60 defect-confirming candidates into 19 first-pass-novel, 11 already covered by upstream fix PRs, 5 by-design, and 25 pending, and the paragraph then says "post-gate deduplication and family merging then register five new defect numbers from this run". How 19 (or 19+25) becomes 5 is not shown. A small funnel table would let a reader verify the ledger independently, and the ledger is one of the paper's stronger exhibits.
   - **3.6 [minor, fixable]** RQ3's reverse direction is in tension with the Limitations section. It says TestVDB's boundary probe "reaches it as a documentation-implementation violation" for the 2^63 crash on v1.4.0, while §5 gives exactly this shape — "a schema-valid parameter value that crashes the service (a resource-exhaustion input accepted with no documented upper bound)" — as an example of cases that "fall outside the strict-verdict path" and are surfaced as reportable incidents rather than adjudicated. Either the v1.4.0 case ran through the strict path (in which case §5's boundary description needs a carve-out) or it did not (in which case the RQ3 sentence overstates what was established). The complementarity claim itself survives either resolution.
   - **3.7 [minor, fixable]** Stability is reported as ranges rather than intervals for the quantities that decide the "systematic, not noise" attribution: core run TPs of 17/10/12 out of 51, recall 0.196–0.333, pairwise agreement 90.1–96.3%. The Wilson intervals are given only for the suppression proportions, where n=30. With n=51 and three runs, the expected per-run recall of the process remains poorly estimated; bootstrap intervals (or additional runs) would firm up the mechanism-attribution argument in §4.3.

4. **Verifiability** — Adequate
   - **4.1** The text describes how the evidence was produced in more depth than is typical for LLM-pipeline papers: the five generation gates, including the contract-existence and response-shape checks (§3.3); the execution logging protocol with post-flush atomic markers and per-batch log/marker count verification (§3.4); the five evidence-chain sections, the four mechanical checks with their bounded three-retry rebuild loop, and the four perspectives with their verdict taxonomy including the Neutral route (§3.5); and the RQ2 blinding/aggregation protocol (§4.3). A reader can follow the causal path from documentation page to submitted issue.
   - **4.2 [major, fixable]** The artifact is declared but not reachable. The Data Availability section promises a replication package "upon publication" at an anonymous URL and still carries the authors' own visible TODO: "Confirm anonymized artifact link before submission; keep author-anonymous."
