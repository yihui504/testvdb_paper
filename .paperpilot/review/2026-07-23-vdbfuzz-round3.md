## Reviewer 1: Domain Expert

**Overall Recommendation:** Accept

### Summary

TestVDB targets documentation-implementation defects in Vector Database Management Systems (VDBMSs): cases where a system silently accepts inputs or produces behaviors that violate its API documentation. The problem is motivated by the observation that about 85% of the 111 issues TestVDB surfaced are unreachable by classical oracles (differential, metamorphic, crash) because the documented boundaries are natural-language rather than formal. The authors identify a two-layer reliability problem when using LLMs as semantic judges: family-specific self-preference (mitigated by cross-model validation) and task-intrinsic errors where ambiguous documentation causes different LLM families to converge on the same wrong claim (unmitigated by cross-model validation). The core contribution is source-grounded falsification, which treats LLM-derived behavioral claims as refutable hypotheses and falsifies them against the implementation's actual behavior. TestVDB surfaced 111 candidate issues across five VDBMSs; maintainers acknowledged 38 as defects. A controlled retrospective shows the source anchor suppresses 81% of false positives (up from 31%) at 96.7% true-positive retention. A twelve-clause pilot on Milvus and Qdrant finds preliminary evidence that cross-model validation misses 2 of 5 task-intrinsic clauses while source-grounded falsification catches all 12.

### Core Strengths

- **S1:** The two-layer reliability problem (family-specific vs. task-intrinsic documentation-interpretation errors) is a well-motivated and clearly articulated contribution that advances our understanding of when LLMs can serve as reliable oracles — see 2.1, 2.2.
- **S2:** Source-grounded falsification is a sound technical approach that correctly treats implementation as the most accessible source of actual behavior for resolving task-intrinsic errors, and the distinction from MASTOR's use of source is sharp — see 3.1.
- **S3:** The bidirectional reachability probe with VDBFuzz (Table 2) provides concrete evidence for the structural asymmetry between crash oracles and documentation-implementation oracles, and the version-level mapping (v1.4.0, v1.18.0, v1.18.2) is now verifiable — see 4.1.
- **S4:** The 111-issue yield with 38 maintainer-acknowledged defects demonstrates that TestVDB surfaces real bugs, and the 81% false-positive suppression from source-grounding is a strong quantitative result — see 4.2.
- **S5:** The within-vendor contrast on Qdrant (over-strict on optional-default parameters `timeout`, `group_size`, `score_threshold`; correct on explicit-bound parameters `shard_number`, `replication_factor`) provides compelling evidence that documentation style, not vendor, drives over-formalization risk — see 4.3.

### Core Weaknesses

- **W1:** The RQ3 probe is limited to twelve clauses (n=12), and the task-intrinsic rate estimate (5/12, Wilson 95% CI [19%, 68%]) has very low precision; the paper correctly flags this as preliminary, but the central claim about task-intrinsic errors rests on this small sample — see 3.2 [major, fixable].
- **W2:** The `k=1.0` cross-model verification uses a "diversity-stratified, non-random sample" of twenty candidates, but the paper provides no details on how stratification was performed or why this sample is representative beyond subtype diversity claims — see 3.3 [minor, fixable].
- **W3:** The version/issue table (Table 2) is a good addition, but the paper still does not fully explain why VDBFuzz's template suite hardcodes `wait=true` in every Qdrant points-upsert template; this is asserted as a limitation of VDBFuzz's current coverage but not verified from the VDBFuzz paper/artifact — see 4.1 [minor, fixable].

### Detailed Assessment

1. **Significance** — Excellent
   - **1.1** The problem is real: documentation-implementation defects in VDBMSs corrupt query semantics and are costly in production (§1). The roadmap and empirical bug study motivate this well.
   - **1.2** The 85% residual quantification (composition of findings, not population estimate) is appropriately scoped and demonstrates that this is a large class unreachable by classical methods — see 4.1.
   - **1.3 [minor, fixable]** External validity is bounded: statistical claims rest on Milvus and Qdrant only, and Weaviate/MeiliSearch/Chroma contribute breadth rather than weight. The paper states this clearly, but it limits the generalizability of the quantitative claims — see 4.5.

2. **Novelty** — Excellent
   - **2.1** The two-layer reliability problem is a clear non-obvious delta over prior LLM-as-judge work. Prior work (Panickssery et al., Haldar et al.) addresses self-preference and intra-judge inconsistency, but the task-intrinsic layer—where documentation ambiguity causes stable misinterpretation across families—is new and well-scoped — see 2.1.
   - **2.2** Source-grounded falsification is correctly distinguished from MASTOR's use of source. MASTOR reads source to test what the implementation does (source as reference); TestVDB reads source to test what the documentation prescribes (source as falsifier for actual behavior). The paper's positioning in §3 and §7 is sharp — see 3.1, §7.
   - **2.3** The documentation-implementation residual concept is novel in VDBMS testing. Prior work (VDBFuzz, metamorphic relations) addresses correctness and crashes; TestVDB targets a distinct class that those methods cannot reach — see 4.1, Table 1.
   - **2.4** Checked the delta against VDBFuzz: the paper's characterization is fair. The bidirectional probe (Table 2) shows that each tool's target defect reproduces on different versions, and the structural hypothesis (crash on documented-valid input is itself a doc-impl violation) is sound — see 4.1.
   - **2.5** Checked the delta against AGORA+, SATORI, MASTOR: the paper's characterization holds. These tools extract from structured sources (traces, OpenAPI, source) where constraints are explicit; TestVDB targets natural-language documentation where interpretation is required. The source-ambiguity gap is the real novelty — see 2.1, §7.

3. **Soundness** — Adequate
   - **3.1** The 81% false-positive suppression claim (54-candidate retrospective) is strong: Wilson 95% CI [55.7%, 80.1%] on adjudicated pool. The three-condition ablation (source alone 75%, threat-model alone 50%, union 91%) isolates the source-grounded anchor as the dominant contributor — see 4.2.

The task-intrinsic rate is 5/12 (CI [19%, 68%]), which is too imprecise to strongly support the claim that "cross-model validation cannot resolve task-intrinsic errors." The paper correctly flags this as preliminary, but this is a central claim and the evidence is thin — see 4.3.

It states the sample spans five defect subtypes, but without knowing how those subtypes were defined or how sampling was performed, the `k=1.0` claim is hard to evaluate — see 4.2.

   - **3.5** The model-free invariant oracle subclass (RQ4) is the least design-contingent part of the evaluation and reproduces across Milvus and Qdrant. The 9 mathematical-invariant issues are classical-addressable and correctly counted within the ~10% non-documentation-implementation portion — see 4.4.

4. **Verifiability** — Excellent
   - **4.1** The paper now includes Table 2 mapping versions (v1.4.0, v1.18.0, v1.18.2) to what reproduces and fix state. This resolves the Round 2 verifiability concern about whether #9045 and the VDBFuzz crash co-occur or live on different versions — see 4.1.
   - **4.2** The paper now footnotes that every Qdrant points-upsert template in VDBFuzz's released suite uses `wait=true`, with #9045 on the `wait=false` path. This is a fair characterization and adequately sourced — see 4.1.
   - **4.3** Artifact promise: the paper states that full prompts, target versions, and per-token accounting will be released at a persistent URL upon acceptance. This is sufficient — see 3.
   - **4.4** The ablation-dataset footnote (added in Round 3) clarifies that the three-condition ablation is on a separate Milvus v2.6.19 control, so the two ablation groups (single-LLM/source/threat-model vs source/threat-model/union) are not directly comparable on identical data.    - **4.5** The "soft result correctness" → "result correctness" change (Round 3) is appropriate and removes the confusing qualifier — see 4.2.

5. **Presentation** — Excellent
   - **5.1** The paper structure is logical and complete: motivation, problem setup, LLM reliability analysis, TestVDB design, evaluation, related work, discussion.

   - **5.3** Table 1 (oracle exclusion) is an excellent decomposition of why each classical oracle misses the documentation-implementation residual.

## Reviewer 2: Area Specialist

**Overall Recommendation:** Weak Accept

### Summary
The paper addresses documentation-implementation consistency testing in vector database management systems (VDBMSs), a defect class where APIs silently accept inputs or behaviors that violate their API documentation. Because many documented boundaries are natural-language prose rather than formal specifications, the authors adopt an LLM to extract behavioral claims and judge consistency, but identify a two-layer reliability problem: family-specific self-preference (mitigated by cross-model validation) and task-intrinsic errors where ambiguous documentation causes different LLM families to converge on the same wrong claim (unmitigated by cross-model validation). The core contribution is source-grounded falsification: treat LLM-derived behavioral claims as refutable hypotheses and falsify them against implementation source code. TestVDB instantiated this approach, surfacing 111 candidate issues across five VDBMSs with 38 maintainer-acknowledged defects. A controlled retrospective shows the source anchor suppresses 81% of false positives (up from 31%) at 96.7% true-positive retention. A twelve-clause pilot on task-intrinsic errors finds that cross-model judging misses 2 of 5 task-intrinsic clauses while source-grounded falsification catches all 12.

### Core Strengths
- **S1:** Clear problem articulation and oracle exclusion rationale (Table 1) — see 1.1, 2.1
- **S2:** Source-grounded falsification as a well-motivated counter to task-intrinsic LLM interpretation errors — see 3.1
- **S3:** Demonstrated reduction in false positives (81% suppression) while maintaining true-positive retention (96.7%) — see 3.3
- **S4:** Proper scoping of claims: treats the RQ3 probe as preliminary evidence with explicit confidence intervals — see 3.4
- **S5:** Related work coverage accurately positions the source-ambiguity gap against AGORA+, SATORI, MASTOR — see 2.2

### Core Weaknesses
- **W1:** RQ3 task-intrinsic probe size (n=29) limits statistical confidence despite proper scoping — see 3.2 [major, fixable]
- **W2:** No estimation of recall (no ground-truth defect catalog for VDBMSs) — limits yield interpretation — see 3.5 [major, unfixable]

### Detailed Assessment

#### 1. Significance — Adequate
- **1.1** The problem is real and practically motivated. VDBMSs are critical infrastructure for retrieval-augmented LLM applications, and the roadmap identifies oracle definition as a key challenge. The paper targets a defect class (about 85% of findings) that classical oracles cannot reach, and Table 1 clearly maps where each classical oracle fails and why the documentation-implementation residual forces an LLM-derived oracle. This is meaningful but bounded impact—useful for VDBMS testing and potentially transferable to other systems with natural-language documentation, but not a fundamental shift in the broader testing field.
- **1.2 [major, fixable]** The 111-submission yield is substantial in absolute terms, but the maintainer-acknowledgment rate (34%, 38/111) and the concentration on two VDBMSs (Milvus and Qdrant) suggest the approach may be high-variance. The paper does not estimate recall because no ground-truth catalog exists, which is acknowledged as a limitation, but this limits the interpretation of the yield—why 22 for Milvus vs. 3 for Weaviate? Is it documentation style, implementation maturity, or TestVDB's coverage? The authors flag this as breadth-only for Weaviate/MeiliSearch/Chroma, which is honest, but it leaves the significance question partially answered.

#### 2. Novelty — Excellent
- **2.1** The source-ambiguity gap is a genuine novel contribution. Prior REST-API oracle work (AGORA+, SATORI, MASTOR) operates on low-ambiguity structured sources (execution traces, OpenAPI schemas, source code) where the LLM's role is transcription of explicit constraints. TestVDB targets high-ambiguity natural-language documentation where the LLM must interpret intent, and interpretation is unreliable. The paper correctly characterizes this as a different problem class, not an incremental improvement. The novelty delta is clear: TestVDB addresses a regime that prior work does not and cannot enter, because the fundamental problem (ambiguous natural-language documentation vs. structured specifications) is different.
- **2.2** The directional distinction from MASTOR is critical and correctly drawn. MASTOR reads source to test what the implementation does (implementation → oracle), so it cannot detect a gap between documentation and code. TestVDB reads source to falsify documentation-derived clauses (documentation → clause → falsify against implementation), targeting exactly that gap. This is not a minor repositioning—it is a fundamentally different testing objective. The related work section nails this distinction.
- **2.3** The two-layer reliability model (family-specific vs. task-intrinsic) is novel. Panickssery et al. establish self-preference bias in LLM-as-judge evaluation, and Haldar et al. study intra-judge inconsistency. The paper's contribution is to identify a third, orthogonal layer: task-intrinsic stability at the extraction step, where ambiguous documentation causes different families to converge on the same wrong clause, and this error survives cross-model validation. The twelve-clause pilot (RQ3) provides preliminary evidence, and the specificity check on explicit-bound parameters (0/13 over-strict) reinforces that the phenomenon concentrates in ambiguous optional-default APIs. This is a novel observation about LLM interpretation behavior in a testing context.
- **2.4** The VDBFuzz bidirectional reachability analysis (Table 2) correctly positions the two tools as complementary rather than competitive. The structural hypothesis (crash oracles detect crashes; documentation-implementation oracles detect silent accepts) is sound and illustrated with two controlled cases (v1.4.0 and v1.18.0). The paper is careful to note that each direction is n=1 and these are hypothesis-generating cases, not generalized results, which is appropriate scoping.

#### 3. Soundness — Adequate
- **3.1** The RQ1 yield composition (85% documentation-implementation residual) is structurally supported. The authors classify each of the 111 submitted issues by fault model (classical-addressable, documentation-implementation, concurrency), and Table 1 maps why each classical oracle fails. This is not an estimate of the true defect distribution (the paper is explicit about this), but it is a coherent characterization of TestVDB's findings. The structural check on Qdrant v1.18.2 (metamorphic relations found no violations, consistent with the claim that mathematical-invariant violations are the domain of the model-free subclass) is a good sanity check.
- **3.2 [major, fixable]** The RQ3 task-intrinsic probe, while properly scoped as preliminary with confidence intervals (Wilson 95% CI: [19%, 68%] for the 5/12 rate, [33%, 77%] for the pooled 9/16 rate), is still small (n=29 clauses across three subtypes). The central claim—that cross-model validation cannot resolve task-intrinsic errors and source is needed—rests on this evidence. The authors treat it as pending a larger study, which is honest, but the small n keeps the statistical confidence at the boundary between Adequate and Excellent. A larger head-to-head study (the paper notes one is ongoing) would strengthen this claim substantially.
- **3.3** The RQ2 precision results are solid. The 81% false-positive suppression (up from 31% without the source anchor) on the controlled retrospective (54 adjudicated candidates) is a clear effect size. The three-configuration ablation (single-LLM self-judgment 25.5%, single source-grounded cycle 45.6%, full multi-agent debate 69.2%) isolates where the precision comes from. The Milvus re-probe (27 candidates) showing the clean-reproduction anchor kills tooling-artifact FPs at 12/14 but by-design ones at only 2/11, followed by the three-condition ablation (source alone 75%, threat-model alone 50%, union 91%), is a strong isolation of the source-grounded anchor as the dominant contributor. The Wilson CIs are properly reported, and the authors flag the pending-resolution worst-case bound transparently.
- **3.4** The κ=1.0 cross-model check is well-motivated. The paper describes the twenty-candidate sample as "diversity-stratified, non-random" chosen to span input-validation, upsert-semantics, idempotent-drop, correct-reject, and dynamic-field subtypes, which is appropriate for checking whether the source-grounded verdict is family-specific. The κ=1.0 agreement between GLM-5.2 and DeepSeek is strong evidence that the verdict is not strongly family-specific when source evidence is explicit. This resolves the Round 2 concern about selection adequately—the authors are now explicit about the sampling strategy and its rationale.
- **3.5 [major, unfixable]** No recall estimation is possible because no public ground-truth defect catalog exists for VDBMSs. The authors acknowledge this limitation, but it is an inherent gap. We know TestVDB found 38 acknowledged defects, but we do not know how many it missed. This limits the interpretation of the yield—particularly the vendor-wise differences (22 Milvus vs. 3 Weaviate)—to breadth-only claims. The honest acknowledgment prevents this from being a fatal flaw, but it bounds the Soundness rating at Adequate.

#### 4. Verifiability — Excellent
- **4.1** The paper is fully self-contained as text. The evaluation sections (RQ1–RQ4) describe the experimental setup, target VDBMSs and versions, candidate pools, and adjudication processes in sufficient detail to follow the methodology. The implementation section describes the multi-agent pipeline, model backbone (GLM-5.2 via Claude Code runtime), Docker-pinned target versions, and cost estimate (on the order of $10^4$ LLM calls, roughly $10 per target at current pricing). The full prompts, target versions, and per-token accounting are promised in the artifact at a persistent URL upon acceptance, which is the appropriate level of detail for a technical paper.
- **4.2** The version/issue timeline (Table 2) resolves the Round 2 concern about reproducibility. The table clearly maps which Qdrant version reproduces which defect (VDBFuzz's crash on v1.4.0, TestVDB's #9045 on v1.18.0, both fixed on v1.18.2). This addresses the concern about temporal alignment and allows a reader to verify the bidirectional reachability claims.
- **4.3** The ablation dataset footnote (RQ2) resolves the Round 2 concern about comparability. The paper now explicitly states that the single-LLM/single-cycle/full configurations are measured on the retrospective adjudicated pool, while the source/threat-model/union ablation is on a separate Milvus v2.6.19 control, so the two groups are not directly comparable on identical data. This is honest and prevents misinterpretation.

#### 5. Presentation — Excellent
- **5.1** The structure is sound and readable. The progression from problem setup to design to evaluation is logical. The abstract efficiently communicates the problem, approach, and key results. The related work section cleanly positions the paper against prior work.
- **5.2 [minor, fixable]** Language and formatting are clean. The writing is clear, with only minor typographical opportunities (e.g., "on the order of" could be "approximately" for brevity). The LaTeX structure appears correct (no stripping failures observed).

### Questions for Authors
- **Q1:** Beyond the ongoing larger head-to-head study for RQ3, do you have plans to estimate recall or construct a ground-truth defect catalog for a subset of VDBMSs? — see 3.5
- **Q2:** Can you characterize the vendor-wise yield differences (22 Milvus vs. 3 Weaviate) in more detail? Is this driven by documentation style, implementation maturity, or TestVDB's coverage? — see 1.2
- **Q3:** For the VDBFuzz bidirectional reachability, have you considered expanding the n=1 per direction to a more systematic controlled study, or do you view the structural hypothesis as sufficiently validated by the current cases? — see 2.4

## Reviewer 3: General Reviewer

**Overall Recommendation:** Weak Accept

### Summary
The paper introduces TestVDB, a system for detecting documentation-implementation defects in Vector Database Management Systems (VDBMSs) where the system silently accepts inputs or produces behaviors that violate their API documentation. The authors argue that classical oracles (crash detection, differential testing, metamorphic relations, property-based testing) cannot reach approximately 85% of these defects, leaving an LLM-derived oracle as the practical approach. They identify a two-layer reliability problem in LLM-derived oracles: family-specific self-preference bias (mitigated by cross-model validation) and task-intrinsic errors where ambiguous documentation causes different LLM families to converge on the same wrong claim (unmitigated by cross-model validation). Their solution is source-grounded falsification, which treats LLM-derived behavioral claims as refutable hypotheses checked against implementation source code. TestVDB surfaced 111 candidate issues across five VDBMSs; maintainers acknowledged 38 as defects. A controlled retrospective shows the source anchor suppresses 81% of false positives while retaining 96.7% of true positives.

### Core Strengths
- **S1:** Clear problem framing and structural analysis of why classical oracles fail for documentation-implementation defects — see §1 (Introduction) and Table 1 (tab:exclusion), which methodically maps each oracle class to the defect subclass it reaches and explains why the residual forces an LLM-based approach.
- **S2:** Well-delineated two-layer reliability analysis of LLM-derived oracles, with a precise scoping of task-intrinsic stability as an extraction-level property across model families — see §3 (sec:regime), which cleanly separates family-specific from task-intrinsic errors and defines the stability claim.
- **S3:** Substantive evidence base with 111 issues submitted across five VDBMSs and 38 maintainer-acknowledged defects, providing concrete grounding for the approach's practical yield — see §6 (sec:eval), RQ1, and Table 3 (tab:yield).
- **S4:** Strong methodological contribution in separating family-specific from task-intrinsic documentation-interpretation errors, with preliminary but compelling evidence that cross-model validation misses task-intrinsic cases while source-grounded falsification catches them — see §6, RQ3, and Table 4 (tab:e2).
- **S5:** Improved Round-3 revisions: Table 2 (tab:versions) now clearly maps the bidirectional reachability experiment across Qdrant versions v1.4.0/v1.18.0/v1.18.2 with fix states, resolving the version/issue mapping confusion from Round 2.

### Core Weaknesses
- **W1:** RQ3 task-intrinsic evidence remains preliminary despite clearer framing — the twelve-clause probe is now explicitly labeled as "preliminary evidence" and "pending a larger study" in the abstract and contributions, but the core finding (5/12 task-intrinsic rate, cross-model judging misses 2/5) still rests on a small, non-random sample that the authors themselves treat as a pilot. This weakens the central claim that source-grounded falsification is necessary for task-intrinsic errors. — see 3.2, 3.3
- **W2:** External validity and generalizability are limited — the abstract already states "about 85%" as the composition of findings rather than a population estimate, and §6 acknowledges that Weaviate, MeiliSearch, and Chroma contribute "breadth rather than statistical weight," but this leaves the quantitative claims (85% residual, 81% FP suppression, 96.7% TP retention) heavily dependent on Milvus and Qdrant. A general reader cannot assess how well these results would transfer to other VDBMSs or documentation styles. — see 1.1, §6
- **W3:** The 85% composition claim is buried in terminology — the abstract and intro mention "about 85%" as a composition figure, but the label "composition of our findings, not a population estimate" appears only in the abstract and is not reinforced in §6 where the classification is presented. A reader skimming RQ1 might misinterpret this as an estimated prevalence. — see 5.1 [minor, fixable]

### Detailed Assessment

1. **Significance** — Adequate
   - **1.1** The problem addressed — documentation-implementation defects in VDBMSs where systems silently accept violating inputs — is practically significant. As §1 notes, these defects corrupt query semantics and can return data the documentation intended to exclude, with empirical support from a bug study finding more than half of VDBMS bugs manifest as functional failures. The practical impact is clear: these defects affect the correctness of RAG applications that depend on VDBMSs for embedding storage.
   - **1.2 [major, unfixable]** However, the significance of the core methodological contribution — source-grounded falsification — is bounded by the narrow setting it targets. The approach applies to documentation-implementation consistency testing where documentation is natural-language prose and implementation source is available. This is a specialized subset of the broader VDBMS testing problem (result correctness, ANN recall, ranking are explicitly out of scope per §2), and the approach itself does not transfer to closed-source systems. The significance is therefore meaningful but limited to this specific testing niche.
   - **1.3** The broader significance claim — that this setting extends beyond VDBMSs to "REST APIs without OpenAPI coverage, configuration validation, and policy-as-code checks" (§8) — is speculative and not empirically validated in the paper. The authors acknowledge they "have not tested these transfers and leave them to future work," so the broader significance remains hypothetical.

2. **Novelty** — Adequate (provisional)
   - **2.1** The paper clearly delineates its novelty delta against prior work. §3 (sec:regime) and §7 (sec:related) establish that prior REST-API oracle tools (AGORA+, SATORI, MASTOR) extract from structured sources (OpenAPI specs, traces, source) where constraints are explicit, whereas TestVDB extracts from ambiguous natural-language documentation where the LLM must interpret intent. This is a genuine methodological distinction: prior work avoids the reliability problem TestVDB addresses by staying in low-ambiguity regimes.
   - **2.2** The two-layer reliability framework — separating family-specific self-preference bias (mitigated by cross-model validation) from task-intrinsic documentation-interpretation errors (unmitigated) — is novel and precisely scoped. This is a non-obvious insight: the observation that cross-model validation cannot resolve errors arising from shared input ambiguity is a meaningful contribution to LLM-as-judge reliability analysis.
   - **2.3 [provisional]** As a general reviewer without field context, I assess novelty from the paper's own characterization against the cited works. The paper cites and positions against AGORA+, SATORI, MASTOR, VDBFuzz, Toradocu, Doc2OracLL, AugmenTest, ChatAssert, Testora, and others. The claimed delta — source-grounded falsification targeting task-intrinsic interpretation errors in ambiguous documentation — appears credible from this internal characterization. However, without surveying the broader REST-API testing and LLM-as-judge literature myself, I flag this novelty assessment as provisional.
   - **2.4** The source-grounded falsification approach itself — treating LLM-derived claims as refutable hypotheses checked against implementation source — is presented as distinct from MASTOR's use of source. The paper argues MASTOR tests what the implementation does (with source as reference) and cannot detect documentation-implementation gaps, whereas TestVDB tests what the documentation prescribes (with source as reference for actual behavior). This distinction appears sound from the paper's description, though I cannot independently verify MASTOR's actual behavior.

3. **Soundness** — Adequate
   - **3.1** The core claims are supported by appropriate methods. RQ1 (yield and documentation-implementation residual) uses a clear classification scheme (classical-addressable, documentation-implementation, concurrency) applied to all 111 submitted issues, with explicit acknowledgment that the 85% figure is a composition of findings, not a prevalence estimate. The structural check — running a classical-oracle suite (metamorphic relations) on Qdrant v1.18.2 to confirm it finds no documentation-implementation defects — provides corroborating evidence that the residual is real.
   - **3.2 [major, fixable]** RQ3 (cross-model validation vs source on task-intrinsic errors) is the weakest link in the evidence chain. The twelve-clause probe, now explicitly framed as preliminary, tests the central claim that source-grounded falsification catches task-intrinsic errors that cross-model validation misses. The probe design is methodologically sound: two LLM families (GLM and DeepSeek) independently formalize documentation, then DeepSeek judges GLM's clauses, then source contradicts all over-strict clauses. However, the sample size (n=12) is small, and the task-intrinsic rate of 5/12 has a wide Wilson 95% CI [19%, 68%]. The authors treat this as "pending a larger study," which understates the claim's dependence on this pilot. The extension to 29 clauses (adding 4 behavior over-strict and 13 explicit-bound negatives) strengthens the pattern but does not eliminate the small-sample concern. The core finding — that cross-model validation misses task-intrinsic errors — rests on limited evidence.
   - **3.3** RQ2 (effect of source-grounded falsification) uses a well-controlled retrospective design. The 54-candidate adjudicated pool (38 acknowledged, 12 by-design, 4 rejected) provides a solid base. The precision measurements (69.2% end-to-end, 81% FP suppression with source anchor) include appropriate confidence intervals (Wilson 95% CI). The ablation study (single-LLM 25.5%, single-source-cycle 45.6%, full multi-agent 69.2%) cleanly isolates the contribution. The three-condition ablation on Milvus v2.6.19 (source alone 75%, threat-model alone 50%, union 91%) further validates the source anchor as the dominant contributor. The cross-model check (DeepSeek re-running 20 candidates, Cohen's κ=1.0) strengthens the claim that source-grounded verdicts are not family-specific when source evidence is explicit.
   - **3.4** The bidirectional reachability experiment with VDBFuzz (Table 2, tab:versions) is now clearly presented following Round 2 revisions. The table maps Qdrant versions v1.4.0/v1.18.0/v1.18.2 to what reproduces (VDBFuzz's integer-overflow crash, TestVDB's #9045) and fix states. The authors correctly treat each direction as n=1 and "hypothesis-generating controlled cases" rather than generalized results. The structural hypothesis — crash oracles cannot reach silent accepts, while documentation-implementation oracles can reach crashes where the input violates a documented bound — is presented as speculative, with the two cases consistent with it but not establishing it.
   - **3.5** Threats to validity (§6, Threats to validity) are appropriately discussed. Internal validity acknowledges the RQ3 probe's contingency and notes that the over-strict subset "remains the most contingent finding." External validity correctly bounds generalization (Weaviate/MeiliSearch/Chroma are breadth-only; statistical claims rest on Milvus/Qdrant). Construct validity acknowledges the single-model-family limitation (GLM-5.2) and notes the cross-model check (κ=1.0) but correctly states they do not estimate recall due to lack of a public ground-truth defect catalog.

4. **Verifiability** — Adequate
   - **4.1** The paper provides sufficient methodological detail to follow how the evidence was produced. §5 (sec:impl) describes the multi-agent pipeline setup (20 agents on Claude Code runtime, GLM-5.2 backbone, no fixed random seed). A reachable artifact link is not provided in the text. It is declared but not reachable from the text provided.
