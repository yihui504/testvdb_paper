## Reviewer 1: Domain Expert

**Overall Recommendation:** Accept

### Summary
TestVDB targets API compliance defects in Vector Database Management Systems (VDBMSs)—bugs where a system silently accepts inputs or produces behaviors that violate its documented contract (e.g., accepting `nprobe=0`, silently normalizing invalid parameters, or returning success where rejection is prescribed). The core problem is that compliance defects produce no crash or exception signal, leaving no practical oracle for existing fuzzers like VDBFuzz (crash-only) and no reference implementation for differential testing across divergent VDBMS APIs. The authors propose TestVDB, an LLM-driven system that auto-derives a contract oracle from API documentation and applies Contract-Truth Separation (CTS)—a design principle that isolates LLM-generated assertions (contract + judgment) from a truth layer (maintainer authority via source code, PRs, issue history) that falsifies them. This is motivated by "contract hallucination propagation": when one LLM family both generates a contract and judges compliance, hallucinated constraints are self-confirmed (25% of adjudicated submissions were marked by-design—stricter than true intent). The dev-reviewer agent implements CTS via three anchors: clean reproduction, source-grounded verification (primary), and threat-model cross-check (ablated as a noisy complement). On a controlled retrospective over 52 maintainer-adjudicated candidates, the source anchor lifts false-positive suppression from 31% to 81% while retaining 96.7% of true positives. End-to-end, TestVDB produced 111 submissions across five VDBMSs; maintainers acknowledged 36 (28 fixed, 8 accepted), yielding adjudicated precision of 69.2% within [43.9%, 80.5%] sensitivity bounds. The paper honestly scopes its contribution: boundary/validation compliance (75% of yield), complementary to crash-focused fuzzing; soft result-correctness (ANN recall) remains open. A model-free invariant oracle subclass (cosine distance > 1.0 for identical vectors, incomplete index results, payload-filter violations) is identified as the most defensible technical finding—violates hard mathematical bounds, needs no LLM judgment, reproduces across Milvus and Qdrant.

### Core Strengths
- **S1:** First practical LLM-driven system for a real, high-impact problem (43% of VDBMS bugs are incorrect-behavior, no oracle exists) — see 1.1, 2.1
- **S2:** Contract-Truth Separation is a novel, well-motivated design principle addressing a genuine LLM failure mode (contract hallucination propagation) — see 1.2, 2.2
- **S3:** Rigorous evaluation design with controlled retrospective, same-population ablations, and honest sensitivity analysis — see 3.1, 3.2, 3.3
- **S4:** Model-free invariant oracle subclass is independently valuable and adoptable outside TestVDB — see 2.3
- **S5:** Presentation is exceptionally clear after recent overhaul — abstract scannable, structure navigable, evaluation well-signposted

### Core Weaknesses
- **W1:** Cross-system generalization claimed only for Milvus and Qdrant; Weaviate submissions largely undiagnosed, limiting broader claims — see 3.1 [major, fixable]
- **W2:** Threat-model anchor contribution under-validated (n=12 ablation, unstable across runs) — see 3.4 [major, unfixable with current data]
- **W3:** VDBFuzz comparison lacks head-to-head empirical data; complementarity argued from oracle definitions only — see 2.1 [minor, fixable]

### Detailed Assessment

1. **Significance** — Adequate
- **1.1** [Real-world impact] The problem is significant and under-served. VDBMSs underpin LLM applications (retrieval-augmented generation, recommendation, multimodal search), and the empirical study (Xie et al. 2025, cited as bugstudy25) shows that 43.0% of VDBMS defects are incorrect-behavior bugs—substantially outnumbering crash/hang bugs (23.1%). Yet current VDBMS testing skews toward the minority: VDBFuzz (the first dedicated VDBMS fuzzer) uses a crash oracle and detects only crash/hang bugs, leaving the majority without a practical oracle. The roadmap (Wang et al. 2025, cited as roadmap25) flags the oracle problem for incorrect behavior as the central open challenge: "poses significant challenges for test oracles," and approximate vector search renders traditional differential testing unsuitable. TestVDB targets a tractable, high-impact slice of this gap: API compliance defects, which admit the documented contract itself as an oracle where general result-correctness does not.
- **1.2** [Clear scope acknowledgment] The authors honestly position their contribution. They explicitly scope to boundary/validation compliance (75% of yield), complementary to crash-focused fuzzing (VDBFuzz). They do not claim to solve the roadmap's result-correctness direction (ANN recall, ranking error), which remains open. The acknowledgment that soft result-correctness "remains open" and that 75% of yield is boundary/validation is a sign of appropriate restraint. However, the significance is bounded by the narrowness of the compliance slice within incorrect behavior—state/logic and diagnostic-quality defects constitute only 14% of acknowledged TPs (5/36), and these are the ones uniquely requiring the full LLM pipeline. The incremental value over a spec-driven boundary fuzzer is real but confined.
- **1.3 [major, fixable]** [Cross-system evidence strength] The evaluation reports results across five VDBMSs (Milvus, Qdrant, Weaviate, MeiliSearch, Chroma), but yield and adjudication concentrate on Milvus (51 submissions, 14 fixed, 8 accepted) and Qdrant (26 submissions, 11 fixed). Weaviate has 30 submissions but only 3 fixed and 21 pending—largely undiagnosed. MeiliSearch (3 submissions) and Chroma (1 submission) contribute near-zero adjudicated signal. The paper claims cross-system generalization primarily for Milvus and Qdrant, with Weaviate/MeiliSearch/Chroma as breadth probes rather than statistical evidence. This is appropriate honesty, but it limits the significance of broader claims. Without more Weaviate adjudication, the claim of generalization beyond Milvus/Qdrant is speculative. A fixable weakness: additional Weaviate triage or a clearer framing that the contribution is "Milvus and Qdrant" not "five VDBMSs."

2. **Novelty** — Excellent
- **2.1** [First LLM-driven VDBMS compliance detector] TestVDB is, to the authors' knowledge and mine, the first end-to-end LLM-driven system for detecting API compliance defects in VDBMSs. Prior work: VDBFuzz (crash-oracle), RESTler/EvoMaster/Schemathesis (REST API fuzzing, schema-driven, crash-oracle), NoREC/TLP/DQE (database correctness oracles via reference SQL, absent in VDBMS), general LLM-as-judge patterns. None target semantic compliance against documented contracts in VDBMSs. The complementarity with VDBFuzz is genuine if VDBFuzz exists as described: VDBFuzz's crash oracle cannot detect non-crash compliance defects, so at most 1/36 of TestVDB's yield (the single crash case) could overlap. The lack of head-to-head empirical comparison is a minor gap (future work acknowledged), but the novelty is clear from the oracle class difference.
- **2.2** [Contract-Truth Separation (CTS) is novel] CTS is a well-motivated, novel design principle. Prior LLM-as-judge work (multi-agent verification surveyed by He et al. 2025, cited as he2025lma) does not separate the assertion layer (LLM-generated contract + judgment) from a truth layer (maintainer authority). The paper identifies a genuine failure mode: contract hallucination propagation. When one LLM family both generates the contract and judges compliance, hallucinated constraints are self-confirmed. The authors observe two forms: (1) fabricated provenance (a "complexity requirement" extracted from constant.go that in fact guards a historical performance regression, not a behavioral constraint) and (2) over-strict intent (12 of 48 adjudicated submissions, 25%, marked by-design—the contract demanded rejection of behaviors maintainers intended to allow). CTS breaks this self-confirmation by introducing an independent truth layer (dev-reviewer agent) that falsifies via source-grounded verification, clean reproduction, and threat-model cross-check. This is novel in LLM-driven testing—prior mitigations for hallucination (self-consistency, prompt-level consensus) do not use maintainer-authority evidence.
- **2.3** [Model-free invariant oracle subclass] The paper identifies a model-free invariant oracle subclass—violations of hard mathematical bounds that need no LLM judgment. Examples: cosine distance returning > 1.0 for identical vectors (bounded in [-1, 1]), incomplete index results (2 of 25 matching points returned), payload filters returning points with a missing field. This subclass reproduces across Milvus and Qdrant and is the paper's most defensible technical finding because it depends on no LLM judgment, violating expressible invariants. It is adoptable independent of TestVDB's LLM pipeline. This is a genuine novel contribution to the VDBMS testing toolkit.
- **2.4** [Delta over REST fuzzing and schema-driven testing] The paper correctly positions its delta over RESTler/EvoMaster/Schemathesis. RESTler (stateful REST API fuzzing, dependency inference) and Schemathesis (property-based testing on OpenAPI/GraphQL) require machine-readable specs. VDBMS REST endpoints do not serve standards-compliant OpenAPI (authors probed /swagger, /openapi.json on Milvus, all 404), so schema-driven fuzzers cannot be applied off-the-shelf. The authors concede that on the boundary/validation subset (75% of yield), a spec-driven fuzzer is effective (71% probe-to-accept rate in their 19-probe hand-written instance). TestVDB's marginal value lies where schema fuzzers cannot reach: (a) non-boundary probes (state/logic, diagnostic, result-correctness: 8/36 TPs), (b) CTS FP-suppression (schema fuzzer lacks source-grounded layer), (c) spec-gap bugs where docs are silent. This is a clear, honest delta.

3. **Soundness** — Adequate
- **3.1** [Controlled retrospective design] The evaluation design is a strength. The primary evidence for the dev-reviewer's contribution is a controlled retrospective on all 52 maintainer-adjudicated candidates (36 TP, 16 FP) under two blind conditions on the same population: claim-only (4-judge layer) vs. source-grounded (dev-reviewer's source anchor). Source-grounding lifts FP suppression from 5/16 (31%) to 13/16 (81%, 2.6x)—Milvus 33%→75%, non-Milvus 0%→100%—while retaining 29/30 TPs (96.7%; 6 TPs unreachable via API rate limits). This same-population comparison is clean evidence that CTS's source anchor provides significant FP suppression at minimal TP loss. The aggregate precision figure (69.2% = 36/52 acknowledged / (acknowledged + by-design + rejected)) is an end-to-end operating point, not the "after" arm of the retrospective (different denominator). The paper appropriately reports sensitivity bounds: [43.9%, 80.5%] based on 59 unadjudicated submissions (30 pending, 29 excluded). This is rigorous, honest evaluation.
- **3.2** [Baseline comparisons are comprehensive but asymmetrical] The paper compares against multiple baselines: single-layer counterfactual (removing FP-suppression chain, re-running on milvus v2.6.19, 27/27 live FPs confirmed), single-LLM (no multi-agent debate, no CTS), and schema-aware boundary fuzzer (19 probes, 71% probe-to-accept). Rows use different ground truths (LLM self-judgment / API-acceptance / blind re-triage / maintainer), so they are not directly comparable across tiers. The paper makes this asymmetry explicit in Table 3 and Figure 3 rather than drawing cross-tier conclusions, which is appropriate. The single-layer counterfactual (45.6% precision = 36/(36+16+27)) is directional evidence at zero recall cost, with the cleaner same-population 31%→81% as the head-to-head. However, the threat-model anchor baseline (Section 5.4) is weak: n=12 ablation (Milvus FPs only), unstable across runs (one boundary FP flipped), over-fires on state/concurrency. The paper reports it as a "noisy complement" and does not claim it as a validated contribution, which is honest but leaves the three-anchor design incompletely validated.
- **3.3** [Discovery recall measured but bounded] The paper goes beyond precision to measure recall via a held-out rediscovery study on 9 pre-2024 compliance bugs (qdrant/weaviate/milvus, GLM-5.2 training-data-external). TestVDB rediscovered 4/9 (44%; 4/7 of the testable, 2 blocked by SDK incompatibility). These 4 are independent held-out bugs (memorization canary: 0/9 recalled at issue-specificity), so this is genuine discovery recall, not memorization. Two bugs were already fixed in the tested version. The paper bounds the rest with two limits: spec-completeness (qdrant dimension-mismatch invisible to spec-derived contract) and version-pinning (milvus cosine>1.0 fixed before release). This is honest, bounded evidence—recall is modest (44%) but the paper explains the limits rather than overstating.
- **3.4 [major, unfixable]** [Threat-model anchor under-validated] The threat-model anchor is one of three CTS anchors but is inadequately validated. An earlier double-blind ablation returned negative due to a wiring gap (threat-modeler populated threat_model.json but dev-reviewer consumed developer_cognition.json). The re-run with fixed wiring on n=12 Milvus FPs shows source-alone 9/12 (75%), threat-alone 6/12 (50%, unstable), union 11/12 (92%), with 4/4 TP retention. Threat catches 2 source residuals but misses 5 state/concurrency FPs. The paper concludes threat is a "noisy complement" whose value is the union. This is honest reporting, but the evidence (n=12, unstable) is too weak to claim the three-anchor design as a contribution. The paper acknowledges this ("we do not claim the three-anchor design as a clean validated contribution on the strength of n=12") but it remains a gap in the evaluation of the CTS architecture. Fixable with larger ablation but unfixable with current data.
- **3.5 [minor, fixable]** [VDBFuzz comparison lacks empirical data] The paper argues complementarity with VDBFuzz based on oracle definitions (VDBFuzz's crash oracle cannot detect non-crash compliance defects, so at most 1/36 overlap) and notes that VDBFuzz's source contains no compliance-checking logic. However, there is no head-to-head empirical comparison on identical targets. The paper acknowledges this as future work, which is appropriate, but it leaves the complementarity claim theoretically grounded rather than empirically verified. A minor fixable weakness: a small joint study would strengthen the claim.

4. **Verifiability** — Excellent
- **4.1** [Complete, reproducible description] The paper provides sufficient detail to verify and replicate the work. Target VDBMS versions are pinned (Milvus 2.6.19 for ablations; full matrix in artifact). All 20 agents are LLM-driven (GLM-5.2, high-budget for 4 heavy-reasoning agents, low-budget for 16; both same backbone, differing in context window and max output tokens). The runtime configuration (Claude Code default sampling, no explicit temperature override) is specified. A full pipeline run per target invokes 20 agents over O(10–50) candidates; wall-clock dominated by dev-reviewer's source-grounding (repo clone, source retrieval) and live Docker re-probes. LLM call budget: ~10^4 calls (~10^7 tokens) total; per target, ~10^3 calls (~2×10^6 tokens), cost on order of $10 per target. Anonymized artifact at https://anonymous.4open.science/r/testvdb-anon-D644/ (to be public on acceptance) contains full prompts, version matrix, per-token/wall-clock accounting. This is complete, verifiable description.
- **4.2** [Threats to validity addressed comprehensively] The paper discusses 8 threat categories thoroughly: Internal (maintainer acknowledgment is weak ground truth, triage may reflect report clarity), Selection (111 submissions filtered from larger pool by novelty gate, candidate-to-submission ratio not instrumented), External (ablation is Milvus+Qdrant only, Weaviate largely undiagnosed), Construct (defect-type classification is title-based, pending per-defect confirmation), LLM variance (99.1% pairwise agreement on 5 independent re-adjudications), Contamination (GLM-5.2 may have seen pre-2024 Milvus source; memorization canary recalls general bug-class knowledge but 0/9 held-out issues at issue-specificity; contract counterfactual with DeepSeek reproduces over-strict constraints in 2/9), Recall scope (96.7% is judgment-layer TP retention, not end-to-end discovery; 4/9 held-out bugs rediscovered, bounded by spec-completeness and version-pinning), Excluded set (17/29 excluded are Milvus, closed-no-label may hide FP tail; bounded in Section 5.3: worst case 36/81=44.4%), Single-layer counterfactual (27 live FPs confirmed, bounded to one feedback cycle). This is comprehensive, honest threat discussion.

5. **Presentation** — Excellent
- **5.1** [Abstract is scannable after cut] The abstract has been overhauled and is now scannable. It clearly states: problem (43% incorrect-behavior VDBMS bugs, no oracle), slice (API compliance defects), approach (TestVDB, LLM-driven, auto-derives contract from docs, applies CTS), motivation (contract hallucination propagation when one LLM family generates contract and judges compliance), results (111 submissions, 36 acknowledged, controlled retrospective 31%→81% FP suppression at 96.7% TP retention, 69.2% aggregate precision). Key numbers upfront, concise.
- **5.2** [Structure is navigable] The paper structure is clear and follows a logical flow: Introduction → Background/Problem Formulation → Approach (overview, contract extraction, attack generation, CTS, novelty gate) → Contract Hallucination Propagation (standalone section) → Evaluation (RQ1 detection capability, RQ2 case studies, RQ3 precision with controlled retrospective/aggregate/sensitivity/baselines/anchor attribution, RQ4 threat-model anchor ablation, Threats to Validity) → Related Work → Conclusion. Section 5.3 (RQ3) is well-structured into subsubsections (Controlled Retrospective, Aggregate Precision, Sensitivity Analysis, Baseline Comparisons, Anchor Attribution), making the complex evaluation easy to follow. Threats to Validity is itemized (previously dense prose).
- **5.3** [Paragraphs are digestible] Sentences are rarely too long or dense. Examples: "By exclusion (Table 1), the only candidate oracle capable of flexible semantic judgment over an undocumented boundary is an LLM." (clear, concise). "When the same model family generates the contract and judges compliance, hallucinated constraints are self-confirmed." (punchy). - **5.4** [Evaluation is well-signposted] Tables and figures are clearly titled and explained. The evaluation text references tables/figures precisely ("Section 5.3", "Table 3", "Figure 3"). Excellent signposting.
- **5.5** [Language and formatting clean] No pervasive language errors or broken figures detected. LaTeX source is well-structured. ## Reviewer 3: General Reviewer

**Overall Recommendation:** Weak Accept

### Summary
The paper presents TestVDB, an LLM-driven system for detecting API compliance defects in Vector Database Management Systems (VDBMSs). These defects—where a system silently accepts inputs or behaviors that violate its documented contract—comprise 43% of VDBMS bugs but lack practical oracles, as current fuzzers detect only crashes. TestVDB auto-derives a contract oracle from API documentation and applies Contract-Truth Separation (CTS), isolating LLM-generated assertions from a truth layer that falsifies them via maintainer-authority evidence. The authors motivate CTS by identifying "contract hallucination propagation"—when one LLM family both generates a contract and judges compliance, hallucinated constraints are self-confirmed. Across five VDBMSs, TestVDB produced 111 submissions; maintainers acknowledged 36 issues (28 fixed, 8 accepted-open). In a controlled 52-candidate retrospective, the dev-reviewer's source anchor lifts false-positive suppression from 31% to 81% while retaining 96.7% of true positives. End-to-end adjudicated precision is 69.2% (within [43.9%, 80.5%] sensitivity). The authors also identify a model-free invariant oracle subclass (e.g., COSINE distance >1.0 for identical vectors) that violates hard mathematical bounds.

### Core Strengths
- **S1:** Contract-Truth Separation (CTS) directly addresses a real, identified failure mode—contract hallucination propagation—where hallucinated constraints are self-confirmed  — see 2.1, 2.2
- **S2:** The model-free invariant oracle subclass (COSINE >1.0 for identical vectors, incomplete index results, payload-filter violations) is the paper's most defensible technical finding—model-independent, reproducible, violates hard mathematical bounds, and adoptable independent of the LLM pipeline  — see 3.2
- **S3:** The presentation overhaul succeeds: the abstract is a clear entry point, Section 5.3's subsubsection structure makes the evaluation navigable, the Threats section's itemized format limits wall-of-text, and the contributions list is trimmed to three  — see 5.1

### Core Weaknesses
- **W1:** Cross-system generalization is claimed primarily for Milvus and Qdrant; Weaviate, MeiliSearch, and Chroma contribute near-zero adjudicated signal, making the "five VDBMSs" framing potentially overstated  — see 3.1 [major, fixable]
- **W2:** The threat-model anchor is reported as a noisy complement on only n=12 FPs (3/4 of the retrospective.s 16 FPs), yet the three-anchor design is presented as a contribution rather than an exploratory partial result  — see 3.3 [major, fixable]
- **W3:** External generalization beyond VDBMSs (REST APIs, configuration validation, policy-as-code) is claimed but not empirically validated  — see 2.1 [minor, fixable]

### Detailed Assessment

1. **Significance** — Adequate
- **1.1** The problem is real and clearly motivated: 43% of VDBMS bugs are incorrect-behavior defects (from a 1,671-bug empirical study), current tools (VDBFuzz) detect only crashes, and no practical oracle exists for the majority — see §1. The opening situates TestVDB as addressing an open challenge on the VDBFuzz roadmap.
- **1.2** The maintained, adjudicated ground truth (36 acknowledged true positives from 111 submissions, 28 fixed, 8 accepted-open) demonstrates practical impact on two systems (Milvus, Qdrant) — see §3.1, Table 3. The fix rate (28/36 acknowledged) is meaningful.
- **1.3** Scope is narrower than the framing suggests: "five VDBMSs" overstates generalization. Weaviate (30 submissions, 3 fixed, 21 pending), MeiliSearch (3 submissions, 0 adjudicated), and Chroma (1 submission, 1 pending) contribute near-zero adjudicated signal — see §3.1, Table 3. The paper honestly qualifies this ("yield concentrates on Milvus and Qdrant"), but the title/abstract/Introduction present "five VDBMSs" as equal contributors, which risks overclaim.
- **1.4 [major, fixable]** Boundary: 75% of yield is boundary/validation compliance; crash bugs are excluded by design (complementary to VDBFuzz); soft result-correctness (ANN recall, ranking) remains open — see §3.1. This is honest scoping, but the gap between "API compliance defects" (the title's focus) and "boundary/validation compliance" (75% of yield) should be clearer in the framing.

2. **Novelty** — Adequate
- **2.1** Contract-Truth Separation (CTS) is a clear, motivated design principle: isolating LLM-generated assertions from a truth layer that falsifies them via maintainer-authority evidence. The motivation—contract hallucination propagation, where hallucinated constraints are self-confirmed when one LLM family both generates and judges—is directly observed (25% of adjudicated submissions were by-design) — see §2, §5. This is a non-obvious delta over naive LLM-as-judge patterns.
- **2.2** The paper identifies a new failure mode in LLM-driven testing (contract hallucination propagation) and a principled mitigation (source-grounded falsification). This is a real, not manufactured, contribution — see §5. The distinction from self-consistency prompt-level approaches is clear.
- **2.3 [major, fixable]** External generalization (REST APIs, configuration validation, policy-as-code) is claimed in §7 ("CTS-style source-grounded falsification is the natural mitigation in each") but not empirically validated. This is a reasonable forward-looking statement but should be marked as speculation, not claimed generalization. The paper's evidence is entirely within VDBMSs.
- **2.4** The model-free invariant oracle subclass (COSINE >1.0 for identical vectors, incomplete index results, payload-filter violations) is a clean, model-independent contribution — see §3.2. It is adoptable independent of TestVDB's LLM pipeline and violates hard mathematical bounds, making it the least contingent finding.

3. **Soundness** — Adequate
- **3.1** The controlled retrospective (RQ3, same 52-candidate pool, blind re-triage) is methodologically sound: claim-only (4-judge) vs. source-grounded (dev-reviewer's source anchor), outcomes hidden via label-isolated agents. Source-grounding lifts FP suppression from 5/16 (31%) to 13/16 (81%) while retaining 29/30 TPs (96.7%) — see §5.3.1. This is a clean head-to-head on the same population.
- **3.2** The model-free invariant oracle cases are well-validated: COSINE distance >1.0 for identical vectors (reproduced on both Milvus and Qdrant), incomplete index results (2/25 matching points returned), payload filter violations. These are hard invariant violations, not semantic judgment calls — see §3.2. This is the paper's most defensible technical result.
