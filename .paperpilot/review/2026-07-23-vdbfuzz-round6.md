## Reviewer 1: Domain Expert

**Overall Recommendation:** Accept

### Summary

This paper introduces TestVDB, a tool that detects documentation-implementation defects in Vector Database Management Systems (VDBMSs) through source-grounded falsification of LLM-derived behavioral claims. The authors identify a gap in the testing landscape: VDBMS API documentation is natural-language prose rather than structured specifications, making accept/reject decisions impossible to mechanically check without semantic interpretation. This forces an LLM into the testing pipeline, but LLM interpretation is unreliable in two ways: family-specific self-preference (mitigated by cross-model validation) and task-intrinsic errors where ambiguous documentation causes different LLM families to converge on the same wrong claim. TestVDB addresses the task-intrinsic layer by treating LLM-derived behavioral claims as refutable hypotheses and falsifying them against source code.

Across five VDBMSs (Milvus, Qdrant, Weaviate, MeiliSearch, Chroma), TestVDB surfaced 111 candidate issues, yielding 50 true-positive defects (36 confirmed: 32 maintainer-acknowledged + 4 fixed via merged PRs; 14 with open fix-PRs). About 85% of these are documentation-implementation defects unreachable by classical oracles. A controlled retrospective on 48 adjudicated candidates shows the source-grounded dev-reviewer reaches 67% precision and 74% recall (3-run ensemble), versus 37% recall without the source anchor. The authors demonstrate that cross-model validation misses 3 of 6 task-intrinsic clauses while source-grounded falsification catches all 18, and that over-strict interpretation concentrates in optional-default APIs (Milvus and Qdrant search parameters) and is absent where documentation states explicit bounds (Weaviate).

### Core Strengths

- **S1:** The paper identifies a real, under-explored testing gap — natural-language documentation-implementation consistency — and provides a principled, empirically-grounded solution (source-grounded falsification). See §1, §4.

- **S2:** The two-layer reliability framework (family-specific vs. task-intrinsic) is precise, well-scoped, and empirically validated through eighteen-clause and behavior-level probes. See §4, RQ3.

- **S3:** The 50 true-positive defects (36 confirmed, 14 with open fix-PRs) represent substantial real-world impact, with 69.4% yield precision on maintainer-adjudicated cases. See RQ1.

- **S4:** The bidirectional VDBFuzz head-to-head (RQ1, Table 2) provides methodologically sound evidence that documentation-implementation oracles can reach crash-class defects at the subset where crash-triggering inputs violate documented bounds, while crash oracles under current template coverage do not reach silent-accept documentation-implementation defects.

- **S5:** The RQ3 within-vendor contrast (over-strict in optional-default parameters like `ef`, `nprobe` on Milvus and `timeout`, `group_size`, `score_threshold` on Qdrant; absent where docs state explicit minimums like `shard_number` ≥ 1) is a clean, falsifiable prediction validated by impl-confirmation. See RQ3.

- **S6:** The cross-model verification (DeepSeek re-running the dev-reviewer on 20 candidates, Cohen's κ=1.0) strengthens the claim that source-grounded verdicts are not family-specific when source evidence is explicit. See RQ2.

### Core Weaknesses

- **W1:** The single-run variance disclosure (recall ranges 15–78% across five independent runs; accuracy 44–65%) is notable, but the authors address it by reporting the 3-run any-confirmed ensemble as the variance-reduced operating point. See RQ2.

- **W2:** The RQ3 task-intrinsic rate estimates (6/18 parameter-TI, 11/11 behavior-TI) have wide confidence intervals due to small sample sizes, though the directional claim (cross-model validation misses task-intrinsic errors) is robust. See RQ3.

- **W3:** The bidirectional VDBFuzz head-to-head is n=1 per direction, which the authors correctly frame as hypothesis-generating rather than definitive. See RQ1, Table 2.

- **W4:** The 85% documentation-implementation residual composition is the composition of TestVDB's findings (biased toward this defect class by design), not a population estimate, which the authors acknowledge. See RQ1.

- **W5:** Weaviate, MeiliSearch, and Chroma are breadth-only coverage; statistical claims rest on Milvus and Qdrant only, which the authors scope as a limitation. See RQ1, Threats to Validity.

### Detailed Assessment

**1. Significance** — Excellent

- **1.1** The problem addressed is significant and under-explored. VDBMSs are critical infrastructure for retrieval-augmented LLM applications, and the empirical bug study (bugstudy25) finds more than half of VDBMS bugs manifest as functional failures. The roadmap (roadmap25) identifies oracle definition as a key challenge. TestVDB targets a prevalent defect class (documentation-implementation consistency) that the roadmap's existing tools (crash oracles like VDBFuzz, differential testing, metamorphic relations) cannot reach. See §1.

- **1.2** The real-world impact is substantial. 50 true-positive defects across three major VDBMSs (Milvus, Qdrant, Weaviate), with 36 confirmed by maintainers (32 acknowledged + 4 fixed via merged PR) and 14 with open fix-PRs, represent actionable findings that improve system reliability. The yield precision (69.4% on maintainer-adjudicated cases; Wilson 95% CI [58.0%, 78.9%]) shows the approach is practical. See RQ1.

- **1.3** The approach generalizes beyond VDBMSs. The authors identify that any system with natural-language documentation (REST APIs without OpenAPI, configuration validation, policy-as-code) enters the same regime where LLM-as-judge faces two-layer unreliability. Source-grounded falsification is a natural mitigation. While they have not tested these transfers (acknowledged as a limitation), the conceptual contribution is clear. See §6.

**2. Soundness** — Adequate

- **2.1** The main claims are supported by appropriate methodology. The two-layer reliability framework (family-specific vs. task-intrinsic) is precisely scoped and empirically validated. The family-specific layer is an instance of established self-preference bias (Panickssery et al., Wataoka and Takahashi). The task-intrinsic layer is defined at the extraction level across model families, distinct from Haldar et al.'s intra-judge self-inconsistency. The eighteen-clause probe (DeepSeek reproducing GLM's over-strict clauses in 6 of 18 parameters) and behavior-level probe (11/11 idempotency behaviors) support the claim that cross-model validation misses task-intrinsic errors. See §4, RQ3.

- **2.2 [major, fixable]** The RQ2 controlled retrospective has methodological strengths but also notable limitations. The 48-candidate ground truth (27 TP + 21 FP) is maintainer-adjudicated, which is appropriate for a documentation-implementation study where no oracle exists. However, the single-run variance is substantial (recall 15–78%, accuracy 44–65%), and the authors report the 3-run any-confirmed ensemble (67% precision, 74% recall) as the variance-reduced operating point. While this is reasonable, the paper does not explain why the ensemble is "any-confirmed" rather than a majority vote or weighted scheme, nor does it report per-run precision to assess whether false-positive rate varies with recall. The disclosure of variance is honest, but the operating point selection rationale is under-specified. See RQ2.

- **2.3 [minor, fixable]** The RQ3 task-intrinsic rate estimates have small sample sizes and wide confidence intervals. The parameter-TI rate is 6/18 (Wilson 95% CI [16%, 56%]), tighter than the twelve-clause pilot's [19%, 68%] but still imprecise. The behavior-TI rate is 11/11 (Wilson 95% CI [74%, 100%]). The pooled rate across both subtypes (n=29) is 17/29 (Wilson 95% CI [41%, 75%]). The directional claim that cross-model validation misses task-intrinsic errors is robust (3 of 6 TI clauses missed at parameter level, 10 of 11 at behavior level), but the point estimates should be treated as provisional pending larger-sample validation. See RQ3.

- **2.4** The VDBFuzz bidirectional head-to-head (RQ1, Table 2) is methodologically sound but limited by n=1 per direction. The version-state control (v1.4.0 where VDBFuzz's integer-overflow crash is live, v1.18.0 where TestVDB's #9045 is live, v1.18.2 where both are fixed) correctly attributes findings to version state rather than insufficient budget. The authors appropriately frame these as hypothesis-generating cases rather than generalized results. The structural hypothesis (documentation-implementation oracles can reach crash-class defects where the crash-triggering input violates a documented bound, but crash oracles under current templates do not reach silent-accept documentation-implementation defects) is plausible but not established by n=1 cases. See RQ1, §6.

- **2.5** The RQ4 model-free invariant oracle subclass (COSINE distance bounds, index completeness, payload filter correctness) is the least design-contingent part of the evaluation. The 9 mathematical-invariant issues across Milvus and Qdrant are classical-addressable and counted within the ~10% non-documentation-implementation portion of RQ1. This provides separation between TestVDB's LLM pipeline contribution and a reusable invariant oracle that is independent of it. See RQ4.

- **2.6 [minor, fixable]** The threats to validity are well-discussed but could be more explicit about construct validity. The paper states that all source-anchor results use a single model family (GLM-5.2) and that a cross-model check (DeepSeek on 20 candidates, κ=1.0) suggests the verdict is not family-specific when source evidence is explicit. However, the paper does not discuss whether source ambiguity (e.g., incomplete or convoluted source code) could introduce family-specific bias in the dev-reviewer's source-reading step, nor does it report inter-rater reliability for source interpretation by different families. See Threats to Validity.

**3. Novelty** — Excellent

- **3.1** TestVDB identifies a clear, non-obvious delta over the closest prior work. The documentation-implementation consistency problem has been addressed in structured regimes (Toradocu for Javadoc `@throws`, AGORA+ for execution traces, SATORI for OpenAPI specs, MASTOR for source code). These operate in low-ambiguity settings where the LLM transcribes explicit constraints, and their oracles are reported as reliable. TestVDB targets the high-ambiguity natural-language regime where LLM interpretation is unreliable, and it introduces source-grounded falsification to address the task-intrinsic error layer that cross-model validation cannot reach. See §4, §7.

- **3.2** The source-grounded falsification mechanism is a distinct contribution over prior LLM-as-judge approaches. Toradocu, Doc2OracLL, and AugmenTest trust the generated oracle without verification. ChatAssert uses iterative prompt repair guided by compilation and execution feedback, but the LLM remains the final semantic arbiter. Testora achieves 55% precision with multi-question classification, demonstrating LLM judgment unreliability. TestVDB uses the implementation's source code (an independent information source) to falsify LLM-derived behavioral claims, targeting task-intrinsic documentation-interpretation errors that prompt refinement and runtime repair cannot reach. See §7.

- **3.3** The two-layer reliability framework (family-specific vs. task-intrinsic) is a precise conceptual contribution. Family-specific self-preference is an instance of established bias (Panickssery et al.). Task-intrinsic stability is defined at the extraction level across model families, distinct from Haldar et al.'s intra-judge self-inconsistency. The eighteen-clause and behavior-level probes provide empirical support for this distinction. See §4, RQ3.

- **3.4** The within-vendor contrast (over-strict in optional-default parameters like `ef`, `nprobe` on Milvus and `timeout`, `group_size`, `score_threshold` on Qdrant; absent where docs state explicit minimums like `shard_number` ≥ 1) is a novel, falsifiable prediction validated by impl-confirmation. This yields a mechanistic hypothesis: a VDBMS parameter documented with an optional default and no explicit bound is a candidate for over-formalization, whereas one documented with an explicit minimum is not. The Weaviate control (zero over-strict parameters, all docs state "Must be >= 1") confirms this predictor holds cross-vendor. See RQ3.

- **3.5** Checked the delta against core competitors (fetched from `.paperpilot/review/.in-progress/reviewer-1/background.md`):
  - **VDBFuzz:** Paper accurately characterizes it as crash-only with no semantic oracle. Novelty delta: TestVDB targets silent-accept documentation-implementation defects, which VDBFuzz cannot reach by design. Verified.
  - **AGORA+, SATORI, MASTOR:** Paper correctly identifies them as structured-source extraction in low-ambiguity regimes. Novelty delta: TestVDB addresses the natural-language regime these tools do not target. Verified.
  - **Toradocu, Doc2OracLL, AugmenTest, ChatAssert, Testora:** Paper correctly identifies that these tools trust the LLM oracle without independent verification (ChatAssert uses runtime feedback but LLM remains final arbiter). Novelty delta: TestVDB's source-grounded falsification addresses the verification gap. Verified.
  - **Property-based testing (Schemathesis, QuickREST), NoREC/TLP/DQE/DDLCheck:** Paper accurately notes these require formal properties or reference semantics unavailable for VDBMS documentation. Novelty delta: TestVDB targets the PBT-inaccessible residual. Verified.

## Reviewer 2: Area Specialist

**Overall Recommendation:** Weak Accept

### Summary
The paper proposes TestVDB, a documentation-implementation consistency testing approach for vector database management systems (VDBMSs) that uses an LLM to extract behavioral claims from natural-language API documentation and then falsifies those claims against source code. The authors argue that classical oracles (crash, differential, metamorphic, property-based) cannot reach about 85% of the documentation-implementation defects they found, because these defects involve accept/reject decisions documented in prose rather than formal specifications. They introduce a two-layer reliability framework: family-specific errors (self-preference bias, mitigated by cross-model validation) and task-intrinsic errors (stable misinterpretation across families due to ambiguous documentation). Source-grounded falsification resolves task-intrinsic errors by treating LLM-derived claims as refutable hypotheses. TestVDB surfaced 111 candidate issues across five VDBMSs, with 50 true-positive defects (36 confirmed, 14 with open fix-PRs). A controlled retrospective on 48 adjudicated candidates shows the source-grounded dev-reviewer reaches 67% precision and 74% recall.

### Core Strengths
- **S1:** The two-layer error decomposition (family-specific vs task-intrinsic) is conceptually sound and grounded in documented LLM-as-judge phenomena (Panickssery, Wataoka, Haldar) — see 1.2.
- **S2:** The source-grounded falsification design offers a principled approach to resolving task-intrinsic documentation-interpretation errors that cross-model validation cannot — see 3.1.
- **S3:** The controlled head-to-head with VDBFuzz on specific versions (v1.4.0, v1.18.0, v1.18.2) provides concrete evidence of oracle asymmetry — see 2.1.
- **S4:** The RQ3 probe design (eighteen-clause parameter set plus behavior-level check) isolates the task-intrinsic phenomenon with falsifiable predictions — see 3.2.

### Core Weaknesses
- **W1:** The reliability claims (κ=1.0, "reliable extraction" for AGORA+/SATORI/MASTOR) need clearer grounding — the κ=1.0 is on 20 non-random, diversity-stratified candidates, not a representative sample, and the AGORA+/SATORI/MASTOR reliability characterization lacks direct evidence — see 3.3 [major, fixable].
- **W2:** The 85% documentation-implementation residual is presented as a structural property of the defect class but is derived from TestVDB's biased sample (the tool is designed to find these defects), making the estimate circular — see 1.1 [major, fixable].
- **W3:** The statistical rigor is uneven: some results report Wilson CIs and Cohen's κ (good), but others (e.g., single-run variance "15--78% recall") present point ranges without confidence intervals — see 4.1 [minor, fixable].

### Detailed Assessment

#### 1. Significance — Adequate
- **1.1** The paper targets a real and costly problem: VDBMS documentation-implementation defects that corrupt query semantics without crashing, exemplified by parameters like `nprobe=0`, `ef=0`, or out-of-range HNSW parameters silently accepted (Introduction, Paragraph 1). The empirical study~\cite{bugstudy25} finding that >50% of VDBMS bugs manifest as functional failures, plus the roadmap attributing ~43% to incorrect behavior, establishes practical importance. However, the 85% residual claim (Introduction, Paragraph 4) overstates generalizability: this is the composition of TestVDB's findings, not an estimate of the true defect population, since TestVDB is explicitly designed to surface documentation-implementation defects. **[minor, fixable]** The authors already disclose this ("the composition of our findings, not a population estimate", line 16); the residual concern is only that the abstract/intro framing could foreground this caveat more so a reader does not misread 85% as a population prevalence.
- **1.2** The two-layer error decomposition (family-specific vs task-intrinsic) is a significant conceptual contribution. The family-specific layer connects cleanly to established LLM-as-judge self-preference work (Panickssery et al., Wataoka and Takahashi), and the task-intrinsic layer—where ambiguous documentation causes different families to converge on the same wrong claim—identifies a real gap that cross-model validation cannot address (Section 4, Paragraph 2). The distinction is theoretically grounded and actionable.
- **1.3** The source-grounded falsification approach has clear practical impact: it enables detection of defects like Qdrant #9045 (wait=false accepts zero-length vectors) that crash oracles miss, and the retrospective shows a recall gain from 37% to 74% (Section 6, Paragraph 2). This addresses a real gap in VDBMS testing.

#### 2. Soundness — Adequate
- **2.1** The controlled head-to-head with VDBFuzz (Section 6, Paragraph 1) is methodologically sound. The bidirectional reachability probe on specific Qdrant versions (v1.4.0 for VDBFuzz's crash, v1.18.0 for TestVDB's #9045, v1.18.2 where both are fixed) establishes concrete, version-controlled evidence that each tool can reach a defect the other cannot. The authors correctly limit this to "hypothesis-generating controlled cases" at $n=1$ per direction rather than a generalized result. The structural hypothesis—that a documentation-implementation oracle can reach crash defects where the crash-triggering input violates a documented bound, but the reverse need not hold for silent accepts—is plausible.
- **2.2** The RQ3 probe design (Section 6, Paragraph 3) is rigorous. The eighteen-clause set (thirteen Milvus, five Qdrant v1.18.2, all live-probe-confirmed) plus the scaling passes (six additional clauses) and the behavior-level extension (eleven by-design/idempotency behaviors) isolates the task-intrinsic phenomenon with multiple subtypes. The falsifiable prediction—over-strict concentrates in optional-default APIs and is absent where documentation states explicit bounds—is tested with within-vendor contrast (Milvus: `ef/nprobe/level/replicaNumber` over-strict vs `M/nlist/dimension` not; Qdrant: `timeout/group_size/score_threshold` over-strict vs `shard_number/replication_factor` not) and cross-vendor validation (Weaviate's explicit-bound parameters show zero over-strict). The specificity check on twenty-one explicit-bound parameters (0/21 over-strict) reinforces this. The Wilson CIs are reported appropriately.
- **2.3 [minor, fixable]** The κ=1.0 between GLM-5.2 and DeepSeek on twenty candidates (Section 6, Paragraph 2) rests on a "diversity-stratified, non-random" purposive sample. The paper already discloses this and hedges the claim ("does not appear family-specific"), so it is not over-claimed; the residual concern is only that a random-sample supplement would further strengthen the construct-validity argument.
- **2.4** The threat-model anchor analysis (Section 6, Paragraph 2) is thorough. The three-condition ablation (source alone kills 9/12 FPs, threat-model alone 6/12, union 11/12, all retaining 4 TPs) cleanly isolates the contribution of each anchor. The cross-model check with DeepSeek re-running the dev-reviewer on twenty candidates adds useful evidence, but suffers from the same sampling limitation as 2.3.

#### 3. Novelty — Adequate
- **3.1** The source-grounded falsification design is novel relative to MASTOR. The paper correctly positions the delta: MASTOR reads source to generate oracles encoding implemented behavior and therefore "cannot detect a gap between the documentation and the code" (Section 5, Paragraph 3), whereas TestVDB reads source to falsify documentation-derived clauses and targets exactly that gap. The distinction is real and clearly articulated. However, the paper's characterization of AGORA+ and SATORI as operating in a "low-ambiguity regime where constraints are explicit" (Section 4, Paragraph 2) lacks direct evidence—the paper does not cite false-positive rates or reliability metrics for AGORA+/SATORI, only asserts their "low false-positive rates" based on the "low ambiguity of their sources." **[minor, fixable]** The authors should either cite concrete reliability numbers from those papers or soften the claim to "reportedly low false-positive rates."
- **3.2** The task-intrinsic error concept is novel and well-differentiated from family-specific self-preference. The eighteen-clause probe provides concrete evidence: DeepSeek reproduces GLM's over-strict clause on the same parameter in 6 of 18 cases (the task-intrinsic subset), and cross-model judging misses 3 of those 6 while source-grounded falsification catches all 18 (Section 6, Paragraph 3). The behavior-level extension (11/11 task-intrinsic) further isolates the phenomenon. The distinction is clear: family-specific errors are mitigated by cross-model validation; task-intrinsic errors are not.
- **3.3** The explicit-bound predictor (over-formalization concentrates in optional-default APIs and is absent where documentation states explicit bounds) is novel and validated by within-vendor contrast. The falsifiable prediction—that parameters documented with "optional, default X" without explicit bounds are candidates for over-formalization, while those with "Minimum Y" are not—is tested across Milvus, Qdrant, and Weaviate. This is a useful, generalizable insight beyond VDBMSs.

#### 4. Verifiability — Adequate
- **4.1** The evaluation provides enough information to follow the work. The artifact declaration is clear: "prompts, target versions, and per-token accounting are in the artifact, which we will release at a persistent URL upon acceptance" (Section 5, Paragraph 1). The 111-submission breakdown (50 TP, 22 by-design/rejected, 24 duplicates, 15 pending) is transparent. - **4.2** The controlled head-to-head with VDBFuzz (Section 6, Paragraph 1) is verifiable: the Qdrant versions (v1.4.0, v1.18.0, v1.18.2) and specific defects (VDBFuzz's integer-overflow crash on size=2^63; TestVDB's #9045 and #7967) are precisely documented, with fix states and root-cause analysis (#7967's panic traced to an inconsistent validation path). - **4.3** The RQ3 probe (Section 6, Paragraph 3) is fully reproducible: the eighteen-clause parameter set is enumerated with TI status and cross-model judging results in Table 2; the scaling passes (ef/nprobe/level/replicaNumber/m/bits) and behavior-level checks (11 by-design/idempotency behaviors) are described with live-probe confirmation. The specificity check on twenty-one explicit-bound parameters is fully listed. The threat-model to validity subsection (Section 6, Paragraph 6) acknowledges the scope: generalization to Weaviate/MeiliSearch/Chroma is breadth-only; statistical claims rest on Milvus and Qdrant; result correctness is out of scope.

Family-specific self-preference is mitigated by cross-model validation. - **5.4 [minor, fixable]** Minor language awkwardness: "The large majority" appears twice in close proximity (Introduction, Paragraph 1; Section 6, Paragraph 1). Consider varying the phrasing or using a precise percentage if available.

### Questions for Authors
- **Q1:** The κ=1.0 between GLM-5.2 and DeepSeek is based on a "diversity-stratified, non-random sample of twenty candidates" (Section 6, Paragraph 2). Can you provide context on why this non-random sampling does not bias the result, or reframe the claim to avoid overgeneralization? If the intent is to demonstrate that source-grounded verdicts are not strongly family-specific when source evidence is explicit, could you supplement with a random-sample check?

## Reviewer 3: General Reviewer

**Overall Recommendation:** Accept

### Summary

The paper introduces TestVDB, an automated testing tool that detects documentation-implementation defects in vector database management systems (VDBMSs). These defects occur when a system silently accepts inputs or produces behaviors that violate its API documentation—for example, accepting invalid parameter values like `nprobe=0` or returning success where the documentation prescribes rejection. The authors argue that classical testing oracles (crash detection, differential testing, metamorphic relations, property-based testing) cannot reach this defect class because accept/reject decisions are documented in natural language rather than formal specifications. TestVDB addresses this by using an LLM to extract behavioral claims from documentation and then falsifying those claims against the actual implementation source code. Across five VDBMSs, TestVDB surfaced 111 candidate issues of which 50 are true-positive defects (36 confirmed by maintainers, 14 with open fix-PRs). The authors report that about 85% of these are documentation-implementation defects unreachable by classical oracles. A controlled retrospective on Milvus and Qdrant shows their source-grounded dev-reviewer achieves 67% precision and 74% recall.

### Core Strengths

- **S1:** Clear articulation of a real, widespread problem with significant practical consequences — see Section 1's framing of VDBMS defects and the costly silent acceptance behavior that corrupts query semantics.
- **S2:** Well-structured, self-contained argument that a generalist can follow — the progression from the oracle problem (§1) through the LLM regime analysis (§4) to the design (§5) and evaluation (§7) is logical and internally coherent.
- **S3:** Strong use of controlled ablations and head-to-head comparisons that isolate the contribution — see RQ2 (§7.2), the three-condition ablation isolating source vs. threat-model anchors, and the VDBFuzz bidirectional reachability study (Table 2).
- **S4:** Honest limitation discussion that flags the key constraints without undermining the core contribution — see §8's acknowledgment that source-grounded falsification requires source, treats implementation as correct, and that the 85% residual is compositional not population-level.

### Core Weaknesses

- **W1:** Limited generalization evidence beyond Milvus and Qdrant — see §7.1 (yield numbers) and §7 (threats to validity) where MeiliSearch and Chroma contribute only breadth, and statistical claims are explicitly scoped to the two main vendors.
- **W2:** Ground truth reliance on maintainer adjudication without an independent defect catalog — see §7's note that "there is no public ground-truth defect catalog for VDBMSs," which means the precision/recall figures are contingent on maintainer responses and pending issues.
- **W3:** Confidence intervals are wide on small probes — see RQ3 (§7.3) where the task-intrinsic rate on 18 clauses has Wilson 95% CI [16%, 56%], and the original 12-clause pilot had [19%, 68%].

### Detailed Assessment

#### 1. Significance — Adequate

- **1.1** The problem identification is strong and well-motivated. Section 1 frames VDBMS defects as costly, cites an empirical study that more than half manifest as functional failures, and points to the VDBMS testing roadmap identifying oracle definition as a key challenge. The documentation-implementation defect class is clearly explained with concrete examples (`nprobe=0`, `ef=0`, negative score thresholds) that a generalist can understand, and the consequences (corrupted query semantics, silent data corruption) are stated plainly. This is not a niche problem—it applies to any system where behavior is specified in natural-language documentation rather than formal contracts.

- **1.2** The scope is narrower than the framing might suggest, and this limits the impact to a specialized setting. The contribution is explicitly scoped to VDBMS documentation-implementation consistency, and result correctness (ANN recall, ranking) is out of scope (§2, §7). The 85% residual is a composition of TestVDB's findings, not an estimate of the true defect distribution (§7.1, §8). Statistical claims rest on Milvus and Qdrant only; MeiliSearch and Chroma "contribute breadth rather than statistical weight" (§7.1). This bounded scope means the contribution is useful and well-executed but applies in a limited domain. The impact is meaningful but not transformative—it is a solid advance in a specialized area, not a broad new testing paradigm.

- **1.3** The practical relevance is clear and well-demonstrated. The 111 submitted issues and 50 confirmed defects (36 maintainer-acknowledged + 14 with open fix-PRs) across five VDBMSs show that the tool finds real problems that matter to developers. Table 3 breaks down submissions and acknowledgments per vendor, and the abstract states that "about 85% [of the 111 issues] are documentation-implementation defects" unreachable by classical oracles. This is concrete evidence that the approach surfaces issues maintainers accept as defects. The significance would be higher if the paper demonstrated broader transfer to REST APIs or configuration validation beyond VDBMSs, but §8 explicitly flags this as future work.

#### 2. Soundness — Adequate

- **2.1** The central claim—that about 85% of the surfaced defects are documentation-implementation defects unreachable by classical oracles—is grounded in a transparent classification process and a structural argument. Section 1's Table 1 maps each classical oracle type to the defect class it reaches and explains why it misses the documentation-implementation residual. The crash oracle cannot detect silent accepts; differential testing cannot adjudicate accept/reject decisions that diverge by design across vendors; metamorphic relations are output relations, not input-acceptance transforms; property-based testing needs machine-checkable properties that VDBMS endpoints lack. The paper classifies each of the 111 submissions by fault model (classical-addressable, documentation-implementation, or concurrency) and states that the per-issue mapping is in the artifact, making the 85% figure auditable rather than asserted. This is sound reasoning and the evidence supports the claim.

- **2.2** The evaluation design for RQ1 includes a strong structural check with the VDBFuzz bidirectional reachability study (§7.1, Table 2). On Qdrant v1.4.0, VDBFuzz's integer-overflow crash on `size=2^63` is live, and TestVDB flags it as a documentation-implementation violation because the OpenAPI declares no maximum. On Qdrant v1.18.0, TestVDB's acknowledged empty-vector defect (#9045) is live, and VDBFuzz finds no failure because its templates use `wait=true` (the correct path) and do not probe `wait=false` (where the violation lives). The authors treat these as hypothesis-generating controlled cases (n=1 per direction) and note the limitation, but they support the structural hypothesis that crash oracles miss silent accepts while documentation-implementation oracles can reach crashes at the subset where the input violates a documented bound. This is careful, well-explained empirical work.

- **2.3 [minor, fixable]** The ground truth reliance on maintainer adjudication is a notable gap that weakens the precision/recall claims. Section 7.1 reports that of 72 maintainer-adjudicated submissions (50 TP + 22 FP), yield precision is 69.4% (Wilson 95% CI [58.0%, 78.9%]), and treating 15 pending submissions as false positives gives a worst-case bound of [47%, 67%]. However, there is no independent defect catalog or unbiased defect sample—§7.4 (threats to validity) explicitly states "we still do not estimate recall because there is no public ground-truth defect catalog for VDBMSs." This means the recall figure (74% in RQ2) and the precision bounds are contingent on maintainer responses and the assumption that pending issues are false positives. The paper is honest about this limitation, but it remains a gap. A stronger design would include an independent manual review or a capture-recapture estimation.

- **2.4** The precision/recall retrospective in RQ2 (§7.2) uses a solid controlled design with appropriate ablations. On 48 maintainer-adjudicated candidates (27 TP + 21 FP), the source-grounded dev-reviewer with a 3-run ensemble reaches 67% precision (Wilson 95% CI [49%, 81%]) and 74% recall, against a single-LLM baseline (no source) of 48%/56%/37%. The paper isolates the contribution with a three-condition ablation on a 12-FP/4-TP control: source alone suppresses 9/12 FPs (75%), threat-model alone 6/12 (50%), and their union 11/12 (91%), each retaining all 4 TPs. This cleanly separates the source-grounded anchor as the dominant contributor. The cross-model check with DeepSeek re-running the dev-reviewer on twenty candidates (Cohen's κ=1.0) further supports that the verdict is not family-specific when source evidence is explicit. The design is sound and the evidence supports the claims.

- **2.5** The RQ3 probe for task-intrinsic documentation-interpretation errors (§7.3) is well-designed but the confidence intervals are wide on small samples. The central claim is that source-grounded falsification resolves task-intrinsic errors that cross-model validation cannot. The probe covers eighteen over-strict clauses (thirteen Milvus + five Qdrant), confirmed over-strict by live probe. DeepSeek independently formalized the documentation and reproduced an over-strict clause on the same parameter in 6 of 18 (the task-intrinsic subset). Cross-model judging caught 8/18 but missed 3/6 task-intrinsic ones. Source-grounded falsification contradicted all 18. The task-intrinsic rate is 6/18 (Wilson 95% CI [16%, 56%]), which is tighter than the 12-clause pilot's [19%, 68%] but still very wide. The paper extends the probe to 50 total clauses across three subtypes (eighteen over-strict parameters, eleven by-design/idempotency behaviors, twenty-one explicit-bound negatives) and reports that on explicit bounds, DeepSeek over-formalized 0/21 (CI [0%, 16%]). This is strong evidence that the phenomenon concentrates in ambiguous optional-default APIs and is absent where documentation states explicit bounds, but the small samples make the effect sizes imprecise.

#### 3. Novelty — Adequate

- **3.1** The paper clearly positions itself against prior work in REST-API oracle generation and documentation-derived oracles. Section 6 (Related Work) discusses AGORA+, SATORI, and MASTOR, which extract oracles from structured sources (OpenAPI, traces, source) where constraints are explicit and the LLM transcribes rather than interprets. Section 4 (The Role of the LLM) draws a sharp contrast: TestVDB extracts from natural-language documentation where constraints are implicit and ambiguous, so the LLM must interpret intent rather than transcribe. This interpretation is unreliable because different families can converge on the same wrong claim when the documentation is ambiguous—this is the task-intrinsic stability phenomenon that cross-model validation cannot fix. The paper also contrasts with Toradocu (deterministic extraction from Javadoc patterns), Doc2OracLL and AugmenTest (LLM extraction without verification), ChatAssert (prompt repair via runtime feedback), and Testora (natural-language PR descriptions as regression oracle). The positioning is clear and the delta is recognizable: source-grounded falsification of LLM-derived behavioral claims, targeting task-intrinsic interpretation errors in high-ambiguity documentation.

- **3.2** The novelty is real but incremental in several dimensions. The source-grounded falsification idea—using implementation source code as an independent verification source to falsify LLM-derived claims—is new in the testing-oracle context, but the general pattern of cross-checking LLM outputs against independent evidence is not. The two-layer reliability model (family-specific self-preference mitigated by cross-model validation, task-intrinsic errors requiring source) is a useful conceptual contribution but builds on established LLM-as-judge reliability work (self-preference bias, intra-judge inconsistency). The model-free invariant oracle subclass (COSINE bounds, index completeness) is classical-addressable and is presented as a side contribution, not the main novelty. The core novelty is in the combination and the application domain: framing VDBMS documentation-implementation consistency as a distinct testing problem, identifying the task-intrinsic interpretation error layer, and demonstrating source-grounded falsification at scale. This is a recognizable advance but not a paradigm shift.

- **3.3** The paper does a good job of distinguishing its contribution from prior work on the LLM-as-judge reliability problem. Section 4 scopes the stability claim precisely: task-intrinsic stability is an extraction-level property defined across model families, distinct from the intra-judge self-inconsistency that Haldar et al. report for LLM-as-a-judge ratings. The claim is that when documentation is ambiguous, different families converge on the same wrong clause at extraction, and cross-model validation cannot break this convergence because the error is in the shared input. This is a clear distinction from the sampling-noise phenomenon in single-judge ratings. The paper also distinguishes from REST-API oracle tools by emphasizing the source-ambiguity gap: AGORA+/SATORI/MASTOR work in a low-ambiguity regime where extraction is reliable, whereas TestVDB operates in a high-ambiguity regime where extraction is unreliable and requires falsification. The positioning is solid.

#### 4. Verifiability — Excellent

- **4.1** The paper provides exceptional methodological detail for reproducing the study. Section 6 (Implementation) describes the multi-agent pipeline on Claude Code runtime, the 20 agents with task-structured role prompts, the GLM-5.2 backbone via the bigmodel API, default sampling with no fixed random seed, and pinned Docker versions for target VDBMSs. It reports wall-clock estimates (dominated by dev-reviewer's source-grounding step, repository clone, and live re-probes), LLM call volume (~10^4 calls), and cost (~$10 per target). The paper states that full prompts, target versions, and per-token accounting are in the artifact, which will be released at a persistent URL upon acceptance. This is enough to fully follow and check the work.

- **4.2** The evaluation sections provide detailed quantitative results with confidence intervals, breakdowns by vendor and subtype, and clear descriptions of the experimental protocols. RQ1 (§7.1) gives the full yield table (Table 3), the classification methodology for the 85% residual, and the VDBFuzz head-to-head with version mapping (Table 2). RQ2 (§7.2) provides the retrospective results with Wilson CIs, the three-condition ablation isolating source vs. threat-model anchors, and the cross-model check with Cohen's κ. RQ3 (§7.3) gives the full table of 18 over-strict clauses with TI annotation (Table 4), the scaling-pass extensions to 50 clauses across three subtypes, and the explicit-bound specificity check. The per-issue mapping (all 111 submissions assigned to fault models with one-line rationale) is stated to be in the artifact. The 48-candidate retrospective, all five dev-reviewer runs, and the corrected ground truth are also in the artifact. This is excellent verifiability.

- **4.3** The paper is honest about what is not verifiable from the text alone. Section 7.4 (threats to validity) flags that all source-anchor results use a single model family (GLM-5.2), but a cross-model check with DeepSeek on twenty candidates suggests the verdict is not strongly family-specific when source evidence is explicit. It also flags that the paper does not estimate recall because there is no public ground-truth defect catalog. The limitations section (§8) reiterates the source requirement, the implementation-as-correct assumption, and the correlative nature of the documentation-style association (optional-default vs. explicit-bound). The artifact declaration is explicit: full prompts, target versions, per-token accounting, and the per-issue fault-model mapping will be released. This transparency about what is and is not provided is exemplary.

#### 5. Presentation — Excellent

- **5.1** The structure is sound and the writing is clear. The progression from the problem (§1) through the oracle gap analysis (§1, §4) to the design (§5), implementation (§6), and evaluation (§7) is logical. The distinction between documentation-implementation consistency and correctness (§2) is important and well-explained. The two-layer reliability model (family-specific vs. task-intrinsic) in §4 is technical but carefully scoped and motivated. The evaluation questions (RQ1–RQ4) map cleanly to the contributions. The writing is precise and avoids ambiguity—the paper consistently uses "about 85%" for the compositional residual and flags the limitation explicitly. There are no structural problems.

- **5.2** The tables and figures are effective. Table 1 maps oracle types to defect classes and exclusion reasons—this is a clear summary of why classical oracles miss the documentation-implementation residual. Table 2 (bidirectional reachability) is concise and well-explained. Table 3 (yield per vendor) is straightforward. Table 4 (RQ3 probe results) clearly marks TI clauses and cross-model judging outcomes. The inline examples (nprobe=0, ef=0, negative score thresholds) are concrete and help a generalist understand the defect class. The use of Wilson confidence intervals throughout is appropriate for small samples and improves rigor.

- **5.3 [minor, fixable]** There are minor language errors and inconsistencies that do not obstruct understanding but should be polished. Section 6 mentions "a few hours of manual boundary testing" in the cost comparison—this is vague and should be quantified or removed. Section 7.1 has a very long sentence (111 words) describing the VDBFuzz head-to-head that is hard to follow and should be split. Section 7.3 has dense prose describing the scaling passes and the pooled task-intrinsic rate across subtypes that could be clearer. Section 8's discussion of crash-oracle asymmetry is conceptually important but the causal hypothesis is presented tentatively (at n=1 per direction) and could be framed more explicitly as speculation. These are minor blemishes that do not affect the core evaluation.

- **5.4** The Related Work section (§6) is comprehensive and well-organized. It covers VDBMS testing (VDBFuzz, roadmap, empirical study), REST-API oracle generation (AGORA+, SATORI, MASTOR), LLM-as-judge reliability, database and property-based oracles, and documentation-derived oracles. Each paragraph positions TestVDB against the prior work and explains the delta. The positioning against Toradocu, Doc2OracLL, AugmenTest, ChatAssert, and Testora is particularly strong because it clarifies that these predecessors either do not verify the LLM output (Toradocu is deterministic but limited to simple patterns; Doc2OracLL and AugmenTest trust the generated oracle) or verify via runtime behavior rather than source (ChatAssert uses compilation feedback, Testora uses differential execution). TestVDB's use of source as an independent verification source is clearly distinct.

### Questions for Authors

- **Q1:** Could you expand on the generalization potential beyond VDBMSs? Section 8 mentions REST APIs without OpenAPI, configuration validation, and policy-as-code as potential transfer targets, but there is no empirical evidence. If the contribution is the source-grounded falsification technique rather than VDBMS-specific defects, a small pilot on a non-VDBMS REST API would strengthen the claim. — This would affect item 1.2's assessment of scope/impact if generalization is demonstrated.

- **Q2:** The recall figure (74% in RQ2) is contingent on maintainer adjudication and the assumption that the 48 candidates are representative. Have you considered capture-recapture or an independent manual review to estimate recall without this assumption? — This would address item 2.3's ground-truth gap.

- **Q3:** The confidence intervals on RQ3's task-intrinsic rate are wide ([16%, 56%] on 18 clauses). What sample size would be needed to tighten this to, say, ±10%? Is scaling to 100+ clauses feasible given the manual source-confirmation requirement? — This would clarify item 2.5's small-sample concern.

- **Q4:** The paper treats the 85% residual as a composition of findings, not a population estimate. Have you considered reporting a lower bound using capture-recapture or a statistical model that accounts for the known biases (documentation-implementation focus, maintainer adjudication rate)? — This would strengthen item 2.1's already-sound argument.
