## Reviewer 1: Domain Expert

**Overall Recommendation:** Weak Accept

### Summary

The paper targets *documentation-implementation bugs* in Vector Database Management Systems (VDBMSs): cases where a system silently accepts an input or returns behavior that contradicts its own natural-language API documentation (e.g., Milvus accepting `nprobe=0` against a documented range of [1, 16384]). Because VDBMS documentation is unstructured prose, the authors argue that every deterministic-oracle candidate (crash signals, differential testing, metamorphic relations, property-based testing, structured-spec oracles) is structurally unable to derive the needed expectation, leaving an LLM-derived oracle as the practical option — and importing the LLM false-positive problem. They instantiate TestVDB, a four-stage pipeline: behavioral-specification extraction from documentation (typed, evidence-tiered, source-verified constraints), test generation by three attack agents under pre-bound strategies (endpoint-level direct probes and system-level state scenarios), sandboxed execution against Docker-pinned targets, and a bug-confirmation stage that splits evidence assembly (evidence builder, grounded in docs, execution logs, and implementation source) from cross-examination (chain auditor: four mechanical checks and four perspectives — contract, physical, maintainer cognition, source).

Empirically, of 81 adjudicated submissions across Milvus, Qdrant, and Weaviate, maintainers confirmed 51 as real bugs and fixed 23 via merged PRs. A blinded three-run re-adjudication of the 81-candidate pool shows the contract-only adjudication core suppresses 86.7–90.0% of false positives with 88.9% case-level verdict agreement, while its recall boundary (0.196–0.333) is attributed to three systematic mechanisms; a controlled single-run ablation of the full stage (adding source forensics and maintainer cognition) reaches suppression 1.000 at precision 1.000 and recall 0.353, at the honest cost of four boundary truths lost to by-design vetoes. A bidirectional probe against VDBFuzz shows the two oracles reach complementary bug classes, including a full-coverage head-to-head in which VDBFuzz's complete 205-template space runs on the same Qdrant v1.18.0 instance and reaches none of the confirmed defects.

### Core Strengths

- **S1:** Real-world validation is unusually strong for this area: 51 maintainer-confirmed bugs with 23 merged fix PRs across three production VDBMSs, with the fix-PR nature classified (all 23 touch implementation code, none documentation-only) and the classifier itself validated against the disproved #9149 — see 1.1, 3.1.
- **S2:** The false-positive measurement is methodologically the strongest part: frozen-package blinding, an explicit conservative adjudication rule, three independent runs plus majority vote, Wilson CIs, systematic (not noise) attribution of both surviving FPs and missed TPs, and a controlled full-stage ablation under the same blinding — see 3.2, 3.3.
- **S3:** Competitor positioning is accurate where I verified it (MASTOR, SATORI, CASCADE full text; Toradocu), and the complementarity claim against VDBFuzz is measured bidirectionally rather than asserted, including a full-search-space head-to-head — see 2.1, 2.2.

### Core Weaknesses

- **W1:** The candidate-selection funnel behind the headline ledger is undocumented: what decided which defect-confirming candidates were submitted upstream is never specified, the ledger is cumulative across pipeline design generations since early 2026, and RQ2's 30 false positives are a submission-filtered subset of the pipeline's raw FP output — so the 63.0% precision and the suppression rates inherit an unstated selection process — see 3.4.
- **W2:** Missing related work on LLM-derived metamorphic relations from API documentation (ARMeta, COMPSAC 2026; also Metamon, LLM4Code@ICSE 2025); Table 1 row 3's claim that deriving relations from prose "is the semantic step MR tooling does not perform" needs scoping — see 2.3.
- **W3:** The full-stage ablation rests on a single run while the contract core gets three runs plus majority voting; given the demonstrated run-to-run spread (TP 17/10/12), the headline suppression of 1.000 lacks cross-run support — see 3.5.

2. **Novelty** — Adequate

## Reviewer 2: Area Specialist

**Overall Recommendation:** Accept

### Summary

The paper targets documentation-implementation bugs in vector database management systems (VDBMSs): cases where the system silently accepts an input or exhibits behavior that violates its own API documentation, with no crash for a conventional oracle to fire on. The authors first argue, via a candidate-by-candidate exclusion analysis, that every deterministic oracle anchors its expectation in signals or structured sources (crash signals, another implementation, output relations, machine-checkable properties, OpenAPI fields, traces, or source code) and therefore cannot derive expectations from natural-language system-level prose — leaving an LLM-derived oracle as the practical option, at the price of importing the LLM's false-positive problem.

TestVDB instantiates this as a four-stage pipeline: (i) extraction of typed, evidence-leveled, source-verified behavioral specifications from crawled documentation; (ii) test generation by attack agents under deterministically pre-bound strategies, with system-level constraints routed through scenario construction; (iii) sandboxed execution against Docker-pinned targets with raw HTTP logging; and (iv) bug confirmation split into an evidence builder and a chain auditor that applies four mechanical checks and cross-examines each candidate from four perspectives (contract, physical behavior, maintainer cognition, implementation source), with the source as the independent falsification anchor.

Evaluation across Milvus, Qdrant, and Weaviate reports 51 of 81 adjudicated upstream submissions confirmed by maintainers as real bugs, 23 already fixed via merged PRs. A blinded three-run re-adjudication of the full 81-candidate pool shows the contract-only confirmation core intercepts 87–90% of the 30 known false positives with 88.9% case-level agreement, attributes its recall loss (0.196–0.333) to three recurrent mechanisms, and a controlled full-stage run with source forensics and cognition reaches 1.000 suppression at precision 1.000 while recovering part of the recall. A bidirectional probe against VDBFuzz (including a full-template-space run on the same version) demonstrates the two oracles reach complementary bug classes.

### Core Strengths

- **S1:** The oracle-exclusion analysis (Table 1, Sections 2.3–2.4) is a genuinely useful conceptual contribution: it delimits, by expectation source, exactly where deterministic oracles fail and where an LLM-derived oracle is forced, rather than asserting "LLM oracles are new" — see 1.1, 2.1.
- **S2:** The detection yield is validated at a level rarely seen: 51 maintainer-confirmed bugs with a fix-PR file-level classification showing all 23 fixes modify implementation code, plus a negative control (the disproved #9149) that the classifier correctly flags as test-only — see 3.1, 3.4.
- **S3:** The RQ2 protocol is unusually honest for an LLM-oracle paper: frozen packages, blinding, three independent runs, an explicit conservative adjudication rule, full denominators, Wilson intervals, and a reported recall of 0.196–0.333 for the paper's own core — an unflattering number reported as the headline boundary rather than buried — see 3.2, 3.3.

### Core Weaknesses

- **W1:** The full confirmation stage's perfect-precision result rests on a single run of a stochastic LLM pipeline, and the 30-false-positive population it is measured on accumulated across mining rounds whose relationship to the current confirmation-stage version is unstated — see 3.5, 3.6.
- **W2:** No non-crash-oracle baseline (e.g., a naive single-LLM documentation-to-assertion oracle over the same scripts) isolates how much of the end-to-end yield the pipeline machinery contributes; the ablation covers only the confirmation stage — see 3.7.
- **W3:** Missing related work: DocTer (ISSTA 2022) already derives constraints from natural-language documentation to guide API testing (in the DL domain), and two 2025 works address documentation–behavior inconsistency detection; none is cited or positioned — see 2.3.

### Detailed Assessment

1. **Significance** — Excellent
   - **1.1** The problem is real infrastructure risk, and the paper establishes it concretely: VDBMSs back RAG applications (Section 1), most VDBMS bugs are non-crashing functional failures (Section 2.2, citing the bug study and roadmap), and the existing dedicated tool (VDBFuzz) structurally reaches only the crash minority. The 51 confirmed / 23 fixed yield across three production systems (Table 2 of the ledger, Section 4.2) is direct evidence of practical impact on widely deployed software — this is not a toy-domain demonstration.
   - **1.2** Beyond the bug count, the characterization of *where* contract-only adjudication fails (three recurrent mechanisms in Section 4.3: unexpressible joint semantics, approximate-behavior ambiguity, cognition-dependent defectiveness) is a reusable map for anyone building documentation-derived oracles; the full-stage ablation then shows source grounding and cognition recover all three Weaviate mechanism-(i) cases among eleven recovered true bugs. This moves the paper from "a tool that found bugs" to "a measured account of an oracle design space."
   - **1.3 [minor, unfixable]** Scope is bounded by construction: the claims hold for prose-constraint regimes (three systems, one LLM family, GLM-5.2, disclosed in Section 5). This limits generality but is inherent to the problem residual the paper defines, and the authors state the boundary explicitly rather than overreaching.

2. **Novelty** — Adequate
   - **2.1** Checked the delta against MASTOR (fetched, cached full text): the paper's claim that MASTOR "encodes implemented behavior and so cannot detect a gap between documentation and code" holds verbatim — MASTOR's own limitations concede it "cannot detect violations of intended requirements that are not reflected in code," and its design demotes OAS claims unsubstantiated in source. TestVDB's inversion (source as falsifier of documentation-derived specifications rather than as the oracle's ground truth) is therefore a real, verifiable structural difference, not a repackaging.
   - **2.2** Checked the delta against SATORI (fetched, cached full text): SATORI's oracles are 17 unary response-field types prompted per OAS field; its real bugs are spec–response mismatches. TestVDB's residual — input-acceptance semantics, error behavior, and multi-request state under untagged system-level prose — is outside SATORI's catalog by construction. The paper's Table 1 wording ("response-field/runtime properties") characterizes SATORI accurately, including the nuance that SATORI does find documentation-implementation inconsistencies on the response side.
   - **2.3 [minor, fixable]** Missing related work within my specialty: DocTer (documentation-guided fuzzing for DL API functions, ISSTA 2022, uncited) extracts input constraints from natural-language documentation to drive test generation — the input-side cousin of TestVDB's extraction stage — and deserves explicit positioning (documentation-guided *input generation* with a crash oracle vs. documentation-derived *oracles* with source-grounded adjudication). This is a solid Adequate: recognizable as new, incremental in its parts, non-obvious in its composition and rationale.

## Reviewer 3: General Reviewer

**Overall Recommendation:** Accept

### Summary

The paper targets silent "documentation–implementation" bugs in vector database management systems (VDBMSs): cases where the system accepts inputs or returns results that contradict its prose API documentation (e.g., accepting `nprobe=0` against a documented range), which produce no crash and therefore escape crash-oracle fuzzers such as VDBFuzz. Because the expectation lives in natural-language prose rather than a structured signal, the authors argue every deterministic oracle candidate is structurally inapplicable (Table 1), forcing an LLM-derived behavioral specification as the oracle — which in turn imports hallucination, self-preference, and inconsistency. TestVDB is a four-stage pipeline (specification extraction, test generation via three pre-bound attack agents, sandboxed execution, confirmation) whose confirmation stage assembles a five-section evidence chain per candidate and adjudicates it from four perspectives, with the implementation source serving as a falsification anchor that breaks the "LLM writes and judges its own oracle" loop.

The empirical case is unusually concrete: across Milvus, Qdrant, and Weaviate, maintainers confirmed 51 of 81 adjudicated submissions as real bugs, 23 fixed via merged implementation PRs. A three-run re-adjudication of frozen packages shows the contract-only confirmation core suppresses 86.7–90.0% of false positives with 88.9% case-level agreement, and a controlled ablation isolates where source grounding and maintainer cognition become necessary (FP suppression 1.000, recall 0.216 → 0.353, with an honestly reported symmetric cost of four lost true bugs). A bidirectional probe against VDBFuzz, including a full-coverage run over its complete 205-template space, shows the two approaches reach disjoint bug classes. The paper is transparent about protocol sensitivity (a prior unblinded run reported recall 0.841 vs. 0.353 blinded), adjudication fallibility (#9149), and external validity (single backbone). My main reservations are the single-run status of the strongest ablation result, an unreconciled dual accounting (submission ledger vs. process ledger), and the fact that no replication artifact is reachable at review time.

### Core Strengths

- **S1:** Real, externally validated impact — 51/81 maintainer-confirmed bugs with 23 merged implementation fixes across three production VDBMSs, not a synthetic benchmark result — see 1.1
- **S2:** Exceptional numeric self-consistency and honest self-measurement; I recomputed the arithmetic across Tables 2–4 and both ledgers and found it airtight, including the disclosed blinding cost (0.841 → 0.353) and symmetric ablation costs — see 3.1, 3.2
- **S3:** A coherent, explicitly differentiated methodological delta: the derived oracle is demoted from final arbiter to hypothesis, falsified against implementation source — see 2.1

### Core Weaknesses

- **W1:** The headline robustness claim (full stage: 1.000 FP suppression at precision 1.000) rests on a single run, while the core component showed substantial run-to-run variation (17→10→12 confirmations) — see 3.3
- **W2:** The cumulative submission ledger (Table 2) and the final-run process ledger (60 defect-confirming candidates) are declared "neither reducible to the other" without any overlap analysis, leaving the provenance of the headline counts opaque — see 3.4
- **W3:** No replication artifact is reachable at review time; the package is promised only "upon publication" and the submission itself contains a visible TODO about the link — see 4.2
- **W4:** Frozen adjudication packages are built from reporter-perspective transcripts, so blinding removes label leakage but not framing; the disclosed mechanism presses the blinded precision-side figures downward (a conservative direction), but the bias is not eliminated — see 3.6

### Detailed Assessment

**1. Significance — Excellent**

- **1.1 (strength):** The paper targets the majority bug class of RAG-critical infrastructure: silent functional failures that crash-oracle fuzzing structurally cannot reach (§1 P1–P2, §2.2). Impact is demonstrated, not argued: 51 maintainer-confirmed bugs, 23 merged fixes of which all modify implementation code and 15 add regression tests, 50/51 carrying official bug labels (§4.2). Upstream projects merging fixes is the strongest available evidence of practical significance.
- **1.2 (strength):** Beyond the bug haul, the quantified recall boundary (three mechanisms: joint semantics inexpressible as a surface assertion, approximate-behavior compatibilities, cognition-dependent defectiveness; §4.3) is reusable knowledge for any future use of LLM oracles, independent of the three systems studied.

**2. Novelty — Adequate (provisional)**

Based on the paper's own positioning, this reads as a real delta.
