## Reviewer 1: Domain Expert

**Overall Recommendation:** Weak Accept

### Summary

The paper targets *documentation-implementation bugs* in vector database management systems (VDBMSs): cases where a system silently accepts an input or exhibits a behavior that contradicts its natural-language API documentation — the canonical illustration being Milvus accepting `nprobe=0` although the documentation declares the range $[1, 16384]$ (the bug threaded as a running example through all four pipeline stages is a different one, Qdrant issue \#10369, a `recommend` dimension bypass). Its argument is that every deterministic-oracle candidate anchors its expectation somewhere other than prose (crash signals, another implementation, output--output relations, machine-checkable properties, structured specs), so an LLM must read the documentation, and that putting an LLM in the oracle role imports a false-positive problem the confirmation stage must break. TestVDB is a four-stage pipeline: a two-level behavioral-specification extraction from crawled vendor documentation; attack agents that turn each constraint into executable probes under deterministically pre-bound strategies (unsupported surfaces routed to scenario construction); sandboxed execution against Docker-pinned versions with raw HTTP logging; and a confirmation stage in which an evidence builder assembles a five-section evidence chain (document verification, execution evidence, contract grounding, chain trace, source grounding) and a chain auditor applies four mechanical checks and four perspectives — contract, physical, cognition (mined from the project's own issue history), and source — before issuing a verdict. The implementation source is the proposed falsification anchor that breaks the loop in which one LLM both reads the documentation and judges the behavior.

The evaluation reports two layers. First, a maintainer-adjudicated submission ledger across Milvus, Qdrant, and Weaviate: of 81 adjudicated candidate issues, 51 were confirmed as real bugs and 23 fixed via merged PRs, with the 51 grouped into eight bug patterns in which silent-accept-family shapes dominate. Second, a controlled three-run re-adjudication of the same 81 frozen candidate packages under blinding: the contract-only core of the confirmation stage intercepts 87--90\% of the 30 false positives at run-level recall 0.196--0.333 with 88.9\% case-level agreement, while the full stage (adding per-case source forensics and maintainer cognition) intercepts all 30 at recall 0.373; a post-hoc single-perspective re-aggregation of the same runs attributes most of the gain to source grounding (recall 0.392 at precision 0.952) and reports that the full priority rule scores marginally below source-only. Finally, a bidirectional probe against the crash-oracle baseline VDBFuzz on Qdrant finds the two oracles reach disjoint bug classes, including a full-coverage run of VDBFuzz's released Qdrant template set on v1.18.0 that reports no crashes.

### Core Strengths

- **S1:** A real-world yield that is audited rather than merely counted: the maintainer-adjudicated ledger (Table 2), the operational definitions of *confirmed* and *false positive*, the September 2026 re-verification, and the classification showing all 23 fixes touch implementation code — including the self-retracted case the classifier was validated against. — see 1.2
- **S2:** The RQ2 measurement is reported with the rigour its claim needs — three runs per arm over 81/81 frozen packages, blinding, majority rules, per-case agreement, and Wilson intervals that I recomputed from the reported counts and found correct — and the paper volunteers the number that hurts it (an earlier unblinded full-stage run reported recall 0.841 against 0.373 here). — see 3.1, 3.2, 4.1
- **S3:** Competitor positioning checked by name against the sources: the "anchor inversion" over MASTOR holds and is corroborated by MASTOR's own stated limitation; Metamon's precision/recall profile reproduces exactly; the SATORI, Toradocu, and VDBFuzz characterizations are accurate. — see 2.1, 2.2, 2.3
- **S4:** Table 5 (single-perspective re-aggregation) is a genuine self-ablation of the paper's own mechanism, reported against the authors' interest: the full priority rule is shown to score *below* source-only on recall, and the reasons (veto power suppressing four boundary truths) are dissected rather than hidden. — see 3.4, 3.6

### Core Weaknesses

- **W1:** The paper's central mechanism claim — that source grounding is what does the falsifying — rests on a post-hoc re-aggregation of recorded per-case perspective fields under a single-perspective rule, not on an independent run of that configuration; the abstract states the result more strongly ("isolates source grounding as the mechanism") than the evidence supports. — see 3.4
- **W2:** The headline numbers cannot be checked by a reader at review time: the replication package is promised rather than present, the adjudicating model is deliberately unpinned ("the exact weights … are not recoverable from this text"), and the judge configuration and the 81 frozen packages are not in the paper. — see 4.2, 4.3, 4.4
- **W3:** Related-work positioning is locally over-broad and misses one direct 2026 measurement of the same prose-only-constraint residual: Table 1's caption claims only row 6 derives its expectation from prose while the paper itself cites prose-derived oracle work (DocTer, Toradocu, JDoctor), and SilentProbe's audit of 2,501 OpenAPI documents over the same silent-accept surface is uncited. — see 2.4, 2.5

### Detailed Assessment

1. **Significance** — Excellent
   - **1.1** Section 2.3 pins the target class to an operational example (Milvus documentation declares `nprobe` in $[1,16384]$; the API accepts `nprobe=0` with HTTP 200 and returns results, issue \#49823), and Sections 1--2.2 establish that this is the *majority* shape rather than an edge case: the motivating empirical study the paper cites reports functional failure as the dominant VDBMS defect symptom (57.3\% of 1,463 bugs) against crash at 15.1\% (checked this session at the study's public listing level), and Table 1 row 1 adds the authors' own count that only 2 of their 51 confirmed bugs crash or panic. The downstream consequence — wrong context reaching a retrieval-augmented model with no error code to log — is what makes the class worth a paper, and Section 2.4 converts a tooling gap into a research question by asking *where each oracle candidate gets its expectation*. This is a well-chosen, well-motivated problem with demonstrated practical reach.
   - **1.2** Section 4.2 reports the maintainer-adjudicated ledger (Table 2): 43/29/11 (Milvus), 28/14/9 (Qdrant), 10/8/3 (Weaviate), 81 submitted, 51 confirmed, 23 fixed. What lifts this above the usual yield claim is the auditing around it: a collection protocol with operational definitions of *confirmed*, *false positive*, and *duplicate-tracked* plus a September 2026 re-verification of every submission; a decomposition of the 51 into 23 fixed, 18 acknowledged-open, 7 closed without fix, and 3 duplicate-tracked; and a fix-nature classification in which all 23 merged fix PRs modify implementation code, 15 also add regression tests, and none is documentation-only. The classifier is even validated against the case the authors retracted themselves (Qdrant \#9149), where it correctly flags the PR as test-only. For a testing paper, maintainer-confirmed and merged-fix evidence is the strongest impact signal available short of deployment, and it is presented without inflation.
   - **1.3 [minor, fixable]** Two scope bounds sit in the body but not where the impact is asserted. (i) Section 2.3 explicitly disclaims result correctness ("result correctness of vector search … is not our claim"), yet the bug taxonomy (Table 3) counts 5 \textsc{Result-Incorrectness} bugs (e.g., Qdrant \#10120 `count` under-counting) and Section 4.3 lists approximate-behavior defects as a recall-loss mechanism — so the 51-bug yield is not purely the consistency class the paper defines. (ii) The abstract leads with "51 of 81" without the qualifier the body supplies — the introduction does carry it in the same sentence ("that ledger is the operational pipeline's cumulative output and carries author-side screening and the submission decision"), but the abstract does not, and the abstract is where most readers will meet the number. Neither is fatal; both should travel with the headline.

2. **Novelty** — Adequate
   - **2.1** Checked the delta against MASTOR (the paper's own "closest to this work"; fetched and read this session). The paper claims an *anchor inversion*: MASTOR's authority is the implementation (per-field status oracles plus behavioural-consistency oracles over operation sequences, with a ChallengerAgent regenerating weak oracles), whereas TestVDB takes the prose as ground and uses the source only as the falsifier. The claim holds — MASTOR's own limitation states it "cannot detect violations of intended requirements that are not reflected in code", which is exactly the documentation--code gap TestVDB targets. The verdict is that the delta is real but *conceptual*: source grounding, an LLM reviewer agent, and cross-operation oracles are all prior work; what is new is the direction of authority and the domain residual, not a new device.
   - **2.2** Checked the numbers against Metamon (fetched): the paper's "precision 0.722 with recall 0.480 at its permissive threshold on 9,482 pairs, with precision reaching 0.967--1.000 only as recall collapses below 0.1" matches the source exactly (thresholds $\le -0.1$, $\le -0.6$, $\le -0.8$, $\le -0.9$, $\le -1.0$). The characterization that Metamon's falsifier "is another LLM question" is also accurate: EvoSuite-captured behavior, metamorphic prompt pairs, self-consistency, no independent evidence source. The paper's use of Metamon as the closest precision--recall comparator is fair, and the residual delta (method-level Javadoc vs. system-level HTTP prose; one codebase vs. stateful multi-request behavior) is genuine.
   - **2.3** Checked the remaining named competitors (each fetched): SATORI's per-response-field prompts over OpenAPI metadata ("its anchor is per-response-field OAS metadata"), Toradocu's @throws-derived oracles with the derived oracle as final arbiter, and VDBFuzz's crash oracle, template-based mutation, its published 120-minute-per-tool protocol, and its three Qdrant crash types (the source's table contains an `OOM, FPE, DoS` Qdrant row and the Qdrant DoS via `dim = 2**63` is its narrated case study). All characterizations hold. One sub-claim is left provisional as a verification gap rather than a defect: "every points-upsert template uses `wait=true`" is stated as a universal over the released Qdrant template set; the artifact's empty-vector template does use the `wait=true` path (verified by the session that cached the artifact facts), but I did not re-check the quantifier over all upsert templates, so that particular observation should be read as unverified rather than wrong.
   - **2.4 [minor, fixable]** Table 1's caption says rows 1--5 anchor their expectations in signals or structured sources "but never in system-level prose", and row 6 concludes that only the LLM-derived oracle derives its expectation from prose. That is over-broad as the table stands: the paper itself cites a documentation-derived oracle line in Section 2.4 and Section 6 (DocTer extracts dependency-grammar *input constraints* from natural-language DL-API documentation; Toradocu and JDoctor derive specifications from tagged Javadoc; RBCTest mines constraints from API specifications), and these do read prose. The distinction that saves the claim — *system-level, untagged prose* versus method-level or tagged prose — is made in the running text but not in the table that carries the paper's first contribution. Add a row (documentation-derived oracles: prose-derived, but method-level/tagged and with the derived oracle as final arbiter) or tighten the caption to "system-level prose" throughout.
   - **2.5 [minor, fixable]** Missing related work (uncited): SilentProbe (2026) audits 2,501 published OpenAPI documents (721,320 parameters), reports that 40.1\% of documents state at least one constraint only in descriptive prose their schema does not encode, and finds that schema-derived perturbations produce honest errors 111/111 while prose-only constraints silently fail 44/61 — the same residual TestVDB targets, measured outside VDBMSs. (Numbers taken from the paper's public listing and its repository description this session; not verified against the PDF, so treat as provisional.) It would strengthen Sections 1--2.3 rather than compete with the method, and it is the natural citation for "the documented boundary is prose". Separately, the static documentation-consistency line the paper joins includes canonically DocRef (Zhong \& Su, OOPSLA 2013) and aComment, neither cited, while iComment and @tComment are — a small gap in an otherwise thorough survey.
   - **2.6 [minor, fixable]** The strongest contrast the paper draws against the closest-in-spirit work, CASCADE, is stated through a quotation ("the generated code and tests made the same false assumption over something underspecified in the documentation") plus the claim that both of CASCADE's residual false positives arose that way. I could not verify either the quotation or the residual-false-positive count: CASCADE's full text was unreachable from this machine this session (download failed with a network error), and its abstract-level record shows only the design (doc-derived tests cross-checked against code generated from the same documentation; precision 0.88/specificity 0.97 on 71 inconsistent + 814 consistent Java pairs). The argument is plausible and, if correct, effective; as written it is not checkable from the citation alone.

3. **Soundness** — Adequate
   - **3.1** The RQ2 design is the paper's methodological high point. All 81 candidates are judged in every run (81/81 per run, no case dropped), the adjudication rule is stated in advance and is conservative by construction (uncertainty resolves to \textsc{False-Positive}), the aggregation is majority vote with per-run values shown separately (Table 4), and case-level agreement is reported alongside the rates. I recomputed every derived number from the reported counts — core majority 11/51 = 0.216 with precision 11/15 = 0.733, full majority 19/51 = 0.373 at precision 1.000, source-only 20/51 = 0.392 at 20/21, cognition-only 13/51 = 0.255, per-run suppression 26/30 and 27/30 — and every Wilson interval in the text matches a hand computation. Internal arithmetic is sound (with the one exception in 5.3).
   - **3.2** The paper discloses the protocol-sensitivity of its own headline. Section 4.3 "Where the boundary sits" reports that an earlier full-stage run under the prior, unblinded protocol reached recall 0.841, versus 0.373 under the blinded protocol reported here, and attributes the gap to the disclosed expectation-framing and observation-leakage threats. Publishing the inflation one's own protocol change caused — and demoting the earlier number — is rare and materially raises the credibility of the 0.373 and 1.000 figures. The same honesty governs the FP pool's provenance (submission-filtered, with the bias direction argued).
   - **3.3 [minor, fixable]** The core-versus-full comparison is paired by construction (the same 81 cases judged in both arms) but is analysed as if independent: the paper reports overlapping Wilson intervals and no paired test, and never states the trivial operating points (always-confirm: recall 1.0, suppression 0; always-reject: recall 0, suppression 1.0) that would let a reader locate the reported operating points on the tradeoff curve. A McNemar test over the same cases plus the two trivial baselines is cheap and would convert "the recall difference is visible" into "the recall difference is distinguishable from rule artifacts".
   - **3.4 [major, fixable]** The paper's central mechanism claim is that the implementation source does the falsifying (abstract: "a source-only re-aggregation of the same judgments isolates source grounding as the mechanism"). The evidence in Section 4.3 "Which perspective carries the decision" is a re-decision of the *same* three runs' recorded per-case A/B/C/D fields under a one-perspective rule — the paper is explicit that these are "post-hoc counterfactuals over the recorded judgments---not independent runs", which is good practice, but three consequences follow that the abstract elides: (i) the fields were produced by the same judges under the full configuration, so the D-only rate inherits any bias in how those fields were recorded; (ii) a D-only rule ("validation_absent confirms, otherwise rejects") confirms precisely those cases where a documentation-directed source search finds no validation, which includes cases whose constraint was misread from the start, so its precision (0.952 on this pool) is a property of this pool rather than of the rule; and (iii) the paper's own comparison shows the full rule scoring *below* source-only on recall, so the "mechanism" claim and the shipped configuration point in different directions. Running the D-only rule as a genuine fourth arm over the same frozen packages would settle the claim; as reported, the mechanism is supported but not isolated.
   - **3.5 [minor, fixable]** The yield's boundary is ambiguous in one place. Section 2.3 defines the target as *consistency* and excludes result correctness, and Section 4.3's recall-loss mechanism (ii) lists "approximate-behavior defects … whose transcripts are compatible with an undocumented accuracy contract" as outside the assertion framework. Yet Table 3 counts 5 \textsc{Result-Incorrectness} bugs among the 51 (representative: Qdrant \#10120), and Section 4.3 elsewhere says all three Weaviate mechanism-(i) cases were recovered by source-absence evidence. Please state how those 5 were confirmed — through a contract assertion, or through maintainer adjudication of a candidate the framework itself treats as unassertable — so that "the pipeline found 51 bugs" and "the confirmation stage adjudicates contract assertions" do not read as inconsistent.
   - **3.6** Threats to validity are treated seriously (Section 5): adjudication is declared revisable and one case is retracted by the authors' own re-probe; expectation-framing bias and observation leakage are named and then engineered out of the reported protocol; the assertion framework's boundary is stated with the two candidate behaviors it could not adjudicate; and the external-validity section names the single backbone, the unpinned snapshot, and training-data contamination as a first-order threat. For a paper whose instrument is an LLM, this is the right list, and it is not boilerplate.
   - **3.7 [minor, fixable]** The RQ3 complementarity claim is asymmetric in its evidence. The forward direction is strong and structural (a crash oracle cannot fire on a non-crashing accept; 0 of 7 on v1.18.2 is consistent with that, and the released-template observation is read as a template limitation rather than a class limitation — a fair reading). The reverse direction is a single existence proof on v1.4.0, fourteen minor releases behind the version used for the systematic direction (v1.4.0 vs. v1.18.2), and it credits TestVDB with *reaching* a bug VDBFuzz had already found. The paper mostly says this, but the heading-level claim "complementary by construction" would be better supported by stating the reverse direction explicitly as reach-only (no new detection), and by giving the request volume of the full-coverage run so it can be compared with the 26,000-request sampled run.

4. **Verifiability** — Weak
   - **4.1** The text describes the pipeline and the RQ2 protocol well enough to follow in concept: each stage's inputs and outputs (knowledge.json, specifications.json with typed and evidence-leveled constraints, the five generation gates, the executor's log/marker discipline), the five-section evidence chain, the four mechanical checks, the four perspectives, the verdict vocabulary, and the blinded re-adjudication protocol with its aggregation rules. Cost is disclosed too (\textasciitilde 67 active hours, \textasciitilde 860 sandboxed executions, \textasciitilde 70M input/4.9M output tokens as a stated lower bound). This is the criterion's strongest part.
   - **4.2 [major, fixable]** The artifact is declared but absent. The Data Availability section promises a replication package (agent role definitions, per-version knowledge bases and specifications, generated scripts with raw HTTP logs, evidence chains, submission ledger) "at an anonymized URL", with the link to be added "once the archive is published". At review time none of the member-level evidence behind the headline exists for a reader: the 81 frozen packages, the per-candidate adjudication labels, and the evidence chains are exactly what a verifier would need to check the 87--90\% / 0.373 / 0.392 numbers, and the paper's own analysis depends on fine-grained per-case detail (per-case A/B/C/D fields, pack completeness strata). For an artifact-dependent empirical claim, "will be released" leaves the paper unverifiable in this cycle.
   - **4.3 [major, fixable]** The adjudicating model is unpinned by design and the judge configuration is not disclosed. Section 4.1 states all agents run on GLM-5.2 "under default sampling", and Section 5 concedes that "the exact weights behind any given run are not recoverable from this text". Combined with the absence of the judge prompts and the frozen package contents, third-party reproduction of the RQ2 numbers is impossible even with the packages restored — and the paper's own cited evidence (intra-judge self-inconsistency, self-preference, contamination) is precisely why LLM-judge rates need snapshot-level provenance. Pinning a snapshot identifier and including the judge prompt template in the package would close this.
   - **4.4 [minor, fixable]** The RQ1 ground truth is not enumerable from the paper. Table 2 gives per-system counts and the text names roughly a dozen issue numbers (Milvus \#49823, \#52308, \#52310, \#52312, \#52325; Qdrant \#9045, \#9149, \#9421, \#9524, \#9942, \#10120, \#10369), but the complete list of the 81 adjudicated candidates with their category and the current state of the 49 unadjudicated submissions is only in the unreleased package, so the confirm/false-positive split cannot be audited independently.

5. **Presentation** — Adequate
   - **5.1** The paper is complete and followable: problem and oracle analysis, its own method, evaluation, limitations, related work, conclusion. Threading one real bug (Qdrant \#10369) through all four stages as a running example — extraction of `qdrant_state_recommend_001`, the scenario construction with the size-4/size-8 lookup collection, the log pair, the four-perspective verdict — is an effective device: each abstract stage description is immediately followed by its concrete instantiation, which is what makes a dense multi-agent pipeline readable at all.
   - **5.2 [minor, fixable]** The third Related Work paragraph ("LLM-derived oracles and judge reliability") is a single ~40-line block that moves through Metamon, RBCTest, CASCADE, ARMeta, LlamaRestTest, self-preference bias, judge self-inconsistency, contamination, and hallucination, with several sentences carrying three or more citations. It is the hardest part of the paper to read and the one place where the reader cannot map a claim to its citation at a glance. Splitting it (or extracting a small positioning table: work / anchor / falsifier / residual) would materially improve both readability and the novelty case it is arguing.
   - **5.3 [minor, fixable]** Funnel arithmetic does not close. Section 4.2 partitions the 60 defect-confirming candidates as 19 unreported + 11 covered by merged fix PRs + 5 by-design + 25 pending (= 60), and then refers to "the 44 candidates the gate does not clear", which by that partition is 41. Either the count or the partition is wrong, and the "two measured points, not a complete chain of subtractions" disclaimer does not cover the discrepancy.
   - **5.4 [minor, fixable]** Two pipeline components appear only in the evaluation. The "novelty gate" and "deduplication and family merging" (Section 4.2) carry the reduction from 119 chain verdicts to five registered defects, and the gate's caveat is even discussed in Section 4.2 ("two of its by-design matches were word-level false positives"), but neither component is described in Section 3, which stops at the auditor's verdict. Add them to the pipeline description (inputs, rule, outputs) or state their inputs/outputs where they are used.
   - **5.5 [minor, fixable]** Named-but-undefined components: Section 3.3 lists strategy names ("dual-key family", "teardown-race", "stale-coupling", "error-diagnostic quality", "contract behavior") without defining what any of them does or giving one example each, and Section 3.5 names `developer_cognition.json` and Section 4.3 leans on a "priority rule" whose contract/source precedence is given in prose only at the point of use. A one-line gloss per strategy (or a table) would make the generation and confirmation stages reproducible on their face.
   - **5.6 [minor, fixable]** Two verdict vocabularies coexist for the same stage: \textsc{Confirmed} / \textsc{Refuted} / \textsc{Neutral} in Section 3.5 and the binary \textsc{Confirmed} / \textsc{False-Positive} rule of Section 4.3. The mapping between them (Neutral cases are routed to human review and lie outside the RQ2 measurement) appears in a single clause; a sentence at the end of Section 3.5 stating which verdicts the evaluation consumes would prevent misreading the denominators.

### Summary

The paper targets documentation–implementation bugs in vector database management systems (VDBMSs): cases where a system silently accepts an input or produces a behaviour that contradicts its prose API documentation — the opening example is Milvus accepting `nprobe=0` against a documented `[1, 16384]` range. Qdrant issue #10369 is threaded through all four stages as a running example.

The evaluation has three parts. RQ1 reports an operational ledger of 81 maintainer-adjudicated submissions across Milvus, Qdrant and Weaviate — 51 confirmed bugs, 23 fixed via merged PRs, grouped into eight patterns. RQ2 re-adjudicates the same 81-candidate pool (51 bugs + 30 maintainer-adjudicated non-bugs) under identical frozen packages, blinded and with no human in the loop, in three runs: a contract core that suppresses 87–90% of the 30 false positives while recalling 0.196–0.333 of the 51 bugs, and a full stage (adding source forensics and maintainer cognition) that intercepts all 30 at majority-vote recall 0.373, plus post-hoc single-perspective re-aggregations of the same judgments that put source grounding at 0.392 and cognition at 0.255. ### Core Strengths

- **S1:** The impact evidence is verified to a level rare in bug-finding papers: all 23 merged fix PRs are classified by changed files, every one modifies implementation code, none is documentation-only, and the classifier is validated against the paper's own disproved candidate. — see 1.1, 1.3
- **S2:** The RQ2 protocol is a methodological contribution in itself — frozen packages, stated blinding, three runs with majority vote, Wilson intervals, and a disclosed leakage incident with a re-mining re-check — and its arithmetic and statistics reproduce on recomputation. — see 3.1, 3.2

### Core Weaknesses

- **W1:** The abstract's mechanism claim ("a source-only re-aggregation … isolates source grounding as the mechanism") rests on post-hoc re-decisions of recorded judgments, not on an independent single-perspective run; the body concedes this. — see 3.5
- **W2:** The automated stage's recall is measured only against the authors' own submission-filtered candidate pool; detection coverage against a bug list the pipeline did not produce is unmeasured and unclaimed. — see 3.9, 1.4
- **W3:** The frozen packages are themselves pipeline products: the four contract-core false-positive leaks are attributed to "pack-induced" contract rows, so extraction-stage error sits outside the error budget reported for the confirmation stage. — see 3.6

### Detailed Assessment

1. **Significance** — Adequate
   - **1.1** (strength) §RQ1, "Fix nature": the authors classify all 23 merged fix PRs by changed files — every one modifies implementation code, 15 also add regression tests, none is documentation-only — and validate the classifier against the disproved #9149, correctly identifying that PR as test-only. This is the strongest evidence available that the ledger counts actionable defects rather than documentation edits, and it pre-empts the standard inflation critique of bug-count papers.
   - **1.2** (strength) §2.2 anchors the target problem in the empirical VDBMS literature (the bug study's functional-failure majority; the roadmap naming oracle definition as the open challenge), and the premise is independently corroborated by a source I read in full this session: VDBFuzz's own analysis reports crash bugs at 15.1% of VDBMS defects, and its future-work paragraph asks for a vector-search-correctness oracle that it explicitly does not build. The problem is real, and the class the paper targets is the one left open by the strongest existing tool.
   - **1.3** (strength) §RQ1 "Collection protocol": confirmed / false-positive / duplicate-tracked are defined with care, every submission is re-verified as of September 2026, and adjudication is treated as revisable — the #9149 reclassification after the authors' own seven-version re-probe is exactly the self-correction that maintainer-adjudicated ground truth usually lacks.
   - **1.4 [major, unfixable]** §RQ1 and §RQ2 together show that the 51-bug/23-fix impact result cannot be attributed to the contribution. §RQ1 states the ledger "measures the human--machine pipeline rather than the automated stage alone", and §RQ2 measures the automated stage alone over the same bugs: majority-vote recall 0.216 for the contract core and 0.373 for the full stage (per-run 0.196–0.333 and 0.353–0.431), with the post-hoc source-only arm at 0.392. No baseline isolates what the pipeline adds over a focused human+LLM workflow on the same targets, so the reader cannot tell how much of the outcome is the tool versus the team's attention; the existing data cannot supply that counterfactual.
   - **1.5 [minor, fixable]** Scope of the demonstrated benefit: three production systems and one LLM backbone family, with documentation, images and source clones pinned per tested version while the ledger is cumulative across mining rounds and versions since early 2026. §Limitations discloses the backbone bound; the contribution paragraph in §1 and the abstract state the impact without any bound, and one qualifying clause would align them.

2. **Novelty** — Adequate
   - **2.1** (strength) The delta against MASTOR (Deng et al.; full text read) is real and correctly stated: MASTOR grounds every assertion in implementation source, demotes OAS claims unsubstantiated in source into unread `pending` fields, and its own §7.4.2 concedes it "cannot detect violations of intended requirements that are not reflected in code". TestVDB's anchor inversion — prose as ground, source as falsifier — is a genuine, non-obvious delta over the closest prior work, and §6 (Related Work) states plainly what is not new (a second LLM agent reviewing generated oracles; cross-request behavioural oracles).
   - **2.2** (strength) The residual claim in the REST doc/spec-derived-oracles row of the exclusion table survives verification against the three names it rests on: SATORI (full text read) generates unary oracles on response fields from OpenAPI metadata and field descriptions, not request-acceptance or state semantics; AGORA+ derives invariants from observed traces; MASTOR from source. "No tool derives expectations from system-level prose" held for the works named.
   - **2.3 [minor, fixable]** §1 and the abstract assert that "no deterministic-oracle candidate derives its expectation from system-level prose documentation… leaving an LLM as the practical oracle", while the documentation-derived line reviewed in §2.4 (The Oracle Problem) and §6 (Related Work) includes deterministic classical-NLP readers (@tComment, Toradocu) that do read prose. The defensible claim is the paper's finer one — those readers are method-level and tagged, and interpretation at system-level prose scale is what needs an LLM — but as written the two statements pull against each other.
   - **2.4 [minor, fixable]** Missing related work in my second specialty: the way RQ1 and RQ2 measure a bug-finder — maintainer adjudication as ground truth, duplicate handling, submission-pool bias, the limits of bug counts — is precisely the subject of Klees et al., "Evaluating Fuzz Testing" (CCS 2018; metadata and abstract verified this session: they assessed 32 fuzzing evaluations, "found problems in every evaluation we considered", and showed such problems "can indeed translate to actual wrong or misleading assessments") and of the ground-truth-benchmark line, e.g. Magma (Hazimeh et al., SIGMETRICS PER 2021; abstract verified: it explicitly problematizes crash count, "perhaps the most commonly-used performance metric"). Neither is cited. The paper's methodology already belongs to that tradition; positioning against it would make the methodological contribution legible and make explicit where the pool-internal recall design departs from it.
   - **2.5** A competitor I could verify only at the abstract level: CASCADE (Kiecker et al., PACMSE/FSE 2026) generates unit tests from natural-language documentation and reports an inconsistency only when the original code fails a test and code generated from the same documentation passes it; §6 (Related Work) characterises its falsifier as "another LLM artifact sharing the documentation's ambiguity", which is consistent with that design. The sentence §6 attributes to CASCADE's own analysis ("the generated code and tests made the same false assumption over something underspecified in the documentation") could not be verified this session — no full text was reachable from this network — and I treat the quotation as provisional.

3. **Soundness** — Adequate
   - **3.1** (strength) §RQ2's protocol is unusually disciplined for an LLM-judge evaluation: identical frozen packages, no access to adjudication labels or issue history, denominator 81/81 per run, three runs under a stated majority-vote rule, a conservative binary decision rule, and Wilson 95% intervals. I recomputed the derived quantities and intervals (11/51 = 0.216, 19/51 = 0.373, 20/51 = 0.392, 26/30 = 0.867, 27/30 = 0.900, 20/21 = 0.952, and the corresponding bounds) and they reproduce.
   - **3.2** (strength) §RQ2 "What the full stage adds" audits the cognition files for leakage from the authors' own submissions, finds that one file had absorbed six candidate-anchored entries, re-mines excluding them, and re-adjudicates the eleven affected candidates, reporting no verdict change in any run, with the other two files checked for candidate references. This is the failure mode that most often invalidates LLM-judge studies, and it is handled visibly rather than asserted away.
   - **3.3** (strength) §RQ3's design is bidirectional and self-limiting: the 26,000-request run is disclosed as the authors' own budget rather than VDBFuzz's published one; the full-coverage run executes VDBFuzz's complete released Qdrant template space (205 templates, 50.8 minutes, within the 120-minute-per-tool protocol I verified in VDBFuzz's own evaluation section) and reports no crash; the `wait=true` observation is correctly scoped to the released templates rather than to VDBFuzz's paper; and the reverse direction reaches a crash-class defect by contract reasoning on v1.4.0.
   - **3.4** (strength) The comparator borrowed from the closest published LLM-judge study is accurate: Metamon (Lee, An and Yoo, LLM4Code 2025; full text read) reports exactly the quoted profile — precision 0.722 with recall 0.480 at its permissive threshold on 9,482 pairs, rising to 0.967/0.099, 0.973/0.046 and 1.000/0.021 as the threshold tightens — so the paper's framing of its own precision-first profile against Metamon's is grounded in the source, not in paraphrase.
   - **3.5 [major, fixable]** §RQ2 "Which perspective carries the decision" re-decides the same three runs' recorded per-case perspective fields under single-perspective rules, and the paper itself calls these "post-hoc counterfactuals over the recorded judgments---not independent runs". The abstract nevertheless asserts that "a source-only re-aggregation of the same judgments isolates source grounding as the mechanism". Re-deciding fields that were produced inside a pipeline whose priority rule and rebuild loop couple the perspectives cannot isolate a mechanism; the recorded D field may itself carry the effect of the other perspectives being present. Either run a D-only arm end-to-end (even on the contract core's frozen packages) or weaken "isolates" to "is consistent with".
   - **3.6 [minor, fixable]** §RQ2 attributes the four contract-core false-positive leaks to "a systematic, pack-induced misreading rather than run-to-run noise", the frozen packs containing "contract rows that read as supporting the violation". The packs are products of the same pipeline's extraction stage. Freezing them is the right way to isolate the confirmation stage, but the consequence is that extraction error leaves the reported error budget: those four leaks belong to the system too, and the paper never decomposes how many trace to a claim the documentation does not actually support.
   - **3.7 [minor, fixable]** §RQ2 "Where the boundary sits" attributes the gap between the earlier unblinded recall (0.841) and the blinded one (0.373) to "the measurement cost of blinding". The two protocols differ along at least the two disclosed axes (expectation framing, observation leakage) and nothing separates them; soften the sentence or decompose the difference.
   - **3.8 [minor, fixable]** §Limitations states that all agents run on GLM-5.2 under default sampling and that "the exact weights behind any given run are not recoverable from this text". Three runs of one unpinned model measure within-model sampling variability; the stability readings ("26 of the 30 false positives are rejected in all three runs"; 88.9% agreement) are scoped to that model and configuration, and the judge's cross-family behaviour is untested. A pinned snapshot, or the contract core repeated on a second backbone for a subset, would bound this.
   - **3.9 [minor, unfixable]** The recall figures (0.196–0.333 core, 0.373 full) are computed on the 51 bugs the pipeline itself found and the authors chose to submit — §RQ1 states the pool is "a submission-filtered subset of the pipeline's confirmed output rather than a random sample of it". The paper argues the direction of the induced bias for suppression (conservative) but claims none for recall, and nothing anchors detection coverage against a bug list the pipeline did not produce. The measurement is valid for its stated pool; it cannot be read as a detection rate for the targets.

4. **Verifiability** — Adequate
   - **4.1** (strength) The empirical protocol is given in checkable detail: the run dates (9–10 September 2026), the 81/81 denominator, the blinding statement, the conservative adjudication rule, per-run and majority rows reported separately, and both senses of "false positive" defined before either is used.
   - **4.2** (strength) Inconvenient facts are reported rather than buried: the earlier unblinded 0.841 recall, the leaked cognition entries, the unmaintained intermediate funnel counts, the 49 excluded unadjudicated submissions, and the #9149 reclassification.
   - **4.3 [major, fixable]** §Data Availability promises the replication package at "an anonymized URL" whose link "will be added here once the archive is published". For a paper whose central evidence is LLM judgments over constructed packages, the frozen packages, the extraction outputs, the cognition files, and the agent prompts are exactly what a reader needs; the text alone cannot reproduce a verdict, and §Limitations concedes the model snapshot is not recoverable. Making the anonymized archive reachable at review time, with a backbone snapshot record, is the single highest-leverage fix for this criterion.
   - **4.4 [minor, fixable]** Even granting the promised package, the text does not say how the frozen packages were assembled and sanitized — in particular what was removed of the reporter-perspective framing that §Limitations says otherwise biases the judge — nor when the per-case A/B/C/D outcomes were recorded (prospectively during the runs or reconstructed afterwards). The entire §RQ2 re-aggregation rests on those recorded fields, so a short protocol paragraph is needed.

5. **Presentation** — Adequate
   - **5.1** (strength) The structure is complete and conventional, and the running example (#10369) is threaded through all four stages, which makes the dense approach section followable.
   - **5.2 [minor, fixable]** Density: several sentences in §1 and §RQ2 carry five or more quantitative claims, and the abstract alone asserts roughly ten numbers. The §RQ1 "Process ledger" paragraph reports a funnel (119 verdicts → 96 candidates → 60 confirming → 19/11/5/25 → five new numbers) as running text while conceding intermediate counts were not maintained; a small table would make it auditable.
   - **5.3 [minor, fixable]** The pack-completeness stratification (24 true-bug packs with a pinned contract row vs the 27 without, four recall ranges) appears only as prose. It is load-bearing for the claim about where the boundary sits and should be a table.
   - **5.4 [minor, fixable]** Imprecise phrasing: §1's "the one dedicated VDBMS testing tool, VDBFuzz" understates MeTMaP, which the same paper cites (metmap24) and which VDBFuzz's own related work calls "the most relevant work" for VDBMS testing; "default sampling" is never defined (temperature? top-p?); and the abstract's "intercepts 87--90\% of false positives" does not say it is the per-run range while the majority figure is 86.7%, which an attentive reader will notice.

## Reviewer 3: General Reviewer

**Overall Recommendation:** Weak Accept

### Summary

Vector database management systems (VDBMSs) such as Milvus, Qdrant, and Weaviate serve the embeddings behind retrieval-augmented LLM applications, and the paper targets a class of their defects it calls documentation-implementation bugs: cases where the system silently accepts an input or produces a behavior that violates its natural-language API documentation (the canonical illustration being Milvus accepting `nprobe=0` against its documented [1, 16384] range). Because no crash occurs, a crash-oracle fuzzer such as VDBFuzz cannot fire; the paper argues in a table of oracle candidates that crash signals, differential testing, metamorphic relations, property-based testing, and structured-spec oracles all anchor their expectations somewhere other than the prose, leaving an LLM-derived oracle as the practical option — and importing the false-positive problem of a single model both deriving and judging the expectation. The system, TestVDB, is a four-stage pipeline: documentation crawling into structured, source-verified behavioral specifications; attack agents bound to pre-registered strategies that turn each constraint into executable probes; a Docker sandbox that executes probes and logs raw HTTP; and a confirmation stage in which an evidence builder assembles a five-section evidence chain (document verification, execution evidence, contract grounding, chain trace, source grounding) and a chain auditor applies four mechanical checks and cross-examines the chain from four perspectives — contract, physical behavior, maintainer cognition, and implementation source — with the implementation source positioned as the falsification anchor that breaks the extraction-judgment self-reference.

The evaluation has three parts. Operationally, 81 adjudicated submissions across the three systems produced 51 maintainer-confirmed bugs, 23 of them fixed by merged pull requests, organized into eight bug patterns. In a controlled re-adjudication of the same 81-candidate pool under frozen packages and blinding, three runs of the contract core suppress 26–27 of 30 false positives (0.867–0.900) at 88.9% case-level verdict agreement while recalling only 0.196–0.333 of the 51 true bugs; a full stage adding source forensics and maintainer cognition reaches majority-vote recall 0.373 with all 30 false positives intercepted, and a post-hoc single-perspective re-aggregation of the same runs attributes the falsifying power to source grounding (recall 0.392, precision 0.952). A bidirectional comparison on Qdrant shows complementarity with VDBFuzz: on v1.18.2 a 26,000-request probe reached none of seven live silent-accept bugs, and on v1.18.0 a full-template-space run (205 templates, 50.8 minutes) likewise reaches none of the confirmed documentation-implementation defects, while in the reverse direction TestVDB's contract reasoning reaches VDBFuzz's integer-overflow crash on v1.4.0.

### Core Strengths

- **S1:** Unusually direct evidence of real-world impact, with the "fixed" status of the yield independently validated by classifying each merged PR's changed files — and that classifier cross-checked against the one case the authors themselves disproved. — see 1.1, 1.2
- **S2:** The quantitative spine is internally consistent and recomputable: I re-derived the reported Wilson intervals, all rate conversions, and the cross-table vote arithmetic from Tables 4–5, and everything closes exactly. — see 3.1
- **S3:** The paper stress-tests its own results adversarially — cognition-file leakage audit with re-mining and zero verdict change, a self-disproved true positive reclassified after a seven-version re-probe, and an unflattering counterintuitive result (source-only beating the full priority rule on recall) reported rather than buried. — see 3.2
- **S4:** The oracle-exclusion analysis (Table 1) and the running example threaded through all four stages make the contribution and its boundaries unusually legible for a paper of this density. — see 2.1, 2.2, 5.1

### Core Weaknesses

- **W1:** The paper's central quantitative claims cannot be checked at review time: the frozen packages, per-case perspective records, cognition files, and the submission ledger all live in an archive that "will be released" later, and the package composition and sanitization are described only in summary terms (the transcript plus the contract; the judge sees only those), so nothing behind the recorded per-case judgments is inspectable from the text alone. — see 4.2, 4.3
- **W2:** The 0.841 → 0.373 recall drop is attributed to "the measurement cost of blinding" without any companion unblinded rates or decomposition, so the reader cannot tell whether blinding or an unstated protocol change produced it. — see 3.4
- **W3:** The endpoint/system level taxonomy contradicts the paper's own running example: the #10369 delete-recreate coupling is labeled endpoint-level although the paper's definition names that exact shape as system-level. — see 3.5
- **W4:** Two statistical claims are phrased more strongly than the reported evidence supports ("direct evidence" from a re-aggregation with overlapping intervals and no paired test; "full search space" from template exhaustion). — see 3.6, 3.7
- **W5:** Several load-bearing passages are ambiguous on first read — the gate-funnel sentence whose arithmetic only closes under one of two readings of "clear", the unresolved relation between the cumulative ledger and the single run, and overloaded vocabulary ("level", "false positive"). — see 5.2, 5.3, 5.4

### Detailed Assessment

1. **Significance** — Adequate
   - **1.1** [strength] The impact case is backed by auditable bookkeeping rather than plausibility. Section 4.2 (Table 2) reports 81 maintainer-adjudicated submissions across Milvus (43), Qdrant (28), and Weaviate (10), with 51 confirmed and 23 fixed, and the "Fix nature" paragraph validates the Fixed column by classifying every merged fix PR's changed files (all 23 modify implementation code, 15 add regression tests, none documentation-only), using the disproved #9149 as a validation probe that the classifier correctly flags as test-only. For a defect-detection method, 23 merged fixes in three production systems is concrete evidence the problem is worth solving, corroborated by the reported acceptance labels (50/51 bug-labeled; 25/29 Milvus `triage/accepted`; 5/14 Qdrant `accepted`).
   - **1.2** [strength] The motivation is anchored in the field's own literature and a structural argument rather than anecdote: Section 2.2 grounds the "non-crashing majority" in the cited bug study and roadmap, and Table 1 argues row by row where each oracle family structurally falls short — delimiting the target niche instead of assuming it.
   - **1.3 [minor, fixable]** The paper's own RQ2 bounds the practical reach: under the blinded, forced-binary protocol the full stage's majority-vote recall over the confirmed bugs is 0.373, with per-run recall of 0.353–0.431 (Table 4), and Section 4.2 discloses that the 51/81 ledger rests on author-side novelty screening and a per-candidate submission decision — a human-in-the-loop pipeline, not an autonomous detector. The disclosure is honest, but no operational number is given for what the deployed configuration actually contributes (how many candidates reached the Neutral/human-review route; how many submissions came from automatic versus human-confirmed verdicts), which leaves the reader unable to size the impact above "assists a human". — see Q3.

2. **Novelty** — Adequate (provisional)
   - *Provisional flag: I did not survey this field for this review. Everything below about other systems is taken from the paper's own descriptions of them, not from independent verification, so this criterion should be re-rated by a literature-grounded reviewer.*
   - **2.1** [strength] The paper is candid about shared components and locates its delta precisely. Section 6 concedes that "a generated oracle reviewed by a second LLM agent is therefore not new here" (MASTOR's ChallengerAgent) and that cross-request behavioral oracles are not unique to TestVDB, then names its closest comparators with specific differences: MASTOR anchors in source code; Metamon interrogates behavior with a same-family LLM judge stabilized by negated-assertion prompt pairs and self-consistency (reported precision 0.722, recall 0.480 at its permissive threshold); CASCADE cross-checks documentation-derived tests against code generated from the same documentation, so its falsifier shares the documentation's ambiguity; RBCTest's verifier is an LLM-side check rather than an independent evidence source. The claimed new element — "anchor inversion": the prose is the authority and the implementation source is the falsifier, whereas MASTOR's authority is the implementation — is a genuinely distinct design stance, and the paper states it as its actual claim rather than overclaiming.
   - **2.2** [strength] Table 1 and Section 2.4 turn "why can't deterministic oracles do this" into a structured exclusion analysis with a per-family reason (crash oracles have no expectation to compare; differential testing's reference may itself diverge from the docs; metamorphic relations check relations the tester already poses; a property-based property is exactly the prose claim; structured specs bound fields, and several endpoints serve none), while explicitly crediting the counterexample class (SATORI-style OpenAPI field oracles). This is an analytic contribution beyond a system description.
   - **2.3 [minor, fixable]** Provisional. On the paper's own account, the machinery is assembled from recognizable LLM-oracle components, and the recognized-new delta is one design idea plus the domain instantiation and the empirical measurements. That is a real but incremental contribution, and it would be sharpened by one worked contrast: a concrete candidate on which a source-anchored authority (MASTOR-style) would call the behavior correct but a documentation-anchored oracle flags it — the scenario the anchor inversion exists to catch. This is a repositioning/illustration fix, not a new-result fix; a field expert may reasonably move this tier in either direction.

3. **Soundness** — Adequate
   - **3.1** [strength] The quantitative spine is internally consistent and recomputable, which I checked rather than assumed. Every row of Tables 4–5 satisfies TP+FN = 51 and FP+TN = 30; the stated Wilson intervals reproduce exactly (26/30 → [0.703, 0.947]; 27/30 → [0.744, 0.965]; 11/51 → [0.125, 0.346]; 19/51 → [0.253, 0.510]; 20/51 → [0.270, 0.529]; 20/21 → [0.773, 0.992]; 30/30 → [0.886, 1.000]); the derived rates match (17/51 = 0.333, 10/51 = 0.196, 26/30 = 0.867, 27/30 = 0.900, 11/15 = 0.733, 19/19 = 1.000, 72/81 = 88.9%, 68/81 = 84.0%). The cross-table vote arithmetic also closes: the core's "nine disagreeing cases, eight true bugs and one two-to-one false positive" resolves uniquely to 10 unanimous true-bug confirmations plus one 2-1 case, and the quoted pairwise range 90.1–96.3% is exactly what those vote patterns imply; on the full stage, the source-only-versus-priority-rule difference (one false positive vetoed, four boundary truths suppressed, three recovered = eight moving cases; 20−4+3 = 19 true positives, 1−1 = 0 false positives) is arithmetically exact. I found no arithmetic inconsistency anywhere in the paper's headline claims.
   - **3.2** [strength] The paper actively tries to falsify its own results. Section 4.2 re-verifies every submission's state as of September 2026 and reclassifies a candidate previously counted as a fixed true positive (Qdrant #9149) after a seven-version re-probe showed its fix PR was test-only. Section 4.3 explains the four systematically misconfirmed false positives as pack-induced rather than run-to-run noise; audits the cognition files and finds one that had absorbed six candidate-anchored entries, re-mines to exclude them, and shows no verdict changed in any run ("suppression stays 1.000"); reports the counterintuitive finding that the full priority rule scores marginally below source-alone on recall and explains the trade rather than burying it; and discloses that an earlier unblinded run had reported recall 0.841, choosing the lower blinded number for the paper. For a method whose judge is an LLM, this is close to best-practice self-auditing.
   - **3.3 [minor, fixable]** Section 5 (Internal validity) says the expectation-framing bias "affects precision-side rates, not the recall headline", while the same paragraph says both disclosed threats are "addressed by the frozen-package RQ2 protocol". Since the headline suppression rate (0.867–1.000) is itself a precision-side rate, the reader cannot tell whether the paper claims that number is free of the residual bias or not. One sentence stating precisely which quoted rates are believed bias-free under the frozen protocol, and which are not, would resolve the tension. — see Q1.
   - **3.4 [minor, fixable]** Section 4.3 states that "an earlier full-stage run under the prior, unblinded protocol had reported recall 0.841; the gap to 0.373 here is the measurement cost of blinding." No unblinded-side suppression or precision figure, and no intermediate configuration, is reported, so a reader cannot distinguish "blinding removed confirmation inflation" from "the protocol also changed in other ways" (the binary forced-FP rule, the priority rule, package construction). Either report the unblinded protocol's companion rates for the same pool, or soften the attribution from a claim to a hypothesis. — see Q2.
   - **3.5 [minor, fixable]** Section 3.2 defines the endpoint/system level observationally: a violation observable from a single request/response pair is endpoint-level; one "whose violation requires observing behavior across requests or against evolved system state (a delete-recreate cycle that must invalidate stale couplings)" is system-level. Two paragraphs later, the running example labels the #10369 constraint `qdrant_state_recommend_001` as "level endpoint", even though its violation is precisely demonstrated by deleting and recreating the lookup collection at a new vector size. One of the two must give: either the definition's parenthetical is too broad, or the example's label is wrong. As written, the taxonomy that routes generation paths is self-contradictory at its showcase case. — see Q5.
   - **3.6 [minor, fixable]** Section 4.4 concludes that the full-template-space run is "measured over VDBFuzz's full search space rather than asserted from a sampled probe". The run's 205 templates are the released Qdrant template set, but the paper itself describes VDBFuzz as using "template-based input mutation" (Section 2.2), so exhausting the templates is not self-evidently exhausting the fuzzer's input space. The structural argument (a crash oracle cannot fire on a HTTP-200 silent accept) cleanly covers the seven silent accepts; the stronger "full search space" phrasing should be justified (mutations are template-bounded) or softened. — see Q4.
   - **3.7 [minor, fixable]** Section 4.3 calls the source-only re-aggregation "direct evidence" that source grounding does the falsifying, but the compared arms have overlapping Wilson intervals (core 0.216 [0.125, 0.346] vs. source-only 0.392 [0.270, 0.529]) and no paired test is reported — although the data are paired by construction (same runs, same cases, different decision rule), which would support a McNemar-style comparison. The effect is large and the interpretation is probably right, but "direct evidence" outruns the reported statistics; add the paired test or calibrate the phrase.

4. **Verifiability** — Adequate
   - **4.1** [strength] The text is unusually rich in procedure. Named intermediate artifacts and their roles are specified throughout Section 3: `knowledge.json` and `specifications.json` with `constraint_id`, `assertion`, `type`, `evidence_tier`, `source_verified`, and `level`; five named generation gates including `py_compile` and a cross-DB signature fingerprint check; `.executor.env`, `output_$B.log` plus atomic `.done` markers with per-batch count verification; the five-section `evidence_chain.json`, the four mechanical checks with a three-retry rebuild bound, and the four perspectives. The evaluation protocols carry concrete numbers (three systems and pinned versions; 81/81 run denominators; the conservative binary rule; majority vote; 26,000 requests; 205 templates; 50.8 minutes; ≈860 script executions; ≈67 hours; token counts; September-2026 re-verification). A competent team could re-implement the pipeline's shape and the RQ2/RQ3 protocols in concept.
   - **4.2 [minor, fixable]** The artifact promise is future-tense: the Data Availability section says the replication package "will be released at an anonymized URL" that "will be added here once the archive is published." The paper does state, at a summary level, what a frozen package is — "the observed execution transcript plus the documented contract" — and that under the RQ2 protocol "the judge sees only observed transcripts and documented contracts." But at review time the per-case records behind Tables 4–5, the cognition files, the evidence chains, and the submission ledger are not inspectable, and the composition and sanitization are described only at that level of detail: the text names the two components and the judge's restricted view, but gives no file-level inventory of a package and no operational detail of how the transcripts were prepared so that the judge sees only them. The headline re-adjudication matrix can therefore be followed but not checked. Since the protocol is the paper's central contribution, the revision should make the anonymized archive live, or state precisely what it will contain and how packages were sanitized. — see Q1.
   - **4.3 [minor, fixable]** Run configuration is under-specified for a paper whose subject is LLM-judgment variance: "GLM-5.2 under default sampling" (Sections 3.5 and 4.1) never gives temperature, top-p, or seed, nor whether any decoding control was used across the three runs — despite Section 5 conceding that "the exact weights behind any given run are not recoverable from this text."
