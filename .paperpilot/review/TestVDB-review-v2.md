# Reviewer 1: Domain Expert

**Overall Recommendation:** Weak Reject

### Summary

TestVDB targets documentation-implementation defects in Vector Database Management Systems (VDBMSs), where a system silently accepts inputs that violate its natural-language API documentation (e.g., accepting `nprobe=0` when documentation declares range `[1, 16384]`). The authors argue that classical oracles (crash, differential, metamorphic, property-based) cannot adjudicate these accept/reject decisions because the boundary is prose rather than a machine-checkable schema, leaving an LLM as the practical oracle. They instantiate a four-stage pipeline—behavioral-claim extraction, test generation, sandboxed execution, and defect confirmation—augmented with a "dev-reviewer" agent that falsifies candidates against implementation source to suppress false positives from two LLM failure modes (hallucination in claim extraction, self-preference in judgment). Evaluation across three VDBMSs (Milvus, Qdrant, Weaviate) reports 107 submitted issues with 50 maintainer-acknowledged true positives (15 merged-PR fixes). A 48-candidate retrospective shows the dev-reviewer reaches 67% precision and 74% recall against a 37% recall baseline without source grounding. A bidirectional probe against VDBFuzz on Qdrant explores complementary coverage.

### Core Strengths

- **S1:** Well-motivated problem domain — documentation-implementation defects in VDBMSs are a real and costly defect class that crash-oracle fuzzers structurally miss (Table 1 exclusion argument is compelling) — see 1, 2.1
- **S2:** Dev-reviewer falsification design is conceptually sound — using implementation source as independent ground truth to break LLM self-preference is a principled response to the documented false-positive problem — see 2.5, 3.2
- **S3:** Empirical validation on three production VDBMSs with maintainer adjudication provides stronger evidence than simulation-only studies; 15 merged-PR fixes demonstrate practical impact — see 3.1
- **S4:** Clear articulation of LLM failure modes (hallucination in extraction, self-preference in judgment) with concrete examples (#9255 reversal, 12-FP/4-TP ablation) — see 3.2

### Core Weaknesses

- **W1:** Cross-family generalization is unproven and severely limits claim — results are backbone-specific (GLM-5.2), cross-model re-runs show verdict is family-specific (Cohen's κ in slight-to-fair band), and the paper offers only cross-family voting as partial mitigation — see 3.2, 6.3 — **[major, unfixable in current form]**
- **W2:** 48-candidate retrospective is non-random and potentially biased; operating point (3-run union) is post-hoc selected, and Wilson CIs do not account for this selection — internal validity concerns weaken the precision/recall claims — see 3.2, 5 — **[major, fixable with stronger methodology]**
- **W3:** Construct validity threat — implementation-as-correct assumption is necessary but not fully justified; paper acknowledges 15 merged-PR fixes support it but provides no systematic analysis of potential false-negative rate where documentation is correct and implementation is buggy — see 5 — **[major, unfixable]**
- **W4:** External validity on Weaviate is weak — only a 11-candidate controlled subset is reported, with no per-vendor recall headline due to sparse fix density — reduces confidence in generalization beyond Milvus/Qdrant — see 3.2, 5 — **[minor, fixable with more data]**
- **W5:** Related Work coverage appears incomplete for a software testing venue — broad connections to property-based testing literature beyond QuickCheck, metamorphic testing frameworks, and formal specification languages are underexplored — see 6 — **[minor, fixable with expansion]**

### Detailed Assessment

#### 1. Significance — Adequate

- **1.1** The problem domain is well-motivated and significant. Documentation-implementation defects in VDBMSs are a real defect class with practical impact (Section 1), and the empirical bug study citation (bugstudy25) provides supporting evidence that >50% of VDBMS bugs manifest as functional failures rather than crashes. The cost argument in Section 1 is persuasive: silent-accept defects corrupt query semantics in retrieval-augmented LLM applications without triggering error codes, making them difficult to detect in production.

- **1.2 [major, fixable]** The scope limitation to documentation-implementation defects (as opposed to result correctness) is both appropriate and clearly stated (Section 2.2), but the paper does not quantify the prevalence of this defect subclass within the broader VDBMS defect landscape. The 107 submitted issues and 50 acknowledged true positives are an absolute count, not a population estimate. Without capture-recapture or unbiased defect sampling (acknowledged as future work in Section 5), the practical significance of this defect class relative to other VDBMS defect types remains unclear. This bounds but does not undermine the contribution.

- **1.3 [minor, fixable]** The portability probe to CouchDB and Elasticsearch (Section 3.4) is preliminary but supports the claim that the regime generalizes to systems with prose documentation rather than VDBMSs specifically. However, the two CouchDB gaps submitted and acknowledged (apache/couchdb #6087, #6088) are a small sample, and the paper claims transferability only on "structural grounds" without empirical testing. Strengthening this section with at least one additional non-VDBMS case study would solidify the significance claim.

#### 2. Novelty — Adequate

- **2.1** The oracle-exclusion argument (Table 1) is a strong novelty framing. The paper systematically walks through why classical oracles (crash, differential, metamorphic, property-based) and recent REST-API oracle tools (AGORA+, SATORI, MASTOR) miss the documentation-implementation residual, leaving an LLM as the practical option. This establishes a clear boundary in the design space and motivates the LLM-derived oracle as a necessary rather than opportunistic choice.

- **2.2** The dev-reviewer falsification mechanism (Section 2.5) is the core novelty contribution. Using implementation source as an independent information source to break LLM self-preference is conceptually sound and distinct from prior work in the documentation-derived oracle lineage (Toradocu and extensions). The three-check falsification (independently reproducible, evidence sufficient, falsifiable) and the distinction between the dev-reviewer as a falsifier (not a second extractor) is a clear advance over runtime-only validation approaches (Doc2OracLL, AugmenTest, ChatAssert, Testora). The #9255 reversal example concretely illustrates how source grounding catches false positives that multi-perspective judging misses.

- **2.3 [major, unfixable]** Cross-family generalization is severely limited and weakens the novelty claim. Section 3.2 reports that a full independent cross-model re-run (DeepSeek, Qwen-3.8-Max, LongCat-2.0) shows the verdict is family-specific (Cohen's κ vs. GLM's 3-run union: 0.32, 0.20, 0.18—all in the slight-to-fair band). The paper acknowledges this but offers only cross-family voting as a partial mitigation (81% recall at 73% precision for GLM ∪ DeepSeek). The fundamental reliance on a single LLM family (GLM-5.2) for all headline results means the approach is not currently generalizable beyond that backbone, which is a significant limitation for a testing tool claimed to be portable across systems. The authors flag this as "open" (Section 6.3), but the current work does not solve it.

- **2.4 [minor, fixable]** The Related Work section (Section 6) is focused on immediate competitors (VDBFuzz, REST-API oracle tools, LLM-as-judge reliability, documentation-derived oracles) but appears incomplete for a software testing venue. Broader connections to the property-based testing literature beyond QuickCheck (e.g., Hypothesis, Hedgehog, Haskell QuickCheck modern variants), metamorphic testing frameworks (e.g., Metamorphic Testing for deep learning systems), and formal specification languages (e.g., Z, TLA+, Alloy for behavioral specifications) are underexplored. While these may not directly address the prose-documentation regime, positioning TestVDB relative to this broader testing literature would strengthen the novelty framing.

#### 3. Soundness — Weak

- **3.1** The main claims are supported by maintainer adjudication across three production VDBMSs, which is stronger evidence than simulation-only or synthetic benchmarks. The 107 submitted issues with 50 acknowledged true positives (69.4% yield precision on adjudicated cases) and 15 merged-PR fixes demonstrate that TestVDB surfaces real defects that maintainers accept and fix. The bidirectional probe against VDBFuzz on Qdrant (Section 3.3) provides controlled evidence that TestVDB reaches defects VDBFuzz misses (silent-accept defects) and can reach some crash-class defects by contract reasoning, while VDBFuzz misses TestVDB's silent-accept defects under current templates. This supports the complementary coverage claim.

- **3.2 [major, fixable]** The 48-candidate retrospective for RQ2 (false-positive suppression) is non-random and potentially biased. The paper states the set is "drawn from the 107 submissions to balance vendor and verdict while requiring maintainer adjudication" but does not describe the sampling procedure. A non-random sample may over-represent cases where source grounding is decisive, which would inflate the precision/recall estimates. The operating point (3-run any-confirmed union) is post-hoc selected from four operating points reported in Table 2, and the Wilson 95% CIs do not account for this selection. The paper acknowledges this ("the Wilson CIs do not account for selection across the four operating points") and provides bootstrap validation and held-out cross-validation as mitigations, but the fundamental concern remains: the headline precision/recall numbers may not generalize to the full population of documentation-implementation defects.

- **3.3 [major, fixable]** Single-run variance is high (15-78% recall across five independent runs, Figure 3), and the 3-run union ensemble is a post-hoc response to this variance. The paper justifies the union as the operating point because "majority voting collapses recall when conservative runs dominate the vote" (Section 3.2), but this is a design decision made after observing the variance, not a pre-registered rule. The ensemble improves the headline but does not address the underlying high-variance phenomenon, which suggests the LLM judge agent's behavior is unstable in ways that union ensembles mask rather than fix.

- **3.4 [major, unfixable]** The implementation-as-correct assumption (Section 5) bounds the approach: an implementation bug can wrongly falsify a clause whose documentation is correct. The paper provides two justifications: (1) 31 of the 50 true positives have merged or open fix-PRs, so implementation bugs were confirmed by maintainers; (2) no false positive was traced to an implementation bug—all FPs are maintainer-adjudicated by-design. However, this does not quantify the false-negative rate where the documentation is correct and the implementation is buggy. Such cases would surface as false negatives of the dev-reviewer (candidates suppressed as false positives when the documentation was actually correct), and the paper acknowledges "we did not quantify this false-negative rate." This is an inherent limitation of treating the implementation as ground truth, and without a ground-truth catalog of documentation errors (which the paper states does not exist for VDBMSs), this limitation cannot be fully resolved. The 15 merged-PR fixes suggest the assumption holds often enough to be useful, but it remains an unbounded threat to construct validity.

- **3.5 [minor, fixable]** The threat-model anchor in dev-reviewer falsification is described as "unstable on state and concurrency false positives where the source behavior is timing-dependent" (Section 2.5). The 12-FP/4-TP ablation (Table 3) shows the threat-model anchor alone suppresses 6/12 false positives (50%), but the instability suggests its contribution is context-dependent. The paper does not characterize when the threat-model anchor is reliable versus when it produces false negatives, which limits understanding of its role in the falsification pipeline.

- **3.6 [minor, fixable]** The external validity assessment on Weaviate is weak. The paper reports "a smaller controlled subset (Section 4)" and notes "Weaviate's sparse maintainer-fixed TP density (3 of 30) precludes a per-vendor recall headline," but Section 4 does not clearly describe this subset. Section 3.2 mentions "to probe a third VDBMS we ran the dev-reviewer once on a Weaviate controlled subset of 11 candidates (v1.38.0 evidence re-probed against v1.38.2, source-grounded against the v1.38.2 clone)," which produced 7 source-grounded confirmations and 4 false positives. This is a single run with no precision/recall headline, reducing confidence in generalization beyond Milvus and Qdrant.

#### 4. Verifiability — Adequate

- **4.1** The paper provides sufficient information to understand the pipeline architecture and agent roles (Section 2, Figure 1). The artifact citation (https://github.com/yihui504/testvdb-anon) promises full prompts (22 agent role definitions), target versions, per-token accounting, the 48-candidate ground truth, and a reproduction driver. If the artifact is complete and reproducible, the work would be verifiable. The paper reports all agents run on GLM-5.2 via the BigModel Anthropic-compatible API under default sampling, which is specific enough for replication.

- **4.2 [minor, fixable]** The paper does not provide per-token accounting or cost details in the main text (only "roughly $10 per target" in Section 2.6). Table 4 provides approximate per-target LLM-call distribution, but actual token counts and API costs would strengthen verifiability. The artifact may contain this, but summarizing in the paper (even an appendix) would be useful for reproducibility.

- **4.3 [minor, fixable]** The 48-candidate ground truth is described as maintainer-adjudicated but not listed in full. The artifact promises it under `test_questions/`, but including a table in the paper (even in an appendix) with case IDs, verdicts, and maintainer labels would allow readers to verify the precision/recall calculations independently. Similarly, the 107 submitted issues are summarized by vendor and yield (Table 1) but not individually listed, making it difficult to verify the 69.4% yield precision calculation (50 TP of 72 adjudicated) without access to external issue trackers.

#### 5. Presentation — Weak

- **5.1** The paper is well-structured with a clear narrative arc: problem → oracle exclusion argument → approach → evaluation → limitations. The figures (especially Figure 1 pipeline overview and Figure 2 dev-reviewer three-check diagram) are clear and well-designed. The tables (especially Table 1 oracle exclusion, Table 2 operating points, Table 3 ablation) effectively communicate key results. The writing is generally clear despite some density.

- **5.2 [minor, fixable]** Section 3.2 (RQ2: False-Positive Suppression) is extremely dense and difficult to follow. It packs root cause analysis, baseline results, dev-reviewer results, ablation, cross-model re-runs, and vendor-specific analysis into a long section with multiple nested paragraphs. Splitting this into subsections (e.g., Root Causes, Baseline, Dev-Reviewer Results, Ablation, Cross-Model Generalization) would improve readability. Similarly, Section 3.3 (RQ3: Comparison with VDBFuzz) is dense and would benefit from clearer separation between the systematic VDBFuzz direction (26,000 requests, 0 of 14 TPs reached) and the controlled case studies (v1.4.0, v1.18.0).

- **5.3 [minor, fixable]** There are several minor language issues and awkward phrasings:
  - Line 16: "yet most of their defects are logical bugs that produce no crash and thus escape crash-oracle fuzzers such as VDBFuzz" — awkward phrasing; consider "yet most defects manifest as logical bugs that do not trigger crashes and thus evade crash-oracle fuzzers such as VDBFuzz"
  - Section 2.5: "The two modes point to different fixes" — unclear what "modes" refers to (hallucination vs. self-preference); rephrase to "the two failure modes point to different mitigation strategies"
  - Section 3.2: "Single-run recall spans 15--78% because some runs are conservative and confirm few candidates" — clarify that conservative runs produce few confirmations, leading to low recall
  - Section 5: "The 15 merged-PR fixes suggest the implementation-as-correct assumption holds often enough to be useful, without guarantee" — awkward ending; rephrase to "holds often enough to be useful, but without guarantee"

- **5.4 [minor, fixable]** Some notation inconsistencies:
  - Section 2.1 uses both `nprobe` and `\texttt{nprobe}`; standardize to one style (likely `\texttt{nprobe}` for code/parameter names)
  - Table 1 uses "VDBFuzz~\cite{vdbfuzz26}" while other rows use plain citation styles; standardize citation formatting
  - Section 3.2 uses both "any-confirmed" and "union"; clarify they are equivalent and use one term consistently

### Questions for Authors

- **Q1:** Can you provide more details on the 48-candidate retrospective sampling procedure? Was it random, stratified, or purposively sampled? How many candidates were excluded, and what were the exclusion criteria? — **intended effect:** If the sampling is clearly described and potential biases acknowledged, item 3.2's rating would move from Weak to Adequate.
- **Q2:** The 3-run union ensemble is a post-hoc operating point. If you had pre-registered a single operating point (e.g., 3-run majority, 5-run union) and evaluated only that, how would the precision/recall trade-off change? — **intended effect:** If pre-registered performance is comparable to the post-hoc selection, item 3.3's rating would move from Weak to Adequate by reducing the post-hoc selection concern.
- **Q3:** For the cross-model re-runs showing family-specific verdicts, did you explore prompt engineering or chain-of-thought modifications to improve cross-family consistency? If not, is this a promising direction for future work? — **intended effect:** If there are promising unexplored directions for improving cross-family consistency, item 2.3's rating would move from unfixable to fixable (with future work), changing the Overall Recommendation to Weak Accept.
- **Q4:** Can you quantify or bound the false-negative rate from the implementation-as-correct assumption? For example, in the 22 by-design or rejected cases, did any appear to be documentation-correct/implementation-bug that the dev-reviewer wrongly suppressed? — **intended effect:** If the false-negative rate can be bounded or shown to be small, item 3.4's rating would move from Weak to Adequate.
- **Q5:** For the Weaviate generalization, can you expand the 11-candidate subset to more runs or candidates to provide a headline precision/recall, even if with wide confidence intervals? — **intended effect:** If Weaviate evaluation is strengthened, item 3.6's rating would move from Weak to Adequate.


## Reviewer 2: Area Specialist (LLM-as-Judge Reliability & Documentation-Derived Oracles)

**Overall Recommendation:** Weak Accept

### Summary

TestVDB targets documentation-implementation defects in Vector Database Management Systems (VDBMSs), where a system silently accepts inputs violating its natural-language API documentation (e.g., accepting `nprobe=0` when documentation specifies range [1, 16384]). The authors argue that because the boundary is prose rather than a structured schema, deterministic oracles (differential, metamorphic, property-based) cannot adjudicate these accept/reject decisions, leaving an LLM as the practical oracle. They instantiate a four-stage pipeline (claim extraction, test generation, sandboxed execution, defect confirmation) with LLMs automating documentation reading, generation, and adjudication. Two failure modes emerge: LLM hallucination in claim extraction and self-preference bias in judgment. A multi-perspective judging baseline raises precision but collapses recall, so the authors introduce a "dev-reviewer" agent that acts as a source-grounded falsifier, reproducing candidates, cross-checking against implementation source, and attempting disproof. On 48 maintainer-adjudicated candidates, the dev-reviewer reaches 67% precision and 74% recall (3-run ensemble) versus 37% recall without source grounding. TestVDB surfaced 107 issues with 50 maintainer-acknowledged true-positive defects (15 merged-PR fixes) across Milvus, Qdrant, and Weaviate. A bidirectional probe against VDBFuzz on Qdrant shows complementary coverage: TestVDB reaches crash-class defects by contract reasoning, while VDBFuzz misses silent-accept defects under its current templates.

### Core Strengths

- **S1:** Strong empirical validation with maintainer-adjudicated ground truth — 50 true-positive defects acknowledged across three production VDBMSs, with 15 merged-PR fixes demonstrating real-world impact. — see 1.1, 3.1

- **S2:** Well-diagnosed false-positive problem with two clear failure modes (hallucination in extraction, self-preference in judgment) and principled falsification solution (source-grounded dev-reviewer). — see 2.1, 2.2

- **S3:** Rigorous multi-method evaluation: yield precision (RQ1), false-positive suppression with ablation (RQ2), and bidirectional comparison with VDBFuzz (RQ3). — see 3.1, 3.2, 3.3

- **S4:** Clear oracle-exclusion argument (Table 1) walking through why deterministic alternatives miss documentation-implementation defects, establishing LLM-derived oracle as the practical residual. — see 1.1

### Core Weaknesses

- **W1:** Single-LLM-family evaluation (GLM-5.2 only for primary results) with demonstrated family-specific verdicts (Cohen's κ 0.32 DeepSeek, 0.20 LongCat, 0.18 Qwen), leaving cross-family robustness open and threatening external validity. — see 2.3 [major, unfixable]

- **W2:** Non-random 48-candidate retrospective for RQ2 may over-represent cases where source grounding is decisive; paper does not quantify false-negative rate (no ground-truth defect catalog for VDBMSs). — see 3.2 [major, fixable]

- **W3:** Literature scripts failed during review; Novelty and Related Work assessments are provisional pending full competitor verification. — see 2.1, 2.2 [minor, fixable]

### Detailed Assessment

#### 1. Significance — Adequate

- **1.1** The paper addresses a real and costly problem: more than half of VDBMS bugs are functional failures (empirical bug study), and existing crash-oracle fuzzers miss the silent-accept majority. The 50 maintainer-acknowledged true positives with 15 merged-PR fixes across three production VDBMSs demonstrate practical impact on systems that power retrieval-augmented LLM applications. The contribution is meaningful and bounded—useful for VDBMS testing and structurally similar documentation regimes (REST APIs without OpenAPI, configuration validation), but not a general solution to all test-oracle problems.

- **1.2 [minor, unfixable]** The problem scope is inherently specialized. TestVDB targets a specific defect class (documentation-implementation consistency) in systems with prose documentation, not the broader correctness problem (ANN recall, ranking). The paper explicitly positions this as a targeted contribution, which limits significance but improves focus. The 107-submission yield is biased by tool design and not a population estimate.

#### 2. Novelty — Adequate (Provisional — Literature Pending)

- **2.1** The core novelty is **source-grounded falsification**: using implementation source code as an independent ground truth to falsify LLM-derived claims, breaking both hallucination (by checking against source) and self-preference (by using an information source outside the LLM family). The authors argue this is a distinct approach from prior documentation-oracle work (Toradocu, AugmenTest, ChatAssert), which treats the LLM as the final semantic arbiter validating only through runtime behavior. The three-check falsification (independently reproducible, evidence sufficient, falsifiable) and three-anchor design (clean-reproduction, source-grounded, threat-model) appear to be a new contribution to the LLM-as-judge reliability literature. **Assessment pending full competitor verification** — literature scripts failed, so this characterization relies on paper's citation analysis.

- **2.2** The dev-reviewer agent architecture is novel within test-oracle work. While self-preference bias is established for general LLM evaluation (Panickssery et al., Wataoka et al.), applying source-grounded falsification to suppress it in a testing pipeline is new. The ablation (source alone suppresses 75% of false positives on a 12-FP/4-TP control) directly measures this contribution. However, the multi-perspective judging baseline (four specialized judge agents with majority vote) that fails due to shared documentation ambiguity is a predictable negative result rather than novel discovery.

- **2.3 [major, unfixable]** **Cross-family robustness is open and threatens external validity.** The paper shows that verdict is family-specific: full independent cross-model re-runs (DeepSeek, Qwen-3.8-Max, LongCat-2.0) achieve low Cohen's κ against GLM's 3-run union (0.32 DeepSeek, 0.20 LongCat, 0.18 Qwen), all in slight-to-fair band. Recall gaps are large: DeepSeek 56%, LongCat 22%, Qwen 19% vs. GLM 74% (3-run). The cross-family voting probe (81% recall at 73% precision, GLM ∪ DeepSeek) is a promising mitigation but remains exploratory. Section 4.3 (Construct validity) acknowledges this limitation honestly, but it bounds the claim: source-grounded falsification is backbone-dependent, and the approach may not generalize beyond GLM-5.2 without further engineering.

#### 3. Soundness — Weak

- **3.1** RQ1 (detection capability) provides strong evidence for the primary claim: 107 submitted issues with 50 maintainer-acknowledged true positives (69.4% yield precision, Wilson 95% CI [58.0%, 78.9%]) across three production VDBMSs. The 15 merged-PR fixes are compelling evidence of real-world impact. The breakdown by vendor (Table 2) shows systematic patterns: Milvus defects concentrate in optional-default parameters, Qdrant in search parameters and state operations, Weaviate in idempotent behaviors—matching the paper's diagnosis that ambiguous defaults invite over-formalization. This supports the mechanistic claim about documentation-implementation defects.

- **3.2** RQ2 (false-positive suppression) demonstrates effectiveness but has notable gaps. The 48-candidate retrospective shows dev-reviewer reaches 67% precision / 74% recall (3-run any-confirmed) vs. 48% / 56% / 37% single-LLM baseline. The 12-FP/4-TP ablation (Table 4) isolates source grounding's contribution (75% FP suppression). However:
  - **[major, fixable]** The 48-candidate set is maintainer-adjudicated but **non-random** and may **over-represent** cases where source grounding is decisive. The paper does not pre-register the candidate set, and a capture-recapture or unbiased defect-sample estimation is listed as future work. The Wilson CIs do not account for selection across four operating points (3-run union, 5-run union, majority voting), though bootstrap resampling (2000 resamples) and held-out cross-validation (200 random 50/50 splits) support that the 3-run choice is not an overfit.
  - **[minor, fixable]** Single-run variance is extreme (15-78% recall), and the paper justifies the 3-run any-confirmed ensemble as a post-hoc operating point ("falsifier semantics: a candidate surviving any independent falsification is more likely a true defect"). This is reasonable for a falsifier but should be flagged as exploratory. The Bonferroni correction widens 3-run CIs to roughly [44%, 84%] (precision) and [51%, 89%] (recall), not changing the qualitative claim.
  - The paper does not quantify **false-negative rate** (how many true defects dev-reviewer suppresses) because no public ground-truth defect catalog exists for VDBMSs. The implementation-as-correct assumption (a correct implementation can wrongly falsify a right documentation clause) bounds the approach. The paper reports no observed false negatives from this assumption (all FPs are maintainer-adjudicated by-design), but the rate is unknown.

- **3.3** RQ3 (comparison with VDBFuzz) provides good bidirectional evidence. The systematic direction (VDBFuzz on Qdrant v1.18.2, 26,000 requests, reaches 0 of 14 TestVDB silent-accept true positives) is structural and compelling—crash oracles cannot detect non-crashing accepts by construction. The controlled cases (v1.4.0 integer-overflow crash, v1.18.0 empty-vector defect) isolate mechanisms but are n=1 each. The paper correctly reads the reverse direction as a **limitation of VDBFuzz's current templates** (template suite uses `wait=true` and doesn't probe `wait=false`), not a property of crash oracles as a class. This is careful reasoning.

- **3.4 [major, unfixable]** **External validity threats are substantial.** (1) Single-LLM-family evaluation (see 2.3 above)—cross-model re-runs show verdict is family-specific, and the paper cannot claim cross-family robustness. (2) Portability beyond VDBMSs is claimed on structural grounds only (Section 3.5, CouchDB/Elasticsearch probe) and is not empirically tested; even one non-VDBMS case study would strengthen the claim. (3) The 107-submission yield is tool-design-biased and not a population estimate; full-space estimation is future work. (4) Result correctness (ANN recall, ranking) is explicitly out of scope. These threats are acknowledged in Section 4, but they bound the generalizability of the results.

#### 4. Verifiability — Weak (Borderline Adequate)

- **4.1** The paper provides substantial artifact links: GitHub repository (https://github.com/yihui504/testvdb-anon) with 22 agent role prompts (`agents/`), 48-candidate ground truth (`test_questions/`), reproduction driver (`reproduction/full52/`), per-target LLM-call accounting, and target versions (Milvus 2.6.19, Qdrant v1.18.2, Weaviate v1.38.2). The artifact description suggests the prompts are complete enough to reproduce the pipeline, and the per-call accounting (Table 3: ~10⁴ calls, ~$10 per target) provides cost transparency. The paper does not claim to provide the full VDBMS instances or Docker environments (standard for this community), but the pinned versions and reproduction scripts appear sufficient.

- **4.2 [major, fixable]** **Key procedural detail is partially missing.** The paper does not fully specify the **dev-reviewer's source-grounding procedure**—how it greps the clone, which constants it traces, what call chains it follows. Section 2.5 describes the three checks at a high level ("rebuild a minimal request," "cross-check through an independent channel," "read source to check whether violation is intentional"), but the specific heuristics for interpreting source (e.g., what patterns indicate "intentional default" vs. "missing validation") are not detailed enough to reproduce the 75% false-positive suppression. Appendix A excerpts prompts for contract-formalizer and dev-reviewer, but the source-grounding logic appears to be in the agent implementation rather than fully captured in prompts. Without full pseudocode or implementation details, a reader cannot independently verify how source grounding achieves the reported precision/recall gains.

- **4.3 [minor, fixable]** The paper reports Wilson 95% CIs for precision/recall (Table 3: 67% [49, 81], 74% [55, 87]) but does not specify the binomial proportion CI method (Wilson score interval is implied but not stated). The bootstrap resampling validation (precision 95% CI [53%, 83%], recall [71%, 96%]) is described but the resampling procedure (2000 resamples, stratified or not) is not fully specified. These are minor statistical reporting issues that should be clarified for reproducibility.

- **4.4 [minor, fixable]** The 3-run any-confirmed ensemble is a **post-hoc operating point** selected after observing four options (single run, 3-run union, 5-run union, 5-run majority). The paper justifies this selection with falsifier semantics (under-confirmation is costlier than forwarding a false positive for human triage) and provides held-out cross-validation support, but the Wilson CIs do not account for this selection. The Bonferroni correction widens CIs but is a conservative bound; the paper should flag the selection issue explicitly rather than presenting CIs as if the operating point were pre-registered.

#### 5. Presentation — Adequate

- **5.1** The paper is well-structured and generally readable. The abstract clearly frames the problem, approach, and results. Section 2 (Preliminaries) provides good background on VDBMSs and documentation-implementation consistency. Section 3 (Approach) is clearly organized with subsections for each pipeline stage and good figures (Figure 1: pipeline overview, Figure 2: dev-reviewer three-check falsification). The four-paragraph contribution list is precise.

- **5.2 [minor, fixable]** **Language and notation issues are minor but present.** Some sentences are overly dense and should be split for clarity (e.g., the second sentence of the abstract packs multiple claims). Table 1 (Oracle candidates) is valuable but uses inconsistent capitalization ("AGORA+" vs "LLM-derived oracle (TestVDB)"). Figure 2 (dev-reviewer three-check falsification) is clear but the TikZ code could be simplified.

- **5.3 [minor, fixable]** The Related Work section (Section 5) is comprehensive but could be more systematic in positioning TestVDB against the four categories it covers (VDBMS testing, REST-API oracle generation, LLM-as-judge reliability, Documentation-derived oracles). Each category gets one paragraph, but the paper's delta could be more explicit (e.g., a comparison table against AugmenTest, AGORA+, SATORI on oracle target, anchoring mechanism, and limitation).

## Reviewer 3: General Reviewer

**Overall Recommendation:** Weak Accept

### Summary

TestVDB addresses documentation-implementation defects in Vector Database Management Systems (VDBMSs), where a system silently accepts inputs that violate its API documentation. The authors argue that because documented boundaries are natural-language prose, deterministic oracles (crash detection, differential testing, metamorphic relations, property-based testing) cannot adjudicate these accept/reject decisions, leaving an LLM as the practical oracle. Their approach extracts behavioral claims from documentation, generates test probes, executes them against sandboxed VDBMSs, and confirms defects. To address false positives from LLM hallucination and self-preference bias, they introduce a dev-reviewer agent that falsifies candidates against implementation source. The paper reports 107 submitted issues across three VDBMSs with 50 maintainer-acknowledged true-positive defects (15 merged-PR-fixed), a controlled retrospective showing source grounding lifts recall from 37% to 74%, and a bidirectional probe against VDBFuzz exploring complementary coverage.

### Core Strengths

- **S1:** The problem of documentation-implementation defects is real and under-explored — the paper persuasively argues that most VDBMS bugs are logical (not crash) bugs and that current fuzzers are structurally blind to this defect class. — see 1.1
- **S2:** The dev-reviewer's source-grounded falsification is a principled mitigation of LLM reliability problems, and the 3-run ensemble (67% precision, 74% recall) represents useful operational performance. — see 3.1, 3.3
- **S3:** The evaluation against three production VDBMSs with maintainer adjudication (50 acknowledged defects) provides credible evidence of practical impact, and the 15 merged-PR fixes demonstrate real-world utility. — see 3.1, 3.2

### Core Weaknesses

- **W1:** The oracle exclusion argument (Table 1) is not fully convincing — it asserts that REST-API oracle tools (AGORA+, SATORI, MASTOR) cannot reach input-acceptance decisions on system-level prose, but this claim needs stronger evidence than the text provides. — see 1.2
- **W2:** Cross-family generalization remains open — the controlled retrospective on DeepSeek, Qwen-3.8-Max, and LongCat-2.0 shows the verdict is family-specific (Cohen's κ in slight-to-fair band), and the cross-family voting mitigation (81% recall at 73% precision) still depends on which families are available. — see 3.4
- **W3:** External validity is limited — the 48-candidate retrospective is non-random and may over-represent cases where source grounding is decisive, and the paper does not estimate recall because no public ground-truth defect catalog exists. — see 3.5

### Detailed Assessment

1. **Significance** — Adequate
   - **1.1** [strength] The paper targets a genuine gap in VDBMS testing: logical bugs that produce no crash (more than half of VDBMS defects per the cited empirical study) and escape crash-oracle fuzzers like VDBFuzz. The concrete example of Milvus issue #49823 (silently accepting nprobe=0 despite documentation declaring range [1, 16384]) makes the problem tangible. The yield (107 issues submitted, 50 acknowledged true positives, 15 merged-PR fixes) across three production systems (Milvus, Qdrant, Weaviate) demonstrates practical impact and provides evidence that the defect class is prevalent and worth addressing.
   - **1.2 [major, fixable]** The oracle exclusion argument (Table 1) is not fully convincing. The paper asserts that REST-API oracle tools (AGORA+, SATORI, MASTOR) "target response-field/runtime properties under per-field structural anchoring (OpenAPI fields, traces, or source), not input-acceptance decisions on system-level prose," but this claim needs stronger evidential support. The Related Work section (Section 5) acknowledges that SATORI "uses an LLM to infer response-field oracles from OpenAPI field names, types, and natural-language descriptions" but does not explain why SATORI's LLM cannot also read system-level prose. The exclusion would be more convincing with a concrete control demonstrating that these tools, run on the same VDBMS endpoints, fail to reach the defects TestVDB finds, or with a clearer argument about the structural difference between per-field anchoring and system-level prose. As stated, the argument risks reading as assertion rather than demonstrated boundary.

2. **Novelty** — Adequate
   - **2.1** [strength] The use of source-grounded falsification to mitigate LLM reliability problems is novel in the test-oracle context. The paper correctly identifies two failure modes (hallucination in extraction, self-preference in judgment) and shows that multi-perspective judging (four specialized judge agents with voting) is insufficient because all judges read the same ambiguous documentation. The dev-reviewer's three-check falsification (independently reproducible, evidence sufficient, falsifiable) is a principled approach that breaks self-preference by grounding the verdict in the implementation rather than the same LLM family's prior claim.
   - **2.2** [strength] The four-stage pipeline (claim extraction, test generation, sandboxed execution, defect confirmation) is a clear instantiation of documentation-implementation consistency testing. While prior work (Toradocu, Doc2OracLL, AugmenTest) derives oracles from documentation, TestVDB's use of source as a falsifier rather than treating the LLM as the final arbiter is a distinct direction. The Related Work section (Section 5) positions this clearly against the line that keeps the LLM as the final semantic arbiter.
   - **2.3 [major, unfixable]** Cross-family generalization remains open. The full independent cross-model re-run on all 48 candidates (DeepSeek, Qwen-3.8-Max, LongCat-2.0) shows the verdict is family-specific (Cohen's κ vs. GLM's 3-run union: 0.32 DeepSeek, 0.20 LongCat, 0.18 Qwen, all in slight-to-fair band). The gap is vendor-specific (DeepSeek reaches 75% recall on Milvus but collapses to 0% on Qdrant). Cross-family voting reaches 81% recall at 73% precision (GLM ∪ DeepSeek), but this mitigation depends on which families are available and whether they are complementary. The paper acknowledges that "cross-family generalization remains open," and this limitation inheres in the LLM-as-judge approach — it is not clear whether the source-grounded falsification strategy can be generalized beyond the specific backbone (GLM-5.2) that was tuned for this task.

3. **Soundness** — Adequate
   - **3.1** [strength] The evaluation methodology is sound overall. Ground truth comes from maintainer adjudication (107 issues submitted, 50 acknowledged true positives), and the controlled retrospective (48 candidates, 27 true-positive and 21 by-design or rejected) provides a reasonable basis for measuring precision/recall. The use of Wilson 95% confidence intervals appropriately quantifies uncertainty. The 3-run any-confirmed ensemble is justified as the operating point because the dev-reviewer is a falsifier, so a candidate that survives any independent falsification is more likely a true defect. The held-out cross-validation (200 random 50/50 splits) confirms that the 3-run selection is not an overfit.
   - **3.2** [strength] The ablation study on a 12-FP/4-TP Milvus control isolates the dev-reviewer's contribution convincingly. Source alone suppresses 9/12 false positives (75%), the threat-model anchor alone suppresses 6/12 (50%), and their union suppresses 11/12 (91%), each retaining all 4 true positives. This directly measures the self-preference reduction: the same-family judge agent over-confirms its own extracted claims, and the source anchor breaks that over-confirmation. The companion control (disabling Step 3.5 source grounding) shows recall drops from 74% to 19%, confirming that source grounding is the dominant contributor.
   - **3.3 [minor, fixable]** The bidirectional probe against VDBFuzz (RQ3) is well-designed but the presentation could be clearer. The systematic direction (VDBFuzz on Qdrant v1.18.2, 26,000 requests, 0 of 14 silent-accept true positives reached) is the generalizable one and cleanly separates the two oracles' reach. The two controlled cases on older versions (v1.4.0, v1.18.0) are n=1 each and isolate the mechanism on crash-class defects, but the paper does not explicitly mark them as n=1 controls or explain why they are sufficient to establish complementarity. A clearer statement that these are existence proofs ("VDBFuzz can reach this crash-class defect via contract reasoning") rather than quantitative coverage claims would strengthen the presentation.
   - **3.4 [major, unfixable]** External validity is limited in two ways. First, the 48-candidate retrospective is maintainer-adjudicated but non-random and "may over-represent cases where source grounding is decisive," which bounds the precision/recall estimates. The paper acknowledges this and flags it as a post-hoc, exploratory operating point, but the limitation remains — we do not know how the dev-reviewer would perform on an unbiased defect sample. Second, the paper does not estimate recall because "no public ground-truth defect catalog for VDBMSs exists." This is a fundamental validity threat: without an estimate of the false-negative rate, we cannot assess whether TestVDB is finding most documentation-implementation defects or only a specific subset. The 107-submission yield is biased by the tool's design toward documentation-implementation defects, so the observed proportion is not an estimate of the distribution in VDBMSs at large. A capture-recapture or unbiased defect-sample estimation is noted as future work but is not attempted.
   - **3.5 [minor, fixable]** The construct validity assumption (implementation-as-correct) bounds the approach but is well-acknowledged. The paper states that "an implementation bug can wrongly falsify a clause whose documentation is right" and notes that 31 of the 50 true positives have merged or open fix-PRs (implementation confirmed buggy by maintainers). No false positive was traced to an implementation bug, which supports the assumption. However, the paper does not quantify the false-negative rate where the documentation itself is wrong — such cases would surface as false negatives of the dev-reviewer. The paper notes that this would require a ground-truth catalog of documentation errors that does not exist, which is a reasonable limitation, but the impact on recall remains unquantified.

4. **Verifiability** — Excellent
   - **4.1** [strength] The paper provides exceptional verifiability. All agents run on a single LLM backbone (GLM-5.2) with default sampling, and the paper provides the approximate per-target LLM-call distribution (Table 2: ~50% dev-reviewer source-grounding, ~25% claim extraction + test generation, ~25% judging + novelty gate). The artifact (https://github.com/yihui504/testvdb-anon) is declared and contains the full prompts (22 agent role definitions under agents/), target versions (Milvus 2.6.19, Qdrant v1.18.2, Weaviate v1.38.2), per-token accounting, the 48-candidate ground truth (test_questions/), and a reproduction driver (reproduction/full52/). The VDBMS versions are pinned via Docker, and the dev-reviewer clones each target's source at the pinned version. A reviewer could fully follow and check the work from the text and artifact.
   - **4.2** [strength] The paper provides sufficient detail to understand the multi-agent implementation. Section 3.6 describes the five stage-aligned roles (contract-formalizer, four attack agents, judge-agent quartet, dev-reviewer, reporter) and notes that wall-clock per target is on the order of $10^4$ LLM calls and roughly $10 at current API pricing. The dominant cost is dev-reviewer source-grounding and live Docker re-probes rather than raw LLM latency. The appendix excerpts the role prompts for the two agents that most affect the pipeline's output (contract-formalizer, dev-reviewer), and the full 22 agent definitions are in the artifact. This level of detail exceeds the typical standard for verifiability.

5. **Presentation** — Adequate
   - **5.1** [strength] The paper is well-structured and readable. The four-stage pipeline overview (Section 3) is clear, and the dev-reviewer's three-check falsification (Figure 2) provides a helpful visual summary. The example paths (#49823, #9255) make the approach concrete. The Related Work section (Section 5) positions TestVDB clearly against prior work on VDBMS testing, REST-API oracle generation, LLM-as-judge reliability, and documentation-derived oracles.
   - **5.2 [minor, fixable]** The figures are generally helpful but Figure 1 (pipeline) could be clearer about which stages are LLM-driven. The caption states "Dashed boxes are LLM-driven; solid boxes (sandboxed execution, dev-reviewer) are not," but the figure itself does not use dashed boxes to make this distinction visually. A reader must rely on the caption to understand which stages are automated by LLMs. Using dashed borders or a different fill pattern would improve the figure's self-contained clarity.
   - **5.3 [minor, fixable]** The per-vendor breakdown in RQ1 (Milvus 22 TP of 51 submitted, Qdrant 14 of 26, Weaviate 14 of 30) is useful context, but the paper does not explain why the yield precision varies by vendor (Milvus 43%, Qdrant 54%, Weaviate 47%). The text states that "the vendor distribution reflects documentation style" — Milvus concentrates defects in optional-default parameters (nprobe, ef, level), Qdrant in search parameters (timeout, score_threshold) and state operations (wait=false), Weaviate in idempotent behaviors (delete nonexistent class). This is helpful but could be expanded with a brief explanation of why these patterns lead to higher or lower yield precision.
   - **5.4 [minor, fixable]** There are minor language issues. Table 1 uses "textbf" formatting for the final row but does not escape the backslash in LaTeX source (should be \\textbf). The abstract uses "emph" twice in sentence 2 ("We target \emph{documentation-implementation defects}") and "\texttt" for nprobe=0, which is inconsistent with the rest of the paper. The abstract also contains a complex sentence structure that could be simplified: "Two failure modes produce false positives: hallucination in claim extraction and self-preference bias in judgment." These are minor blemishes that do not obstruct evaluation but should be polished for publication.

### Questions for Authors

- **Q1:** Can you provide a more detailed argument for why REST-API oracle tools (AGORA+, SATORI, MASTOR) cannot reach input-acceptance decisions on system-level prose, ideally with a concrete control showing these tools fail to reach the defects TestVDB finds? — This would strengthen the oracle exclusion argument in Table 1 and address concern 1.2.
- **Q2:** Given that the cross-model re-run shows the verdict is family-specific (Cohen's κ in slight-to-fair band), what theoretical or empirical principles might guide the selection of complementary families for cross-family voting? — This would address concern 2.3 about cross-family generalization.

- **Q4:** Figure 1 states that dashed boxes are LLM-driven, but the figure itself does not use dashed boxes. Can this be made visually self-consistent? — This would address presentation concern 5.2.
