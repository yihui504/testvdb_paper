## Reviewer 1: Domain Expert

**Overall Recommendation:** Weak Accept

### Summary

TestVDB targets documentation-implementation defects in Vector Database Management Systems (VDBMSs), where a system silently accepts inputs that violate its natural-language API documentation (e.g., Milvus accepting `nprobe=0` when the documentation declares the range `[1, 16384]`). Because the boundary is prose rather than a structured schema, classical deterministic oracles (crash detection, differential testing, metamorphic relations, property-based testing) cannot adjudicate these accept/reject decisions. The authors argue that an LLM is the practical oracle for this residual, introduce a four-stage pipeline (claim extraction, test generation, sandboxed execution, defect confirmation), and diagnose two false-positive failure modes: hallucination in extraction and self-preference bias in judgment. A multi-perspective judging baseline raises precision but collapses recall, so the authors introduce a dev-reviewer agent that acts as a source-grounded falsifier, reproducing each candidate against live VDBMS instances and cross-checking against implementation source. On 107 submitted issues across three VDBMSs (Milvus, Qdrant, Weaviate), maintainers acknowledged 50 as true-positive defects (69% adjudicated yield; 15 fixed via merged PR). On a 48-candidate retrospective, the dev-reviewer reaches 67% precision and 74% recall (3-run any-confirmed ensemble) against a 37% recall baseline without source grounding. A bidirectional probe against VDBFuzz shows complementary coverage: TestVDB reaches a crash-class defect by contract reasoning, while VDBFuzz misses TestVDB's silent-accept defects under its crash-only templates.

### Core Strengths

- **S1:** The oracle-exclusion argument (Table 1) cleanly separates the documentation-implementation residual from classical deterministic oracles, establishing why an LLM is the practical oracle for natural-language API boundaries — see 1.1.
- **S2:** The dev-reviewer's source-grounded falsification is a well-motivated mitigation for LLM-as-judge reliability problems (hallucination, self-preference, self-inconsistency) that breaks the circular dependency between extractor and judge — see 2.1.
- **S3:** Real-world validation with 50 maintainer-acknowledged true-positive defects (15 merged-PR fixes) across three production VDBMSs demonstrates practical impact — see 3.1.
- **S4:** The bidirectional VDBFuzz probe (Section 4.3) empirically validates the complementarity claim: crash oracles and documentation-implementation oracles reach disjoint defect classes — see 3.2.

### Core Weaknesses

- **W1:** Cross-family generalization is open and not claimed, but the paper's headline results (67% precision / 74% recall) are family-specific to GLM-5.2; DeepSeek/Qwen/LongCat recall collapses to 56%/22%/19%, and vendor-specific gaps (Qdrant κ 0.32/0.20/0.18) suggest backbone-dependence that limits portability — see 2.2.
- **W2:** Construct validity concerns around the implementation-as-correct assumption (Section 4.2, para 3): an implementation bug can wrongly falsify a correct documentation clause, and the paper does not quantify this false-negative rate — see 2.3.
- **W3:** Threats to validity (Section 4.2) disclose post-hoc operating-point selection (3-run union chosen from four operating points after observing the retrospective) but the Wilson CIs in Table 3 do not account for this selection; a Bonferroni correction widens CIs to [44%,84%] (precision) and [51%,89%] (recall), which overlaps the single-LLM baseline — see 4.1.

### Detailed Assessment

#### 1. Significance — Adequate

- **1.1** The problem is real and motivated. The empirical bug study (citation ~\cite{bugstudy25}) establishes that >50% of VDBMS bugs manifest as functional failures rather than crashes, and the roadmap (citation ~\cite{roadmap25}) identifies oracle definition as a key challenge. TestVDB targets the silent-accept subset, where wrong results propagate into retrieval-augmented LLM applications without error signals. The oracle-exclusion table (Table 1) cleanly separates this residual from classical deterministic oracles, establishing that an LLM is the **practical** (not **only**) oracle for natural-language boundaries. The framing is sound: the problem is worth solving, and the residual after excluding deterministic oracles is genuinely unaddressed by existing tools.

- **1.2 [minor, fixable]** Scope is narrower than the title suggests. The title claims "doc-implementation defects in VDBMSs," but the evaluation is VDBMS-only. The Discussion (Section 6) claims transferability to "structurally similar documentation regimes" (REST APIs without OpenAPI, configuration validation, policy-as-code) and reports preliminary ports to Apache CouchDB (3 gaps reproduced) and Elasticsearch (rejected all invalid probes with 400). However, these are **existence proofs**, not systematic evaluation. Significance for the broader regime is claimed but not empirically tested. A stronger claim would require at least one non-VDBMS case study with full pipeline execution and maintainer adjudication. The current scope supports VDBMS-specific significance; broader claims are preliminary.

#### 2. Novelty — Adequate

- **2.1** Novelty over REST-API oracle tools (SATORI, MASTOR, AGORA+) is clear and verified against cached summaries. SATORI (ASE 2025) generates response-field oracles from OpenAPI field names/descriptions; its oracle catalog (format, length, enum, range of response fields) is anchored on per-field OpenAPI properties, and **input-acceptance decisions are outside its oracle target** (verified from SATORI Introduction, para 2). MASTOR (J. ACM 2026) reads source to generate oracles that encode **implemented behavior**; it tests what the implementation does and cannot detect documentation-implementation gaps (verified from MASTOR summary, Novely vs. TestVDB paragraph). AGORA+ depends on observed traffic and cannot reach unexercised inputs. TestVDB's delta is genuine: it reads documentation to extract claims (like Toradocu/Doc2OracLL/ChatAssert) but **falsifies against implementation source** (unlike prior LLM-as-judge oracles that treat the LLM as the final arbiter). The source-grounded falsifier is the novel contribution that breaks self-preference and hallucination modes.

- **2.2 [major, fixable]** Cross-family generalization is open and not claimed, but the headline precision/recall numbers are family-specific to GLM-5.2. Section 4.2 (para 3) reports an independent cross-model re-run on all 48 candidates (DeepSeek, Qwen-3.8-Max, LongCat-2.0, each running the complete SOP with live probes and source exploration, three runs per family). Results show family-specific verdicts: Cohen's κ vs. GLM's 3-run union is 0.32 (DeepSeek), 0.20 (LongCat), 0.18 (Qwen)—all in the slight-to-fair band. Combined recall is 56%/22%/19% vs. GLM's 74%. The gap is vendor-specific: DeepSeek reaches 75% recall on Milvus (approaching GLM's 95%) but collapses on Qdrant (0% vs. GLM's 29%). All families stay ≤14% recall on Qdrant. This suggests source-grounded falsification is **backbone-dependent** and the dependence concentrates on Qdrant (possibly because Qdrant's HTTP responses directly expose accept/reject decisions that the contract encodes, while Milvus parameter validation lives deeper in the source). The authors flag cross-family generalization as an open question (not a claimed result), which is proper, but the headline 67%/74% numbers are GLM-specific and may not transfer. Cross-family voting (GLM ∪ DeepSeek) reaches 81% recall at 73% precision (κ = 0.39, complementary), suggesting voting is a viable mitigation direction. For a revision, the authors should: (1) clarify the headline numbers are GLM-5.2-specific in the abstract; (2) expand the cross-family discussion to include the vendor-specific pattern (Milvus vs. Qdrant); (3) mention cross-family voting as an empirical mitigation direction, not just an open question. The current disclosure is adequate but could be stronger.

- **2.3 [minor, fixable]** Novelty over documentation-derived oracles (Toradocu, Doc2OracLL, AugmenTest, ChatAssert, Testora) is stated but not empirically compared. The Related Work (Section 5, para 4) characterizes these tools as treating "the LLM as the final semantic arbiter, verifying through runtime behavior" while TestVDB "falsifies against implementation source." This is a conceptual delta, but no empirical comparison is provided (e.g., running Toradocu or AugmenTest on the VDBMS documentation to compare yield/precision). Given the VDBMS-specific regime (system-level prose rather than Javadoc), a direct empirical comparison may be infeasible, but the paper would be stronger with at least a **qualitative** comparison on a shared example (e.g., show how Toradocu would handle the Milvus `nprobe` case versus TestVDB's source-grounded falsification). The current conceptual positioning is sound but would benefit from a concrete illustration.

#### 3. Soundness — Adequate

- **3.1** RQ1 (detection capability) is convincingly answered with real-world impact. 107 submitted issues, 50 maintainer-acknowledged true-positive defects (69% adjudicated yield; Wilson 95% CI [58.0%, 78.9%]). 15 fixed via merged PR, 16 with open fix-PRs, 19 acknowledged but unfixed. Vendor distribution (Milvus 22/51, Qdrant 14/26, Weaviate 14/30) reflects documentation style: Milvus defects concentrate in optional-default parameters (`nprobe`, `ef`, `level`) where documentation omits explicit bounds; Qdrant in search parameters (`timeout`, `score_threshold`) and state operations (`wait=false`); Weaviate in idempotent behaviors (delete nonexistent class). This pattern aligns with the failure-mode analysis in Section 3 (ambiguous defaults invite over-formalization; explicit error conditions are uniformly over-formalized), showing internal consistency. The yield is biased toward documentation-implementation defects by design (Section 6), not a population estimate—this is proper limitation disclosure. The 15 merged-PR fixes across three production VDBMSs establish practical impact.

- **3.2** RQ3 (comparison with VDBFuzz) provides strong empirical evidence for complementary coverage. The systematic direction (VDBFuzz on Qdrant v1.18.2, TestVDB's pinned version) ran 26,000 mutated requests and reached 0 of TestVDB's 14 Qdrant true positives—all are silent accepts (HTTP 200) that a crash oracle cannot detect by construction. The controlled cases (Qdrant v1.4.0 where VDBFuzz's integer-overflow crash on `size=2^63` is live; Qdrant v1.18.0 where TestVDB's #9045 `wait=false` zero-length vector defect is live) isolate the mechanism on crash-class defects. TestVDB reaches VDBFuzz's crash by contract reasoning (OpenAPI declares `size≥1` with no maximum, implementation panics); VDBFuzz misses TestVDB's silent-accept defect under its current templates (every `points-upsert` template uses `wait=true`, the correct path, and does not probe `wait=false`). The #9045 root cause (vector validation under `debug_assert` skipped by release builds, so `wait=false` accepts while `wait=true` rejects) illustrates why crash-focused patching misses silent-accept residuals. The bidirectional probe is well-designed: the systematic direction (26k requests, 0/14 reached) is the generalizable claim; the controlled cases are n=1 mechanism isolations. This is a strong evaluation.

- **3.3 [major, fixable]** Construct validity around the implementation-as-correct assumption (Section 6, para 2) needs clearer quantification. The authors state: "the implementation-as-correct assumption bounds the approach: an implementation bug can wrongly falsify a clause whose documentation is right." They provide partial mitigation: 31 of the 50 true positives have merged or open fix-PRs (implementation confirmed buggy by maintainers), and no false positive was traced to an implementation bug (all FPs are maintainer-adjudicated by-design). However, the paper does not quantify the **false-negative rate** from this assumption—how many documentation-correct/implementation-bug cases were suppressed as false positives? The authors state "we did not observe maintainer-rejected confirmed TPs where the documentation itself was wrong" and that such cases "would surface as false negatives of the dev-reviewer," but they "did not quantify this false-negative rate, which would require a ground-truth catalog of documentation errors that does not exist for VDBMSs." This is an inherent limitation (no ground truth), but the paper would be stronger with at least a **sensitivity analysis** on the 48-candidate retrospective: how many confirmed candidates would be flipped to suppressed if we assumed X% of the "by-design" adjudications were actually implementation bugs? Or, manually inspect the 22 by-design cases and report how many show evidence of implementation bugs vs. documentation ambiguity. The current disclosure acknowledges the limitation but does not bound its impact. For a revision, the authors should: (1) report a manual inspection of the 22 by-design cases for implementation-bug evidence; (2) provide a sensitivity analysis on the retrospective assuming different false-negative rates; (3) clarify the limitation in the abstract (currently unstated).

- **3.4 [minor, fixable]** Statistical rigor is adequate but could be more transparent. The authors use Wilson 95% CIs for yield precision (69.4% [58.0%, 78.9%]) and dev-reviewer precision/recall (67% [49%, 81%] / 74% [55%, 87%]). They report Bonferroni correction across the four operating points in Table 3 (widens 3-run CIs to roughly [44%,84%]/[51%,89%]) and bootstrap resampling validation (2000 resamples: precision [53%,83%]/recall [71%,96%]). A held-out cross-validation (200 random 50/50 splits) confirms the 3-run selection is not overfit (3-run, when selected on 27% of splits, gives test 68%/71% matching headline). This is thorough. However, the **post-hoc selection** of the 3-run union as the headline (after observing the retrospective) is not fully accounted for in the main-text CIs. The Wilson CIs in Table 3 do not incorporate the selection effect; the Bonferroni-corrected CIs are mentioned in the prose but not in the table itself. For a revision, the authors should: (1) add the Bonferroni-corrected CIs to Table 3 as a secondary column or footnote; (2) clarify in the abstract that the 67%/74% headline is a post-hoc operating point; (3) report the bootstrap validation as the primary robustness check rather than a parenthetical. The current analysis meets standards but could be more transparent.

#### 4. Verifiability — Adequate

- **4.1** The artifact is declared and reachable (Section 4, para 4: https://github.com/yihui504/testvdb-anon). The paper reports the artifact contains: (1) 22 agent role prompts (under `agents/`), (2) target versions (Milvus 2.6.19, Qdrant v1.18.2, Weaviate v1.38.2), (3) per-token accounting, (4) the 48-candidate ground truth (`test_questions/`), and (5) a reproduction driver (`reproduction/full52/`). The authors specify all agents run on GLM-5.2 via the BigModel Anthropic-compatible API under default sampling (no decoding overrides; temperature and top-p at provider defaults). The appendix (Section A) excerpts the two most critical agent prompts (contract-formalizer, dev-reviewer) with role, input/output, and key instructions. However, the **cost reporting** is approximate: "roughly $10 per target at current API pricing" with a distribution table (Table 2: ~50% dev-reviewer source-grounding, ~25% claim extraction/generation, ~25% judging/novelty gate). No exact token counts or per-stage cost breakdown are provided. For a revision, the authors should add a precise cost accounting (e.g., total tokens per stage, cost per 1M tokens at the GLM-5.2 rate) to the artifact or an extended table. The current verifiability is adequate (artifact link + sufficient procedural detail) but not fully reproducible without cost specifics.

The paper follows a clear logical flow: Introduction (problem + oracle-exclusion argument) → Approach (four-stage pipeline) → False-Positive Problem (two failure modes + multi-perspective baseline) → Dev-Reviewer (source-grounded falsifier) → Evaluation (RQ1-3) → Related Work → Discussion/Limitations → Conclusion. ## Reviewer 2: Area Specialist

**Overall Recommendation:** Weak Accept

### Summary

This paper proposes TestVDB, a system for detecting documentation-implementation defects in Vector Database Management Systems (VDBMSs). The core problem is that VDBMSs often silently accept inputs that violate their API documentation (e.g., accepting `nprobe=0` when documentation specifies range `[1, 16384]`). These defects corrupt query semantics but produce no crash, rendering crash-oracle fuzzers like VDBFuzz ineffective. Because the boundary is specified in natural-language prose, the authors argue that deterministic oracles (differential testing, metamorphic relations, property-based testing) cannot adjudicate these accept/reject decisions, leaving LLMs as the practical oracle.

TestVDB instantiates a four-stage pipeline: (1) behavioral-claim extraction from documentation using an LLM, (2) test-script generation, (3) sandboxed execution against Docker-pinned VDBMS instances, and (4) defect confirmation via LLM adjudication. The authors identify two false-positive failure modes: hallucination in claim extraction and self-preference bias in judgment (the same LLM family tends to confirm its own claims). Multi-perspective judging (four specialized judge agents) raises precision to ~80% but collapses recall to ~15%. The key innovation is a **dev-reviewer agent** that acts as a source-grounded falsifier: it reproduces each candidate, cross-checks it against implementation source code, and attempts to disprove it. On 48 maintainer-adjudicated candidates, the dev-reviewer achieves 67% precision and 74% recall (3-run ensemble) versus 37% recall without source grounding.

Evaluation spans three VDBMSs (Milvus, Qdrant, Weaviate). TestVDB surfaced 107 candidate issues with 50 maintainer-acknowledged true positives (69% adjudicated yield; 15 fixed via merged PR). A bidirectional probe against VDBFuzz on Qdrant shows complementary coverage: VDBFuzz (26,000 requests) reached 0 of 14 silent-accept true positives on v1.18.2; TestVDB reached VDBFuzz's integer-overflow crash by contract reasoning on an older version, but VDBFuzz missed TestVDB's `wait=false` zero-length vector defect under current templates.

### Core Strengths

- **S1:** Clear articulation of the documentation-implementation defect class as a gap left by crash-oracle approaches — see 1.1, 2.1

- **S2:** Well-motivated dev-reviewer architecture that addresses both hallucination (by falsifying against source) and self-preference bias (by breaking same-family confirmation) — see 2.3, 3.2, 4.2

- **S3:** Rigorous exclusion argument (Table 1) that systematically walks through deterministic oracle candidates and explains why each misses the documentation-implementation residual — see 2.1

- **S4:** Honest evaluation design with controlled retrospective (48-candidate ground truth), ablation studies (source/threat-model anchor isolation), and cross-family backbone analysis — see 4.1, 4.2

- **S5:** Practical impact demonstrated through 50 maintainer-acknowledged defects across three production VDBMSs — see 4.1

### Core Weaknesses

- **W1:** Single-LLM-family evaluation (GLM-5.2 only) with cross-family κ values in "slight-to-fair" range (0.18–0.32), leaving the central claim of source-grounded falsification effectiveness unsubstantiated across model families — see 4.2 [major, fixable]

- **W2:** Post-hoc operating-point selection (3-run union from 4 candidates) with CIs that don't account for selection; Bonferroni correction widens CIs to [44%, 84%] (precision) and [51%, 89%] (recall), substantially weakening statistical support — see 4.2 [major, fixable]

- **W3:** RQ3 bidirectional probe uses n=1 controlled cases (v1.4.0, v1.18.0) for mechanism-level claims, while the systematic direction (v1.18.2, 26,000 requests) is the only generalizable result — see 4.3 [minor, fixable]

- **W4:** Limited external validation: evaluation is VDBMS-only, and the "transferability to non-VDBMS REST APIs without OpenAPI" claim (Section 6) is supported only by CouchDB/Elasticsearch ad-hoc probes without systematic evaluation — see 6 [minor, unfixable]

### Detailed Assessment

**1. Significance — Adequate**

- **1.1** The problem is well-motivated: VDBMS bug studies show >50% of defects are logical bugs producing no crash, and the VDBMS testing roadmap identifies oracle definition as a key challenge. The documentation-implementation subset (accept/reject violations on natural-language prose boundaries) is a credible and costly defect class. The 107 issues submitted and 50 maintainer-acknowledged TPs across three production VDBMSs (15 merged-PR fixes) demonstrate practical relevance.

- **1.2** The impact is bounded. The setting is specific to systems with natural-language API documentation (no structured schema). The approach doesn't transfer to closed-source VDBMSs (requires source access) or to result-correctness testing (ANN recall, ranking). The authors acknowledge these bounds (Section 6), which limits the scope but doesn't undermine the contribution within it.

**2. Novelty — Adequate**

- **2.1** The paper makes a convincing case that existing approaches miss the documentation-implementation residual. Table 1 (oracle exclusion argument) walks through crash oracles (VDBFuzz), differential testing, metamorphic relations, property-based testing, and REST-API tools (AGORA+, SATORI, MASTOR). Each is structurally unable to reach accept/reject decisions on natural-language prose: crash oracles detect crashes only; differential testing assumes cross-vendor agreement but accept/reject diverges by design; metamorphic relations test output correctness, not input acceptance; property-based testing requires machine-checkable properties and OpenAPI schemas; REST-API tools anchor on per-field structural sources and target response-field properties. The characterization is accurate based on cached summaries of SATORI and MASTOR, and the gap is real.

- **2.2** The core novelty is the **source-grounded falsifier design**. Prior LLM-as-judge work (Panickssery et al. 2024, Wataoka et al. 2025, Haldar et al. 2025) establishes self-preference and self-inconsistency biases but proposes multi-judge panels or calibration as mitigations. TestVDB's dev-reviewer breaks both failure modes by moving ground truth from the LLM to the implementation source: the falsifier greps the source clone, traces constants and call chains, and attempts to disprove each candidate. This architectural innovation is genuine and not present in prior work.

- **2.3 [minor, fixable]** The Related Work section could better position TestVDB against documentation-derived oracle lines that also use LLMs (Toradocu, AugmenTest, ChatAssert, Testora). The paper notes they "keep the LLM as the final arbiter by validating only through runtime behavior" while TestVDB "falsifies against implementation source." This is a meaningful distinction but could be more explicit in Table 1 rather than relegated to text.

**3. Soundness — Weak**

- **3.1** RQ1 (detection capability) is solid. 107 issues submitted, 72 adjudicated, 50 TPs acknowledged. The 69.4% precision (95% CI [58.0%, 78.9%]) on adjudicated cases and 15 merged-PR fixes show real defects. The yield is biased by the tool's design toward documentation-implementation defects (authors acknowledge this in Section 6), so the proportion isn't a population estimate—but that doesn't weaken the detection capability claim.

- **3.2** RQ2 (false-positive suppression) on the 48-candidate retrospective is well-designed. The dev-reviewer reaches 67% precision / 74% recall (3-run union) against a 56% / 37% single-LLM baseline. The ablation on a 12-FP/4-TP control (Table 3) isolates contributions: source alone suppresses 75% of FPs, source+threat-model 91%. The comparison with multi-perspective judging (80% precision, 15% recall) shows why source grounding is necessary. These controls are methodologically sound.

- **3.3 [major, fixable]** **Single-family evaluation limits claims.** All RQ2 results use GLM-5.2 only. The cross-family re-run (DeepSeek, Qwen-3.8-Max, LongCat-2.0) shows Cohen's κ vs. GLM's 3-run union at 0.32, 0.20, 0.18 respectively—all in the "slight-to-fair" band. Inter-run self-consistency is also mixed: DeepSeek/LongCat high (κ ~1.0 on Milvus), Qwen lower (κ = 0.65). The paper acknowledges "cross-family generalization is an open question" but doesn't substantiate the central source-grounding claim across families. Given that the dev-reviewer's core value is breaking self-preference (a family-specific bias per Panickssery/Wataoka), showing backbone dependence weakens the contribution's generalizability.

- **3.4 [major, fixable]** **Post-hoc operating-point selection weakens statistical support.** The paper reports four operating points (single-run, 3-run union, 5-run union, 5-run majority) and selects the 3-run union as the "post-hoc headline justified by falsifier semantics." The Wilson CIs in Table 2 don't account for this selection. The Bonferroni correction (α=0.05/4) widens the 3-run CIs to [44%, 84%] (precision) and [51%, 89%] (recall), which substantially overlap the single-LLM baseline (56% precision, 37% recall). A bootstrap validation (2000 resamples, 200 random 50/50 splits) supports non-artifact selection, but the headline numbers should be presented with corrected CIs or the selection should be pre-registered.

- **3.5** The three-condition ablation (Table 3) on a blind Milvus 12-FP/4-TP control is methodologically strong. Source alone (75% FP suppression) and source+threat-model (91%) show the falsifier's value. The threat-model anchor instability on state/concurrency FPs is acknowledged. This isolates the source-grounded contribution well.

- **3.6** The source-grounding isolation (disabling Step 3.5) is a strong control. Without source access, recall drops from 74% to 19%, precision from 67% to 56%. The vendor-specific effect (Milvus 80%→5%, Qdrant ~unchanged) explains *why* grounding matters: parameter validation logic lives in source for Milvus but is exposed in HTTP responses for Qdrant. This triangulates the contribution effectively.

- **3.7** RQ3 (bidirectional VDBFuzz probe) has mixed rigor. The systematic direction (VDBFuzz on v1.18.2, 26,000 requests, 0 of 14 TPs reached) is generalizable and structural: crash oracles cannot detect silent accepts by construction. The two controlled cases (v1.4.0, v1.18.0) are n=1 isolations of crash-class mechanisms, not generalizable claims. The paper correctly flags them as controlled, but the asymmetry in evidential weight should be clearer in the abstract/summary.

**4. Verifiability — Adequate**

- **4.1** The artifact is comprehensive and linked: https://github.com/yihui504/testvdb-anon (agents/, test_questions/ as 48-candidate ground truth, reproduction/full52/). The 22 agent role prompts (Appendix A) give the implementation detail needed to understand the pipeline. The target versions (Milvus 2.6.19, Qdrant v1.18.2, Weaviate v1.38.2) are specified.

- **4.2** The RQ2 methodology is fully reproducible from the text. The 48-candidate retrospective definition, the three-condition ablation, the source-grounding isolation, and the cross-family re-run protocols are all specified with sufficient detail. A reproduction driver exists in the artifact.

- **4.3** The cost analysis (Table 4: ~$10 per target, ~10^4 LLM calls, 50% dev-reviewer share) enables cost estimates for others to apply the approach.

## Reviewer 3: General Reviewer

**Overall Recommendation:** Weak Accept

### Summary
This paper introduces TestVDB, a system for detecting documentation-implementation defects in Vector Database Management Systems (VDBMSs)—cases where a VDBMS silently accepts inputs that violate its API documentation. The authors address a practical problem: existing VDBMS testing tools like VDBFuzz detect only crashes, but more than half of VDBMS bugs are logical failures that do not crash. TestVDB uses Large Language Models (LLMs) to extract behavioral claims from natural-language documentation, generate executable tests, run them against sandboxed VDBMS instances, and adjudicate defects. A key innovation is the dev-reviewer agent, which suppresses false positives by falsifying LLM-derived claims against implementation source code. The authors report 107 submitted issues across three VDBMSs (Milvus, Qdrant, Weaviate) with 50 maintainer-acknowledged true positives (15 fixed via merged PR), and demonstrate that source-grounded falsification improves recall from 37% to 74% on a 48-candidate retrospective. They also conduct a bidirectional comparison with VDBFuzz, showing complementary coverage: TestVDB reaches silent-accept defects that crash oracles miss, while VDBFuzz reaches some crash-class defects that TestVDB's contract-based reasoning also detects.

### Core Strengths
- **S1:** The paper addresses a real, costly problem with clear motivation — VDBMSs store embeddings for LLM applications, and their defects propagate silently through the stack without error signals. The bug study and roadmap citations establish this convincingly — see 1, 34.
- **S2:** The oracle-exclusion argument (Table 1) is well-structured and clearly situates the contribution relative to prior work. Each oracle candidate (crash, differential, metamorphic, property-based, REST-API-derived) gets a concrete explanation of why it misses the documentation-implementation residual — see 1, 61.
- **S3:** Source-grounded falsification is a sound countermeasure to two well-diagnosed false-positive modes (hallucination in extraction, self-preference in judgment). The three-check design (independently reproducible, evidence sufficient, falsifiable) is clearly motivated and operationalized — see 161-169, 197-202.
- **S4:** The evaluation includes both yield (107 submitted, 50 acknowledged) and controlled measurement (48-candidate retrospective). The ablation studies, per-run variance analysis, and cross-model generalization probe give a nuanced picture of the method's behavior — see 234-293.
- **S5:** The bidirectional VDBFuzz probe is concrete and persuasive. VDBFuzz reaching 0 of 14 silent-accept true positives on Qdrant v1.18.2 establishes structural complementarity — see 310.

### Core Weaknesses
- **W1:** Cross-family generalization is not empirically established. The cross-model re-run (DeepSeek, Qwen, LongCat) shows family-specific verdicts (κ = 0.32/0.20/0.18), with all three families collapsing on Qdrant (≤14% recall vs. GLM's 29%). The authors flag this as an open question but do not propose a mitigation direction beyond cross-family voting — see 292, 334.
- **W2:** The 48-candidate retrospective is maintainer-adjudicated but non-random, and the authors acknowledge they did not pre-register the candidate set. This limits the strength of the precision/recall claims — see 330, 334.
- **W3:** Result correctness (ANN recall, ranking) is explicitly out of scope, and the authors do not quantify how many of the 50 true positives affect search semantics versus metadata-only operations. The contribution is framed as "defects" without this distinction — see 58, 333.
- **W4:** The implementation-as-correct assumption bounds the approach but is not empirically stress-tested. The authors report no observed false negatives from this assumption but also did not quantify the false-negative rate — see 334, 355.
- **W5:** External validation beyond VDBMSs is preliminary. The CouchDB/Elasticsearch probe is a cursory portability test (3 gaps on CouchDB, 0 on Elasticsearch) and does not establish transferability — see 353.

### Detailed Assessment

#### 1. Significance — Adequate
- **1.1** The problem is well-motivated and practical. VDBMS defects are costly in an LLM stack, the empirical study shows most are logical bugs, and the roadmap identifies oracle definition as a key challenge — 34, 38. The 50 maintainer-acknowledged true positives and 15 merged-PR fixes demonstrate real impact — 213.
- **1.2** The impact is bounded by two factors. First, the method targets documentation-implementation defects only, not result correctness of vector search — 58. Second, the contribution is specific to VDBMSs in evaluation; transfer to other domains is claimed on structural grounds only — 353. The practical impact is meaningful but not a foundational shift.

#### 2. Novelty — Adequate
- **2.1** The paper clearly situates itself relative to prior work in VDBMS testing, REST-API oracle generation, LLM-as-judge reliability, and documentation-derived oracles — 339-349. The oracle-exclusion table (Table 1) cleanly demarcates the residual TestVDB addresses — 62-78.
- **2.2** The novelty is incremental but real. Documentation-derived oracles are not new (Toradocu, Doc2OracLLm, AugmenTest, ChatAssert, Testora), but prior work keeps the LLM as the final arbiter through runtime verification. TestVDB's source-grounded falsification is a clear delta — it uses implementation source as an independent falsifier rather than another documentation reader — 161-169, 197-202. The bidirectional VDBFuzz probe also shows structural complementarity that prior work did not establish — 310.
- **2.3 [major, fixable]** The novelty claim against REST-API oracle tools (AGORA+, SATORI, MASTOR) is under-specified. The paper argues these tools "target response-field or runtime properties under per-field structural anchoring" and "do not adjudicate input-acceptance decisions on system-level prose" — 342, 74-75. However, the boundary case is not empirically tested: we do not see SATORI or MASTOR run on the same VDBMS targets to demonstrate they miss the 50 true positives TestVDB finds. The exclusion is structurally argued but not experimentally verified.

#### 3. Soundness — Weak
- **3.1 [major, unfixable]** The main claim — 67% precision and 74% recall on the 48-candidate retrospective — is undermined by the non-random, non-pre-registered candidate set. The authors acknowledge this limitation ("we did not pre-register the candidate set; a capture-recapture or unbiased defect-sample estimation is future work") — 330, 334. This weakens the evidentiary basis for the headline numbers. The Wilson CIs and bootstrap validation mitigate but do not eliminate this concern — 234, 292.
- **3.2 [major, unfixable]** Cross-family generalization is not established. The independent re-run with DeepSeek, Qwen, and LongCat shows family-specific verdicts (κ = 0.32/0.20/0.18), and all three families collapse on Qdrant (≤14% recall vs. GLM's 29%) — 292, 334. The authors flag this as an "open question" and do not propose a mitigation beyond cross-family voting, which reaches 81% recall at 73% precision but is not integrated into the main method. The core dev-reviewer approach is demonstrated on a single backbone (GLM-5.2) and does not generalize automatically.
- **3.3 [major, fixable]** The implementation-as-correct assumption is a validity threat that is not empirically bounded. The authors report no observed false negatives from this assumption but also state "we did not quantify this false-negative rate" — 334. The 15 merged-PR fixes (implementation confirmed buggy by maintainers) support the assumption's utility, but without a systematic estimate of its failure rate, the bounds on the approach are unclear. A sensitivity analysis or conservative estimate would strengthen this.
- **3.4 [minor, fixable]** The 107-submission yield is described but not contextualized as a population estimate. The authors acknowledge the bias ("our yield is biased by the tool's design toward documentation-implementation defects, so the proportion we observe is not an estimate of the distribution in VDBMSs at large") — 357. This is appropriate, but the paper does not even attempt a capture-recapture or other estimation method, which would contextualize the 50/107 yield.
- **3.5** The bidirectional VDBFuzz probe is well-designed and convincing. VDBFuzz reaching 0 of 14 silent-accept TPs on Qdrant v1.18.2 establishes structural complementarity — 310. The two controlled cases (v1.4.0 crash-class defect, v1.18.0 silent-accept defect) are n=1 each but isolate the mechanism concretely — 310-327.

#### 4. Verifiability — Adequate
- **4.1** The paper provides an artifact link (https://github.com/yihui504/testvdb-anon) with prompts, ground truth, and reproduction drivers — 125. The Appendix excerpts the two most critical agent prompts (contract-formalizer, dev-reviewer) — 373-377. This is sufficient to follow the main pipeline steps and adjudication logic.
- **4.2** Some procedural detail is missing. The paper does not fully specify the novelty gate algorithm (Step 5 of the pipeline), the exact encoding of the "three checks" in the dev-reviewer's decision procedure, or the 12-FP/4-TP control selection criteria for the ablation study — 161-169, 273-290. These details would aid replication but are not critical to understanding the core contribution.
- **4.3 [minor, fixable]** The artifact URL is declared but not verified as reachable in the paper text. A brief statement confirming repository contents (e.g., "the artifact contains agents/, test_questions/, and reproduction/full52/") would strengthen the verifiability claim — 125.
- **4.4 [minor, fixable]** The paper does not specify the GLM-5.2 model version beyond the backbone name. A model identifier (e.g., "GLM-5.2-turbo" or a checkpoint hash) would aid exact replication — 125.

#### 5. Presentation — Adequate
- **5.1** The structure is logical and the writing is generally clear. The problem setup, oracle-exclusion argument, approach, and evaluation sections flow well. The figures (pipeline diagram, dev-reviewer three-check diagram, per-run recall plot) are informative — 87-90, 171-194, 254-270.
- **5.2 [minor, fixable]** Some notation is inconsistent. The paper uses both "Wilson 95% CI" and "Wilson 95\% CI" — 213, 237. The LLaMA-based model "LongCat-2.0" is introduced without context on its provenance or relationship to other LLM families — 292.
- **5.3 [minor, fixable]** The Related Work section is dense but not integrated with the evaluation. The REST-API oracle tools (AGORA+, SATORI, MASTOR) are discussed as structurally out-of-scope but not empirically compared to TestVDB on the same targets — 342, 273. This weakens the novelty positioning.

Either a concrete non-VDBMS case study or a more guarded claim would improve the presentation.

A brief table or listing would aid navigation.
