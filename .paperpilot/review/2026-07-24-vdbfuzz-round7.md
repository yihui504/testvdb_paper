## Reviewer 1: Domain Expert

**Overall Recommendation:** Weak Accept

### Summary

This paper tackles the problem of detecting documentation-implementation defects in Vector Database Management Systems (VDBMSs) — cases where the API silently accepts inputs or behaviors that violate its natural-language API documentation. The authors argue that existing oracle families (crash, differential, metamorphic, property-based, and REST-spec-derived) cannot reach this defect class because the documented boundaries are natural-language prose rather than formal constraints, leaving an LLM as the practical oracle. They identify a two-layer reliability problem: family-specific self-preference (mitigated by cross-model validation) and task-intrinsic errors (where ambiguous documentation causes different LLM families to converge on the same wrong claim). The paper's methodological contribution is source-grounded falsification, which treats LLM-derived behavioral claims as refutable hypotheses and falsifies them against the implementation's source code. This is instantiated in TestVDB, a 20-agent pipeline. The evaluation spans five VDBMSs (Milvus, Qdrant, Weaviate, MeiliSearch, Chroma), surfacing 111 candidate issues (50 true-positive defects: 36 confirmed + 14 with open fix-PRs). A controlled retrospective on Milvus and Qdrant shows the source-grounded dev-reviewer reaches 67% precision and 74% recall (3-run any-confirmed ensemble) versus 37% recall without the source anchor. A task-intrinsic error probe on 18 over-strict clauses shows cross-model judging catches 8/18 but source-grounded falsification catches all 18.

### Core Strengths

- **S1:** The paper identifies and empirically separates a genuinely novel phenomenon (task-intrinsic documentation-interpretation errors) that prior documentation-oracle work has not addressed — see 1.1, 2.1.
- **S2:** The source-grounded falsification mechanism is a principled solution to the two-layer oracle reliability problem, with a clean experimental demonstration of efficacy (recall 37% without anchor → 74% with) — see 1.2, 3.2.
- **S3:** The evaluation is thorough and honest, including a reproducible ensemble design, per-run variance reporting, a bidrectional reachability probe against VDBFuzz, explicit threats to validity, and the frank admission that earlier single-run figures are "superseded" — see 4.1, 3.3.

### Core Weaknesses

- **W1:** The RQ2 any-confirmed ensemble rule is justified operationally ("the dev-reviewer is a falsifier") but the paper does not address the concern that union voting would inflate false positives if the per-run FP sets are disjoint — a majority-voting comparison would clarify this — see 3.1.
- **W2:** The RQ3 task-intrinsic analysis pools over-strict parameters (6/18 TI) with idempotency behaviors (11/11 TI) in the aggregate "pooled TI rate" (17/29), but the two subtypes have different root causes (documentation ambiguity vs. implicit idempotency), so the pooled figure is hard to interpret — see 2.2.
- **W3:** The single LLM family (GLM-5.2) as the backbone for all extraction, attack, and judging agents, with only a 20-candidate cross-model check, limits the generalizability of the pipeline beyond Chinese-hosted model families — see 3.4.

### Detailed Assessment

1. **Significance** — Adequate
   - **1.1** The problem is practically important: VDBMSs underpin retrieval-augmented LLM applications, and the paper's data (§RQ1, Table 1) show 50 true-positive defects across five systems, 36 confirmed by maintainers. The 85% residual (documentation-implementation defects beyond classical oracle reach) is a genuine gap the paper identifies and measures. This is useful and timely work.
   - **1.2** The impact is bounded in two ways the paper acknowledges. First, the approach requires source code access (§Limitations), excluding closed-source VDBMSs. Second, the approach treats the implementation as correct (§Limitations), meaning an implementation bug can wrongly falsify a correct clause. These are honest limitations, not flaws, but they narrow the contribution's scope. The paper does not attempt to estimate what fraction of real-world VDBMS defects are documentation-implementation (the 85% figure is the composition of TestVDB's findings, not an unbiased population estimate), which limits the significance claim to "these defects exist and here is a tool that finds them" rather than "this is a dominant defect class." **[minor, unfixable]**

2. **Novelty** — Adequate
   - **2.1** The identification and characterization of task-intrinsic documentation-interpretation errors (Section \ref{sec:regime}) is a genuine new finding. Prior documentation-oracle work (Toradocu~\cite{toradocu16}, Doc2OracLL~\cite{doc2oracll25}, ChatAssert~\cite{chatassert24}) treats the LLM as the final semantic arbiter and does not distinguish family-specific from task-intrinsic error modes. The 18-clause probe (Table \ref{tab:e2}) with cross-model judging failing on 3/6 task-intrinsic clauses while source-grounded falsification catches all 18 is a clean empirical demonstration of a previously-unreported phenomenon.
   - **2.2** Source-grounded falsification itself is incremental over MASTOR~\cite{mastor26}, as the paper acknowledges (§\ref{sec:regime}, §\ref{sec:related}). Both use source, but in opposite directions: MASTOR reads source to encode implemented behavior, TestVDB reads source to falsify documentation-derived claims. The delta is real and well-articulated, but it is an application-level twist rather than a fundamentally new oracle paradigm. The claim that prior REST-API oracle work (AGORA+~\cite{agoraplus25}, SATORI~\cite{satori25}) operates in a "low-ambiguity regime" (verified against the cached AGORA+ abstract, which describes deterministic invariant detection at 80% precision) is accurate. **[minor, fixable]**
   - **2.3** The "model-free invariant oracle subclass" (RQ4) is a useful engineering addition but is not novel — mathematical bound checking against known invariants is standard property-based testing practice. The paper correctly does not overclaim here.

3. **Soundness** — Adequate
   - **3.1 [major, fixable]** The RQ2 controlled retrospective uses a 3-run any-confirmed (union) ensemble to reach 67% precision and 74% recall (Milvus 69%/73%/80%, Qdrant 56%/50%/57%). The paper justifies union voting as appropriate because "the dev-reviewer is a falsifier, so a candidate that survives any independent falsification attempt is more likely a true defect." This operational argument is reasonable but incomplete. The paper reports that single-run recall ranges 15-78% across five runs (accuracy 44-65%, precision 50-73%), which is very wide variance. If the per-run false positive sets are disjoint, a union ensemble would inflate FPs. The paper reports that a 5-run ensemble reaches 85% recall at 62% precision — this is informative, but a comparison against majority voting (which would reach only 26% recall per the paper) is critical: it would show whether the any-confirmed rule is necessary (majority voting may under-recall due to the wide variance) or whether a precision-optimal rule exists between union and majority. Reporting only the union-based ensemble gives an incomplete picture of the operating characteristic.
   - **3.2** The cross-model check (DeepSeek re-running the dev-reviewer on 20 candidates, Cohen's $\kappa=1.0$) is well-designed and the result is strong evidence that source-grounded verdicts are not family-specific. The paper correctly flags that this does not estimate recall.
   - **3.3** The paper's handling of its own superseded data is a strength. The earlier single-run, single-vendor figures (81% false-positive suppression, 69.2% precision, 96.7% recall on a 16-candidate control) are explicitly reported as no longer recoverable and "superseded by this reproducible cross-vendor ensemble." This is honest scholarship.
   - **3.4 [minor, fixable]** The entire pipeline uses a single LLM family (GLM-5.2) as the backbone for extraction, attack, and judging agents, with only DeepSeek used for a subset of cross-model checks. The pipeline's architecture (20 agents with task-structured prompts) is described in Section \ref{sec:impl} but the prompts themselves are deferred to a "released at a persistent URL upon acceptance" artifact. This makes it impossible to assess prompt quality or reproduce results. The cost claim ("on the order of $10 per target") is reasonable but the dollar figure is stated without an error margin.

4. **Verifiability** — Adequate
   - **4.1** The per-issue classification of all 111 submissions into three fault models (classical-addressable, documentation-implementation, concurrency) is described as available in the artifact with a "one-line rationale." This is the right commitment, but the artifact is not yet released. The version matrix, prompts, and per-token accounting are similarly deferred. For a reproducibility study this is a weakness, but for a paper at this stage it is acceptable.
   - **4.2** The 48-candidate controlled retrospective, all five dev-reviewer runs, the corrected ground truth, and the stability analysis are declared as part of the artifact. If delivered, these would provide strong verifiability. The paper correctly references specific GitHub issues (#9045, #7967) that can be independently verified.
   - **4.3 [minor, fixable]** The paper does not state whether the 14 "open fix-PR" candidates have maintainer responses or are simply open PRs. Clarifying this would help readers assess the confirmation rate.

5. **Presentation** — Excellent
   - **5.1** The paper is well-structured and clearly written. The central conceptual contribution — the two-layer reliability problem and source-grounded falsification — is explained with good narrative flow from problem (§\ref{sec:regime}) to design (§\ref{sec:design}) to evaluation (§\ref{sec:eval}).
   - **5.2** Table \ref{tab:exclusion} (oracle candidates by defect class) and Table \ref{tab:e2} (over-strict clause probe) are effective visual summaries of complex comparative claims.
   - **5.3 [minor, fixable]** The abstract is dense. The sentence beginning "Of the 111 issues TestVDB surfaced" runs 6 lines with three parenthetical clauses and a "this is the composition of our findings, not a population estimate" caveat buried mid-paragraph. A tighter abstract would improve first-reader comprehension.
   - **5.4 [minor, fixable]** The "large majority" qualifier for "most documentation-implementation defects do not crash" is used twice (§Introduction, §\ref{tab:exclusion}) without a precise number. Table \ref{tab:exclusion} says "the large majority of the 50" but earlier the text says "about 85%." If the number is available, use it directly.

### Questions for Authors

- **Q1:** For the RQ2 ensemble, what is the performance of majority voting (e.g., 2-of-3 or 3-of-5) on the 48-candidate retrospective? Reporting the union-only ensemble leaves open the question of whether a more precise aggregation rule exists — does the union inflate false positives, and if so, by how much compared to majority? — This would clarify item 3.1.
- **Q2:** The 14 "open fix-PR" candidates across the 50 TP set — have these been submitted to maintainers, or are they PRs the authors opened? Do any have maintainer responses? — This would clarify item 4.3.
- **Q3:** The 48-candidate retrospective is described as "27 true-positive, 21 by-design/rejected." How were these 48 selected from the full 111? If this is a non-random subset, what selection criteria were used? — This would place the precision/recall numbers in context.
- **Q4:** The paper treats the 3/6 task-intrinsic clauses that cross-model judging missed as the key finding of RQ3. Is there a mechanistic explanation for why DeepSeek missed exactly those three (timeout >= 1, group_size >= 1, score_threshold in [0,1]) while catching others? The paper suggests "default-based parameters" as the pattern — was this a post-hoc observation or a pre-registered hypothesis?


## Reviewer 2: Area Specialist

**Overall Recommendation:** Weak Accept

### Summary

This paper targets documentation-implementation consistency defects in vector DBMSs (VDBMSs) -- cases where the API silently accepts inputs or behaviors that violate its natural-language documentation. Existing oracles (crash, differential, metamorphic, property-based) cannot adjudicate these accept/reject decisions because the documented boundary is natural-language prose rather than a formal specification, so the authors adopt an LLM as the semantic oracle. The key insight is that LLM interpretation errors split into two layers: family-specific self-preference (mitigated by cross-model validation) and task-intrinsic errors (where ambiguous documentation causes different model families to converge on the same wrong claim). The latter cannot be resolved by another LLM. The paper proposes source-grounded falsification -- treat LLM-derived behavioral claims as refutable hypotheses and check them against the implementation's source code. TestVDB instantiates this approach and surfaces 111 candidate issues across five VDBMSs, with 50 true-positive defects (36 confirmed). On a controlled retrospective (Milvus, Qdrant), the source-anchored dev-reviewer reaches 67% precision and 74% recall (3-run ensemble), versus 37% recall without source grounding.

### Core Strengths

- **S1:** Clear problem diagnosis and well-motivated solution -- the two-layer error decomposition (family-specific vs. task-intrinsic) is the paper's analytic contribution and cleanly motivates why a second LLM judge cannot fully replace source grounding. -- see 2.1, 3.1
- **S2:** The source-as-falsifier inversion distinguishes TestVDB from MASTOR and the broader REST-API oracle work, and the paper draws this contrast explicitly and honestly. -- see 2.1, 2.2
- **S3:** Substantial empirical footprint -- 111 submitted issues, 50 TPs across three major VDBMSs, with controlled retrospective and RQ3 probes across 50 clauses. The yield itself is reproducible evidence that the approach finds real defects. -- see 1.1, 2.3

### Core Weaknesses

- **W1:** Ensemble-rule justification (any-confirmed over majority voting) is plausible but rests on a domain-specific cost asymmetry that is assumed rather than demonstrated; the per-run variance is large (recall 15-78%) and the any-confirmed rule's precision ceiling is unclear from the current data. -- see 2.4, 2.5
- **W2:** The task-intrinsic phenomenon, while convincingly demonstrated, rests on n=6 TI clauses (parameters) plus n=11 behavior-level clauses; the parameter-level TI set is small and the Wilson CIs are wide ([16%, 56%]). The authors are appropriately cautious, but the headline claim's strength exceeds what the evidence can bear. -- see 2.6, 3.1
- **W3:** Run-to-run variance is disclosed but the paper's primary metrics (precision 67%, recall 74%) come from an any-confirmed 3-run ensemble that is not reproducible by a reader with a single run, and the paper does not specify a principled stopping criterion for how many ensemble runs are enough. -- see 2.5

### Detailed Assessment

1. **Significance** -- Adequate
   - **1.1** The paper identifies a real, practical problem: documentation-implementation defects in VDBMSs are costly (corrupt query semantics), prevalent (50 TPs found), and inaccessible to existing automated oracles. The 85% residual statistic (the proportion of found issues that are documentation-implementation defects) concretely quantifies the gap. This is a meaningful contribution to software testing practice, especially as VDBMS adoption grows.
   - **1.2 [minor, fixable]** The significance argument rests partly on the 85% residual being "of the issues TestVDB surfaced" -- the paper is careful to state this bias, but the framing in the abstract and intro may lead a reader to over-generalize. The Discussion section (page 7) explicitly caveats this, which is good, but the abstract's first paragraph ("About 85% are documentation-implementation defects") could be read as a population estimate. The authors should rephrase the abstract to match the caveated framing in Section 7.
   - **1.3 [minor, fixable]** The paper claims the approach generalizes beyond VDBMSs (REST APIs without OpenAPI, configuration validation, policy-as-code), but provides no evidence. This is acknowledged as future work, which is honest, but the claim in the conclusion that this is "where we see the testing of LLM-dependent systems heading" is speculative. I would prefer the Discussion to keep this as a conjecture rather than a forward-looking conclusion.

2. **Novelty** -- Adequate
   - **2.1** The two-layer error decomposition (family-specific vs. task-intrinsic) is the paper's core analytic contribution. I verified the characterization of MASTOR (Deng et al., 2026) against the paper's description: MASTOR extracts oracles from source code, with source-as-reference for implemented behavior, so it cannot detect doc-impl gaps. The paper's claim that TestVDB inverts source's role (source as falsifier of doc-derived claims, not source as oracle generator) is accurate and genuinely novel. The delta over MASTOR is real and well-articulated.
   - **2.2** The separation from documentation-derived oracle work (Toradocu, Doc2OracLL, ChatAssert, Testora) is also fairly drawn. I verified that the paper correctly characterizes these as operating in the "LLM as final arbiter" regime. The paper's claim that these predecessors work in low-ambiguity regimes (structured Javadoc, API specs) while TestVDB targets high-ambiguity natural-language prose is correct and supported.
   - **2.3** The novelty in the LLM-as-judge dimension is more incremental. The paper correctly identifies Panickssery et al.'s self-preference bias as the family-specific layer and Wataoka & Takahashi's converging evidence. The extension from text evaluation to the test-oracle pipeline is reasonable but not transformative. The paper's own contribution is separating the task-intrinsic extraction convergence from self-preference and intra-judge inconsistency (Haldar et al.), which is a useful conceptual distinction.
   - **2.4 [major, fixable]** The ensemble-rule justification (any-confirmed union over majority voting) is a design decision that impacts novelty positioning: the approach effectively trades precision (67% at 3 runs) for recall (74%). The paper argues this is justified because "under-confirmation is costlier than forwarding a false positive for human triage" (RQ2). This is a domain-specific assumption that may not hold universally. The paper should either (a) provide evidence for this cost asymmetry in VDBMS bug reporting (e.g., developer preference data) or (b) characterize the any-confirmed rule as a configurable design parameter rather than a core contribution.
   - **2.5 [major, fixable]** Single-run recall ranges 15-78% across five runs (RQ2). This variance is enormous and means the ensemble is critical to the headline metrics. The paper does not provide a principled stopping criterion for ensemble size (why 3 runs? what would justify 5 runs' 85% recall at 62% precision?). The current treatment ("we report the any-confirmed ensemble as the operating point") is ad-hoc. This needs a more rigorous justification or a sensitivity analysis showing how ensemble size affects the precision-recall tradeoff.
   - **2.6 [minor, fixable]** The task-intrinsic phenomenon, while convincingly demonstrated for the behavior-level subtype (11/11), rests on n=6 for parameters. The Wilson CI [16%, 56%] on 6/18 is wide, and the addition of only 1 new TI clause from the two scaling passes (6 new clauses, 1 TI) suggests saturation may be approaching but is not convincingly demonstrated. The paper's claim about "the phenomenon concentrates in optional-default APIs" is supported by the within-vendor contrast, but the sample is small.

3. **Soundness** -- Adequate
   - **3.1** The two-layer error decomposition is the paper's most important claim and the evidence for it is well-structured. The probe protocol (independent formalization by two families, then cross-model judging, then source-grounded checking) cleanly isolates each layer. The within-vendor contrast (optional-default vs. explicit-bound on Qdrant and Milvus independently) strengthens the claim by decoupling documentation style from vendor-specific factors. The explicit-bound specificity check (0/21 over-formalized) provides a negative control.
   - **3.2 [minor, fixable]** The behavior-level TI probe (11/11) adds additional evidence, but 7 of the 11 behaviors are "impl-confirmed idempotent but not separately maintainer-acknowledged" (RQ3). This means the ground truth for these 7 rests on the authors' own implementation reading rather than maintainer confirmation. This is a weaker standard than the maintainer-adjudicated defects in the yield study. The authors flag this caveat, which I appreciate, but the pooled TI rate of 17/29 includes these unconfirmed behaviors. I recommend either separating them more prominently or acknowledging that the behavior-TI finding is a hypothesis about idempotency rather than a confirmed defect pattern.
   - **3.3** The RQ1 yield numbers are credible. 36 confirmed defects (32 maintainer-acknowledged, 4 merged PRs) across three major VDBMSs is substantial. The Wilson CIs on yield precision ([58.0%, 78.9%] on 72 adjudicated; [47%, 67%] worst-case) are honestly reported and bound the uncertainty.
   - **3.4** The VDBFuzz head-to-head is appropriately cautious (n=1 per direction, hypothesis-generating). The paper does not overclaim this comparison, and the structural hypothesis about asymmetry is presented as conjecture, which is the correct approach.
   - **3.5 [minor, fixable]** The 85% documentation-implementation residual is based on the authors' own fault-model classification of their 111 submitted issues. While the per-issue mapping is in the artifact, a second-rater reliability check on this classification would strengthen the claim. Without it, the 85% figure is a single-author judgment.
   - **3.6 [minor, fixable]** The κ=1.0 cross-model check (GLM-5.2 vs. DeepSeek on 20 candidates) is striking but the sample is "a diversity-stratified, non-random sample" -- i.e., not random. Non-random sampling means the κ may not generalize. This is a minor concern (the authors acknowledge it) but worth noting.

4. **Verifiability** -- Adequate
   - **4.1** The paper declares that artifacts (full prompts, version matrix, per-token accounting, stability analysis, all dev-reviewer runs, corrected ground truth) will be released "at a persistent URL upon acceptance." This is standard but contingent. The artifact details described in the paper (footnotes, table captions, RQ footnotes) are thorough enough that a motivated reader could reconstruct the approach, but the lack of a currently reachable artifact lowers Verifiability from Excellent to Adequate.
   - **4.2** The paper discloses the uncontrolled random seed and run-to-run variance (Implementation section), which transparency is good. The version pinning (Docker versions listed) and the controlled version matrix (Table 1) enable reproduction.
   - **4.3 [minor, fixable]** The earlier superseded results (16-candidate control, 81% false-positive suppression) are mentioned as "no longer recoverable." This is a reasonable acknowledgment of evolving results, but it means a key ablation is not auditable from the current artifact.

5. **Presentation** -- Adequate
   - **5.1** The paper is well-structured and the argument progresses logically: problem → two-layer reliability diagnosis → method → implementation → evaluation → related work. The use of Table 1 (oracle exclusion) to frame the residual is effective.
   - **5.2** The paper is dense. Several paragraphs in RQ2 and RQ3 run to 30+ lines with embedded parentheticals, footnotes, and multiple statistics, making them difficult to parse. This is a structural issue rather than a language problem.
   - **5.3 [minor, fixable]** The term "contract-grounded dev-reviewer" is used in RQ2 but the paper elsewhere uses "source-grounded"; consistency would help.
   - **5.4 [minor, fixable]** The 85% figure appears with different denominators in different places: "about 85% are documentation-implementation defects" (abstract) vs. "89% on the 50-TP subset" (RQ1). The abstract should carry the same denominator as the evaluation section.
   - **5.5 [minor, fixable]** Table 2 (yield) shows "Acknowledged" but the text uses "true-positive defects (36 confirmed: 32 maintainer-acknowledged + 4 fixed via merged PR; 14 with open fix-PRs)." The column should be labeled "True Positives" with a footnote explaining the composition, since "Acknowledged" conflates confirmed and open-fix-PR states.
   - **5.6 [minor, fixable]** Minor typographical issues: "attribution" in the author block placeholder may need review; the \texttt{COSINE} bound reference in the abstract says "score_threshold that disables a filter" which may confuse readers unfamiliar with the space.

### Questions for Authors

- **Q1:** The any-confirmed ensemble (3-run union) achieves 74% recall but single-run recall ranges 15-78%. How should a practitioner decide how many ensemble runs to execute? Is there a stopping rule (e.g., diminishing returns on novel confirmations) or a recommended default?
- **Q2:** The 7 unconfirmed idempotency behaviors in the behavior-level TI probe -- do you plan to submit these as issues to the respective projects? If maintainers reject them as by-design, would that change the pooled TI rate of 17/29?
- **Q3:** The 85% residual is the composition of TestVDB's own findings, not a population estimate. Do you have plans for a capture-recapture or unbiased-sampling study that could bound the true documentation-implementation defect rate in VDBMSs?
- **Q4:** The κ=1.0 cross-model check on 20 candidates is based on a non-random diversity-stratified sample. What guided the stratification choices, and would you expect κ to hold on a random sample?


## Reviewer 3: General Reviewer

**Overall Recommendation:** Weak Accept

### Summary

This paper proposes TestVDB, a system that uses LLMs to detect documentation-implementation defects in Vector Database Management Systems (VDBMSs). The core problem is that VDBMS API documentation is natural-language prose, so accept/reject decisions for parameter boundaries and behavioral constraints cannot be mechanically checked by classical oracles (crash, differential, metamorphic, property-based testing). The paper makes a central observation that LLM-derived behavioral claims suffer from two reliability layers: family-specific errors (mitigated by cross-model validation) and task-intrinsic errors (where ambiguous documentation causes different LLM families to converge on the same wrong claim, which cross-model validation cannot resolve). The evaluation reports 111 candidate issues across five VDBMSs (Milvus, Qdrant, Weaviate, MeiliSearch, Chroma), 50 true-positive defects (36 confirmed), and controlled experiments showing the source-grounded dev-reviewer achieves 67% precision and 74% recall versus 56%/37% without the source anchor.

### Core Strengths

- **S1:** Well-motivated and precisely scoped problem — the paper carefully delineates documentation-implementation consistency from correctness, maps the failure modes of four oracle classes (crash, differential, metamorphic, property-based), and explains why the residual is structurally unreachable by each. This argument is clearly presented and persuasive. — see 1.1, 1.2
- **S2:** The two-layer reliability decomposition (family-specific vs. task-intrinsic errors) and the demonstration that cross-model validation cannot resolve the task-intrinsic layer (3 of 6 task-intrinsic clauses missed) is the paper's most interesting intellectual contribution. The within-vendor contrast between optional-default APIs (over-strict) and explicit-bound APIs (not over-strict) provides a falsifiable prediction that strengthens the claim. — see 2.1, 2.2
- **S3:** The paper produces substantial empirical evidence: 111 submissions, 50 true-positive defects, controlled retrospective with 48 adjudicated candidates, and a bidirectional reachability probe with VDBFuzz. For a first tool in this space, this constitutes meaningful scale. — see 1.3

### Core Weaknesses

- **W1:** The 85% "documentation-implementation residual" claim is explicitly caveated as the composition of TestVDB's own findings ("about 85% of the issues we submitted"), not an unbiased estimate of the underlying defect distribution, yet the abstract and introduction present it in a way that a casual reader will interpret as a population-level claim. This framing is misleading despite the paper's own caveats. — see 1.4
- **W2:** The evaluation lacks any comparison against a human baseline. Without knowing how many defects a human tester with equivalent domain familiarity would find in the same time budget, the real value added by the LLM pipeline is unclear. — see 1.5
- **W3:** The paper's claims about 5-system coverage are weakened by the extreme skew: MeiliSearch (3 submitted, 0 acknowledged) and Chroma (1 submitted, 0 acknowledged) contribute nothing statistically. Breadth claims should be dropped or explicitly restated as preliminary probes. — see 3.1

### Detailed Assessment

1. **Significance** — Adequate
   - **1.1** The paper identifies a genuine and under-studied problem: documentation-implementation defects in VDBMSs that are invisible to crash oracles and resist classical testing approaches. Section 2 (Background and Problem Setup) and Table 1 (tab:exclusion) provide a clear, structured argument for why the residual exists and why prior oracle families cannot reach it. This problem framing is the paper's strongest contribution and has clear practical relevance: the 50 true-positive defects (36 confirmed) demonstrate real-world impact on widely-used systems.
   - **1.2** The paper's argument that the problem extends beyond VDBMSs to "any system whose documentation is natural-language prose" (Section 8, Discussion) is plausible but the paper provides no evidence for this generalization. As a generalist reviewer, I find this transferability claim interesting but unsubstantiated, and it does not detract from the VDBMS-specific contribution.
   - **1.3** The defect yield (50 TP across three main VDBMSs) is non-trivial and demonstrates practical value. The maintainer acknowledgment rate (32 acknowledged + 4 merged PRs + 14 open fix-PRs) is convincing evidence that these are real defects, not tooling artifacts.
   - **1.4 [major, fixable]** The 85% residual figure is presented prominently in the abstract ("about 85% are documentation-implementation defects") and in the introduction. While the paper later caveats this as "the composition of our findings, not a population estimate" (abstract) and "the composition of TestVDB's findings, biased toward documentation-implementation defects by design" (Section 8), the prominence of the 85% number in headline positions will lead most readers to interpret it as a general claim about the defect distribution. The abstract in particular reads as if TestVDB's findings characterize the landscape. The paper should restructure this: either present the 85% as a "by-construction" property of TestVDB's biased sampling (TestVDB targets these defects, so naturally most of what it finds are these), or provide some independent evidence of the underlying distribution. As written, the caveat exists but is easily missed against the headline number's rhetorical weight.
   - **1.5 [major, fixable]** No human baseline is provided. How long would a manual boundary-testing session take? How many defects would it find? The paper mentions "comparable to a few hours of manual boundary testing" for cost (Section 5), but does not actually compare TestVDB's output against that manual baseline. Without a human-effort comparison, the practical significance claim — that TestVDB surfaces defects that would otherwise be missed — rests entirely on the 50 TP number, which is meaningful but hard to contextualize.
   - **1.6 [minor, fixable]** The capture-recapture estimation or unbiased defect sample is deferred to future work (Section 6). This is appropriate to flag, but means the paper cannot bound what fraction of all documentation-implementation defects TestVDB finds, which limits the significance of the yield numbers.

2. **Novelty** — Adequate
   - **2.1** The source-grounded falsification approach — treating LLM-derived claims as hypotheses to be falsified against source, rather than trusting the LLM's documentation interpretation — is a genuine methodological contribution. The paper clearly differentiates this from prior REST-API oracle work (AGORA+, SATORI, MASTOR) on the dimension of source ambiguity, and from documentation-derived oracle work (Toradocu, Doc2OracLL, ChatAssert) that still trusts the LLM as final arbiter. The conceptual contrast is convincing.
   - **2.2** The task-intrinsic error analysis (Section 3) and the probe demonstrating that cross-model validation misses 3 of 6 task-intrinsic clauses (Table e2) represents a non-obvious finding. As a generalist, I cannot assess whether this finding is entirely novel to the field of LLM-based oracle generation, but it appears to cleanly identify a failure mode that prior work (cited as Panickssery et al., Wataoka and Takahashi, Haldar et al.) had not separated out for the oracle-extraction setting. The within-vendor contrast between optional-default and explicit-bound documentation styles (RQ3) adds a falsifiable prediction that strengthens the scientific contribution.
   - **2.3 [minor, unfixable]** The individual components — LLM-as-judge, multi-agent pipeline, documentation extraction — are individually established techniques. The novelty is in their composition and the problem framing, not in any single algorithmic innovation. This is a genuine contribution but an incremental one in terms of method novelty; the principal novelty is in the problem characterization rather than the solution architecture.

3. **Soundness** — Adequate
   - **3.1 [major, fixable]** The evaluation claims coverage of "five VDBMSs," but MeiliSearch (3 submitted, 0 TP) and Chroma (1 submitted, 0 TP) contribute zero empirical support for any of the paper's claims. The paper's conclusions about defect patterns, precision/recall, and the task-intrinsic phenomenon are entirely based on Milvus, Qdrant, and (partially) Weaviate. The breadth claim about 5 systems should be either replaced with "3 primary systems + 2 exploratory probes" or supported with additional evidence that the two low-yield systems were meaningfully tested (e.g., a minimum per-system effort budget). As it stands, claiming "5 systems" inflates the apparent scope.
   - **3.2** The controlled retrospective on 48 adjudicated candidates (Milvus 32, Qdrant 16) is the paper's strongest quantitative evidence. The precision (67%) and recall (74%) figures for the 3-run ensemble are credible, and the reporting of variability across single runs (recall 15-78%) is honest and informative. The decision to report the "any-confirmed" ensemble rather than majority voting is well-justified given the falsification role of the dev-reviewer.
   - **3.3 [minor, fixable]** The RQ3 probe on task-intrinsic errors (18 parameters + 11 behaviors + 21 explicit-bound negatives = 50 clauses total) is carefully designed with within-vendor contrasts and a falsifiable prediction. However, the head-to-head with VDBFuzz is explicitly labeled as n=1 per direction and "hypothesis-generating" (Section 6). The paper is appropriately cautious here, but the cognitive effect of presenting it alongside the stronger controlled experiments is to imply more evidence than the two single cases warrant. The bidirectional probe should be more clearly separated from the main quantitative results.
   - **3.4 [minor, fixable]** The 14 "open fix-PR" issues are counted as true positives alongside the 36 confirmed/merged. While open fix-PRs do suggest maintainer agreement, they have not yet been accepted. The paper should report headline figures both including and excluding these pending issues. As it stands, 50 TP = 36 confirmed + 14 open; a reader who only tracks confirmed+merged would see 36.
   - **3.5** The paper honestly discloses its limitations (Section 8): source-grounded falsification requires source access and treats the implementation as correct (so an implementation bug can wrongly falsify a correct documentation claim). The correlation between documentation style and over-formalization is correctly labeled as correlative, not causal.

4. **Verifiability** — Adequate
   - **4.1** The paper declares that "the full prompts, target versions, and per-token accounting are in the artifact, which we will release at a persistent URL upon acceptance." This is the standard artifact commitment for an anonymous submission. A generalist reviewer cannot verify the artifact link during review, which is normal practice.
   - **4.2** The paper provides substantial procedural detail: the pipeline has five stages (Section 4), the dev-reviewer has three anchors (Section 4), the evaluation covers specific Docker versions (Milvus 2.6.19, Qdrant v1.18.2, v1.18.0, v1.4.0), and the LLM backbone is specified (GLM-5.2 via bigmodel API, Section 5). The cross-model check with DeepSeek is named and its results (Cohen's kappa = 1.0 on 20 candidates) are reported. A motivated reader could reconstruct the experimental setup.
   - **4.3 [minor, fixable]** Several important procedural details are missing from the text and deferred to the artifact: the per-issue fault-model classification (stated as "in the artifact"), the full version matrix for the five-system study (stated as "in the artifact"), and the earlier 16-candidate control data that the paper says "is no longer recoverable" (Section 6, RQ2). This latter point is concerning: if a previous experiment's data is no longer recoverable, it cannot be inspected. The paper does at least explicitly supersede those earlier figures with the reproducible cross-vendor ensemble, which is the correct practice.

5. **Presentation** — Adequate
   - **5.1** The paper's structure is logical and well-organized: problem setup (Section 1-2), the LLM reliability regime (Section 3), design (Section 4), implementation (Section 5), evaluation (Section 6), related work (Section 7), discussion (Section 8). Transitions between sections are smooth.
   - **5.2** The paper is dense and technically demanding. As a generalist reviewer, I found Section 3 (the LLM reliability regime) the most difficult: the distinction between family-specific and task-intrinsic errors, the extraction-vs-judgment role separation, and the stability claim are explained in prose that requires careful re-reading. The within-vendor contrast argument (optional-default vs. explicit-bound) was clearer, but the multiple layers of abstraction (extraction roles, judgment roles, cross-model validation, source falsification) could benefit from a concrete running example or a single illustrative case study that walks through all five pipeline stages end-to-end.
   - **5.3 [minor, fixable]** The RQ3 section (paragraph starting line 149) is unusually long and packs a remarkable density of results, caveats, and sub-analyses into a single paragraph. It reports parameter-TI results (18 clauses), behavior-TI results (11 clauses), explicit-bound negative results (21 parameters), a within-vendor contrast, a cross-vendor contrast, and aggregate pooled rates — all in one paragraph without sub-headings or clear visual separation. Restructuring RQ3 with sub-headings (e.g., Parameter-Level TI, Behavior-Level TI, Explicit-Bound Negatives) would substantially improve readability.
   - **5.4 [minor, fixable]** The paper's title is very long: "TestVDB: Source-Grounded Falsification of LLM-Derived Behavioral Claims for Documentation-Implementation Consistency Testing of Vector Databases." The running-head title in the document class header ("TestVDB: source-grounded falsification for VDBMS API documentation-implementation consistency") is more readable and should be the primary title, with the longer version as a subtitle.
   - **5.5 [minor, fixable]** Minor language issues throughout: "the LLM serves as the semantic oracle" (line 56) is ambiguous — does it mean the LLM acts as a semantic oracle, or serves as if it were one? The distinction between an oracle and a proxy for one is central to the paper's argument. A few sentences are excessively long and embed multiple caveats via dashes and parentheticals, making them hard to parse (e.g., the abstract's sentence beginning "Of the 111 issues TestVDB surfaced...").

### Questions for Authors

- **Q1:** You report 14 "open fix-PRs" as true positives. Have these PRs been reviewed by maintainers or are they self-submitted as part of the TestVDB pipeline? If the latter, on what basis are they classified as TP rather than pending? (Background: item 3.4 — the 50/36/14 accounting needs a clearer audit trail for the open-PR category.)
- **Q2:** You state that testVDB is comparable to "a few hours of manual boundary testing" in cost. Did you perform such manual testing? If so, how many defects did it find, and how does that compare to TestVDB's yield on the same version? If not, on what basis is the "few hours" estimate made? (Background: item 1.5 — the human baseline comparison is missing.)
- **Q3:** The earlier 16-candidate control study whose data "is no longer recoverable" — what guarantee do readers have that the current 48-candidate retrospective was not similarly affected by data loss? Has the data management protocol changed to prevent recurrence? (Background: item 4.3 — data recoverability is a verifiability concern.)
