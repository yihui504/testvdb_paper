## Reviewer 1: Domain Expert

**Overall Recommendation:** Accept

### Summary
TestVDB targets documentation-implementation defects in Vector Database Management Systems (VDBMSs): cases where a VDBMS silently accepts inputs or produces behaviors that violate its API documentation (e.g., accepting nprobe=0 when documentation declares range [1, 16384]). The paper argues that because documentation boundaries are natural-language prose rather than structured specifications (OpenAPI, traces, source code), deterministic oracles cannot adjudicate these accept/reject decisions, leaving an LLM as the practical oracle. TestVDB instantiates a four-stage pipeline (behavioral-claim extraction, test-script generation, sandboxed execution, defect confirmation) with LLMs automating documentation reading, test generation, and adjudication. Two false-positive modes arise: hallucination in claim extraction (LLM invents constraints documentation does not state) and self-preference bias in judgment (same-family LLM tends to confirm its own extracted claims). A multi-perspective judging baseline raises precision but collapses recall to ~15%. The paper introduces a dev-reviewer agent that acts as a source-grounded falsifier: it reproduces candidates under clean probes, cross-checks against implementation source, and tries to disprove them. On 107 submitted issues across three VDBMSs, maintainers acknowledged 50 as true positives (69% adjudicated yield; 15 fixed via merged PR). On a 48-candidate retrospective, the dev-reviewer (GLM-5.2 backbone, 3-run any-confirmed ensemble) reaches 67% precision and 74% recall, against 37% recall without source grounding. A bidirectional probe against VDBFuzz shows complementary coverage: TestVDB reaches a crash-class defect by contract reasoning (Qdrant integer overflow on size=2^63), while VDBFuzz misses a TestVDB silent-accept defect (wait=false accepting zero-length vector) under its current templates. The paper also reports a held-out cross-validation (200 random 50/50 splits; on each train half, select highest-recall operating point at precision ≥60%, evaluate on test half) confirming the 3-run selection is not overfit.

### Core Strengths
- **S1: Well-defined problem and oracle-exclusion argument** — see 1.1, 1.2. The paper systematically eliminates deterministic oracle candidates (crash, differential, metamorphic, property-based, REST-API tools) via an oracle-exclusion table (Table 1) showing why each misses the documentation-implementation residual, leaving an LLM-derived oracle as the only practical option. This cleanly motivates the approach.
- **S2: Dev-reviewer source-grounded falsification** — see 3.1, 3.2, 4.2. The dev-reviewer's three-check falsification (independently reproducible, evidence sufficient, falsifiable) breaks both hallucination and self-preference by grounding truth in implementation source rather than same-family LLM interpretation. The 37%→74% recall lift (without→with source grounding) on the 48-candidate retrospective directly measures this contribution.
- **S3: Substantive real-world evaluation** — see 4.1, 4.2. 107 submitted issues across three production VDBMSs with 50 maintainer-acknowledged TPs (15 merged-PR fixes) is strong practical impact. The 48-candidate retrospective (controlled subset, vendor-balanced) enables rigorous precision/recall measurement. The bidirectional VDBFuzz probe on Qdrant (Table 3) convincingly demonstrates complementary coverage.
- **S4: Honest cross-family limitation reporting** — see 4.2, 5.3. The cross-family re-run (DeepSeek, Qwen-3.8-Max, LongCat-2.0) revealing family-specific verdicts (κ=0.32, 0.20, 0.18 vs. GLM's 0.18) and vendor-specific recall collapse (DeepSeek 75% Milvus but 0% Qdrant) is transparently reported. The paper does not overgeneralize; it correctly flags cross-family generalization as an open question.

### Core Weaknesses
- **W1: Operating point selection is post-hoc and exploratory, not pre-registered** — see 4.2. The 3-run any-confirmed ensemble is selected as the "headline" operating point after examining five options (single-run per-run band, 3-run union, 5-run union, 5-run majority). The Wilson CIs do not account for this selection, and while a held-out cross-validation and bootstrap validation support the choice, the operating point was not pre-specified. This introduces selection bias, though the validations mitigate it.
- **W2 [minor, fixable]: Construct validity concern on implementation-as-correct assumption.** The dev-reviewer treats implementation source as ground truth for falsification. The paper acknowledges that implementation bugs can wrongly falsify correct documentation (false negatives), stating no maintainer-rejected confirmed TPs were observed and that 62% of true positives (31 of 50) have merged or open fix-PRs. This suggests the assumption "holds often enough," but the false-negative rate (documentation-only errors misclassified as defects) is unquantified. This is a validity concern: an oracle that treats source as truth can produce false negatives when documentation is right and source is wrong. Fixable via systematic disclosure of the 22 maintainer-rejected cases and documentation-error analysis.
- **W3 [minor, fixable]: External validity limited on non-VDBMS transferability claim.** The introduction claims transferability to "structurally similar documentation regimes" (REST APIs without OpenAPI, configuration validation, policy-as-code) and provides two non-VDBMS probes as preliminary evidence. Section 6 clarifies this is "a preliminary portability probe, not a generalization result." CouchDB exposed three input-validation gaps; Elasticsearch rejected every invalid probe with a 400 (zero gaps, mature baseline). Only CouchDB reproduced gaps, weakening the "two probes" generalization. Claiming transferability beyond VDBMS REST APIs on structural grounds without broader testing is overstated. Tightening to "structurally similar VDBMS REST API regimes" would be more accurate.

### Detailed Assessment

**1. Significance** — Adequate

- **1.1: Clear practical impact on VDBMS testing.** Documentation-implementation defects are a prevalent, costly subset of VDBMS bugs (empirical bug study: >50% are functional failures; roadmap: 43% are incorrect behavior). TestVDB's 50 acknowledged TPs (15 fixed) across production systems shows real-world relevance. The impact is bounded (three VDBMSs, one LLM family) but meaningful. The problem—silent-accept defects corrupting RAG context—motivates the work well.

- **1.2 [minor, fixable]: Scope clarity on non-VDBMS transferability.** The introduction (Section 6) claims transferability to structurally similar regimes (REST APIs without OpenAPI, configuration validation, policy-as-code) on structural grounds, with CouchDB/Elasticsearch probes as preliminary evidence. This is stated as a "preliminary portability probe" but reads like a generalization. The external validity section correctly flags it as an open empirical question without broad testing. Tightening the claim (e.g., "structurally similar to VDBMS REST APIs") would strengthen it.

**2. Novelty** — Excellent

- **2.1: Genuine delta over SATORI and MASTOR.** The oracle-exclusion argument (Table 1) is systematic and convincing. SATORI targets response-field oracles under per-field OpenAPI anchoring; TestVDB targets input-acceptance decisions on system-level prose where no per-field schema exists. MASTOR reads source to generate oracles encoding implemented behavior; it cannot detect documentation-implementation gaps. TestVDB reads source to falsify documentation-derived claims, targeting exactly that gap. This delta is real, not incremental. The related work (Section 7) accurately cites and positions both.

- **2.2: Dev-reviewer as novel LLM-as-judge bias mitigation.** Multi-perspective judging (4 specialized judge agents) raises precision (~80%) but collapses recall (~15%) because all judges read the same ambiguous documentation. The dev-reviewer breaks this by introducing an independent ground truth (implementation source) that falsifies LLM verdicts. This directly addresses the self-preference and hallucination literature (Panickssery24, Wataoka24, Haldar25) with a targeted mechanism, not a generic ensemble. The 37%→74% recall lift is substantial evidence of efficacy.

- **2.3: Unique methodological contribution in oracle-exclusion framing.** Rather than presenting TestVDB as "another LLM-based oracle generator," the paper frames the contribution as identifying where LLM-derived oracles are the *only* remaining option after systematically excluding deterministic candidates. This reframing is valuable for the field: it clarifies the boundary where LLM interpretation is necessary and where source-grounded falsification helps.

**3. Soundness** — Adequate

- **3.1: Core claims are supported, but operating point selection introduces mild selection bias.** The 50 acknowledged TPs out of 107 submissions (69% adjudicated yield) is strong evidence of detection capability. The 48-candidate retrospective shows the dev-reviewer lifting recall from 37% to 74% with source grounding, directly measuring the dev-reviewer's contribution. Abllation (Table 3) isolates source grounding as the dominant contributor (75% FP suppression alone). However, the headline 3-run operating point is selected post-hoc from four options without pre-registration. While held-out cross-validation (200 50/50 splits; test precision/recall 68%/71% matching headline) and bootstrap validation (precision CI [53%,83%], recall [71%,96%]) support the choice, the Wilson CIs in Table 2 do not account for selection bias. This is a fixable reporting limitation; the underlying data are strong.

- **3.2 [major, fixable]: Construct validity on implementation-as-correct assumption.** The dev-reviewer treats implementation source as ground truth for falsification. This is reasonable but not quantified: the paper states no maintainer-rejected confirmed TPs were observed and 31 merged/open PRs suggest the assumption "holds often enough." However, without a false-negative rate estimate or a systematic probe for documentation-error cases (where documentation is wrong but source-right), the assumption's robustness is unmeasured. This is a fundamental validity concern for an oracle that treats source as truth. Fixable via: (a) disclosing the 22 by-design/rejected cases and whether any were documentation-only errors, or (b) explicitly bounding the false-negative rate as a limitation.

- **3.3: Cross-family generalization limitation is transparent but substantive.** The cross-family re-run (DeepSeek, Qwen, LongCat) showing family-specific verdicts (κ=0.32, 0.20, 0.18) and vendor-specific recall collapse (DeepSeek 0% on Qdrant) is honestly reported as an open question. This is a clear limitation: the approach does not cross-family generalize. The paper does not overclaim; it flags the gap. This reduces the contribution scope to a single-family solution, but the single-family results (GLM-5.2: 67% precision, 74% recall) are still substantive.

- **3.4: Bidirectional VDBFuzz probe is methodologically sound.** The systematic direction (VDBFuzz 26k requests, 0 of 14 silent-accept TPs reached) cleanly shows crash oracles miss the target defect class. The controlled cases (v1.4.0 integer overflow reached by TestVDB via contract reasoning; v1.18.0 silent-accept missed by VDBFuzz) isolate the mechanism. This is strong evidence of complementary coverage, not just two isolated tools.

**4. Verifiability** — Adequate

- **4.1: Artifact is comprehensive and appears reproducible.** The paper promises a "reproduction driver" and full agent prompts (22 definitions, contract-formalizer and dev-reviewer excerpted in Appendix) at an anonymous GitHub repo. Table 2 shows approximate LLM-call distribution (~10⁴ calls per target). The 48-candidate ground truth is included. A bidder could in principle clone the repo, re-run the 3-run ensemble, and verify the precision/recall numbers. The artifact does not include raw LLM API keys or Docker images, but the methodology is clearly specified enough for independent replication using the same LLM API (GLM-5.2) and VDBMS versions.

- **4.2: Threats to validity are extensively discussed but one critical gap remains.** The paper provides detailed internal validity (single-run variance, multi-run ensemble selection bias, Wilson/Bonferroni/bootstrap validation, controlled retrospective non-randomness) and external validity (vendor coverage, construct validity assumptions) sections. However, the false-negative rate under the implementation-as-correct assumption (Section 6, W2) is unquantified. This is a gap: an oracle that falsifies against source can produce false negatives when documentation is right and source is wrong. The paper provides qualitative evidence (31 fix-PRs suggest assumption holds often) but no systematic estimate.

**5. Presentation** — Adequate

- **5.1 [minor, fixable]: Oracle-exclusion table (Table 1) could be clearer on "input-acceptance decisions" scope.** The table lists "REST doc/spec-derived oracles" (AGORA+, SATORI, MASTOR) as reaching "response-field/runtime properties from OpenAPI fields, traces, or source" but missing "input-acceptance on system-level prose." The prose explanation is clear, but the table cell could be clearer about why each tool misses the residual. This is a minor wording fix.

- **5.2 [minor, fixable]: Operating point selection description could explicitly flag post-hoc nature earlier.** Section 4.2 introduces Table 2 with operating points but does not flag that 3-run union is selected post-hoc until later text ("we select the 3-run union as the headline because it sits at the knee of the precision-recall trade-off"). Flagging this in Table 2 or the first mention would improve transparency.

- **5.3 [minor, fixable]: Cross-family re-run results could be more accessible.** The cross-family results are dense (κ values, vendor-specific recall collapse, inter-run disagreement patterns). A summary table of per-vendor, per-family recall/precision would make it easier to assess generalization gaps without parsing dense prose. The current presentation is understandable but could be clearer.

## Reviewer 3: General Reviewer

**Overall Recommendation:** Weak Accept

### Summary
The paper introduces TestVDB, a system for detecting documentation-implementation defects in Vector Database Management Systems (VDBMSs)—cases where a VDBMS silently accepts an input that violates its API documentation. The approach uses a four-stage pipeline where LLMs extract behavioral claims from documentation, generate test scripts, execute them against sandboxed VDBMS instances, and adjudicate whether responses violate the documented constraints. - **S2:** Comprehensive evaluation with maintainer-acknowledged ground truth and multiple validation angles — see 4.1, 4.2, 4.3

### Detailed Assessment

#### 1. Significance — Adequate
- **1.1** The paper targets a real and costly problem: silent-accept defects in VDBMSs that corrupt query semantics without producing crashes. The empirical motivation is strong: the bug study (cite{bugstudy25}) finds more than half of VDBMS bugs manifest as functional failures, and the roadmap (cite{roadmap25}) attributes 43% of bugs to incorrect behavior. TestVDB's 50 maintainer-acknowledged defects (15 fixed) demonstrate practical impact.
- **1.2 [minor, fixable]** The scope is narrower than the broader VDBMS testing problem the introduction gestures toward. The paper explicitly bounds itself to documentation-implementation consistency, excluding result correctness (ANN recall, ranking) from scope. This is appropriate for a focused contribution but limits the claimed impact to one defect class rather than VDBMS reliability broadly.

The gap claim is structurally argued (Table 2) but would be strengthened by a fetched comparison against a tool like REST-GPT or API conformance checkers that operate on prose documentation.
- **2.3** The dev-reviewer's three-check falsification (independent reproducibility, evidence sufficiency, falsifiability) is a methodological contribution but the individual checks are standard practices in debugging and code review. The innovation is systematizing them as an automated LLM pipeline, not the checks themselves.

#### 3. Soundness — Adequate
- **3.1** The main claims are supported with appropriate methods. The RQ1 yield study (107 submitted, 50 acknowledged) provides real-world evidence. The RQ2 controlled retrospective (48 candidates, maintainer-adjudicated) allows precision/recall measurement. The RQ3 bidirectional probe against VDBFuzz is well-designed: the systematic direction (VDBFuzz on TestVDB's pinned version, 26k requests, 0 of 14 TPs reached) is generalizable; the controlled cases (v1.4.0 crash, v1.18.0 silent-accept) are n=1 but isolate mechanism.
- **3.2** The implementation-as-correct assumption (Section 6) is a necessary limitation for source-grounded falsification. The paper provides partial validation: 31 of 50 TPs have merged/open fix-PRs (implementation confirmed buggy), and no FP was traced to an implementation bug. However, the false-negative rate from this assumption is not quantified, and the acknowledgment ("we did not quantify this false-negative rate, which would require a ground-truth catalog of documentation errors") is honest but leaves a gap.
- **3.3 [major, unfixable]** The post-hoc operating-point selection in RQ2 undermines the 67%/74% headline's reliability. The paper tests three evaluated operating points (single-run, 3-run union, 5-run union); a 5-run majority row is reported but rejected as collapsing recall. The authors select 3-run union as the headline because it sits at "the knee of the precision-recall trade-off." This selection is exploratory, not pre-registered, and the Wilson CIs do not account for it. A held-out cross-validation (200 random 50/50 splits) confirms 3-run generalizes (test precision/recall 68%/71% matching headline when selected, 27% of splits), but this is post-hoc validation of a post-hoc choice. The Bonferroni correction widens CIs but does not fix the selection problem.
- **3.4** The cross-family generalization experiment (DeepSeek, Qwen, LongCat) is honest about the limitation but exposes a weakness. The verdict is family-specific (κ 0.18–0.32), and all three families stay at ≤14% recall on Qdrant versus GLM's 74%. The paper flags this as an open question, but the single-backbone evaluation (GLM-5.2 only) limits claims about LLM-derived oracle reliability.

#### 4. Verifiability — Adequate
- **4.1** The paper provides enough information to follow the evidence production pipeline. The four-stage approach is clearly described with examples (Section 3). The dev-reviewer's three-check process is illustrated with a concrete reversal case (#9255, payload-filter FP). The artifact link (GitHub repo with agents/, ground truth, reproduction) is declared and appears reachable.
- **4.2 [minor, fixable]** Some procedural details are sparse. The paper does not specify the exact sampling parameters for GLM-5.2 ("default sampling" is provider-dependent) or the precise prompts for the 22 agents (only excerpts in Appendix). The 12-FP/4-TP ablation control (Table 5) does not explain how the 12 FPs were selected or whether they are representative.
- **4.3 [minor, fixable]** The transferability probe (CouchDB, Elasticsearch) is described with concrete findings but lacks methodological detail: how many candidates were run, what the candidate selection criteria were, and whether a maintainer adjudicated the CouchDB gaps. This limits reproducibility of the non-VDBMS validation.

#### 5. Presentation — Adequate
- **5.1** The paper is well-structured and readable. The introduction clearly frames the problem and contribution. The pipeline walkthrough (Section 3) with the #49823 example makes the approach concrete. The figures (pipeline diagram, dev-reviewer three-check flow, per-run recall plot) are effective.
- **5.2 [minor, fixable]** Notation inconsistencies are minor but present. Table 4 reports "Accuracy, Precision, Recall" for operating points but the baseline row (single-LLM) lists a "per-run band" (44–65% accuracy) in the same column, breaking the table's internal consistency. The perrun figure labels runs 1–5 but does not specify what "run" means operationally (independent LLM calls? independent docker executions?).
- **5.3 [minor, fixable]** Some language is ambiguous. The abstract states "two failure modes produce false positives: hallucination in claim extraction and self-preference bias in judgment" but the paper later shows multi-perspective judging reaches 80% precision—suggesting self-preference is not the only precision issue. Section 6 states "We did not observe maintainer-rejected confirmed TPs where the documentation itself was wrong" but does not define how "confirmed TP" is adjudicated in that observation.

### Questions for Authors
- **Q1:** How was the 12-FP/4-TP ablation control set constructed, and what evidence supports its representativeness for the full 48-candidate retrospective? — [intended effect: if the authors clarify the selection bias, item 3.4's rating would move from major to minor because the ablation's quantitative claims (75% FP suppression by source alone) would be more credible]
- **Q2:** What specific sampling parameters (temperature, top-p, top-k) does "default sampling" mean for the GLM-5.2 backbone under the BigModel Anthropic-compatible API? — [intended effect: clarifying reproducibility would move 4.2 from minor to adequate by resolving a procedural gap]
- **Q3:** In the CouchDB/Elasticsearch transferability probe, how many candidates were run and what was the selection criteria? — [intended effect: clarifying scope would move 4.3 from minor to adequate by showing the probe was systematic rather than anecdotal]

### Assessment of Round-5 Changes
The authors have partially addressed my prior R4 concern (item 3.5, post-hoc operating-point selection as [major, fixable]). The addition of a held-out cross-validation (200 random 50/50 splits) is a meaningful step: it confirms that 3-run, when selected (27% of splits), achieves test precision/recall 68%/71% matching the headline. The held-out-preferred 5-run (61%) reaching test recall 85% is also valuable context. However, the core issue remains: the operating point is still post-hoc, not pre-registered. The cross-validation validates generalization but does not eliminate selection bias. I am upgrading from Weak Accept (R4) to a stronger Weak Accept, but the post-hoc selection remains a [major, fixable] issue that prevents full Accept.

### Final Judgment
The paper makes a solid contribution to VDBMS testing with a well-executed empirical evaluation. The source-grounded falsification approach is a principled countermeasure to LLM false-positive modes. The limitations (post-hoc operating point, single-backbone evaluation, narrow transferability evidence) are real but do not invalidate the core claims. The work is publishable with minor revisions acknowledging these limitations explicitly. The Weak Accept reflects that the contribution is incremental rather than transformative and that key claims (74% recall, cross-family robustness) are conditional on unmet prerequisites.
