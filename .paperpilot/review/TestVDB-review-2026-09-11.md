## Reviewer 1: Domain Expert

**Overall Recommendation:** Weak Accept

### Summary

The paper targets *documentation–implementation bugs* in vector database management systems (VDBMSs): non-crashing failures where the system silently accepts an input or returns behavior that contradicts its own API documentation (e.g., Milvus accepting `nprobe=0` although the documentation declares [1, 16384]). The authors argue, via a systematic exclusion analysis (Table 1), that no deterministic oracle candidate anchors its expectation in system-level untagged prose, so an LLM-derived oracle is the practical option — which imports the LLM false-positive problem. Their pipeline, TestVDB, responds with four stages: documentation-to-specification extraction with evidence tiers and source verification; test generation through pre-bound (deterministically selected) attack strategies including stateful multi-request scenarios; Docker-pinned sandbox execution; and a confirmation stage that splits evidence assembly from cross-examination, grounding every verdict in a five-section evidence chain whose implementation-source section serves as a falsification anchor independent of the documentation.

Empirically, across Milvus, Qdrant, and Weaviate, maintainers confirmed 51 of 81 adjudicated submissions as real bugs and fixed 23 via merged PRs. A controlled three-run re-adjudication of the same pool under frozen packages and blinding shows the contract-only core intercepts 87–90% of false positives at 88.9% verdict agreement but recalls only 0.196–0.333 of the true bugs; adding source forensics and maintainer cognition reaches recall 0.373 with perfect suppression; an independent source-only arm reaches 0.333, indicating source grounding carries most of the gain; and a flat single-prompt judge with source access matches the structured stage, so the scaffolding is claimed as discipline rather than measured accuracy. A bidirectional probe against VDBFuzz on the same Qdrant instance — run over its complete 205-template space with the time limit removed — shows the crash oracle reaches none of the silent-accept defects, while TestVDB's boundary reasoning reaches VDBFuzz's crash-class integer overflow on an older version.

### Core Strengths

- **S1:** The oracle-exclusion analysis (Table 1, Sections 2.4 and 2.3) is a genuinely useful formalization: organizing oracle candidates by *where their expectation is anchored* cleanly delimits the residual that forces an LLM, and I verified the characterizations of the named competitors against their own texts — see 2.1, 2.2, 2.4.
- **S2:** Concrete, well-validated real-world impact: 51 maintainer-confirmed bugs, 23 fixed, with a fix-nature audit showing all 23 merged PRs modify implementation code (15 add regression tests, none doc-only), and the PR classifier itself validated on the disproved #9149 — see 1.1, 3.1.
- **S3:** Measurement rigor well above the genre's norm: blinded frozen-package re-adjudication in three independent runs, conservative forced-binary rule, Wilson intervals, exact paired McNemar tests, the "re-aggregation is not an arm" methodological point, and voluntary disclosure that the prior unblinded protocol reported recall 0.841 versus 0.373 here — see 3.2.
- **S4:** The RQ3 baseline study is done forensically: the authors discovered the released VDBFuzz runner reports exit-0 and "100% success" against a dead port, substituted an independent per-template liveness oracle, measured the zero's bound from two directions, and explicitly withdrew an earlier wrong explanation — see 3.3.

### Core Weaknesses

- **W1:** The effectiveness headline rests on a submission-filtered pool: the 81 candidates passed author-side novelty screening with no deterministic submission rule, and the blinded automated stage recalls only 0.216–0.373 of that already-screened pool, so the raw-stream behavior of the pipeline remains unestablished — see 1.2, 3.2.
- **W2:** Every agent and every judge runs on a single LLM family (GLM-5.2) with unpinned weights; all RQ2 rates are therefore properties of one backbone, and cross-family generalization is untested — see 3.4.
- **W3:** The paper's own flat-judge arm shows the four-perspective confirmation scaffolding adds no statistically distinguishable accuracy over a flat judge with source access, so contribution 2's mechanism claim survives only in the weakened "discipline and auditability" form — see 2.3.

### Detailed Assessment

1. **Significance** — Adequate
   - **1.1** The fix-nature audit (Section 4.2, "Fix nature" paragraph) converts the confirmation count into evidence of actionable defects: all 23 fixed bugs have merged PRs touching implementation code, 15 add regression tests, none is documentation-only; and the authors apply the same classifier to the fix PR of the disproved #9149, correctly identifying it as test-only. This is exactly the validation most bug-finding papers skip, and it makes the 51-bug yield (Table 2) credible as practical impact on three production systems.
   - **1.2 [minor, fixable]** The practical significance of RQ1 is a human–machine number: Section 4.2's closing pool-provenance paragraph (the unheaded paragraph beginning "The 30 adjudicated false positives are not waste…") and Section 4.3's opening disclose that submissions passed author-side novelty screening and manual review with no deterministic rule, and Section 4.3's opening concedes the direction of the induced recall bias is "unestablished." Since the blinded automated stage recalls at most 0.373 of the screened pool, a reader cannot tell from the paper what unassisted TestVDB would find on a fresh target. Quantifying the confirmation stage on the unsubmitted candidates of the reported Qdrant run (60 defect-confirming, of which only 11 correspond to submitted-and-fixed bugs) would substantially sharpen the significance claim — see Q1.
   - **1.3** The residual claim is well chosen: the paper explicitly disclaims result correctness of ANN search (Section 2.3, "consistency versus correctness") and confines itself to documentation conformance, and the roadmap's oracle-definition challenge (Section 2.2) is the gap this work addresses. Scoping the claim this way is what makes the contribution useful rather than overreaching.

2. **Novelty** — Adequate
   - **2.1** Delta against MASTOR (fetched and read): the paper positions MASTOR as the closest work — source-grounded multi-agent oracle generation with a ChallengerAgent — and concedes "a generated oracle reviewed by a second LLM agent is therefore not new here" (Section 6, second paragraph). I verified MASTOR's own limitation statement that it "cannot detect violations of intended requirements that are not reflected in code": the anchor inversion (prose as ground, implementation as falsifier) is exactly the complement of MASTOR's authority direction. The delta holds and is honestly scoped.
   - **2.2** Delta against CASCADE and Metamon (both fetched/cached and read): the paper's characterization that CASCADE's falsifier is "another LLM artifact sharing the documentation's ambiguity" matches CASCADE's actual design (doc-derived tests cross-checked against doc-regenerated code, report only on fail-to-pass transitions with no pass-to-fail), and the quoted residual-FP sentence about CASCADE's "same false assumption over something underspecified" appears verbatim in CASCADE's own ablation section. Metamon's falsifier is likewise an LLM question (metamorphic prompt pairs over the same judge), and the quoted precision/recall profile (0.722/0.480; 0.967 only below recall 0.1) matches its reported numbers. The design rationale for a non-LLM falsifier is therefore empirically motivated by prior work's own failure modes, not merely asserted.
   - **2.3 [minor, fixable]** The paper's own fifth arm (Section 4.3, "Does the scaffolding itself matter?") finds the flat single-prompt judge statistically indistinguishable from the full structured stage (p=1.000) while beating the contract core (p=0.008), and the authors respond by claiming the four perspectives as "discipline and auditability rather than as measured accuracy." That is the right call, but contribution 2 (Section 1, contributions list) still leads with the evidence-chain/four-perspective confirmation stage as *the* mechanism that "breaks the LLM's extraction-judgment self-reference"; the contributions list should be tempered to match what the evaluation shows — that evidence access (source grounding), not judgment structure, carries the measurable gain — see Q5.
   - **2.4** Related-work coverage is unusually complete and, in every case I checked, accurate: VDBFuzz (crash oracle, 205-template Qdrant set, the `dim=2^63` overflow case study), Konstantinou et al. (LLM oracles capture actual rather than expected behavior — confirmed against its abstract and conclusions), and the doc-derived line from iComment through RBCTest and Testora are characterized correctly. My scoped coverage searches surfaced no uncited close competitor (Doc2OracLL and the testing roadmap are already cited; remaining hits were on requirements-to-tests generation and architectural conformance — not competitors). One provisional note: OAS-driven REST test generators of the RESTest family are not cited, though the structured-source class they belong to is represented (Schemathesis, QuickREST, AGORA+/SATORI/MASTOR) — provisional, unverified this session, and not load-bearing.

3. **Soundness** — Adequate
   - **3.1** Ground-truth discipline is strong: maintainer adjudication with explicit confirm/FP/duplicate-tracked definitions (Section 4.2, "Collection protocol" paragraph), duplicate handling kept orthogonal to the outcome axis, 49 unadjudicated submissions excluded from every rate, all states re-verified as of September 2026, and adjudication treated as revisable — the #9149 candidate was reclassified on the authors' own seven-version re-probe. Disclosing that one's own earlier accepted bug was an artifact of a test-only "fix" PR is unusual candor.
   - **3.2** The RQ2 protocol is sound and its numbers are internally consistent — I recomputed them: 11/51 = 0.216 majority core recall, 26/30 = 0.867 suppression, per-run 0.196–0.333 and 0.867–0.900, full stage 19/51 = 0.373 at 30/30 suppression, source-only 17/51 = 0.333 at precision 0.944, eligible-subset 11/47 = 0.234 and 19/47 = 0.404, agreement 72/81 = 88.9%, per-run precisions 0.750–0.810 — all match the quoted rates, and the Wilson intervals and exact McNemar p-values are appropriate for a pool of this size. The stratification analysis (Table 6) and the attribution of the four Milvus leaks to pack-induced contract misreadings (extraction-side, outside the confirmation-stage error budget) are the kind of error accounting that makes the results interpretable. The limitation disclosures (expectation-framing bias, observation leakage) are concrete and their mitigation by the frozen-package protocol is described precisely.
   - **3.3** The RQ3 evidence is measured, not asserted: 22,540 mutations over 205 templates in 50.8 minutes, 23,258 HTTP responses over 96 endpoint paths, and — critically — the demonstration that the released runner's summary counters are uninformative (exit-0 and "100% success" against a port with no server), which replaces a would-be vacuous zero with a per-template liveness oracle plus a two-sided bound on the released configuration's reachable space (integer ceiling 65,536 and dimension ceiling 10,000 versus the ~2^62 needed for the overflow).
   - **3.4 [major, fixable]** All extraction, generation, and judging — including every RQ2 judge in every arm — runs on one LLM family (GLM-5.2) under default sampling, and Section 5 (Limitations, External validity paragraph) admits no snapshot identifier is reported, so the exact weights behind any run are unrecoverable. The suppression/agreement/recall rates reported as properties of the *confirmation-stage design* are thus measured on a single backbone that also produced the packs being judged; the paper's own citation of Molinelli et al. on per-subject unreliability of LLM oracles makes the single-family restriction a first-order concern for generalization. One cross-family replication of the frozen-package re-adjudication (the protocol is cheap — 81 packages, three runs) would resolve most of this — see Q2.
   - **3.5 [minor, fixable]** Extraction accuracy is unmeasured, as the paper itself states (Section 4.3, "False-positive interception is stable" paragraph: "end-to-end precision — extraction and confirmation together — is unmeasured"). The four leaked false positives are diagnosed as pack-induced (extraction-side), which means the extraction stage's error rate directly bounds the operational pipeline's precision, yet no constraint-level audit against the cited documentation pages is reported. A sampled audit of specifications.json against source pages is a bounded, feasible revision.
   - **3.6 [minor, fixable]** The per-template liveness oracle substituted in RQ3 has limited sensitivity to the crash class by the paper's own footnote: on Qdrant v1.4.0 the reproduced integer overflow is a recovered panic — HTTP 500 with `GET /` still returning 200 — so "a liveness oracle would not record it either." The "neither constructible nor observable" conclusion for the overflow class survives on the constructibility bound alone, but the observability claim should be stated as covering service death, not recovered-panic or error-response crashes; as written, the measured zero is narrower than "the crash class is unobservable" may suggest to a reader — see Q4.

If a snapshot identifier exists, adding it to the package would close the largest remaining reproduction gap — see Q3.

## Reviewer 2: Area Specialist

*Specialty areas for this review: (1) LLM-derived test oracles from documentation/specifications; (2) LLM-as-judge reliability. **Overall Recommendation:** Accept

### Summary

The paper targets documentation-implementation bugs in vector database management systems (VDBMSs): cases where the system silently accepts an input or returns a wrong success that violates its natural-language API documentation — behaviors that produce no crash and are therefore structurally invisible to the crash-oracle fuzzer VDBFuzz. The authors argue (Table 1) that every deterministic oracle candidate anchors its expectation in something other than system-level, untagged prose, which forces an LLM-derived oracle and imports the false-positive problem of an LLM both writing and judging the oracle. TestVDB is a four-stage pipeline: documentation-to-specification extraction with evidence tiers and source verification; attack-agent test generation under deterministically pre-bound strategies; sandboxed execution against Docker-pinned versions; and a confirmation stage that splits evidence assembly from cross-examination, auditing five-section evidence chains from four perspectives (contract, physical behavior, maintainer cognition, implementation source), with the source as the falsification anchor.

The evidence has two layers. Operationally, across Milvus, Qdrant, and Weaviate, 51 of 81 adjudicated upstream submissions were maintainer-confirmed as real bugs and 23 were fixed via merged implementation-code PRs. In a controlled layer, the 81-candidate pool was re-adjudicated under blinding in three runs per arm over frozen packages: the contract core suppresses 87–90% of false positives at 88.9% verdict agreement but recalls only 0.196–0.333; the full stage reaches perfect suppression at recall 0.373; an independent source-only arm recovers 0.333, indicating source grounding carries most of the gain; and a flat single-prompt judge matches the structured stage, so the authors claim the scaffolding as discipline rather than measured accuracy. A bidirectional probe on Qdrant shows VDBFuzz's full template space reaches none of the paper's silent-accept defects while TestVDB's boundary reasoning reaches VDBFuzz's crash-class integer overflow.

### Core Strengths

- **S1:** Demonstrated operational impact with validated ground truth: 51 maintainer-confirmed bugs (23 merged fix PRs, all verified to modify implementation code, none documentation-only) across three production VDBMSs, with the fix classifier checked against a negative control — see 1.1, 3.1.
- **S2:** The central novelty delta over the closest LLM-oracle competitors checks out against the competitors themselves: MASTOR's own limitation section concedes source-anchored oracles cannot detect documentation-code gaps, and CASCADE/Metamon both falsify with LLM-side artifacts, whereas TestVDB falsifies with the human implementation — see 2.1, 2.2.
- **S3:** The blinded, five-arm, three-run measurement of the confirmation stage — including a flat-judge control whose result the authors report against their own architecture narrative, and the disclosed correction of an unblinded recall of 0.841 down to 0.373 — is an unusually honest measurement design for an LLM-judge system — see 3.2, 1.2.

### Core Weaknesses

- **W1:** End-to-end precision is unmeasured: extraction accuracy is never audited, the four contract-core leaks are pack-induced, and the suppression headline is conditional on unmeasured frozen-pack quality — see 3.4.
- **W2:** Missing positioning against two uncited, genuinely related works in my specialty: a 2026 SLR that organizes LLM-based test oracles by exactly this paper's framing axis (source of an oracle's authority), and the reference TOSEM survey on LLM test-oracle automation — see 2.4.
- **W3:** The "statistically real increment" claim for the remaining perspectives rests on p = 0.017 with no multiplicity handling across six paired tests, which any correction would erase — see 3.6.

### Detailed Assessment

1. **Significance** — Excellent
   - **1.1** §4.2 (Table 2, "Bug status", "Fix nature"): the paper reports an operational deployment that yielded 81 adjudicated upstream submissions, of which 51 were maintainer-confirmed (63.0%) and 23 fixed via merged PRs; the "Fix nature" paragraph validates that every fix PR modifies implementation code (15 add regression tests) and validates the classifier itself on the disproved #9149 PR, correctly identifying it as test-only. This is demonstrated practical impact on real infrastructure, and the validation work makes the yield considerably more trustworthy than raw bug-finding counts.
   - **1.2** §4.3 ("Where the boundary sits") and §5, Limitations, the internal-validity paragraph: the disclosed gap between the earlier unblinded recall (0.841) and the blinded 0.373, together with the named judgment-side mechanisms (expectation-framing bias, observation leakage), is itself a research result the LLM-oracle field needs — it complements leakage/contamination findings in the LLM-oracle literature (Molinelli et al., fetched this session) with judgment-side inflation mechanisms, and the authors adopt the blinding protocol rather than the flattering number.
   - **1.3 [minor, fixable]** The impact is bound to the human–machine pipeline: §4.2's closing caveat states submission decisions were author-made with "no deterministic submission rule", and the automated stage alone recalls 0.216–0.373 on this pool with end-to-end precision unmeasured (see 3.4). 2. **Novelty** — Adequate

## Reviewer 3: General Reviewer

**Overall Recommendation:** Weak Accept

### Summary

The paper targets *documentation-implementation bugs* in vector database management systems (VDBMSs): silent accepts and wrong successes that violate the system's own natural-language API documentation and therefore escape crash-oracle fuzzing. The authors argue (Table 1) that every deterministic oracle candidate anchors its expectation somewhere other than system-level, untagged prose, which forces an LLM-derived oracle and imports the LLM false-positive problem. Their pipeline, TestVDB, has four stages: two-step extraction of structured behavioral specifications from crawled documentation; test generation by strategy-pre-bound attack agents; sandboxed execution against Docker-pinned instances; and a bug-confirmation stage that splits evidence assembly (evidence builder) from cross-examination (chain auditor with four mechanical checks and four perspectives), with the implementation source as the falsification anchor.

Evidence is reported on three layers: (1) an operational ledger across Milvus, Qdrant, and Weaviate in which maintainers confirmed 51 of 81 adjudicated submissions and fixed 23 via merged PRs; (2) a controlled three-run, blinded re-adjudication of that same 81-case pool under frozen packages, where the contract core suppresses 87-90% of the 30 false positives at 88.9% verdict agreement but recalls only 0.196-0.333 of the true bugs, the full stage reaches 0.373 recall at 1.000 suppression, and an independent source-only arm (0.333) plus a flat single-prompt judge (0.392) attribute most of the gain to evidence access rather than to the four-perspective scaffolding; and (3) a bidirectional probe against VDBFuzz showing complementarity, including a full-template-space run on the same Qdrant v1.18.0 instance that reaches none of the paper's silent-accept defects.

### Core Strengths

- **S1:** Tangible, externally verifiable impact: 51 maintainer-confirmed bugs with 23 merged fix PRs, validated by a fix-PR file classifier with its own sanity check — see 1.1, 3.1
- **S2:** Methodologically careful blinded re-adjudication: frozen packages, three runs, majority vote, Wilson intervals, exact McNemar tests, and a multi-arm design (core / full / source-only / flat judge) that isolates evidence access from scaffolding — see 3.2, 3.3
- **S3:** Unusually honest negative reporting: the 0.841-to-0.373 recall drop under blinding is disclosed, an incorrect RQ3 explanation is withdrawn rather than silently replaced, and VDBFuzz's own summary counters are investigated and rejected as uninformative — see 3.4
- **S4:** Clear problem framing via the oracle-anchor analysis (Table 1 and Section 2.4), which makes the case for an LLM oracle structurally rather than rhetorically — see 2.1

### Core Weaknesses

- **W1:** The automated stage's measured capability is modest (recall 0.216-0.392 across arms on its own pool) and end-to-end precision is unmeasured, because extraction accuracy is never audited and the contract core's four false-positive leaks are attributed to pack (extraction-side) errors — see 3.5
- **W2:** All RQ2 rates are measured on a submission-filtered pool whose construction was a human judgment call, so even the direction of the recall bias is unestablished; the practical meaning of the recall figures outside the pool is unknown — see 3.6
- **W3:** The central mechanism narrative (source grounding carries most of the gain) rests on orderings whose individual steps are not statistically significant (core vs. source-only p=0.093; source-only vs. full p=0.648), and the shipped aggregation rule is an uncalibrated choice — see 3.8
- **W4:** Internal count inconsistencies and dense reporting impair trust in the numbers: five vs. four assertion-ineligible bugs, an unanchored "four boundary truths," and a misleading "thirteen cases above" phrasing — see 3.7, 5.5, 5.6

For a testing paper, 23 merged upstream fixes across three systems is a concrete, checkable contribution, and the bug-pattern taxonomy (Table 3: silent-accept family = 37/51 = 72.5%) quantifies precisely the class a crash oracle misses.
   - **1.2 [minor, unfixable]** The scope that bounds significance is the paper's own finding: Section 4.3 shows the assertion-framework boundary concentrates the misses (recall 0.373 for the full stage on its own pool, mechanism (i)-(iii)), and Section 5's external-validity paragraph bounds claims to prose-constraint APIs of three systems. The method as measured is a recall-limited, human-assisted finding tool rather than a standalone detector; this inheres in the contribution, not the writing.

The related-work section is exceptionally thorough and candid ("A generated oracle reviewed by a second LLM agent is therefore not new here"), which supports the claimed delta as described.
