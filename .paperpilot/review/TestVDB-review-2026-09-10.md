## Reviewer 1: Domain Expert

**Overall Recommendation:** Weak Accept

### Summary

The paper targets *documentation-implementation bugs* in vector database management systems (VDBMSs): the system silently accepts an input or exhibits behavior that violates its natural-language API documentation, producing no crash and therefore escaping crash-oracle fuzzers such as VDBFuzz. Because the documented constraints live in prose, the authors argue that every deterministic-oracle candidate (crash, differential, metamorphic, property-based, spec/trace/source-derived) is structurally unable to derive the expectation, leaving an LLM-derived oracle as the practical option — at the cost of the LLM's false-positive problem. TestVDB is a four-stage multi-agent pipeline: behavioral specification extraction from crawled documentation (typed, evidence-tiered, source-verified constraints), pre-bound-strategy test generation with scenario construction for system-level constraints, Docker-pinned sandboxed execution with raw HTTP logging, and a bug-confirmation stage that splits evidence assembly (builder) from cross-examination (auditor), grounding every verdict in a five-section evidence chain anchored in the implementation source and maintainer cognition mined from issue history. Evaluation: maintainers confirmed 51 of 81 adjudicated submissions across Milvus, Qdrant, and Weaviate as real bugs, 23 fixed via merged PRs (RQ1); a three-run re-adjudication of the full 81-candidate pool under a frozen-package protocol shows the contract-adjudication core intercepts 86.7–90% of false positives with 88.9% case-level agreement, while its low recall (0.196–0.333) is attributed to three systematic mechanisms delimiting where source grounding and cognition become necessary (RQ2); a bidirectional and full-coverage probe against VDBFuzz on Qdrant shows the two oracles reach complementary bug classes (RQ3).

### Core Strengths

- **S1:** Externally validated detection yield with unusually honest adjudication epistemics — 51 maintainer-confirmed bugs, 23 with merged implementation-code fix PRs, a fix-PR classifier validated on the authors' own disproved candidate (#9149), and adjudication treated as revisable — see 1.1, 3.1, 3.2.
- **S2:** The oracle-exclusion analysis (Table 1) is correct against the actual competitor mechanisms: I verified MASTOR's own admission that it cannot detect requirements not reflected in code, SATORI's response-field-only anchoring, and VDBFuzz's crash-oracle scope; the delimitation of where an LLM oracle is forced holds — see 2.1, 2.2.
- **S3:** The RQ2 frozen-package three-run protocol is the right design for measuring judgment-side reliability, and it addresses two disclosed threats (expectation-framing bias, observation leakage) that most LLM-oracle evaluations leave silent — see 3.3.
- **S4:** RQ3 is a fair, budget-unconfounded complementarity probe: the reverse direction plus a full-template-space run on a commit-matched instance converts the standard "our oracle reaches a class theirs cannot" assertion into a measurement — see 3.5.

### Core Weaknesses

- **W1:** The RQ2 reporting is internally inconsistent: the RQ2 matrix table's majority row (TN=26, FP leaked=4) cannot be reconciled with the prose claims that the four remaining false positives are "still rejected by a majority," that "not one false positive is ever confirmed by a majority of runs," and that all nine disagreeing cases sit on the recall side — see 3.4. - **W3:** Related-work coverage gaps in the paper's own lineage: TOGLL (LLM oracles from Javadoc with an explicit false-positive analysis) is uncited, as are the LLM-based REST API testing line (LlamaRestTest, AutoRestTest) and the classical documentation-inconsistency line (@tComment, DocRef) that Toradocu's own related work frames — see 2.4.

## Reviewer 2: Area Specialist

**Overall Recommendation:** Weak Accept

### Summary

The paper targets *documentation-implementation bugs* in vector database management systems (VDBMSs): cases where the system silently accepts an input or returns a behavior that contradicts its own API documentation (e.g., Milvus accepting `nprobe=0` against a documented `[1, 16384]` range) — failures that produce no crash and therefore escape crash-oracle fuzzers such as VDBFuzz. Because the documented constraints are natural-language prose, the authors argue that every deterministic oracle candidate (crash signals, differential/metamorphic relations, property/schema checks, structured-spec oracles) is structurally unable to derive the expectation, leaving an LLM-derived oracle as the practical option — which imports a false-positive problem, since the same model family both reads the documentation into a specification and then judges violations of it.

TestVDB is a four-stage multi-agent pipeline: (i) behavioral-specification extraction from versioned documentation with evidence tiers and source verification; (ii) test generation by boundary/state/semantic attack agents under deterministically pre-bound strategies, with scenario construction for system-level constraints; (iii) sandboxed execution against Docker-pinned targets with raw HTTP logging; and (iv) bug confirmation that splits evidence assembly (evidence builder, grounded in documentation, execution output, and implementation source) from cross-examination (chain auditor with four mechanical checks and four perspectives: contract, physical, maintainer cognition, source), where the implementation source serves as the falsification anchor independent of the documentation the specification was read from.

The evaluation reports 51 of 81 adjudicated upstream submissions confirmed by maintainers as real bugs (23 fixed via merged code-fix PRs) across Milvus, Qdrant, and Weaviate; a three-run re-adjudication of the full candidate pool showing the contract-only confirmation core intercepts 86.7–90.0% of false positives with 88.9% case-level verdict agreement, while its recall boundary (0.196–0.333) is attributed to three mechanisms; and a bidirectional comparison with VDBFuzz on Qdrant, including a full-coverage head-to-head on the same version, showing the two oracles reach complementary bug classes.

### Core Strengths

- **S1:** Demonstrated real-world impact with verified fix provenance: 51 maintainer-confirmed bugs, 23 with merged fix PRs, every fix PR classified by changed files (all modify implementation code; none documentation-only), and the classifier itself validated on the disproved case — see 1.1, 3.5.
- **S2:** The RQ2 evaluation design is methodologically careful: frozen candidate packages, judges blinded to adjudication labels and issue history, three independent runs over the full 81-case pool with a majority rule and a Wilson CI on the suppression rate — see 3.1.
- **S3:** The novelty delta against the closest competitors is real and verified: neither MASTOR (source-derived oracles) nor CASCADE (documentation-regenerated falsifier) nor SATORI (per-field OpenAPI anchoring) derives expectations from system-level prose or anchors falsification in the actual implementation source — see 2.1, 2.2, 2.3.
- **S4:** The bidirectional VDBFuzz probe is well constructed and honestly attributed, including the candid reading of the `wait=false` template miss as a template limitation rather than an oracle-class limitation — see 3.6.

### Core Weaknesses

- **W1:** The headline attribution claim — that source grounding and maintainer cognition contribute roughly +0.5 recall ("quantifies exactly where source grounding and maintainer cognition become necessary") — rests on a confounded cross-protocol comparison against a prior full-stage run affected by the paper's own disclosed biases — see 3.2.
- **W2:** Missing related work within the documentation-oracle/inconsistency line: JDoctor, @tComment/iComment, Metamon, DocChecker, and Panthaplackel et al. are uncited although the paper's target class is exactly documentation–implementation inconsistency and JDoctor belongs squarely in its "oracles derived from documentation" paragraph — see 2.4.
- **W3:** Reproducibility of the central RQ2 evidence from the text alone is not possible: the "conservative rule" that produced Table 4 is never defined, the one-run process ledger (119 chains, 70 defect-confirming) is not reconciled with the submission ledger (28 submitted, 14 confirmed for Qdrant), and the artifact link carries an unresolved TODO — see 4.2, 4.3, 3.4.

## Reviewer 3: General Reviewer

**Overall Recommendation:** Accept

### Summary

The paper targets documentation–implementation inconsistency bugs in VDBMSs: cases where the system silently accepts an input or returns a result that contradicts its own API documentation (e.g., accepting `nprobe=0` when the docs declare `[1, 16384]`). Because the expectation lives in natural-language prose, the authors argue that every deterministic oracle family (crash, differential, metamorphic, property, structured-spec) is structurally inapplicable (Table 1), forcing an LLM-derived oracle — which in turn imports hallucination, self-preference, and instability. Their system, TestVDB, is a four-stage pipeline (spec extraction from versioned docs, attack-script generation with pre-bound strategies, sandboxed execution, and a two-agent confirmation stage that builds a five-section evidence chain and audits it from contract, physical-behavior, maintainer-cognition, and implementation-source perspectives, using the source code as a falsification anchor to break the LLM-judges-its-own-oracle loop).

Empirically, across Milvus, Qdrant, and Weaviate, maintainers confirmed 51 of 81 adjudicated submissions as real bugs, 23 already fixed via merged implementation-code PRs. A frozen-package, three-run re-adjudication isolates the contract-only adjudication core and shows 86.7–90.0% false-positive suppression with 88.9% case-level agreement, while honestly quantifying a large recall boundary and attributing the residual to three named mechanisms. A bidirectional comparison against VDBFuzz, upgraded to a full-coverage head-to-head (205 templates, time limit removed, commit-matched instance), shows the two oracles reach disjoint bug classes. The evaluation is unusually self-critical: two internal-validity threats (expectation framing, observation leakage) are disclosed by name, and ground-truth fallibility is demonstrated on the authors' own disproved candidate (#9149).

### Core Strengths

- **S1:** Externally validated effectiveness on production systems — 51/81 maintainer-confirmed bugs with 23 merged fixes, all of which modify implementation code (none doc-only), plus a construct-validity check on a disproved candidate — see 1.1, 3.1.
- **S2:** Disciplined, transparent evaluation of the system's own oracle: frozen candidate packages, three independent judge runs over the full 81-case denominator, Wilson CI on suppression, zero majority-confirmed FPs, and a mechanistic account of the recall boundary — see 3.2, 3.3.
- **S3:** A clear structural-exclusion analysis (Table 1) plus a complementarity claim upgraded from a sampled probe to VDBFuzz's complete template space on a matched instance — see 1.2, 3.4.

### Core Weaknesses

- **W1:** The claim that source grounding + maintainer cognition add ≈+0.5 recall compares an 81-case contract-core protocol against a 71-case "prior full-stage run" — different populations and protocols, so the attribution is indicative, not controlled — see 3.5.
- **W2:** The disclosed observation-leakage threat is said to be "addressed" by the frozen-package protocol, yet if probe/expectation description text lives inside the transcripts the judge reads, the channel persists — see 3.6.
- **W3:** Reproducibility is currently conditional: the artifact link is an unconfirmed TODO, and the candidate funnel (119 chains → 19 unreported → submissions) plus prompts/strategy registry are not fully specified in the text — see 4.2, 4.3.
- **W4:** Single LLM backbone (GLM-5.2) and 49 still-pending submissions (≈37% of submissions) bound the generalization of both the confirmation-stage design and the precision headline — see 3.7, 3.8.

### Detailed Assessment

**1. Significance — Excellent**

- **1.1** (strength) The paper demonstrates real practical impact rather than asserting it. Section 4.2 (Table 2) reports 51 confirmed bugs across three widely deployed VDBMSs, 23 fixed via merged PRs, 50/51 carrying an official bug label, and includes concrete high-consequence instances: Milvus #49823 (boundary acceptance, Intro/§2.3), the still-live malformed-archive path-disclosure defect reproducing 4/4 on the latest release (§4.2), and Qdrant #10369 as the running example (§3.1). Since silent wrong behavior propagates into RAG outputs without any crash signal (§1 P1–P2), a tooling contribution that yields 23 upstream fixes on this bug class clears the bar for clear practical impact.
- **1.2** (strength) The research contribution is also reusable beyond the three targets: the Table 1 structural-exclusion account formalizes why documentation-derived expectation testing needs an LLM oracle, and §4.3 quantifies exactly where contract-only adjudication fails (three mechanisms, per-system concentration). This gives follow-up work a map of the oracle boundary, which is independently valuable even for teams who reject parts of the pipeline design.
- **1.3** (strength) The cost disclosure (§4.1: ≈67 active hours, ≈860 executions, ≈70M input tokens for the orchestrating session alone) lets practitioners judge deployability — a rare and welcome transparency for LLM-agent systems.

**2. Novelty — Adequate (provisional; assessed from the paper's own related-work account, no independent field survey)**

- **2.1** (strength) The paper's stated delta over the closest lines is non-obvious and internally coherent: MASTOR encodes implemented behavior and cannot detect doc–code gaps; CASCADE's falsifier is another LLM artifact generated from the same doc; the Toradocu/AugmenTest/ChatAssert/Doc2OracLL/Testora line keeps the derived oracle as final arbiter (§2.4, §6). TestVDB inverts the roles — prose supplies the expectation, implementation source is only the falsifier — and adds maintainer cognition distilled from issue history as a fourth perspective. That inversion, plus pre-bound (not LLM-chosen) attack strategies (§3.3), is a genuine architectural difference, not a repackaging, as far as the paper's own comparison goes.
- **2.2** (strength) The extraction-stage discipline (typed constraints, four evidence tiers, cited-URL containment verification with unverified evidence excluded from bug use, §3.2) is a concrete mechanism addressing the extraction-hallucination channel, and the endpoint/system-level split with an observational criterion is clearly operationalized.
- **2.3** [moderate, not fixable within this review] The overall pattern — LLM reads documentation, generates tests, an LLM-based process judges outcomes — is an established template, and the novelty resides in the disciplining architecture around it. Without an independent survey I cannot rule out concurrent work with similar builder/auditor + source-grounding designs; my Adequate rating is therefore provisional and could be understated.

**3. Soundness — Adequate**

- **3.1** (strength) Ground truth is external and hard: maintainer adjudication re-verified September 2026 (§4.1), with a robustness layer — all 23 fixes modify implementation code (15 add regression tests, none doc-only), and the disproved #9149 was correctly routed test-only by their classifier (§4.2). This directly supports the central effectiveness claim and the construct that these are implementation bugs, not documentation bugs.
- **3.2** (strength) The RQ2 design is the paper's methodological high point (§4.3, Table 4): identical frozen packages, three independent runs, full 81/81 denominator, no access to labels or issue history, conservative rule. I recomputed the arithmetic: per-run suppression 26/30=0.867 and 27/30=0.900 matches the quoted 0.867–0.900; precision 17/21=0.810, 10/13=0.769, 12/16=0.750 matches 0.750–0.810; per-run TP+FN=51 and leaked+TN=30 hold in every row. [Patched during review: the snapshot I read asserted "not one FP ever confirmed by majority," which conflicted with the majority row (FP=4); the authors corrected §4.3 during this review round — the text now states three unanimous and one two-to-one misconfirmations, which matches the table, and the nine-disagreement sentence now reads "eight true bugs + one two-to-one false positive," also matching the data.]
- **3.3** (strength) The recall side is reported as a boundary, not buried: per-run recall 0.196–0.333, all nine case-level disagreements on the recall side, three named mechanisms with per-system concentration (§4.3). This honesty substantially raises the credibility of the headline numbers.
- **3.4** (strength) RQ3 was upgraded from an asserted structural argument to a measured one: the full-coverage head-to-head runs VDBFuzz's complete 205-template space on a commit-matched v1.18.0 instance with the time limit removed entirely (50.8 min, within its own 120-min protocol), yielding zero crashes and zero reaches (§4.4). Removing the budget confound is the right fairness move, and the paper correctly notes the residual result is near-definitional for a crash oracle.
- **3.5** [moderate, fixable] The attribution claim "source grounding + cognition contribute ≈+0.5 recall at essentially unchanged precision" (§4.3) is derived by comparing the 81-case frozen-package contract core against a *prior full-stage run on a 71-case subset* — different population, different protocol, different point in the project's history. Subset composition could easily shift recall by more than the claimed margin. A controlled rerun of the full stage on the same 81 frozen packages would make this a measured result rather than a cross-experiment inference.
- **3.6** [moderate, fixable] §5 discloses observation leakage ("probe description text enters judge observations unsanitized") and then states both threats are "addressed by frozen-package RQ2 protocol (judge sees only transcripts+contracts)". If probe descriptions live inside the transcripts, the frozen-package protocol constrains what the judge sees but does not remove this specific channel, and "addressed" overstates it. Mitigating factor: the plausible bias direction (expectation framing pushes toward confirmation) would *lower* measured FP suppression, so the 0.867–0.900 headline is conservative under this bias; the recall-side comparison is more exposed. Sanitizing transcripts and rerunning would settle it.
- **3.7** [moderate, not fixable short-term] All results use a single backbone (GLM-5.2, default sampling; §4.1, §5 External). The confirmation stage is the paper's core intellectual claim, and its dependence on the model family is unquantified — the evidence-chain design plausibly mitigates self-preference, but cross-family variance in extraction quality and judge calibration remains unknown.
- **3.8** [minor, not fixable] 49 of 130 submissions await maintainer response and are excluded from all rates (§4.2, §5), so the 63.0% precision figure is an adjudicated-subset statistic — disclosed, but it leaves open whether pending items skew toward either tail. Relatedly, per-system triage asymmetry (25/29 Milvus accepted vs 5/14 Qdrant accepted, §4.2) means cross-system confirmation comparisons partially measure maintainer responsiveness, not just defect quality; the paper reports the numbers but does not discuss this asymmetry.

**4. Verifiability — Adequate**

- **4.1** (strength) The procedural description is unusually deep for a systems paper: specification record fields including `evidence_tier` and `source_verified` (§3.2), the registry/pre-binding mechanism and five named generation gates (§3.3), execution artifacts (raw logs, atomic `.done` markers, count verification, §3.4), the `verification_outcome` taxonomy and five-section evidence chain (§3.5), and a full single-run process ledger (§4.2). The main flow is reproducible in concept from the text alone.
- **4.2** [moderate, fixable] The replication package (agent role definitions, per-version knowledge bases, scripts with raw HTTP logs, evidence chains, ledger) is declared but the anonymous link is explicitly a remaining TODO (Data Availability). Until the artifact is live, the paper's verifiability rests entirely on the prose, which is strong but not sufficient for the level of numeric claims made.
- **4.3** [moderate, fixable] The candidate funnel is not fully traceable in the text: §4.2's process ledger reports 119 evidence chains adjudicated and 19 candidates cleared as unreported at first pass for one Qdrant run, but the selection rules from chains/cleared candidates to the 81 submissions in Table 2 (and the role of the novelty gate's two word-level false positives) are not specified. Exact prompts, judge rubric wording, and the strategy registry contents are likewise absent — acceptable only if the artifact (4.2) ships them.

**5. Presentation — Adequate**

- **5.1** (strength) The argument arc is clean and each RQ maps to a specific claim: RQ1 effectiveness, RQ2 oracle self-evaluation, RQ3 complementarity. The quantitative reporting is largely cross-consistent — I verified Table 2 row/column sums (81/51/23/30), the bug-status partition (23+18+7+3=51), the category table summing to 51 (§4.2, Table 3), and all Table 4 derivations (see 3.2). This level of arithmetic coherence is not universal in this genre and supports trust.
- **5.2** [minor, fixable] Table 4's "FP-leaked" column benefits from a one-line definition in the caption (per run: false positives this run confirmed; for the majority row: false positives the ≥2/3 vote confirms). The textual contradiction this column exposed in the reviewed snapshot was corrected during the review round (see 3.2 patch note).
- **5.3** [minor, fixable] The 71-case subset invoked in §4.3 ("prior full-stage run") appears without provenance — which population it was drawn from, and why 71 of 81 — which weakens the +0.5-recall comparison (see 3.5) as well as readability.
- **5.4** [minor, fixable] The abstract is long and parenthesis-dense, and much of the body inherits the compressed "P5-style" enumeration style; individual sentences frequently carry three or more claims (e.g., the single-sentence process ledger in §4.2). Content is complete, but reader effort is high.
- **5.5** [minor, fixable] The remaining TODO in Data Availability ("confirm anonymized artifact link before submission") must be resolved before camera-ready; a placeholder in a submitted manuscript undermines the verifiability section it accompanies.
