# TestVDB — Three-Reviewer Peer Review (2026-09-12, round 8; paper rev: post-RQ2 audit/rebuild/protocol realignment)

## Reviewer 1: Domain Expert

**Overall Recommendation:** Weak Accept

### Summary

The paper targets *documentation–implementation bugs* in vector database management systems (VDBMSs): silent failures where the system accepts an input or returns a result that contradicts its own API documentation, with no crash. Because the only source of the expectation is untagged natural-language prose, the authors argue every deterministic-oracle family anchors its expectation elsewhere (Table 1), leaving an LLM-derived oracle as the practical option — which imports a false-positive problem. Their system, TestVDB, is a four-stage pipeline (specification extraction, strategy-bound test generation, sandboxed execution, bug confirmation) whose confirmation stage cross-examines a five-section evidence chain from four perspectives, with the implementation source — not another LLM artifact — as the falsification anchor.

Operationally, maintainers confirmed 51 of 81 adjudicated submissions as real bugs (23 fixed via merged PRs) across Milvus, Qdrant, and Weaviate. For RQ2 the authors audited their own frozen evidence packages (43.3% of 134 cited constraint–page pairs unsupported), rebuilt all 81 packages against version-pinned documentation, and re-adjudicated the full pool three times under five judge arms: the contract-only core recalls 0.137 at 0.967 suppression; the full structured stage recalls 0.804 at 0.800 suppression; a flat single-prompt judge with the same evidence reaches 0.588, with the full-vs-flat separation surviving Holm correction. RQ3 probes VDBFuzz bidirectionally: run over its entire released Qdrant template space, the crash oracle reaches none of TestVDB's silent-accept defects, while TestVDB's boundary reasoning reaches VDBFuzz's crash-class integer overflow, confirmed by hand on v1.4.0.

### Core Strengths

- **S1:** Measurement transparency of the RQ2 redesign: the audit/rebuild/protocol-alignment layering isolates one variable per layer and reports all three — see 3.1.
- **S2:** Real operational yield with anti-inflation checks: 51 maintainer-confirmed bugs, a fix-PR classifier validating that all 23 fixes modify implementation code, and duplicate/novelty handling — see 1.1, 1.2.
- **S3:** The novelty delta is real and honestly positioned against the closest competitors (MASTOR, CASCADE, SATORI, AGORA+, VDBFuzz), all of whose characterizations I verified against their own texts — see 2.1–2.4.

### Core Weaknesses

- **W1:** Multiple internal numeric inconsistencies survive into the revised text, including one substantive contradiction about the evidence composition of the 51 true bugs — see 3.2, 3.4, 3.5.
- **W2:** The headline full-stage recall is scored with Human-Review verdicts counted as confirmed; no forced-verdict-only sensitivity is given, and the abstract's 21% review-routing rate contradicts the body's 10.4% — see 3.3.
- **W3:** The central McNemar comparison is internally unreconcilable with the reported confusion tables — see 3.4.

### Detailed Assessment

1. **Significance** — Adequate
   - **1.1** The problem is real and the impact is demonstrated, not asserted: Table 2 reports 51 maintainer-confirmed bugs (63.0% of 81 adjudicated) with 23 merged fix PRs, and the fix-nature audit (Section 4.2, "Fix nature") verifies every fix PR modifies implementation code, 15 add regression tests, none is documentation-only. Upstream fixes landing in following releases for two defects corroborate. This is a meaningful, bounded contribution to a previously oracle-less bug class.
   - **1.2 [minor, fixable]** Impact is bounded by scope: three systems, one LLM family for the main arms (Section 5, "External validity"), and the prose-constraint regime only. The authors delimit this honestly; the significance claim should stay scoped accordingly.

2. **Novelty** — Adequate
   - **2.1** Checked the delta against MASTOR (cached summary + prior full read, arXiv 2606.10465): the paper's claim that MASTOR "encodes implemented behavior and cannot detect a documentation-code gap" holds verbatim in MASTOR's own §7.4.2 ("cannot detect violations of intended requirements that are not reflected in code"), and MASTOR demotes OAS claims not substantiated in source to `pending` — source is the authority. TestVDB's anchor inversion (prose as ground, source as falsifier) is therefore a real, non-obvious inversion, and the paper correctly concedes that LLM reviewer agents (MASTOR's ChallengerAgent) and cross-request behavioral oracles are not new by themselves.
   - **2.2** Checked SATORI (ASE 2025) and AGORA+ (TOSEM 2026, fetched this review): the paper's scoping — SATORI yields response-field oracles from OAS fields, AGORA+ infers invariants from observed traffic — matches both texts (SATORI: per-response-field prompts, 17 unary oracle types; AGORA+: Daikon-style invariants over request/response corpora, 106 types, precision 80% at 10K requests). One nuance the paper should not blur: AGORA+'s 32 bugs did trigger documentation updates, so trace-anchored oracles do surface *some* spec/doc mismatches — but all on the response-property side, never input-acceptance/state conformance. The paper's residual claim survives only under the input-acceptance/state scoping it actually states; keep that scoping explicit.
   - **2.3** Checked CASCADE (FSE 2026): the quoted residual-FP analysis ("the generated code and tests made the same false assumption over something underspecified in the documentation") matches CASCADE's own evaluation verbatim. The falsifier-independence argument (CASCADE's falsifier is another LLM artifact sharing the documentation's ambiguity; TestVDB's is the implementation source) is verified and is the paper's sharpest positioning point.
   - **2.4** Checked VDBFuzz (ICSE 2026, cached artifact facts): crash-oracle-by-design is confirmed by its own stated limitation; the RQ3 artifact numbers (205 Qdrant templates per `generation_summary.json`, `dim = 2**63` PoC, three Qdrant crashes with one narrated case study) all check out. The complementarity claim is measured in both directions rather than asserted — commendable.
   - **2.5 [minor, fixable]** The pipeline packaging (multi-agent roles, strategy registries, builder/auditor split) is recognizable from current agentic-LLM practice; the novelty rests on the inversion plus the measured confirmation-stage mechanism. The paper says as much (Section 4.3, "Structure is a measured mechanism"); the framing should not drift back toward architectural novelty.

3. **Soundness** — Adequate
   - **3.1** The RQ2 measurement design is the strongest part of the paper: Layer 0 audits the shipped packages (43.3% of 134 cited pairs unsupported — 58/134 checks out; four provenance leaks found and removed), Layer 1 rebuilds all 81 packages version-pinned, Layer 2 aligns the judging protocol with the deployed rules and names the two recall-suppressing pre-deployment rules it removed. Five arms re-adjudicate the identical pool three times under blinding; Wilson intervals and Holm correction are reported; a second backbone replicates the source-only arm; a seeded 32-candidate sample anchors the submission filter's direction. The stratified analysis (37/3/11 evidence strata summing to 51, recalls 0.784/0.667/0.909 decomposing exactly to the 41 majority TPs) is internally consistent and genuinely explanatory.
   - **3.2 [major, fixable]** Direct internal contradiction about evidence composition: the contract-core paragraph (Section 4.3) states "37 of the 51 true bugs violate semantics the packages record only as behavioral inference, not checkable assertions", while the stratification paragraph states "The 37 evidence-present packs (a verifiable contract row)" — the same 37 cannot be both "no checkable assertion" and "a verifiable contract row", and the stratification (37+3+11=51) is the version consistent with the rest of the arithmetic. One of the two 37s is a stale carry-over; the "assertion-framework floor" narrative depends on which.
   - **3.3 [major, fixable]** Human-Review scoring shapes the headline without a sensitivity analysis: full-stage recall 0.804 counts Human-Review verdicts as confirmed (Section 4.3, "Arms and adjudication"); 17 of its 41 confirmations carry at least one Human-Review component, and the flat judge has no such channel. The paper discloses the convention and its rationale, but the full-vs-flat comparison is partly an artifact of the routing convention, and no forced-verdict-only sensitivity is reported (the 24 all-component confirmations are given, but the comparison is not re-run under that scoring). Compounding this, the abstract and introduction claim "21% of full-stage verdicts route to review" while Section 4.3 and Section 5 state 10.4% — two different numbers for the same construct, no reconciliation of denominators.
   - **3.4 [major, fixable]** The central paired test does not reconcile with its own tables: Section 4.3 reports the full stage beats the flat judge on 18 paired cases and loses on 3 (McNemar p=0.0013, Holm p=0.0030), yet majority-vs-majority TP difference is 41−30=11, not 18−3=15. Additionally, the exact two-sided McNemar p for 18/3 is 0.00149 (which Holm-corrected ×2 gives exactly the reported 0.0030), so the quoted raw p=0.0013 appears stale. Either the discordant counts or the confusion tables are wrong; as printed, the paper's flagship statistic cannot be recomputed from its own inputs.
   - **3.5 [minor, fixable]** Arithmetic slips that a careful pass should catch: (a) Section 4.2 "Bug status": 23 fixed + 18 open + 7 closed = 48, not 51 — three confirmed bugs are unaccounted for (the duplicate-tracked three are claimed "orthogonal" to this breakdown, which makes the shortfall worse, not better); (b) Section 4.3 Layer 1: 2,106 − 674 (endpoint filtering) − 463 (evidence verification) = 969, not the stated 674 rebuilt rows (though 22+652=674 is internally consistent, so one addend is wrong); (c) "The suppression cost relative to the core is exactly six cases" contradicts Tables 4–5: core TN 29 → full TN 24 is five (the 4+2 decomposition also sums to six); (d) RQ3 footnote: 65,536 vs the 2^62 overflow threshold is ~14 orders of magnitude, not "four"; (e) the audit's "(58 constraint rows)" is actually the pair count (0.433×134≈58), mislabeled.
   - **3.6 [minor, fixable]** Ground truth is maintainer adjudication, fallible in both directions — the #9149 episode (a "fixed" TP disproved by the authors' own seven-version re-probe) proves diligence and noise at once. The submission-filter direction argument is qualitative; the seeded 32-candidate anchor (0.594, Wilson [0.423, 0.745]) helps but is measured under the pre-audit protocol and so is only directional, as the paper itself states.
   - **3.7** RQ3's negative results are carefully bounded: the zero is measured over 22,540 mutations with a substituted per-template liveness oracle after showing the released counters cannot fire (the no-server control is a nice touch), and the paper correctly narrows the conclusion to the released configuration (integer boundaries top out at 65,536; recovered panics are invisible to a liveness oracle). The withdrawn "synchronous-path-only" explanation is handled with exemplary candor.
   - **3.8 [minor, fixable]** The operational run's process ledger (Section 4.2) reports 119 chain verdicts with "none unresolved", which sits oddly with a deployed protocol whose Human-Review channel routes 10.4–21% of verdicts to review (Section 4.3). Clarify whether the ledger counts post-human-resolution verdicts or a different protocol vintage.

4. **Verifiability** — Excellent
   - **4.1** The replication package (Data Availability) is declared and, per its contents list, comprehensive: the submission ledger including all 49 unadjudicated submissions, original and rebuilt RQ2 packages with audit verdict records and per-case judge outputs for every arm and run, RQ3 per-template logs, and analysis scripts that recompute every reported rate, interval, and paired test. The text itself is detailed enough to follow the protocol end to end; combined with the artifact this meets the bar for full checkability.
   - **4.2 [minor, fixable]** The backbone is identified by serving identifier and date (GLM-5.3-Flash, September 2026) rather than a pinned weights snapshot; exact replication of judge behavior is therefore not possible even with the artifact. Disclosed, and the right disclosure to make.
   - **4.3 [minor, fixable]** Given the inconsistencies in 3.2–3.5, the recomputation scripts are not merely good practice but the acceptance condition: every number in Section 4 should be re-issued from them after reconciliation.

5. **Presentation** — Adequate
   - **5.1** The paper is dense but navigable, and the tables are built so the arithmetic can be cross-checked — which is how the inconsistencies above surfaced. Figures/tables are complete and the running example (#10369) threads effectively through all four stages.
   - **5.2 [minor, fixable]** Prose is overloaded with em-dash-chained parentheticals, especially in Sections 1 and 4.3; several sentences carry three or more nested qualifications. A tightening pass would not lose content.
   - **5.3 [minor, fixable]** Section 3.2: "coverage self-check 98.6%, two gaps flagged" — state the denominator (98.6% of what; why two gaps do not imply 97.5%).
   - **5.4 [minor, fixable]** Table 1 row 1 embeds a study result ("only 2 of the 51 maintainer-confirmed bugs...") inside what is otherwise a definitional analysis table; the audit paragraph's "% of pairs" vs "(58 constraint rows)" labeling should be fixed (see 3.5e).

### Questions for Authors

- **Q1:** How do 23 fixed + 18 open + 7 closed account for only 48 of the 51 confirmed bugs (Section 4.2, "Bug status")? — Clarifying would resolve item 3.5a; if the three duplicate-tracked bugs are outside the breakdown, the "orthogonal" sentence must be corrected instead.
- **Q2:** Which is correct: 37 true bugs with only behavioral-inference evidence (Section 4.3, contract-core paragraph) or 37 evidence-present packs with verifiable contract rows (Section 4.3, stratification)? — One figure is stale; item 3.2's rating, and part of the contract-core narrative, depends on it.
- **Q3:** The suppression cost from core (TN 29) to full stage (TN 24) is five cases, but the text says "exactly six" with a 4+2 decomposition (Section 4.3). — If one of the six was also missed by the core, say so; this affects item 3.5c only.
- **Q4:** Reconcile the abstract's 21% review-routing rate with the body's 10.4% (Section 4.3, Section 5), and report the full-vs-flat comparison under forced-verdict-only scoring (Human-Review = not confirmed). — If the full stage still separates from the flat judge without the routing convention, item 3.3 would move up; if not, the contribution claim must be reworded.
- **Q5:** For the flagship McNemar test: how do 18 wins / 3 losses square with the 41-vs-30 majority TP difference (difference 15 vs 11), and is the raw p 0.0013 or 0.0015 (18/3 exact two-sided)? — A corrected, recomputable test resolves item 3.4; the Holm-corrected 0.0030 is consistent with 0.0015×2, suggesting the raw value is the typo.

# Reviewer 2 (Area Specialist) — Draft Review

Expertise: (1) LLM-based test oracle generation; (2) database software testing.
Competitors checked this run (cached summaries read): VDBFuzz (ICSE 2026), MASTOR (arXiv 2026), Metamon (LLM4Code 2025), CASCADE (PACM SE 2026), SATORI (ASE 2025); coverage search added MASTEST (IEEE AITest 2026, uncited).

## Reviewer 2: Area Specialist

**Overall Recommendation:** Accept

### Summary

The paper targets *documentation-implementation bugs* in vector database management systems (VDBMSs): cases where the system silently accepts an input or exhibits behavior that contradicts its natural-language API documentation, with no crash for a crash oracle to fire on. Because the documented constraints live in untagged prose rather than in any structured source, the authors argue that every deterministic-oracle family (crash, differential, metamorphic, property-based, schema- or trace- or source-derived) anchors its expectation elsewhere, leaving an LLM as the only practical reader of the prose — at the price of the LLM's false-positive problem.

TestVDB answers with a four-stage pipeline: documentation is distilled into typed, source-verified behavioral specifications; pre-bound attack strategies turn each constraint into executable probes; a sandbox runs the probes against Docker-pinned versions while logging raw HTTP traffic; and a confirmation stage splits evidence assembly (evidence builder) from cross-examination (chain auditor, four perspectives, implementation source as the falsification anchor). In an operational deployment across Milvus, Qdrant, and Weaviate, maintainers confirmed 51 of 81 adjudicated submissions as real bugs and fixed 23 via merged PRs. Because an audit found 43% of the evidence packages' cited constraints unsupported by the pages they cite, the authors rebuilt all packages against version-pinned documentation and re-adjudicated the full pool three times under five judge configurations: the contract-only core recalls 0.137 at 0.967 suppression, the full structured stage reaches 0.804 recall at 0.800 suppression, and a flat single-prompt judge with the same evidence access reaches 0.588, with the full-vs-flat separation surviving Holm correction. A bidirectional probe against VDBFuzz on Qdrant shows complementary reach in both directions.

### Core Strengths

- **S1:** The confirmation-stage evaluation is unusually self-critical and methodologically solid: a three-layer audit/rebuild/protocol-realignment design that isolates one variable per layer, five judge arms over the same 81 candidates in three runs each, Wilson intervals, exact McNemar with Holm correction across seven paired tests, stratified recall, and a seeded re-adjudication of 32 never-submitted registrations to anchor the submission-filter direction — see 3.1, 3.2.
- **S2:** The bug yield is real and validated beyond label counting: 51 maintainer-confirmed bugs with 23 merged fix PRs, every fix PR verified by changed-file classification to touch implementation code (with the classifier itself validated on the disproved #9149 PR) — see 1.1.
- **S3:** The oracle-exclusion analysis (Table 1) plus the evidence-absent stratum result give the field a reusable criterion — where an oracle's expectation anchors — and quantify the motivating asymmetry: the 11 packs with no verifiable contract entry yield 0.909 recall for the full stage while the contract core scores 0.000 on them, i.e., documentation constrains a minority of the defect surface — see 1.2, 1.3.
- **S4:** The RQ3 comparison is instrumented rather than asserted: the authors discovered the released VDBFuzz runner's success counters cannot fire its failure markers (100% "success" against a dead port), substituted a liveness oracle, and bounded their conclusions to the released configuration, including the recovered-panic-vs-service-death distinction — see 3.3, 3.8.

### Core Weaknesses

- **W1:** The headline mechanism claim (structured stage > flat judge, p=0.003) is a single-backbone result; the only cross-family replication (source-only on Qwen) no longer separates from the flat judge after Holm correction, and full-vs-source-only is indistinguishable on the primary family — the abstract and contributions state the advantage without the single-family qualifier — see 3.4.
- **W2:** The Human-Review-counts-as-Confirmed convention carries a large share of the full stage's recall (17 of 41 confirmations include an HR component), and no sensitivity analysis is given; the abstract's "21%" review-routing figure conflicts with Section 4.3's "10.4%" without reconciliation — see 3.5.
- **W3:** Ground truth is maintainer adjudication of author-written issue reports (unblinded on the positive side), the operational ledger cumulates mining rounds across two backbone generations since early 2026, and the process funnel is reported only at two measured points — all disclosed, but together they mean the RQ1 yield is not attributable to a single configuration and inherits author-side selectivity — see 3.6, 3.7.

### Detailed Assessment

1. **Significance** — Excellent
   - **1.1** (strength) The problem is quantified, not just asserted: Table 3 shows the acceptance family (Silent-Accept, Type-Coercion, Silent-Ignore) accounts for 37 of 51 confirmed bugs (72.5%), and Section 4.2's fix-nature classification verifies all 23 "fixed" bugs have merged PRs that modify implementation code, none documentation-only. Practical impact on three production systems is direct and demonstrated: maintainers accepted, labeled, and fixed these bugs. This satisfies the "clear practical impact on a real problem" anchor.
   - **1.2** (strength) Table 1 and Section 2.3 give the field a reusable analytical criterion — where each oracle candidate anchors its expectation — and correctly delimit the residual (system-level, untagged behavioral prose) where an LLM reader is forced. This framing organizes a scattered literature (crash fuzzers, differential engines, MR/property tools, OAS/trace/source-derived REST oracles, tagged-Javadoc miners) into one axis and is citable independently of the pipeline.
   - **1.3** (strength) The evidence-absent stratum finding (Section 4.3, "Where recall lives") is a transferable research insight: 37 evidence-present packs yield full-stage recall 0.784 while the 11 packs where documentation simply does not constrain the behavior yield 0.909 — the objective-constraint classes, not the prose, carry recall exactly where prose is absent. This quantifies, rather than illustrates, the paper's central asymmetry.
   - **1.4** [minor, fixable] The impact is bounded in two disclosed ways: the operational 51-bug ledger is a human-machine pipeline number (author-side novelty screening and the submission decision sat in the loop, Section 4.2 final paragraph), and claims are scoped to prose-constraint API regimes (Section 5, external validity). The scoping is honest; a one-sentence statement in the abstract that the headline yield is a pipeline-with-humans figure would prevent over-quotation.

2. **Novelty** — Adequate
   - **2.1** (strength) The anchor inversion — prose as ground, implementation source as falsifier — is a genuine, non-obvious delta over the closest prior work I checked against their own texts: MASTOR grounds oracles in source and states in its own limitations that it "cannot detect violations of intended requirements that are not reflected in code"; CASCADE's falsifier is code regenerated from the same documentation (and its own residual false positives arose from the shared false assumption, which the paper quotes accurately); Metamon's falsifier is another LLM question over the same judge model family; SATORI and AGORA+ anchor in OAS fields and traces. The paper's characterizations of all five are accurate, and its positioning of Metamon as same-tradeoff-different-pool rather than a head-to-head baseline is fair.
   - **2.2** [minor, fixable] The individual mechanisms are largely known: LLM specification extraction, multi-agent pipelines, builder/judge separation (MASTOR's specialist-plus-ChallengerAgent with deterministic normalization at temperature 0 is structurally close), source-code cross-checking of doc claims (the iComment/DocRef line), and cross-request behavioral oracles. The paper concedes this in Section 6 ("A generated oracle reviewed by a second LLM agent is therefore not new here"), which is the right call; the residual novelty is the inversion plus the measured protocol effect, and Section 6 could state in one sentence which protocol elements are claimed as new (I read it as: perspective B's objective-constraint classes and the fixed three-valued aggregation).
   - **2.3** [minor, fixable] Table 1's row-5 exclusion ("anchored in structured sources") and the Section 6 framing slightly overstate the untouched residual: SATORI's reported bugs include specification–response mismatches — a form of documentation-implementation inconsistency where the prose lives in OAS descriptions — so the SATORI line reaches a subset of the residual class. The paper's own hedge (row 4, "several endpoints serve no schema") partially covers this; one sharper sentence would close the gap.
   - **2.4** [minor, fixable] One recent competitor is missing: MASTEST (Han and Zhu, IEEE AITest 2026; arXiv:2511.18038), a multi-agent LLM pipeline from OpenAPI spec to executed, human-reviewed API tests. It anchors in the structured spec, so it belongs in row 5 of the paper's own taxonomy; a one-sentence citation suffices and would preempt an easy reviewer objection elsewhere.

3. **Soundness** — Adequate
   - **3.1** (strength) Section 4.3's measurement design is the paper's methodological high point. Layer 0 audits the shipped packages (43.3% of 134 cited (constraint, page) pairs unsupported, 32% of rows off-endpoint, four provenance leaks) and attributes every defect to the assembler, not the stage; Layer 1 rebuilds all 81 packages with page citations, source-type labels, and evidence tiers (674 surviving rows of 2,106, honestly reported as 22 explicit vs. 652 inferred-from-behavior); Layer 2 realigns the judging protocol to the deployed rules after finding two pre-deployment rules that suppressed recall by construction. Reporting all three layers converts what could have been one opaque number into an attribution.
   - **3.2** (strength) The RQ2 protocol is rigorous: five arms re-adjudicating the identical 81-candidate pool in three independent runs under blinding (leakage measured, not assumed — 19 expectation-flavored phrases, all inside verbatim server responses), majority voting, Wilson intervals on every headline rate, exact McNemar with Holm correction across all seven paired tests, stratified recall by evidence presence, and the seeded 32-candidate never-submitted anchor with its own Wilson interval. The three-valued verdict and the two senses of "false positive" are carefully kept apart.
   - **3.3** (strength) The RQ3 instrumentation is exemplary for baseline comparisons: the authors read the released runner, found the failure markers unreachable (one emitted by no code path, one mismatched against actual template messages), validated the consequence with a dead-port experiment, substituted a per-template liveness oracle, and reported full traffic counts (22,540 mutations; 23,258 responses over 96 paths) so the zero is verifiably measured rather than a silent no-op. They also withdraw their own earlier, wrong explanation for VDBFuzz's silence on #9045 — commendable.
   - **3.4** [major, fixable] The central mechanism claim is under-replicated. The abstract and contribution 2 state that "the structured protocol's advantage survives Holm correction (p=0.003)" with no qualifier, but this full-vs-flat separation is measured on a single LLM family; the one cross-family replication (source-only on Qwen, Section 4.3 "Backbone replication") reaches 0.706 recall yet "does not separate from the flat judge after Holm correction (p=0.10)", and on the primary family the full stage is indistinguishable from source-only (p=0.42). The paper discloses every one of these facts, but the headline sentence outruns them: what survives correction is structure-beats-flat on one backbone, with structure-beats-source-only unestablished on any backbone. A revision should either re-run the full-vs-flat pair on the second family or qualify the abstract/contribution claims to the measured scope.
   - **3.5** [minor, fixable] The scoring convention does quiet work: Human-Review verdicts count toward Confirmed in every rate, and 17 of the full stage's 41 confirmations carry at least one HR component — the 0.804 headline is materially supported by cases the automated stage routed to a human. The deployment-faithful justification (Section 4.3, "Arms and adjudication") is defensible, but no sensitivity row (HR-as-non-confirm) is given, so the reader cannot see how much of the 0.804-vs-0.588 gap survives the alternative convention. Separately, the abstract says 21% of full-stage verdicts route to review while Section 4.3 says 10.4% — presumably per-run verdicts vs. case-level majority, but the two numbers are never reconciled and currently contradict each other as written.
   - **3.6** [minor, fixable] Ground truth is maintainer adjudication of author-written issues: the 51 positives were confirmed by maintainers who saw the authors' framing and evidence (no blinding is possible on that side), and the authors themselves disproved one of their own confirmed-and-fixed candidates (#9149) by re-probe — proof that the arbiter is fallible in both directions. The limitations section handles this honestly and the two stage-vs-adjudication conflicts are properly labeled as arbiter disagreements; a double-adjudication of even a small sample of the 51 positives by an independent maintainer contact would materially strengthen the denominator.
   - **3.7** [minor, fixable] The RQ1 ledger aggregates mining rounds accumulated since early 2026 on GLM-5.2 with the reported run on GLM-5.3-Flash (Section 5, external validity), and the end-to-end funnel of the reported run is reported at only two measured points (119 chain verdicts; 96 candidates → 60 defects → 44 post-gate → five registrations), with the many-to-one steps uncounted by the authors' own admission (Section 4.2, "Process ledger"). Both disclosures are appropriate, but the consequence — the yield is not attributable to one pipeline configuration, and per-stage funnel losses are unknown — deserves one explicit sentence in the evaluation rather than only in limitations.
   - **3.8** (strength) The RQ3 conclusions are drawn at exactly the width the evidence supports: the complementarity claim rests on the released configuration only; the reverse-direction confirmation is labeled a hand-executed probe whose PoC value was chosen with knowledge of VDBFuzz's case study; and the footnote distinguishes recovered panics from service death so the liveness oracle's reach is not overstated.

4. **Verifiability** — Excellent
   - **4.1** (strength) The Data Availability statement declares an anonymous artifact whose enumerated contents map one-to-one onto the paper's evidence: agent role definitions and the strategy-trigger registry, per-version knowledge bases and specifications, all generated scripts with raw HTTP logs, one evidence chain per candidate, the submission ledger (including the 49 unadjudicated submissions), original and rebuilt RQ2 packages with audit verdict records and per-case judge outputs for every arm and run, RQ3 baseline reports with per-template logs, and analysis scripts that recompute every rate, interval, and paired test. Judged from the text, the link is declared and the contents are sufficient to check the work.
   - **4.2** (strength) The text is close to self-contained even without the artifact: the confirmation protocol's decision rules are quoted (three-valued verdict, fixed aggregation order, perspective B's seven objective-constraint classes with the ef/nprobe carve-out, perspective C's verbatim-intent-evidence requirement), every target version is pinned, the cost profile and serving identifiers with run dates (GLM-5.3-Flash, September 2026; GLM-5.2 for earlier rounds) are disclosed, and the RQ2 term vocabulary (candidate, pack, case, leak) is defined once and used consistently.
   - **4.3** [minor, fixable] The judging prompts themselves are not in the text (only role definitions are declared in the artifact), and the flat-judge prompt is never characterized beyond "single prompt with the same inputs"; since the paper's central statistical comparison is full-vs-flat, a compact appendix quoting both prompts would let readers assess prompt-sensitivity without the artifact.

5. **Presentation** — Adequate
   - **5.1** [minor, fixable] The abstract is a single ~380-word block that carries nested method-asides; the sentence "An audit of the frozen evidence packages ... found 43% of their cited constraints unsupported ...; after rebuilding every package ... and re-adjudicating the full pool three times under the deployment protocol, the structure of the stage is what the numbers resolve" is nearly unparseable on first read (what resolves what?). Split into two sentences and state the finding plainly.
   - **5.2** [minor, fixable] Section 4.3 is the densest section in the paper: the measurement-design paragraph alone runs several hundred words interleaving three layers, five arms, leak handling, and four term definitions (candidate/pack/case/leak); a three-row layer table and a short glossary would cost little space and read much easier.
   - **5.3** [minor, fixable] The process-ledger paragraph in Section 4.2 reports 119 chain verdicts → 96 candidates → 60 defects → 19/11/5/25 gate partition → 44 → "register five new defect numbers" with no funnel figure; the reader cannot reconstruct the arithmetic (the authors admit no per-step counts are maintained, but a small figure of the two measured points would still orient the reader).

## Reviewer 3: General Reviewer

**Overall Recommendation:** Weak Accept

### Summary

The paper targets *documentation-implementation bugs* in vector database management systems (VDBMSs): cases where the system silently accepts an input or returns a behavior that contradicts its natural-language API documentation, producing no crash and therefore escaping crash-oracle fuzzers like VDBFuzz. Because the expectations for such checks live in untagged prose that no deterministic oracle family reads, the authors argue an LLM must serve as the oracle, which imports a false-positive problem. Their system, TestVDB, is a four-stage pipeline: behavioral specification extraction from documentation, strategy-bound test generation, Docker-pinned sandboxed execution with raw HTTP logging, and a bug-confirmation stage that splits evidence assembly from a chain auditor cross-examining each candidate from four perspectives, with the implementation source as the falsification anchor.

Empirically, maintainers confirmed 51 of 81 adjudicated upstream submissions as real bugs (23 fixed via merged PRs) across Milvus, Qdrant, and Weaviate. The revised RQ2 re-adjudicates this whole pool under blinding after an audit found 43% of the originally assembled evidence packages' cited constraints unsupported: on rebuilt packages, the contract-only core recalls 0.137 at 0.967 suppression, the full structured stage recalls 0.804 at 0.800 suppression, and a flat single-prompt judge with the same evidence access reaches 0.588, with the full-vs-flat difference surviving Holm correction (McNemar p=0.0013, corrected p=0.003). A bidirectional probe against VDBFuzz on one Qdrant version shows the crash oracle reaches none of the paper's silent-accept defects across its full 205-template space, while TestVDB's boundary reasoning reaches VDBFuzz's crash-class integer overflow by hand on an older version.

### Core Strengths

- **S1:** Upstream validation is unusually concrete: 51 maintainer-confirmed bugs with 23 merged fix PRs, each fix PR classified by changed files to rule out documentation-only "fixes" — see 1.1, 3.1.
- **S2:** The RQ2 measurement corrects itself in three named layers (audit, rebuild, protocol alignment), each isolating one variable, and the judging arms differ only in what the judge sees — see 3.1.
- **S3:** Candor about the measurement's limits: submission-filtered pool, Human-Review-counts-as-confirmed convention, two protocol-vs-adjudication conflicts named, a previously published wrong explanation withdrawn in RQ3 — see 3.5, 3.6.
- **S4:** The RQ3 complementarity probe audits the baseline's own counters rather than trusting a zero, and bounds its conclusion to the released configuration — see 3.5.
- **S5:** A real bug is threaded through all four pipeline stages as a worked example, which makes the mechanism followable for a non-specialist — see 5.1.

### Core Weaknesses

- **W1:** A cluster of internal numeric inconsistencies that a careful reader cannot reconcile, including a direct contradiction between the abstract/intro (21% of full-stage verdicts route to human review) and the RQ2/limitations text (10.4%) for the same quantity — see 3.2.
- **W2:** The paper's central comparison (structured stage vs. flat judge) is single-LLM-family; the only cross-family replication (source-only on Qwen) fails to separate from the flat judge after correction, so "structure is a measured mechanism" is established on one backbone — see 3.3.
- **W3:** The size of the full stage's advantage over the flat judge is not decomposed between the objective-constraint perspectives and the explicit human-review escape channel, so the mechanism attribution behind the 0.804-vs-0.588 gap is partially open — see 3.4.

### Detailed Assessment

1. **Significance** — Adequate
   - **1.1** The practical impact claim is backed by an auditable ledger (Table 2, RQ1): 81 adjudicated submissions, 51 maintainer-confirmed, 23 fixed via merged PRs, with the fix-PR classifier validated against a known-disproved control (#9149). For a reader outside database testing, this is the strongest kind of significance evidence — third parties changed production code in response to the tool's output — and it is reported per system with acceptance labels where available.
   - **1.2 [minor, unfixable]** The impact is bounded by construction to prose-constraint API regimes of three production VDBMSs; the paper says so explicitly (Limitations, external validity) and does not claim transfer to schema-constrained systems. This is honest scoping, but it means the contribution is useful rather than field-shaping: the method's reach depends on each target having exactly the documentation pathology the paper targets.

2. **Novelty** — Adequate (provisional; I did not survey the field)
   - **2.1** The paper's own positioning is precise about what is *not* new: it concedes that a generated oracle reviewed by a second LLM agent exists (MASTOR's ChallengerAgent, Related Work), that cross-request behavioral oracles are not unique, and that Metamon already pairs generated oracles with an LLM specification judge. The claimed delta — the *anchor inversion*, where prose is ground truth and the implementation serves only as falsifier — is a clean, checkable conceptual delta as the paper describes its competitors, and Table 1 (exclusion analysis) is a genuinely useful articulation of *why* each deterministic oracle family misses this bug class, anchored in the paper's own bug distribution (only 2 of 51 confirmed bugs crash).
   - **2.2 [minor, unfixable]** Provisionally, the delta over the closest prior work (MASTOR, Metamon, CASCADE, as characterized by the paper itself) is an inversion of authority plus a measured confirmation protocol rather than a new mechanism; whether that suffices for field novelty depends on the actual prior texts, which I did not verify. My rating could move either way under a domain reviewer's check.

3. **Soundness** — Adequate
   - **3.1** The evaluation design is careful in ways most papers in this area are not: the RQ2 pool is re-adjudicated under blinding with three independent runs per arm and majority voting; Wilson intervals and Holm-corrected exact McNemar tests accompany the paired comparisons; the three-layer correction (audit → rebuild → protocol alignment) explicitly isolates which variable each number measures; and the seeded 32-candidate unsubmitted- registrations anchor bounds the submission-filter bias direction. I recomputed the headline rates from the confusion tables and they all check out: 7/51=0.137, 29/30=0.967, 41/51=0.804, 24/30=0.800, precision 41/47=0.872, flat 30/51=0.588, D-only 39/51=0.765, Qwen 36/51=0.706; all sixteen rows across Tables 4 and 5 sum to 81; the stratum recalls (0.784×37 + 0.667×3 + 0.909×11 = 41) reconcile exactly with the full stage's 41 TPs; the RQ3 response-status counts (14,022+7,520+1,512+204 = 23,258) close.
   - **3.2 [major, fixable]** A cluster of internal numeric inconsistencies survives that otherwise recomputable surface, and jointly they undermine confidence in the results section as stated: (a) the human-review routing rate is 21% in the abstract and introduction but 10.4% in RQ2 and Limitations for the same quantity, and neither is derivable from the given counts (17 HR-component confirmations / 81 = 21.0%; no stated count yields 10.4%); (b) rebuilt-package arithmetic does not close: 2,106 original rows minus 674 endpoint-filtered minus 463 evidence-failed leaves 969, not the stated 674 (and the coincidence of 674 removed and 674 remaining begs a typo); (c) "the suppression cost relative to the core is exactly six cases" (4 HR-majority + 2 disagreements) contradicts Tables 4–5, where core TN=29 and full TN=24 differ by five; (d) the contract core's stratified recalls "0.137/0.000/0.000" sum to about 5 TPs over the strata, not the 7 the majority table reports — and 0.137 is exactly the core's *overall* rate 7/51, suggesting a copied number; (e) the fix-status partition 23+18+7=48 leaves 3 of the 51 confirmed bugs unaccounted while the text insists the duplicate-tracked flag is "orthogonal ... rather than a fourth state within it" — the arithmetic says exactly the three duplicates are a fourth state; (f) "four orders of magnitude below the overflow threshold" (65,536) is contradicted by the paper's own footnote (threshold 2^62 ≈ 4.6×10^18, i.e., roughly fourteen orders). None of these breaks the headline chain (0.804 vs 0.588, p=0.003, all verified), but a results section this explicit about recomputability should not contain six reconciliation failures.
   - **3.3 [major, fixable]** The central mechanism claim — the structured protocol beats a flat judge — is measured on a single LLM family (GLM) for both arms, and the one cross-family replication the paper runs (source-only on Qwen) *fails* to separate from the flat judge after Holm correction (p=0.10). The paper discloses this in Limitations, but the contribution bullet ("a measured mechanism, not scaffolding") and the abstract do not carry the qualifier; as stated, the mechanism's generality rests on one backbone, and the only external evidence points the other way.
   - **3.4 [minor, fixable]** The attribution of the full-vs-flat gap is only partially decomposed: 17 of the flat judge's 21 misses are credited to "objective-constraint classes ... or its fixed aggregation" (an disjunction, not a count), and 17 of the full stage's 41 confirmations carry a Human-Review component — a channel the flat judge by construction lacks. The abstract concedes the gain is "bought partly" by the human-review channel, but the paper never states how much of the 18-vs-3 paired advantage is routing policy versus cross-examination substance.
   - **3.5** The RQ3 work is methodologically the most careful part of the paper: the authors audit what VDBFuzz's three summary counters actually measure, demonstrate the harness reports 100% success against a dead port, substitute a per-template liveness oracle, measure the mutation-space bound from two directions, and then draw only the conclusion the evidence supports ("on that configuration the crash class is not constructible"). Withdrawing the earlier draft's wrong explanation for the zero (three templates do issue wait=false upserts) is exactly how a revision should behave.
   - **3.6 [minor, fixable]** Ground truth and measurement share a circular structure that the paper handles candidly but that still caps what the numbers mean: the entire 81-candidate pool is pipeline-generated and author-screened, so "recall 0.804" is pool-internal re-adjudication, not system recall, and the 63.0% precision inherits the authors' submission selectivity. The paper says all of this; my concern is only that the abstract's bare "0.804 recall" does not signal the qualifier the body works so hard to establish.

4. **Verifiability** — Adequate
   - **4.1** The replication package is declared at an anonymous repository with a detailed contents list: per-version knowledge bases and specifications, all generated scripts with raw HTTP logs, one evidence chain per candidate, the submission ledger (all 81 adjudicated plus 49 unadjudicated), original and rebuilt RQ2 packages with audit verdicts and per-case judge outputs for every arm and run, RQ3 per-template logs, and analysis scripts that "recompute every rate, interval, and paired test reported here." The link is declared; per the review protocol I treat it as reachable and do not clone it. The text itself is largely self-contained: the confirmation protocol's aggregation rule, the seven objective-constraint classes, and the strategy-prebinding mechanism are specified precisely enough to re-implement in concept.
   - **4.2 [minor, fixable]** The text's own recomputability claim is undercut by the arithmetic failures in 3.2 — a reader with the artifact could resolve them, but the paper as read cannot be fully checked from itself. The RQ1 funnel is also explicitly reported at only two measured points ("many-to-one without a maintained per-step count," line in RQ1's process-ledger paragraph), so the path from 119 chain verdicts to 5 registered defect numbers is only partially auditable by design.

5. **Presentation** — Adequate
   - **5.1** The paper is well structured for an outsider: the running example (#10369) threads all four stages with concrete requests and responses; terms that matter to the counting (pack, case, leak, the two senses of "false positive") are defined before use; the tables are clean and every row is checkable; the limitations are organized by validity type rather than listed.
   - **5.2 [minor, fixable]** The abstract is overlong and results-saturated — three dense paragraphs carrying percentages, p-values, and audit findings, including a sentence ("the structure of the stage is what the numbers resolve") whose meaning I could only recover from the body. Several introduction sentences run long and carry nested em-dash qualifications (the four-stage pipeline sentence exceeds 70 words); a tightening pass would help first-time readers.
   - **5.3 [minor, fixable]** The same quantity (human-review routing) is stated as 21% and 10.4% in different sections (3.2a), and two different strata both use the number 37 with opposite-sounding descriptions: "37 of the 51 true bugs violate semantics the packages record only as behavioral inference" (contract-core paragraph) versus "the 37 evidence-present packs (a verifiable contract row)" (stratification paragraph). Both may be true simultaneously (a pack can contain a verifiable contract row while the violated semantics sits elsewhere), but nothing tells the reader so; a disambiguating clause is needed.
   - **5.4 [minor, fixable]** Minor usage friction: "adjudicable", "delimiting where an LLM-derived oracle is forced", and repeated parenthetical restatements of the seven objective-constraint classes (four times across Sections 3 and 4) add length without new information; the pipeline figure could not be assessed from the stripped source.

### Questions for Authors

- **Q1:** What are the denominators behind "21%" (abstract, introduction) and "10.4%" (RQ2, Limitations) for human-review routing? If 21% is 17 HR-component confirmations over 81 cases, what population yields 10.4%? — Clarifying resolves 3.2(a) and would settle whether the abstract's headline framing of the human-review channel is sized correctly.
