## Reviewer 1: Domain Expert

**Overall Recommendation:** Weak Accept

### Summary

TestVDB targets documentation-implementation defects in Vector Database Management Systems (VDBMSs) — cases where a VDBMS silently accepts an input or behavior that violates its API documentation. These defects do not crash and thus escape crash-oracle fuzzers like VDBFuzz. Because the documented boundary is natural-language prose, the authors argue that deterministic oracles (differential, metamorphic, property-based) cannot adjudicate these accept/reject decisions, leaving an LLM as the practical oracle. The paper proposes a four-stage pipeline: (1) behavioral-claim extraction from documentation, (2) test-script generation, (3) sandboxed execution, and (4) defect confirmation via a dev-reviewer agent that acts as a source-grounded falsifier. The dev-reviewer independently reproduces each candidate, cross-checks it against implementation source, and tries to disprove it — suppressing false positives from LLM hallucination (extraction) and self-preference bias (judgment). The evaluation spans three production VDBMSs (Milvus, Qdrant, Weaviate), yielding 107 submitted issues with 50 maintainer-acknowledged true-positive defects (15 fixed via merged PR). A 48-candidate retrospective shows the dev-reviewer reaches 67% precision and 74% recall against a 37% recall single-LLM baseline. A bidirectional probe against VDBFuzz demonstrates complementary coverage: VDBFuzz reaches crash-class defects via crashes, TestVDB reaches crash-class defects via contract reasoning (and vice versa).

### Core Strengths

- **S1:** Well-motivated problem characterization — The documentation-implementation defect class is clearly defined and empirically motivated by the VDBMS bug study (43% incorrect behavior, most not crashing). The oracle-exclusion argument (Table 2) is thorough and convincing. — see 1.1, 2.1

- **S2:** Source-grounded falsification is a substantive technical contribution — The dev-reviewer's three-check mechanism (independent reproducibility, evidence sufficiency, falsifiability) breaks both hallucination and self-preference by anchoring ground truth in implementation source rather than the LLM. This is a clear advance over prior LLM-as-oracle work. — see 2.2, 3.2

- **S3:** Strong empirical validation with maintainer adjudication — 107 real-world submissions with 50 maintainer-acknowledged true positives (15 merged-PR fixes) across three production VDBMSs is substantial evidence of practical impact. The 48-candidate controlled retrospective with precision/recall metrics and confidence intervals is methodologically sound. — see 3.1, 3.2

- **S4:** Complementarity to VDBFuzz is empirically established — The bidirectional probe (Section 4.4) cleanly separates crash-oracle and documentation-oracle regimes, showing each reaches defects the other misses. This positions TestVDB as complementary to existing tooling rather than a replacement. — see 2.1, 3.3

### Core Weaknesses

- **W1:** External validity is limited — The 48-candidate retrospective is non-random (convenience sample from submitted issues), and the paper does not estimate recall against the full defect space. No capture-recapture or unbiased sampling. Yield proportions (50/107) are not population estimates. — see 3.1 [major, unfixable]

- **W2:** Cross-family generalization is unestablished — All dev-reviewer results use a single LLM family (GLM-5.2). The cross-model re-run (DeepSeek, Qwen, LongCat) shows family-specific verdicts (κ = 0.18–0.32), with Qdrant recall collapsing to ≤14% for non-GLM families. The paper explicitly calls this "an open question," but it materially limits generalizability. — see 3.2 [major, unfixable]

- **W3:** Operating point selection is post-hoc — The 3-run union ensemble is selected post-hoc from four operating points (single-run, 3-run union, 5-run union, majority voting). Wilson CIs do not account for this selection. The Bonferroni correction is provided as sensitivity analysis but is not integrated into the headline claims. — see 3.2 [major, fixable]

- **W4:** Threat-model anchor evaluation is thin — The threat-model anchor is described as "unstable on state and concurrency false positives" (Table 7), but the paper does not characterize when or why it fails. The 12-FP/4-TP ablation shows it contributes only 50% suppression alone. Its design and limitations are not explored. — see 3.2 [minor, fixable]

### Detailed Assessment

1. **Significance** — Adequate
   - **1.1** The problem is well-motivated and impactful. VDBMSs are critical infrastructure for LLM applications, and the bug study shows 43% of defects are "incorrect behavior" rather than crashes. Documentation-implementation defects directly corrupt query semantics (e.g., disabled filters return all matches, negative thresholds disable filters), leading to wrong context sent to models. This is a real, costly problem. The oracle-exclusion argument (Table 2) systematically shows why deterministic approaches cannot reach this residual. The motivation is strong.

2. **Novelty** — Adequate
   - **2.1** TestVDB's documentation-implementation defect class is a novel target for VDBMS testing. The paper correctly positions it against crash-oracle fuzzers (VDBFuzz [vdbfuzz26]) and REST-API oracle tools (AGORA+ [agoraplus25], SATORI [satori25], MASTOR [mastor26]). The distinction is real: VDBFuzz targets crashes (structural blindness to silent accepts), while AGORA+/SATORI/MASTOR target response-field properties under per-field structural anchoring (OpenAPI, traces, source), not input-acceptance decisions on system-level prose. The bidirectional probe (Section 4.4) empirically validates complementarity with VDBFuzz. The shift to consistency (vs. correctness) is clearly articulated and grounded in the roadmap's challenge identification [roadmap25].

   - **2.2** The dev-reviewer's source-grounded falsification is a substantive advance over prior LLM-derived oracle work (Toradocu [toradocu16], Doc2OracLL, AugmenTest [augmentest25]). Those approaches treat the LLM as the final semantic arbiter, verifying through runtime behavior only. TestVDB instead anchors ground truth in implementation source, breaking self-preference bias (established for LLM evaluators [panickssery24, wataoka24]) and hallucination [ji23hall]. The three-check mechanism (independent reproducibility, evidence sufficiency, falsifiability) is a well-designed falsifier architecture. The 75% false-positive suppression in ablation (Table 7) and recall gain from 37% to 74% (Table 6) demonstrate its value.

   - **2.3 [minor, fixable]** The paper does not cite or compare against concurrent work on LLM-as-judge for software testing beyond the self-preference bias papers. For example, Haldar et al. [haldar25] show intra-judge self-inconsistency (same input, different ratings across runs) — a sampling-noise phenomenon intersecting TestVDB's false-positive modes. The paper addresses this via the any-confirmed union ensemble, but explicit positioning would strengthen novelty claims.

3. **Soundness** — Adequate
   - **3.1** The empirical methodology is generally sound but has important limitations. Ground truth from maintainer adjudication (50 true-positive, 22 by-design/rejected, 35 pending) is appropriate for this domain. The 48-candidate controlled retrospective (27 TP, 21 FP) with Wilson 95% confidence intervals is methodologically solid. However, the retrospective is non-random (convenience sample from submitted issues), so it does not estimate recall against the full defect space. No capture-recapture or unbiased defect sampling. Yield proportions (69.4% precision on adjudicated submissions; 46.7% worst-case treating pending as FP) are not population estimates. The paper acknowledges this ("biased by tool's design") but it limits external validity [W1].

   - **3.2** The dev-reviewer evaluation is thorough but the operating point selection is post-hoc [W3]. The 3-run union ensemble is selected from four operating points (single-run, 3-run union, 5-run union, majority voting) based on precision-recall trade-off. Wilson CIs (Table 6) do not account for this selection. The paper provides Bonferroni-corrected CIs (α=0.05/4 ≈ [44,84]/[51,89]) as sensitivity analysis and validates via bootstrap resampling (2000 resamples) and held-out cross-validation (200 random 50/50 splits), which supports robustness. But the headline claims should reflect the post-hoc selection. Cross-family generalization is unestablished [W2] — all headline results use GLM-5.2. The cross-model re-run shows family-specific verdicts (κ = 0.18–0.32 vs. GLM), with Qdrant recall collapsing to ≤14% for non-GLM families. This materially limits claims about the approach's backbone-agnostic efficacy.

   - **3.3 [major, fixable]** The VDBFuzz bidirectional probe is well-designed but one controlled case is n=1. The systematic direction (VDBFuzz on v1.18.2, 26,000 requests, 0 of 14 TestVDB TPs reached) is generalizable and clean. The two controlled cases (v1.4.0 crash, v1.18.0 silent-accept) are each n=1 and isolate mechanisms but are not statistically powered. The paper reads v1.18.0 as a VDBFuzz template limitation rather than a crash-oracle limitation, which is reasonable but underexplored — does VDBFuzz reach silent-accept defects if templates are expanded? This limits the strength of the "complementarity" claim.

4. **Verifiability** — Excellent
   - **4.1** The paper provides sufficient detail to follow and replicate the work. The four-stage pipeline is clearly described (Section 2). Agent role prompts are excerpted in Appendix A (full 22 prompts in artifact). Target versions are specified (Milvus 2.6.19, Qdrant v1.18.2, Weaviate v1.38.2). LLM backbone and sampling parameters are documented (GLM-5.2, default sampling). The 48-candidate ground truth is available in the artifact. The artifact URL (https://github.com/yihui504/testvdb-anon) is declared as reachable. Per-target cost (~$10, ~10^4 LLM calls) and call distribution (Table 4) support reproducibility. No critical method or data is undisclosed.

5. **Presentation** — Adequate
   - **5.1 [minor, fixable]** The paper is well-structured and readable, but some notation inconsistencies exist. Table 6 reports "Per-run band" as min--max but the column header is "Accuracy / Precision / Recall" (implied order). Table 7 column headers are "FP suppressed / TP retained" but the caption says "Each configuration retains all 4 true positives" — clarify that this refers to the control, not the full retrospective. Figure 3 (per-run recall) y-axis should be labeled "Recall (%)" not just run number.

   - **5.2 [minor, fixable]** Minor language issues: Section 4.3, paragraph 4 ("The two modes point to different fixes") is awkward; consider "The two failure modes point to different fixes." Section 4.3, last paragraph ("On the same 3-run any-confirmed union") is missing a comma after "union".

   - **5.3 [minor, fixable]** The Related Work section is comprehensive but could better position TestVDB against concurrent work on LLM-as-judge beyond self-preference bias (e.g., Haldar et al. [haldar25] on intra-judge inconsistency). This would strengthen the falsification rationale.

   - **5.4** Figures and tables are generally clear. Figure 2 (pipeline) and Figure 4 (dev-reviewer three-check) effectively communicate the architecture. Tables 2 (oracle exclusion), 6 (operating points), and 7 (ablation) are well-designed. Table 5 (yield) could include confidence intervals.

### Questions for Authors

- **Q1:** The 48-candidate retrospective is a convenience sample from submitted issues. What would be required to estimate recall against the full defect space? Could capture-recapture or a stratified random sample of documentation passages be feasible? — intended effect: if authors clarify feasibility, item 3.1's external validity rating could move from Adequate to Weak (acknowledged) or remain Adequate with clearer boundaries.

- **Q2:** All headline dev-reviewer results use GLM-5.2. The cross-model re-run shows family-specific verdicts (κ = 0.18–0.32) and Qdrant recall collapse (≤14% for non-GLM). Is this a Qdrant-specific phenomenon (e.g., response structure) or a general backbone dependency? - **Q3:** The 3-run union ensemble is selected post-hoc from four operating points. Wilson CIs do not account for selection. Could pre-registering the ensemble selection criterion (e.g., "choose highest-recall ensemble with precision ≥ 60%") and recomputing CIs on that rule strengthen the headline claims? — intended effect: if authors adopt this, item 3.2's operating point selection concern would be mitigated, moving Soundness from Adequate toward Adequate (acknowledged and addressed).

## Reviewer 2: Area Specialist

**Overall Recommendation:** Weak Accept

### Summary
TestVDB targets documentation-implementation defects in Vector Database Management Systems (VDBMSs)—cases where a system silently accepts inputs that violate its API documentation, such as accepting `nprobe=0` when the documented range is [1, 16384]. Because the documented boundary is natural-language prose rather than a structured specification, classical deterministic oracles (crash detection, differential testing, metamorphic relations, property-based testing) cannot adjudicate these accept/reject decisions. The paper instantiates a four-stage pipeline that uses LLMs to extract behavioral claims from documentation, generate executable tests, run them against sandboxed VDBMSs, and confirm defects. A key innovation is the dev-reviewer agent, which acts as a source-grounded falsifier to suppress two false-positive modes: LLM hallucination in claim extraction and self-preference bias in judgment. The authors evaluated TestVDB on three production VDBMSs (Milvus, Qdrant, Weaviate), surfacing 107 candidate issues with 50 maintainer-acknowledged true-positive defects (15 fixed via merged PR). On a controlled 48-candidate retrospective, the dev-reviewer reaches 67% precision and 74% recall against a 37% recall baseline without source grounding. A bidirectional probe against VDBFuzz shows complementary coverage: VDBFuzz reached 0 of 14 silent-accept defects on Qdrant v1.18.2, while TestVDB reached a crash-class defect by contract reasoning.

### Core Strengths
- **S1:** Well-motivated problem and clear target defect class — see 1.1, 1.2
- **S2:** Strong empirical validation with maintainer-adjudicated ground truth — see 3.1
- **S3:** Source-grounded falsification is a methodological innovation over prior work — see 2.1

### Core Weaknesses
- **W1:** Cross-family generalization is open and claimed too broadly for the evidence — see 2.3 [major, unfixable]
- **W2:** Network/access issues prevent full verification of some core competitors — see 4.2 [minor, fixable]

### Detailed Assessment

#### 1. Significance — Adequate

- **1.1** The problem is well-motivated and real. VDBMSs are infrastructure for retrieval-augmented LLM applications, and the authors cite an empirical bug study (bugstudy25) showing that more than half of VDBMS defects manifest as functional failures rather than crashes. The specific target class—documentation-implementation defects where silent accepts corrupt query semantics—is a genuine operational problem. The 50 maintainer-acknowledged true positives across three production systems, with 15 merged-PR fixes, demonstrate practical impact. This is meaningful but bounded: the approach applies to a specific consistency subset (documentation vs. implementation) and does not address result correctness (ANN recall, ranking), which the authors explicitly leave out of scope.

- **1.2 [major, fixable]** The portability claim beyond VDBMSs is preliminarily supported. The authors ran a probe on Apache CouchDB and Elasticsearch, finding three input-validation gaps in CouchDB that were acknowledged as bugs. However, this is a limited probe (one non-VDBMS case study) and the authors claim transferability "only to structurally similar documentation regimes" without defining what "structurally similar" means operationally. The claim would be stronger with: (a) a clearer characterization of the documentation regime properties that enable transfer (e.g., prose-based API docs, no OpenAPI schema, parameter-level constraints), and (b) at least one additional non-VDBMS case study to establish a pattern. As stated, the portability claim is suggestive but not generalizable.

#### 2. Novelty — Adequate

- **2.1** The methodological innovations over prior work are genuine and well-differentiated. For REST-API oracle generation, MASTOR (Deng et al. 2026) reads source code to generate oracles that encode implemented behavior—it validates code against itself. TestVDB inverts this directionality: it extracts claims from documentation (the contract), then uses source as a falsifier to check whether the implementation violates that contract. This is a non-trivial delta that enables detection of documentation-implementation gaps, which MASTOR cannot reach by design. The authors accurately characterize this distinction in Related Work and empirically validate it in RQ3's bidirectional probe against VDBFuzz (the crash-oracle fuzzer), where VDBFuzz reached 0 of 14 silent-accept true positives on Qdrant v1.18.2, while TestVDB reached a crash-class defect by contract reasoning. The complementarity is empirically demonstrated.

- **2.2** The application of self-preference bias mitigation to test oracle judgment is novel in this context. The authors correctly ground their approach in established LLM evaluation literature (Wataoka et al. 2024, Panickssery et al. 2024) showing that same-family judges over-confirm their own family's outputs due to self-recognition and perplexity-based familiarity. TestVDB's dev-reviewer agent breaks this bias by using implementation source as an independent ground truth—this is a creative application of general LLM reliability insights to the specific problem of test oracle reliability. The three-check falsification process (independently reproducible, evidence sufficient, falsifiable) is a well-designed operationalization.

- **2.3 [major, unfixable]** Cross-family generalization is open and the evidence does not support the strength of the claim in Section 4.3. The authors ran a cross-model re-run with DeepSeek, Qwen-3.8-Max, and LongCat-2.0, finding that "the verdict is family-specific" (Cohen's κ vs. GLM: 0.32 DeepSeek, 0.20 LongCat, 0.18 Qwen, all in the slight-to-fair band). They report that combined recall was 56% (DeepSeek), 22% (LongCat), and 19% (Qwen) vs. 74% for GLM-5.2, and that "Source-grounded falsification is backbone-dependent, and the dependence concentrates on Qdrant." However, the abstract states: "These results use a single LLM backbone (GLM-5.2); cross-family generalization is an open question." The disconnect is: the abstract acknowledges it's open, but the body presents substantial cross-family data (three additional families, full SOP re-runs) without a clear take-away. Either cross-family generalization is a limitation (open question) or it's a preliminary finding (family-specific, with complementary coverage via voting). The current presentation muddles this: the abstract frames it as open, but the detailed results suggest a more nuanced story (dependence concentrates on Qdrant, some families like DeepSeek approach GLM performance on Milvus). This is not fixable in a revision cycle without new experiments, so it's an unfixable limitation on the generality of the contribution.

#### 3. Soundness — Adequate

- **3.1** The empirical methodology is strong and appropriately grounded. Ground truth comes from maintainer adjudication (107 submitted issues, 50 true-positive, 22 by-design/rejected, 35 pending), which is a gold standard for defect detection. The 48-candidate controlled retrospective (27 TP, 21 by-design/rejected; Milvus 32, Qdrant 16) provides a solid evaluation substrate for false-positive suppression analysis. The authors report Wilson 95% confidence intervals for precision and recall, and they run bootstrap resampling (2000 resamples) and held-out cross-validation (200 random 50/50 splits) to validate that the 3-run union operating point is not an overfit to a specific candidate sample. This is rigorous experimental practice.

- **3.2 [major, fixable]** The operating point selection is post-hoc and the statistical reporting does not fully account for this. The authors evaluate four operating points (single run, 3-run union, 5-run union, 5-run majority) and select the 3-run union as the headline because it "sits at the knee of the precision-recall trade-off at modest reproducibility cost." They flag it as "post-hoc, exploratory" and note that "the Wilson CIs above do not account for this selection." They then apply a Bonferroni correction across the four points, which widens the 3-run CIs to roughly [44%, 84%] (precision) and [51%, 89%] (recall), and report bootstrap validation giving [53%, 83%] and [71%, 96%]. This is better than not correcting at all, but the fundamental issue is that the headline operating point was selected after seeing the data, and no adjustment fully recovers the uncertainty from that selection. A stronger design would pre-register the operating point (e.g., commit to 3-run union as the falsifier semantics) or use a held-out validation set to select it. The current approach is acceptable as exploratory but weakens the statistical claims somewhat.

- **3.3** The threat-model anchor (optional check in dev-reviewer) is less rigorously evaluated than the source-grounded anchor. The ablation in Table 4 shows it suppresses 6/12 false positives (50%) but is "unstable on state and concurrency FPs." The authors note it "adds coverage on by-design patterns that source grounding alone reads as implementation choices." This suggests the threat-model anchor is useful but not fully characterized. A clearer description of what patterns it catches (with examples) and why it's unstable on certain defect types would strengthen the design rationale.

#### 4. Verifiability — Weak

- **4.1 [minor, fixable]** Artifact accessibility is partially compromised by broken or inaccessible links for some core competitors. During literature search, I encountered HTTP 429 errors from Semantic Scholar (rate limiting) and could not locate clear metadata for VDBFuzz, SATORI, or AGORA+ in DBLP/CrossRef/arXiv. This is likely temporary (network issues, indexing delays) but affects verifiability of the Related Work characterization. The authors should ensure stable, permalinks to all cited works, ideally with DOIs or arXiv IDs, and consider including direct PDF links in an appendix for works that are hard to discover via bibliographic databases.

- **4.2 [minor, fixable]** The artifact (prompts, target versions, ground truth, reproduction driver) is linked at https://github.com/yihui504/testvdb-anon, which is good practice. However, the paper does not report on artifact evaluation (e.g., whether the artifact was reviewed by an artifact evaluation committee) or provide a hash for reproducibility. Adding a git commit hash and a brief artifact availability statement (e.g., "An artifact evaluated at [venue] is available at...") would strengthen Verifiability.

#### 5. Presentation — Adequate

- **5.1 [minor, fixable]** The paper is well-structured and readable overall. The figures (pipeline overview, dev-reviewer three-check diagram, per-run recall plot) are clear and well-integrated. The notation is consistent. There are minor language errors and awkward phrasings throughout (e.g., "the residual leaves an LLM as the practical oracle" could be smoother), but these do not obstruct understanding.

- **5.2 [minor, fixable]** Some forward references and organizational choices could be improved. The oracle exclusion argument (Table 2) is presented in Preliminaries (Section 2.3) but would fit better as the opening of Approach (Section 3) to directly motivate the pipeline. The cross-family results (Section 4.3, final paragraph) are dense and hard to follow—breaking them into a separate subsection with a table summarizing per-family performance would improve clarity. The Limitations section (Section 6) is thorough but could be more explicitly tied to the evaluation results (e.g., explicitly referencing the κ values when discussing external validity).

- **5.3 [minor, fixable]** Minor notation inconsistencies: The paper uses both "TestVDB" and "TestVDB's" inconsistently. Some citations use "~\cite{key}" format while others use "\cite{key}"—standardize to one style. Table 3's caption is cut off in the source ("(3.5.x source)")—ensure version numbers are consistent.

### Questions for Authors

- **Q1:** Can you clarify the cross-family generalization claim? The abstract says "cross-family generalization is an open question" but Section 4.2 presents substantial cross-family data (DeepSeek, Qwen, LongCat) with the conclusion that "Source-grounded falsification is backbone-dependent, and the dependence concentrates on Qdrant." Should readers interpret this as (a) an open limitation (more work needed), (b) a preliminary finding (family-specific but some complementarity via voting), or (c) a negative result (the approach doesn't generalize)? The abstract suggests (a), the body suggests (b). Clarifying this would sharpen the contribution claims. (Intended effect: if clarified to (a), item 2.3's rating moves from Weak to Adequate; if clarified to (b), the paper should weaken the abstract's "open question" framing.)

## Reviewer 3: General Reviewer

**Overall Recommendation:** Weak Accept

### Summary

TestVDB targets a class of defects in Vector Database Management Systems (VDBMSs) where a system silently accepts an input or produces a behavior that violates its API documentation (e.g., accepting `nprobe=0` when documentation declares the range as `[1, 16384]`). These defects corrupt query semantics but produce no crash, so existing crash-oracle fuzzers like VDBFuzz miss them. The paper argues that because the documented boundary is natural-language prose rather than a structured specification (e.g., OpenAPI), deterministic oracles cannot adjudicate these accept/reject decisions, leaving an LLM as the practical oracle. This introduces two false-positive failure modes: hallucination during claim extraction (the LLM invents constraints the documentation does not state) and self-preference bias during judgment (the same LLM family that extracts a claim tends to confirm it). The authors present TestVDB, a four-stage pipeline (behavioral-claim extraction, test generation, sandboxed execution, defect confirmation) that uses LLMs to read documentation, generate tests, and adjudicate responses. To suppress false positives, they introduce a dev-reviewer agent that acts as a source-grounded falsifier: it reproduces each candidate defect, cross-checks it against implementation source, and tries to disprove it. A candidate that survives all three checks is adjudicated a defect. The evaluation reports 107 submitted issues across three VDBMSs (Milvus, Qdrant, Weaviate) with 50 maintainer-acknowledged true-positive defects (69% adjudicated yield; 15 fixed via merged PR, 16 with open fix-PRs, 19 acknowledged but unfixed). On a controlled retrospective of 48 maintainer-adjudicated candidates, the dev-reviewer reaches 67% precision and 74% recall (3-run any-confirmed ensemble), versus 37% recall without the source anchor. A bidirectional probe against VDBFuzz on Qdrant shows TestVDB reaches a crash-class defect by contract reasoning (integer overflow on `size=$2^{63}$` on Qdrant v1.4.0) while VDBFuzz misses a TestVDB silent-accept defect (`wait=false` accepting a zero-length vector, issue #9045 on v1.18.0). The paper is positioned as a technical contribution proposing a novel pipeline and a source-grounded falsification technique to address a documented gap in VDBMS testing. All evaluation uses a single LLM backbone (GLM-5.2); cross-family generalization is identified as an open question.

### Core Strengths

- **S1:** Clear characterization of the documentation-implementation defect class and a principled argument for why deterministic oracles cannot reach it — see 1.1, 1.2.

- **S2:** The source-grounded dev-reviewer falsifier is a well-motivated technical response to two documented LLM failure modes (hallucination, self-preference) and shows measurable improvement — see 2.2, 3.3.

- **S3:** Substantial real-world impact: 50 maintainer-acknowledged true positives across three production VDBMSs with 15 merged-PR fixes — see 3.1.

- **S4:** A thoughtful external probe on CouchDB/Elasticsearch suggests the approach may transfer to other documentation regimes — see 3.4.

### Core Weaknesses

- **W1:** Limited external validation of the cross-family generalization claim — only GLM-5.2 is used in the main evaluation, and the cross-family re-run results show significant inter-family variance — see 2.3 [major, unfixable].

- **W2:** The 48-candidate retrospective is maintainer-adjudicated but non-random; the paper does not address selection bias or provide a defended sampling strategy — see 3.2 [major, fixable].

- **W3:** The paper's LLM-as-judge reliability discussion and the cross-family variance results are buried in late subsections and should be surfaced as limitations earlier — see 5.2 [minor, fixable].

### Detailed Assessment

1. **Significance** — Adequate

   - **1.1** The paper characterizes a real, costly defect class in VDBMSs with empirical motivation: more than half of VDBMS bugs manifest as functional failures rather than crashes (citing [bugstudy25]), and the roadmap identifies oracle definition as a key challenge (citing [roadmap25]). The concrete example (Milvus issue #49823, `nprobe=0`) clearly illustrates a defect that corrupts query semantics without producing a crash. The significance is bounded to the VDBMS domain and to consistency defects (result correctness of vector search is explicitly out of scope), but the 50 maintainer-acknowledged true positives and 15 merged-PR fixes across three production systems demonstrate practical impact. The paper stakes a clear boundary (Section 2.2) between problems where structured-source extraction suffices and those where natural-language documentation forces LLM interpretation, which marks a useful contribution at the intersection of testing and LLM-as-oracle reliability.

   - **1.2 [minor, fixable]** The external portability probe (Section 4.5) on CouchDB and Elasticsearch is a valuable strength for demonstrating that the documentation-implementation defect class exists beyond VDBMSs, but the probe is preliminary and the paper does not claim a generalization result. The Elasticsearch case (rejected every invalid probe with a 400 error) suggests that some systems already enforce input validation cleanly, while CouchDB exposed three gaps (two acknowledged as bugs). This probe is encouraging for transferability but is not sufficient as a generalization claim; the paper correctly frames it as structural only. A more substantial external validation (e.g., a second non-VDBMS case study with submitted issues and maintainer adjudication) would strengthen the significance argument beyond VDBMSs.

2. **Novelty** — Adequate

   - **2.1** The paper's novelty claim rests on two pillars: (1) documentation-implementation consistency testing as a target for VDBMS testing, and (2) source-grounded falsification to suppress LLM false positives. On the first pillar, the Related Work section (Section 6) positions the contribution against REST-API oracle tools (AGORA+, SATORI, MASTOR), LLM-as-judge reliability (self-preference bias), and documentation-derived oracles (Toradocu, Doc2OracLL). The positioning is clear: prior work targets response-field or runtime properties under per-field structural anchoring (OpenAPI, traces, source), not input-acceptance decisions on system-level prose. The paper shows that TestVDB reads source as a falsifier of documentation-derived claims and targets exactly the gap between documentation and code, which MASTOR (the closest prior work) cannot detect because it encodes implemented behavior. This is a non-obvious delta: the problem space (consistency vs. correctness) and the oracle regime (LLM-derived with source falsification) are distinct from prior work.

   - **2.2** On the second pillar, the dev-reviewer's source-grounded falsification is a novel technique for mitigating LLM false positives in test oracle pipelines. The two failure modes (hallucination during extraction, self-preference during judgment) are well-diagnosed and grounded in established LLM reliability literature (self-preference bias [panickssery24, wataoka24], hallucination [ji23hall]). The multi-perspective judging baseline (four specialized judge agents with voting) is a reasonable counterfactual, and the paper shows it reaches ~80% precision but collapses recall to ~15% because the judge agents share the same documentation ambiguity. The dev-reviewer breaks this by introducing an independent ground truth (the implementation source) that does not depend on the LLM's interpretation of the documentation. The ablation results (Table 6, where source-grounded alone suppresses 75% of false positives and retains all true positives) quantify the contribution. This is a solid, incremental novelty.

   - **2.3 [major, unfixable]** The cross-family generalization limitation is a significant constraint on the novelty's robustness. The main evaluation uses only GLM-5.2 (all agents, all targets). The cross-family re-run (Section 4.2, three additional families: DeepSeek, Qwen-3.8-Max, LongCat-2.0) shows that the verdict is family-specific (Cohen's κ vs. GLM's 3-run union: 0.32 DeepSeek, 0.20 LongCat, 0.18 Qwen, all in the slight-to-fair band). Recall varies widely across families: DeepSeek reaches 56% recall (3-run union), LongCat 22%, Qwen 19%, vs. 74% for GLM-5.2. The paper acknowledges this as an open question and provides cross-family voting as a mitigation direction, but the core contribution (source-grounded falsification) is backbone-dependent. This is an inherent property of the technique: the dev-reviewer's reliability depends on the LLM family's ability to read source and adjudicate against documentation-derived claims. The paper's focus on GLM-5.2 is a reasonable scope choice for a single paper, but readers should be aware that the results do not generalize automatically to other LLM families without additional validation. The paper's statement that "cross-family generalization is an open question" is honest and appropriate, but it limits the novelty claim to a demonstration rather than a general solution.

3. **Soundness** — Adequate

   - **3.1** The main claims are supported by appropriate methods and credible evidence. RQ1 (detection capability) uses maintainer adjudication as ground truth, which is the strongest feasible validation for real-world defects. The yield (50 true-positive of 107 submitted, 69% adjudicated precision; 15 merged-PR fixes) is substantial. RQ2 (false-positive suppression) uses a controlled 48-candidate retrospective (27 true-positive, 21 by-design or rejected) to measure the dev-reviewer's accuracy, precision, and recall. The single-LLM baseline (no source anchor) provides a clear comparison, and the dev-reviewer's 3-run any-confirmed ensemble reaches 65% accuracy, 67% precision (Wilson 95% CI [49, 81]), and 74% recall, against a baseline of 48%/56%/37%. The paper also provides ablations (Table 6, three-condition ablation on a 12-FP/4-TP control) to isolate the source-grounded anchor's contribution (75% FP suppression) and a source-disabled control that collapses recall from 74% to 19%. RQ3 (comparison with VDBFuzz) is a bidirectional reachability probe that cleanly separates the two oracles' coverage: VDBFuzz on Qdrant v1.18.2 ran over 26,000 mutated requests and reached 0 of TestVDB's 14 silent-accept true positives; TestVDB on Qdrant v1.4.0 reached VDBFuzz's integer-overflow crash via contract reasoning. The methods are sound for the claims.

   - **3.2 [major, fixable]** The 48-candidate retrospective for RQ2 is maintainer-adjudicated but non-random, and the paper does not address selection bias or defend the sampling strategy. The abstract states the 48-candidate set is "controlled," but the methodology section (Section 4.1) does not describe how candidates were selected for this retrospective (e.g., were they a random sample from the 107 submitted? a convenience sample? selected to balance Milvus/Qdrant vendors?). The limitation section (Section 5) acknowledges the set is "non-random" and notes that capture-recapture or unbiased defect-sample estimation is future work, which is honest. However, for a central evaluation that drives the headline claim (67% precision, 74% recall), the paper should describe the selection criteria and discuss potential bias (e.g., are the 48 candidates harder or easier than the full 107? do they over-represent certain defect types or vendors?). This is a fixable gap: the authors can add a sentence in Section 4.1 describing the retrospective's composition and a sentence in Section 5 acknowledging how selection might affect the precision/recall estimates.

   - **3.3 [minor, fixable]** The operating-point selection for the dev-reviewer (3-run any-confirmed union) is post-hoc and not pre-registered. The paper flags this explicitly ("post-hoc, exploratory operating point justified by falsifier semantics, not a pre-registered rule") and provides validation (bootstrap resampling, held-out cross-validation) to show it is not an artifact of the specific candidate sample. The Wilson 95% CIs do not account for selection across the four operating points (single run, 3-run union, 5-run union, 5-run majority), which the paper acknowledges. A Bonferroni correction would widen the 3-run CIs (the paper reports roughly [44, 84] for precision and [51, 89] for recall). This is a minor blemish because the headline claim (74% recall vs. 37% baseline) is robust to the correction, but the paper should be more explicit about the operating-point selection process and its statistical implications in the methodology section. The current treatment is honest but scattered; consolidating the operating-point discussion and the validation (bootstrap, cross-validation) into a single subsection would improve clarity.

   - **3.4 [minor, fixable]** The paper's external validity discussion (Section 5) correctly notes that all dev-reviewer results use a single LLM family (GLM-5.2) and that the verdict is family-specific (citing Cohen's κ). However, the paper could strengthen the soundness of the cross-family generalization claim by providing a more detailed analysis of where and why inter-family disagreement occurs. The current results report vendor-specific gaps (DeepSeek reaches 75% recall on Milvus but 0% on Qdrant) and note that "tightening the contract-formalizer would raise κ sharply" for Qwen, but the paper does not dissect whether disagreements stem from (a) hallucination differences in extraction, (b) self-preference bias in judgment, or (c) source-grounding interpretation. A more fine-grained analysis of a few representative disagreements (e.g., one candidate where GLM-5.2 confirms and DeepSeek rejects, with root-cause attribution) would help readers understand the mechanism of cross-family variance and whether it is addressable via prompt engineering or architectural changes. This is a minor enhancement to an already sound cross-family evaluation.

4. **Verifiability** — Adequate

   - **4.1** The paper provides sufficient detail to follow how the evidence was produced and to verify or replicate the work. Section 3.5 (Multi-Agent Implementation) describes the agent architecture (22 role definitions), the LLM backbone (GLM-5.2 via BigModel Anthropic-compatible API, default sampling), the target versions (Milvus 2.6.19, Qdrant v1.18.2, Weaviate v1.38.2), the cost estimate (~$10 per target, ~10^4 LLM calls), and the source clones for dev-reviewer grounding. The paper declares an artifact repository (https://github.com/yihui504/testvdb-anon) with prompts (agents/), ground truth (test_questions/), and reproduction scripts (reproduction/full52/). The artifact link is declared and appears reachable (the URL follows a standard GitHub pattern). For readers who do not clone the artifact, the paper's text describes the pipeline stages, the agent roles, the evaluation methodology (Section 4.1), the retrospective composition (48 candidates, 27 true-positive), and the operating-point selection. The paper is self-contained enough to understand the what and how, though full replication requires the artifact for prompts and ground truth.

   - **4.2 [minor, fixable]** The paper's artifact description (Section 3.5) is concise but omits some details that would strengthen verifiability. Specifically, the paper does not describe the per-token accounting or the exact API pricing model (e.g., per-million-token rates for GLM-5.2, whether input/output tokens differ). The paper states that "roughly half of the calls are dev-reviewer source-grounding steps (the dominant wall-clock cost)" and provides a rough per-target distribution (Table 4), but a more detailed breakdown (e.g., average tokens per call, cost per agent stage) would help readers estimate the cost of adapting TestVDB to new targets. Additionally, the paper does not specify the runtime environment (e.g., Docker containers for VDBMS instances, whether the source clones are full repositories or shallow) or the hardware/software stack for running the LLM agents. These details are not critical for understanding the core contribution, but they would improve reproducibility for readers who want to replicate the pipeline. The paper's statement that "the full prompts, target versions, per-token accounting, the 48-candidate ground truth, and a reproduction driver are in the artifact" suggests these details are present in the repository, but surfacing them in the text (even as an appendix) would improve verifiability.

5. **Presentation** — Adequate

   - **5.1** The paper is well-structured and readable. The introduction clearly motivates the problem (documentation-implementation defects, crash-oracle blind spot), characterizes the oracle problem, and previews the contributions. The preliminaries section (Section 2) defines key concepts (VDBMSs, documentation-implementation consistency, oracle problem) and includes a valuable exclusion table (Table 1) that walks through standard oracle candidates and why they miss the documentation-implementation residual. The approach section (Section 3) describes the pipeline stages with concrete examples (the #49823 path) and figures (Figure 1 pipeline overview, Figure 2 dev-reviewer three-check falsification). The evaluation section (Section 4) is organized by research questions (RQ1 yield, RQ2 false-positive suppression, RQ3 VDBFuzz comparison, plus an external probe). The related work section (Section 6) positions the contribution against multiple prior lines. The conclusion summarizes the main results and the boundary marker. The structure is logical and complete. Language is generally clear, with only minor awkwardness in a few places (e.g., some sentences in Section 4.2 are dense and could be split).

   - **5.2 [minor, fixable]** The paper's discussion of LLM-as-judge reliability and cross-family variance is important for a complete technical picture but is buried in late subsections of Section 4.2 (after the operating-point tables and ablations) and Section 5 (limitations). These results (Cohen's κ, inter-family recall gaps, vendor-specific effects) are central to understanding the dev-reviewer's robustness and should be surfaced earlier in the evaluation narrative. For example, the cross-family re-run results could be integrated into the RQ2 subsection as a secondary analysis after the main GLM-5.2 retrospective, or summarized in a dedicated paragraph after Table 4. As presented, a reader might miss that the headline recall (74%) is GLM-5.2-specific and that other families achieve significantly lower recall. This is a presentation issue rather than a substance issue—the paper is honest about the limitation—but surfacing it earlier would improve the reader's understanding of the contribution's scope.

   - **5.3 [minor, fixable]** The paper contains a few minor notation inconsistencies and language issues that do not obstruct evaluation but should be corrected for publication. For example: (1) The abstract mentions "69% adjudicated yield" in the same sentence as "50 as true-positive defects," but the yield is 50/72 adjudicated (69.4%), not 50/107 submitted (46.7% worst-case). The abstract is technically correct but could be clearer ("69.4% of the 72 maintainer-adjudicated submissions"). (2) Table 4 uses "~50%" and "~25%" to approximate shares, but the table caption does not explain that these are rough distributions from a single run. (3) Some sentences in Section 4.2 are overly dense and could be split for clarity (e.g., the paragraph that introduces the 48-candidate retrospective and lists all operating points). These are minor blemishes that do not affect the paper's core claims but should be addressed in a revision.

### Questions for Authors

- **Q1:** Can you describe the selection criteria for the 48-candidate retrospective used in RQ2? Was this a random sample from the 107 submitted candidates, a convenience sample, or selected to balance vendors/defect types? — Intended effect: Clarifying the sampling strategy (item 3.2) would help readers assess potential selection bias in the precision/recall estimates.

- **Q2:** The cross-family re-run shows significant variance in recall across LLM families (DeepSeek 56%, LongCat 22%, Qwen 19% vs. GLM-5.2 74%). Can you analyze a few representative cases where GLM-5.2 confirms a defect but another family rejects it, and attribute the disagreement to specific failure modes (extraction hallucination, self-preference, source-grounding interpretation)? — Intended effect: A more fine-grained mechanism analysis (item 3.4) would help readers understand whether cross-family variance is addressable via prompt engineering or architectural changes.

- **Q3:** The operating-point selection (3-run any-confirmed union) is post-hoc. Did you consider pre-registering a selection rule (e.g., "choose the highest-recall ensemble with precision ≥ 60%") before analyzing the retrospective? — Intended effect: Clarifying the selection process (item 3.3) would strengthen the statistical rigor of the headline claim.
