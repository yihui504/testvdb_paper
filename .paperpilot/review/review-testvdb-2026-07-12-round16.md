## Reviewer 1: Domain Expert

**Overall Recommendation:** Accept

### Summary

The paper presents TestVDB, an LLM-driven system for detecting API compliance defects in Vector Database Management Systems (VDBMSs). VDBMSs increasingly underpin LLM applications, yet 43% of bugs in this domain are functional incorrect-behavior defects that lack practical oracles, as existing fuzzers like VDBFuzz only detect crashes. The authors introduce "API compliance defects"---bugs where a VDBMS silently accepts inputs or behaviors violating its documented contract---and propose Contract-Truth Separation (CTS) to mitigate a key failure mode: when one LLM family both generates a contract from documentation and judges compliance against it, hallucinated constraints are self-confirmed. TestVDB's dev-reviewer agent falsifies LLM-generated assertions against a truth layer grounded in maintainer authority (source code, prior PRs, issue history). Across five VDBMSs (Milvus, Qdrant, Weaviate, MeiliSearch, Chroma), TestVDB produced 111 submissions; maintainers acknowledged 36 (28 fixed). The work validates CTS primarily on Milvus and Qdrant, with three other systems serving as breadth probes. The authors honestly report boundary conditions: 75% of yield is boundary/validation compliance; crash bugs are excluded by design; soft result-correctness remains open; and a model-free invariant oracle subclass (e.g., COSINE distance bounded in [-1,1]) emerges as a transferable contribution independent of the LLM pipeline.

### Core Strengths

- **S1:** The problem targeting is significant and well-motivated: 43% of VDBMS bugs are incorrect-behavior defects that current fuzzers miss, and TestVDB is the first end-to-end realization for this class on the research agenda — see 1.1, 1.3.
- **S2:** Contract-Truth Separation (CTS) and the contract hallucination propagation observation are novel, well-motivated design principles with empirical backing (12 by-design cases, 25% of adjudicated submissions) — see 2.1, 2.2.
- **S3:** The model-free invariant oracle subclass (e.g., COSINE distance >1.0 for identical vectors, incomplete index results) is the paper's most defensible and transferable finding, needing no LLM judgment and reproducing across vendors — see 2.3, 3.2.
- **S4:** The evaluation is unusually thorough and honest: a controlled 52-candidate retrospective ($31\%\to 81\%$ FP suppression with 96.7% TP retention), multiple baselines (single-LLM, schema-fuzzer), and transparent sensitivity analysis (pending submissions, spec-completeness limits) — see 3.1, 3.3, 3.5.
- **S5:** Related Work coverage is comprehensive across VDBMS testing, REST API testing, database oracles, and LLM-based testing, with clear positioning against VDBFuzz (complementary oracles) and REST fuzzers (schema-driven vs. semantic compliance) — see 2.4, 2.5.

### Core Weaknesses

- **W1:** Single-layer grounding validation is narrow: the source-anchor lift ($31\%\to 81\%$ FP suppression) and threat-model ablation (noisy complement) are demonstrated only on Milvus (n=12 FPs), not across the five systems claimed — see 3.2 [major, fixable].
- **W2:** The threat-model anchor contribution is under-validated: after fixing a wiring gap, the ablation shows threat-alone is unstable and over-fires on state/concurrency cases, leaving the three-anchor design claimed as a contribution only partially validated on n=12 — see 3.4 [major, fixable].
- **W3:** Cross-system generalization of precision is claimed only for Milvus and Qdrant (adjudicated signal concentrated there); Weaviate (30 pending), MeiliSearch (3 excluded), and Chroma (1 pending) contribute near-zero adjudicated precision, so "cross-system" claims for the method's precision are overbroad — see 3.1 [major, fixable].
- **W4:** The schema-fuzzer baseline (71% post-filter precision on Milvus boundary probes) concedes that spec-driven fuzzing is effective on the 75% boundary/validation subset, weakening TestVDB's marginal value claim on that subset — see 3.3 [minor, fixable].
- **W5:** LLM contamination is not fully bounded: the memorization canary (0/9 held-out bugs recalled) is a positive control for recall, but the source anchor's power on Milvus could still be inflated by pre-2024 training data exposure — see 3.6 [minor, fixable].

### Detailed Assessment

1. **Significance** — Adequate

- **1.1** The problem is significant and well-established: 43% of VDBMS bugs are incorrect-behavior defects (Introduction, citing [roadmap25]), yet current testing focuses on crash/hang bugs (23.1%). TestVDB targets this majority gap with API compliance defects as a tractable slice. The problem motivation is clear, the stakes are practical (downstream LLM application correctness), and the work directly addresses the roadmap's flagged open challenge: "incorrect behavior poses significant challenges for test oracles" (Introduction).

- **1.2** The impact is bounded but meaningful: TestVDB produced 111 submissions across five VDBMSs, with 36 maintainer acknowledgments (28 fixed). The authors honestly report the boundary: 75% of yield is boundary/validation compliance, crash bugs are excluded by design (complementary to VDBFuzz), and soft result-correctness (ANN recall, ranking) remains open (§3.2, §3.6). This positioning makes clear what problem the work solves and what it deliberately leaves open, which is appropriate for a first realization.

- **1.3** The model-free invariant oracle subclass (e.g., COSINE distance >1.0 for identical vectors, incomplete index results, payload filters returning points with missing fields) is highly significant because it needs no LLM judgment and reproduces across Milvus and Qdrant (§3.2). This is the paper's most defensible and transferable finding---a set of expressible, hard-mathematical-bound oracles that can be adopted independent of TestVDB's agent-design choices. The COSINE invariant, in particular, violates a fundamental mathematical property (cosine similarity bounded in [-1,1]) and is therefore the least contingent on LLM reliability or prompt engineering.

- **1.4 [minor, fixable]** The cross-system significance claim is weakened by uneven validation: 75% of adjudicated signal (48/52 submissions with maintainer outcomes) concentrates on Milvus and Qdrant. Weaviate has 30 pending (21 pending, 5 excluded, 3 acknowledged), MeiliSearch has 3 excluded, and Chroma has 1 pending (§3.1). The authors qualify this honestly---"we claim cross-system generalization of the method's attack surface, not of its precision" (Contributions item 1)---but the title and abstract's broad five-system framing may overpromise on statistical generality. A clearer separation would help: Milvus+Qdrant as validated precision; others as attack-surface probes only.

2. **Novelty** — Adequate

- **2.1** Contract-Truth Separation (CTS) is a novel design principle with clear motivation: contract hallucination propagation, where one LLM family both generates a contract and judges compliance, leads to self-confirmed hallucinations (§4). The authors observe this concretely (formalizer fabricated a "complexity requirement" from constant.go; judge confirmed violations) and quantify it (12 by-design cases, 25% of 48 adjudicated submissions). CTS isolates assertion and truth layers, using maintainer-authority evidence (source code, PRs, history) to falsify LLM assertions. This is a principled reversal from "LLM as oracle" to "LLM as falsifiable claim," with the dev-reviewer as the concrete realization.

- **2.2** The dev-reviewer's three-anchor architecture (clean reproduction, source-grounded verification, threat-model cross-check) is a novel multi-agent verification pattern for LLM-driven testing. While multi-agent debate is known (du2023improving), CTS's specific split---assertion layer (LLM contract + 4-judge) falsified by a truth layer proxying maintainer authority---is new to VDBMS testing and to contract-oracle problems generally. The source anchor as "the direct counter to hallucination" (§3.5) is a well-motivated design choice.

- **2.3** The contract hallucination propagation phenomenon itself, to the authors' knowledge, has not been characterized in LLM-driven testing (§4). The observation that hallucinated constraints are self-confirmed under single-family generation-judgment is both qualitatively illustrated (fabricated provenance case) and quantitatively bounded (25% by-design rate). The contract counterfactual (feeding doc passages to DeepSeek) refines this: over-strict constraints reproduce in 2/3 of GLM-actual cases but 2/9 of an expanded N=10 set, indicating the problem is partly task-intrinsic (default-as-value cases) but predominantly GLM-specific. This is a nuanced contribution beyond "LLMs hallucinate."

- **2.4** Related Work coverage is comprehensive and well-positioned. The paper clearly situates itself against VDBFuzz (complementary: crash vs. compliance oracle), REST fuzzers (RESTler, EvoMaster, Schemathesis, foREST, MINER, DynER all schema-driven with 5XX/crash oracles; TestVDB extends to semantic compliance), database correctness oracles (NoREC, TLP, DQE assume reference SQL semantics; TestVDB replaces with documentation-derived invariants), and LLM-based testing (multi-agent debate adopted, but contract hallucination is a newly identified failure mode). The delta is clear.

- **2.5 [minor, fixable]** The schema-fuzzer baseline concedes that spec-driven fuzzing is effective on the boundary/validation subset (75% of yield). A hand-written boundary-value fuzzer on Milvus surfaced 7 API-accepted candidates, with 5 source-grounded as genuine violations (71% post-filter precision) and 2 as by-design defaults (§3.3). The authors acknowledge TestVDB's marginal value lies where the fuzzer cannot reach: state/logic, diagnostic, result-correctness probes (8/36 TPs are non-boundary), CTS FP-suppression (the fuzzer has no source-grounded layer), and spec-gap bugs. However, this narrows TestVDB's novelty on the dominant yield subset. A more explicit framing---"TestVDB complements schema fuzzing with semantic compliance and FP-suppression"---would sharpen the novelty claim.

3. **Soundness** — Adequate

- **3.1** The controlled retrospective (RQ3) is methodologically sound: all 52 maintainer-adjudicated candidates (36 TP, 16 FP) re-triaged under two blind conditions on the same population---claim-only (4-judge layer) vs. source-grounded (dev-reviewer's source anchor), outcomes hidden via label-isolated agents (§3.3). Source-grounding lifts FP suppression from 5/16 (31%) to 13/16 (81%, 2.6x) while retaining 29/30 TPs (96.7%, n=30; 6 TPs unreachable due to API rate limits). This same-population comparison is the cleanest evidence for CTS's contribution and avoids denominator-shifting that plagues many ablations.

- **3.2 [major, fixable]** The source-anchor validation is narrow: the 31%→81% lift and the Milvus breakdown (33%→75%, non-Milvus 0%→100%) are the only cross-system data. The threat-model ablation (§3.4) and single-layer arms are Milvus-only (n=12 FPs, n=4 TPs for threat-model; n=27 suppressed for single-layer). Weaviate, MeiliSearch, and Chroma have no source-anchor or threat-anchor validation. The authors claim CTS is "empirically validated" (Contributions item 2), but the validation is primarily Milvus+Qdrant only. Cross-library ablation beyond Milvus is future work (§3.6), which weakens the generalizability claim. The fix is to qualify the validation scope explicitly in the abstract/contributions: "validated primarily on Milvus and Qdrant."

- **3.3** Multiple baselines are provided with clear ground-truth tiering: single-LLM (LLM self-judgment, weak proxy), schema fuzzer (API-acceptance, weak proxy), single-layer 4-judge (claim-only re-triage, same population), TestVDB source-grounded (source re-triage, same population), and TestVDB end-to-end (maintainer adjudication, gold) (Table 2, Figure 4). The asymmetry is made explicit rather than disguised, and the retrospective and maintainer tiers share the same 52-candidate pool, enabling fair comparison. The schema-fuzzer baseline (71% post-filter precision) is a necessary concession that bounds TestVDB's marginal value.

- **3.4 [major, fixable]** The threat-model anchor contribution is under-validated. The initial ablation (v2.6.17, n=5 TP, 7 FP) was confounded by a wiring gap (threat_model.json vs. developer_cognition.json blindspot_indicators). After fixing the wiring, a three-condition ablation on the 12 Milvus FPs shows: source-alone suppresses 9/12 (75%), threat-alone suppresses 6/12 (50%, unstable across runs), union suppresses 11/12 (92%), with all conditions retaining 4/4 TPs (§3.4). The threat anchor catches 2 of source's 3 residuals (boundary-default cases) but over-fires on state/concurrency FPs (bs-03/06 push them toward CONFIRMED). The authors conclude it is "a noisy complement whose value is the union," but this is based on n=12 Milvus FPs only. The three-anchor design is claimed as a contribution (Contributions item 2), but the threat anchor's standalone effect and cross-system behavior are not validated. The fix is to downscale the claim from "three-anchor design" to "source anchor as primary, threat-model as noisy complement validated on Milvus only."

- **3.5** Threats to Validity are thoroughly and honestly addressed. Internal validity (maintainer acknowledgment as weak ground truth, selection bias, construct validity), external validity (same-population ablation is Milvus+Qdrant only), LLM variance (99.1% pairwise agreement, 45/46 unanimous), contamination (memorization canary: 0/9 held-out bugs recalled at issue-specificity), recall scope (96.7% is judgment-layer TP retention, not end-to-end discovery recall), and excluded-set (17/29 excluded are Milvus, potentially hiding FP tail) are all acknowledged with clear mitigation or bounding (§3.6). The contract counterfactual (DeepSeek reproduces over-strict constraints in 2/9 expanded cases) refines the GLM-specificity claim. This is above-average disclosure for a systems paper.

- **3.6** Aggregate precision is reported with sensitivity analysis: 69.2% adjudicated-only (36/52), within [43.9%, 80.5%] under pending-resolution sensitivity (30 pending submissions could swing to either extreme) (§3.3). The 29 excluded submissions (closed-no-label or duplicate) are excluded because their true status is unknowable post-closure, not because they were judged invalid. This interval reporting makes the selection effect explicit and is the right way to handle incomplete maintainer feedback. The single-layer end-to-end precision (45.6%) and TestVDB's 69.2% are presented as directional lifts, not as strict head-to-head comparisons, which is appropriate given the different ground-truth tiers.

4. **Verifiability** — Excellent

- **4.1** The paper provides a complete self-contained description of the TestVDB pipeline: five stages (contract extraction, attack generation, four-judge debate, dev-reviewer with three anchors, novelty gate), agent roles (20 LLM agents, 4 high-reasoning on GLM-5.2 high-budget, 16 low-budget), implementation details (Claude Code runtime, default sampling, no explicit temperature override), and reproducibility artifacts (pinned target versions, full prompts in anonymized artifact, end-to-end trace) (§2, §3.6). The wall-clock and token budgets are on the order of 10^4 LLM calls (~10^7 tokens) for the full study and 10^3 calls (~2x10^6 tokens) per target. An anonymized artifact repository (https://anonymous.4open.science/r/testvdb-anon-D644/) is declared and will be made public on acceptance. This satisfies the Verifiability criterion for a systems paper.

- **4.2** All evaluation data is presented with sufficient detail to reconstruct the analysis: Table 1 (yield by VDBMS with maintainer outcomes), Table 2 (precision/ground-truth comparison across arms with n, ground-truth tier, and 95% Wilson CI), Figure 4 (precision by ground-truth tier with whiskers), and detailed text breakdowns of each baseline (single-LLM, schema-fuzzer, single-layer 4-judge, source-grounded, end-to-end) (§3.1, §3.3). The 52-candidate retrospective (same-population comparison) and the 27 suppressed-candidate live re-probe (all 27 confirmed FP, over-kill 0/27) are fully described with case-class breakdowns. The threat-model ablation conditions (source-alone, threat-alone, union) are fully specified with n, FP suppression, TP retention, and stability notes (§3.4). A reviewer could follow these descriptions to verify the precision calculations and FP-suppression lifts.

- **4.3** The artifact link is declared and reachable (https://anonymous.4open.science/r/testvdb-anon-D644/). The paper states it contains "the five VDBMSs and all 111 submissions with their maintainer outcomes," plus "full prompts," "pinned target versions," and "precise per-token and wall-clock accounting" (§2, §3.6). This is sufficient for Verifiability; cloning and running is not required by the rubric. The artifact covers the full study pipeline, not just a subset, which is strong.

5. **Presentation** — Adequate

- **5.1** The paper is well-structured: Introduction (problem, motivation, approach, results, contributions, positioning), Background and Problem Formulation (VDBMS architecture, bug taxonomy, API compliance defects, oracle problem), Approach (overview, contract extraction, attack generation, CTS and dev-reviewer, novelty gate), Contract Hallucination Propagation (phenomenon, forms, mitigation), Evaluation (RQ1 yield, RQ2 case studies, RQ3 precision with controlled retrospective and baselines, RQ4 threat-model ablation, threats to validity), Related Work (VDBMS testing, REST API testing, database oracles, LLM-based testing, test oracles), Conclusion and Future Work. The flow is logical, and the CTS principle is motivated before the system description.

- **5.2** Figures and tables are clear and purposeful. Figure 1 (exclusion table) cleanly motivates why LLM is the only candidate oracle. Figure 2 (pipeline diagram) visually distinguishes assertion layer (blue) from truth layer (red) and marks anchor status (source solid, threat-model dashed, reproduction gray dashed). Table 1 (yield) cleanly reports submissions and maintainer outcomes with pendings/excluded separated. Table 2 (baselines) groups by ground-truth tier and makes asymmetry explicit. Figure 4 (precision by tier) uses darkness to indicate ground-truth strength and cleanly separates tiers. Case studies (RQ2) provide concrete end-to-end traces (Milvus #47729, #49844, #50193) that illustrate the TP/FP boundary and dev-reviewer's role.

- **5.3 [minor, fixable]** Language is occasionally dense or parenthetical, with some clauses stacked three-deep (e.g., §3.3: "precisionadj = acknowledged / (acknowledged + by-design + rejected) = 36/(36+12+4) = 69.2%"). The "model-free invariant oracle subclass" terminology is introduced abruptly (§3.2) without a forward reference; a clearer introduction in the Approach section would help. The "spec-completeness and version-pinning" limits (§3.3) are important design insights but could be surfaced earlier. These are minor clarity issues that do not obstruct understanding.

- **5.4 [minor, fixable]** There are scattered typos and formatting inconsistencies: "TestVDB's marginal value over a spec-driven fuzzer is its non-boundary yield plus source-grounded FP-suppression, not boundary-finding" (§3.3) has a missing "A" before "spec-driven fuzzer." "MeiliSearch" appears as both "MeiliSearch" and "MeiliSearch" (inconsistent spacing). The Wilson CI notation is introduced once but used consistently afterward. These are cosmetic and do not affect the core contribution.

### Questions for Authors

- **Q1:** The source-anchor validation (31%→81% FP suppression, 96.7% TP retention) and threat-model ablation (noisy complement) are demonstrated only on Milvus (n=12 FPs). Do you have any cross-library validation data on Weaviate, MeiliSearch, or Chroma? If not, would you qualify the CTS validation scope in the abstract to "validated primarily on Milvus and Qdrant"? — Intended effect: clarify the validation scope so readers do not assume cross-library anchor validation.

- **Q2:** The threat-model anchor is unstable across runs (one boundary FP flipped) and over-fires on state/concurrency FPs (bs-03/06). You conclude it is "a noisy complement whose value is the union," but this is based on n=12. Do you have plans to investigate whether a threat-model rewrite (e.g., separate state/concurrency blindspots) could stabilize it? — Intended effect: signal whether the three-anchor design is a working contribution or a preliminary observation.

- **Q3:** The schema-fuzzer baseline concedes that spec-driven fuzzing achieves 71% post-filter precision on Milvus boundary probes. You frame TestVDB's marginal value as (a) non-boundary yield (8/36 TPs), (b) CTS FP-suppression, and (c) spec-gap bugs. Have you measured the overlap between TestVDB's boundary yield and the fuzzer's? If ~1--2 overlap and 3--4 are variants, this supports complementarity; if higher, it strengthens the marginal value claim. — Intended effect: sharpen the novelty positioning against spec-driven fuzzing.

- **Q4:** The memorization canary (0/9 held-out bugs recalled) is a positive control for recall, but the source anchor's power on Milvus could still be inflated by pre-2024 training data exposure. Have you audited GLM-5.2's training cutoff? Does it include Milvus source before 2024? — Intended effect: bound the contamination risk more explicitly than "0/9 recalled" alone.

- **Q5:** The 30 pending submissions (21 Weaviate, 8 Qdrant, 1 Chroma) drive the precision sensitivity interval [43.9%, 80.5%]. Do you have any preliminary triage signals (e.g., reply rates, issue engagement) that suggest where these might land? — Intended effect: give readers a sense of whether the interval is symmetric or skewed toward one endpoint.

## Reviewer 2: Area Specialist

**Overall Recommendation:** Weak Accept

### Summary

TestVDB targets API compliance defects in Vector Database Management Systems (VDBMSs) — bugs where a system silently accepts inputs or behaviors that violate its documented contract. This is the majority of VDBMS bugs (43% incorrect-behavior vs 23% crash/hang), but crash-focused fuzzers like VDBFuzz cannot detect them because compliance defects produce no observable failure signal. TestVDB introduces Contract-Truth Separation (CTS): an LLM extracts contracts from API documentation and generates attack candidates, but a separate "truth layer" (a dev-reviewer agent) falsifies them using maintainer-authority evidence (source code, prior PRs, by-design intent). The authors report 111 submissions across five VDBMSs; 52 have maintainer adjudication (36 acknowledged, 28 fixed). On a controlled retrospective over the same 52 candidates, the dev-reviewer's source anchor lifts false-positive suppression from 31% to 81% while retaining 96.7% of true positives. The paper also identifies "contract hallucination propagation" — when one LLM family both generates and judges, hallucinated constraints self-confirm — with 12 by-design cases (25% of 48 adjudicated non-rejected submissions) as evidence. TestVDB is positioned as complementary to VDBFuzz (crash vs compliance) and to schema-driven fuzzers like Schemathesis (which require OpenAPI specs that VDBMS endpoints do not serve). The authors release an open-source system and reproducible dataset.

### Core Strengths

- **S1:** Contract-Truth Separation is a well-motivated design principle that addresses a real failure mode in LLM-driven testing — see 2.3, 5.1.
- **S2:** The controlled retrospective (31%→81% FP suppression, 96.7% TP retention) is a clean, same-population ablation that cleanly isolates the dev-reviewer's contribution — see 3.1.
- **S3:** The paper honestly concedes where alternatives are strong: it acknowledges that spec-driven fuzzers like Schemathesis are "genuinely effective" on the boundary/validation subset (75% of yield) — see 3.4.
- **S4:** The model-free invariant oracle subclass (e.g., COSINE distance bounded in [-1,1], incomplete index results) is the most defensible and transferable finding — it depends on no LLM judgment and reproduces across vendors — see 2.3.
- **S5:** The paper correctly positions novelty against LLM-driven REST testing tools like LlamaRestTest (generation quality vs hallucination mitigation) and RESTler (crash vs semantic compliance) — see Background, 2.3.

### Core Weaknesses

- **W1:** Cross-system generalization is only claimed for the attack surface, not precision: the 69.2% precision figure (36/52) is Milvus+Qdrant-dominated; Weaviate, MeiliSearch, and Chroma contribute near-zero adjudicated signal (3 TP, 0 by-design, 1 rejected, 22 pending), so the method's precision on non-Milvus/Qdrant systems is not established — see 3.1 [minor, fixable].
- **W2:** The threat-model anchor is presented as a three-anchor design in the contribution list but is ablated as a "noisy complement" on n=12, with no end-to-end validation — the paper hedges this appropriately, but the disconnect between the contribution framing and the weak evidence is notable — see 1.4, 3.5 [minor, fixable].
- **W3:** The single-layer counterfactual (45.6% precision) combines maintainer-adjudicated baseline with 27 live-reprobed, source-grounded FPs; while the authors acknowledge this, the comparison remains asymmetric across different ground truths — see 3.1 [minor, fixable].
- **W4:** The held-out-bug pilots (qdrant 1.5.0, milvus 2.3.0) are design insights, not measured recall: the paper bounds full recall by "spec-completeness and version-pinning limits" but provides no quantitative discovery-recall study — see 3.4 [minor, fixable].

### Detailed Assessment

1. **Significance** — Adequate
   - **1.1** The problem is real and under-served. VDBMSs underpin LLM applications, and incorrect-behavior bugs (43.0%) substantially outnumber crash/hang bugs (23.1%). Current fuzzers like VDBFuzz only target crashes, leaving the majority without a practical oracle — see Introduction. This is a meaningful but bounded impact: API compliance is a tractable slice of the incorrect-behavior problem, not the full result-correctness challenge that remains open.
   - **1.2 [minor, fixable]** Cross-system generalization is claimed for the attack surface, not precision. The yield concentrates on Milvus (51 submissions) and Qdrant (26); Weaviate (30 submissions), MeiliSearch (3), and Chroma (1) contribute near-zero adjudicated signal (3 TP, 0 by-design, 1 rejected, 22 pending). The paper honestly reports this and frames Weaviate/MeiliSearch/Chroma as "breadth probes," not statistical evidence — see Table 1, RQ1. However, this limits the significance of the 69.2% aggregate precision figure: it is well-supported only for Milvus and Qdrant. The method's precision on other VDBMSs is not established. A revision should either (a) de-emphasize the aggregate figure in favor of per-system reporting, or (b) run longer-horizon studies on Weaviate/MeiliSearch/Chroma to close the pending gap.

2. **Novelty** — Adequate
   - **2.1** Contract-Truth Separation is a clear delta over prior work. RESTler (Atlidakis et al., 2019) and Schemathesis (Hatfield-Dodds & Dygalo, 2021) target schema-conformance and crash/5XX oracles; TestVDB extends to semantic compliance against the documented contract. LlamaRestTest (Kim et al., 2025) fine-tunes LLMs for input generation; TestVDB's delta is orthogonal, targeting contract hallucination via maintainer-authority falsification, not input quality — see Section 6. The multi-agent debate (4-judge) draws on prior work (Du et al., 2023) but is novel in this VDBMS context.
   - **2.2** The paper correctly characterizes its competitors. I verified the characterizations of RESTler, Schemathesis, and LlamaRestTest against their original papers — see Background.md. No mischaracterizations were detected. The paper also honestly concedes where alternatives are strong: the schema-fuzzer baseline (Section 8.3) acknowledges that "on the boundary/validation subset (75% of yield), a spec-driven fuzzer is genuinely effective" — this is an appropriate limitation.
   - **2.3 [minor, fixable]** The threat-model anchor is framed as a three-anchor design in Contribution 2 ("a three-anchor counter-evidence pipeline") but is ablated as a "noisy complement" on n=12 with no end-to-end validation. The RQ4 ablation shows source-alone (9/12 FP suppression) vs threat-alone (6/12, unstable), with union (11/12) as the practical configuration. The paper hedges appropriately — "we do not claim the three-anchor design as a clean validated contribution on the strength of n==12" — but the contribution framing (three-anchor pipeline) is stronger than the evidence (noisy complement on small n). A revision should either (a) rephrase Contribution 2 to emphasize the source anchor as primary and threat-model as a noisy complement, or (b) strengthen the threat-model evaluation.
   - **2.4** Contract hallucination propagation is a novel observation. The 12 by-design cases (25% of 48 adjudicated non-rejected submissions) are direct observations, and the contract counterfactual (feeding the same doc passages to DeepSeek) refines the task-intrinsic vs model-specific reading — see Section 5. However, the paper correctly notes this is a qualitative characterization, not a measured prevalence; a full frequency study is future work. This is appropriate scoping.

3. **Soundness** — Adequate
   - **3.1** The controlled retrospective (RQ3) is the core evidence. Re-triaging all 52 maintainer-adjudicated candidates under two blind conditions on the same population (claim-only vs source-grounded) shows the dev-reviewer's source anchor lifts FP suppression from 31% to 81% while retaining 96.7% of TPs (29/30 reachable via GitHub API; 6 TPs rate-limited) — see RQ3. This is a clean, same-population ablation that isolates the dev-reviewer's contribution. The 69.2% aggregate precision (36/52) is a valid end-to-end operating point, with the sensitivity interval [43.9%, 80.5%] appropriately bounding the 30 pending submissions.
   - **3.2 [minor, fixable]** The single-layer counterfactual (45.6% precision) combines the maintainer-adjudicated 36/52 baseline with 27 live-reprobed, source-grounded FPs. The authors acknowledge the asymmetry: "the residual gap is that triage might reclassify a few of the 27, and the arm is bounded to one feedback cycle" — see RQ3. However, the comparison rests on different ground truths (maintainer adjudication vs live re-probe + source grounding). The same-population 31%→81% figure is cleaner; the 45.6% figure is a directional lift at zero recall cost but should be framed cautiously as a bounded counterfactual, not a definitive baseline.
   - **3.3 [minor, fixable]** The threat-model anchor ablation (RQ4) has a wiring gap confound: the original negative was confounded because the dev-reviewer consumed `developer_cognition.json`'s blindspot indicators (empty) rather than `threat_model.json`. The authors re-ran with the wiring fixed, but the ablation remains small (n=12 Milvus FPs). ## Reviewer 3: General Reviewer

**Overall Recommendation:** Weak Accept

### Summary
The paper introduces TestVDB, an LLM-driven system for detecting API compliance defects in Vector Database Management Systems (VDBMSs). VDBMSs suffer from functional correctness bugs (43% of all bugs) that do not crash, making them invisible to crash-oracle fuzzers like VDBFuzz. TestVDB targets "API compliance defects"—behaviors that violate documented API contracts, such as accepting invalid parameter values or returning incorrect status codes. The core technical contribution is Contract-Truth Separation (CTS), which separates LLM-generated assertions from a truth layer that falsifies them using maintainer-authority evidence (source code, prior PRs, issue history). TestVDB produced 111 issue submissions across five VDBMSs; 52 received maintainer adjudication (36 acknowledged, 12 by-design, 4 rejected), yielding 69.2% adjudicated precision. A controlled retrospective on the same 52-candidate pool shows that the dev-reviewer's source anchor lifts false-positive suppression from 31% to 81% while retaining 96.7% of true positives. The paper also identifies "contract hallucination propagation"—when one LLM family both generates the contract and judges compliance, hallucinated constraints are self-confirmed—and reports 12 by-design cases (25% of adjudicated submissions) as evidence.

### Core Strengths
- **S1:** The paper articulates a clear, motivated problem: API compliance defects lack practical oracles and represent a substantial gap (43% of VDBMS bugs vs. 23% crash/hang bugs) — see Introduction, §1.
- **S2:** The Contract-Truth Separation design principle is crisply defined and motivated by concrete observations of contract hallucination propagation (12 by-design cases, 25%) — see §5, §4.
- **S3:** The evaluation design is unusually honest and thorough: a controlled retrospective on the same 52-candidate pool (primary FP-suppression evidence), end-to-end maintainer adjudication, multiple baselines (single-LLM, schema-fuzzer, single-layer), and explicit sensitivity analysis for pending submissions — see §6.3.
- **S4:** The model-free invariant oracle subclass (COSINE distance >1.0 for identical vectors, incomplete index results, payload filters returning points with missing field) is the most defensible and transferable finding — violates hard mathematical bounds, needs no LLM judgment, reproduces across vendors — see §6.2.
- **S5:** The paper is forthright about limitations: cross-system generalization is claimed for Milvus/Qdrant only (Weaviate, MeiliSearch, Chroma are breadth probes), threat-model anchor is a noisy complement, reproduction anchor remains unevaluated — see §1, §6.3, §6.4.

### Core Weaknesses
- **W1:** Precision is validated on only two systems (Milvus and Qdrant); Weaviate, MeiliSearch, and Chroma contribute near-zero adjudicated signal, so claims of cross-system generalization are provisional — see 1.1, 1.2, 2.2, 4.1.
- **W2:** The threat-model anchor evaluation is on n=12 FPs only and shows mixed results (50% FP suppression, unstable across runs); treating it as a validated component requires stronger evidence — see 3.3.
- **W3:** No external baseline (e.g., VDBFuzz head-to-head, Schemathesis comparison) is provided; all arms are internal, which limits confidence in marginal value — see 3.5, 3.6.
- **W4:** Related Work coverage is thin on REST API testing competitors; RESTler, EvoMaster, Schemathesis are each mentioned in one paragraph without detailed positioning — see 5.1, 5.2.

### Detailed Assessment

1. **Significance** — Adequate
- **1.1** The paper identifies a real and motivated problem: incorrect-behavior defects represent 43% of VDBMS bugs (of which API compliance is a tractable subset), substantially outnumbering crash/hang bugs (23%), and are invisible to crash-oracle fuzzers like VDBFuzz — see Introduction. The motivation is clear and grounded in empirical bug-study data.
- **1.2** The impact is bounded and specialized: TestVDB targets boundary/validation compliance (75% of yield) and complements crash-focused fuzzing; it does not solve general result-correctness (ANN recall), which remains open — see §1, §6.1, §8. The contribution is significant within its specialized scope but not broad enough to be transformative for the field.
- **1.3 [minor, fixable]** The paper hedges cross-system generalization claims appropriately, stating that precision is validated on Milvus and Qdrant only, with Weaviate, MeiliSearch, and Chroma serving as breadth probes — see §1, §6.1. This honesty about the scope of validation is a strength, but the three breadth probes collectively contribute only 4 adjudicated outcomes (3 acknowledged, 1 rejected), so they are effectively anecdotal evidence for generality.

2. **Novelty** — Adequate
- **2.1** The Contract-Truth Separation principle and its dev-reviewer realization are novel to my knowledge: separating LLM-generated assertions from a maintainer-authority truth layer and falsifying them through source-grounded verification is not, per the paper's own Related Work survey, an existing pattern in LLM-driven testing — see §4, §5. The paper identifies a new failure mode (contract hallucination propagation) and proposes a mitigation (CTS).
- **2.2** The novelty is incremental rather than transformative: multi-agent LLM systems for testing are surveyed (He et al. 2025), and LLM-as-judge patterns exist; TestVDB's delta is identifying contract hallucination propagation and instantiating source-grounded falsification as the mitigation — see §5.4. This is a real but focused contribution within a broader area.
- **2.3 [minor, fixable]** The Related Work section is thin on REST API testing competitors: RESTler, EvoMaster, Schemathesis, foREST, MINER, and DynER are each mentioned in one paragraph without detailed positioning on how TestVDB's semantic compliance oracle differs from their schema-conformance and crash-oracle approaches — see §5.2. This makes it difficult for a non-specialist to assess precisely how TestVDB extends or differs from prior work.
- **2.4** The model-free invariant oracle subclass is novel in the VDBMS context but conceptually straightforward: identifying violations of hard mathematical bounds (COSINE distance ∈ [-1,1]) is a general testing principle, not specific to TestVDB — see §6.2. The value is in recognizing this subclass within the VDBMS domain and showing it reproduces across vendors.

3. **Soundness** — Adequate
- **3.1** The core claim—that source-grounded falsification improves FP suppression from 31% to 81% on a controlled 52-candidate retrospective—is strongly supported: the paper explicitly states that this is a same-population comparison (the 52 maintainer-adjudicated candidates) under two blind conditions (claim-only vs. source-grounded), outcomes hidden via label-isolated agents — see §6.3. This is a clean experimental design, and the 2.6× lift is substantial.
- **3.2** The maintainer-adjudicated precision of 69.2% (36/52) is clearly reported as an end-to-end operating point, not as the "after" arm of the ablation ratio above, because it is measured on a different population (five libraries) and denominator (adjudicated submissions) — see §6.3. The paper honestly distinguishes between the controlled retrospective (same-population internal comparison) and the end-to-end maintainer adjudication (cross-system external evidence).
- **3.3** The threat-model anchor evaluation is limited and preliminary: the ablation is on n=12 FPs only, the threat-alone condition suppresses 50% (6/12) and is unstable across runs (one boundary FP flipped between runs), and the union with source reaches 92% (11/12) but TP retention is only measured on 4 TPs — see §6.4. The paper treats this as an exploratory result and explicitly states that it does not claim the three-anchor design as a clean validated contribution on the strength of n=12, which is appropriate given the weak evidence, but this means the threat-model anchor is effectively an unvalidated optional prior rather than a working component of the evaluated system.
- **3.4** The paper is forthright about LLM variance contamination: it reports 99.1% pairwise agreement and 45/46 unanimous verdicts when re-adjudicating the 46 source-grounded candidates five times with independent agents, noting that judgment-layer noise is near-zero and residual variance sits upstream in version-pinned source extraction — see §6.5. It also directly audits GLM-5.2 memorization with a canary (0/9 recalled at issue-specificity), bounding discovery recall against training-data regurgitation — see §6.5. This level of rigor around LLM reliability is unusually strong.
- **3.5 [minor, fixable]** No external baseline (e.g., VDBFuzz head-to-head, Schemathesis comparison) is provided: all arms are internal to TestVDB (single-LLM, single-layer, schema-fuzzer post-filter), which limits confidence in the marginal value of the full system — see §6.3. The paper argues that complementarity follows from the oracle definitions (VDBFuzz targets crashes, TestVDB targets non-crash compliance) and that a head-to-head empirical comparison on identical targets is future work, which is a reasonable position but leaves the practical advantage over existing tools under-demonstrated.
- **3.6** The schema-fuzzer baseline is limited and directional: it surfaces 7 API-accepted candidates (probe→accept rate 37%) on 19 hand-written probes derived directly from Milvus's documented parameter constraints, and source-grounded post-filter classifies 5 as genuine violations (71%) — see §6.3. This shows that on the boundary/validation subset (75% of yield), a spec-driven fuzzer is genuinely effective, which TestVDB concedes, but the comparison is on a single system (Milvus) and a small set of probes, so it is evidence rather than proof.

4. **Verifiability** — Excellent
- **4.1** The paper provides exceptionally detailed evaluation methodology: the controlled retrospective explicitly states that it re-triages all 52 maintainer-adjudicated candidates under two blind conditions on the same population (claim-only vs. source-grounded), outcomes hidden via label-isolated agents — see §6.3. The single-layer arm (27 suppressed candidates, all live-reconfirmed as FP via fresh Docker re-probe) is described with concrete steps (fresh milvus v2.6.19 container, source grounding via constants plus observed response code) — see §6.3. This level of procedural detail is well above the typical for this venue.
- **4.2** The paper links to an anonymized artifact (https://anonymous.4open.science/r/testvdb-anon-D644/) and states that precise per-token and wall-clock accounting, target VDBMS versions (e.g., Milvus 2.6.19 for the single-LLM and single-layer ablations), and full agent prompts are part of the artifact — see §4. The abstract states that an open-source system and reproducible dataset spanning the five VDBMSs and all 111 submissions will be made public on acceptance. The artifact declaration is reachable and specific.
- **4.3** The paper provides granular sensitivity analysis: it distinguishes between 30 pending submissions (open, awaiting triage) and 29 excluded submissions (closed-no-label or duplicate, unresolvable), and reports the precision interval [43.9%, 80.5%] under pending-resolution sensitivity — see §6.3. It also bounds the single-layer arm's FP inflow via live re-probe (27/27 live, over-kill 0/27) and classifies FP classes (5 input-validation rejections, 4 by-design upsert/idempotent accepts, 5 correct rejections, 5 oracle script bugs, 8 state-semantics cases) — see §6.3. This level of transparency around uncertainty is exemplary.
- **4.4** The paper honestly reports all experimental results, including negatives: the RQ4 threat-model anchor ablation returned an exploratory negative (TP recall 20%/60%, blindspot indicators never reached the dev-reviewer's consumption path, agent unstable across runs), which was later diagnosed as a wiring gap — see §6.4. The paper re-ran the ablation with the wiring fixed and reports the mixed results (threat-alone 50% FP suppression, unstable across runs). This candor about false starts and limitations is rare and strengthens confidence in the positive results.
- **4.5** The paper reports LLM variance measurements and memorization audits: 99.1% pairwise agreement, 45/46 unanimous verdicts on five independent re-adjudications, with the explicit statement that judgment-layer noise is near-zero; a memorization canary returned 0/9 specific issues recalled at the specificity needed to regurgitate them through the pipeline — see §6.5. This controls for a common concern in LLM-based methods and makes the results more verifiable.

5. **Presentation** — Excellent
- **5.1** The paper is exceptionally well-structured: the problem formulation (§2), approach (§4), contract hallucination observation (§5), and evaluation (§6) follow a clear logical flow, with the controlled retrospective as the primary evidence and end-to-end adjudication as secondary — see the overall structure. The separation between same-population internal comparison (retrospective) and cross-system external evidence (maintainer adjudication) is consistently maintained throughout.
- **5.2** The figures and tables are clear and informative: Figure 1 (TestVDB pipeline) visually distinguishes the assertion layer (blue) from the truth layer (red) and marks the primary (solid) and unvalidated/dashed anchors — see §4. Table 2 (yield and maintainer outcomes) cleanly presents the adjudication counts and clearly separates pending from excluded submissions — see §6.1. Table 3 (precision/ground-truth comparison) groups arms by truth tier and explicitly states that rows are not directly comparable across tiers — see §6.3.
- **5.3** The writing is unusually precise and honest: the paper consistently qualifies claims (precision validated on Milvus and Qdrant only; threat-model anchor is a noisy complement; reproduction anchor remains unevaluated; single-layer arm is bounded to one feedback cycle) and avoids overstatement — see §1, §6.3, §6.4. The distinction between "validated on Milvus and Qdrant" vs. "breadth probes on Weaviate, MeiliSearch, Chroma" is maintained throughout. This level of nuance is rare and greatly improves readability.
- **5.4** The related work section, while thin on REST API testing competitors (see 2.3), is well-organized by sub-area (VDBMS testing, REST API and schema testing, database correctness oracles, LLM-based testing and verification, test oracles and contracts) and positions TestVDB's delta relative to each — see §5. The citations are recent and relevant.
- **5.5 [minor, fixable]** The abstract contains a compressed sentence that is difficult to parse on first reading: "On a controlled retrospective, the dev-reviewer's source anchor lifts false-positive suppression from 31% to 81% while retaining 96.7% of true positives; source is the validated primary anchor (threat-model a noisy complement, reproduction future work)" — see Abstract. The parenthetical structure and compressed terminology make this sentence dense; expanding or splitting it would improve clarity.
- **5.6 [minor, fixable]** The threat-model anchor evaluation description is dense and difficult to follow: the wiring gap diagnosis (threat-modeler populated threat_model.json but dev-reviewer consumed developer_cognition.json's blindspot_indicators field) and the three-condition ablation (source-alone, threat-alone, union) are compressed into a single long paragraph — see §6.4. Breaking this into multiple sentences or a small table would improve readability.

### Questions for Authors
- **Q1:** The Related Work section on REST API testing (§5.2) is thin: RESTler, EvoMaster, Schemathesis, foREST, MINER, and DynER are each mentioned in one paragraph. Can you elaborate on how TestVDB's semantic compliance oracle (documented contract vs. observed behavior) differs from their schema-conformance (OpenAPI-driven) and crash-oracle (5XX) approaches? — intended effect: if the authors clarify this positioning in Related Work, item 2.3's rating would move up because Novelty would be better contextualized relative to prior work.
