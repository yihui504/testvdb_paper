## Reviewer 1: Domain Expert

**Overall Recommendation:** Weak Accept

### Summary

The paper targets documentation-implementation bugs in vector database management systems (VDBMSs): cases where the system silently accepts an input or returns a behavior that violates its own natural-language API documentation (e.g., `nprobe=0` accepted although documented as $[1, 16384]$). The authors first argue, via a candidate-by-candidate exclusion table (Table 1), that every standard test-oracle family anchors its expectation somewhere other than system-level untagged prose — crash signals, other implementations, metamorphic relations, machine-checkable properties, or structured OpenAPI/trace/source specifications — leaving an LLM-derived oracle as the practical option, with its attendant false-positive problem. They then present TestVDB, a four-stage multi-agent pipeline: behavioral specification extraction from crawled documentation, pre-bound test-strategy generation, Docker-pinned sandboxed execution with raw HTTP logging, and a confirmation stage that splits evidence assembly from cross-examination (contract, physical, maintainer-cognition, and implementation-source perspectives, with the source as the falsification anchor).

Empirically, across Milvus, Qdrant, and Weaviate, maintainers confirmed 51 of 81 adjudicated submitted issues as real bugs and 23 were fixed via merged PRs (Table 2). A controlled five-arm re-adjudication of that pool under frozen packages and blinding shows the contract core intercepts 87–90% of false positives at 88.9% verdict agreement but recalls only 0.196–0.333 of the true bugs; adding source forensics and cognition reaches majority-vote recall 0.373 at perfect suppression; an independent source-only arm reaches 0.333; and a flat single-prompt judge matches the structured stage — so the paper attributes the gain to evidence access (the source), not judgment structure. A bidirectional probe against VDBFuzz on the same Qdrant instance shows the crash oracle reaches none of the silent-accept defects, while TestVDB's boundary reasoning reaches VDBFuzz's crash-class integer overflow, with the zero carefully audited rather than assumed.

### Core Strengths

- **S1:** The oracle-exclusion analysis (Table 1, Sections 2.3 and 6) is a genuine conceptual contribution: organizing oracle candidates by *where their expectation anchors* cleanly delimits the residual that forces an LLM oracle, and my verification against the closest competitors found the characterizations accurate — see 2.1.
- **S2:** Real, externally validated impact: 51 maintainer-confirmed bugs with 23 merged fix PRs, every fix PR classified by changed files (none documentation-only), with a self-check of the classifier against the disproved #9149 — see 1.1, 3.5.
- **S3:** Exemplary measurement honesty: the blinded frozen-package five-arm re-adjudication, the explicit withdrawal of an earlier unblinded recall figure (0.841) and of a wrong VDBFuzz explanation, and the demotion of the paper's own scaffolding after the flat-judge arm matched it — see 3.1, 3.2, 3.6.
- **S4:** The RQ3 zero-result audit is far above community norm: VDBFuzz's success/failure counters are shown uninformative (one failure marker unreachable, the other mismatched; 100% success with no server), the zero is re-measured with a per-template liveness oracle over 22,540 mutations, and the mutation space's inability to construct the crash class is bounded from two directions — see 3.3.

### Core Weaknesses

- **W1:** End-to-end precision is unmeasured: the extraction stage has no constraint-level audit against the cited documentation pages, and the four contract-core false-positive leaks are shown to be extraction-induced — the paper concedes this, but it leaves the pipeline's headline usability claim (precision of what a user actually receives) open — see 3.4.
- **W2:** The central mechanism attribution ("source grounding carries most of the gain") rests on pairwise deltas that are not individually significant (McNemar $p{=}0.093$; $p{=}0.017$ uncorrected does not survive Holm), and the second-backbone replication covers one arm with a backbone/runtime confound — the claims are hedged, but the abstract still leads with the ordering — see 3.5.
- **W3:** The RQ1 yield measures the human–machine pipeline with author-side novelty screening and submission decisions in the loop; the automated stage's standalone yield is only directionally anchored (19/32 on a seeded sample), so the operational significance of the tool *as an automation* is not established — see 1.2, 3.6.
- **W4:** Table 1's binary framing ("anchored in structured sources ... misses the residual") overstates the delta against SATORI, whose LLM reads natural-language OAS descriptions and whose confirmed real bugs include documentation-implementation mismatches on the response side; the honest axis is response-field vs. input-acceptance/state coverage, which Related Work states correctly but Table 1 does not — see 2.3.

### Detailed Assessment

1. **Significance** — Adequate
   - **1.1** The deployment evidence is strong and externally grounded (Section 4.2, Table 2): 51/81 adjudicated submissions confirmed by maintainers, 23 fixed via merged PRs that all modify implementation code, plus per-system acceptance labels (50/51 with an official `bug` label). For a new testing target on production infrastructure (Milvus, Qdrant, Weaviate), this is meaningful practical impact, and the bug-pattern taxonomy (Table 3, silent-accept family = 72.5%) gives the field a concrete shape for the non-crashing majority the bug study says dominates (functional failures = 57.3% of VDBMS bug symptoms, per the cited empirical study).
   - **1.2 [minor, fixable]** The significance of the *automated* pipeline is bounded by the paper's own measurements: blinded recall tops out at 0.373 (majority, full stage) on the pool, and the operational yield carried author-side screening (Section 4.2). The paper is candid about both, but a practitioner deciding whether to adopt TestVDB unattended still lacks a direct number; the 32-candidate seeded anchor (0.594 blinded re-confirm rate on never-submitted candidates, Section 4.3 first paragraph) helps but is directional only, as the authors themselves note.
   - **1.3 [minor, unfixable]** Scope is bounded to prose-constraint APIs of three systems and disclaims transfer to schema-constrained systems (Section 5, external validity); this inheres in the contribution and is properly disclosed.

2. **Novelty** — Adequate
   - **2.1** The anchor-inversion delta is real and verified against the paper's closest competitors. Against MASTOR (fetched; arXiv/CoRR 2026): the paper's claim that "source-derived oracles (MASTOR) encode implemented behavior and cannot detect a documentation-code gap" matches MASTOR's own self-stated limitation almost verbatim ("It cannot detect violations of intended requirements that are not reflected in code"), so the inversion — prose as ground, implementation as falsifier — is a genuine repositioning, and the paper honestly concedes that "a generated oracle reviewed by a second LLM agent" (MASTOR's ChallengerAgent) is not new. Against CASCADE (FSE 2026, fetched): the quoted residual-FP diagnosis ("the generated code and tests made the same false assumption over something underspecified in the documentation") is accurate, and the critique that CASCADE's falsifier shares the documentation's ambiguity holds — CASCADE's Phase-2 check regenerates code from the same documentation, whereas TestVDB's falsifier is the pinned implementation source. Against Metamon (LLM4Code 2025, fetched): the quoted profile (precision 0.722 at recall 0.480 on 9,482 pairs; 0.967 only as recall falls to 0.099) is exact, and Metamon's summary confirms no independent non-LLM evidence source is consulted — so "its falsifier is another LLM question" is fair. Against VDBFuzz (ICSE 2026, fetched): the crash-oracle-by-design characterization matches its self-stated limitation, and the RQ3 artifact-level claims I could check (205 released Qdrant templates; 120-minute-per-tool protocol; Qdrant case study = integer overflow) all match.
   - **2.2** The honest demotion of the four-perspective scaffolding to "discipline and auditability" after the flat-judge arm matched it (Section 4.3, "Does the scaffolding itself matter?") is a novelty-relevant act of intellectual hygiene that strengthens what remains: the measured contributions are the anchor analysis, the pre-bound strategy mechanism, and the evaluation methodology, not the panel structure.
   - **2.3 [minor, fixable]** Table 1's row-5 framing ("anchored in structured sources ... Why it misses the documentation-implementation residual") is broader than the verified delta. SATORI (ASE 2025, fetched) prompts an LLM with natural-language OAS field descriptions and its 18 confirmed real bugs include documentation-implementation mismatches (undocumented enum values, values outside documented ranges) — i.e., documentation-implementation inconsistency on the response side. The defensible delta is (a) input-acceptance/state behavior vs. response-field properties and (b) system-level untagged prose vs. OAS-embedded field descriptions; Related Work states exactly this, but Table 1 and the abstract's wording ("no deterministic-oracle candidate derives its expectation from it—crash signals, reference implementations, output relations, and schemas all fall structurally short") read as if the whole residual were untouched. Tighten the table wording.
   - **2.4 [minor, fixable]** Missing related work: DGDB (arXiv 2402.00292) applies LLM-generated queries with differential testing to detect wrong-result bugs in graph database engines (Neo4j, AgensGraph, JanusGraph) — the closest sibling-domain instance of LLM-in-the-loop non-crashing bug detection for non-relational DBMSs; its oracle is differential (which the paper covers), but the VDBMS-testing paragraph should position against it. All other coverage-search hits were either already cited (Doc2OracLL, ChatAssert, DocTer, RBCTest, SATORI) or not genuinely related.
   - **2.5 [minor, fixable]** MASTOR is positioned as "the closest to this work" but is, per its own metadata, an arXiv/CoRR preprint without a peer-reviewed venue yet; the dependency of the central "anchor inversion" positioning on an unreviewed closest-competitor deserves a note.

3. **Soundness** — Adequate
   - **3.1** The five-arm RQ2 protocol is methodologically careful: identical frozen packages across three independent runs per arm, blinding from adjudication labels and issue history, 81/81 per-run denominators with per-case judgments written at run time, a conservative binary adjudication rule (uncertainty resolves to False-Positive), majority voting, Wilson intervals, exact McNemar tests with Holm-correction honesty, and a seeded 32-candidate anchor showing the submission filter does not inflate pool confirmability. The arithmetic in Tables 4 and 5 is internally consistent (all rows sum to 81; all quoted rates recompute correctly from the cell counts, e.g., 11/51 = 0.216, 19/51 = 0.373, 17/18 = 0.944, 26/30 = 0.867).
   - **3.2** Construct-validity handling is unusually mature for this area: ground truth is revisable (the #9149 seven-version re-probe that disproved a "fixed" TP), duplicates are tracked orthogonally, the two senses of "false positive" are explicitly separated, and the disagreement analyses (four contract-core leaks are pack-induced; three unanimous, one 2–1; 13/81 full-stage disagreements all on the recall side) localize errors rather than averaging over them.
   - **3.3** The RQ3 audit sets a standard: the zero is shown to be measured rather than a silent no-op (22,540 mutations, 23,258 responses over 96 endpoint paths), the harness counters are demonstrated uninformative (exit-zero success; one failure marker emitted by no code path; 100% success against a dead port), the crash class is shown unconstructible in the released mutation space (boundary set topping at 65,536; dimension candidates at 10,000), and the earlier wrong explanation (sync-only upsert path) is explicitly withdrawn.
   - **3.4 [major, fixable]** End-to-end precision is unmeasured, and the paper says so: "We report no constraint-level audit of extraction accuracy against the cited documentation pages, so end-to-end precision—extraction and confirmation together—is unmeasured" (Section 4.3). This matters because the four contract-core FP leaks are shown to be pack-induced (extraction-side), i.e., the stage boundary the paper measures is not the boundary a user experiences. A constraint-level audit on the three targets (90 Qdrant constraints are already enumerated) is feasible within a revision cycle and would close the paper's biggest evidentiary gap.
   - **3.5 [major, fixable]** The mechanism attribution is underpowered at this pool size: source-only vs. core is $p{=}0.093$, full vs. core is $p{=}0.017$ uncorrected and "does not survive Holm correction across our six paired tests," and source-only vs. full is indistinguishable ($p{=}0.648$) — yet the abstract states "the ordering consistent with source grounding carrying most of the gain" as a headline. The second-backbone replication of the source-only arm (Qwen3.8-Flash, 76/81 agreement) mitigates, but the authors disclose that backbone and agent runtime co-varied, and the other three arms remain single-family. Either add runs to power the pairwise contrasts or demote the ordering claim in the abstract to the hedged form used in Section 4.3.
   - **3.6 [minor, fixable]** The RQ1 ledger ran unblinded with both disclosed judgment-side threats live (expectation-framing bias, observation leakage, Section 5); external maintainer adjudication contains the damage for confirmed bugs, but the 63.0% precision figure and the FP denominator (30) inherit the authors' own screening selectivity. The paper's own analysis of the induced bias is sound; the residual concern is unavoidable framing, not an error.
   - **3.7 [minor, fixable]** RQ3's reverse direction has a provenance and parameter ambiguity: the text says "TestVDB's boundary probe reaches it as a documentation-implementation violation: the OpenAPI declares `size` $\geq 1$ with no maximum" (Section 4.4), while the footnote attributes the crash to a *dimension* overflow ("a dimension of $2^{62}$ or larger to overflow dim$\times$sizeof(f32)") and says "We reproduced the crash by hand on Qdrant v1.4.0." It is unclear whether an automated TestVDB-generated probe fired the panic end-to-end on v1.4.0, and whether the unbounded parameter that triggers it is the query `size` or the vector dimension — as written, the two passages do not reconcile.
   - **3.8 [minor, fixable]** Three of the four judgment arms (contract core, full stage, flat judge) are single-backbone measurements on one LLM family under vendor default sampling (Section 5); the cross-family check covers the source-only arm only. Disclosed, but it bounds the generality of the suppression numbers.

4. **Verifiability** — Adequate
   - **4.1** The declared replication package (Data Availability) is comprehensive: agent role definitions, the strategy-trigger registry, per-version knowledge bases and specifications, all generated scripts with raw HTTP logs, one evidence chain per candidate, the full submission ledger (81 adjudicated + 49 unadjudicated, per-case), the frozen RQ2 packages with per-case judge outputs for every arm, RQ3 baseline reports with per-template logs, and analysis scripts that recompute every reported rate, interval, and paired test. The link is declared with a reachable-looking anonymous repository; per the review protocol I did not clone it, but the package as described would allow an independent reader to re-derive every number in Tables 4–5 from the shipped per-case outputs, which is the strongest form of verifiability for an LLM-pipeline paper.
   - **4.2 [minor, fixable]** Models are pinned only by serving identifiers with dates ("GLM-5.3-Flash (September 2026)", "Qwen3.8-Flash") rather than immutable weights snapshots, under vendor default sampling — exact re-execution is impossible by construction (disclosed in Section 5). Since all judge outputs are shipped, the rates remain checkable, but the extraction and generation stages' outputs should likewise be regenerable from the shipped role prompts; the package claims to include these, so this is a completeness check rather than a gap.
   - **4.3 [minor, fixable]** The one-run process funnel (Section 4.2, "Process ledger of one complete run") reports 119 chain verdicts → 96 candidates → 60 confirmed → novelty-gate partition (19/11/5/25) → 44 → 5 new defect numbers, with the last two steps explicitly "many-to-one without a maintained per-step count." The disclosure is honest, but the derivation of the final count cannot be checked from the text; the artifact presumably contains the underlying records, and the paper should say where.

5. **Presentation** — Adequate
   - **5.1 [minor, fixable]** The abstract is overloaded: it packs five number groups (87–90%, 88.9%, 0.196–0.333, 0.373/0.333, plus the five-arm logic and the bidirectional VDBFuzz probe) into dense sentences that require the reader to already understand the arm structure. Two or three headline numbers with the tradeoff framing would serve better.
   - **5.2 [minor, fixable]** Section 4.3 (RQ2) is a sequence of long run-in-bold paragraphs, some nearly a page ("Which perspective carries the decision" interleaves a fourth arm, a re-aggregation caveat, a cognition re-aggregation, and a backbone replication in one block). The material is important, but sub-subsection headings or an arms-overview table would substantially aid navigation.
   - **5.3 [minor, fixable]** The same quantities (0.373, 0.333, 87–90%, 51/81, 23) are restated in the abstract, introduction, contribution list, RQ1/RQ2, and conclusion — at least three full restatements each. Trimming the introduction's near-duplicate of the abstract would free space for the RQ2 restructuring above.
   - **5.4 [minor, fixable]** Notation load in RQ2 is high: "pack," "case," "leak"/"FP leaked," contract core, source-only (D-only) arm, flat judge, and re-aggregation are all defined in one dense paragraph, and the tables then add "majority (ref.)" rows. A small notation box or table footnote would help.
   - **5.5 [minor, fixable]** Minor clarity lapses: the running-example version pinning for the Qdrant #10369 example (v1.19.0) versus the RQ3 instance (v1.18.0) is easy to conflate; the sentence "the funnel is reported at its two measured points, not as a complete chain of subtractions" will be cryptic on first read; and Table 1's caption parenthetical "(some via an LLM reader, as SATORI does)" is the only place that qualifies the row's determinism framing.

### Questions for Authors

- **Q1:** Can you report a constraint-level audit of the extraction stage (e.g., for the 90 Qdrant constraints, how many assertions are verbatim-supported, over-strong, or under-strong versus the cited page), yielding an end-to-end precision estimate? — A positive answer would move 3.4 from major to minor and would let W1 be retired, because the four contract-core leaks are already shown to be extraction-induced.
- **Q2:** In RQ3's reverse direction, was the v1.4.0 integer-overflow panic triggered by an automated TestVDB-generated probe (which parameter, which endpoint), or was it hand-reproduced after contract reasoning identified the unbounded parameter? — Clarifying provenance and reconciling `size` vs. vector dimension would resolve 3.7; if the automated pipeline did not fire it end-to-end, the abstract's "TestVDB reaches VDBFuzz's crash-class integer overflow" should be softened.
- **Q3:** Were all 14 maintainer-confirmed Qdrant bugs live (reproducible) on the single v1.18.0 instance used for the RQ3 systematic direction, given that Qdrant candidates span v1.12.1–v1.19.0? — If some were version-specific, "reaches none of our confirmed defects on that version" needs a live-on-instance qualifier, affecting 3.3's strength.
- **Q4:** Would adding runs (e.g., five instead of three) change the source-only vs. core contrast ($p{=}0.093$) or the Holm-survival of full vs. core? — If the ordering firms up, 3.5 and W2 resolve upward; if not, I would ask for the abstract's ordering claim to be demoted to the Section 4.3 hedged form.
- **Q5:** For the four pack-induced false-positive leaks, what is the extraction-side root cause (over-strong constraint text, wrong tier, missing context), and could a corrected pack set be re-run through the confirmation stage to report an extraction-corrected suppression? — This connects 3.4 and 3.2 and would turn the leak analysis from attribution into a fix.

## Reviewer 2: Area Specialist

**Overall Recommendation:** Weak Accept

### Summary

The paper targets *documentation-implementation bugs* in vector database management systems (VDBMSs): cases where the system silently accepts an input or exhibits behavior that violates its natural-language API documentation, producing no crash and thus escaping the crash-oracle fuzzer VDBFuzz. The authors argue (Table 1) that every deterministic-oracle candidate anchors its expectation in a signal or structured source other than untagged system-level prose, which forces an LLM-derived oracle and imports the LLM's false-positive problem. Their system, TestVDB, is a four-stage multi-agent pipeline: behavioral specification extraction from crawled documentation, pre-bound-strategy test generation, Docker-pinned sandboxed execution with raw HTTP logging, and a bug-confirmation stage that splits evidence assembly from a four-perspective cross-examination whose implementation-source perspective is the falsification anchor.

Empirically, across Milvus, Qdrant, and Weaviate, maintainers confirmed 51 of 81 adjudicated submissions as real bugs, 23 fixed via merged implementation-code PRs. A controlled, blinded five-arm re-adjudication of that pool over frozen packages shows the contract-only core intercepts 87–90% of false positives at 88.9% verdict agreement but recalls only 0.196–0.333 of the confirmed bugs; adding source forensics and maintainer cognition reaches majority-vote recall 0.373 with perfect suppression, and an independent source-only arm reaches 0.333 — with no individual step statistically significant at this pool size, and a flat single-prompt judge matching the structured arms. A bidirectional probe against VDBFuzz on Qdrant shows complementary oracle reach, with an unusually deep audit of the baseline's released runner and mutation space.

### Core Strengths

- **S1:** Real-world impact, externally validated: 51/81 maintainer-confirmed bugs with 23 code-fix PRs, none documentation-only, and the fix classifier itself validated against a case the authors' own re-probe disproved — see 1.1, 3.6.
- **S2:** The oracle-exclusion analysis (Table 1) and the "anchor inversion" positioning are the paper's most original content, and the competitor claims I checked hold against the fetched sources (MASTOR, Metamon, CASCADE, SATORI) — see 2.1–2.3, 2.6.
- **S3:** The five-arm blinded RQ2 protocol is unusually rigorous for this space, and its reporting is strikingly honest — including the disclosed collapse of an earlier unblinded recall of 0.841 to 0.373 under blinding; the paired statistics check out when recomputed — see 3.1, 3.5.
- **S4:** The RQ3 baseline comparison audits VDBFuzz's released runner rather than trusting its summary counters (showing the counters cannot fire), measures the mutation-space bound from two directions, and withdraws one of its own prior explanations — see 3.2.

### Core Weaknesses

- **W1:** The pipeline's standalone automated performance is materially uncharacterized: end-to-end (extraction+confirmation) precision is admitted unmeasured, and the headline RQ1 yield comes from an author-screened, unblinded ledger with no deterministic submission rule — see 3.3, 3.4.
- **W2:** The central architectural claim is underpowered and partially self-refuted by the paper's own ablation: source grounding "carries most of the gain" but no step is significant, and a flat single-prompt judge with the same evidence access matches the four-perspective scaffolding, which is therefore claimed only as discipline/auditability — see 3.5, 2.4.
- **W3:** Missing related work: the natural-language-API-description constraint-inference line (RESTInfer, FSE 2022; ICON, ICSME 2016) is uncited, and the abstract's "no deterministic-oracle candidate derives its expectation from it [the prose]" overclaims against it — see 2.5.
- **W4:** Validity gaps that a revision can bound but not close at this pool size: single-backbone evidence for most arms with backbone and runtime co-varying in the one replication; an in-demonstrated ground-truth error rate (1 of 51 confirmed bugs disproved by the authors' own re-probe) with no sensitivity analysis; disclosed training-contamination threat — see 3.5, 3.6, 3.9.

### Detailed Assessment

1. **Significance** — Adequate
   - **1.1** Strength: the operational ledger (Table 2, Section 4.2) reports 51 maintainer-confirmed bugs out of 81 adjudicated submissions across three production VDBMSs, 23 fixed via merged PRs; Section 4.2's "Fix nature" audit shows all 23 fix PRs modify implementation code, 15 add regression tests, and none is documentation-only. Fix-validated, maintainer-adjudicated impact on real systems is the strongest kind of evidence a bug-finding paper can offer.
   - **1.2** Strength: the problem framing has standalone research value. Table 1 organizes oracle candidates by where their expectation anchors, and Section 2.3 turns that into a criterion ("where each oracle candidate gets its expectation") that explains why the documentation-implementation residual is reachable only by an LLM-derived oracle. This is a reusable lens for the oracle-automation community, and it answers a challenge the cited VDBMS-testing roadmap names as open.
   - **1.3 [minor, fixable]** The practical impact is bounded by the deployment shape the paper itself discloses (Section 4.2 caveat paragraph): candidates were submitted by the authors after novelty screening and manual review with "no deterministic submission rule", 49 submissions remain unadjudicated and excluded, and the reported Qdrant run cost ≈67 active hours across five days (Section 4.1). What is measured is a human–machine pipeline's yield, not an autonomous tester's; the significance claim should keep saying so even more prominently than it does.

2. **Novelty** — Adequate
   - **2.1** Verified delta vs. MASTOR (fetched; cached summary `mastor a multi agent approach to semantic test oracle generation for restful apis (corr 2026)`): the paper claims (Section 6, "Oracles derived from structured sources") that MASTOR's authority is the implementation and it therefore cannot detect a documentation-code gap. This holds: MASTOR demotes OAS-declared items not substantiated in source to `pending` and its own limitation states it "cannot detect violations of intended requirements that are not reflected in code." The anchor inversion — prose as ground, implementation as falsifier — is therefore a real, non-obvious delta, and the paper honestly concedes that reviewer-agent loops (MASTOR's ChallengerAgent) and cross-operation behavioral oracles are not new.
   - **2.2** Verified delta vs. Metamon (fetched; cached summary `metamon finding inconsistencies between program documentation and behavior using metamorphic llm queries (ieee acm international workshop on large language models for code llm4code 2025)`): the paper's characterization that Metamon's falsifier is "another LLM question — precisely the self-reference TestVDB breaks" is accurate (Metamon consults no independent non-LLM evidence source), and the quoted profile (precision 0.722 at recall 0.480 on 9,482 pairs; 0.967–1.000 only as recall collapses below 0.1) matches Metamon's reported numbers exactly. Declining a head-to-head reading is fair given different pools and ground truths.
   - **2.3** Verified delta vs. CASCADE (fetched; cached full text): the direct quote about CASCADE's two residual false positives ("the generated code and tests made the same false assumption over something underspecified in the documentation") is confirmed verbatim in CASCADE's own text, and the paper's inference — CASCADE's falsifier shares the documentation's ambiguity, so grounding in the implementation source is a genuine answer — holds.
   - **2.4 [minor, fixable]** The confirmation-stage machinery delta is thin on the paper's own evidence: Section 1 states the four-perspective chain is "claimed for discipline and auditability, since a flat single-prompt judge with the same evidence access matches it (Section 4.3)", and the flat-judge arm indeed statistically matches both structured arms while beating the contract core. What remains original is the problem formalization, the anchor inversion, and the empirical ledger — not the pipeline structure. The paper positions this correctly, but reviewers and readers should understand the system contribution as an audit framework, not an accuracy mechanism.
   - **2.5 [minor, fixable]** Missing related work within my specialty: the paper's Table 1 row 6 asserts doc-derived oracles are "method-level and tagged", and the abstract claims "no deterministic-oracle candidate derives its expectation from" the prose. Two uncited works derive checkable constraints from untagged natural-language REST/API descriptions: RESTInfer (ESEC/FSE 2022 tool demo, DOI 10.1145/3540250.3559078) infers parameter constraints from natural-language RESTful API descriptions, and ICON (ICSME 2016, DOI 10.1109/ICSME.2016.59) infers temporal constraints from natural-language API descriptions. I verified these only at metadata level (resolver returned titles/venues; abstracts unavailable), so my reading of their scope is provisional — but on their titles and venues they sit squarely in the NL-API-description-to-constraint line and predate the LLM era. They do not threaten the paper's core division (their derived oracle remains the final arbiter; they target parameter/temporal constraints, not behavioral/state conformance), but the blanket negative claim needs softening and a positioning sentence.
   - **2.6 [minor, fixable]** SATORI proximity under-acknowledged (fetched; cached summary `satori static test oracle generation for rest apis (40th ieee acm international conference on automated software engineering ase 2025)`): SATORI's LLM reads natural-language OAS field descriptions, and its confirmed real bugs include invalid enum values and out-of-range numbers versus the specification — i.e., documentation-implementation inconsistency on the response side. The paper's characterization (response-field properties, not behavioral conformance) is accurate but draws the structured-vs-prose boundary more sharply than the reality of "LLM reads OAS descriptions" vs. "LLM reads prose pages" warrants; one sentence acknowledging SATORI's bug classes as a unary, response-field subset of the residual would make Table 1's row 5 harder to dispute.

# Reviewer 3: General Reviewer

**Overall Recommendation:** Accept

## Summary

The paper targets *documentation-implementation bugs* in vector database management systems (VDBMSs): defects where the system silently accepts an input or returns a behavior that contradicts its natural-language API documentation (e.g., Milvus accepting `nprobe=0` though the docs declare $[1,16384]$). The authors argue that because the binding constraints are untagged prose, every deterministic test-oracle candidate — crash signals, differential and metamorphic relations, property-based checks, structured OpenAPI schemas, method-level doc-mining — anchors its expectation somewhere other than system-level prose (Table 1), leaving an LLM-derived oracle as the practical option, which imports an LLM false-positive problem.

TestVDB is a four-stage multi-agent pipeline: (i) documentation is distilled into typed, source-verified behavioral specifications; (ii) attack agents bound to pre-registered strategies generate executable probes; (iii) probes run against Docker-pinned versions with raw HTTP logging; (iv) an evidence builder assembles a five-section evidence chain per candidate and a chain auditor cross-examines it from four perspectives (contract, physical behavior, maintainer cognition, implementation source), with the source as the falsification anchor.

Evidence: across Milvus, Qdrant, and Weaviate, maintainers confirmed 51 of 81 adjudicated submissions as real bugs, 23 fixed via merged implementation-code PRs (RQ1). A blinded, three-run re-adjudication of the same pool over frozen packages (RQ2) shows the contract-only core suppresses 86.7–90% of false positives at 88.9% verdict agreement but recalls only 0.196–0.333 of the true bugs; adding source forensics and maintainer cognition reaches recall 0.373 with perfect suppression, and an independent source-only arm reaches 0.333 — the gain tracking evidence access rather than judgment structure, since a flat single-prompt judge matches the structured arms. A bidirectional probe against VDBFuzz on Qdrant (RQ3) shows the two oracles are complementary: VDBFuzz's full 205-template space reaches none of TestVDB's silent-accept defects, while TestVDB's contract reasoning reaches VDBFuzz's crash-class integer overflow.

## Core Strengths

- **S1:** The problem is real, currently open, and the operational yield is substantial and independently validated — 51 maintainer-confirmed bugs, 23 merged fix PRs, all 23 classified as touching implementation code, across three production systems — see 1.1, 1.2.
- **S2:** The evaluation is unusually disciplined and honest: a blinded frozen-package re-adjudication with five arms, Wilson intervals, exact McNemar tests, explicit disclosure that the headline ledger measures the human–machine pipeline, and two self-disclosed judgment-side threats — see 3.1, 3.2.
- **S3:** The oracle-exclusion analysis (Table 1) gives a structural, reusable argument for where an LLM oracle is forced, and the paper's own ablation (flat judge) demotes its own scaffolding claim — see 2.1, 3.2.
- **S4:** Verifiability is excellent: an itemized replication package whose contents map onto every reported analysis, plus in-text file paths and analysis scripts that recompute the reported rates — see 4.1.

## Core Weaknesses

- **W1:** The automated confirmation stage's recall is low (0.216–0.373 majority across arms), so the headline yield depends on author-side submission screening and human-in-the-loop operation; the paper discloses and scopes this, but it caps the automation claim — see 3.4.
- **W2:** The abstract and introduction state "no individual step reaches significance," but Section 4.3's own six paired tests contradict even the corrected reading: p=0.017 (full vs. core) does not survive Holm, while p=0.008 (flat vs. core) does (0.008×6=0.048) — so one step reaches corrected significance and two reach uncorrected significance — see 3.6.
- **W3:** Extraction-stage accuracy is never audited, so end-to-end precision (extraction + confirmation) is unmeasured; the four contract-core FP leaks are correctly attributed to extraction, but the boundary of the extraction error budget is unknown — see 3.3.
