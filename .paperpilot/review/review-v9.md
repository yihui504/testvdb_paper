## Reviewer 1: Domain Expert

**Overall Recommendation:** Weak Accept

### Summary

The paper proposes TestVDB, a system for detecting documentation-implementation defects in Vector Database Management Systems (VDBMSs). It targets a class of defects where a VDBMS silently accepts inputs that violate its API documentation (e.g., accepting `nprobe=0` when documentation specifies the range as `[1, 16384]`). Because the documented boundary is natural-language prose, the authors argue that classical deterministic oracles (crash, differential testing, metamorphic relations, property-based testing) cannot adjudicate these accept/reject decisions, leaving an LLM as the practical oracle. The paper instantiates a four-stage pipeline—behavioral-claim extraction, test-script generation, sandboxed execution, and defect confirmation—that uses LLMs to read documentation, generate tests, and adjudicate responses. Two LLM-specific failure modes (hallucination in extraction and self-preference in judgment) produce false positives. A multi-perspective judging baseline raises precision but collapses recall, so the authors introduce a dev-reviewer agent that acts as a source-grounded falsifier, reproducing each candidate, cross-checking it against source, and trying to disprove it. The authors evaluate TestVDB on three VDBMSs (Milvus, Qdrant, Weaviate), surfacing 107 candidate issues with 50 maintainer-acknowledged true-positive defects (15 fixed via merged PR). On a controlled retrospective over 48 candidates, the dev-reviewer reaches 67% precision and 74% recall against 37% recall without the source anchor. A bidirectional probe against VDBFuzz shows complementary coverage: TestVDB reaches a crash-class defect by contract reasoning, while VDBFuzz misses a silent-accept defect under its current templates.

### Core Strengths

- **S1:** Well-motivated problem target — documentation-implementation defects are a real and prevalent gap in VDBMSs, with 50 maintainer-acknowledged defects and 15 merged-PR fixes across three production systems demonstrating practical impact. — see 1.1
- **S2:** Novel contribution in source-grounded falsification — the dev-reviewer agent breaks both hallucination (at extraction) and self-preference (at judgment) by anchoring the verdict to implementation source rather than LLM-generated text, a substantive technical advance over treating the LLM as the final arbiter. — see 2.3
- **S3:** Rigorous empirical evaluation on multiple dimensions — RQ1 (real-world yield), RQ2 (controlled retrospective with ablations), and RQ3 (bidirectional VDBFuzz comparison) provide complementary evidence, with vendor-specific analysis, Wilson CIs, and multiple cross-model validations that strengthen the claims. — see 3.1, 3.2

### Core Weaknesses

- **W1:** Construct validity threat on single-family evaluation — all dev-reviewer results use a single LLM family (GLM-5.2), and a full cross-model re-run shows the verdict is family-specific (Cohen's κ = 0.18–0.32 vs. GLM), undermining the claim that source-grounded falsification generalizes across LLM families. — see 3.3 [major, unfixable]
- **W2:** Post-hoc operating-point selection without pre-registration — the 3-run any-confirmed ensemble is selected post-hoc from four operating points, and the Wilson CIs do not account for this selection; while bootstrap resampling and cross-validation mitigate the concern, the operating point remains exploratory rather than a pre-registered hypothesis. — see 3.2 [major, fixable]
- **W3:** Limited external validity on cross-family generalization — the cross-model re-run shows DeepSeek reaches 75% recall on Milvus but collapses to 0% on Qdrant, and all three families stay at ≤14% recall on Qdrant, suggesting source-grounded falsification's reliability is backbone-dependent and may not generalize beyond the GLM-5.2 family. — see 3.3 [major, unfixable]

### Detailed Assessment

#### 1. Significance — Adequate

- **1.1** The paper targets a real and prevalent problem. The authors cite a VDBMS bug study (roadmap25) finding that more than half of VDBMS bugs manifest as functional failures, and an empirical study (bugstudy25) attributing about 43% of VDBMS bugs to incorrect behavior. The 50 maintainer-acknowledged true-positive defects across three production VDBMSs (Milvus, Qdrant, Weaviate) provide concrete evidence that documentation-implementation defects exist and are worth detecting. The 15 merged-PR fixes demonstrate that maintainers find these defects actionable. The impact is bounded—the paper addresses a specific defect class in a specific domain (VDBMSs)—but the setting (natural-language documentation forcing LLM interpretation) is structurally similar to other domains (REST APIs without OpenAPI, configuration validation, policy-as-code). The authors acknowledge this limitation in Section 8 and provide preliminary portability evidence (CouchDB, Elasticsearch), which is sufficient for an Adequate rating.

- **1.2 [minor, fixable]** The paper's exclusion argument in Table 1 could be strengthened by acknowledging that some oracle candidates (e.g., property-based testing with schemas) could theoretically reach documentation-implementation defects if VDBMSs exposed OpenAPI schemas that encoded parameter constraints. The current table treats OpenAPI as a binary (present/absent), but a middle ground exists where partial schema coverage encodes some constraints (e.g., integer ranges) while leaving others (e.g., semantic conditions like "must be positive when X is true") in prose. The authors should clarify that VDBMS endpoints "serve no schema that encodes these constraints" rather than "serve no OpenAPI at all" (some VDBMSs do serve OpenAPI, but not for the semantic constraints that matter). This is a nuance, not a flaw, but clarifying it would strengthen the exclusion argument.

- **1.3 [minor, fixable]** The paper's external validity claim that the setting "is not specific to VDBMSs in principle" (Section 8) is supported only by two non-VDBMS case studies (CouchDB, Elasticsearch) with minimal detail. The authors report that CouchDB exposed three input-validation gaps and Elasticsearch rejected every invalid probe with a 400 error, but they do not provide enough detail to assess whether the pipeline ported cleanly (e.g., Did the dev-reviewer need VDBMS-specific modifications? Did the LLM prompts generalize? Were the false-positive modes the same?). More detail on the porting process and a third non-VDBMS case study would strengthen the transferability claim. This is not required for an Adequate rating but would elevate the contribution.

#### 2. Novelty — Adequate

- **2.1** The paper makes a clear, non-obvious delta over the closest prior work. The two most relevant competitors are SATORI (ASE 2025) and MASTOR (J. ACM 2026), which both generate semantic oracles for REST APIs. SATORI infers response-field oracles (format, length, enum, range) from OpenAPI field names, types, and descriptions; MASTOR reads source code to generate oracles that encode implemented behavior. The paper correctly identifies that neither approach can detect documentation-implementation gaps: SATORI operates under per-field structural anchoring (OpenAPI properties) and targets response-field oracles, not input-acceptance decisions; MASTOR tests what the implementation does, not what the documentation prescribes. TestVDB's contribution is to use source as a falsifier of documentation-derived claims, targeting exactly that gap. I verified this characterization against the cached competitor summaries (Section 1 of background.md); the paper's positioning is accurate.

- **2.2** The application of LLM-as-judge reliability research (Panickssery et al., NeurIPS 2024; Wataoka et al., CORR 2024) to test-oracle pipelines is novel. The self-preference bias literature establishes that LLM evaluators favor their own family's outputs, but the paper correctly identifies that this manifests as a specific false-positive mode in test-oracle pipelines: the same family that extracts a claim tends to confirm it. The dev-reviewer's source-grounded falsification breaks this mode by anchoring the verdict to implementation source rather than LLM-generated text. This is a non-obvious mitigation—multi-perspective judging (four specialized judge agents voting) is the natural baseline, and the paper shows it collapses recall because the judges share the documentation ambiguity. The dev-reviewer's three-check falsification (independently reproducible, evidence sufficient, falsifiable) is a substantive technical advance.

- **2.3 [minor, fixable]** The paper could more clearly position its work against prior documentation-derived oracle tools (Toradocu, ChatAssert, Doc2OracLL, AugmenTest, Testora). The Related Work section (Section 6) mentions these tools and states that they "treat the LLM as the final semantic arbiter, verifying through runtime behavior," but the delta is somewhat terse. A concrete example would help: e.g., Toradocu extracts Javadoc `@throws` clauses via NLP and has acknowledged false positives; ChatAssert repairs false positives via compilation/execution feedback but still relies on LLM judgment. TestVDB's dev-reviewer differs by reading source code as an independent falsifier, not by refining the LLM prompt or adding runtime checks. The current description is sufficient but could be more explicit.

- **2.4 [minor, fixable]** The paper's boundary with AGORA+ (execution-trace invariant inference) could be sharpened. Table 1 claims AGORA+ "cannot reach inputs the traffic did not exercise," but AGORA+ also generalizes beyond observed traffic via invariant inference rules (e.g., "if response always has field X, then X is required"). The exclusion argument should acknowledge that AGORA+ could theoretically infer some documentation-implementation violations (e.g., if the trace shows the API accepts invalid inputs and AGORA+ infers an invariant that contradicts documentation), but in practice AGORA+ targets response-field/runtime properties, not input-acceptance decisions. The current characterization is not wrong, but it would be more precise to say AGORA+ targets response-field/runtime properties and has not been evaluated on input-acceptance gaps, rather than claiming it cannot reach them by construction.

#### 3. Soundness — Adequate

- **3.1** The main claims are supported by appropriate evaluation. RQ1 (detection capability) is answered by 107 submitted issues with 50 maintainer-acknowledged true-positive defects (69.4% yield precision, Wilson 95% CI [58.0%, 78.9%]). The authors provide a worst-case bound (46.7% if all pending submissions are false positives) and acknowledge that the yield is biased by the tool's design rather than a population estimate. RQ2 (false-positive suppression) is answered by a controlled retrospective over 48 maintainer-adjudicated candidates (27 TP, 21 FP), showing the dev-reviewer reaches 67% precision and 74% recall against 37% recall without source grounding. RQ3 (VDBFuzz comparison) is answered by a bidirectional reachability probe on Qdrant, showing VDBFuzz reaches 0 of 14 TestVDB silent-accept TPs on v1.18.2 (26,000 requests) and TestVDB reaches VDBFuzz's integer-overflow crash via contract reasoning on v1.4.0. These three evaluation dimensions provide complementary evidence, and the vendor-specific analysis (Milvus defects concentrate in optional-default parameters; Qdrant in search parameters and state operations; Weaviate in idempotent behaviors) strengthens the external validity.

- **3.2** The ablation studies isolate the dev-reviewer's contribution. Table 4 (three-condition ablation on a 12-FP/4-TP Milvus control) shows source-grounded falsification alone suppresses 75% of false positives while retaining all true positives, and the union of source + threat-model anchors suppresses 91%. This directly measures the self-preference reduction (same-family judge agent over-confirms its own extracted claims). The source-grounding-ablation experiment (disabling Step 3.5 drops recall from 74% to 19%) further triangulates that source grounding is the dominant contributor to recall. The cross-model re-run on three additional families (DeepSeek, Qwen-3.8-Max, LongCat-2.0) shows the verdict is family-specific (Cohen's κ = 0.18–0.32 vs. GLM), which is a threat to construct validity but is honestly reported rather than hidden.

- **3.3 [major, unfixable]** The paper's core claim—that source-grounded falsification mitigates LLM false positives—is supported only for a single LLM family (GLM-5.2). The cross-model re-run shows DeepSeek, Qwen, and LongCat all perform worse on the 48-candidate retrospective (recall 56%, 19%, 22% vs. GLM's 74%, with vendor-specific collapse on Qdrant). The authors acknowledge this as a limitation in Section 7 ("we cannot claim cross-family robustness"), but it undermines the generalizability of the contribution. The paper presents source-grounded falsification as a general solution to LLM-as-judge false positives, but the evidence suggests it is family-specific. This is not a fatal flaw (the contribution is still valid for GLM-5.2 and may extend to other families with tuning), but it bounds the claim to a specific backbone rather than a general methodological advance.

- **3.4 [major, fixable]** The operating point (3-run any-confirmed ensemble) is selected post-hoc. The authors evaluate four operating points (single run, 3-run union, 5-run union, 5-run majority) and select the 3-run union as the headline because it sits at the knee of the precision-recall trade-off. They report Wilson CIs (67% [49, 81], 74% [55, 87]) but acknowledge these do not account for selection across the four points. They provide bootstrap resampling (precision [53%, 83%], recall [71%, 96%]) and cross-validation (3-run selected in 27% of splits, test precision/recall 68%/71%) to show the selection is not an overfit, but the operating point remains exploratory rather than a pre-registered rule. The authors should flag this explicitly in the abstract and results as a post-hoc, exploratory operating point (which they do in Section 7, but the abstract presents the 67%/74% numbers without the selection caveat). This is fixable by adding a sentence to the abstract acknowledging the post-hoc selection.

- **3.5 [minor, fixable]** The paper does not estimate recall because no public ground-truth defect catalog exists for VDBMSs. The authors acknowledge this as a limitation (Section 7), but it would be stronger to provide a capture-recapture estimate or to argue that the 48-candidate retrospective is representative of the defect space. The current evaluation treats the 48 candidates as a fixed set, which is sufficient for a controlled comparison (single-LLM vs. dev-reviewer), but provides no evidence on how many defects TestVDB missed overall. This is not required for Adequate—maintainer acknowledgment is a reasonable ground truth for the defects that were submitted—but it bounds the recall claim to the submitted candidate set rather than the full defect space.

- **3.6 [minor, fixable]** The threat-model anchor (Section 5) is described as an optional third anchor that compares candidates against maintainer-acknowledged by-design and wont-fix patterns. The ablation (Table 4) shows it suppresses 6/12 false positives (50%) but is "unstable on state and concurrency FPs." The authors do not elaborate on what "unstable" means (Does it fail to suppress some FPs? Does it suppress TPs?). More detail on the threat-model anchor's stability and a quantitative breakdown of its FP/TP trade-off would strengthen the evaluation. This is not required for Adequate but would clarify the dev-reviewer's design.

#### 4. Verifiability — Adequate

- **4.1** The paper provides sufficient information to follow the work. The four-stage pipeline (Section 3) is described in enough detail to understand the flow: contract-formalizer extracts behavioral claims from documentation, attack agents generate executable probes, sandboxed execution runs them on Docker-pinned VDBMS instances, and judge agents triage candidates before the dev-reviewer falsifies them. The dev-reviewer's three-check falsification (independently reproducible, evidence sufficient, falsifiable) is specified with concrete examples (the #9255 reversal). The Appendix (Section A) excerpts the contract-formalizer and dev-reviewer role prompts, and the artifact (https://github.com/yihui504/testvdb-anon) contains the full 22 agent definitions, target versions, per-token accounting, 48-candidate ground truth, and a reproduction driver. The link is declared and reachable (the domain resolves; I did not clone the repository).

- **4.2** The paper provides sufficient detail to reproduce the key results. Table 2 reports the per-target LLM-call distribution (~50% dev-reviewer source-grounding, ~25% claim extraction + test generation, ~25% judging + novelty gate) and the wall-clock cost (~$10 per target at current API pricing). The authors specify the GLM-5.2 backbone via the BigModel Anthropic-compatible API under default sampling (no decoding overrides; temperature and top-p at provider defaults). Section 7 describes the controlled retrospective (48 candidates, Milvus 32, Qdrant 16, Weaviate covered by a smaller subset) and the cross-model re-run protocol (three families, three independent runs per family, complete SOP with independent live probes and source exploration). A researcher could reproduce the dev-reviewer's 67%/74% precision/recall from this description, given access to the 48-candidate ground truth (which the artifact provides).

- **4.3 [minor, fixable]** The paper does not specify the prompt templates or sampling parameters for the cross-model re-run (DeepSeek, Qwen, LongCat). It states that each family ran "the complete SOP with independent live probes and source exploration, three independent runs per family" but does not give the model versions, API providers, or sampling settings (temperature, top-p, etc.). Reproducing the cross-model results would require these details. This is not required for Adequate—the headline results use GLM-5.2 and are fully specified—but it would strengthen the cross-model comparison.

- **4.4 [minor, fixable]** The paper does not specify the 48-candidate ground truth beyond the count (27 TP, 21 FP, Milvus 32, Qdrant 16). The artifact contains the full ground truth, but the paper should at least state that the artifact includes `test_questions/` with maintainer-adjudicated labels and that the selection criteria are "all maintainer-adjudicated submissions up to [date]." This is a minor omission but would aid verifiability.

#### 5. Presentation — Adequate

- **5.1** The paper is well-structured and readable. The introduction (Section 1) clearly motivates the problem, characterizes the defect class, and positions the contribution. The background (Section 2) cleanly separates documentation-implementation consistency from result correctness and walks through the oracle-exclusion argument (Table 1). The approach (Section 3) describes the four-stage pipeline with concrete examples (the #49823 path). The false-positive problem (Section 4) diagnoses two failure modes and shows multi-perspective judging is insufficient. The dev-reviewer (Section 5) specifies the three-check falsification with a diagram (Figure 3). The evaluation (Section 7) answers three research questions with complementary evidence. The writing is clear, and the figures (pipeline, dev-reviewer falsification, per-run recall) aid understanding.

- **5.2 [minor, fixable]** The paper has some minor language issues. For example, Table 1 uses the phrase "Rows 1 to 5 keep a deterministic oracle; only row 6 enters the LLM regime," which is slightly awkward—"keep" is not the right verb (perhaps "use" or "apply"). In Section 7, the phrase "the 3-run union is the post-hoc headline" is jargon-heavy; "the 3-run union is our post-hoc selected operating point" would be clearer. These are minor and do not impede understanding, but polishing would improve the presentation.

- **5.3 [minor, fixable]** The paper uses notation inconsistently in places. For example, Section 7 writes "Cohen's κ vs. GLM's 3-run union on a CONFIRMED-vs-not split over n=48" but does not define CONFIRMED (it is the dev-reviewer's defect verdict, implied from context). Section 7 also writes "Wilson 95% CI [58.0%, 78.9%]" in one place and "[49, 81]" in another; the percentage symbols should be consistent. These are minor but should be corrected.

- **5.4 [minor, fixable]** Figure 2 (TestVDB four-stage pipeline) is described in the caption but not referenced in the text. The caption mentions "dashed boxes are LLM-driven; solid boxes (sandboxed execution, dev-reviewer) are not," but the text does not walk through the figure. Adding a sentence in Section 3 pointing to Figure 2 would improve the presentation.

### Questions for Authors

- **Q1:** The cross-model re-run shows source-grounded falsification is family-specific (κ = 0.18–0.32 vs. GLM). Did you investigate whether tuning the contract-formalizer or dev-reviewer prompts for each family would improve cross-family consistency? For example, Qwen's variance on Milvus is attributed to "contract-vs-source tensions" — would tightening the contract-formalizer (e.g., explicit instruction "do not infer unstated constraints") reduce over-strict assertions? — Intended effect: If the authors have evidence that prompt tuning improves cross-family generalization, item 3.3's rating would move from Adequate toward Excellent (the family-specific limitation would be mitigated).

- **Q2:** The 3-run any-confirmed ensemble is selected post-hoc from four operating points. Did you pre-register any hypothesis about which operating point would perform best, or was this purely exploratory? If the latter, have you considered withholding a subset of the 48 candidates as a validation set to confirm the selected operating point generalizes? — Intended effect: Clarifying the pre-registration status would address item 3.4's concern and might move it from [major, fixable] to [minor, fixable].

- **Q3:** The threat-model anchor is described as "unstable on state and concurrency FPs." Can you quantify this instability? Does it fail to suppress some FPs (lower precision)? Does it suppress TPs (lower recall)? A breakdown of the threat-model anchor's FP/TP trade-off by defect type (state, concurrency, boundary) would clarify its role in the dev-reviewer. — Intended effect: More detail on the threat-model anchor's stability would address item 3.6's concern and might move it from [minor, fixable] to resolved.

### Summary

TestVDB targets a specific defect class in Vector Database Management Systems (VDBMSs): documentation-implementation defects where a system silently accepts inputs violating its API documentation. Because the documented boundary is natural-language prose rather than a structured specification, deterministic oracles (crash-based, differential, metamorphic, property-based) cannot adjudicate these accept/reject decisions. The paper argues that an LLM-derived oracle is the practical solution for this residual. It instantiates a four-stage pipeline (claim extraction, test generation, sandboxed execution, defect confirmation) that surfaced 107 candidate issues across Milvus, Qdrant, and Weaviate, with 50 maintainer-acknowledged true-positive defects (15 fixed via merged PR). A key contribution is the dev-reviewer agent, which acts as a source-grounded falsifier to suppress two LLM failure modes: hallucination in claim extraction and self-preference bias in judgment. On a controlled 48-candidate retrospective, the dev-reviewer reaches 67% precision and 74% recall (3-run ensemble) against a 37% recall baseline without source grounding. A bidirectional probe against VDBFuzz shows complementary coverage: TestVDB reaches a crash-class defect by contract reasoning, while VDBFuzz misses a silent-accept defect under current templates.

### Core Strengths

- **S1:** The dev-reviewer's source-grounded falsification design is well-motivated by LLM bias literature (Panickssery, Haldar) and demonstrated to lift recall from 37% to 74% — see 2.1, 3.2.

- **S2:** The oracle-exclusion argument (Table 1) systematically positions why deterministic oracles miss the documentation-implementation residual, leaving LLM-derived oracles as the practical option — see 2.2.

- **S3:** Real-world impact is clear: 50 maintainer-acknowledged true positives across three production VDBMSs, with 15 fixed via merged PR — see 3.1.

- **S4:** The bidirectional VDBFuzz probe concretely demonstrates complementary coverage, not just theoretical — see 3.3.

### Core Weaknesses

- **W1:** Cross-family generalization is unproven. Three additional LLM families (DeepSeek, Qwen, LongCat) show family-specific verdicts (κ=0.32, 0.20, 0.18 vs. GLM), collapsing on Qdrant specifically. The paper's headline 74% recall is GLM-5.2-only — see 3.2 [major, unfixable].

- **W2:** The 3-run union operating point is post-hoc and exploratory, selected across four candidates after observing performance. Wilson CIs do not account for this selection, and Bonferroni correction widens CIs substantially — see 3.2 [major, fixable].

- **W3:** Weaviate coverage is incomplete. Only 11 candidates (7 source-grounded confirmations, 4 false positives) were run, insufficient for per-vendor recall headline due to sparse TP density — see 3.2 [minor, fixable].

### Detailed Assessment

1. **Significance** — Excellent

   - **1.1** The problem is real and costly. The paper cites a VDBMS bug study showing more than half of defects are functional failures, not crashes. The roadmap identifies oracle definition as a key challenge. Documentation-implementation defects corrupt query semantics and propagate errors silently in LLM stacks. This is a significant practical problem worthy of research attention.

   - **1.2** The impact is demonstrated. Fifteen merged-PR fixes across three production VDBMSs show practical value. Fifty maintainer-acknowledged true positives from 107 submissions (69.4% adjudicated yield) indicate the tool reaches genuine defects. The yield is biased by design toward documentation-implementation defects, not a population estimate, but the absolute count (15 fixed) is substantial.

2. **Novelty** — Excellent

   - **2.1** The dev-reviewer's source-grounded falsification is a clear, non-obvious delta over prior LLM-as-judge work. Multi-perspective judging (four specialized judge agents) reaches ~80% precision but collapses recall to ~15%. The paper diagnoses why: all judges read the same ambiguous documentation and converge on the same over-strict claim. The dev-reviewer breaks self-preference by introducing an independent signal (implementation source) that falsifies the extracted claim. This directly addresses Panickssery's self-preference bias (LLMs favor their own family's outputs) and Haldar's self-inconsistency (low intra-rater reliability). The characterization of MASTOR (source-based oracle generation for implemented behavior, not gap detection) is accurate. Verified against cached summaries.

   - **2.2** The oracle-exclusion argument (Table 1) systematically walks through why deterministic oracles miss the documentation-implementation residual: crash oracles miss silent accepts, differential testing cannot adjudicate accept/reject across vendors by design, metamorphic relations target output correctness not input acceptance, property-based testing needs machine-checkable properties and OpenAPI schemas that VDBMS endpoints rarely expose. The residual leaves LLM-derived oracles as the practical option. This is a clean positioning of the contribution relative to REST-API oracle tools (AGORA+, SATORI, MASTOR) that target response-field properties under structural anchoring, not input-acceptance decisions on system-level prose.

3. **Soundness** — Adequate

   - **3.1** **3.1 [major, unfixable]** The headline recall (74%, 3-run union) is family-specific. Three additional LLM families (DeepSeek, Qwen-3.8-Max, LongCat-2.0) were run on all 48 candidates, showing family-specific verdicts (Cohen's κ vs. GLM's 3-run union: 0.32 DeepSeek, 0.20 LongCat, 0.18 Qwen, all in slight-to-fair band). Combined recall is 56% (DeepSeek), 22% (LongCat), 19% (Qwen) vs. 74% for GLM-5.2. The gap is vendor-specific: DeepSeek approaches GLM on Milvus (75% vs. 80%) but collapses on Qdrant (0% vs. 29%). All three stay at ≤14% recall on Qdrant. The paper acknowledges cross-family generalization is an open question and does not claim cross-family robustness, but the headline numbers are GLM-dependent. This is inherent to the contribution (LLM behavior is family-dependent) and cannot be fixed by revision.

   - **3.2** **3.2 [major, fixable]** The operating point selection is post-hoc. The paper evaluates four operating points (single run, 3-run union, 5-run union, 5-run majority) and selects the 3-run union as the headline because it "sits at the knee of the precision-recall trade-off." The fix is to either pre-register the operating point or explicitly frame the selection as exploratory with appropriate correction (which the paper partially does, but the headline presentation should acknowledge the selection more prominently).

   - **3.3** The 48-candidate retrospective is maintainer-adjudicated but non-random. The paper acknowledges it did not pre-register the candidate set and cannot estimate recall without a ground-truth defect catalog. A capture-recapture or unbiased defect-sample estimation is future work. Given no public catalog exists for VDBMSs, this is a reasonable limitation honestly stated. The yield precision (69.4% on 72 adjudicated) is defensible as a conservative bound if all 35 pending submissions are false positives (46.7%).

If the implementation has a bug, it could wrongly falsify a correct clause. The paper reports that 31 of 50 true positives have merged or open fix-PRs (implementation confirmed buggy by maintainers), and no false positive was traced to an implementation bug. The assumption produced no observed false negatives in the retrospective. The assumption is explicitly bounded in Section 7, and the evidence suggests it holds often enough to be useful without guarantee.

## Reviewer 3: General Reviewer

**Overall Recommendation:** Weak Accept

### Summary
The paper introduces TestVDB, a tool for detecting documentation-implementation defects in Vector Database Management Systems (VDBMSs)—cases where a VDBMS silently accepts inputs that violate its API documentation. The authors argue that classical fuzzing oracles (crash-based) miss this defect class because these silent accepts produce no crash, and deterministic oracles cannot adjudicate natural-language documentation boundaries. TestVDB uses Large Language Models (LLMs) in a four-stage pipeline: extract behavioral claims from documentation, generate executable tests, run them in sandboxed Docker instances, and confirm defects via a judge agent. The authors identify two false-positive failure modes (LLM hallucination in extraction and self-preference bias in judgment) and propose a dev-reviewer agent that acts as a source-grounded falsifier to suppress false positives. In evaluation, TestVDB surfaced 107 candidate issues across three VDBMSs (Milvus, Qdrant, Weaviate) with 50 maintainer-acknowledged true positives (15 fixed via merged PR). A controlled retrospective over 48 candidates shows the dev-reviewer reaches 67% precision and 74% recall (3-run ensemble) versus 37% recall without source grounding. A bidirectional probe against VDBFuzz shows complementary coverage on crash vs. silent-accept defects.

### Core Strengths
- **S1:** Clear problem framing and oracle-exclusion argument — see 1.1, 2.1
- **S2:** Rigorous false-positive analysis with source-grounded falsification — see 3.1, 3.2
- **S3:** Comprehensive evaluation with maintainer-acknowledged ground truth — see 4.1, 4.2
- **S4:** Transparent acknowledgment of limitations and threats to validity — see 3.3, 4.3

### Core Weaknesses
- **W1:** Narrow empirical scope (3 VDBMSs, single LLM family) — see 1.2 [major, fixable]
- **W2:** Cross-family generalization is unproven — see 1.2
- **W3:** Post-hoc operating-point selection without pre-registration — see 4.2 [major, fixable]
- **W4:** Limited external validity beyond VDBMS regime — see 3.3

### Detailed Assessment

**1. Significance — Adequate**
- **1.1** The paper targets a real and prevalent problem: logical bugs in VDBMSs that escape crash-oracle fuzzers. The authors cite an empirical bug study showing that more than half of VDBMS bugs manifest as functional failures, and the VDBMS testing roadmap attributes about 43% of VDBMS bugs to incorrect behavior. The 50 maintainer-acknowledged true-positive defects (with 15 merged-PR fixes) across three production VDBMSs demonstrate practical impact. This is meaningful but bounded—the problem is specific to systems where documentation is natural-language prose and input-acceptance decisions diverge from implementation behavior.
- **1.2 [major, fixable]** The empirical scope is narrow. All evaluation is confined to three VDBMSs (Milvus, Qdrant, Weaviate) and a single LLM backbone (GLM-5.2). A cross-model re-run with DeepSeek, Qwen-3.8-Max, and LongCat-2.0 shows the verdict is family-specific (Cohen's κ = 0.32, 0.20, 0.18 vs. GLM), with collapsed recall on Qdrant for all three families. Cross-family generalization remains an open question—the authors acknowledge it as a limitation but do not provide a clear mitigation path beyond exploratory voting probes. The paper would be significantly stronger if it demonstrated cross-family robustness or provided a principled method for selecting backbones that generalize.

**2. Novelty — Adequate**
- **2.1** The contribution is clearly situated against prior work. Table 1 (oracle candidates) provides a systematic exclusion argument that distinguishes TestVDB from classical approaches (crash oracles, differential testing, metamorphic relations, property-based testing, REST-API tools). The key novelty is treating the oracle problem as a natural-language interpretation task where an LLM is the practical oracle, then introducing source-grounded falsification (the dev-reviewer) to mitigate LLM-induced false positives. This is a real but incremental delta over prior LLM-derived oracle work (Toradocu, Doc2OracLL, AugmenTest), which kept the LLM as the final arbiter.
- **2.2** The positioning against VDBFuzz is strong but limited in scope. The bidirectional probe on Qdrant (Section 4.3) shows TestVDB reaches a crash-class defect by contract reasoning, while VDBFuzz misses a silent-accept defect under its current templates. However, the systematic direction (VDBFuzz against TestVDB's pinned version) is a single budget-fixed run (26,000 requests, 0 of 14 silent-accept TPs reached), and the two controlled cases are n=1 each. The structural claim is plausible—that crash oracles cannot detect silent accepts by construction—but the empirical evidence is limited to one vendor and three isolated version checks.

**3. Soundness — Adequate**
- **3.1** The core claims are supported by appropriate methods. The false-positive problem is rigorously analyzed with two failure modes (hallucination in extraction, self-preference in judgment), and the dev-reviewer's three-check falsification (independently reproducible, evidence sufficient, falsifiable) is well-motivated by the limitations of multi-perspective judging. The 48-candidate retrospective provides maintainer-adjudicated ground truth (27 TP, 21 FP) and isolates the source-grounded anchor's contribution via ablation (Table 3: source alone suppresses 9/12 FPs, 75%). The RQ2 evaluation (65% accuracy, 67% precision, 74% recall) directly measures the recall gain from source grounding (37% → 74%).
- **3.2** The statistical reporting is thorough. The authors provide Wilson 95% CIs for precision and recall, acknowledge that the 3-run operating point is post-hoc (with Bonferroni correction and bootstrap validation), and report per-run variance (recall 15–78% across five runs). The cross-model re-run with three additional families (DeepSeek, Qwen, LongCat) and Cohen's κ quantification (0.32, 0.20, 0.18) transparently shows family-specific performance. The VDBFuzz bidirectional probe, while limited in scope, includes version-controlled reproduction (Table 4) and isolates crash-class mechanisms.
- **3.3** The threats to validity are honestly and explicitly discussed. Internal validity threats include single-run variance, post-hoc operating-point selection, and a non-random 48-candidate retrospective. External validity threats include limited vendor coverage (Milvus and Qdrant in the controlled retrospective; Weaviate covered by a smaller subset) and lack of cross-family robustness. Construct validity threats include the implementation-as-correct assumption and the fact that all results use a single LLM family. The paper acknowledges that 31 of the 50 TPs have merged or open fix-PRs (implementation confirmed buggy), and no FP was traced to an implementation bug, but does not quantify the false-negative rate from documentation errors.

**4. Verifiability — Excellent**
- **4.1** The paper provides sufficient information to follow and reproduce the work. The four-stage pipeline is clearly described in Section 3 with concrete examples (the #49823 nprobe=0 case). The authors provide approximate per-target LLM-call distribution (Table 2: ~50% dev-reviewer source-grounding, ~25% claim extraction + test generation, ~25% judging + novelty gate) and cost (~$10 per target at current API pricing). All agent role definitions, target versions, per-token accounting, the 48-candidate ground truth, and a reproduction driver are declared in an artifact repository (https://github.com/yihui504/testvdb-anon). The link is reachable and the description is self-contained.
- **4.2** The evaluation is reproducible in concept. The 48-candidate retrospective is fully specified (27 TP, 21 FP; Milvus 32, Qdrant 16; Weaviate controlled subset). The RQ1 yield (107 submitted, 50 acknowledged TP) is broken down by vendor (Table 3) with Wilson CIs. The ablation study (Table 3) isolates the dev-reviewer's anchors on a 12-FP/4-TP Milvus control. The cross-model re-run is fully specified (three families, three independent runs per family, complete SOP with independent live probes and source exploration). The VDBFuzz bidirectional probe specifies versions, configurations, and reproduction steps (Table 4). Some detail is missing (exact LLM sampling parameters beyond "default," full prompts in appendix), but the main flow is followable.

**5. Presentation — Adequate**
- **5.1** The paper is well-structured and readable. The introduction clearly motivates the problem (silent-accept defects in VDBMSs), distinguishes documentation-implementation consistency from correctness, and states the contributions. The approach section (Section 3) walks the pipeline step-by-step with a concrete example. The evaluation section (Section 4) is organized by three research questions with clear quantitative claims. The related work section (Section 6) systematically covers VDBMS testing, REST-API oracle generation, LLM-as-judge reliability, and documentation-derived oracles.
- **5.2 [minor, fixable]** The figures and tables are generally clear but some have minor issues. Figure 1 (pipeline sketch) is referenced but not rendered in the stripped LaTeX source—this is a formatting issue that does not obstruct understanding. Table 1 (oracle candidates) is dense with text but conveys the exclusion argument clearly. Table 4 (bidirectional reachability) uses a "Reproduces" column that is slightly ambiguous—it lists both VDBFuzz's crash and TestVDB's #9045 under "Reproduces" without clearly distinguishing which oracle reproduces which defect on each version. A minor wording clarification would help.
- **5.3 [minor, fixable]** The language is generally clear but has occasional awkward phrasing. Some sentences are long and densely packed with parenthetical citations (e.g., the abstract sentence listing yield breakdown). Section 3.1's "LLM automation" paragraph is information-dense and could be split for readability. The appendix agent prompts are useful but truncated (excerpts only), which limits verifiability of the exact prompt engineering—though the full prompts are declared in the artifact.

### Questions for Authors
- **Q1:** Can you provide more detail on the LLM sampling parameters beyond "default"? Specifically, what temperature and top-p values were used, and were there any decoding overrides? This would clarify the source of run-to-run variance in recall (15–78%) and help interpret the cross-model κ differences. — Intended effect: if the authors clarify that variance stems from sampling noise rather than fundamental instability, item 3.1's rating would move up.
- **Q2:** The cross-family generalization results show collapsed recall on Qdrant for all three tested families (DeepSeek, Qwen, LongCat). Is this specific to Qdrant's API documentation style, or do you have evidence that it generalizes to other vendors? A non-VDBMS case study (beyond the brief CouchDB/Elasticsearch probes) would strengthen the external validity claim. — Intended effect: if the authors provide additional evidence or a principled mitigation for cross-family collapse, item 1.2's rating would move up.
- **Q3:** The 3-run operating point is selected post-hoc from four candidates (3-run union, 5-run union, 5-run majority, single run) based on the knee of the precision-recall trade-off. Have you considered pre-registering the operating point selection rule (e.g., "select the highest-recall ensemble with precision ≥ 60%") in future work to avoid selection bias? — Intended effect: if the authors commit to a pre-registered selection rule, item 4.2's rating would move up.
- **Q4:** The paper treats the implementation as correct (implementation-as-correct assumption). You report that no FP was traced to an implementation bug, but do not quantify the false-negative rate from documentation errors. Can you provide an estimate or bound on this rate, even if approximate? — Intended effect: if the authors provide a quantitative bound, item 3.3's rating would move up.
