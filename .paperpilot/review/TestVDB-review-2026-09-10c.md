# Reviewer 1 (Domain Expert) — Review

Paper: "Detecting Logic Bugs in Vector Database Management Systems via LLM-Derived Behavioral Specifications"
Paper type: TECHNICAL. Round 4 review; the paper is judged as it stands.

## Reviewer 1: Domain Expert

**Overall Recommendation:** Accept

### Summary

The paper targets *documentation-implementation bugs* in vector database management systems (VDBMSs): cases where the system silently accepts an input or exhibits behavior that violates its API documentation (e.g., Milvus accepting `nprobe=0` although the documentation declares [1, 16384]). Because such bugs produce no crash, they escape the one dedicated VDBMS fuzzer (VDBFuzz), and because the constraints live in natural-language prose rather than schemas or OpenAPI fields, the paper argues that every deterministic-oracle candidate is structurally excluded, leaving an LLM-derived oracle as the practical option — which imports a false-positive problem, since the same model family reads the prose and judges the behavior.

The proposed system, TestVDB, is a four-stage pipeline: (i) two-agent behavioral-specification extraction from vendor documentation with typed, evidence-tiered, source-verified constraints; (ii) probe generation by three attack agents under deterministically pre-bound strategies, with scenario construction for system-level state constraints; (iii) sandboxed execution against Docker-pinned targets with raw HTTP logging; and (iv) bug confirmation split into an evidence builder (five-section evidence chain, including grounding in the implementation source) and a chain auditor (four mechanical checks, four perspectives: contract, physical, maintainer cognition, source).

Empirically, across Milvus, Qdrant, and Weaviate, 51 of 81 adjudicated upstream submissions were confirmed by maintainers as real bugs, 23 fixed via merged PRs. A three-run blinded re-adjudication of the full 81-candidate pool measures the contract-only confirmation core at 87–90% false-positive suppression with 88.9% verdict agreement, and a three-run controlled ablation of the full stage (adding source forensics and maintainer cognition) achieves 1.000 suppression in all three runs while raising majority recall from 0.216 to 0.373; the recall loss is attributed to three systematic mechanisms. A bidirectional probe plus a full-template-space run against VDBFuzz establishes that the two oracles reach complementary bug classes.

### Core Strengths

- **S1:** Demonstrated practical impact on a real problem: 51 maintainer-confirmed bugs with 23 merged fix PRs, and a fix-nature audit showing all 23 fixes modify implementation code (15 add regression tests, none documentation-only), with the audit itself validated on a self-disproved case — see 1.1, 3.1.
- **S2:** The blinded, three-run frozen-package re-adjudication protocol, including a controlled core-vs-full ablation under identical blinding and the explicit deprecation of an earlier, inflated unblinded recall figure (0.841) — an unusually honest measurement design for LLM-testing work — see 3.2, 3.3.
- **S3:** The novelty delta over the closest competitors is real and verified: I checked the paper's characterizations against CASCADE (full text), MASTOR and SATORI (cached summaries), and Toradocu, and found no mischaracterization; the inversion of the implementation source from oracle-ground (MASTOR) or synthesized-artifact falsifier (CASCADE) to *falsification anchor* is a genuine, empirically supported advance — see 2.1, 2.2.
- **S4:** The RQ3 comparison removes the budget-artifact alternative explanation by running VDBFuzz's complete template space (205 templates, 50.8 minutes, within its own published 120-minute protocol) on the commit-matched instance where the confirmed defects live — see 3.4.

### Core Weaknesses

- **W1:** The recall-boundary interpretation conflates two different failure sources: 27 of the 51 true-bug frozen packages contain no pinned contract row, so the conservative adjudication rule defaults them to False-Positive regardless of judgment quality; "no pinned row" can mean the prose states no expressible assertion (the paper's reading) *or* the extraction stage missed an assertion the documentation actually states (a fixable extraction deficiency). The abstract's claim that the measured recall boundary "quantifies exactly where source grounding and maintainer cognition become necessary" needs this stratification — see 3.5. [major, fixable]
- **W2:** The provenance of the maintainer-cognition material used by the full-stage ablation is underspecified relative to the candidates' own upstream issue threads; if `developer_cognition.json` was distilled from a tracker that already contained the candidates' adjudicated issues, the full stage's 1.000 suppression is partially label-informed. The protocol's "no access to adjudication labels or issue history" statement does not by itself exclude this channel — see 3.6. [major, fixable]
- **W3:** Generality and funnel transparency: all agents run on a single LLM backbone (disclosed), the submission pool is an author-selected subset of confirmed output (bias direction argued but unquantified), and the per-version mining coverage behind the cumulative 51-bug ledger is not tabulated — see 3.7, 1.2, 4.3. [minor, fixable]
- **W4:** Minor related-work coverage gaps: a recent source-of-authority taxonomy for LLM-based test oracles (arXiv 2607.05031, provisional — title/abstract level), Hossain et al. 2025 on documentation's impact on LLM oracle generation, the Molina et al. 2025 survey, and Metamon (LLM4Code@ICSE 2025) are uncited though adjacent to the paper's central expectation-source analysis — see 2.4. [minor, fixable]

### Detailed Assessment

1. **Significance** — Excellent
   - **1.1** The submission ledger (Table 2: Milvus 43/29/11/14, Qdrant 28/14/9/14, Weaviate 10/8/3/2, total 81 submitted / 51 confirmed / 23 fixed / 30 FP) is a strong, externally validated yield, and the paper goes beyond the headline: the "Fix nature" paragraph in Section 4.2 classifies every merged fix PR by changed files (23/23 modify implementation code, 15 add regression tests, none documentation-only) and validates the classifier against the disproved #9149, whose fix PR it correctly identifies as test-only. This is exactly the kind of audit that makes "fixed" claims trustworthy, and it directly supports the practical-impact claim.
   - **1.2** The problem framing (Sections 1–2, Table 1) is significant beyond the three systems studied: the expectation-source analysis ("where each oracle candidate gets its expectation") delimits a bug class — silent documentation violations in prose-documented, stateful HTTP systems — that the existing tooling (VDBFuzz's crash oracle, per the official ICSE 2026 abstract a boundary-value crash-bug framework whose oracle cannot fire on a 200-returning accept) structurally misses. The bug-pattern table (Table 3: 37/51 = 72.5% in the silent-acceptance family) empirically substantiates that the targeted class is the dominant one.
   - **1.3 [minor, fixable]** Impact is bounded in two disclosed ways that temper the headline: the 51-bug ledger is cumulative across mining rounds and tool versions since early 2026 (Section 4.2, "Process ledger" paragraph states the ledger "predates this run" and the two layers "neither is reducible to the other"), and the fully reported single run registers only five new defect numbers (three independently corroborated). The per-run novel yield is therefore modest even though the cumulative yield is strong; stating this ratio in the abstract or contributions would set expectations correctly.

2. **Novelty** — Adequate
   - **2.1** Checked the delta against **CASCADE** (FSE 2026; fetched and read in full via arXiv 2604.19400v1): CASCADE generates unit tests from natural-language method documentation and reports an inconsistency only when the original code fails a test and an LLM-regenerated implementation passes the same test (f2p > 0 and p2f = 0). The paper's characterization — "its falsifier is therefore another LLM artifact" — is accurate, and CASCADE's own analysis of its two residual false positives ("the generated code and tests made the same false assumption over something underspecified in the documentation") independently corroborates the paper's shared-ambiguity critique of same-source falsifiers. The paper's delta — anchor the falsification in the *actual* implementation source and maintainer cognition, and target system-level stateful HTTP behavior rather than method-level Java — is clear, non-obvious, and empirically supported by the ablation (full-stage suppression 1.000 vs core 0.867). This is the paper's strongest originality claim and it holds.
   - **2.2** Checked the deltas against **MASTOR** and **SATORI** (cached summaries from prior rounds): MASTOR's self-stated limitation — "MASTOR infers semantics from implementation behavior. It cannot detect violations of intended requirements that are not reflected in code" — matches the paper's Table 1/Related-Work characterization verbatim in substance, so the direction inversion (documentation as ground, source as falsifier) is a real delta, and "closest to this work" is defensible given MASTOR's multi-operation stateful oracles. SATORI's per-response-field OAS anchoring is also accurately characterized; the paper correctly scopes its residual to *system-level* prose rather than claiming SATORI cannot find documentation mismatches at all (SATORI's real bugs include response-side documented-range/enum violations).
   - **2.3 [minor, fixable]** The top-line mechanism — an LLM reads prose to derive an expectation — is established prior work (the paper itself cites the line from iComment through DocTer, Toradocu, and the LLM generators, plus Konstantinou et al.'s actual-behavior-capture finding). The originality therefore concentrates in the confirmation architecture and the domain instantiation; the paper mostly says exactly this, but two phrasings overshoot Table 1's own precise scoping: the abstract's "no deterministic-oracle candidate derives its expectation from documentation" and the intro's "every deterministic-oracle candidate falls structurally short" should say "no candidate anchors its expectation in *system-level prose*" (SATORI derives expectations from a documentation artifact, though structured per-field — as Table 1 itself states).
   - **2.4 [minor, fixable]** Related-work coverage is otherwise strong (the VDBMS-testing, structured-source-oracle, and LLM-oracle lines are all cited and positioned). Four adjacent works appear uncited, verified at abstract/title level only (provisional): the "LLM-Based Test Oracles: Source-of-Authority Taxonomy" preprint (arXiv 2607.05031, 2026), whose expectation-source taxonomy is conceptually parallel to Table 1's analysis; Hossain et al. 2025 (ACM) on how documentation affects LLM-based oracle generation; the Molina et al. 2025 survey "Test Oracle Automation in the Era of LLMs"; and Metamon (Lee, An, Yoo, LLM4Code@ICSE 2025), an LLM that judges whether existing tests are consistent with documentation — the nearest "LLM-as-judge-of-doc-consistency" relative in the Java line. None of these threatens the delta; citing and one-line positioning them would close the gap.

3. **Soundness** — Adequate
   - **3.1** The ground-truth protocol for RQ1 is careful: maintainer adjudication with explicit confirm/duplicate/FP criteria (Section 4.2, "Collection protocol"), re-verification of every submission's state as of September 2026, a revisable-adjudication stance demonstrated by the #9149 self-disproof (seven-version re-probe), and status/acceptance detail (51 = 23 fixed + 18 open-acknowledged + 7 closed-after-acknowledgment + 3 duplicates; 50/51 carry an official `bug` label). Internally consistent: all table sums check out (Table 2 rows sum to 81/51/23/30; Table 3 patterns sum to 51; every RQ2 confusion-matrix row sums to 81; recall/suppression/precision figures recompute correctly from Table 4, including Wilson CIs).
   - **3.2** The RQ2 core measurement is well designed for its claim: three independent runs over frozen packages with an 81/81 denominator in every run, a conservative binary adjudication rule (uncertainty resolves to False-Positive), and per-run CIs. The finding that the four persistent FPs are all Milvus pack-induced misreadings (confirmed across runs) is a genuinely useful result — it separates systematic error from run-to-run noise, which most LLM-judge evaluations do not do.
   - **3.3** The full-stage ablation (Table 4, "What the full confirmation stage adds") now isolates perspectives C+D under the same blinding: 1.000 suppression in all three runs, majority recall 0.216 to 0.373, all case-level disagreement on the recall side, and the symmetric cost (in-source/cognition vetoes suppressing boundary truths) disclosed rather than hidden. The explicit deprecation of the earlier unblinded recall figure (0.841) is exemplary practice.
   - **3.4** RQ3's protocol is fair: the systematic direction probes seven live silent-accept TPs with VDBFuzz's default 26,000-request run; the reverse direction is probed on v1.4.0 where VDBFuzz's own crash is live; and the new full-coverage run (205 templates, 50.8 minutes, time limit removed — consistent with the VDBFuzz artifact's `-l 0` option, which I verified in its repository) rules out the budget-artifact explanation on the commit-matched instance. The paper also correctly limits the #9045 finding to VDBFuzz's *templates* rather than the oracle class.
   - **3.5 [major, fixable]** The recall-boundary interpretation needs stratification. Section 4.3 states that the true-bug packs contain 18 explicit and 6 inferred-from-example contract rows and that **27 of the 51 true bugs have no pinned contract row**; under the conservative rule those 27 default to False-Positive. The paper reads this as the assertion-framework boundary (mechanism (i)), and the abstract claims the measured recall boundary "quantifies exactly where source grounding and maintainer cognition become necessary." But "no pinned row" has two distinct causes: (a) the documentation genuinely states no expressible assertion (the framework boundary — the paper's reading), or (b) the *extraction stage* failed to pin an assertion the documentation actually states (an upstream deficiency the confirmation stage cannot be charged with). These have opposite practical implications: (a) is a fundamental boundary, (b) is fixable tooling debt. The FP-suppression headline is unaffected, but the recall-boundary narrative — one of the paper's three headline results — requires separating them: report recall stratified by pack completeness, and for a sample of the no-row cases, audit the documentation to classify (a) vs (b).
   - **3.6 [major, fixable]** The full-stage ablation's cognition material has an underspecified leakage channel. Perspective C consumes `developer_cognition.json`, distilled from the target's "historical issues and PRs" (Section 3.5); the 81-candidate pool was itself submitted upstream, so the candidates' own issue threads — which contain the very adjudication labels being predicted — live in the mineable corpus. The protocol statement that runs had "no access to adjudication labels or issue history" governs what the judge is fed, but does not state *when* the cognition file was frozen relative to each candidate's submission or whether the candidates' own threads are excluded from the distillation corpus. Four of the core's majority-misconfirmations were corrected by "in-source by-design or cognition evidence" — exactly the perspective at risk. The authors should state the freeze date and exclusion rule, and ideally re-run any affected cases with a cognition corpus frozen pre-submission; if the freeze predates all submissions, 3.6 resolves favorably.
   - **3.7 [minor, fixable]** The submission pool is author-selected without a deterministic rule (disclosed in Section 4.2 with a bias-direction argument: raw-stream suppression likely higher than measured; 63.0% precision inherits human selectivity). The direction argument is plausible but unquantified, and 49 submissions remain pending. A simple sensitivity bound on the 63.0% figure under adverse/favorable resolution of the pending set would make the caveat concrete.
   - **3.8 [minor, fixable]** An internal tension in the class boundary: Section 5 (Limitations) declares that "a schema-valid parameter value that crashes the service" falls outside the strict-verdict path and is escalated, yet RQ3 presents TestVDB's boundary probe reaching the v1.4.0 `size=2^63` panic "as a documentation-implementation violation" on nearly the same shape (OpenAPI declares size ≥ 1 with no maximum), and Table 1 counts 2 of the 51 confirmed bugs as producing a crash or panic. The distinction may be sound (forced verdict vs escalation channel), but the paper never explains how the 2 crash-class bugs were adjudicated; without that, the definition of the target bug class is inconsistent across sections.

4. **Verifiability** — Adequate
   - **4.1** The main flow is reproducible in concept from the text: the two-agent extraction with its two gating self-checks (endpoint coverage, version alignment), the constraint schema (type, evidence tier, level, source verification), the five generation gates, the executor's environment manifest, atomic `.done` markers, and per-batch log/marker counts, the five-section evidence chain, the four mechanical checks with a bounded (≤3) rebuild loop, the priority aggregation rule for the ablation, and the frozen-package blinding protocol with explicit denominators. Cost disclosure (≈67 active hours, ≈860 executions, ≈70M/4.9M tokens, orchestrating-session-only lower bound) is unusually concrete.
   - **4.2 [minor, fixable]** The artifact is declared but not reachable: Data Availability says the replication package "will be made available … upon publication" at an anonymous.4open.science placeholder, and the source still contains a rendered `\todo{Confirm anonymized artifact link before submission…}`. As submitted, nothing can be checked against the declared artifact; for RQ2's replication the essential artifacts are the 81 frozen packages (transcript + contract rows), the agent role prompts, and the strategy registries.
   - **4.3 [minor, fixable]** LLM-side procedural detail is thin for exact replication: the strategy registries (trigger conditions for the boundary/state/semantic strategies) and per-agent prompt texts are described but not enumerated in the paper — acceptable if the artifact carries them, but the text alone does not permit re-derivation of which strategies bind to which constraints. Relatedly, the tested-version coverage behind the cumulative ledger (which Milvus/Weaviate/Qdrant versions were mined in which round) is never tabulated; a target × version × round table would let readers audit what the 51 bugs were found on.

5. **Presentation** — Adequate
   - **5.1** The structure is sound and the argumentative devices work: Table 1 (oracle candidates by expectation source) is the paper's best exhibit; the #10369 running example is threaded through all four stages (Sections 3.2–3.5); the two-ledger relationship (cumulative submissions vs single-run funnel) is stated explicitly and honestly in Section 4.2 rather than left for readers to trip over.
   - **5.2 [minor, fixable]** A leftover `\todo{...}` command in Data Availability renders red placeholder text in the PDF — this must be removed before any submission.
   - **5.3 [minor, fixable]** Two paragraphs in Section 4.2 are density outliers: the "Process ledger of one complete run" paragraph and the following funnel/bias paragraph each run well past a dozen lines with nested parentheticals; a small funnel diagram or table (chains → candidates → gate partitions → new registrations) would make both easier to audit.
   - **5.4 [minor, fixable]** Minor wording/notation: the abstract's "87–90%" rounds the per-run suppression range without saying majority-vote suppression is 0.867 (Section 4.3 gives the exact figures — add "(per-run)" or "majority" once in the abstract); the phrase "the crash baseline on v1.18.2" (Section 4.4) is used before the budget provenance of that configuration is defined. The abstract is also one very long paragraph and could be trimmed.

### Questions for Authors

- **Q1:** How was `developer_cognition.json` frozen relative to the 81 candidates' upstream submissions, and are the candidates' own issue threads excluded from the cognition-distillation corpus? — If a pre-submission freeze/exclusion is confirmed, item 3.6 (and with it W2) resolves upward, since the full stage's 1.000 suppression would be leakage-free by construction.
- **Q2:** What is the confirmation-stage recall stratified by pack completeness — i.e., restricted to the 24 true-bug packs that do carry a pinned contract row? — If recall on complete packs is high, the assertion-boundary claim in 3.5 survives in a sharper form ("given an expressible assertion, the stage confirms it"); for the 27 no-row packs, what fraction of documentations actually state an expressible assertion the extraction missed?
- **Q3:** How were the 2 crash/panic bugs among the 51 (Table 1, row 1) adjudicated — forced through the strict-verdict path, or via the human escalation channel of Section 5? — A clear answer would reconcile 3.8 and fix the class-boundary inconsistency between RQ3 and Limitations.
- **Q4:** What is the sensitivity of the 63.0% submission-precision figure if the 49 pending submissions resolve uniformly as confirmations or as false positives? — A two-line bound would convert the 3.7 caveat into a quantified statement.
- **Q5:** Will the replication package include the 81 frozen adjudication packages (transcripts plus contract rows), the agent role prompts, and the strategy trigger registries? — Affirmative would move 4.2/4.3 up, since those are the artifacts on which RQ2's replication actually hinges.

## Reviewer 2: Area Specialist

**Overall Recommendation:** Weak Accept

### Summary

The paper targets *documentation-implementation bugs* in vector database management systems (VDBMSs): cases where the system silently accepts an input or produces behavior that violates its API documentation, and therefore never crashes. Because the documented constraints live in natural-language prose, the paper argues that every deterministic-oracle candidate (crash signals, differential testing, metamorphic relations, property-based testing, structured-spec-derived oracles) is structurally unable to derive the needed expectation, leaving an LLM-derived oracle as the practical option — at the cost of importing the LLM's false-positive problem. The proposed system, TestVDB, is a four-stage pipeline (behavioral specification extraction, strategy-bound test generation, sandboxed execution against Docker-pinned targets, and bug confirmation) whose confirmation stage splits evidence assembly from cross-examination: an evidence builder grounds each candidate in documentation, execution transcripts, and the implementation source, and a chain auditor applies four mechanical checks plus four perspectives (contract, physical, maintainer cognition, source) before issuing a verdict.

Evidence is reported on Milvus, Qdrant, and Weaviate: maintainers confirmed 51 of 81 adjudicated submissions as real bugs, 23 fixed via merged PRs. A three-run blinded re-adjudication of the full 81-candidate pool shows the contract-only adjudication core intercepts 86.7–90% of the known false positives (88.9% case-level agreement) with a measured recall boundary, and a controlled three-run ablation of the full stage (adding source forensics and maintainer cognition) achieves 1.000 FP suppression in all runs at recall 0.373 under majority voting. A bidirectional probe against VDBFuzz shows the two oracles reach complementary bug classes: VDBFuzz's 26,000 mutated requests (and its full 205-template space in a follow-up run) reach none of the silent-accept defects, while TestVDB's boundary reasoning reaches VDBFuzz's crash-class integer overflow.

### Core Strengths

- **S1:** The problem framing and oracle-exclusion analysis are crisp and, where I verified them against the named competitors, accurate — see 2.1, 2.2.
- **S2:** The RQ2 measurement design is unusually careful for this literature: frozen packages, three independent blinded runs, a conservative verdict rule, full denominators, Wilson intervals, and a controlled core-vs-full ablation — see 3.2, 3.3.
- **S3:** The headline yield is externally validated (51 maintainer-confirmed bugs, 23 merged fix PRs classified as implementation-code repairs, with the classifier itself validated on the one self-disproved case) — see 3.1.
- **S4:** Limitation disclosure is substantive: expectation-framing bias, observation leakage, the submission-filtered pool with an explicit bias-direction statement, and the honest deprecation of the earlier unblinded 0.841 recall figure — see 3.4.

### Core Weaknesses

- **W1:** The full-stage ablation's perfect 1.000 FP suppression rests on an unstated leakage channel: perspective C consumes maintainer cognition distilled from the targets' issue histories, and the snapshot's timing relative to the authors' own upstream submissions (some closed as by-design — exactly the FP labels) is never stated — see 3.5, Q1.
- **W2:** Missing related work in the LLM-oracle-reliability cluster: Molinelli et al. (ASE 2025) is uncited, and the contamination threat it foregrounds (LLM training-data memorization of mined issues and known bugs) is unaddressed in this paper despite a single-backbone design — see 2.4, 3.6, Q2.

### Detailed Assessment

1. **Significance** — Adequate
   - **1.1** The paper targets a real and current problem: VDBMSs are core RAG infrastructure, and the cited empirical studies (Section 2.2) support the claim that the dominant bug class is non-crashing functional failure that silently corrupts query results. The yield is concrete and externally validated: 51 maintainer-confirmed bugs across three production systems, with 23 fixed via merged PRs, and Section 4.2's fix-nature classification showing every fix PR modifies implementation code (15 add regression tests, none is documentation-only). That is clear practical impact on the systems operators actually run.
   - **1.2 [minor, fixable]** The impact is bounded and the cost of the boundary is under-discussed. The method is scoped to prose-constraint APIs of three systems, and the disclosed cost of one Qdrant run is large: roughly 67 active pipeline hours and about 70M input tokens for the orchestrating session alone (Section 4.1, with parallel attack-agent sessions excluded from that bound). A reader cannot judge adoption cost-effectiveness (cost per confirmed bug) because the orchestrator-only token figure is a stated lower bound and the parallel sessions are unquantified. One paragraph bounding full-pipeline cost against the per-run yield would materially help practitioners assess significance.

2. **Novelty** — Adequate
   - **2.1** The oracle-exclusion analysis (Table 1, Section 2.4) is the paper's best conceptual artifact: it delimits the residual by where each oracle candidate anchors its expectation, rather than by topic. I verified the two structured-source competitors it leans on most. Against MASTOR (cached summary, arXiv:2606.10465): the paper's claim that MASTOR "encodes implemented behavior and so cannot detect a gap between documentation and code" matches MASTOR's own stated limitation ("It cannot detect violations of intended requirements that are not reflected in code"). Against SATORI (cached summary, ASE 2025): the characterization of per-field LLM-inferred response-property oracles anchored in OAS fields is accurate. The delta — inverting the role of source from oracle ground (MASTOR) to falsification anchor (TestVDB) — is real and correctly drawn.
   - **2.2** The confirmation-stage delta against CASCADE (FSE 2026; I read the arXiv full text) is verified accurate: CASCADE suppresses false positives of documentation-derived tests by regenerating code from the same documentation and flagging an inconsistency only when the original code fails a test that the regenerated code passes. The paper's objection — that CASCADE's falsifier is therefore another LLM artifact and shares the documentation's ambiguity — is not just fair but empirically corroborated by CASCADE itself, whose two residual false positives both arose because "the generated code and tests made the same false assumption over something underspecified in the documentation." The authors should quote that sentence; it is the strongest available evidence for their shared-ambiguity argument (Section 2.4). (CASCADE also found LLM voting baselines improve pair-wise precision but still lose on precision/specificity to its execution-based dual check — a nuance that slightly softens, without refuting, the paper's claim that panels do not fix the problem.)
   - **2.3 [minor, fixable]** The abstract's blanket phrasing "no deterministic-oracle candidate derives its expectation from documentation" is overbroad relative to the body's careful scoping: SATORI's per-field expectations *do* derive from OAS documentation, including its natural-language field descriptions, and SATORI's reported real bugs include specification-response mismatches. The accurate scope — which the body and Table 1 maintain — is *system-level* prose governing input acceptance and state. Tighten the abstract to carry that qualifier.
   - **2.4 [minor, fixable]** Coverage gap in the LLM-oracle reliability cluster (backs W2): Molinelli, Di Grazia, Martin-Lopez, Ernst, and Pezzè, "Do LLMs Generate Useful Test Oracles? An Empirical Study with an Unbiased Dataset" (ASE 2025, pp. 278–290), is uncited. It is directly in the cluster the paper reviews (adjacent to `konstantinou24`, `testora26`, `togll24`) and is the first large-scale study to evaluate LLM oracles on a leakage-free benchmark (13,866 oracles from 135 Java projects, all created after the models' training cut-offs; LLM oracles reach 43% average mutation score vs 45% for human oracles). Also a bib-hygiene note: the `armeta26` entry ("Khan, Shehroz and others", arXiv note unresolvable in my searches, though the paper exists in IEEE proceedings under the matching title) should be completed with full authors and a verifiable identifier.

3. **Soundness** — Adequate
   - **3.1** Ground truth is externally anchored and honestly revisable: candidate issues are adjudicated by project maintainers, every submission's state was re-verified as of September 2026, and the one candidate the authors' own re-probe disproved (#9149) is reclassified and even reused to validate the fix-PR classifier (its PR is correctly identified as test-only, Section 4.2). This is the right way to handle fallible ground truth.
   - **3.2** The RQ2 protocol is well designed: frozen candidate packages, three independent runs at default sampling with no access to labels, a conservative binary rule (uncertainty resolves to False-Positive), full 81/81 denominators, and Wilson intervals. I recomputed the reported intervals: [0.699, 0.947] for 26/30 and [0.747, 0.966] for 27/30, and [0.886, 1.000] for the full stage's 30/30 — all check out. The attribution of the four surviving FPs to pack-induced contract misreadings (all Milvus, consistent across runs) is a genuinely useful mechanistic finding, not noise-washing.
   - **3.3** The Table 4 full-stage ablation is the right experiment: it isolates the C+D perspectives under the same frozen-package blinding, in three runs, and it discloses the symmetric cost — the same veto power that perfects precision suppresses boundary truths (recall 0.216 → 0.373 under majority). The honest reporting of the earlier unblinded run's 0.841 recall and its deprecation is exemplary.
   - **3.4** Judgment-side threats are disclosed rather than hidden: expectation-framing bias and observation leakage (Section 5, internal validity), the submission funnel's author-selectivity with an explicit statement of the bias direction (raw-stream suppression likely higher than measured; submission precision inherits human selectivity), and the funnel/run two-ledger reconciliation (Section 4.2). This is a model of disclosure, though the magnitudes of the disclosed biases remain unquantified.
   - **3.5 [major, fixable]** There is one unstated leakage channel that sits directly under the ablation's headline result (backs W1). The RQ2 protocol states judges have "no access to adjudication labels or issue history" (Section 4.3), yet the full stage's perspective C is fed by `developer_cognition.json`, distilled from "the target's historical issues and merged PRs" (Section 3.5) — and the authors' own 130 submissions *are* issues in those trackers, 30 of them closed in exactly the ways that define the FP labels (by-design, not-reproducible). If the cognition distillation was mined after the submissions, the labels are derivable from C's input despite the nominal blinding, and the perfect 1.000 suppression across three runs could be partly label-derivation rather than generalizable interception. The paper never states the snapshot timing. The fix is cheap: state when cognition was mined per target, or re-mine from a pre-submission snapshot and re-run. This does not touch RQ1 (externally validated) or the contract-core results (which use no C input), but it caps how much weight the 1.000 can carry until answered — hence it is the decision-driving weakness in my review.
   - **3.6 [minor, fixable]** Training-data contamination is never discussed (backs W2). The backbone (GLM-5.2, Section 4.1) may have memorized the targets' well-known historical issues and fixes; the novelty gate's already-covered-by-fix-PR bucket (Section 4.2) excludes only findings already covered by upstream fix PRs, not memory of open or by-design discussions. ## Reviewer 3: General Reviewer
**Overall Recommendation:** ACCEPT (conditional on the promised artifact being deposited and accessible at decision time — see 4.2)

### Summary

The paper addresses the detection of documentation–implementation divergence bugs in vector database management systems (VDBMSs) — silent logic bugs (e.g., an out-of-range `nprobe=0` silently accepted against a documented bound) that escape crash-oracle fuzzers such as VDBFuzz by construction. Since documented boundaries are prose, no deterministic oracle candidate in the paper's taxonomy (crash, differential, metamorphic, property-based, REST spec oracles) can derive expectations from them; the authors therefore adopt an LLM as a practical oracle and build TestVDB, a four-stage pipeline (specification extraction, script generation, sandboxed execution, bug confirmation). The confirmation stage is the paper's core methodological device: a five-section evidence chain cross-examined from four perspectives (contract, physical behavior, maintainer cognition, implementation source), with implementation source as the falsification anchor that closes the loop where the same LLM both writes and judges the oracle.

The evaluation is unusually candid and quantitative: across three pinned VDBMSs, 51 of 81 adjudicated submissions are confirmed as real bugs (23 fixed upstream, 50/51 bug labels accepted by maintainers); a blinded three-run re-adjudication measures FP interception at 0.867–1.000 depending on confirmation strictness, and honestly quantifies the recall boundary (core run-level recall 0.196–0.333 and full-stage per-run 0.353–0.431) with mechanism-level attribution; a bidirectional VDBFuzz probe plus a full-template-space head-to-head on a commit-matched version substantiates the complementarity claim. Limitations — including author-mediated submission filtering of the evaluation pool and a large unblinded-to-blinded recall gap (0.841 → 0.373) — are disclosed by the authors themselves rather than left for reviewers to find.

### Core Strengths

- **S1:** Externally corroborated bug yield with revisable ground truth — 51/81 confirmed, 23 upstream fixes, 50/51 labels maintainer-accepted, all fixes implementation-code (none doc-only), and the #9149 self-disproof showing the GT protocol is genuinely revisable — see 4.2
- **S2:** The RQ2 experiment is a real controlled measurement of the LLM-oracle reliability tradeoff (blinded, frozen packages, three runs, conservative binary rule, majority vote, Wilson CIs), isolating the decision value of source grounding and cognition, and quantifying the cost of blinding itself — see 4.3
- **S3:** A systematic oracle-landscape analysis that walks each deterministic-oracle family and derives the residual (system-level, untagged, stateful HTTP prose) that motivates the approach — see 2.4, Table 1
- **S4:** Verifiable internal arithmetic and process transparency: Table 4 cells cross-foot to 51 TPs / 30 FPs per run, the reported Wilson intervals recompute from the cell counts, and the process ledger (119 chain verdicts → 96 candidates → 60 defect-confirming) plus gate overrides are disclosed — see 4.2–4.3

### Core Weaknesses

- **W1:** The headline 63.0% precision is a submission-filtered subset figure: the pool was cut by per-candidate author decisions (novelty screening + manual review) with no deterministic rule, so end-to-end pipeline precision is unmeasured — see 4.2
- **W2:** FP ground-truth provenance is stated by the paper (maintainer-adjudicated: §4.1 "Ground truth comes from maintainer adjudication"; §4.2 collection protocol defining FP as "labeled by-design or closed as not reproducible"; Table 2 caption) — the residual concern is symmetric revisability: maintainer FP labels are, like the confirmed labels, fallible (cf. #9149), so the FP-interception headline inherits the same revisable-label caveat as the yield figure, not an author-mediation gap — see 4.3
- **W3:** External validity is narrow for the generality implied by the framing: single LLM backbone (GLM-5.2, default sampling), three systems, prose-constraint HTTP APIs only — see 5
- **W4:** No artifact is available at review time; the data availability statement promises a link "upon publication" with a visible TODO, while the pipeline is LLM-version-sensitive — see Data Availability

### Detailed Assessment

**1. Significance — Excellent**

- 1.1 (S) The problem is real and the impact is demonstrated, not asserted: silent logic bugs in production VDBMS infrastructure (Sec 1, #49823 motivating example), with Table 2 showing 51 confirmed bugs across Milvus/Qdrant/Weaviate and 23 fixed upstream. The upstream acceptance figures (50/51 bug labels; 25/29 + 5/14 triage accepted, Sec 4.2) make the practical value concrete.

- 1.3 (P) Bounded scope of the headline number: because the evaluation pool is a submission-filtered subset (Sec 4.2 funnel caveat), the significance of the confirmed-bug yield is solid but the significance of the *precision* figure is narrower than the abstract implies. **[moderate, hard]** (irreducible without re-running selection under a fixed rule)

**2. Novelty — Adequate (provisional, field-context-dependent)**
