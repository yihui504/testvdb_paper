# Paper Review — TestVDB (paper-draft-acm-sigconf.tex)

Three independent reviews (Reviewer 1 Domain Expert, Reviewer 2 Area Specialist, Reviewer 3 General) followed by a Meta-Review. Reviews are independent and intact; the Meta-Review integrates them.

## Reviewer 1: Domain Expert

**Overall Recommendation:** Weak Accept

### Summary
This paper introduces TestVDB, a system for detecting documentation-implementation defects in Vector Database Management Systems (VDBMSs) using LLM-derived behavioral claims falsified against source code. The authors identify that approximately 85% of the 111 candidate issues they found are documentation-implementation defects unreachable by classical oracles (differential, metamorphic, crash-based). They propose "source-grounded falsification" to address task-intrinsic LLM interpretation errors and report 38 maintainer-acknowledged defects across five VDBMSs, with precision improvements from 31% to 81% when using source anchoring. The VDBFuzz head-to-head comparison (added in this version) provides controlled empirical evidence for oracle asymmetry. However, concerns remain about the n=1 sample size in the comparison, the generalizability of the task-intrinsic error claims, and whether the asymmetry finding is fairly characterized.

### Core Strengths
- **S1:** Important problem space — the identification of documentation-implementation defects as a prevalent but under-explored class is valuable; the 85% residual claim highlights a genuine gap.
- **S2:** Technical innovation — the two-layer reliability model (family-specific vs task-intrinsic) and source-grounded falsification are a meaningful conceptual contribution, well-differentiated from AGORA+/SATORI/MASTOR.
- **S3:** Controlled empirical validation — the RQ3 probe (n=29 clauses) with vendor-wise contrast and cross-model validation (κ=1.0 on 20 candidates) provides credible evidence.
- **S4:** Improved VDBFuzz comparison — the bidirectional reachability experiment using reproducible versions (Qdrant v1.4.0 for VDBFuzz's crash, v1.18.0 for TestVDB's defect) provides controlled evidence for oracle asymmetry, substantially stronger than a disjoint-classes observation.
- **S5:** Real-world impact — 38 maintainer-acknowledged defects (31 fixed) demonstrate practical utility; the Qdrant #7967↔#9045 case (crash symptom vs root cause) is compelling.

### Core Weaknesses
- **W1:** Insufficient statistical justification — the n=1 per direction in the VDBFuzz head-to-head undermines the statistical soundness of the asymmetry claim. — see 3.1
- **W2:** Over-generalized structural claims — the Discussion crash-oracle asymmetry section over-generalizes from the n=1 finding; "a crash on a doc-valid input is itself a doc-impl violation" is structurally correct but empirically unsupported beyond one case. — see 3.3
- **W3:** VDBFuzz template fairness — the empty-vector template uses wait=true (correct-reject path) while #9045 occurs on wait=false; this should be framed as a template-coverage limitation, not fundamental oracle incapability. — see 3.1
- **W4:** Limited external validity — statistical claims concentrate on Milvus (22) and Qdrant (13); Weaviate/MeiliSearch/Chroma are breadth-only. — see 1.1
- **W5:** Task-intrinsic rate CI width — [19%, 68%] is extremely wide; preliminary nature should be emphasized more. — see 3.2
- **W6:** Unclear VDBFuzz budget — "over 26,000 requests" without runtime budget or whether it matches VDBFuzz's 2h/DB protocol. — see 4.1
- **W7:** Presentation density — multiple complex contributions packed into limited space. — see 5.1

### Detailed Assessment

#### 1. **Significance** — Adequate
- **1.1** [major, fixable] The 85% residual is compositional (based on TestVDB's findings) not population-estimated, limiting broader significance; the paper should more clearly distinguish "85% of defects we found" from "85% of all VDBMS defects." External validity is limited (Milvus+Qdrant carry the weight).
- **1.2** Practical impact (38 acknowledged, 31 fixed) is solid; the #7967↔#9045 case shows practical value.

#### 2. **Novelty** — Adequate
- **2.1** The two-layer model and source-grounded falsification are novel; the MASTOR distinction (source-as-oracle for implemented behavior vs source-as-reference for doc-impl gap) is clear and could be highlighted more.
- **2.2** [minor, fixable] The task-intrinsic stability claim (families converging on the same wrong interpretation) is novel but supported by limited evidence (n=12).

#### 3. **Soundness** — Weak
- **3.1** [major, fixable] The n=1 VDBFuzz head-to-head is statistically insufficient. The paper states "we do not generalize" but then uses these cases to support structural asymmetry claims — contradictory. Either expand to n≥5 per direction, or frame all asymmetry claims as hypothesis-generating. Related: the empty-vector template tests wait=true while #9045 is on wait=false — this is a template-coverage limitation, not fundamental oracle incapability; the framing "crash oracle cannot reach doc-impl defects" is too strong.
- **3.2** [minor, fixable] The RQ3 CIs are extremely wide [19%, 68%]; the preliminary nature should be emphasized more prominently given task-intrinsic is a central contribution. Vendor-wise contrast (Milvus/Qdrant vs Weaviate) and κ=1.0 cross-model check are credible.
- **3.3** [major, fixable] The crash-oracle asymmetry discussion overstates empirical support — only one controlled example (dim=2^63); generalization to "doc-impl oracle can reach crash-class" is unsupported beyond it.
- **3.4** [minor, unfixable] Internal-validity mitigations (cross-model κ=1.0 on 20) are limited; source-grounded verdicts may still have unknown false negatives.

#### 4. **Verifiability** — Adequate
- **4.1** [minor, fixable] The VDBFuzz protocol needs more detail — runtime budget, exact VDBFuzz version/configuration; "over 26,000 requests" without duration limits comparability.
- **4.2** [minor, fixable] The 111 candidates / 38 acknowledged classification would benefit from a supplementary table; the artifact promises this.
- **4.3** [minor, fixable] The cross-model κ=1.0 on 20 candidates — specify selection criteria (random vs purposive) and defect-type coverage.
- **4.4** [minor, fixable] Prompt engineering for GLM-5.2/DeepSeek not fully described; limits LLM-component reproducibility.

#### 5. **Presentation** — Adequate
- **5.1** [minor, fixable] Table 1 is dense; consider splitting (classical exclusion vs LLM-oracle reliability).
- **5.2** [minor, fixable] The §2 family-specific vs task-intrinsic discussion could introduce the concrete example earlier.
- **5.3** [minor, fixable] Related Work is comprehensive but dense; consider restructuring to map the novelty space explicitly.

### Questions for Authors
- **Q1:** [3.1] What minimum sample size would support statistical claims about oracle asymmetry? If infeasible, how to reframe the claim as preliminary?
- **Q2:** [3.1] Should the wait=true vs wait=false gap be characterized as "VDBFuzz's current template misses this path" rather than "crash oracles cannot reach doc-impl defects"?
- **Q3:** [3.3] Would you reframe the asymmetry as "hypothesis confirmed on one case" rather than a general structural principle?
- **Q4:** [4.1] What was the VDBFuzz runtime budget? Was it the standard 2h/DB protocol?
- **Q5:** [1.1] Should the title/abstract specify "on Milvus and Qdrant" rather than implying broader VDBMS coverage?
- **Q6:** [3.2] What sample size is needed for a ±15% CI width on the task-intrinsic rate?

## Reviewer 2: Area Specialist

**Overall Recommendation:** Weak Accept

### Summary
TestVDB addresses a real and under-studied problem: documentation-implementation defects in VDBMS APIs where the system silently accepts inputs that violate natural-language documentation constraints. The core insight---that LLM-derived behavioral claims from ambiguous documentation are unreliable and require falsification against source---is sound and well-differentiated from prior REST-API oracle work (AGORA+, SATORI, MASTOR) that extracts from structured sources. The method demonstrates practical value (38 maintainer-acknowledged defects, 81% FP suppression), and the VDBFuzz head-to-head usefully illustrates crash-oracle asymmetry. However, the evidentiary base for the central RQ3 claim (task-intrinsic errors) is thin: the twelve-clause probe (n=12) and four by-design behavior cases (n=4) are small, and the generalization to "task-intrinsic" as a distinct class from family-specific errors is insufficiently validated. The evaluation relies heavily on Milvus and Qdrant; Weaviate, MeiliSearch, and Chroma contribute breadth but not statistical weight. The presentation is generally clear, though some terminology ("task-intrinsic") could be more sharply defined.

### Core Strengths
- **S1:** Clear problem framing — the exclusion table (Table 1) convincingly maps where classical oracles fail.
- **S2:** Solid differentiation from prior work — structured sources (OpenAPI/traces/source) vs natural-language documentation; MASTOR directional contrast (source as oracle vs source as falsifier) is clear.
- **S3:** Practical scale and maintainer validation — 111 submissions / 38 acknowledged (31 fixed); 81% FP suppression (up from 31%) is a strong precision result.
- **S4:** VDBFuzz head-to-head insight — the bidirectional reachability probe (n=1 per direction) is appropriately framed as structural demonstration; the #9045↔#7967 case linking silent accept to crash recurrence is compelling.
- **S5:** Reusable artifact — the model-free invariant subclass is a clean, design-independent contribution.

### Core Weaknesses
- **W1:** Thin evidentiary base for RQ3 (task-intrinsic errors) — n=12 + n=4 = 16 clauses; Wilson CIs wide ([19%,68%] / [33%,77%]); the task-intrinsic layer is the key conceptual contribution and warrants more than a pilot.
- **W2:** Limited statistical generalization — results concentrate on Milvus (22) and Qdrant (13); 85% residual is composition, not prevalence.
- **W3:** Abstract scope imprecision — "about 85%" is vague (base unclear: 37/38 acknowledged vs 94/111 submitted).
- **W4:** VDBFuzz comparison fairness — the wait=true claim (line 110) is not cited from VDBFuzz's code/docs; if wait=true is not the default, the "VDBFuzz cannot reach" claim needs qualification.
- **W5:** Terminology ambiguity — "task-intrinsic" overlaps with documentation ambiguity; "documentation-intrinsic" might be clearer.

### Detailed Assessment

#### 1. **Significance** — Adequate
- **1.1** Problem significance (Adequate): documentation-implementation defects are a real gap; prevalence unknown (85% is composition, not population), honestly stated but limits assessment.
- **1.2** Practical impact (Adequate): 38 acknowledged (31 fixed), 81% FP suppression strong; source-access dependence limits transfer to closed-source VDBMSs.

#### 2. **Novelty** — Adequate
- **2.1** Conceptual novelty (Adequate): two-layer reliability model + source-grounded falsification novel and well-differentiated; task-intrinsic concept not strongly validated beyond n=16.
- **2.2** Technical novelty (Adequate): multi-agent pipeline + dev-reviewer three anchors novel in this setting; LLM-as-judge + cross-model architecture is incremental over Panickssery/wataoka, contribution is the domain instantiation.

#### 3. **Soundness** — Adequate
- **3.1** Methodology soundness (Adequate): falsification rule sound; retrospective design appropriate; ablations well-controlled; threat-model cross-check good.
- **3.2** Evaluation soundness (Adequate): RQ1 yield + RQ2 precision (69.2%, Wilson [55.7%,80.1%]) solid; DeepSeek κ=1.0 strengthens source-anchor claim; VDBFuzz head-to-head appropriately framed as structural demonstration; specificity check (0/13) strong control.
- **3.3 [major, fixable]** RQ3 task-intrinsic validation (Weak): rests on n=12+n=4=16; CIs wide; Milvus-heavy (9/12); generalization to "task-intrinsic" as a distinct class needs more than n=16.

#### 4. **Verifiability** — Adequate
- **4.1** Artifact availability (Excellent): commits to releasing prompts/versions/per-token accounting; Docker-pinned versions well-specified; ~$10^4 LLM calls / ~$10 per target is substantial reproducibility evidence.
- **4.2** Reproducibility risk (Adequate): no fixed random seed, run-to-run variance unmeasured; GLM-5.2 via bigmodel API may have sampling differences; cross-model κ=1.0 mitigates family-specific variance for source-anchor verdict.
- **4.3 [minor, fixable]** Text clarity: abstract "about 85%" imprecise (W3); "task-intrinsic" could be clearer (W5); VDBFuzz wait=true unsourced (W4).

#### 5. **Presentation** — Adequate
- **5.1** Structure and flow (Adequate): logical progression; exclusion table excellent; RQ3 presentation dense.
- **5.2** Writing quality (Adequate): prose clear; MASTOR directional contrast clear; abstract imprecision + terminology could sharpen.
- **5.3 [minor, fixable]** Minor: abstract "about 85%" exact base; rename "task-intrinsic"→"documentation-intrinsic"; cite/qualify VDBFuzz wait=true; Table add explicit-bound negative (0/13).

### Questions for Authors
- **Q1:** [3.3] Do you have additional data (from the 111 submissions or 73 non-acknowledged) to expand the task-intrinsic validation beyond n=16? If not, frame explicitly as a pilot.
- **Q2:** [W4] Is wait=true the default in VDBFuzz's code/docs? Cite it, or qualify "if wait=true is the default, VDBFuzz cannot reach this defect." Affects head-to-head fairness.
- **Q3:** [W3] Clarify "about 85%" with an exact base (37/38 acknowledged or 94/111 submitted excluding classical-addressable).
- **Q4:** [W5] Would "documentation-intrinsic" be clearer than "task-intrinsic"? Or explicitly define the distinction.
- **Q5:** [W2] Expand threats to validity on how a full-space estimation (capture-recapture) could be done and its challenges.
- **Q6:** [4.2] Expand the cross-model check to a third family (e.g., GPT-4) or larger sample to strengthen "not family-specific."

## Reviewer 3: General Reviewer

**Overall Recommendation:** Weak Accept

### Summary
The paper addresses documentation-implementation consistency testing in vector databases, where classical oracles (crash, differential, metamorphic, property-based) cannot reach accept/reject violations. The core innovation is source-grounded falsification: treating LLM-derived behavioral claims as refutable hypotheses and falsifying them against source code. TestVDB surfaced 111 issues across five VDBMSs; maintainers acknowledged 38 as defects. The source anchor suppresses 81% of false positives at 96.7% true-positive retention. The paper effectively argues that ambiguous documentation forces an LLM into both extraction and judgment roles, creating two layers of unreliability (family-specific and task-intrinsic), and that source-grounded falsification addresses the task-intrinsic layer that cross-model validation cannot.

### Core Strengths
- **S1:** Clear articulation of the documentation-implementation residual as distinct from correctness, and a convincing structural argument for why classical oracles fail (Table 1 maps each oracle class to the defect class it reaches).
- **S2:** The source-grounded falsification concept is well-differentiated from prior REST-API oracle work; the contrast with MASTOR is particularly strong.
- **S3:** Strong empirical grounding: 81% FP suppression with 96.7% TP retention; ablation tracing precision contribution from source vs other anchors is convincing.
- **S4:** The task-intrinsic vs family-specific error split is a useful contribution; the twelve-clause probe provides direct evidence.
- **S5:** The VDBFuzz head-to-head bidirectional reachability analysis (RQ1) is well-motivated and appropriately caveated; the Qdrant #9045/#7967 case is persuasive evidence for crash-oracle asymmetry.

### Core Weaknesses
- **W1:** The VDBFuzz head-to-head evidence is critically limited: n=1 per direction, with no statistical qualification, making the crash-oracle asymmetry claim stronger than what's shown.
- **W2:** Generalizability bounds are stated but not mapped to specific claim boundaries; central claims rest almost entirely on Milvus and Qdrant.
- **W3:** Task-intrinsic CIs are wide (5/12: [19%, 68%]; pooled 9/16: [33%, 77%]); contribution weight is disproportionate to sample size.
- **W4:** Version-number and GitHub issue-number usage for the VDBFuzz comparison is ambiguous for a reader without external context.

### Detailed Assessment

#### 1. **Significance** — Adequate
- **1.1** The documentation-implementation residual is a real problem; the 85% composition is compelling as a claim about the found set, not the population. Adequate rather than Excellent because prevalence in the wild is not established.
- **1.2 [moderate, fixable]** Practical impact is clear (38 acknowledged), but cost-benefit vs manual testing is not fully developed.

#### 2. **Novelty** — Adequate (provisional)
- **2.1** The source-grounded falsification concept is novel and well-differentiated from prior REST-API oracle work. Precise novelty of the two-layer split vs broader LLM-as-judge literature cannot be fully assessed without field context; provisional.
- **2.2 [minor, fixable]** Whether the task-intrinsic distinction is new or a reframing needs literature context.

#### 3. **Soundness** — Adequate
- **3.1 [severe, fixable]** The RQ1 VDBFuzz head-to-head is the critical weakness. Bidirectional reachability relies on n=1 per direction. The paper qualifies this ("we do not generalize the direction"), but the structural asymmetry claim and #9045/#7967 discussion read as representative rather than anecdotal. Fix: strengthen caveating or provide additional cases.
- **3.2 [moderate, fixable]** Generalizability bounds need clearer mapping — tag each quantitative claim with its scope.
- **3.3 [minor, fixable]** Precision-recall framing incomplete: recall not estimated. Fix: briefly discuss whether partial-recall estimation is feasible.

#### 4. **Verifiability** — Adequate
- **4.1 [moderate, fixable]** The VDBFuzz version-number/issue-number usage needs clarification — a reader cannot tell whether v1.18.0 includes the fix for #9045/#7967, or whether v1.4.0 and v1.18.0 are disjoint. Footnote URLs are provided but the relationship is not explicit. Fix: add one sentence.
- **4.2 [minor, fixable]** The RQ3 VDBFuzz discussion does not explicitly map the two crash cases to Table 1's rows.
- **4.3 [minor, fixable]** The RQ3 cross-model judging procedure could be more explicitly stated as a two-phase process.

#### 5. **Presentation** — Excellent
- **5.1** Well-written, clear structure, comprehensive abstract.
- **5.2** Figures and tables clear; Table 1 (exclusion) particularly effective.
- **5.3** Language issues minimal; some passive voice.
- **5.4 [minor, fixable]** Section 8 (Discussion) mentions closed-source VDBMSs as a limitation but does not discuss whether source-grounded falsification could adapt to binary-only/gray-box settings.

### Questions for Authors
- **Q1:** [3.1] Can you provide additional bidirectional cases, or strengthen caveating to flag the n=1-per-direction evidence as anecdotal rather than structural?
- **Q2:** [4.1] Add one explicit sentence clarifying the version/issue relationship (disjoint versions? which contains which issue/fix?).
- **Q3:** [3.2] Tag each quantitative claim with its scope (adjudicated pool / pilot / compositional).
- **Q4:** [3.3, 1.2] Briefly discuss the cost-benefit tradeoff of LLM hallucination cleanup vs manual testing.
- **Q5:** [2.2] Clarify whether the task-intrinsic vs family-specific split is novel or a reframing.
- **Q6:** [4.2] Add a mapping sentence connecting the VDBFuzz head-to-head cases to Table 1's rows.

### Meta Recommendation
**ACCEPT**

All three reviewers leaned Weak Accept, and no consensus criterion falls below Adequate (the unanimous-shortcut rule applies: three Weak Accept → ACCEPT). The consensus Soundness tier is Adequate by majority, but this masks the run's single most important signal: **all three reviewers independently flagged the VDBFuzz head-to-head's n=1-per-direction evidence as the dominant risk** (R1 elevated Soundness to Weak on exactly this point; R2 and R3 kept the tier at Adequate but each listed it as a severe/major fixable item). The verdict is therefore ACCEPT *pending* the Priority Revisions below — the asymmetry claim is the paper's newest and most prominent addition, and in its current form it outruns the two controlled cases that support it. The core contributions (the documentation-implementation residual framing, source-grounded falsification, the 81% FP-suppression retrospective, the maintainer-acknowledged yield) are solidly supported and carry the accept; the head-to-head needs the reframing below to land safely.

### Priority Revisions
Rank by impact on the verdict — `[major, fixable]` first.

1. **[major, fixable] VDBFuzz head-to-head soundness (n=1 per direction).** All three flagged this (R1 3.1/3.3, R2 W1/3.3, R3 3.1/W1). Either expand to more cases per direction, or reframe every asymmetry claim as hypothesis-generating: the Discussion's "a crash on a doc-valid input is itself a documentation-implementation violation" reads as a general principle from one case — mark it as a hypothesis confirmed on one controlled example. This is the issue that decides whether the asymmetry contribution survives.
2. **[major, fixable] Template-fairness framing.** R1 (3.1/W3) and R2 (W4): the empty-vector template tests `wait=true` while #9045 is on `wait=false`. Reframe this as a template/input-coverage limitation (and cite or qualify that `wait=true` is VDBFuzz's default), not as "the crash oracle cannot reach documentation-implementation defects." The current phrasing overstates oracle incapability.
3. **[minor, fixable] VDBFuzz protocol + version/issue clarity.** R1 (4.1) and R3 (4.1): state the runtime budget (was it VDBFuzz's 2h/DB protocol?) and add one sentence relating v1.4.0 / v1.18.0 / v1.18.2 and issues #9045 / #7967 (which version contains which defect/fix), so a reader without the issue tracker can follow.
4. **[minor, fixable] Task-intrinsic pilot emphasis.** R1 (3.2/W5), R2 (W1/3.3), R3 (W3): the CIs are wide ([19%,68%] on n=12; [33%,77%] pooled n=16) yet task-intrinsic is a title/abstract-level claim. Emphasize the preliminary nature more prominently and tag the claim scope.
5. **[minor, fixable] Quantitative-claim scope + abstract precision.** R2 (W3/3.2), R3 (3.2): tag each headline number with its base/scope (adjudicated pool of 54; twelve-clause pilot; compositional 85%) and give "about 85%" an exact denominator.
6. **[minor, fixable] κ=1.0 sampling + prompt detail.** R1 (4.3/4.4): state the sampling criteria for the 20 cross-model candidates and give more prompt-engineering detail for reproducibility.

*Divergence:* R1 rated Soundness Weak vs R2/R3 Adequate — R1 would push harder to reframe the asymmetry claim; R2/R3 accepted the current caveating. The consensus is Adequate, but the convergence of all three on the n=1 concern is why item 1 leads this list.
