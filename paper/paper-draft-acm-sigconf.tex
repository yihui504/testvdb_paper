Vector Database Management Systems (VDBMSs) store the embeddings that retrieval-augmented LLM applications depend on, yet a large class of their defects lacks any practical oracle. We study \emph{API compliance defects}: cases where a VDBMS silently accepts an input or behavior that violates its documented contract, such as accepting \texttt{nprobe=0}, normalizing \texttt{shardsNum=-1}, or returning success where the docs prescribe rejection. These defects corrupt query semantics and widen the attack surface, but produce no crash; fuzzers miss them, and the only reference is the documentation, which is natural-language and ambiguous.

Across 111 real VDBMS compliance defects we collected, about 90\% form a residual that differential, metamorphic, and property-based oracles cannot reach. The reason is structural: an accept/reject decision against a natural-language contract does not compile into a deterministic assertion. That non-compilability forces the checker to be an LLM, a regime that prior REST-API oracle work avoids by keeping deterministic, executable assertions. Inside this LLM-as-checker regime, contract errors split in two. Family-specific self-preference is mitigated by cross-model validation. \emph{Task-intrinsic} errors, where ambiguous documentation makes every LLM family infer the same wrong contract, are not: a different family reproduces the over-strict contract in fewer than half of our cases. The only ground truth that resolves task-intrinsic errors is the implementation.

We instantiate this as TestVDB, which falsifies LLM-derived contracts against source. TestVDB found 111 defects across five VDBMSs; maintainers acknowledged 38, and a controlled retrospective shows the source anchor lifts false-positive suppression from 31\% to 81\% while retaining 96.7\% of true positives.
\end{abstract}

\section{Introduction}

Vector Database Management Systems (VDBMSs) store the embeddings that retrieval-augmented LLM applications depend on. Their defects are costly: an empirical study~\cite{bugstudy25} attributes about 43\% of real VDBMS bugs to incorrect behavior rather than crashes, and the VDBMS testing roadmap~\cite{roadmap25} names the missing oracle for this class as the central open challenge. Existing VDBMS fuzzers~\cite{vdbfuzz26} detect only crashes. We target a prevalent subset: \emph{API compliance defects}, where a VDBMS silently accepts an input or produces a behavior that violates its documented contract, such as accepting \texttt{nprobe=0}, silently normalizing \texttt{shardsNum=-1}, or returning success where the documentation prescribes rejection. These defects corrupt query semantics and widen the attack surface, yet produce no crash and no exception.

The oracle problem~\cite{barr15} is acute here. Across 111 real VDBMS compliance defects we collected, about 90\% form a residual that the standard oracle families cannot reach (Table~\ref{tab:exclusion}). Differential testing catches mathematical-invariant violations across vendors but cannot adjudicate accept/reject, which diverges across VDBMSs by design and admits no reference~\cite{roadmap25}. Metamorphic relations~\cite{metmap24} address result correctness but not input-acceptance decisions, because a metamorphic relation is an output relation, not an input-acceptance transform. Property-based testing needs a machine-checkable property and an OpenAPI schema, neither of which VDBMS endpoints serve. The root cause is uniform: an accept/reject decision against a natural-language contract does not compile into a deterministic assertion.

That non-compilability forces the checker to be an LLM. We call the resulting setting the \emph{LLM-as-checker regime}: the pass/fail judgment over an undocumented boundary must come from a language model because no mechanical oracle exists. Recent REST-API oracle work stays outside this regime by construction: AGORA+, SATORI, and MASTOR derive oracles that remain executable assertions, checked deterministically, so the LLM never judges a test outcome.\footnote{Citations for AGORA+, SATORI, MASTOR, and for Panickssery et al.\ on LLM-as-judge self-preference are pending the Related Work bibliography pass.} VDBMS compliance admits no such deterministic oracle, which places it inside the regime.

Entering the regime creates the reliability problem. A naive design has one LLM family both extract the contract from documentation and judge compliance against it, and the two roles share biases. This is the LLM-as-judge self-preference phenomenon (Panickssery et al.), which cross-model validation mitigates. A second failure mode is deeper: when the documentation is ambiguous, every LLM family infers the same wrong contract. We call these \emph{task-intrinsic} contract errors. On a counterfactual probe, a different family reproduces the over-strict contract in fewer than half of our cases. The remaining cases are task-intrinsic, and cross-model cannot resolve them, because both families agree, wrongly, on what the documentation says.

The only ground truth that resolves task-intrinsic errors is the implementation itself. This motivates \emph{source-grounded falsification}: treat an LLM-derived contract as a refutable hypothesis and falsify it against source code, where the documentation expresses the intended behavior and the source expresses the actual behavior. The idea complements cross-model validation rather than replacing it: cross-model covers the family-specific subset, source covers both. We instantiate it in TestVDB, a detector that extracts contracts from documentation, probes VDBMS endpoints, and falsifies LLM verdicts against maintainer-authority evidence, primarily source.

\paragraph{Contributions.}
\begin{itemize}
  \item \textbf{The LLM-as-checker regime (\S\ref{sec:regime}).} We frame VDBMS API compliance as a setting where a deterministic oracle is unavailable and an LLM checker is forced, and show this is the precise boundary that separates VDBMS compliance from prior REST-API oracle work.
  \item \textbf{Quantification of the compliance residual.} Across 111 real defects, about 90\% are unreachable by differential, metamorphic, or property-based oracles, mapping where each classical class fails.
  \item \textbf{Task-intrinsic contract errors and the source-grounded counter.} We separate family-specific from task-intrinsic contract errors, show that cross-model fixes only the former, and argue that source is the only ground truth for the latter, with counterfactual evidence.
  \item \textbf{TestVDB and scale.} TestVDB found 111 defects across five VDBMSs; maintainers acknowledged 38. A controlled retrospective shows the source anchor lifts false-positive suppression from 31\% to 81\% at 96.7\% true-positive retention.
  \item \textbf{A reusable model-free invariant oracle subclass} (\texttt{COSINE} bounds, index completeness) that is classical-addressable, cross-vendor, and independent of TestVDB's LLM pipeline.
\end{itemize}

\section{The LLM-as-Checker Regime} \label{sec:regime}
\textit{Plan --- NEW section, the conceptual core (§8/§9). This is what v1 lacked.}
\begin{itemize}
  \item \textbf{Definition:} a setting is in the LLM-as-checker regime when the oracle cannot be compiled to a deterministic assertion, so the pass/fail judgment must come from an LLM.
  \item \textbf{Why VDB compliance forces it:} accept/reject semantics are NL-defined; contrast with AGORA+/SATORI/MASTOR, whose oracles ARE executable assertions $\Rightarrow$ deterministic checker $\Rightarrow$ they stay OUT of this regime (this is the precise distinction from the REST oracle line).
  \item \textbf{Two failure modes inside the regime:}
    \begin{itemize}
      \item \emph{Family-specific} (self-preference, Panickssery 2024): same family generates contract + judges $\Rightarrow$ shared bias self-confirms. Mitigated by cross-model.
      \item \emph{Task-intrinsic}: ambiguous docs make ALL families infer the same wrong (e.g., over-strict) contract. Cross-model CANNOT fix this --- both agree wrongly.
    \end{itemize}
  \item \textbf{t25 evidence:} feed the same doc passage to GLM vs DeepSeek; DeepSeek reproduces GLM's over-strict contract in only $\sim$half of cases $\Rightarrow$ the other half is task-intrinsic. (t25 N=9 pilot; expand for camera-ready.)
  \item \textbf{Implication:} source-grounded falsification is needed precisely for the task-intrinsic subset --- implementation is the only ground truth that resolves what cross-model cannot. This is the precise, defensible ``why source'' argument.
\end{itemize}

\section{TestVDB Design} \label{sec:design}
\textit{Plan --- reuse v1 mechanism, reframe CTS as the task-intrinsic resolver.}
\begin{itemize}
  \item 5-stage pipeline, 20 agents (reuse v1 §3): contract extraction $\to$ attack generation $\to$ 4-judge debate $\to$ dev-reviewer (source-grounded falsification) $\to$ novelty gate.
  \item Contract-Truth Separation (CTS): assertion layer (LLM) vs truth layer (source-grounded falsifier) --- reframe as ``the truth layer resolves task-intrinsic contract errors that cross-model cannot.''
  \item dev-reviewer's three anchors: clean reproduction, source-grounded verification (primary), threat-model cross-check (optional).
  \item Model-free invariant oracle subclass (COSINE$\in[-1,1]$, index completeness) --- the classical-addressable slice, reusable standalone.
\end{itemize}
