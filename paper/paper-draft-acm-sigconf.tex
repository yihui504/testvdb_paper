\title[TestVDB: source-grounded falsification for VDB API conformance]{TestVDB: Source-Grounded Falsification of LLM-Derived Contracts for API-Conformance Testing of Vector Databases}

\author{Authors TBD}

\begin{abstract}
Vector Database Management Systems (VDBMSs) store the embeddings that retrieval-augmented LLM applications depend on, yet a large class of their defects lacks a practical oracle. We study \emph{API conformance defects}: cases where a VDBMS silently accepts an input or behavior that violates its documented contract, such as accepting \texttt{nprobe=0}, accepting out-of-range index parameters such as \texttt{ef=0}, or returning success where the docs prescribe rejection. These defects corrupt query semantics and can return data the documented contract intended to exclude; the large majority produce no crash, so fuzzers miss them. The only reference for the intended behavior is the documentation, which is natural-language and ambiguous.

Across 111 submitted VDBMS issues (38 maintainer-acknowledged as defects), about 85\% are conformance defects that differential, metamorphic, and property-based oracles cannot reach. The reason is structural: an accept/reject decision against a natural-language contract does not compile into a deterministic assertion. That non-compilability forces the oracle to be an LLM, a setting that prior REST-API oracle work avoids by keeping deterministic, executable assertions. Inside this LLM-as-oracle setting, contract errors split in two. Family-specific self-preference is mitigated by cross-model validation. \emph{Task-intrinsic} errors, where ambiguous documentation makes different LLM families infer the same wrong contract, are not: a different family reproduces the over-strict contract in fewer than half of our cases. The only ground truth that resolves task-intrinsic errors is the implementation.

We instantiate this as TestVDB, which falsifies LLM-derived contracts against source. TestVDB surfaced 111 candidate issues across five VDBMSs; maintainers acknowledged 38 as defects, and a controlled retrospective shows the source anchor suppresses 81\% of false positives (up from 31\%) while retaining 96.7\% of true positives.
\end{abstract}

\section{Introduction}

Vector Database Management Systems (VDBMSs) store the embeddings that retrieval-augmented LLM applications depend on. Their defects are costly: an empirical study~\cite{bugstudy25} finds that more than half of VDBMS bugs manifest as functional failures, and the VDBMS testing roadmap~\cite{roadmap25} attributes about 43\% of VDBMS bugs to incorrect behavior and identifies oracle definition as a key challenge. Existing VDBMS fuzzers~\cite{vdbfuzz26} detect only crashes. We target a prevalent subset: \emph{API conformance defects}, where a VDBMS silently accepts an input or produces a behavior that violates its documented contract, such as accepting \texttt{nprobe=0} or out-of-range index parameters such as \texttt{ef=0}, or returning success where the documentation prescribes rejection. These defects corrupt query semantics and can return data the documented contract intended to exclude (for example, a negative score threshold that disables a filter and returns all matches). Most produce no crash (37 of 38 acknowledged in our data).

The oracle problem~\cite{barr15} is acute here. Across 111 submitted VDBMS issues (38 maintainer-acknowledged as defects), about 85\% are conformance defects that the standard oracle families cannot reach (Table~\ref{tab:exclusion}). Differential testing catches mathematical-invariant violations across vendors but cannot adjudicate accept/reject, which diverges across VDBMSs by design and leaves no cross-vendor reference; the roadmap flags differential testing as challenging in this setting~\cite{roadmap25}. Metamorphic relations~\cite{metmap24} address result correctness but not input-acceptance decisions, because a metamorphic relation is an output relation, not an input-acceptance transform. Property-based testing needs a machine-checkable property and an OpenAPI schema; VDBMS endpoints serve no schema that encodes these conformance constraints, and several serve no OpenAPI at all. The root cause is uniform: an accept/reject decision against a natural-language contract does not compile into a deterministic assertion.

That non-compilability forces the oracle to be an LLM. We refer to this as the \emph{LLM-as-oracle setting}: the pass/fail judgment over an undocumented boundary must come from a language model because no mechanical oracle exists. Recent REST-API oracle work stays outside this setting by construction: AGORA+, SATORI, and MASTOR derive oracles that remain executable assertions, checked deterministically, so the LLM never judges a test outcome.\footnote{Citations for AGORA+, SATORI, MASTOR, and for Panickssery et al.\ on LLM-as-judge self-preference are pending the Related Work bibliography pass.} VDBMS conformance admits no such deterministic oracle, which places it inside this setting.

Entering this setting creates the reliability problem. A naive design has one LLM family both extract the contract from documentation and judge whether behavior conforms to it, and the two roles share biases. This is the LLM-as-judge self-preference phenomenon (Panickssery et al.), which cross-model validation mitigates. A second failure mode is deeper: when the documentation is ambiguous, different LLM families infer the same wrong contract. We call these \emph{task-intrinsic} contract errors. On a counterfactual probe, a different family reproduces the over-strict contract in fewer than half of our cases. The remaining cases are task-intrinsic, and cross-model cannot resolve them, because both families agree, wrongly, on what the documentation says.

The only ground truth that resolves task-intrinsic errors is the implementation itself. This motivates \emph{source-grounded falsification}: treat an LLM-derived contract as a refutable hypothesis and falsify it against source code, where the documentation expresses the intended behavior and the source expresses the actual behavior. The idea complements cross-model validation rather than replacing it: cross-model covers the family-specific subset, source covers both. We instantiate it in TestVDB, a detector that extracts contracts from documentation, probes VDBMS endpoints, and falsifies LLM verdicts against maintainer-authority evidence, primarily source.

\paragraph{Contributions.}
\begin{itemize}
  \item \textbf{The LLM-as-oracle setting (\S\ref{sec:regime}).} We frame VDBMS API conformance as a setting where a deterministic oracle is unavailable and an LLM oracle is forced, and show this is the precise boundary that separates VDBMS conformance from prior REST-API oracle work.
  \item \textbf{Quantification of the conformance residual.} Across 111 submitted issues (38 maintainer-acknowledged as defects), about 85\% are conformance defects unreachable by differential, metamorphic, or property-based oracles, mapping where each classical class fails.
  \item \textbf{Task-intrinsic contract errors and the source-grounded counter.} We separate family-specific from task-intrinsic contract errors, show that cross-model fixes only the former, and argue that source is the only ground truth for the latter, with counterfactual evidence.
  \item \textbf{TestVDB and scale.} TestVDB surfaced 111 candidate issues across five VDBMSs; maintainers acknowledged 38 as defects. A controlled retrospective shows the source anchor suppresses 81\% of false positives (up from 31\%) at 96.7\% true-positive retention.
  \item \textbf{A reusable model-free invariant oracle subclass} (\texttt{COSINE} bounds, index completeness) that is classical-addressable, cross-vendor, and independent of TestVDB's LLM pipeline.
\end{itemize}

\section{Background and Problem Setup}

Barr et al.~\cite{barr15} classify test oracles by the artifact that supplies the pass/fail verdict: \emph{specified} (from a specification or contract), \emph{derivable} (from execution, as in differential, metamorphic, or invariant testing), \emph{implicit} (a crash), or \emph{none} (a human). TestVDB uses two: a contract oracle for conformance defects, in the specified class, and a model-free invariant oracle for mathematical-bound violations, in the derivable class. The subset we care about is conformance, and the central observation is that on this subset the first three classes fail, leaving only the human oracle, or its scalable proxy, an LLM.

We separate conformance from correctness. \emph{Conformance} asks whether the API's accept/reject behavior matches its documented contract. \emph{Correctness} asks whether a returned result is mathematically right, such as ANN recall or ranking. TestVDB targets conformance; result correctness of vector search remains open and is not our claim~\cite{roadmap25}.

The focus is well-supported and structural. An empirical study~\cite{bugstudy25} finds that more than half of VDBMS bugs manifest as functional failures, and the roadmap~\cite{roadmap25} attributes about 43\% of VDBMS bugs to incorrect behavior. Conformance defects are a large slice of that, and about 85\% of the ones we collected are unreachable by differential, metamorphic, or property-based oracles (Section~\ref{sec:eval}). The reason is structural: the inputs an endpoint should accept are declared in natural-language documentation rather than a formal grammar, so they cannot be turned into a deterministic assertion. The contract is the only reference, and it is ambiguous prose. We formalize the consequence next.

\section{The LLM-as-Oracle Setting} \label{sec:regime}

A testing problem belongs to the \emph{LLM-as-oracle setting} when the pass/fail verdict for the behavior under test cannot be issued by a deterministic assertion and must instead come from a language model. The defining property is the absence of a mechanical oracle: no reference implementation, no equivalence transform, no checkable property. VDBMS API conformance belongs to this setting.

The contrast with recent REST-API oracle work is sharp. AGORA+, SATORI, and MASTOR use a language model, but only to \emph{derive} an oracle that is then a deterministic assertion, such as a status code, a field-presence check, or an invariant.\footnote{Citations for AGORA+, SATORI, MASTOR, and for Panickssery et al.\ on LLM-as-judge self-preference are pending the Related Work pass.} A deterministic engine executes that assertion, so the model never issues a test verdict, and their problem sits outside the setting we define. VDBMS conformance has no such assertion, because the accept/reject boundary is natural-language prose, so the model must judge. This boundary is a property of the problem, not a choice of method, and it is what separates us from that line of work.

Entering the setting exposes a reliability problem with two layers. The first is family-specific: when one LLM family both derives the contract and judges conformance, the two roles share biases, and the judge tends to confirm the generator's errors. This is the LLM-as-judge self-preference phenomenon (Panickssery et al.), and cross-model validation, in which a second family judges, mitigates it. The second layer is deeper. When the documentation itself is ambiguous, different LLM families infer the same wrong contract. For example, a parameter documented as ``optional, default 1'' is over-formalized by both families as ``must be at least 1,'' when the real semantics is that the value 0 selects the default. The error originates in the shared input rather than in either model, so cross-model validation cannot remove it.

We confirmed the split with a counterfactual probe. We fed the same raw documentation passage to two LLM families, GLM and DeepSeek, and asked each to formalize the contract. DeepSeek reproduced GLM's over-strict contract in fewer than half of the nine cases we examined, and formalized the remainder correctly where GLM had not. The reproduced cases are task-intrinsic, and the rest are family-specific. We treat the probe as a pilot pending a larger study (Section~\ref{sec:eval}).

The implication is the basis for our method. Cross-model validation covers the family-specific subset only. The task-intrinsic subset requires a ground truth that does not depend on the documentation, and the only candidate is the implementation. This motivates source-grounded falsification, developed in Section~\ref{sec:design}: treat the LLM-derived contract as a refutable hypothesis and falsify it against source, where the documentation expresses the intended behavior and the source expresses the actual behavior.

\section{TestVDB Design} \label{sec:design}
\textit{Plan --- reuse v1 mechanism, reframe CTS as the task-intrinsic resolver.}
\begin{itemize}
  \item 5-stage pipeline, 20 agents (reuse v1 §3): contract extraction $\to$ attack generation $\to$ 4-judge debate $\to$ dev-reviewer (source-grounded falsification) $\to$ novelty gate.
  \item Contract-Truth Separation (CTS): assertion layer (LLM) vs truth layer (source-grounded falsifier) --- reframe as ``the truth layer resolves task-intrinsic contract errors that cross-model cannot.''
  \item dev-reviewer's three anchors: clean reproduction, source-grounded verification (primary), threat-model cross-check (optional).
  \item Model-free invariant oracle subclass (COSINE$\in[-1,1]$, index completeness) --- the classical-addressable slice, reusable standalone.
\end{itemize}
