\title[TestVDB: source-grounded falsification for VDB API conformance]{TestVDB: Source-Grounded Falsification of LLM-Derived Contracts for API-Conformance Testing of Vector Databases}

\author{Authors TBD}

\begin{abstract}
Vector Database Management Systems (VDBMSs) store the embeddings that retrieval-augmented LLM applications depend on, yet a large class of their defects lacks a practical oracle. We study \emph{API conformance defects}: cases where a VDBMS silently accepts an input or behavior that violates its documented contract, such as accepting \texttt{nprobe=0} or out-of-range index parameters such as \texttt{ef=0}, or returning success where the docs prescribe rejection. These defects corrupt query semantics and can return data the documented contract intended to exclude; the large majority produce no crash, so fuzzers miss them. The only reference for the intended behavior is the documentation, which is natural-language and ambiguous.

Across 111 submitted VDBMS issues (38 maintainer-acknowledged as defects), about 85\% are, by our fault-model classification, conformance defects that differential, metamorphic, and property-based oracles cannot reach. The reason is structural: an accept/reject decision against a natural-language contract does not compile into a deterministic assertion. That non-compilability rules out a mechanical oracle, so we adopt an LLM as the semantic judge. Prior REST-API oracle work avoids this setting by keeping deterministic, executable assertions. Inside this LLM-as-oracle setting, contract errors split in two. Family-specific self-preference is mitigated by cross-model validation. \emph{Task-intrinsic} errors, where ambiguous documentation makes different LLM families infer the same wrong contract, are not: in an initial nine-clause probe on Milvus, a different family reproduced the over-strict contract in 2. The most accessible automated ground truth that resolves task-intrinsic errors is the implementation.

We instantiate this as TestVDB, which falsifies LLM-derived contracts against source. TestVDB surfaced 111 candidate issues across five VDBMSs; maintainers acknowledged 38 as defects, and a controlled retrospective shows the source anchor suppresses 81\% of false positives (up from 31\%) while retaining 96.7\% of true positives.
\end{abstract}

\section{Introduction}

Vector Database Management Systems (VDBMSs) store the embeddings that retrieval-augmented LLM applications depend on. Their defects are costly: an empirical study~\cite{bugstudy25} finds that more than half of VDBMS bugs manifest as functional failures, and the VDBMS testing roadmap~\cite{roadmap25} attributes about 43\% of VDBMS bugs to incorrect behavior and identifies oracle definition as a key challenge. Existing VDBMS fuzzers~\cite{vdbfuzz26} detect only crashes. We target a prevalent subset: \emph{API conformance defects}, where a VDBMS silently accepts an input or produces a behavior that violates its documented contract, such as accepting \texttt{nprobe=0} or out-of-range index parameters such as \texttt{ef=0}, or returning success where the documentation prescribes rejection. These defects corrupt query semantics and can return data the documented contract intended to exclude (for example, a negative score threshold that disables a filter and returns all matches). Most produce no crash (37 of 38 acknowledged in our data).

The oracle problem~\cite{barr15} is acute here. Across 111 submitted VDBMS issues (38 maintainer-acknowledged as defects), about 85\% are, by our classification, conformance defects that the standard oracle families cannot reach (Table~\ref{tab:exclusion}). Differential testing catches mathematical-invariant violations across vendors but cannot adjudicate accept/reject, which diverges across VDBMSs by design and leaves no cross-vendor reference; the roadmap flags differential testing as challenging in this setting~\cite{roadmap25}. Metamorphic relations~\cite{metmap24} address result correctness but not input-acceptance decisions, because a metamorphic relation is an output relation, not an input-acceptance transform. Property-based testing needs a machine-checkable property and an OpenAPI schema; VDBMS endpoints serve no schema that encodes these conformance constraints, and several serve no OpenAPI at all. The root cause is uniform: an accept/reject decision against a natural-language contract does not compile into a deterministic assertion.

That non-compilability places VDBMS conformance in the \emph{LLM-as-oracle setting} (Section~\ref{sec:regime}): an LLM both derives the contract and judges conformance, a setting that prior REST-API oracle work~\cite{agoraplus25,satori25,mastor26} avoids by keeping deterministic assertions. The errors this introduces split into a family-specific layer that cross-model validation mitigates and a \emph{task-intrinsic} layer it cannot, because the ambiguity is in the documentation. \emph{Source-grounded falsification} (Section~\ref{sec:design}) resolves the task-intrinsic layer by treating the contract as a refutable hypothesis and the implementation as the ground truth. We instantiate it in TestVDB, a detector that extracts contracts from documentation, probes VDBMS endpoints, and falsifies LLM verdicts against source.

\paragraph{Contributions.}
\begin{itemize}
  \item \textbf{The LLM-as-oracle setting (\S\ref{sec:regime}).} We frame VDBMS API conformance as a setting where a deterministic oracle is unavailable and we adopt an LLM as the semantic judge, and show this is the precise boundary that separates VDBMS conformance from prior REST-API oracle work.
  \item \textbf{Quantification of the conformance residual.} About 85\% of the conformance defects we found are unreachable by differential, metamorphic, or property-based oracles, mapping where each classical class fails.
  \item \textbf{Task-intrinsic contract errors and the source-grounded counter.} We separate family-specific from task-intrinsic contract errors and show, on an initial nine-clause probe on Milvus, that cross-model judging misses the task-intrinsic subset (0/2) while source-grounded falsification catches all 9.
  \item \textbf{TestVDB and scale.} TestVDB surfaced 111 candidate issues across five VDBMSs; maintainers acknowledged 38 as defects. A controlled retrospective shows the source anchor suppresses 81\% of false positives (up from 31\%) at 96.7\% true-positive retention.
  \item \textbf{A reusable model-free invariant oracle subclass} (\texttt{COSINE} bounds, index completeness) that is classical-addressable, cross-vendor, and independent of TestVDB's LLM pipeline.
\end{itemize}

\section{Background and Problem Setup}

Barr et al.~\cite{barr15} classify test oracles by the artifact that supplies the pass/fail verdict: \emph{specified} (from a specification or contract), \emph{derivable} (from execution, as in differential, metamorphic, or invariant testing), \emph{implicit} (a crash), or \emph{none} (a human). TestVDB uses two: a contract oracle for conformance defects, in the specified class, and a model-free invariant oracle for mathematical-bound violations, in the derivable class. The subset we care about is conformance, and the central observation is that on this subset the first three classes fail, leaving only the human oracle, or its scalable proxy, an LLM.

We separate conformance from correctness. \emph{Conformance} asks whether the API's accept/reject behavior matches its documented contract. \emph{Correctness} asks whether a returned result is mathematically right, such as ANN recall or ranking. TestVDB targets conformance; result correctness of vector search remains open and is not our claim~\cite{roadmap25}.

Because the contract is natural-language prose rather than a formal grammar, the conformance verdict cannot be compiled into a deterministic assertion. We formalize the consequence in Section~\ref{sec:regime}.

\section{The LLM-as-Oracle Setting} \label{sec:regime}

A testing problem belongs to the \emph{LLM-as-oracle setting} when the pass/fail verdict cannot be issued by a deterministic assertion and must instead be made by a semantic judge. A human can serve as that judge but does not scale, so in practice the oracle is a language model. The defining property is the absence of a mechanical oracle: no reference implementation, no equivalence transform, and no checkable property for the accept/reject decision. VDBMS API conformance belongs to this setting.

The contrast with recent REST-API oracle work is sharp. AGORA+~\cite{agoraplus25}, SATORI~\cite{satori25}, and MASTOR~\cite{mastor26} use a language model, but only to \emph{derive} an oracle that is then a deterministic assertion, such as a status code, a field-presence check, or an invariant. A deterministic engine executes that assertion, so the model never issues a test verdict, and their problem sits outside the setting we define. VDBMS conformance has no such assertion, because the accept/reject boundary is natural-language prose, so a semantic judge must decide it. This boundary is a property of the problem, not a choice of method, and it is what separates us from that line of work.

Entering the setting exposes a reliability problem with two layers. The first is family-specific: when one LLM family both derives the contract and judges conformance, the two roles share biases, and the judge tends to confirm the generator's errors. This is the LLM-as-judge self-preference phenomenon (Panickssery et al.~\cite{panickssery24}), and cross-model validation, in which a second family judges, mitigates it. The second layer is deeper. When the documentation itself is ambiguous, different LLM families infer the same wrong contract. For example, a parameter documented as ``optional, default 1'' is over-formalized by both families as ``must be at least 1,'' when the real semantics is that the value 0 selects the default. The error originates in the shared input rather than in either model, so cross-model validation cannot remove it.

We confirmed the split with two probes on the same nine over-strict clauses. We first fed each raw documentation passage to two LLM families, GLM and DeepSeek, and asked each to formalize the contract independently; DeepSeek reproduced GLM's over-strict clause in 2 of the 9, the task-intrinsic subset, and corrected the other 7. We then tested the operational alternative directly: we asked DeepSeek to judge each of GLM's over-strict clauses against the documentation. Cross-model judging caught 6 of the 9 but missed all of the task-intrinsic subset, where DeepSeek read the ambiguous documentation as GLM had. Source-grounded falsification, by contrast, contradicts every over-strict clause, because the implementation accepts the value the clause rejects. The probes are small, nine Milvus clauses, and we treat them as a pilot pending a larger study (Section~\ref{sec:eval}).

The implication is the basis for our method. Cross-model validation covers the family-specific subset but not the task-intrinsic one. The task-intrinsic subset requires a ground truth that does not depend on the documentation; the most accessible automated ground truth is the implementation. This motivates source-grounded falsification, developed in Section~\ref{sec:design}: treat the LLM-derived contract as a refutable hypothesis and falsify it against source, where the documentation expresses the intended behavior and the source expresses the actual behavior.

\section{TestVDB Design} \label{sec:design}

TestVDB instantiates source-grounded falsification. It treats an LLM-derived contract as a set of clauses, each a hypothesis that the API enforces some documented constraint, and uses the implementation as the ground truth that can falsify them.

The falsification rule is concrete. For a clause that asserts the API rejects inputs where a parameter violates a constraint (for example, \texttt{shardsNum} $\geq 1$), the dev-reviewer examines the implementation. If the source shows that \texttt{shardsNum = 0} selects the default shard number, the clause is over-strict and the verdict that relied on it is falsified, a false positive suppressed. If the source shows no such intended semantics yet the implementation still accepts a value the contract rejects, the violation stands as a real defect.

This use of source is the opposite of MASTOR's~\cite{mastor26}: MASTOR reads source to generate oracles that encode implemented behavior and so cannot detect a gap between the documentation and the code, whereas TestVDB reads source to falsify documentation-derived clauses and targets exactly that gap (Section~\ref{sec:related}).

The pipeline has five stages. An LLM first extracts the documented contract as clauses. Attack agents then generate boundary inputs targeting each clause. An LLM-as-oracle judges whether each observed response conforms to the contract; this is the step whose two-layer unreliability we described in Section~\ref{sec:regime}. The dev-reviewer then falsifies the contract clauses and the LLM's verdicts against source. A novelty gate finally removes duplicates and known issues. The contract and the verdicts form the assertion layer; the dev-reviewer is the truth layer that falsifies them.

Within the truth layer, the dev-reviewer applies three anchors: a clean reproduction that re-probes the live API, a source-grounded verification that is the primary falsifier, and an optional threat-model cross-check. We separate the assertion layer from the truth layer because the same LLM family produces both the contract and the verdicts, and the implementation, a ground truth outside that family, is what falsifies them.

\section{Implementation} \label{sec:impl}

TestVDB runs as a multi-agent pipeline on the Claude Code runtime, with each of the 20 agents defined by a task-structured role prompt and dispatched to a GLM-5.2 backbone under the runtime's default sampling. Target VDBMSs run in pinned Docker versions (Milvus 2.6.19 for the single-LLM and single-layer ablations; the full version matrix is in the artifact). A complete run per target exercises the 20 agents over tens of generated candidates; wall-clock is dominated by the dev-reviewer's source-grounding step, repository clone and source retrieval, and live Docker re-probes, rather than by raw LLM latency. The 111-submission study plus the evaluation batches amount to on the order of $10^4$ LLM calls and roughly $\$10$ per target at current pricing, comparable to a few hours of manual boundary testing. The full prompts, target versions, and per-token accounting are in the artifact.

\section{Evaluation} \label{sec:eval}

We evaluate TestVDB on five VDBMSs (Milvus, Qdrant, Weaviate, MeiliSearch, Chroma) and ask four questions. \textbf{RQ1:} how many conformance defects does TestVDB surface, and how large is the residual beyond classical oracles? \textbf{RQ2:} does source-grounded falsification suppress false positives? \textbf{RQ3:} can cross-model validation resolve task-intrinsic contract errors, or is source needed? \textbf{RQ4:} does the model-free invariant subclass find real bugs on its own?

\paragraph{RQ1: yield and the conformance residual.}
TestVDB surfaced 111 candidate issues across the five systems; maintainers acknowledged 38 as defects (31 fixed, 7 accepted-open). The remaining 73 comprise 12 by-design, 4 rejected, 24 duplicates, and 33 pending or closed. Submissions span Milvus (51), Weaviate (30), and Qdrant (26), but maintainer acknowledgment concentrates on Milvus (22) and Qdrant (13); Weaviate, MeiliSearch, and Chroma contribute breadth rather than statistical weight (Table~\ref{tab:yield}). To quantify the residual, we classified each submitted issue by fault model: classical-addressable (a mathematical-invariant or crash that a differential, metamorphic, or crash oracle could in principle find), conformance (an accept/reject violation only a semantic judge reaches), or concurrency (a race or atomicity violation). About 85\% of the issues we submitted are, by this classification, conformance defects that classical oracles cannot reach, and 89\% on the 38 maintainer-acknowledged subset; the remainder split between classical-addressable cases (about 10\%) and concurrency defects (about 5\%). This composition reflects what TestVDB is designed to surface, not the true defect distribution; a full-space estimation with capture-recapture or an unbiased defect sample is future work. As a structural check, we ran a classical-oracle suite on Qdrant v1.18.2: a metamorphic relation set (distance symmetry, top-$k$ monotonicity, the \texttt{COSINE} bound, self-similarity) found no violations on this version and, by construction, no conformance defects, since metamorphic relations relate outputs rather than input-acceptance decisions. The mathematical-invariant violations such checks surface are the domain of our model-free subclass (RQ4); the conformance residual lies outside classical reach.

\paragraph{RQ2: effect of source-grounded falsification.}
On a controlled retrospective over 54 maintainer-adjudicated candidates (38 acknowledged, 12 by-design, 4 rejected), the dev-reviewer's source-grounded anchor suppresses 81\% of false positives, up from 31\% with only the other two anchors (clean reproduction and threat-model cross-check), while retaining 96.7\% of true positives ($n{=}30$). Aggregated end-to-end precision on the adjudicated pool is 69.2\% (Wilson 95\% CI $[55.7\%, 80.1\%]$). Of the remaining submissions, about 30 are still pending maintainer triage; the pending-resolution worst-case bound, which treats all pending as false positives, widens the interval to $[43.9\%, 80.5\%]$. Ablating the configuration shows where the precision comes from: single-LLM self-judgment (no source, no multi-agent debate) achieves 25.5\%; adding a single source-grounded cycle lifts precision to 45.6\%; the full multi-agent debate with the source anchor reaches 69.2\%. The per-anchor breakdown (clean reproduction, source-grounded verification, threat-model cross-check) is in the artifact, and the source anchor is the dominant contributor. RQ3 next isolates the subset of these errors that cross-model validation cannot reach, where source is the only resolver.

\paragraph{RQ3: cross-model validation vs source on task-intrinsic errors.}
The central claim is that source-grounded falsification resolves task-intrinsic contract errors that cross-model validation cannot. We tested this directly on nine GLM-derived over-strict clauses (Milvus). We first asked a second family, DeepSeek, to formalize each contract independently; it reproduced GLM's over-strict clause in 2 of the 9, the task-intrinsic subset. We then asked DeepSeek to judge each of GLM's clauses against the documentation. Cross-model judging caught 6 of the 9 over-strict clauses but missed both task-intrinsic ones, where DeepSeek read the ambiguous documentation as GLM had. Source-grounded falsification contradicts all nine, because the implementation accepts the value each over-strict clause rejects. Cross-model validation therefore covers the family-specific subset but leaves the task-intrinsic residual to source. A cross-vendor check on Qdrant (v1.18.2, live-probed) shows where the pattern concentrates: Qdrant documents explicit minimum bounds that its server mostly enforces (it rejects \texttt{limit=0} with 422), so its doc-code gaps are conformance defects (for example, it accepts \texttt{timeout=0} against a documented minimum of 1) rather than over-formalized clauses, and the over-strict phenomenon is largely confined to APIs with many optional-default parameters such as Milvus. We treat the nine-clause Milvus probe as a pilot; a larger head-to-head study is future work.

\paragraph{RQ4: model-free invariant oracle subclass.}
Separately from the LLM pipeline, a model-free invariant subclass detects violations of hard mathematical bounds: \texttt{COSINE} distance above 1 for identical vectors, an index returning 2 of 25 matching points, and a payload filter returning points that miss a required field. The subclass probes the API directly with boundary inputs (identical vectors, a partially indexed collection, a filter on an absent field) and checks each response against the bound, with no contract extraction or LLM judgment. These reproduce across Milvus and Qdrant and are the least design-contingent part of the evaluation.

\paragraph{Threats to validity.}
\emph{Internal validity.} The RQ3 probe is small (nine clauses, Milvus) and is the most contingent finding; the retrospective and the yield are the broader evidence base, and a binomial interval on the task-intrinsic catch rate awaits a larger study. \emph{External validity.} Generalization to Weaviate, MeiliSearch, and Chroma is breadth-only; statistical claims rest on Milvus and Qdrant, and soft result correctness of vector search (ANN recall, ranking) is out of scope. \emph{Construct validity.} All source-anchor results use a single model family (GLM-5.2), a full cross-model ablation of the dev-reviewer is open, and we do not estimate recall because there is no public ground-truth defect catalog for VDBMSs.

\section{Related Work} \label{sec:related}

\paragraph{VDBMS testing.} VDBFuzz~\cite{vdbfuzz26} is the first dedicated VDBMS fuzzer and uses crash as its oracle, which makes it complementary to this work. The roadmap~\cite{roadmap25} sets the agenda we build on, and the empirical bug study~\cite{bugstudy25} the taxonomy; both point to the conformance subset we target.

\paragraph{REST-API oracle generation.} A recent line derives test oracles for REST APIs from specifications or source code. AGORA+~\cite{agoraplus25} learns dynamic invariants from request and response traces, SATORI~\cite{satori25} uses an LLM to read the OpenAPI specification, and MASTOR~\cite{mastor26} uses a multi-agent system over source code. These are not in our setting: SATORI requires an OpenAPI specification and AGORA+ an executable trace against a schema, neither of which VDB endpoints serve, and each produces an oracle that remains an executable assertion, checked deterministically, so the LLM never issues a test verdict (Section~\ref{sec:regime}). MASTOR is the closest, since it also uses source, but it tests what the implementation does, with source as the reference, and so cannot detect a gap between the documentation and the code; TestVDB tests what the documentation prescribes, with source as the actual-behavior ground truth, and that gap is exactly what it targets.

\paragraph{LLM-as-judge reliability.} Self-preference bias, in which an LLM evaluator favors its own family's outputs, is established for general text evaluation (Panickssery et al.~\cite{panickssery24}); we observe the analogous bias in the test-oracle pipeline. Our family-specific layer is an instance of it, and cross-model validation mitigates it as expected. Our addition is the task-intrinsic layer, where the error is in the shared documentation rather than the model, and which cross-model validation cannot remove.

\paragraph{Database and property-based oracles.} NoREC~\cite{norec20}, TLP~\cite{tlp20}, DQE~\cite{dqe20}, and DDLCheck~\cite{ddlcheck25} test SQL correctness against reference semantics that VDBMS conformance lacks. Property-based testing~\cite{claessen00} and its REST instances, Schemathesis~\cite{schemathesis} and QuickREST~\cite{quickrest20}, together with metamorphic testing (MeTMaP~\cite{metmap24}), cover the mathematical-invariant subset; the conformance residual is where they, by construction, stop.

\section{Discussion and Limitations}

The LLM-as-oracle setting is not specific to VDBMSs. Any system whose correctness criterion is a natural-language contract that cannot be compiled to a deterministic assertion enters it: REST contract testing where the schema is absent or silent on the semantics, configuration validation, and policy-as-code checks where the documentation is the only oracle. In each, a single LLM family that both extracts the specification and checks conformance is susceptible to the two-layer unreliability we describe, and source-grounded falsification is the natural mitigation. We have not tested these transfers and leave them to future work.

Beyond the threats to validity in Section~\ref{sec:eval}, two limitations bound the approach itself. Source-grounded falsification requires source, so it does not transfer to closed-source VDBMSs, and it treats the implementation as correct, so an implementation bug can wrongly falsify a clause whose contract is right. The 85\% residual is the composition of TestVDB's findings, biased toward conformance by design, not an estimate of the true defect distribution.

\section{Conclusion}

VDBMS API conformance is a defect class where no deterministic oracle exists, which leads us to adopt an LLM as the semantic judge. The LLM's contract errors split into a family-specific layer that cross-model validation mitigates and a task-intrinsic layer that it cannot, because the ambiguity lives in the documentation. Source-grounded falsification resolves the task-intrinsic layer by treating the LLM-derived contract as a hypothesis and the implementation as the ground truth. TestVDB demonstrates the approach at scale: 111 candidate issues across five VDBMSs, 38 maintainer-acknowledged, with the source anchor suppressing 81\% of false positives. The boundary we draw, between problems whose oracle can be checked deterministically and those that require a semantic judge, is where we see the testing of LLM-dependent systems heading.
