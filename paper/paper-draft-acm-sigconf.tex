\title[TestVDB: doc-implementation defects in VDBMSs]{TestVDB: Detecting Documentation-Implementation Defects in Vector Databases via LLM-Derived Behavioral Claims}

\author{Authors TBD}
\email{tbd@example.org}

\begin{abstract}
Vector Database Management Systems (VDBMSs) store the embeddings that retrieval-augmented Large Language Model (LLM) applications depend on, yet most of their defects are logical bugs that produce no crash and thus escape crash-oracle fuzzers such as VDBFuzz. We target \emph{documentation-implementation defects}: cases where a VDBMS silently accepts an input or behavior that violates its API documentation, such as accepting \texttt{nprobe=0} when the documentation declares the range as $[1, 16384]$. These defects corrupt query semantics. Across 107 issues TestVDB surfaced, maintainers acknowledged 49 as true-positive defects (68\% adjudicated yield; 15 fixed via merged PR, 16 with open fix-PRs, 18 acknowledged but unfixed). Because the boundary is natural-language prose, current instantiations of deterministic oracles (differential, metamorphic, property-based) miss these accept/reject decisions, leaving an LLM as the practical oracle. We instantiate TestVDB, a four-stage pipeline (claim extraction, test generation, execution, confirmation) that uses LLMs to read documentation, generate tests, and adjudicate responses. Two failure modes produce false positives: hallucination in claim extraction and self-preference bias in judgment. A multi-perspective judging baseline raises precision but collapses recall, so we introduce a \emph{dev-reviewer} agent that acts as a source-grounded falsifier, reproducing each candidate, cross-checking it against source, and trying to disprove it. On 48 maintainer-adjudicated candidates, the dev-reviewer reaches 67\% precision and 74\% recall (3-run ensemble), versus 37\% recall without the source anchor. These results use a single LLM backbone (GLM-5.2); cross-family generalization is an open question. A bidirectional probe against VDBFuzz on Qdrant shows TestVDB reaches a crash-class defect by contract reasoning, while VDBFuzz misses a silent-accept defect under its current templates.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Vector Database Management Systems (VDBMSs) store the embeddings that retrieval-augmented LLM applications depend on. Their defects are costly. An empirical bug study~\cite{bugstudy25} finds that more than half of VDBMS bugs manifest as functional failures, and the VDBMS testing roadmap~\cite{roadmap25} attributes about 43\% of VDBMS bugs to incorrect behavior and identifies oracle definition as a key challenge. Existing VDBMS fuzzers~\cite{vdbfuzz26} apply classical fuzzing~\cite{manes21} but detect only crashes, so the logical-bug majority goes unreached.

A silent-accept defect does not surface as a crash; it surfaces as wrong results returned to the application. In a retrieval-augmented LLM stack, this means the wrong context reaches the model: a disabled filter returns all matches, a zero-length vector corrupts an index, or a dropped partition hides data the application expects. The downstream model has no signal that its context is corrupted, so the error propagates into generated text without an error code to log. The absence of a crash is the wrong signal for this defect class, which is why an oracle that fires only on crashes (such as VDBFuzz) is structurally blind to it.

We target a prevalent subset: \emph{documentation-implementation defects}, where a VDBMS silently accepts an input or produces a behavior that violates its API documentation. A representative case is Milvus issue~\#49823, which silently accepts \texttt{nprobe=0} although the documentation declares the parameter range as $[1, 16384]$. Such defects corrupt query semantics. They can return data the documentation intended to exclude (for example, a negative score threshold that disables a filter and returns all matches), and most produce no crash.

The oracle problem~\cite{barr15} is acute here. The documented boundary is natural-language prose, so deterministic oracles cannot adjudicate these accept/reject decisions. Differential testing catches mathematical-invariant violations across vendors but cannot adjudicate accept/reject, which diverges across VDBMSs by design~\cite{roadmap25}. Metamorphic relations~\cite{metmap24} address result correctness but not input-acceptance decisions. Property-based testing~\cite{claessen00} needs a machine-checkable property and an OpenAPI schema, but VDBMS endpoints rarely expose such schemas. REST-API oracle tools~\cite{agoraplus25,satori25,mastor26} extract from low-ambiguity structured sources (OpenAPI, traces, source-as-oracle), not from ambiguous natural-language documentation. We expand this exclusion argument in Section~\ref{sec:background} (Table~\ref{tab:exclusion}); the residual leaves an LLM as the practical oracle.

Putting an LLM in both the extraction role (documentation to behavioral claims) and the judgment role (response to verdict) creates a false-positive problem with two failure modes. On the extraction side, the LLM hallucinates constraints the documentation does not state~\cite{ji23hall}. On the judgment side, the same family that extracts a claim tends to confirm it, the self-preference bias established for LLM evaluators~\cite{panickssery24}. A multi-perspective judging baseline (four specialized judge agents with a vote) raises precision but collapses recall, because the judge agents share the documentation ambiguity. We therefore add a \emph{dev-reviewer} agent that acts as a source-grounded falsifier: it reproduces each candidate, cross-checks it against the implementation source, and tries to disprove it. A candidate that survives all three checks is adjudicated a defect; one that fails any check is suppressed.

We instantiate this as TestVDB, a four-stage pipeline (Section~\ref{sec:approach}): behavioral-claim extraction, test-script generation, sandboxed execution, and defect confirmation, with LLMs automating the documentation-reading, generation, and adjudication steps. TestVDB surfaced 107 candidate issues across three VDBMSs (Milvus, Qdrant, Weaviate); maintainers acknowledged 49 as true-positive defects, and 15 are fixed via merged PR. On a controlled retrospective over 48 maintainer-adjudicated candidates, the dev-reviewer reaches 67\% precision and 74\% recall (3-run any-confirmed ensemble), against 37\% recall without the source anchor. A bidirectional probe against VDBFuzz~\cite{vdbfuzz26} shows TestVDB reaches a crash-class defect (Qdrant integer overflow on \texttt{size}$=2^{63}$) by contract reasoning, while VDBFuzz misses a TestVDB silent-accept defect (\texttt{wait=false} accepting a zero-length vector, \#9045) under its current templates.

\paragraph{Contributions.}
\begin{itemize}
  \item \textbf{Documentation-implementation defects as a VDBMS target.} We characterize the defect class that VDBMS fuzzers miss, formalize it as consistency with natural-language documentation, and show by an oracle-exclusion argument (Section~\ref{sec:background}) why an LLM is the practical oracle for the residual.
  \item \textbf{TestVDB.} A four-stage pipeline that uses LLMs to extract behavioral claims from documentation, generate executable tests, run them on sandboxed VDBMSs, and confirm defects by comparing expected and actual behavior (Section~\ref{sec:approach}).
  \item \textbf{Source-grounded falsification.} We diagnose two false-positive failure modes (extraction hallucination, judgment self-preference), show multi-perspective judging is insufficient, and introduce a dev-reviewer agent that falsifies LLM verdicts against implementation source (Sections~\ref{sec:fp}--\ref{sec:devreviewer}).
  \item \textbf{Evaluation.} 107 submitted issues with 49 maintainer-acknowledged true-positive defects (15 merged-PR-fixed) across three VDBMSs; a 48-candidate retrospective showing the source anchor lifts recall from 37\% to 74\%; and a bidirectional probe against VDBFuzz that explores complementary coverage (Section~\ref{sec:eval}).
\end{itemize}

\section{Background and Problem Setup}
\label{sec:background}

VDBMS API documentation, unlike the structured sources that REST-API oracle tools rely on (OpenAPI specifications, execution traces, or source code), is natural-language prose. Constraints are implicit and ambiguous: a parameter described as ``optional, default 1'' may or may not admit a zero, and the documentation rarely says. This forces a semantic interpretation step that deterministic oracles cannot perform, and an LLM is the scalable proxy for it.

We separate \emph{documentation-implementation consistency} from \emph{correctness}. Consistency asks whether the API's accept/reject behavior matches its documentation. Correctness asks whether a returned result is mathematically right, such as approximate nearest neighbor (ANN) recall or ranking. TestVDB targets consistency; result correctness of vector search remains open and is not our claim~\cite{roadmap25}.

The oracle problem~\cite{barr15} is acute on this subset. Table~\ref{tab:exclusion} walks the standard oracle candidates and the structural reason each misses the documentation-implementation residual. Differential testing catches mathematical-invariant violations across vendors but cannot adjudicate accept/reject, which diverges across VDBMSs by design~\cite{roadmap25}. Metamorphic relations~\cite{metmap24} address result correctness but not input-acceptance decisions, because a metamorphic relation is an output relation, not an input-acceptance transform. Property-based testing~\cite{claessen00} needs a machine-checkable property and an OpenAPI schema; VDBMS endpoints serve no schema that encodes these constraints, and several serve no OpenAPI at all. REST-API oracle tools~\cite{agoraplus25,satori25,mastor26} extract from low-ambiguity structured sources and so avoid the regime where documentation is ambiguous prose. The residual leaves an LLM-derived oracle as the practical option. A prior line also derives oracles from documentation with LLMs~\cite{toradocu16,augmentest25}, but keeps the LLM as the final arbiter by validating only through runtime behavior; TestVDB instead falsifies against implementation source (Section~\ref{sec:devreviewer}). The reliability problem this introduces is the subject of Sections~\ref{sec:fp}--\ref{sec:devreviewer}.

\section{TestVDB Approach}
\label{sec:approach}

TestVDB instantiates documentation-implementation consistency testing as a four-stage pipeline: behavioral-claim extraction, test-script generation, sandboxed execution, and defect confirmation, with LLMs automating the documentation-reading, generation, and adjudication steps. A novelty gate finally removes duplicates and known issues. Figure~\ref{fig:pipeline} sketches the pipeline.

\paragraph{Step 1: behavioral-claim extraction.}
The contract-formalizer agent reads the VDBMS API documentation and emits structured behavioral claims as a JSON contract. Each claim records a \texttt{constraint\_id}, the endpoint, the assertion (for example, \texttt{nprobe} $\in [1, \texttt{nlist}]$), and a source pointer into the documentation. The LLM performs the semantic interpretation that deterministic oracles cannot, translating ``optional, default 1'' into a checkable clause.

\paragraph{Step 2: test-script generation.}
Attack agents turn each claim into an executable probe. For a claim asserting the API rejects \texttt{nprobe=0}, the agent generates a request carrying the boundary value and a control value, plus any setup the endpoint needs (collection creation, indexing, payload insertion). Scripts target the boundary so that an accept where the documentation prescribes reject is observable in the response.

\paragraph{Step 3: sandboxed execution.}
TestVDB runs each script against a Docker-pinned VDBMS instance (Milvus 2.6.19, Qdrant v1.18.2, Weaviate v1.38.2 in our study). Raw HTTP requests and responses are logged for downstream inspection. The sandbox isolates runs so a candidate reproduces under a clean probe, free of tooling artifacts.

\paragraph{Step 4: defect confirmation.}
A judge agent compares the documented expectation (the claim) against the actual response, the VDBMS state, and the logs. A response that accepts a value the documentation prescribes rejecting becomes a candidate defect. The LLM also adjudicates this step, which introduces the false-positive problem we examine next.

\paragraph{Example: the \#49823 path.}
Milvus documents \texttt{nprobe} as an integer in $[1, 16384]$. The contract-formalizer extracts the claim \texttt{nprobe}~$\in [1, 16384]$ from the documentation passage. An attack agent generates a probe that issues \texttt{entities/search} with \texttt{nprobe=0} and a control with \texttt{nprobe=1}. On Milvus 2.6.19 the \texttt{nprobe=0} request returns HTTP 200 with results, while the documentation prescribes rejection. The judge agent flags a documentation-implementation violation, and the dev-reviewer verifies that the implementation accepts the value by reading the search-parameter handler in source, which performs no range check on \texttt{nprobe}.

\paragraph{LLM automation.}
TestVDB runs as a multi-agent pipeline~\cite{hou23llmse} on the Claude Code runtime, with each agent defined by a task-structured role prompt and dispatched to a GLM-5.2 backbone under default sampling. The agents span five stage-aligned roles: a contract-formalizer that reads documentation and emits structured JSON claims; four attack agents (boundary, semantic, state, discovery) that generate probes from claims; a judge-agent quartet (documentation, evidence, severity, novelty) that triages candidates; the dev-reviewer that falsifies against source; and a reporter that assembles defect reports. Each agent operates independently. For source-grounded falsification, TestVDB clones each target's source at the pinned version (\texttt{milvus-src}~v2.6.19, \texttt{qdrant-src}~v1.18.2, \texttt{weaviate-src}~v1.38.2); the dev-reviewer greps the clone to trace constants and call chains, and the clone is the only ground truth for what the implementation does. Wall-clock per target is dominated by source-grounding and live Docker re-probes rather than raw LLM latency; a full run is on the order of $10^4$ LLM calls and roughly $\$10$ per target at current API pricing. Roughly half of the calls are dev-reviewer source-grounding steps (the dominant wall-clock cost), a quarter are claim extraction and test generation, and the rest are judging and the novelty gate (Table~\ref{tab:cost}).

\section{The False-Positive Problem}
\label{sec:fp}

Putting an LLM in both the extraction role and the judgment role creates a false-positive problem with two failure modes. The LLM may extract a claim the documentation does not state, and the LLM may confirm a claim it extracted even when the response contradicts it. The two modes have different causes and require different countermeasures.

\paragraph{Hallucination in extraction.}
When the contract-formalizer reads ambiguous documentation, it sometimes emits a constraint stronger than the documentation states. A parameter documented as ``optional, default 1'' becomes ``must be at least 1,'' or a parameter whose documentation illustrates a power-of-two value becomes ``must be a power of two.'' Both reject values the documentation allows, so the boundary test reports a violation that is not a defect. This is the test-oracle instance of LLM hallucination~\cite{ji23hall}: the model supplies a plausible constraint the input does not support.

\paragraph{Self-preference in judgment.}
When the same LLM family extracts a claim and later judges whether the response conforms, the two roles share biases, and the judge agent tends to confirm the extractor's claim~\cite{panickssery24}. A verdict that should be ``accept'' (the documentation allows the value) is read as ``reject'' because the judge agent leans toward the extracted clause. Self-preference compounds hallucination: an over-strict extracted claim is more likely to be confirmed by a judge agent of the same family.

\paragraph{Multi-perspective judging is insufficient.}
A natural counter is to replace the single judge agent with a panel. We tried a multi-perspective design with four specialized judge agents (documentation, evidence, severity, novelty), each reading the documentation independently and voting on each candidate under a majority-of-four rule. On the retrospective (Section~\ref{sec:eval}), it reaches about 80\% precision but only about 15\% recall. The 15\% figure is the highest recall we could reach by tuning the voting threshold; higher thresholds traded recall for at most a few points of precision. The judge agents read the same ambiguous documentation and converge on the same over-strict claim, so voting cannot break the agreement. The failure is structural, not a tuning problem. Any judge agent that reads the documentation shares the documentation's ambiguity. Table~\ref{tab:multipersp} lists the four judge agents and their focus.

The two modes point to different fixes. Hallucination calls for a falsifier that does not depend on the documentation for ground truth, and self-preference calls for a signal that does not come from the same family. The most accessible independent signal is the implementation. The API's actual behavior is a fact the LLM cannot argue with. This motivates the dev-reviewer.

\section{Dev-Reviewer: Source-Grounded Falsifier}
\label{sec:devreviewer}

The dev-reviewer agent is a source-grounded falsifier. It acts as a VDBMS maintainer would: reproduce each candidate under a clean probe, cross-check it against the implementation source, and try to disprove it. A candidate that survives all three checks is adjudicated a defect; one that fails any check is suppressed as a false positive.

\paragraph{Three checks.}
For each candidate, the dev-reviewer applies:
\begin{enumerate}
  \item \emph{Independently reproducible.} Does the candidate reproduce under a clean probe, free of tooling artifacts? The dev-reviewer rebuilds a minimal request from the contract and the raw evidence, rather than copying the original probe, and runs it on the live VDBMS.
  \item \emph{Evidence sufficient.} Do the response, the VDBMS state, and the source code jointly establish the documentation-implementation gap? The dev-reviewer cross-checks the response through an independent channel (a primary-key read, a scroll, a count) so the gap does not depend on a single field the request failed to request.
  \item \emph{Falsifiable.} Can the candidate be disproven by an alternative documented interpretation, such as a by-design behavior or a wont-fix pattern? The dev-reviewer reads the implementation source to check whether the ``violation'' is an intentional default, an idempotent return, or a maintainer-acknowledged design choice.
\end{enumerate}

\paragraph{Three anchors.}
The checks draw on three evidence anchors. A \emph{clean-reproduction} anchor re-probes the live API to filter tooling-artifact false positives. A \emph{source-grounded} anchor (the primary falsifier) reads the implementation source across the full clone, tracing constants and call chains, to check whether the constraint is real and whether the source implements it. An optional \emph{threat-model} anchor compares the candidate against maintainer-acknowledged by-design and wont-fix patterns. The same LLM family produces both the behavioral claims and the verdicts; the implementation, an independent information source, is what falsifies them.

\paragraph{Example: the \#9255 reversal.}
Qdrant issue \#9255, a payload-filter false positive, illustrates falsification in action. The original oracle flagged a search returning points whose \texttt{payload} appeared absent as a filter violation, but the raw request had not set \texttt{with\_payload=true}, so the absence was a projection artifact rather than a stored-data gap. The dev-reviewer rebuilt the request with \texttt{with\_payload=true} and confirmed every returned point carried the filtered field; the candidate was suppressed as a false positive whose root cause was \texttt{assertion\_depends\_on\_unrequested\_field}. This is the failure mode the multi-perspective panel misses, because every judge agent reads the same response and none re-issues the request.

The dev-reviewer is not a second extractor that reads the documentation again. It reads the source, where the actual behavior is defined, and uses the contract only as the assertion under test. This separation is what breaks self-preference: the falsifier's ground truth is the implementation, not the same family's prior claim.

\section{Evaluation}
\label{sec:eval}

We evaluate TestVDB on three VDBMSs (Milvus, Qdrant, Weaviate) and ask three questions:
\begin{description}
  \item[RQ1 (detection capability):] how many documentation-implementation defects does TestVDB surface in real-world VDBMSs?
  \item[RQ2 (false-positive suppression):] how effectively does the source-grounded dev-reviewer suppress false positives, relative to a single-LLM baseline and a multi-perspective panel?
  \item[RQ3 (comparison with VDBFuzz):] how many defects detected by TestVDB can the existing crash-oracle approach reach, and vice versa?
\end{description}

\paragraph{RQ1: detection capability.}
TestVDB surfaced 107 candidate issues across the three systems; maintainers acknowledged 49 as true-positive defects, of which 15 are fixed via merged PR, 16 have open fix-PRs, and 18 are acknowledged but unfixed (8 still open with an accepted label and 10 acknowledged but stale-closed without a merged PR). The remaining 58 comprise 23 by-design or rejected and 35 still pending maintainer adjudication. Submissions span Milvus (51), Qdrant (26), and Weaviate (30); true positives span Milvus (22), Qdrant (14), and Weaviate (13). Of the 72 maintainer-adjudicated submissions (49 true-positive, 23 by-design or rejected), the yield precision is 68.1\% (Wilson 95\% CI $[56.6\%, 77.7\%]$); treating all 35 still-pending submissions as false positives gives a worst-case bound of 45.8\% (Wilson 95\% CI $[36.7\%, 55.2\%]$). The 15 merged-PR fixes across three production VDBMSs show practical impact. Table~\ref{tab:yield} breaks the yield down by vendor. The yield is biased toward documentation-implementation defects by the tool's design (Section~\ref{sec:disc}); the proportion reflects our yield, not a population estimate. The vendor distribution reflects documentation style: Milvus (22 TP of 51 submitted) concentrates defects in optional-default parameters (\texttt{nprobe}, \texttt{ef}, \texttt{level}) where documentation omits explicit bounds; Qdrant (14 of 26) in search parameters (\texttt{timeout}, \texttt{score\_threshold}) and state operations (\texttt{wait=false}); Weaviate (13 of 30) in idempotent behaviors (delete nonexistent class). This mirrors the pattern in Section~\ref{sec:fp}: ambiguous defaults invite over-formalization, while explicit error conditions are uniformly over-formalized.

\paragraph{RQ2: false-positive suppression.}
On a controlled retrospective over 48 maintainer-adjudicated candidates (27 true-positive, 21 by-design or rejected; Milvus 32, Qdrant 16), the dev-reviewer (GLM-5.2 backbone, 3-run any-confirmed ensemble) reaches 65\% accuracy, 67\% precision (Wilson 95\% CI $[49\%, 81\%]$), and 74\% recall, against a single-LLM baseline (no source anchor) of 48\%/56\%/37\%; the source-grounded contract anchor drives the recall gain ($37\%\to74\%$). Single runs vary widely: across five independent runs, recall ranges $15$--$78\%$ (accuracy $44$--$65\%$, precision $50$--$73\%$, Figure~\ref{fig:perrun}), because some runs are conservative and confirm few candidates. We report the any-confirmed (union) ensemble as the operating point: the dev-reviewer is a falsifier, so a candidate that survives any independent falsification is more likely a true defect, and under-confirmation is costlier than forwarding a false positive for human triage. Table~\ref{tab:opr} reports four operating points. Among those that keep precision at least 60\%, the 3-run union has the highest recall; the 5-run union reaches higher recall (85\%) but lower precision (62\%) and lower accuracy (62\% vs.\ 65\%), and majority voting collapses recall to 26\%. We select the 3-run union as the headline because it sits at the knee of the precision-recall trade-off at modest reproducibility cost. We flag it as a post-hoc operating point justified by falsifier semantics, not a pre-registered rule, and the Wilson CIs above do not account for this selection. A Bonferroni correction across the four operating points (at $\alpha=0.05/4$) would widen the 3-run precision CI to roughly $[44\%, 84\%]$ and the recall CI to roughly $[51\%, 89\%]$, which does not change the qualitative claim that source grounding lifts recall above the 37\% baseline. A bootstrap resampling validation (2000 resamples of the 48-candidate set) gives precision 95\% CI $[53\%, 83\%]$ and recall $[71\%, 96\%]$, supporting that the operating point is not an artifact of the specific candidate sample.

A three-condition ablation on a 12-FP/4-TP control (Milvus v2.6.19, blind) isolates the dev-reviewer's two anchors (Table~\ref{tab:ablation}). Source alone suppresses 9/12 false positives (75\%), the threat-model anchor alone 6/12 (50\%, unstable on state and concurrency FPs), and their union 11/12 (91\%), each retaining all 4 true positives. The source-grounded anchor is the dominant contributor, and the threat-model anchor adds coverage on by-design patterns that source grounding alone reads as implementation choices. The precision gain from the single-LLM baseline (56\%) to the dev-reviewer (67\%), together with this ablation's 75\% false-positive suppression, directly measures the self-preference reduction~\cite{panickssery24,wataoka24}: the same-family judge agent over-confirms its own extracted claims, and the source anchor is what breaks that over-confirmation.

To isolate source grounding's contribution on the full 48-candidate retrospective, we ran the dev-reviewer with Step 3.5 (source grounding) disabled (single run, since this configuration is deterministic). Without source access, recall drops from 74\% (3-run any-confirmed, the headline) to 19\%, and precision from 67\% to 56\%. The effect is vendor-specific: on Milvus, recall collapses from 80\% to 5\% (1 of 20 true positives), because parameter validation logic lives in the source rather than the contract or response; on Qdrant, recall is roughly unchanged (57\%), because Qdrant's HTTP responses directly expose accept/reject decisions that the contract already encodes. Source grounding is the dominant contributor to recall, and its value concentrates where the contract under-specifies what the implementation does. Combined with the 12-FP/4-TP source-alone ablation (Table~\ref{tab:ablation}, where source alone suppresses 75\% of false positives), these two controls triangulate source grounding's contribution: disabling it collapses recall from 74\% to 19\%, and enabling it alone accounts for most of the false-positive suppression.

\paragraph{RQ3: comparison with VDBFuzz.}
We ran a bidirectional reachability probe between TestVDB and VDBFuzz~\cite{vdbfuzz26} on Qdrant (Table~\ref{tab:versions}). The systematic direction is VDBFuzz against TestVDB's pinned version: on Qdrant v1.18.2, where all 14 of TestVDB's Qdrant true positives are live, VDBFuzz (default configuration) ran over 26{,}000 mutated requests---the crash baseline on v1.18.2---and reached 0 of them. This is structural rather than a budget artifact: the 14 are silent accepts that return HTTP 200, and a crash oracle cannot detect a non-crashing accept by construction. The two Qdrant crashes VDBFuzz reports in its own case study are also fixed in v1.18.2, so the run cleanly separates the two oracles' reach on this version. On the older Qdrant v1.4.0, where VDBFuzz's integer-overflow crash on a vector \texttt{size} of $2^{63}$ is still live, TestVDB's boundary probe reaches it as a documentation-implementation violation: the OpenAPI declares \texttt{size}~$\geq 1$ with no maximum, so the value is documented-valid yet the implementation panics. On Qdrant v1.18.0, where TestVDB's acknowledged empty-vector defect (\#9045, \texttt{wait=false} silently accepts a zero-length vector) is live, VDBFuzz's template suite reports no failure: every points-upsert template uses \texttt{wait=true} (the path that correctly rejects) and does not probe \texttt{wait=false}. We read the reverse direction as a limitation of VDBFuzz's current templates and input coverage, not a property of crash oracles as a class. The two controlled cases below are $n{=}1$ each and isolate the mechanism on crash-class defects; the systematic direction above (26{,}000 requests, 0 of 14 silent-accept true positives reached) is the generalizable one.

The \#9045 root cause shows why the residual survives crash-focused patching: vector validation runs only under a \texttt{debug\_assert} that release builds skip, so \texttt{wait=false} accepts a zero-length vector while \texttt{wait=true} rejects it. The resulting panic (\#7967) survived three crash-fix iterations across v1.16.3--v1.18.0 until an API-level check independent of \texttt{wait} resolved it; a crash oracle would flag the panic once triggered, but the silent-accept residual on \texttt{wait=false} stays out of reach.

\paragraph{Threats to validity.}
\emph{Internal validity.} Single-run recall varies widely (15--78\%) because the LLM judge agent is high-variance; the any-confirmed union ensemble is the operating point we match to this variance, since majority voting collapses recall when conservative runs dominate the vote. The operating point is post-hoc, however, and the Wilson CIs in Table~\ref{tab:opr} do not account for selection across the four operating points. The 48-candidate retrospective is maintainer-adjudicated but non-random, and we did not pre-register the candidate set; a capture-recapture or unbiased defect-sample estimation is future work.

\emph{External validity.} Generalization to Weaviate is yield-only; the controlled retrospective covers Milvus and Qdrant. Result correctness of vector search (ANN recall, ranking) is out of scope. Transfer to documentation regimes beyond VDBMSs (REST APIs without OpenAPI, configuration validation, policy-as-code) is claimed on structural grounds only and is not empirically tested; even one non-VDBMS case study would strengthen the claim.

\emph{Construct validity.} All dev-reviewer results use a single LLM family (GLM-5.2). A full independent cross-model re-run on all 48 candidates (DeepSeek, Qwen-3.8-Max, and LongCat-2.0, each running the complete SOP) shows the verdict is family-specific ($\kappa = 0.14$ DeepSeek, $\kappa = 0.37$ Qwen, $\kappa = 0.51$ LongCat vs.\ GLM single-run), so we cannot claim cross-family robustness. We do not estimate recall because no public ground-truth defect catalog for VDBMSs exists. The implementation-as-correct assumption (Section~\ref{sec:disc}) bounds the approach: an implementation bug can wrongly falsify a clause whose documentation is right.

\section{Related Work}
\label{sec:related}

\paragraph{VDBMS testing.}
VDBFuzz~\cite{vdbfuzz26} is the first dedicated VDBMS fuzzer and uses crash as its oracle. Its template-based input mutation and crash detection reach exactly the crash-class subset that documentation-implementation defects, which silently accept rather than crash, escape; the bidirectional probe in Section~\ref{sec:eval} makes this complementarity concrete. The roadmap~\cite{roadmap25} sets the agenda we build on, identifying oracle definition as a key challenge for VDBMS testing and flagging differential testing as hard in this setting. The empirical bug study~\cite{bugstudy25} provides the taxonomy that motivates our focus on logical bugs, attributing more than half of VDBMS defects to functional failures rather than crashes.

\paragraph{REST-API oracle generation.}
A recent line derives test oracles for REST APIs from structured sources: AGORA+~\cite{agoraplus25} from execution traces, SATORI~\cite{satori25} from OpenAPI specifications, and MASTOR~\cite{mastor26} from source code. AGORA+ infers invariants from observed traffic and so cannot reach inputs the traffic did not exercise. SATORI reads OpenAPI schema elements (type, format, minimum, maximum) and stays in a regime where the constraints are explicit. MASTOR, the closest to this work, reads source to generate oracles that encode implemented behavior and so cannot detect a gap between documentation and code; TestVDB reads source as a falsifier of documentation-derived claims and targets exactly that gap. All three operate in a low-ambiguity regime where the LLM transcribes explicit constraints rather than interprets ambiguous documentation. A concrete boundary: SATORI's extraction assumes every relevant constraint has a corresponding OpenAPI field (\texttt{type}, \texttt{format}, \texttt{minimum}, \texttt{maximum}); VDBMS documentation carries these constraints in prose with no schema field to anchor on, so SATORI's extraction step has no input to work from.

\paragraph{LLM-as-judge reliability.}
Self-preference bias, in which an LLM evaluator favors its own family's outputs, is established for general text evaluation~\cite{panickssery24,wataoka24}. Panickssery et al. show that self-recognition correlates with self-preference across model families, and we observe the analogous bias in the test-oracle pipeline, where the same family extracts a claim and later judges conformance. A separate reliability axis is intra-judge self-inconsistency: Haldar et al.~\cite{haldar25} show that a single LLM judge agent's ratings on the same input vary across runs, a sampling-noise phenomenon in the judgment step. Our false-positive problem intersects both, with hallucination at extraction~\cite{ji23hall} added: an LLM may stably produce a wrong claim across runs and families when the documentation is ambiguous. Source-grounded falsification mitigates all three by moving the ground truth from the LLM to the implementation.

\paragraph{Documentation-derived oracles.}
Toradocu~\cite{toradocu16} pioneered NL-documentation oracle extraction (Javadoc \texttt{@throws} via NLP), with acknowledged false positives. Doc2OracLL~\cite{doc2oracll25} extended this to LLMs; AugmenTest~\cite{augmentest25} infers oracles from available documentation; ChatAssert~\cite{chatassert24} repairs false positives via compilation/execution feedback; Testora~\cite{testora26} uses PR descriptions as a regression oracle ($\sim$55\% precision). All treat the LLM as the final semantic arbiter, verifying through runtime behavior; TestVDB instead falsifies against implementation source, targeting the ambiguous-prose regime Javadoc and OpenAPI extraction do not enter.

\section{Discussion and Limitations}
\label{sec:disc}

The setting is not specific to VDBMSs in principle, though our evaluation is VDBMS-only. Systems whose documentation is natural-language prose rather than a structured specification, such as REST APIs without OpenAPI coverage, configuration validation, and policy-as-code checks, enter the same regime. We claim transferability only to structurally similar documentation regimes, and only as a preliminary portability probe rather than a generalization result; to probe it, we ran the TestVDB pipeline on Apache CouchDB~3.4.3, a mature non-VDBMS REST API whose documentation is natural-language prose. The contract-formalizer extracted five behavioral claims from CouchDB's \texttt{\_all\_docs} documentation (\texttt{limit}, \texttt{skip}, \texttt{descending}, \texttt{include\_docs}, \texttt{update\_seq}), and we probed each boundary value on a Docker-pinned instance. CouchDB rejected every clearly-invalid probe (negative \texttt{limit}, floating-point \texttt{limit}, non-boolean flags, invalid Mango query operators) with a 400 error; the only silent-accept was \texttt{limit=0}, which returns an empty result set rather than erroring, a graceful behavior rather than a defect. The pipeline ran end-to-end on a non-VDBMS target, probing method portability rather than defect detection (CouchDB's mature validation surfaced no silent-accept defect). A second probe on Elasticsearch~8.11.0 confirmed the pattern: Elasticsearch rejected every invalid probe (negative \texttt{size}, float \texttt{size}, invalid \texttt{timeout}) with a 400 error; the only silent-accept was \texttt{size=0}, which returns an empty hit set. Both mature non-VDBMS APIs validate more strictly than the three VDBMSs in our study, where 49 maintainer-acknowledged defects came from silent acceptance of invalid values. The extraction, probing, and falsification steps all port across non-VDBMS targets.

Beyond the threats in Section~\ref{sec:eval}, two limitations bound the approach. Source-grounded falsification requires source, so it does not transfer to closed-source VDBMSs, and it treats the implementation as correct, so an implementation bug can wrongly falsify a clause whose documentation is right. The 15 merged-PR fixes suggest the implementation-as-correct assumption holds often enough to be useful, without guarantee. We did not observe maintainer-rejected confirmed TPs where the documentation itself was wrong; such cases would surface as false negatives of the dev-reviewer and are most likely where a maintainer closes a confirmed candidate as wont-fix without a source-level explanation. We did not quantify this false-negative rate, which would require a ground-truth catalog of documentation errors that does not exist for VDBMSs.

Our 107-submission yield is biased by the tool's design toward documentation-implementation defects, so the proportion we observe is not an estimate of the distribution in VDBMSs at large. A full-space estimation with capture-recapture or an unbiased defect sample is future work.

\section{Conclusion}
\label{sec:concl}

We target documentation-implementation defects in Vector Database Management Systems, where a VDBMS silently accepts inputs that violate its API documentation. Because the documented boundary is natural-language prose, current instantiations of deterministic oracles miss these accept/reject decisions, leaving an LLM as the practical oracle. The LLM introduces two false-positive failure modes, hallucination in claim extraction and self-preference in judgment, that multi-perspective judging cannot resolve. Our dev-reviewer agent reads implementation source as an independent falsifier and breaks both modes. TestVDB surfaced 107 candidate issues across three VDBMSs with 49 maintainer-acknowledged true-positive defects (15 merged-PR-fixed), reaches 67\% precision and 74\% recall on a controlled retrospective against 37\% recall without source grounding, and a bidirectional probe against VDBFuzz explores complementary coverage. The boundary we draw, between problems where structured-source extraction suffices and those where natural-language documentation forces LLM interpretation, marks where an LLM-derived oracle needs an independent falsifier.
