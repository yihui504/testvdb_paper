On the Faults Found in REST APIs by Automated Test Generation
Bogdan Marculescu, Man Zhang, Andrea Arcuri
ACM Transactions on Software Engineering and Methodology (TOSEM),
  Vol. 31, Issue 3, Article No. 41, Pages 1-43
Published: 07 March 2022   DOI: 10.1145/3491038
Downloaded as text from ACM DL (free HTML full text).

================================================================
Abstract
================================================================
RESTful web services are often used for building a wide variety of enterprise applications. The diversity and increased number of applications using RESTful APIs means that increasing amounts of resources are spent developing and testing these systems. Automation in test data generation provides a useful way of generating test data in a fast and efficient manner. However, automated test generation often results in large test suites that are hard to evaluate and investigate manually.

This article proposes a taxonomy of the faults we have found using search-based software testing techniques applied on RESTful APIs. The taxonomy is a first step in understanding, analyzing, and ultimately fixing software faults in web services and enterprise applications. We propose to apply a density-based clustering algorithm to the test cases evolved during the search to allow a better separation between different groups of faults. This is needed to enable engineers to highlight and focus on the most serious faults.

Tests were automatically generated for a set of eight case studies, seven open-source and one industrial. The test cases generated during the search are clustered based on the reported last executed line and based on the error messages returned, when such error messages were available. The tests were manually evaluated to determine their root causes and to obtain additional information.

The article presents a taxonomy of the faults found based on the manual analysis of 415 faults in the eight case studies and proposes a method to support the classification using clustering of the resulting test cases.

================================================================
1 Introduction
================================================================
The Representational State Transfer (REST) is an architectural style for distributed hypermedia systems. REST is an abstraction that ignores details of implementation and focuses on roles of components, constraints upon the interactions between components, and their interpretation of the data. This allows a degree of flexibility that has led to the widespread use of REST to provide web services.

The flexibility that has enabled the widespread use of RESTful web services, however, also makes testing such systems more difficult. While some constraints are defined as part of REST, most of the business logic is up to individual developers. Moreover, REST allows web services to call upon other web services, further improving their usefulness and flexibility, but complicating testing.

Automation provides a useful way of generating large amounts of test data in a fast and efficient manner. In particular, search-based techniques have been applied to an increasing extent to the problem of software testing. However, many of the faults found as a result of these efforts may not be critical. It is important to provide engineers with an overview of the different failure types that automated systems have revealed, and the tools to identify and prioritize the more important of those faults.

In this article, we propose a taxonomy for software faults found by automatically generated tests in RESTful web services. This was based on manual analysis of 415 detected faults. In addition, we propose a method to automatically support such a classification by clustering test cases based on the similarities between their error messages.

The clustering of test cases is implemented as an extension of EvoMaster, an open-source test case generation tool that supports both black-box and white-box testing. EvoMaster uses the Many Independent Objectives algorithm (MIO) to generate test cases. Lines of code and potential faults are labeled as separate objectives by MIO, and tests are generated to maximize the number of objectives covered by the test suite. EvoMaster is primarily focused on RESTful APIs. It generates and runs HTTP calls with generated input data to maximize code coverage and fault detection.

================================================================
2 Background
================================================================
The Hypertext Transfer Protocol (HTTP) is a protocol that defines a set of rules for data communication over a network. HTTP actions are defined by HTTP verbs (POST, PUT, GET, DELETE) for CRUD operations. The server returns a response with a status code:
- 1xx: request received, continuing process
- 2xx: request successfully carried out
- 3xx: additional actions required (redirection)
- 4xx: client error (request contains errors or cannot be performed)
- 5xx: server error (apparently valid request that server could not complete; considered a fault in the server)

Representational State Transfer (REST) is an architectural style on top of HTTP. REST is an architectural style rather than a protocol — the guidelines are proposed and recommended but not enforced. This leads to the possibility of non-conforming APIs being developed and used.

OpenAPI is a programming language-agnostic interface description for REST APIs, the purpose of which is to allow machine and human clients to understand the capabilities of a web service without requiring access to its source code, additional documentation, or other data sources. Earlier versions of OpenAPI (pre-3.0.0) were also known as Swagger.

EvoMaster is an automated tool that uses evolutionary algorithms and dynamic program analysis to automatically generate system level test cases for RESTful APIs. Potential faults considered for fault finding are based on HTTP responses with 500 status codes and discrepancies between the API responses and what is expected based on the OpenAPI schemas.

================================================================
3 Related Work
================================================================
The popularity of RESTful APIs has led to a significant amount of frameworks that support development and deployment, and more recently, in research on testing such systems. Efforts are mostly focused on black-box automated test case generation, based on the OpenAPI schema definitions.

- QuickREST (Karlsson et al.): uses the OpenAPI specification to derive properties of inputs and then uses the specification as an oracle. The authors describe the faults as "input validation bugs." APIs are often under-specified — OpenAPI restrictions are looser than valid inputs of the underlying API.
- RESTTESTGEN (Viglianisi et al.): uses OpenAPI + runtime information to identify dependencies between resources and operations, expressed as an Operation Dependency Graph.
- Ed-douibi: using OpenAPI to derive models of the RESTful API for test generation.
- Atlidakis et al. (RESTler): using OpenAPI as a basis for fuzzing RESTful APIs.

Two major knowledge gaps emerge:
1. It is not clear what types of faults can be found with automated testing (existing studies rely on user session data or seeded faults).
2. The absence of a general means of supporting developers in classifying test data, especially from novel sources.

================================================================
4 Method
================================================================
Research Questions:
(1) What faults are actually found in RESTful systems by automated testing?
(2) What types of faults are more common across the SUTs being studied?
(3) How can automated support for the classification of faults be provided?
  (a) To what extent is automated support for fault classification useful in distinguishing between different faults?
  (b) To what extent is a subset of test cases derived from sampling each automatically identified category representative of the categories of faults found in practice?

A "potential fault" is defined as an HTTP call that results in a 500 status code. Additionally, an HTTP call that results in a code not supported by the OpenAPI specification is also considered erroneous (e.g., returning a 400 when such code is not explicitly stated in the schema). Codes in the 5xx family are technically unexpected; the "Expectation Faults" category only includes responses with status codes not supported by the OpenAPI specification but not 500.

5 Taxonomy
================================================================
The taxonomy was developed using a facet-based classification structure (per Usman et al.). Faults fall under four major categories:

(A) Configuration and Execution Faults — faults related to setup of frameworks, testing scaffolding, or external systems.
  - Framework Misconfiguration: e.g., framework rejects strings containing ";" as malicious → 500 instead of 4xx. Manifests as Rejected Calls and Timeouts.
  - Inconsistent Behavior: Multiple Execution inconsistencies; Fail by Succeeding (unexpected 2xx); Unexpected 500; Try-Catch (timeouts wrapped).

(B) Schema Conflicts — mismatches between the OpenAPI schema and the underlying SUT.
  - Format: mismatch in acceptable formats (e.g., date regex allows "42" as month).
  - Type: type not clearly specified (e.g., JSON body expected numerical but schema says string).
  - Missing or Null Values: SUT expects input not mandatory in schema.
  - Negative: input expected non-negative (e.g., offset) but no schema restriction.
  - Pre-approved List: input must be from a list (e.g., 247 country names) not in schema.
  - Invalid Combination: multi-parameter constraints (not supported by OpenAPI).
  - Semantic: semantic meaning not captured (e.g., invalid but well-formed dates).
  - Unsupported Code: HTTP response codes not supported by OpenAPI.

(C) Data Related Faults — initialization, data consistency, database injection.
  - DB Operations: DB.OptimisticLock, DB.Key, Constraint Violation Exception.
  - DB Injection: inconsistent data injected directly into DB.
  - Seeding: incomplete seeded data causing NullPointerException.

(D) Faults in the Business Logic — general unwanted behaviors / crashes in business logic.
  - Hardcoded: hardcoded values invalid under testing (e.g., sublist of 10).
  - Not Found: improper handling of missing resources (should be 404, crashes with 500).
  - Unsafe Cast: ClassCastException from unsafe casts.

The most prevalent fault is "Not Found" (mishandling of requests on non-existent resources). "Schema Conflicts" (mismatches between OpenAPI and SUT) are also frequent, present in all but two (artificial) systems.

Conclusion: mishandling resources that are not found and mismatches between OpenAPI specifications and the RESTful APIs they describe are common types of faults.

6 Clustering — Results and Interpretation
================================================================
The clustering uses DBSCAN (Density Based Spatial Clustering of Applications with Noise). DBSCAN does not require the number of clusters to be defined in advance — useful for stochastic search output. Parameters: epsilon (neighborhood) and minPts (minimum points per cluster).

Two distance metrics:
1. Textual similarity between error messages (Levenshtein-based, normalized by length).
   - Downside: generic error messages give no differentiation; security wrapping obscures messages.
2. Textual similarity of the path of the last executed statement.
   - Downside: fault location may be imprecise; identical code on different lines; SUT structure misleading.

Results (proxyprint case study): Separation is high (most fault classes exist in one cluster), but Cohesion is low (each cluster contains more than one class of fault). Clustering does separate different fault classes but clusters are not cohesive — a cluster is "a bin where several classes of fault, which manifest in similar ways or have similarity in terms of error message, are grouped."

Initial results: clustering can separate between different types of faults and has the potential to provide test engineers with automated support when classifying large numbers of test cases.

================================================================
7 Discussion
================================================================
The taxonomy is meant to be a flexible and robust description of faults encountered in practice, not only in the case studies. The current EvoMaster oracle: any 500 response = possible fault (crash oracle). Most common 500 fault = mismatch between OpenAPI schema (used to generate inputs) and SUT, i.e., mishandling invalid inputs. Mismatches between OpenAPI schemas and SUTs are interesting because most OpenAPIs in the case studies are automatically generated — improvements can be made in auto-derivation tools.

The large number of "Unsupported Code" and "Schema Conflict" faults indicates current OpenAPI schemas are under-specified. As automated testing tools improve, this could generate large amounts of false positives.

================================================================
8 Threats to Validity
================================================================
- Conclusion validity: search randomness; 10 runs per SUT; results not outliers.
- Construct validity: stopping criterion = number of HTTP calls (100,000).
- Internal validity: manual evaluation of 415 faults; analyzed by one author, checked by second; disagreements discussed until agreement.
- External validity: 8 diverse case studies (open-source artificial + real + industrial); taxonomy designed to be extensible to new fault classes.

================================================================
9 Conclusions
================================================================
A taxonomy of 415 faults found by EvoMaster in RESTful APIs is proposed. It describes diverse faults ranging from RESTful-specific framework misconfigurations and schema mismatches to generic software faults. Large numbers of Unsupported Code and Schema Conflict faults indicate current OpenAPI schemas are under-specified, which could generate false positives as automated testing becomes more widespread. An initial means of automatically classifying software faults based on error-message similarity (DBSCAN clustering) is proposed; clustering separates several categories when error messages are informative. EvoMaster is open-source at www.evomaster.org.

================================================================
Appendix: Failed clustering
================================================================
- scout-api: wraps all errors by default, removes all info except "code 500" → all faults in one cluster.
- feature-service: removes all text from error → no clustering possible.
- Last executed line: problematic because textual similarity misled by module structure.
