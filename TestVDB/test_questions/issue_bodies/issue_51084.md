# Issue #51084: [Bug]: REST API silently substitutes invalid `consistencyLevel` enum value with default instead of rejecting
# State: closed, Labels: ['kind/bug', 'triage/accepted']

### Is there an existing issue for this?

- [x] I have searched the existing issues

### Environment

```markdown
- Milvus version: **v2.6.19** (also reproduced on v2.6.17 image)
- Deployment mode: standalone (Docker Compose, official `milvusdb/milvus:v2.6.19`)
- MQ type: rocksmq (default for standalone)
- SDK version: N/A — reproduced via raw HTTP/REST (`curl` + Python `urllib`)
- OS: Windows 11 (Docker Desktop); Milvus container runs Linux
- CPU/Memory: host 8 vCPU / 16 GB; container default
- GPU: none
- Others: REST endpoint `POST /v2/vectordb/collections/create`
```

### Current Behavior


When creating a collection via the REST API with an **invalid `consistencyLevel` enum string** (e.g. `"Invalid"`), Milvus returns `200 OK` with `code: 0` (success) and **silently substitutes the default value `Bounded`**, rather than rejecting the request.

The client has no way to know their input was invalid — `describe` later returns `"Bounded"`, masking the typo/bug in the client.

```http
POST /v2/vectordb/collections/create
{"collectionName":"audit1","dimension":4,"metricType":"L2","idType":"Int64","autoID":true,"vectorFieldType":"FloatVector","consistencyLevel":"Invalid"}

HTTP/1.1 200 OK
{"code":0,"data":{}}

POST /v2/vectordb/collections/describe
{"collectionName":"audit1"}

HTTP/1.1 200 OK
{"code":0,"data":{ ..., "consistencyLevel":"Bounded", ...}}
```


### Expected Behavior


Return a non-success response (HTTP 4xx, or HTTP 200 with `code != 0`) with a clear error message such as:

> `invalid consistencyLevel: "Invalid"; must be one of [Strong, Session, Bounded, Eventually]`

This is important because:
1. A client typo (`"Bouned"`, `"Invalid"`, etc.) currently produces a silently-wrong consistency level.
2. Users who require `Strong` consistency but typo the value get `Bounded` in production without any error, leading to stale reads that violate their correctness assumptions.
3. Other enum fields (e.g. `idType`, `metricType` with non-empty invalid strings) **do** get rejected — the behavior is inconsistent across enum fields.

### Steps To Reproduce

```markdown
1. Start Milvus v2.6.19 (standalone, Docker):
   
   docker run -d --name milvus-standalone -p 19530:19530 milvusdb/milvus:v2.6.19 standalone
   
2. Create a collection with an invalid `consistencyLevel`:
   
   curl -s -X POST http://localhost:19530/v2/vectordb/collections/create \
     -H "Content-Type: application/json" \
     -d '{"collectionName":"audit1","dimension":4,"metricType":"L2","idType":"Int64","autoID":true,"vectorFieldType":"FloatVector","consistencyLevel":"Invalid"}'
   # -> {"code":0,"data":{}}    <- should have been rejected
   
3. Describe the collection and observe the substituted value:
   
   curl -s -X POST http://localhost:19530/v2/vectordb/collections/describe \
     -H "Content-Type: application/json" \
     -d '{"collectionName":"audit1"}'
   # -> {..., "consistencyLevel":"Bounded", ...}    <- silently replaced
   
4. (Contrast) Other enum fields correctly reject invalid values, e.g.:
   
   curl -s -X POST http://localhost:19530/v2/vectordb/collections/create \
     -H "Content-Type: application/json" \
     -d '{"collectionName":"x","dimension":4,"metricType":"L2","idType":"InvalidType","autoID":true,"vectorFieldType":"FloatVector"}'
   # -> {"code":1100,"message":"idType can only be [Int64, VarChar], default: Int64: invalid parameter..."}
```

### Milvus Log


REST layer only — no error/warning is emitted server-side because the request is treated as successful. Standalone container log around the create call shows a normal `CreateCollection` trace with no validation failure.

Relevant source constant (`client/entity/collection.go`):
```go
const DefaultConsistencyLevel ConsistencyLevel = ClBounded
```

`DefaultConsistencyLevel = ClBounded` defines the **default** value (used when the field is omitted), but does **not** imply that arbitrary invalid strings should fall back to this default. The REST handler appears to apply the default substitution to any value that fails to parse as a known enum, rather than rejecting it.


### Anything else?


- Impact severity is low (no data loss / no crash), but it is a real **validation gap** that can mask client bugs in production. A user intending `Strong` consistency who mistypes the value gets silent `Bounded`, which can produce stale-read anomalies that are very hard to debug.
- The same "silent default substitution" pattern affects `vectorFieldType` (see companion issue). Suggest a unified validation pass for all enum-typed fields in the REST `CreateCollection` handler.
- Not a security issue (no injection / no privilege escalation), purely a robustness/validation concern.
