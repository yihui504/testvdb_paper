# Issue #49844: [Bug]: REST API v2 query accepts null/missing filter and silently returns all entities
# State: open, Labels: ['kind/bug', 'triage/accepted']

## Is your feature request related to a problem? Please describe.

REST API v2 `/v2/vectordb/entities/query` accepts `null` or **missing** `filter` parameter and silently returns all entities in the collection, despite the official documentation marking `filter` as a **required** parameter.

This behavior creates a security risk: a client-side bug that omits the `filter` field (e.g., `filter=None` in Python, which serializes to JSON `null`) will unintentionally leak the entire collection's data without any error or warning.

## Describe the problem you're trying to solve

### Current Behavior

The `filter` parameter is documented as **required** in the REST API v2 specification:
- https://milvus.io/api-reference/restful/v2.4.x/v2/Vector%20(v2)/Query.md states: `filter (string, required)`
- The PyMilvus SDK documentation also marks `filter` as `[REQUIRED]`, noting: *"You can set this parameter to an empty string to skip scalar filtering."*

However, the REST API v2 implementation treats `null`/missing `filter` as "no filter" and returns all entities:

**Case 1: `filter` is `null` (Python `None` → JSON `null`)**
```bash
curl -s 'http://localhost:19530/v2/vectordb/entities/query' \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer root:Milvus' \
  -d '{"collectionName":"test_coll","filter":null,"outputFields":["id"]}'
```
Response: `{"code":0,"data":[{"id":1},{"id":2}]}` — returns all rows ❌

**Case 2: `filter` field is completely omitted**
```bash
curl -s 'http://localhost:19530/v2/vectordb/entities/query' \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer root:Milvus' \
  -d '{"collectionName":"test_coll","outputFields":["id"]}'
```
Response: `{"code":0,"data":[{"id":1},{"id":2}]}` — returns all rows ❌

**Case 3: `filter` is an empty string (explicit "skip filtering")**
```bash
curl -s 'http://localhost:19530/v2/vectordb/entities/query' \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer root:Milvus' \
  -d '{"collectionName":"test_coll","filter":"","outputFields":["id"]}'
```
Response: `{"code":0,"data":[{"id":1},{"id":2}]}` — returns all rows ✅ (this is the documented way)

All three cases produce identical results, but only Case 3 is the documented mechanism for skipping scalar filtering.

### Expected Behavior

When `filter` is `null` or missing, the API should return an error since `filter` is documented as required:

```json
{"code":65535,"message":"filter is required for query operation. Use an empty string (\"\") to query all entities."}
```

This is consistent with how other REST API v2 endpoints validate required parameters. For example, `search` with `limit=0` correctly returns:

```json
{"code":65535,"message":"topk [0] is invalid, it should be in range [1, 16384]"}
```

### Security Implications

In a multi-tenant application, a client-side bug that fails to set the `filter` expression could unintentionally expose all tenants' data:

```python
# Developer intent: query only the current tenant's data
filter_expr = f"tenant_id == {current_tenant}"
# But a code path forgets to set filter_expr, leaving it as None
response = requests.post(url, json={"collectionName": coll, "filter": None, ...})
# Result: ALL tenants' data is returned — silent data leak!
```

If the API returned an error for `null`/missing `filter`, this bug would be caught immediately at development time instead of becoming a production security incident.

## Describe the solution you'd like

Reject `null` and missing `filter` values in the REST API v2 query endpoint, returning an error with a clear message directing users to use an empty string `""` if they intentionally want to query all entities.

This aligns with:
1. The official documentation marking `filter` as required
2. The PyMilvus SDK's documented mechanism of using an empty string to skip filtering
3. The principle of explicit intent: returning all data should require an explicit action (empty string), not happen implicitly through a missing parameter

## Describe alternatives you've considered

1. **Keep current behavior but add documentation**: Document that `null`/missing `filter` returns all data. This is risky because it legitimizes a security-sensitive implicit behavior.
2. **Add a warning in the response**: Return the data but include a `"warning"` field. This is fragile — clients may not check warnings.

Neither alternative addresses the core issue: the API should enforce its own documented contract.
