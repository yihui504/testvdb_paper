### Current Behavior

`POST /v2/vectordb/users/create` has two distinct validation failures:

**1. HTTP status code always 200**: Password validation failures return HTTP 200 instead of HTTP 4xx, making programmatic error detection impossible.

**2. Password complexity not enforced**: The official documentation requires passwords to contain 3 of 4 character types (uppercase, lowercase, numbers, special characters), but the API only enforces length (6-256 characters). A password of all lowercase letters like `"abcdefgh"` is accepted.

#### Verified test results (with valid usernames):

| Password | Length | HTTP | code | Message | Bug? |
|----------|--------|------|------|---------|------|
| `""` (empty) | 0 | **200** | 1802 | "Field validation for 'Password' failed on the 'required' tag" | HTTP should be 4xx |
| `"a"` | 1 | **200** | 1100 | "1 out of range 6 <= value <= 256" | HTTP should be 4xx |
| `"abcdefgh"` | 8 | **200** | 200 | User created | **Complexity not enforced** |
| `"ValidP@ss1"` | 9 | 200 | 200 | User created | Expected ✅ |

#### Validation order note:
When both username and password are invalid, the error returned depends on which validation triggers first:
- Invalid username + valid password → username validation error (code=1100)
- Invalid username + empty password → password required error (code=1802)

This inconsistent validation order means users cannot predict which error they'll receive.

```bash
# Password complexity not enforced — HTTP 200 + code=200!
curl -s -X POST 'http://localhost:19530/v2/vectordb/users/create' \
  -H 'Content-Type: application/json' \
  -d '{"userName":"testuser1","password":"abcdefgh"}'
# HTTP 200 / {"code":200,"data":{}}   ← All-lowercase password accepted!

# Empty password — HTTP 200 (should be 400)
curl -s -X POST 'http://localhost:19530/v2/vectordb/users/create' \
  -H 'Content-Type: application/json' \
  -d '{"userName":"testuser2","password":""}'
# HTTP 200 / {"code":1802,"message":"...Password...required..."}

# Short password — HTTP 200 (should be 400)
curl -s -X POST 'http://localhost:19530/v2/vectordb/users/create' \
  -H 'Content-Type: application/json' \
  -d '{"userName":"testuser3","password":"a"}'
# HTTP 200 / {"code":1100,"message":"1 out of range 6 <= value <= 256"}
```


### Expected Behavior


1. **HTTP status code**: Password validation failures should return HTTP 400, not HTTP 200
2. **Password complexity**: Per the official documentation, passwords must contain at least 3 of the following 4 character types: uppercase, lowercase, numbers, special characters. The API should enforce this.

```
HTTP 400 / {"code": 400, "message": "password must be 8-64 characters with 3 of 4 types (uppercase, lowercase, numbers, special characters)"}
```

### Official Documentation Reference

- **REST API v2.6.x Create User**: https://milvus.io/api-reference/restful/v2.6.x/v2/User%20(v2)/Create.md
  - Documents password: "The password must include at least three of the following character types: uppercase letters, lowercase letters, numbers, and special characters."
- **Milvus v2.6.x Users and Roles**: https://milvus.io/docs/v2.6.x/users_and_roles.md
  - States: "Password: Must be 8-64 characters long and must include three of the following: uppercase letters, lowercase letters, numbers, and special characters."
- **Note**: The API error message says "6 <= value <= 256" which contradicts the documentation's "8-64 characters" requirement. Both the length range and complexity requirements are misaligned between documentation and implementation.

### Impact

- **Security**: Password complexity is not enforced, allowing weak passwords that violate documented requirements
- **Documentation vs implementation mismatch**: Docs say 8-64 chars + 3 types, API enforces 6-256 chars + 0 types
- **SDK confusion**: Client libraries that check HTTP status codes will consider validation failures as success
- **Authentication integrity**: The Milvus RBAC system's security depends on proper password validation

- Discovered through automated boundary value testing on v2.6.17
- The Milvus user system is critical for RBAC — password validation issues undermine the entire authentication model
