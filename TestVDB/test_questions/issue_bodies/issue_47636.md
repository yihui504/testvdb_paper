### Current Behavior

Providing an invalid token (e.g., `===`) in a boolean expression causes the underlying ANTLR lexer to leak its error message directly to the SDK, while returning `code=0`. This bypasses standard error handling and exposes internal parser details.
### Error Message
```
<MilvusException: (code=0, message=failed to create query plan: cannot parse expression: tag === 'x', error: line 1:6 token recognition error at: '= ')>
```

### Expected Behavior

The API should return `Code 1` (IllegalArgument) with a clean error message indicating an invalid expression. The error message should not expose internal implementation details (e.g., ANTLR lexer errors).

### Contract Violation

1. **Error Code Violation**: According to the [Milvus Java SDK R.Status definition](https://milvus.io/api-reference/java/v2.3.x/v1/Misc/RT.md), `Code 0` is strictly defined as **Success (Operation succeeded)**. Returning `code=0` for a failed operation violates this API contract.

2. **API Contract Violation**: According to the [Highlevel API search() specification](https://milvus.io/api-reference/java/v2.3.x/v1/HighlevelAPI/search.md), the API should only return `R.Status.Success` when the operation is successful. Invalid expressions should trigger `IllegalArgument` errors.

3. **Security Risk**: The error message directly exposes the underlying ANTLR parser implementation (`token recognition error`), which violates the principle of least exposure and could potentially be exploited.

### Code Reference

The issue is likely in the [planparserv2](https://github.com/milvus-io/milvus/tree/master/internal/parser/planparserv2) component, where ANTLR exceptions are captured but only the `Reason` is filled without properly setting `commonpb.ErrorCode_IllegalArgument`.

### Impact

- Automated error handling fails because `code=0` is interpreted as success
- Internal implementation details are exposed to clients
- Security risk from exposing parser internals
- Client applications cannot properly handle syntax errors

### Severity

**P1 (High)** - This is an API consistency and security issue that affects error handling and exposes internal implementation details.

### Suggested Fix

In `planparserv2`, intercept parsing exceptions and map them to `IllegalArgument` status code instead of `Success`. Sanitize error messages to remove internal implementation details.
