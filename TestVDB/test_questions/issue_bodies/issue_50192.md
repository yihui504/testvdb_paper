# Issue #50192: [Bug] Concurrent rename and create with same target name both succeed, causing state violation
# State: open, Labels: ['resolution/by-design']

## Bug: Concurrent rename and create with same target name both succeed, causing state violation

### Environment
- Milvus version: v2.6.16
- Deployment mode: Standalone (Docker)
- SDK: REST API v2

### Current Behavior
When a rename operation and a create operation target the same collection name concurrently, **both operations succeed** (return code 0). This results in a state violation where the system allows conflicting collection names to coexist.

### Expected Behavior
Only one of the operations should succeed. Either the rename succeeds and the create fails with a conflict error, or the create succeeds and the rename fails. The system should never allow two collections with the same name to exist.

### Steps To Reproduce
1. Create a source collection with a unique name
2. Insert some data into the source collection
3. Concurrently send a rename request to rename the source collection to a new name, and a create request to create a new collection with the same new name
4. Observe that both requests return success (code 0)

### Reproduction Script
```python
import requests
import json
import sys
import uuid
import time
import threading

BASE = "http://localhost:19530"
HEADERS = {"Authorization": "Bearer root:Milvus"}

collection_name = "test_rename_src_" + uuid.uuid4().hex[:8]
new_name = "test_rename_dst_" + uuid.uuid4().hex[:8]

# SETUP: Create source collection
payload = {
    "collectionName": collection_name,
    "schema": {
        "autoID": False,
        "enableDynamicField": True,
        "fields": [
            {"fieldName": "id", "dataType": "Int64", "isPrimary": True},
            {"fieldName": "vector", "dataType": "FloatVector", "elementTypeParams": {"dim": 4}},
            {"fieldName": "value", "dataType": "Int64"}
        ]
    },
    "indexParams": [
        {"fieldName": "vector", "metricType": "COSINE", "indexType": "AUTOINDEX"}
    ]
}
r = requests.post(f"{BASE}/v2/vectordb/collections/create", json=payload, headers=HEADERS)
print(f"Create source: {r.json()}")
time.sleep(0.5)

# Insert data
insert_payload = {
    "collectionName": collection_name,
    "data": [{"id": 1, "vector": [0.1, 0.2, 0.3, 0.4], "value": 100}]
}
r = requests.post(f"{BASE}/v2/vectordb/entities/insert", json=insert_payload, headers=HEADERS)
print(f"Insert: {r.json()}")
time.sleep(0.3)

# ACTION: Concurrently rename AND create with same target name
rename_results = []
create_results = []

def do_rename():
    r = requests.post(f"{BASE}/v2/vectordb/collections/rename",
                      json={"collectionName": collection_name, "newCollectionName": new_name},
                      headers=HEADERS)
    rename_results.append(r.json())
    print(f"Rename: {r.json()}")

def do_create_conflict():
    create_payload = {
        "collectionName": new_name,
        "schema": {
            "autoID": False,
            "enableDynamicField": True,
            "fields": [
                {"fieldName": "id", "dataType": "Int64", "isPrimary": True},
                {"fieldName": "vector", "dataType": "FloatVector", "elementTypeParams": {"dim": 4}},
                {"fieldName": "value", "dataType": "Int64"}
            ]
        },
        "indexParams": [{"fieldName": "vector", "metricType": "COSINE", "indexType": "AUTOINDEX"}]
    }
    r = requests.post(f"{BASE}/v2/vectordb/collections/create", json=create_payload, headers=HEADERS)
    create_results.append(r.json())
    print(f"Create conflict: {r.json()}")

t_rename = threading.Thread(target=do_rename)
t_create = threading.Thread(target=do_create_conflict)
t_rename.start()
t_create.start()
t_rename.join()
t_create.join()

time.sleep(1)

# VERIFY
rename_code = rename_results[0].get('code', -1) if rename_results else -1
create_code = create_results[0].get('code', -1) if create_results else -1

if rename_code == 0 and create_code == 0:
    print("BUG: Both rename and create succeeded - conflicting state!")
else:
    print("OK: At least one operation was rejected")
```

### Verification
This bug was reproduced in **4 independent sandbox runs** (initial + repro_1 + repro_2 + variant_1), all confirming the same behavior:
- Rename response: `{"code":0,"data":{}}`
- Create conflict response: `{"code":0,"data":{}}`
- Old collection name no longer exists
- New collection name exists but data state is ambiguous

### Root Cause
The rename and create operations lack distributed lock or transactional isolation when targeting the same collection name. The rename operation atomically changes the name of an existing collection, while the create operation checks for name uniqueness before creating. Without mutual exclusion, both can proceed simultaneously.

### Suggested Fix
1. Implement a distributed lock or transactional operation to serialize rename and create operations on the same collection name
2. Add a pre-check in the rename operation to verify the target name does not already exist
3. Return a conflict error (HTTP 409) when a rename or create operation detects a name collision
