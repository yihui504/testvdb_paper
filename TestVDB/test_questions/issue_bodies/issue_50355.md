### Current Behavior


Upsert operation does not work with `autoID=true` collections. When no primary key is provided (the correct usage for autoID), upsert fails across all SDKs. This contradicts the official v2.6.x documentation which explicitly states that upsert should auto-generate primary keys when autoID is enabled.

**Cross-SDK test results:**

| SDK | autoID | Provided PK? | Operation | Result | Error Message |
|-----|--------|-------------|-----------|--------|---------------|
| REST API v2 | true | ❌ | upsert | ❌ code=1100 | "upsert can not assign primary field data when auto id enabled id" |
| PyMilvus | true | ❌ | upsert | ❌ DataNotMatchException | "Insert missed an field `id`" |
| REST API v2 | true | ✅ | upsert | ❌ code=1804 | "set primary key but autoID == true" |
| PyMilvus | true | ✅ | upsert | ❌ MilvusException | "the number of fields is less than needed" |
| REST API v2 | false | ✅ | upsert | ✅ code=200 | — |
| PyMilvus | false | ✅ | upsert | ✅ upsert_count=1 | — |
| REST API v2 | true | ❌ | insert | ✅ code=200 | auto-generated ID |
| PyMilvus | true | ❌ | insert | ✅ insert_count=1 | auto-generated ID |

**Key observations:**

1. **Upsert is a dead end for autoID=true collections**: Providing PK → rejected (code=1804, correct); Not providing PK → also rejected (code=1100, bug). There is no valid input.
2. **Insert works correctly**: auto-generates primary keys as expected, proving the autoID mechanism itself is functional.
3. **Root cause is server-side (gRPC)**: Both SDKs fail, confirming this is not a REST API v2 specific issue. Milvus gRPC layer always requires a primary key for upsert, regardless of autoID setting.

**SDK error message quality:**

| Dimension | REST API v2 | PyMilvus |
|-----------|------------|----------|
| Accuracy | ❌ Misleading — "can not assign" implies user did something wrong | ✅ Accurate — "missed an field" correctly describes missing field |
| Actionability | ❌ No guidance on how to fix | ⚠️ Partial — knows field is missing, but doesn't explain upsert doesn't support autoID |
| Error origin | REST proxy layer (pre-gRPC) | gRPC server layer (data validation) |

REST API v2 returns a semantically inaccurate error message: "upsert can not assign primary field data when auto id enabled" — the user did NOT provide primary field data, yet the message implies they did.

**Documentation self-contradiction:**

The official v2.6.x [Upsert Entities](https://milvus.io/docs/v2.6.x/upsert-entities.md) page contains two contradictory statements:

1. **Override mode section** (promises autoID support):
   > "If the target collection has `autoid` enabled on its primary field, Milvus will generate a new primary key for the data carried in the request payload before inserting it."

2. **Limits & Restrictions section** (requires primary key):
   > "The `upsert` request must always include the primary keys of the target entities."

Statement #1 says upsert auto-generates PKs when autoID=true (no PK needed). Statement #2 says upsert must always include PKs. The implementation follows #2, but the override mode description follows #1.

Additionally, v2.6.x introduced `allow_insert_auto_id` property (see [Modify Collection](https://milvus.io/docs/v2.6.x/modify-collection.md)) that controls autoID behavior for **insert** operations only. No equivalent `allow_upsert_auto_id` property exists, further confirming upsert lacks autoID support at the implementation level.


### Expected Behavior

When `autoID=true` and no primary key is provided:

```json
// Current (BUG):
{"code": 1100, "message": "upsert can not assign primary field data when auto id enabled id"}

// Expected (per official documentation):
{"code": 200, "data": {"upsertCount": 1, "upsertIds": [466823717613999776]}}
```

Upsert should auto-generate the primary key when `autoID=true`, just like `insert` does.

### Steps To Reproduce

```markdown
import requests

BASE = "http://localhost:19530"
HEADERS = {"Content-Type": "application/json"}
name = "test_upsert_autoid"

# 1. Create collection with autoID=true
r = requests.post(f"{BASE}/v2/vectordb/collections/create", json={
    "collectionName": name, "dimension": 4, "metricType": "L2",
    "idType": "Int64", "autoID": True, "primaryFieldName": "uid"
}, headers=HEADERS)
print(f"Create: code={r.json()['code']}")

# 2. Upsert WITHOUT primary key — BUG: code=1100
r = requests.post(f"{BASE}/v2/vectordb/entities/upsert", json={
    "collectionName": name,
    "data": [{"vector": [1.0, 2.0, 3.0, 4.0], "color": "red"}]
}, headers=HEADERS)
print(f"Upsert (no PK): code={r.json()['code']}")  # Expected: 200, Actual: 1100

# 3. Insert WITHOUT primary key — Works fine!
r = requests.post(f"{BASE}/v2/vectordb/entities/insert", json={
    "collectionName": name,
    "data": [{"vector": [5.0, 6.0, 7.0, 8.0], "color": "blue"}]
}, headers=HEADERS)
print(f"Insert (no PK): code={r.json()['code']}")  # Actual: 200
```

### Anything else?


- **Documentation references:**
  - [Milvus v2.6.x Upsert Entities](https://milvus.io/docs/v2.6.x/upsert-entities.md) — Override mode section promises autoID support, Limits & Restrictions section requires primary keys
  - [Milvus v2.6.x Modify Collection](https://milvus.io/docs/v2.6.x/modify-collection.md) — Documents `allow_insert_auto_id` for insert only, no equivalent for upsert
  - [REST API v2.6.x Upsert](https://milvus.io/api-reference/restful/v2.6.x/v2/Vector%20(v2)/Upsert.md) — Does not mention autoID limitation
  - [REST API v2.6.x Create Collection](https://milvus.io/api-reference/restful/v2.6.x/v2/Collection%20(v2)/Create.md) — Documents `autoID` and `primaryFieldName` parameters
- **Third-party corroboration**: A Korean developer documented the same issue in February 2025 — [upsert는 auto_id를 모름](https://velog.io/@yoonene/Milvus-upsert%EB%8A%94-autoid%EB%A5%BC-%EB%AA%A8%EB%A6%84) — encountered identical `DataNotMatchException` and had to fall back to insert
- **Historical context**: Earlier Milvus versions (pre-2.3) explicitly required autoID=false for upsert. The v2.6.x documentation now states autoID is supported for upsert, but the server implementation has not been updated to match
- **Impact**: Upsert is completely broken for autoID=true collections — no valid input exists (providing PK is rejected, not providing PK is also rejected). Users must use `insert` instead. REST API v2 additionally returns a misleading error message
