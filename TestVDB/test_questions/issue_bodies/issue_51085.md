# Issue #51085: [Bug]: REST API silently substitutes invalid `vectorFieldType` enum value with default instead of rejecting
# State: closed, Labels: ['kind/bug', 'triage/accepted']

### Is there an existing issue for this?

- [x] I have searched the existing issues

### Environment

```markdown
- Milvus version: **v2.6.19** (also reproduced on v2.6.17 image)
- Deployment mode: standalone (Docker Compose, official `milvusdb/milvus:v2.6.19`)
- MQ type: rocksmq (default for standalone)
- SDK version: N/A — reproduced via raw HTTP/REST (`curl` + Python `urllib`)
- OS: Windows 11 (Docker Desktop); Milvus container runs Linux
- CPU/Memory: host 8 vCPU / 16 GB; container default
- GPU: none
- Others: REST endpoint `POST /v2/vectordb/collections/create`
```

### Current Behavior


When creating a collection via the REST API with an **invalid `vectorFieldType` enum string** (e.g. `"InvalidVectorType"`), Milvus returns `200 OK` with `code: 0` (success) and **silently substitutes the default `FloatVector`**, rather than rejecting the request.

The client has no way to know their input was invalid — the collection is created with a vector field of type `FloatVector`, masking the typo/bug in the client.

```http
POST /v2/vectordb/collections/create
{"collectionName":"audit5","dimension":4,"metricType":"L2","idType":"Int64","autoID":true,"vectorFieldType":"InvalidVectorType"}

HTTP/1.1 200 OK
{"code":0,"data":{}}

POST /v2/vectordb/collections/describe
{"collectionName":"audit5"}

HTTP/1.1 200 OK
{"code":0,"data":{"fields":[
  {"name":"id","type":"Int64","primaryKey":true},
  {"name":"vector","type":"FloatVector", ...}
]}}
```


### Expected Behavior


Return a non-success response (HTTP 4xx, or HTTP 200 with `code != 0`) with a clear error message such as:

> `invalid vectorFieldType: "InvalidVectorType"; supported types: [FloatVector, BinaryVector, Float16Vector, BFloat16Vector, SparseFloatVector]`

This is important because:
1. A client typo (`"FloatVecotr"`, `"InvalidVectorType"`, etc.) currently creates a `FloatVector` collection without any warning.
2. Users intending a sparse/binary/half-precision vector collection who typo the type silently get a `FloatVector` collection, which:
   - consumes more memory than intended (e.g. wanted `BinaryVector` for compact storage),
   - breaks downstream code that assumes the requested element type,
   - produces confusing search results because the metric type may be wrong for the actual stored type.
3. Other enum fields (e.g. `idType`) **do** get rejected — the behavior is inconsistent across enum fields.


### Steps To Reproduce

```markdown
1. Start Milvus v2.6.19 (standalone, Docker):
   
   docker run -d --name milvus-standalone -p 19530:19530 milvusdb/milvus:v2.6.19 standalone
   
2. Create a collection with an invalid `vectorFieldType`:
   
   curl -s -X POST http://localhost:19530/v2/vectordb/collections/create \
     -H "Content-Type: application/json" \
     -d '{"collectionName":"audit5","dimension":4,"metricType":"L2","idType":"Int64","autoID":true,"vectorFieldType":"InvalidVectorType"}'
   # -> {"code":0,"data":{}}    <- should have been rejected
   
3. Describe the collection and observe the substituted type:
   
   curl -s -X POST http://localhost:19530/v2/vectordb/collections/describe \
     -H "Content-Type: application/json" \
     -d '{"collectionName":"audit5"}'
   # -> {"code":0,"data":{"fields":[
   #       {"name":"id","type":"Int64","primaryKey":true},
   #       {"name":"vector","type":"FloatVector", ...}
   #    ]}}
   
4. (Contrast) `idType` correctly rejects invalid values:
   
   curl -s -X POST http://localhost:19530/v2/vectordb/collections/create \
     -H "Content-Type: application/json" \
     -d '{"collectionName":"x","dimension":4,"metricType":"L2","idType":"InvalidType","autoID":true,"vectorFieldType":"FloatVector"}'
   # -> {"code":1100,"message":"idType can only be [Int64, VarChar], default: Int64: invalid parameter..."}
```

### Milvus Log


REST layer only — no error/warning is emitted server-side because the request is treated as successful. Standalone container log around the create call shows a normal `CreateCollection` trace with no validation failure.

The REST handler appears to apply `FloatVector` as the default for any `vectorFieldType` value that fails to parse as a known vector type enum, rather than rejecting it.

### Anything else?


- Impact severity is low-to-medium (no data loss / no crash), but a real **validation gap**. The worst case: a user wanting `BinaryVector` (1 bit per dim, ~32× smaller for binary embeddings) who mistypes the type silently gets `FloatVector` (32-bit per dim), inflating memory ~32× and breaking their pipeline.
- Same root pattern as the `consistencyLevel` companion issue: the REST `CreateCollection` handler silently substitutes defaults for unparseable enum strings. Suggest a unified validation pass covering all enum-typed create parameters: `consistencyLevel`, `vectorFieldType`, and any others that currently fall back silently.
- Not a security issue (no injection / no privilege escalation), purely a robustness/validation concern.
