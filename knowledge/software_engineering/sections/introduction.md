# Writing a Good SE Introduction

## Core Principle
SE reviewers want practical impact. Lead with the problem's real-world significance.

## What Makes It Good
### Grounded Opening: Start with something developers/practitioners face. Use concrete numbers. Avoid generic openings.
### Specific Problem: Name the exact challenge. Show evidence it's real. Explain why existing solutions fall short.
### Clear Approach Preview: What's your key insight? How does it differ? Brief mention of what makes it work.
### Verifiable Contributions: Each maps to a section. Be specific. Include tool names if you built something.

## Language Patterns
**Opening with impact**: "Developers spend X% of their time doing Y...", "Bug type X accounts for Y% of security vulnerabilities..."
**Hook variants**: Dramatic ("Every week, another leak!"), Tension ("[Problem] silently compute an incorrect result")
**Gap statement (3-part)**: prior work → gap → consequence
**Transition to approach**: "To address this gap, we propose [TOOL], which..."
**Contribution**: "We present [TOOL], a technique/tool that...", "Our key insight is that..."
**Scope limitation**: "As a starting point, in this paper, we propose..."
**First-to-study**: "To the best of our knowledge, we are the first to systematically study..."

## Common Pitfalls
- Starting too broad ("Software engineering is important")
- No clear problem statement
- Contributions that sound like activities ("We study X")
- Missing related work context
