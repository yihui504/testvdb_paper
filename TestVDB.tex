\title[TestVDB: doc-implementation defects in VDBMSs]{TestVDB: Detecting Documentation-Implementation Defects in Vector Databases via LLM-Derived Behavioral Claims}

\author{Authors TBD}
\email{tbd@example.org}

\begin{abstract}
Vector Database Management Systems (VDBMSs) store the embeddings that retrieval-augmented Large Language Model (LLM) applications depend on, yet most of their defects are logical bugs that produce no crash and thus escape crash-oracle fuzzers such as VDBFuzz. We target \emph{documentation-implementation defects}: cases where a VDBMS silently accepts an input or produces a behavior that violates its API documentation, such as accepting \texttt{nprobe=0} when the documentation declares the range as $[1, 16384]$. These defects corrupt query semantics. Across 124 issues TestVDB surfaced, maintainers fixed 28 via merged PRs and acknowledged a further 17 as true-positive defects awaiting fixes (63\% adjudicated yield over the 71 adjudicated submissions). Because the boundary is natural-language prose, no deterministic-oracle candidate derives its expectation from documentation---crash signals, reference implementations, output relations, and schemas all fall structurally short---leaving an LLM as the practical oracle. We instantiate TestVDB, a four-stage pipeline (claim extraction, test generation, execution, confirmation) that uses LLMs to read documentation, generate tests, and adjudicate responses. Putting an LLM in both the extraction and the judgment role creates a false-positive problem; a three-arm controlled experiment on 71 maintainer-adjudicated candidates shows that judgment architecture alone cannot fix it: a multi-judge cascade suppresses false positives but pays the full recall price, while a \emph{dev-reviewer} agent---a source-grounded falsifier that reproduces each candidate, cross-checks it against implementation source, and tries to disprove it---reaches 69\% recall at 86\% precision, and the tool-versus-architecture gap is statistically significant where the architecture-versus-architecture gap is not. On the same candidates, the confirmation stage over hand-authored probes reaches 93\% recall, bounding end-to-end capability from above. All results use a single LLM backbone (GLM-5.2). A bidirectional probe against VDBFuzz on Qdrant shows TestVDB reaches a crash-class defect by contract reasoning, while VDBFuzz misses a silent-accept defect under its current templates.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Vector Database Management Systems (VDBMSs) store the embeddings that retrieval-augmented LLM applications depend on. Their defects are costly. An empirical bug study~\cite{bugstudy25} finds that more than half of VDBMS bugs manifest as functional failures, and the VDBMS testing roadmap~\cite{roadmap25} attributes about 43\% of VDBMS bugs to incorrect behavior and identifies oracle definition as a key challenge. The existing dedicated VDBMS fuzzer, VDBFuzz~\cite{vdbfuzz26}, applies classical fuzzing~\cite{manes21} but detects only crashes, so the logical-bug majority goes unreached.

What does the unreached majority look like in practice? In the bug study's five-category symptom taxonomy, the dominant category is functional failure---the system does not crash but silently returns wrong results to the application---and its representative shape is a silent-accept defect: the system accepts an input or performs an operation it should have rejected, and the failure surfaces only in the query results returned to the application. In a retrieval-augmented LLM stack, this means the wrong context reaches the model: a disabled filter returns all matches, a zero-length vector corrupts an index, or a dropped partition hides data the application expects. The downstream model has no signal that its context is corrupted, so the error propagates into generated text without an error code to log. The absence of a crash is the wrong signal for this defect class, which is why an oracle that fires only on crashes (such as VDBFuzz) is structurally blind to it.

We target a prevalent subset of this unreached majority: \emph{documentation-implementation defects}, where a VDBMS silently accepts an input or produces a behavior that violates its API documentation. A representative case is Milvus issue~\#49823, which silently accepts \texttt{nprobe=0} although the documentation declares the parameter range as $[1, 16384]$. Such defects corrupt query semantics. They can return data the documentation intended to exclude (for example, a negative score threshold that disables a filter and returns all matches), and most produce no crash.

The oracle problem~\cite{barr15} is acute here. Every oracle compares observed behavior against an expectation, and the standard candidates anchor that expectation in crash signals, another implementation, output--output relations, or machine-checkable schemas---never in natural-language prose. Differential testing catches mathematical-invariant violations across vendors but cannot adjudicate which side the documentation blesses, since cross-vendor behavior diverges by design~\cite{roadmap25}. Metamorphic relations~\cite{metmap24} check relations the tester already knows to pose, and the existing VDBMS relations are result-correctness relations. Property-based testing~\cite{claessen00} needs a machine-checkable property, but the property here is the prose claim itself, and VDBMS endpoints rarely expose a schema encoding it. REST-API oracle tools~\cite{agoraplus25,satori25,mastor26} anchor expectations per-field in OpenAPI specs, traces, or source code---and a source-derived oracle encodes implemented behavior, so it cannot detect a documentation-code gap. We expand this exclusion argument in Section~\ref{sec:prelim} (Table~\ref{tab:exclusion}); the residual leaves an LLM as the practical oracle.

Putting an LLM in both the extraction role (documentation to behavioral claims) and the judgment role (response to verdict) creates a false-positive problem, whose root causes---hallucination in extraction~\cite{ji23hall} and self-preference in judgment~\cite{panickssery24}---we analyze as failure modes in the evaluation (Section~\ref{subsec:rq3}). The design consequence is a \emph{dev-reviewer} agent that acts as a source-grounded falsifier: it reproduces each candidate, cross-checks it against the implementation source, and tries to disprove it. A candidate that survives all three checks is adjudicated a defect; one that fails any check is suppressed.

We instantiate this as TestVDB, a four-stage pipeline (Section~\ref{sec:approach}): behavioral-claim extraction, test-script generation, sandboxed execution, and defect confirmation, with LLMs automating the documentation-reading, generation, and adjudication steps. TestVDB surfaced 124 candidate issues across three VDBMSs (Milvus, Qdrant, Weaviate) plus 2 fix PRs we authored; maintainers fixed 28 issues via merged PRs and acknowledged a further 17 as defects awaiting fixes. A three-arm controlled experiment on 71 maintainer-adjudicated candidates isolates what suppresses the false positives: architecture (a multi-judge cascade) or tools (source grounding and live re-execution); the dev-reviewer reaches 69\% recall at 86\% precision, and the architecture axis alone is not significantly different from a single LLM call. A bidirectional probe against VDBFuzz~\cite{vdbfuzz26} shows TestVDB reaches a crash-class defect (Qdrant integer overflow on \texttt{size}$=2^{63}$) by contract reasoning, while VDBFuzz misses a TestVDB silent-accept defect (\texttt{wait=false} accepting a zero-length vector, \#9045) under its current templates.

\paragraph{Contributions.}
\begin{itemize}
  \item \textbf{Documentation-implementation defects as a VDBMS target.} We characterize the defect class that VDBMS fuzzers miss, formalize it as consistency with natural-language documentation, and show by an oracle-exclusion argument (Section~\ref{sec:prelim}) why an LLM is the practical oracle for the residual.
  \item \textbf{TestVDB.} A four-stage pipeline that uses LLMs to extract behavioral claims from documentation, generate executable tests, run them on sandboxed VDBMSs, and confirm defects by comparing expected and actual behavior (Section~\ref{sec:approach}).
  \item \textbf{Source-grounded falsification.} We analyze the false-positive failure modes (extraction hallucination, judgment self-preference), and introduce a dev-reviewer agent that falsifies LLM verdicts against implementation source (Section~\ref{subsec:falsification}).
  \item \textbf{Evaluation.} 124 submitted issues with 45 maintainer-acknowledged true-positive defects (28 merged-PR-fixed, 17 acknowledged but unfixed) across three VDBMSs, re-verified in August 2026; a 93\% recall oracle upper bound from confirmation over hand-authored probes (RQ2); a three-arm experiment isolating tool access from judgment architecture, showing the source anchor is what lifts recall (69\% at 86\% precision) while architecture alone is not significant (RQ3); and a bidirectional probe against VDBFuzz that explores complementary coverage (Section~\ref{sec:eval}).
\end{itemize}

\section{Preliminaries}
\label{sec:prelim}

\subsection{Vector Database Management Systems}
\label{subsec:vdbms}

A Vector Database Management System (VDBMS) stores high-dimensional embedding vectors and serves similarity queries over them. Its core operations are vector insertion and upsert, approximate nearest neighbor (ANN) search, and payload-filtered retrieval, exposed through an HTTP/REST API whose parameters govern query behavior---for example, the probe count \texttt{nprobe}, the search width \texttt{ef}, or the result cap \texttt{limit}. Production VDBMSs such as Milvus, Qdrant, and Weaviate back retrieval-augmented LLM applications, where a defective query returns the wrong context to the model and the error propagates into generated text without any crash or error code to log.

\subsection{Documentation-Implementation Consistency}
\label{subsec:consistency}

We separate \emph{documentation-implementation consistency} from \emph{correctness}. Consistency asks whether the system's observable behavior---what it accepts, what it errors on, what it returns, and how its state evolves---matches what its API documentation prescribes. Correctness asks whether a returned result is mathematically right, such as ANN recall or ranking. TestVDB targets consistency; result correctness of vector search remains open and is not our claim~\cite{roadmap25}. A consistency defect arises when a VDBMS produces behavior its API documentation prescribes otherwise: silently accepting \texttt{nprobe=0} where the documentation declares the range as $[1, 16384]$, returning success for a duplicate create where the documentation prescribes an already-exists error, or returning deleted IDs in a search where the documentation prescribes exclusion. VDBMS API documentation, unlike the structured sources that REST-API oracle tools rely on (OpenAPI specifications, execution traces, or source code), is natural-language prose. Constraints are implicit and ambiguous: a parameter described as ``optional, default 1'' may or may not admit a zero, and the documentation rarely says. Every consistency check therefore needs an expectation of what the documentation prescribes, and deriving that expectation from prose is a semantic-interpretation step that deterministic oracles cannot perform; an LLM is the scalable proxy for it.

\subsection{The Oracle Problem}
\label{subsec:oracle}

The oracle problem~\cite{barr15} is acute on this consistency subset, and the cleanest way to see it is through \emph{where each oracle candidate gets its expectation}. Every oracle compares observed behavior against an expectation; the standard candidates anchor that expectation in crash signals, another implementation, output--output relations, machine-checkable properties, or structured specs---never in system-level prose. Table~\ref{tab:exclusion} walks the candidates and the structural reason each misses the documentation-implementation residual. Differential testing catches mathematical-invariant violations across vendors, but its expectation comes from another implementation, and cross-vendor behavior diverges by design~\cite{roadmap25}, so it cannot adjudicate which side the documentation blesses. Metamorphic relations~\cite{metmap24} check relations the tester already knows to pose; the existing VDBMS relations are result-correctness relations (top-$k$ monotonicity, recall versus \texttt{ef}), and deriving what relation the prose prescribes is itself the semantic step they do not perform. Property-based testing~\cite{claessen00} needs a machine-checkable property, and the property is exactly the prose claim; VDBMS endpoints serve no schema that encodes these constraints, and several serve no OpenAPI at all. REST-API oracle tools~\cite{agoraplus25,satori25,mastor26} anchor expectations in OpenAPI fields, execution traces, or source code under per-field structural anchoring---MASTOR, reading source, encodes implemented behavior and so cannot detect a gap between documentation and code. The residual leaves an LLM-derived oracle, with the expectation read from the prose, as the practical option. A prior line also derives oracles from documentation with LLMs~\cite{toradocu16,augmentest25}, but keeps the LLM as the final arbiter by validating only through runtime behavior; TestVDB instead falsifies against implementation source (Section~\ref{subsec:falsification}). The reliability problem this introduces is analyzed as root causes in Section~\ref{sec:eval}.

\section{Approach}
\label{sec:approach}

\subsection{Overview}
\label{subsec:overview}

TestVDB instantiates documentation-implementation consistency testing as a four-stage pipeline---behavioral-claim extraction, test-script generation, sandboxed execution, and defect confirmation---followed by source-grounded falsification (the dev-reviewer, Section~\ref{subsec:falsification}) that suppresses the false positives the LLM-in-the-loop introduces, with LLMs automating the documentation-reading, generation, and adjudication steps. A novelty gate finally removes duplicates and known issues. Figure~\ref{fig:pipeline} sketches the pipeline.

\subsection{Behavioral-Claim Extraction}
\label{subsec:extraction}

The contract-formalizer agent reads the VDBMS API documentation and emits structured behavioral claims as a JSON contract. Each claim records a \texttt{constraint\_id}, the endpoint, the assertion (for example, \texttt{nprobe} $\in [1, \texttt{nlist}]$), and a source pointer into the documentation. The LLM performs the semantic interpretation that deterministic oracles cannot, translating ``optional, default 1'' into a checkable clause.

\subsection{Test-Script Generation}
\label{subsec:generation}

Attack agents turn each claim into an executable probe. For a claim asserting the API rejects \texttt{nprobe=0}, the agent generates a request carrying the boundary value and a control value, plus any setup the endpoint needs (collection creation, indexing, payload insertion). Scripts target the boundary so that an accept where the documentation prescribes reject is observable in the response.

\subsection{Sandboxed Execution}
\label{subsec:execution}

TestVDB runs each script against a Docker-pinned VDBMS instance (Milvus 2.6.19, Qdrant v1.18.2, Weaviate v1.38.2 in our study). Raw HTTP requests and responses are logged for downstream inspection. The sandbox isolates runs so a candidate reproduces under a clean probe, free of tooling artifacts.

\subsection{Defect Confirmation}
\label{subsec:confirmation}

A judge agent compares the documented expectation (the claim) against the actual response, the VDBMS state, and the logs. A response that accepts a value the documentation prescribes rejecting becomes a candidate defect. The LLM also adjudicates this step, which introduces the false-positive problem we analyze as root causes in Section~\ref{subsec:rq3}.

\paragraph{Example: the \#49823 path.}
Milvus documents \texttt{nprobe} as an integer in $[1, 16384]$. The contract-formalizer extracts the claim \texttt{nprobe}~$\in [1, 16384]$ from the documentation passage. An attack agent generates a probe that issues \texttt{entities/search} with \texttt{nprobe=0} and a control with \texttt{nprobe=1}. On Milvus 2.6.19 the \texttt{nprobe=0} request returns HTTP 200 with results, while the documentation prescribes rejection. The judge agent flags a documentation-implementation violation, and the dev-reviewer verifies that the implementation accepts the value by reading the search-parameter handler in source, which performs no range check on \texttt{nprobe}.

\subsection{Source-Grounded Falsification}
\label{subsec:falsification}

The dev-reviewer agent is a source-grounded falsifier. It acts as a VDBMS maintainer would: reproduce each candidate under a clean probe, cross-check it against the implementation source, and try to disprove it. A candidate that survives all three checks is adjudicated a defect; one that fails any check is suppressed as a false positive.

\paragraph{Three checks.}
For each candidate, the dev-reviewer applies:
\begin{enumerate}
  \item \emph{Independently reproducible.} Does the candidate reproduce under a clean probe, free of tooling artifacts? The dev-reviewer rebuilds a minimal request from the contract and the raw evidence, rather than copying the original probe, and runs it on the live VDBMS.
  \item \emph{Evidence sufficient.} Do the response, the VDBMS state, and the source code jointly establish the documentation-implementation gap? The dev-reviewer cross-checks the response through an independent channel (a primary-key read, a scroll, a count) so the gap does not depend on a single field the request failed to request.
  \item \emph{Falsifiable.} Can the candidate be disproven by an alternative documented interpretation, such as a by-design behavior or a wont-fix pattern? The dev-reviewer reads the implementation source to check whether the ``violation'' is an intentional default, an idempotent return, or a maintainer-acknowledged design choice.
\end{enumerate}

\paragraph{Three anchors.}
The checks draw on three evidence anchors. A \emph{clean-reproduction} anchor re-probes the live API to filter tooling-artifact false positives. A \emph{source-grounded} anchor (the primary falsifier) reads the implementation source across the full clone, tracing constants and call chains, to check whether the constraint is real and whether the source implements it. An optional \emph{threat-model} anchor compares the candidate against maintainer-acknowledged by-design and wont-fix patterns; for example, idempotent deletes of a nonexistent resource that return success rather than an error, which TestVDB flags but maintainers often classify as intended, and the anchor is unstable on state and concurrency false positives where the source behavior is timing-dependent. The same LLM family produces both the behavioral claims and the verdicts; the implementation, an independent information source, is what falsifies them.

\paragraph{Example: the \#9255 reversal.}
Qdrant issue \#9255, a payload-filter false positive, illustrates falsification in action. The original oracle flagged a search returning points whose \texttt{payload} appeared absent as a filter violation, but the raw request had not set \texttt{with\_payload=true}, so the absence was a projection artifact rather than a stored-data gap. The dev-reviewer rebuilt the request with \texttt{with\_payload=true} and confirmed every returned point carried the filtered field; the candidate was suppressed as a false positive whose root cause was \texttt{assertion\_depends\_on\_unrequested\_field}. This is the failure mode the multi-perspective panel misses, because every judge agent reads the same response and none re-issues the request.

The dev-reviewer is not a second extractor that reads the documentation again. It reads the source, where the actual behavior is defined, and uses the contract only as the assertion under test. This separation is what breaks self-preference: the falsifier's ground truth is the implementation, not the same family's prior claim.

\subsection{Multi-Agent Implementation}
\label{subsec:multiagent}

TestVDB runs as a multi-agent pipeline~\cite{hou23llmse} on the Claude Code runtime, with each agent defined by a task-structured role prompt and dispatched to a GLM-5.2 backbone under default sampling. The agents span five stage-aligned roles: a contract-formalizer that reads documentation and emits structured JSON claims; four attack agents (boundary, semantic, state, discovery) that generate probes from claims; a judge-agent quartet (documentation, evidence, severity, novelty) that triages candidates; the dev-reviewer that falsifies against source; and a reporter that assembles defect reports. Each agent operates independently. For source-grounded falsification, TestVDB clones each target's source at the pinned version (\texttt{milvus-src}~v2.6.19, \texttt{qdrant-src}~v1.18.2, \texttt{weaviate-src}~v1.38.2); the dev-reviewer greps the clone to trace constants and call chains, and the clone is the only ground truth for what the implementation does. Wall-clock per target is dominated by source-grounding and live Docker re-probes rather than raw LLM latency; a full run is on the order of $10^4$ LLM calls and roughly $\$10$ per target at current API pricing. Roughly half of the calls are dev-reviewer source-grounding steps (the dominant wall-clock cost), a quarter are claim extraction and test generation, and the rest are judging and the novelty gate (Table~\ref{tab:cost}).

\section{Evaluation}
\label{sec:eval}

\subsection{Experimental Methodology}
\label{subsec:methodology}

We evaluate TestVDB on three production VDBMSs---Milvus 2.6.19, Qdrant v1.18.2, and Weaviate v1.38.2---pinned via Docker, with each target's source cloned at the pinned version for the dev-reviewer (Section~\ref{subsec:falsification}). All agents run on a GLM-5.2 backbone under default sampling. Ground truth comes from maintainer adjudication: we submitted 124 candidate issues plus 2 fix PRs and re-verified every submission's current state (labels, closing comments, and merged-PR cross-references) in August 2026 (Section~\ref{subsec:rq1}). For detection capability (RQ2) we re-probe the 71 maintainer-adjudicated candidates on their originally reported versions and adjudicate the evidence with the confirmation stage alone, yielding an oracle upper bound; the complementary forward-mining measurement is in progress and its slot is left open here. For false-positive suppression (RQ3) the same 71 candidates, frozen into leak-audited materials packages, are judged by three arms---single-LLM, multi-judge voting, and the source-grounded dev-reviewer---each for three rounds (Section~\ref{subsec:rq3}). We report yield precision for RQ1, recall/precision with Wilson 95\% confidence intervals for RQ2, and recall/precision/false-positive rate for RQ3. We ask four questions:
\begin{description}
  \item[RQ1 (mining yield):] how many documentation-implementation defects does TestVDB surface in real-world VDBMSs, as hard maintainer-adjudicated numbers?
  \item[RQ2 (detection capability):] when a candidate defect is reproduced as a standalone behavioral probe, how reliably does the confirmation stage adjudicate it---and where does the residual loss sit?
  \item[RQ3 (false-positive suppression):] why does putting an LLM in both the extraction and the judgment role create false positives, and how much of the suppression comes from the judgment architecture versus the tool access (source grounding, live re-execution) of the dev-reviewer?
  \item[RQ4 (comparison with VDBFuzz):] how many defects detected by TestVDB can the existing crash-oracle approach reach, and vice versa?
\end{description}

\subsection{RQ1: Mining Yield}
\label{subsec:rq1}
TestVDB has surfaced 126 submissions across the three systems---124 candidate issues plus 2 fix PRs we authored. We re-verified every submission's current state (labels, maintainer comments, closing events, and PR cross-references) in August 2026, so the numbers below reflect the latest maintainer adjudication rather than a historical snapshot. Maintainers fixed 28 issues via merged PRs (Milvus 12, Qdrant 8, Weaviate 8), each confirmed by a cross-referenced PR; 17 further issues are acknowledged but unfixed (8 open with an accepted label, 6 maintainer-closed without a merged PR, and 3 closed as duplicates of acknowledged issues); and 26 are maintainer-adjudicated false positives (16 by-design, 8 refuted in maintainer comments, 2 unreproducible). The remaining 53 submissions are unadjudicated (26 open pending, 25 self-closed, 1 stale-closed, 1 open unlabeled). Of the 71 maintainer-adjudicated submissions (45 true-positive, 26 false-positive), the yield precision is 63.4\% (Wilson 95\% CI $[51.8\%, 73.6\%]$); treating all 53 unadjudicated submissions as false positives gives a worst-case bound of 35.7\% (Wilson 95\% CI $[27.9\%, 44.4\%]$). The 28 merged-PR fixes across three production VDBMSs---including one crash fix (Qdrant \#9520, missing upper-bound validation on \texttt{shard\_number})---show practical impact. Table~\ref{tab:yield} breaks the yield down by vendor. The yield is biased toward documentation-implementation defects by the tool's design (Section~\ref{sec:limit}); the proportion reflects our yield, not a population estimate, and detection capability is quantified separately on a controlled set in RQ2. The vendor distribution reflects documentation style: Milvus (29 TP of 61 submitted) concentrates defects in optional-default parameters (\texttt{nprobe}, \texttt{ef}, \texttt{level}) where documentation omits explicit bounds; Qdrant (8 of 33) in search and collection parameters (\texttt{hnsw\_ef}, \texttt{shard\_number}) and state operations (\texttt{wait=false}); Weaviate (8 of 30) in schema validation of collection and vector-index configuration (\texttt{desiredCount}, \texttt{replicationFactor}, \texttt{vectorIndexConfig}). This mirrors the pattern in Section~\ref{subsec:rq3}: ambiguous defaults invite over-formalization, while explicit error conditions are uniformly over-formalized.

\subsection{RQ2: Detection Capability}
\label{subsec:rq2}

RQ1's yield precision bounds detection capability only indirectly: it treats all 53 unadjudicated submissions as false positives to obtain a worst-case bound. We now measure detection capability directly on a controlled set with known ground truth. Because the measurement requires separating the confirmation stage from the generation stage, we report it in two parts: an upper bound here, from confirmation over hand-authored probes, and the end-to-end forward measurement (generation plus confirmation over the same ground truth) that is in progress.

\paragraph{Controlled set and procedure.}
The controlled set is the 71 maintainer-adjudicated submissions of RQ1 (45 true defects, 26 false positives; all three vendors). For each candidate we run the confirmation stage in isolation: (i)~an issue-specific probe reproduces the reported behavior on the DB version where it was originally reported, pinned via Docker; (ii)~a mechanical gate flags execution failures and self-contradicting observations; and (iii)~GLM-5.2 adjudicates the surviving evidence in a single blind pass, sanitized of all ground-truth signals (maintainer labels and stances, duplicate relations, issue text). The probes are reproduction scripts authored from each report, not tests the tool generates---this isolates the oracle stage (does the judge correctly read reproduction evidence, free of extraction noise?) from the extraction stage evaluated in RQ1, and makes the result an upper bound on end-to-end capability: whatever the confirmation stage achieves here, the pipeline can only lose at the generation stage.

\paragraph{Oracle upper bound.}
TestVDB's confirmation logic confirms 42 of the 45 true defects (recall \textbf{93.3\%}, Wilson 95\% CI $[82.1\%, 97.7\%]$), at precision \textbf{79.2\%} $[66.5\%, 88.0\%]$ on the scored set, and suppresses 15 of the 26 maintainer-adjudicated false positives (57.7\% $[38.9\%, 74.5\%]$). The capability is vendor-asymmetric: per-vendor recall is Milvus 28/29 (96.6\%), Qdrant 6/8 (75.0\%), Weaviate 8/8 (100\%); FP-suppression is Qdrant 9/10 and Weaviate 2/2 but Milvus only 4/14---the gap we analyze in RQ3 as contract ambiguity rather than judge noise. As a triage signal on the 53 unadjudicated submissions, the pipeline flags 34 as confirmed defects and 19 as false positives; these are not scored (no ground truth).

\paragraph{Where the residual loss sits.}
The three recall misses are all probe-trigger failures, not judgment errors: \#47635 is a load-to-search race that needs a distributed deployment for a reliable window; \#9045 is a server panic whose trigger lies in the distributed/sharded search path rather than the standalone upsert we probe; and \#9149 is a ground-truth annotation issue---the validation it reports as missing is present on its stated versions. Conversely, every candidate for which the probe produced positive evidence was confirmed: the judge layer scores 42/42 on probed-true candidates. The upper bound is therefore a lower bound on the confirmation stage itself, and its entire loss is attributable to probe coverage of non-deterministic and distributed behaviors. The open question---how much of the 93.3\% survives when the probes are not hand-authored but generated by TestVDB's forward pipeline---is the forward-mining measurement we leave open.


\subsection{RQ3: False-Positive Suppression}
\label{subsec:rq3}

Putting an LLM in both the extraction role and the judgment role creates a false-positive problem with two failure modes whose root causes we diagnose before quantifying suppression.

\paragraph{Root cause: hallucination in extraction.}
When the contract-formalizer reads ambiguous documentation, it sometimes emits a constraint stronger than the documentation states. A parameter documented as ``optional, default 1'' becomes ``must be at least 1,'' or a parameter whose documentation illustrates a power-of-two value becomes ``must be a power of two.'' Both reject values the documentation allows, so the boundary test reports a violation that is not a defect. This is the test-oracle instance of LLM hallucination~\cite{ji23hall}: the model supplies a plausible constraint the input does not support.

\paragraph{Root cause: self-preference in judgment.}
When the same LLM family extracts a claim and later judges whether the response conforms, the two roles share biases, and the judge agent tends to confirm the extractor's claim~\cite{panickssery24,wataoka24}. Two mechanisms drive this bias: self-recognition (a model recognizes its own family's outputs~\cite{panickssery24}) and perplexity-based familiarity (a model favors lower-perplexity text, which its own outputs tend to be~\cite{wataoka24}); both predict over-confirmation of same-family claims. Self-preference compounds hallucination: an over-strict extracted claim is more likely to be confirmed by a judge agent of the same family.

The two modes point to the design question the experiment answers: does replacing the single judge with a multi-judge architecture suppress these false positives, or does suppression require an independent evidence channel? Both candidate fixes fail for the same structural reason if they share the judge's evidence base---any judge agent that reads the documentation shares the documentation's ambiguity, and a panel of them converges on the same over-strict claim.

\paragraph{Controlled set.}
The controlled set is the 71 maintainer-adjudicated submissions of RQ1: 45 true defects (28 fixed by merged PRs, 17 acknowledged unfixed) and 26 maintainer-adjudicated false positives (16 by-design, 8 comment-refuted, 2 unreproducible); all three vendors are covered (Milvus 43, Qdrant 18, Weaviate 10). For each candidate, an issue-specific probe reproduces the reported behavior on the DB version where it was originally reported, pinned via Docker; the probes are reproduction scripts authored from each report, not tests the tool generates, which isolates the oracle stage from the extraction stage evaluated in RQ1. The reproduction evidence is then frozen into a materials package that contains exactly the candidate's observed behavior (raw HTTP exchange and execution log) and its expected behavior (the matching contract constraints), with all ground-truth signals---labels, maintainer stances, duplicate relations, issue text---removed by a mechanical audit (zero violations across all leak channels). One candidate (Milvus~\#47635, the earliest report) has a placeholder log because its replay captured no raw HTTP; we keep it with the same materials face in all three arms.

\paragraph{Three arms.}
Each arm judges all 71 candidates under the GLM-5.2 backbone, three independent rounds, with the verdict decided by per-arm aggregation---a candidate counts as confirmed only if at least two of its three rounds adjudicate it CONFIRMED: (i)~\emph{single-LLM}: one pure call per candidate, the materials inlined verbatim, no tools of any kind; (ii)~\emph{multi-judge voting}: the four specialized judge agents (documentation, evidence, severity, novelty) under their as-shipped cascade aggregation, with documentation and novelty judges degraded to their network-disabled fallback paths (all documentation checks unverifiable; all novelty ratings unknown, which votes conservatively)---under this degradation the cascade reduces to the evidence judge as the sole substantive gate plus a crash-signal bypass; and (iii)~\emph{dev-reviewer}: the full source-grounded falsifier of Section~\ref{subsec:falsification} with source access, live re-execution, and maintainer-signal anchors. The arms hold the evidence constant---arm (i) and (ii) see exactly the frozen materials; arm (iii) additionally reaches the implementation, which is precisely the axis under test. Pre-registered expectation bands, judge prompts, and aggregation rules were frozen before any arm executed; round-to-run deviations and incidents (rate-limit interruptions, one late-arriving rewrite of ten single-LLM verdicts) are documented in the artifact.

\paragraph{Headline.}
Table~\ref{tab:arms} reports the three arms (per-arm 3-round majority). The dev-reviewer confirms 31 of 45 true defects (recall \textbf{68.9\%}, Wilson 95\% CI $[54.3\%, 80.5\%]$) at precision \textbf{86.1\%} $[71.3\%, 93.9\%]$ on the scored set, and suppresses 21 of the 26 false positives (false-positive rate \textbf{19.2\%} $[8.5\%, 37.9\%]$). The two tool-free arms reach the same recall (single-LLM 44.4\%, voting 37.8\%, median round values 42.2\% both) but sit at opposite ends of the false-positive axis: single-LLM forwards 23.1\% of the false positives (median round), while the voting cascade forwards only 11.5\%---the cascade trades recall for precision, moving along the trade-off rather than off it.

\paragraph{Architecture does not substitute for tools.}
Paired McNemar tests on the majority verdicts separate the two axes. Between the two tool-free arms, the difference is not significant (single-LLM exclusive hits 12, voting exclusive hits 7, $\chi^2{=}0.84$): no judgment architecture built on the same evidence reaches what the tools reach. Against the dev-reviewer, both tool-free arms are significantly dominated (single-LLM 6 vs.\ 17, $\chi^2{=}4.35$; voting 5 vs.\ 21, $\chi^2{=}8.65$), and the asymmetry is one-directional---the dev-reviewer exclusively confirms 12 true defects that both tool-free arms miss in all rounds (contract-consumption and structural-forensics classes, where confirmation requires reading the source or re-executing), while only 6 candidates go the other way (single-LLM exclusive hits concentrate in gray-zone false positives that the dev-reviewer itself drifts on). The evidence channel, not the judgment architecture, sets the recall ceiling: 8 strong-signal candidates (parameter-validation classes) are confirmed by all three arms, 6 are missed by all three (attitude- and materials-unreachable classes), and the 12 dev-reviewer-exclusive true defects are the tool increment made concrete. This is the experimental answer to the root-cause analysis: the panel does suppress false positives (11.5\% forwarded), but it pays the full recall price, and the suppression the dev-reviewer achieves comes from the evidence channel, not from judging harder on the same materials.

\paragraph{Variance is model-intrinsic, not architecture-induced.}
Round-to-round agreement (Cohen's $\kappa$) falls in the same 0.19--0.62 band for all three arms (single-LLM 0.29--0.45, voting 0.44--0.62, dev-reviewer 0.19--0.32), so neither removing tools (single-LLM) nor adding deterministic components (the voting cascade's crash bypass and code aggregation) removes the run variance; the deterministic components transmit bias (the cascade's confirmed count drifts monotonically 32$\to$21$\to$20 across rounds) rather than stabilizing judgment. Notably, the dev-reviewer has the \emph{lowest} inter-round $\kappa$ yet the best metrics---agent exploration variance is what buys the recall ceiling---which qualifies the common expectation that lower judgment variance implies better judgment quality.

\subsection{RQ4: Comparison with VDBFuzz}
\label{subsec:rq4}
We ran a bidirectional reachability probe between TestVDB and VDBFuzz~\cite{vdbfuzz26} on Qdrant (Table~\ref{tab:versions}). The systematic direction (a fixed-budget run, not an $n{=}1$ case) is VDBFuzz against TestVDB's pinned version: on Qdrant v1.18.2, where all eight of TestVDB's Qdrant merged-PR-fixed true positives are live, VDBFuzz (default configuration) ran over 26{,}000 mutated requests---the crash baseline on v1.18.2---and reached 0 of them. This is structural rather than a budget artifact: the eight are silent accepts that return HTTP 200, and a crash oracle cannot detect a non-crashing accept by construction. The two Qdrant crashes VDBFuzz reports in its own case study are also fixed in v1.18.2, so the run cleanly separates the two oracles' reach on this version. On the older Qdrant v1.4.0, where VDBFuzz's integer-overflow crash on a vector \texttt{size} of $2^{63}$ is still live, TestVDB's boundary probe reaches it as a documentation-implementation violation: the OpenAPI declares \texttt{size}~$\geq 1$ with no maximum, so the value is documented-valid yet the implementation panics. On Qdrant v1.18.0, where TestVDB's acknowledged empty-vector defect (\#9045, \texttt{wait=false} silently accepts a zero-length vector) is live, VDBFuzz's template suite reports no failure: every points-upsert template uses \texttt{wait=true} (the path that correctly rejects) and does not probe \texttt{wait=false}. We read the reverse direction as a limitation of VDBFuzz's current templates and input coverage, not a property of crash oracles as a class. The two controlled cases below are $n{=}1$ each and isolate the mechanism on crash-class defects; the systematic direction above (26{,}000 requests, 0 of eight silent-accept true positives reached) is the generalizable one.

The \#9045 root cause shows why the residual survives crash-focused patching: vector validation runs only under a \texttt{debug\_assert} that release builds skip, so \texttt{wait=false} accepts a zero-length vector while \texttt{wait=true} rejects it. The resulting panic (\#7967) survived three crash-fix iterations across v1.16.3--v1.18.0 until an API-level check independent of \texttt{wait} resolved it; a crash oracle would flag the panic once triggered, but the silent-accept residual on \texttt{wait=false} stays out of reach.

\subsection{Portability beyond VDBMSs}
\label{subsec:portability}

The consistency-testing regime is not specific to VDBMSs: any system whose documentation is natural-language prose rather than a structured specification enters it, including REST APIs without OpenAPI coverage, configuration validation, and policy-as-code checks. To probe portability, we ran the pipeline on Apache CouchDB~3.4.3 (all three gaps reproduced on 3.5.2; the \texttt{limit}-handling code is byte-identical in the 3.5.x source) and Elasticsearch~8.11.0. Elasticsearch rejected every invalid probe with a 400 error. CouchDB's \texttt{/\_all\_docs} behaved the same, but its \texttt{/\_changes} feed exposed three input-validation gaps: \texttt{limit=0} returns zero rows although the docs state ``the same effect as 1''; non-numeric \texttt{limit} returns HTTP 500 (\texttt{badarg}) rather than the 400 that \texttt{/\_all\_docs} returns; and \texttt{limit=-1} is silently accepted as unlimited. Two of the three gaps were submitted to the CouchDB maintainers (apache/couchdb \#6087, \#6088) and acknowledged as bugs (labeled \texttt{bug}, closed within one day), confirming genuine documentation-implementation defects rather than by-design behavior. The gaps concentrate where the contract is a prose remark rather than a schema-enforced bound---the same regime behind the 45 maintainer-acknowledged VDBMS defects. We claim transferability only to structurally similar documentation regimes, namely those whose constraints live in prose rather than a machine-checkable schema, and whose defect checks are behavioral-conformance decisions rather than result-correctness relations; this probe is preliminary rather than a generalization result.

\section{Limitations}
\label{sec:limit}

\paragraph{Threats to validity.}
\emph{Internal validity.} The three-arm experiment measures round-to-run variance directly: inter-round agreement (Cohen's $\kappa$) falls in the same 0.19--0.62 band for all three arms, so per-arm majority voting over three rounds is the aggregation we match to this variance. Pre-registered expectation bands, judge prompts, and aggregation rules were frozen before any arm executed; execution incidents (rate-limit interruptions, one late-arriving rewrite of ten single-LLM verdicts) are documented in the artifact. One candidate has contested ground truth between two internal adjudication passes; we adopt the adjudication used in RQ1 throughout, and the contested case is judged FALSE\_POSITIVE by all arms under either adjudication. The controlled set is maintainer-adjudicated but non-random, and we did not pre-register the candidate set; a capture-recapture or unbiased defect-sample estimation is future work.

\emph{External validity.} The controlled set covers all three vendors but is dominated by Milvus (43 of 71); per-vendor recall is not a headline for any vendor. Result correctness of vector search (ANN recall, ranking) is out of scope. Transfer to documentation regimes beyond VDBMSs (REST APIs without OpenAPI, configuration validation, policy-as-code) is claimed on structural grounds only and is not empirically tested beyond the CouchDB probe of Section~\ref{subsec:portability}.

\emph{Construct validity.} All results use a single LLM family (GLM-5.2), so we cannot claim cross-family robustness; generalization to other backbones is untested and future work. The frozen materials' \emph{expected-behavior} field quotes the reporter's normative phrasing (e.g., ``should error'') rather than the documentation verbatim; this frames the C-group (false-positive) candidates toward confirmation, so precision and false-positive suppression are optimistic estimates, while the recall headline (whose ground-truth framing agrees with the expectation direction) is unaffected. The same framing prevents separating the Milvus FP gap of RQ2 from contract ambiguity: both mechanisms act on the same candidates. A secondary leak channel (probe case descriptions entering the observation verbatim) was removed by the mechanical materials audit, which reports zero violations across all leak channels. We do not estimate recall against a defect census because no public ground-truth defect catalog for VDBMSs exists. The implementation-as-correct assumption bounds the approach: an implementation bug can wrongly falsify a clause whose documentation is right. In practice, 28 of the 45 true positives are fixed via merged PRs and the remaining 17 are acknowledged but unfixed---implementation confirmed buggy by maintainers---and no false positive was traced to an implementation bug, so the assumption produced no observed false negatives in the retrospective.

Beyond these validity threats, two further limitations bound the approach. Source-grounded falsification requires source, so it does not transfer to closed-source VDBMSs, and it treats the implementation as correct, so an implementation bug can wrongly falsify a clause whose documentation is right. The 28 merged-PR fixes suggest the implementation-as-correct assumption holds often enough to be useful, without guarantee. We did not observe maintainer-rejected confirmed TPs where the documentation itself was wrong; such cases would surface as false negatives of the dev-reviewer and are most likely where a maintainer closes a confirmed candidate as wont-fix without a source-level explanation. We did not quantify this false-negative rate, which would require a ground-truth catalog of documentation errors that does not exist for VDBMSs.

Our 124-submission yield is biased by the tool's design toward documentation-implementation defects, so the proportion we observe is not an estimate of the distribution in VDBMSs at large. A full-space estimation with capture-recapture or an unbiased defect sample is future work.

\section{Related Work}
\label{sec:related}

\paragraph{VDBMS testing.}
VDBFuzz~\cite{vdbfuzz26} is the first dedicated VDBMS fuzzer and uses crash as its oracle. Its template-based input mutation and crash detection reach exactly the crash-class subset that documentation-implementation defects, which silently accept rather than crash, escape; the bidirectional probe in Section~\ref{sec:eval} makes this complementarity concrete. The roadmap~\cite{roadmap25} sets the agenda we build on, identifying oracle definition as a key challenge for VDBMS testing and flagging differential testing as hard in this setting. The empirical bug study~\cite{bugstudy25} provides the taxonomy that motivates our focus on logical bugs, attributing more than half of VDBMS defects to functional failures rather than crashes.

\paragraph{REST-API oracle generation.}
A recent line derives test oracles for REST APIs from structured sources: AGORA+~\cite{agoraplus25} from execution traces, SATORI~\cite{satori25} from OpenAPI specifications, and MASTOR~\cite{mastor26} from source code. AGORA+ infers invariants from observed traffic and so cannot reach inputs the traffic did not exercise. SATORI uses an LLM to infer response-field oracles (e.g., enum values, length, range) from OpenAPI field names, types, and natural-language descriptions; its oracle catalog targets response-field properties, not behavioral conformance to system-level prose. MASTOR, the closest to this work, reads source to generate oracles that encode implemented behavior and so cannot detect a gap between documentation and code; TestVDB reads source as a falsifier of documentation-derived claims and targets exactly that gap. All three operate under per-field structural anchoring (OpenAPI fields, execution traces, or source) and target response-field or runtime properties; none derives its expectation from system-level prose. A concrete boundary: SATORI's oracle catalog (format, length, enum, range of response fields) is anchored on per-field OpenAPI properties, and documentation-derived behavioral expectations are outside its oracle target; VDBMS documentation constraints, in addition, live in system-level prose with no per-field schema to anchor on.

\paragraph{LLM-as-judge reliability.}
Self-preference bias, in which an LLM evaluator favors its own family's outputs, is established for general text evaluation~\cite{panickssery24,wataoka24}. Panickssery et al. show that self-recognition correlates with self-preference across model families, and we observe the analogous bias in the test-oracle pipeline, where the same family extracts a claim and later judges conformance. A separate reliability axis is intra-judge self-inconsistency: Haldar et al.~\cite{haldar25} show that a single LLM judge agent's ratings on the same input vary across runs, a sampling-noise phenomenon in the judgment step. Our false-positive problem intersects both, with hallucination at extraction~\cite{ji23hall} added: an LLM may stably produce a wrong claim across runs and families when the documentation is ambiguous. Source-grounded falsification mitigates all three by moving the ground truth from the LLM to the implementation.

\paragraph{Documentation-derived oracles.}
Toradocu~\cite{toradocu16} pioneered NL-documentation oracle extraction (Javadoc \texttt{@throws} via NLP), with acknowledged false positives. Doc2OracLL~\cite{doc2oracll25} extended this to LLMs; AugmenTest~\cite{augmentest25} infers oracles from available documentation; ChatAssert~\cite{chatassert24} repairs false positives via compilation/execution feedback; Testora~\cite{testora26} uses PR descriptions as a regression oracle ($\sim$55\% precision). All treat the LLM as the final semantic arbiter, verifying through runtime behavior; TestVDB instead falsifies against implementation source, targeting the ambiguous-prose regime Javadoc and OpenAPI extraction do not enter.

\section{Conclusion}
\label{sec:concl}

We target documentation-implementation defects in Vector Database Management Systems, where a VDBMS silently accepts inputs or produces behaviors that violate its API documentation. Because the documented boundary is natural-language prose, every deterministic-oracle candidate falls structurally short of deriving its expectation from documentation, leaving an LLM as the practical oracle. The LLM introduces a false-positive problem whose root causes multi-perspective judging cannot resolve, because the panel shares the documentation's ambiguity. Our dev-reviewer agent reads implementation source as an independent falsifier and breaks the failure modes. TestVDB surfaced 124 candidate issues across three VDBMSs with 45 maintainer-acknowledged true-positive defects (28 merged-PR-fixed); the confirmation stage over hand-authored probes reaches 93\% recall; and the three-arm experiment shows the source-grounded dev-reviewer reaches 69\% recall at 86\% precision where judgment architecture alone does not significantly differ from a single call. A bidirectional probe against VDBFuzz explores complementary coverage. The boundary we draw, between problems where structured-source extraction suffices and those where natural-language documentation forces LLM interpretation, marks where an LLM-derived oracle needs an independent falsifier.
